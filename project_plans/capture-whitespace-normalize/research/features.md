# Research: Android Share Capture Whitespace Normalization

## 1. Where normalization should live (confirmed code paths)

- `CaptureActivity.buildShareText()` (`androidApp/src/main/kotlin/dev/stapler/stelekit/CaptureActivity.kt:181-201`) is a `companion object` pure function — already unit-tested in isolation via `CaptureShareTextTest.kt` (12 tests, no Android framework mocking needed). Normalization should be applied to its return value, or inline within it, to stay testable the same way.
- `CaptureActivity.parseShareIntent()` (`CaptureActivity.kt:128-141`) is the actual ingestion point — it resolves `clipData` text via `coerceToText(this)`, `EXTRA_TEXT`, and `EXTRA_SUBJECT`, then calls `buildShareText()`. This is an `Activity` method (needs `Context` for `coerceToText`), so it's harder to unit-test directly than `buildShareText()` — the existing test suite tests `buildShareText()` only, not `parseShareIntent()`.
- Two call sites both currently do ad hoc `.trim()` after building the image-prefixed string (`CaptureActivity.kt:82`, `CaptureActivity.kt:120`) — `onCreate()` and `onNewIntent()`. Both call `parseShareIntent()` then branch on `imageLocalPath`. Whatever normalization function is added must be applied before/within `buildShareText()`/`parseShareIntent()` so it covers both call sites uniformly, not duplicated at each `.trim()` site.
- `CaptureViewModel.updateText()` (`CaptureViewModel.kt:42-44`) is the manual-typing path — direct passthrough, no processing. `CaptureViewModel.save()` (`CaptureViewModel.kt:53-54`) only does `.trim()`. Per the requirements' explicit scope decision, neither should be touched.

## 2. Real-world share payload artifacts (grounded, not guessed)

**Concrete mechanism specific to this codebase**: `parseShareIntent()` calls `intent.clipData?.getItemAt(0)?.coerceToText(this)`. Android's `ClipData.Item.coerceToText()` on an HTML-typed clip item runs it through `Html.fromHtml()`-equivalent HTML→Spanned conversion. Per HTML whitespace semantics, runs of literal spaces/tabs/newlines in source HTML collapse to a single space during that conversion — but `&nbsp;` entities decode to literal U+00A0 (non-breaking space) characters, which do **not** collapse. This means: any NBSP reaching this code path most likely arrived via HTML-sourced clipData (browser "Share" on a text selection, copy-from-webpage) where the source page used `&nbsp;` for layout spacing — a well-documented class of artifact (see Obsidian forum threads on NBSP surviving paste from Word/HTML: ["Fix irregular whitespaces"](https://forum.obsidian.md/t/fix-irregular-whitespaces/76270), ["Non-breaking space turn into code ONLY in LP"](https://forum.obsidian.md/t/non-breaking-space-turn-into-code-only-in-lp/41782)). This directly justifies the requirement's "normalize NBSP to regular space" line — it isn't a hypothetical, it's what `coerceToText()` is expected to hand back.
- **`EXTRA_TEXT`** (plain `String` extra, most common path — used by Reddit, X/Twitter, Gmail "Share" when no rich clipData is attached): source-app-controlled. Known patterns from Android share-intent bug reports/discussions found in search (general ACTION_SEND ecosystem, e.g. the long-standing [Facebook ACTION_SEND text-payload complaints](https://gist.github.com/tajchert/73422616624090851fa5)) is that apps commonly append boilerplate with double-newline separators (e.g. `"<tweet text>\n\n— via App Name https://t.co/xyz"`), and Reddit's own markdown source text uses **trailing double-space** for intentional line breaks (Reddit's markdown flavor) — a case explicitly worth preserving, not collapsing, since it's an intentional single line break represented by trailing spaces, not multiple blank lines.
- **`EXTRA_SUBJECT`**: typically a page title from Chrome/browsers — rarely has internal whitespace issues, but is joined with `\n` to the body in `buildShareText()`, so post-join blank-line collapsing must not eat that single separator newline (requirement: "collapse 3+ consecutive newlines to at most 2" — a single `title\nbody` join is already safe under that rule since it's only one newline).
- **Gmail**: signatures/quoted text often carry literal tab characters or multiple-space indentation from HTML-based mail bodies — reinforces the "collapse tabs and space-runs" requirement.
- Zero-width spaces (U+200B) were not identified as a distinct documented artifact for Android `ACTION_SEND` sources in the searches run; the requirements doc doesn't list them either. Worth flagging to the plan phase as a "may exist, not in scope per requirements text" edge case rather than silently adding handling for it.

## 3. Markdown-corruption risk: raw share text IS re-parsed as markdown later

This is the most important risk to flag to the plan phase.

- `CaptureViewModel.save()` builds a `Block` with `content = text` (the raw, only-`.trim()`'d share text) and writes it via `GraphWriter.savePage()` → `LogseqPageSerializer.serialize()` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/db/GraphWriter.kt:561-562`) directly to the `.md` file on disk, verbatim.
- On the **next graph load**, that markdown file is re-read and re-parsed by `MarkdownParser` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/parser/MarkdownParser.kt`), which recognizes fenced code blocks (`` ``` `` — `MarkdownParser.kt:82-83`, `CodeFenceBlockNode`/`rawContent`), tables (`MarkdownParser.kt:66-79`, pipe-delimited with alignment rows), and blockquotes. So **if a user shares text containing a code fence or table**, whitespace-collapsing at ingestion time is safe on the *first* write (share text isn't parsed as markdown before saving — it's just a content string), but if the block is later edited/re-parsed, internal-whitespace collapsing done at ingestion could have already destroyed significant leading whitespace inside what would become a code fence (e.g. indented Python inside a shared Stack Overflow snippet) or destroyed the `| --- |` alignment row of a table (space-sensitive only in that padding is cosmetic, but consecutive-space collapse inside a `key:: value` looking line, or `- ` list markers, matters more).
- Also relevant: `OutlinerPipeline.parseProperties()`/`stripProperties()` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/outliner/OutlinerPipeline.kt:39-79`) treats any line at the start of block content matching `^([a-zA-Z0-9_-]+)::\s*(.*)$` as a Logseq property (e.g. a shared line like `Time:: 3:45pm` would silently become a page/block property, not visible content). This is a **pre-existing** behavior unrelated to whitespace normalization, but worth flagging: normalization should not be the thing that *creates* a property-looking line by collapsing whitespace (e.g. collapsing `key ::  value` → `key:: value` is not something this feature proposes, so it's a non-issue, but it's adjacent enough that a reviewer might ask).
- **Conclusion for the plan phase**: collapsing consecutive spaces/tabs to one space and NBSP→space is safe for the vast majority of share payloads (tweets, article snippets, URLs, subject lines) which never contain code fences or tables. But the design should explicitly document (or the plan should decide) whether to special-case content that already contains a `` ``` `` fence marker or a `|...|` table-like line and skip internal-space collapsing for those cases — otherwise a user sharing a code snippet via Android share sheet will get it silently mangled. Given the requirements doc's explicit "Out of scope" section doesn't mention code/tables, this is a **gap worth surfacing**, not a blocker — most real share-sheet traffic (social media posts, article excerpts, URLs) has no code fences.

## 4. Existing whitespace/text-cleanup precedent in the codebase

No existing "collapse whitespace" utility exists anywhere in `androidApp/` or `kmp/src` — grepped for `trim(`, `replace(Regex`, `collapse` across both trees. Existing patterns are all narrow, single-purpose:

| Location | Pattern | Purpose |
|---|---|---|
| `CaptureActivity.kt:82,120` | `.trim()` | Outer whitespace only, post image-prefix join |
| `CaptureViewModel.kt:54` | `.trim()` | Outer whitespace only, pre-save |
| `parser/PropertiesParser.kt:17,32,64` | `line.trim()`, final `.trim()` | Per-line property parsing, not general text cleanup |
| `parser/TimestampParser.kt:46` | `Regex(...).replace(content, "").trim()` | Strips `SCHEDULED:`/`DEADLINE:` markers, then trims |
| `outliner/OutlinerPipeline.kt:44,48,67,78,94,113` | multiple `.trim()` calls | Per-line/per-token trimming during block/property parsing — never collapses internal whitespace |
| `androidApp/.../AudiobookNoteScreen.kt:124` | `.trim().split("\\s+".toRegex())` | Word-count only (splits on whitespace runs, doesn't rewrite the string) — this is the **closest existing precedent** for a `\s+` regex pattern in the codebase, though it's used for counting, not normalizing |

No shared/reusable "TextNormalizer" or similar utility exists. A new function is warranted; there's no existing convention to violate by adding one as a small standalone (e.g. companion-object function on `CaptureActivity` alongside `buildShareText`, or a small internal helper file) rather than reusing something.

## 5. Unstated user need / scope-boundary judgment call

The requirements doc explicitly scopes normalization to `buildShareText()`/`parseShareIntent()` only, **not** `updateText()`/`save()`, so manual typing is untouched. This research did not find a code-level reason to challenge that boundary — worth flagging two considerations to the plan phase rather than deciding unilaterally:

- **Argument for staying scoped to share-intent only (supports requirements as written)**: manual typing in the `OutlinedTextField` (`CaptureActivity.kt` `CaptureScreen`) is live, character-by-character input; a user who intentionally hits space twice (e.g. after a period, a long-standing personal typing habit) or pastes multi-line content on purpose would have their intent silently rewritten if normalization ran on every `updateText()` call. Share-intent text, by contrast, is app-generated/attacker-adjacent-formatting text the user didn't type themselves, so normalizing it doesn't touch anything the user typed live.
- **Argument for also covering manual paste-into-field (a gap the requirements doc doesn't address)**: a user can also long-press-paste share-sourced text (e.g. copied from Chrome, containing the same NBSP/multi-space artifacts) directly into the manual capture field without going through the Android share sheet at all — `updateText()` has no way to distinguish "typed" from "pasted" input, since Compose's `OutlinedTextField` `onValueChange` callback doesn't disambiguate. If the underlying complaint is "text from other apps looks messy in my journal," restricting the fix to share-intent-only leaves this paste path unaddressed. This is explicitly called out in the requirements as out of scope, so no code change is proposed here — flagging only so the plan phase can note it as a known follow-up rather than an oversight discovered later.
