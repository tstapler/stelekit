# Research: Whitespace-normalization pitfalls for Android share capture

Scope: `CaptureActivity.buildShareText()` (androidApp/src/main/kotlin/dev/stapler/stelekit/CaptureActivity.kt:186-201), the `[image: path]\n{text}` concatenation in `onCreate`/`onNewIntent` (lines 82, 120), and `CaptureViewModel.save()`'s `.trim()` (CaptureViewModel.kt:54). Test target: `androidApp/src/test/kotlin/dev/stapler/stelekit/CaptureShareTextTest.kt` (plain JUnit, no Robolectric — see `androidApp/src/test/` module).

## 1. Regex pitfalls

- **Catastrophic backtracking**: not a real risk at this scale. Share-sheet payloads are short (typically < a few KB — Android's `Intent.EXTRA_TEXT` has no hard size cap but share-sheet UX and the receiving app's clipboard/text-field context keep it small in practice). Simple non-nested quantifiers like `[ \t]+`, `\n{3,}`, `\p{Zs}` have linear worst-case time; there's no alternation-with-overlap or nested-quantifier pattern here that could exhibit ReDoS. Worth a one-line comment in the implementation ("no nested quantifiers — safe for arbitrary-length input") rather than a design concern.
- **"Collapse 3+ newlines to at most 2" and `\r\n`**: `\n{3,}` → `\n\n` only matches bare LF runs. If the source text contains `\r\n` (CRLF), a run of `\r\n\r\n\r\n` does **not** match `\n{3,}` as a contiguous newline run under a naive regex, because each `\r` sits between the `\n` characters — `\n{3,}` requires the LFs to be *adjacent*, and CRLF pairs break that adjacency. Concretely `"\r\n\r\n\r\n"` contains no substring of 3 consecutive `\n` characters, so a rule that only targets `\n{3,}` silently does nothing on CRLF-heavy input.
  - Android `Intent.EXTRA_TEXT` share payloads **can** contain `\r\n` — sources vary: text copied from a PDF viewer, some browsers' "share selection," or apps that build share text with `System.lineSeparator()` on a JVM boundary (rare on Android itself, `\n` is standard, but content pasted from Windows-authored documents/emails routed through another app's clipboard can retain `\r\n`). Given the feature explicitly targets share-sheet ingestion from arbitrary source apps, this is not a purely theoretical case.
  - Recommended fix: normalize line endings first — replace `\r\n` and lone `\r` with `\n` — **before** applying the newline-collapse regex. This must happen prior to (or combined with) the `\n{3,}` step, otherwise the collapse rule is silently ineffective on CRLF input. This is a second order-of-operations dependency beyond the NBSP one called out in the requirements — worth stating explicitly in the implementation, since the requirements doc only mentions NBSP-before-space-collapse.

## 2. Order-of-operations: NBSP before space-run collapse

Confirmed the order matters and reverse order is a real bug, not a theoretical one.

- If space-run collapse (`[ \t]+` → single space) runs **first**, then NBSP (` `) normalization runs second: a sequence like `"a   b"` (three consecutive NBSPs) is untouched by `[ \t]+` (NBSP is not `\t` or ASCII space), then each NBSP is independently replaced with a regular space, leaving `"a   b"` — three regular spaces, not collapsed. The output has un-collapsed whitespace, defeating the purpose.
- Correct order: normalize NBSP → regular space **first**, then run the space/tab collapse regex over the now-uniform whitespace. This is what the requirements state ("collapse runs of spaces/tabs, normalize non-breaking spaces... collapse 3+ consecutive newlines") but the prose lists collapse before NBSP-normalize — the *narrative* order in the requirements doc does not match the *required execution* order. Flag this explicitly in the implementation plan/code comment so whoever writes the code doesn't transliterate the requirements bullet order into the code's statement order.
- Newline-collapse and space/tab-collapse are independent (operate on disjoint character classes) and can run in either order relative to each other, but both must run **after** NBSP normalization if NBSP could plausibly appear adjacent to newlines or other NBSPs (it can — e.g. text copied from a web page with `&nbsp;` entities before a line break).

## 3. Markdown-content corruption risk (code fences / indented content)

This is a **real, non-theoretical risk** given how block content flows through this codebase, though the blast radius is narrow.

- `Block.content` (kmp/src/commonMain/kotlin/dev/stapler/stelekit/model/Models.kt) is a single opaque string per block. `CaptureViewModel.performSave()` (CaptureViewModel.kt:89-98) writes the entire captured text as the content of **one new block** — there is no splitting into multiple blocks/lines at capture time.
- When that page is later loaded through the normal graph pipeline, `MarkdownParser` (kmp/src/commonMain/kotlin/dev/stapler/stelekit/parser/MarkdownParser.kt) does recognize `CodeFenceBlockNode` and indentation-sensitive constructs (`block.indentLevel`, fenced code blocks with a `language`). If a user shares a multi-line code snippet via the share sheet (e.g. from a code viewer, terminal app, or GitHub mobile), and the whitespace-collapse regex runs indiscriminately over the *entire* shared string:
  - Leading indentation inside a code fence (e.g. 4-space Python indentation) would be collapsed to a single space by `[ \t]+`, silently breaking the snippet's semantics if it's later re-parsed as code.
  - This corruption happens **once**, at share-ingestion time, before the text is ever stored — it is irreversible; the original indentation is gone by the time `save()` runs.
- However, the actual risk of this being triggered in practice is moderate-to-low given the product surface: `CaptureActivity` is a bottom-sheet quick-capture overlay with a 3-8 line `OutlinedTextField` (CaptureActivity.kt:294-295, `minLines = 3, maxLines = 8`), positioned for short journal-style notes, not a code-paste destination. Still, nothing in the share-intent handling (`ACTION_SEND` from any app) prevents a user from sharing a longer code block from e.g. a GitHub/GitLab mobile client's "share file" action.
- Mitigation options worth considering (design decision, not mine to make): (a) skip normalization entirely if the text contains a fenced code block marker (three backticks) or looks like it has consistent multi-space leading indentation on ≥1 line; (b) accept the risk given requirements explicitly scope this to short share-sheet captures and explicitly exclude "auto-link/tag-suggest" and other markdown-aware features — normalization-vs-code-fence-awareness was not called out in scope either way, so this is a gap worth flagging back rather than silently resolving. Recommend surfacing this as an open question rather than deciding unilaterally, since the requirements' whitespace rules ("collapse runs of spaces/tabs") do not carve out an exception for fenced/indented content.

## 4. Trim interaction — no conflict, but confirm ordering intent

- `CaptureViewModel.save()` (CaptureViewModel.kt:54): `val text = _captureText.value.trim()`. This trims **outer** whitespace only (leading/trailing), on every save, regardless of whether the text originated from share-intent ingestion or manual typing.
- The new normalization step runs once, earlier, inside `buildShareText()`/`parseShareIntent()` (share-intent path only) and is expected to also handle *internal* whitespace (space runs, NBSP, blank-line collapse). It should very likely include its own outer-trim as part of producing clean output (e.ks. so the normalized text stored in `_captureText` via `initializeText()` doesn't carry leading/trailing blank lines into the visible text field before the user even starts editing).
- No double-work or conflict: `.trim()` in `save()` is idempotent — trimming an already-trimmed string is a no-op — so even if the normalization step also trims, calling `.trim()` again in `save()` is harmless. The two operations are not mutually exclusive; they run at different times (ingestion vs. save) and outer-trim is safe to apply redundantly.
- One thing to verify at implementation time: if normalization's internal blank-line collapse produces leading/trailing blank lines as a byproduct (e.g. collapsing `\n\n\n` at the very start of the string down to `\n\n` still leaves 2 leading newlines, not 0), those survive until `save()`'s `.trim()` removes them — but the on-screen text field will show them in the meantime, since `initializeText()` sets `_captureText.value` directly from the normalized share text without its own trim. Confirm whether the normalization function should end with a `.trim()` of its own so the *displayed* text (not just the saved text) doesn't show stray leading/trailing blank lines. This is a UX-visible edge case, not a data-integrity one.

## 5. The `[image: path]\n{text}` separator — blank-line collapse cannot eat it, but check the composition order

- `CaptureActivity.kt:82` and `:120`: `"[image: ${shareContent.imageLocalPath}]\n${shareContent.text}".trim()`.
- Requirements specify normalization applies to "the winning share text" inside `buildShareText()`/`parseShareIntent()` — i.e. to `shareContent.text` **before** it is concatenated with the `[image: ...]` marker line. Confirmed this ordering is safe: the single `\n` separator between `[image: path]` and the body is added *after* normalization has already run on `shareContent.text` alone, so the separator itself is never subject to the newline-collapse regex (which only sees the pre-concatenation body).
- The specific concern in the question — "does blank-line collapsing on `shareContent.text` alone (before concatenation) risk eating the `\n` separator if body starts with a blank line?" — does not apply as a corruption risk to the separator itself, because the separator is inserted by string-template concatenation, not part of the string that was normalized. What it *can* affect: if `shareContent.text` starts with one or more blank lines (e.g. `"\n\nSome shared text"`), the normalization's blank-line collapse (3+ → 2) only fires at 3+ consecutive newlines; 2 leading newlines pass through untouched, so the final concatenated string becomes `"[image: path]\n\n\nSome shared text"` (1 separator `\n` + 2 leading `\n` from the body) — three consecutive newlines, which is exactly what the normalization was supposed to prevent, except it can't see across the concatenation boundary because normalization already happened on `shareContent.text` alone, before the marker line was prepended.
  - This is a real, testable edge case: normalizing before concatenation cannot enforce the "≤2 consecutive newlines" invariant on the *final* stored string when an image marker is present, because the marker line's `\n` combines with the body's leading newlines to potentially exceed the limit after the fact. If the intent is "no visual double/triple gap in the saved block, ever," normalization would need to also run (or re-run) after the concatenation, or the concatenation itself needs to strip the body's leading blank lines before joining. Flag this back rather than silently deciding — requirements say "Apply once at share-intent ingestion (buildShareText()/parseShareIntent())," which as literally scoped does not cover the post-concatenation string, so under a literal reading this is out of scope, but it does mean the stated guarantee ("collapse 3+ consecutive newlines to at most 2") doesn't strictly hold for the final `[image: ...]\n{text}` block content when text has leading blank lines.

## 6. Locale/Unicode pitfalls beyond NBSP

Requirements explicitly scope normalization to NBSP (U+00A0) only. Other Unicode space-like code points that could plausibly appear in real share payloads:

- **U+2007 FIGURE SPACE**, **U+202F NARROW NO-BREAK SPACE**, **U+2009 THIN SPACE**, **U+2002/U+2003 EN/EM SPACE**: these appear in text copied from typeset sources — PDFs, some news sites, word processors, and certain locales' number formatting (e.g. French uses U+202F as a thousands/decimal separator space, which is common enough that French-locale share content could contain it).
- **U+2060 WORD JOINER** and other zero-width characters (U+200B ZERO WIDTH SPACE, U+FEFF BOM/ZWNBSP): these are *not* visible whitespace but can cause "why didn't this collapse" or "why is there an invisible gap" bug reports. They are categorically different from Zs-category normalization — U+2060 in particular is `\p{Cf}` (format character), not `\p{Zs}` (space separator), so a regex targeting `\p{Zs}` would not touch it, and that's probably correct (it's not whitespace, it's a joining control character, and removing it hides a signal from the original source rather than fixing whitespace).
- **Over-engineering risk assessment**: requirements say "normalize non-breaking spaces (U+00A0)" specifically, not a general Unicode-space sweep. Recommend following requirements literally (NBSP only) rather than expanding to `\p{Zs}`, for two concrete reasons:
  1. Scope creep risk — the requirements explicitly enumerate what to normalize; unilaterally broadening to all Unicode space separators is an undiscussed scope expansion into locale-sensitive territory (e.g. collapsing U+202F in French numeric text like "1 234,56" could alter meaning, not just cosmetic whitespace — thousands-separator spaces are semantically part of the number, not incidental whitespace).
  2. Testing risk (see §7 below) — `\p{Zs}` support has JVM/Android engine differences worth avoiding rather than routing around.
  - If broader normalization is later desired, it should be a separate, explicitly-scoped follow-up, not folded into this change silently.

## 7. Testing pitfall — `\p{Zs}` / `\s` and NBSP matching, plain JUnit vs. on-device

- `androidApp/src/test/kotlin/dev/stapler/stelekit/CaptureShareTextTest.kt` runs as a plain JVM JUnit test (no Robolectric, no Android runtime) — confirmed by the test file: it imports only `org.junit.Assert`/`org.junit.Test`, no `@RunWith(RobolectricTestRunner)`. It calls `CaptureActivity.buildShareText()` directly, a `companion object` pure function with no Android framework dependency (verified: `buildShareText` takes only `String?` params, does no `Context`/`Resources` calls) — this test class is already representative of "regex logic tested off-device," which is good — but any *new* regex-based normalization logic must remain equally framework-free to keep running here without Robolectric.
- **`java.util.regex` and Unicode properties**: Android's regex engine (via `java.util.regex.Pattern`, same API surface as desktop JVM, both ultimately ICU-influenced) supports `\p{Zs}` for Unicode "space separator" category, which does include U+00A0 NBSP — this is standard `java.util.regex.Pattern` behavior on both plain JVM (desktop, where `androidApp/src/test` unit tests actually execute — it's the *host* JVM, not the Android runtime) and on-device Android (which has its own regex implementation but a very similar public contract for Unicode categories, using ICU-based Unicode tables since API 24+).
  - Caveat: `\s` (the short-hand whitespace class) in `java.util.regex.Pattern` **without** `Pattern.UNICODE_CHARACTER_CLASS` set is ASCII-only by default (`[ \t\n\x0B\f\r]`) — it does **not** match NBSP. `\p{Zs}` is the correct explicit class to use for NBSP; do not rely on bare `\s` and assume it covers NBSP, on either desktop-JVM test execution or on-device Android.
  - Because `androidApp/src/test` unit tests run on the **host JVM** (Gradle's `testDebugUnitTest` task, not `connectedAndroidTest`), and `java.util.regex.Pattern`'s `\p{Zs}` behavior is standard-library, not Android-specific, this is one of the few areas where host-JVM test execution should reliably match on-device behavior — there is no known Android-vs-desktop regex engine divergence for `\p{Zs}` specifically. The bigger practical risk is a developer writing `\s` when they mean `\p{Zs}` (or vice versa) and having it silently pass basic-ASCII-only tests while failing on real NBSP input — so **test cases must include an explicit NBSP character** (`" "`), not just regular-space assertions, to catch this class of bug. The existing `CaptureShareTextTest.kt` has no such case yet — this is a concrete test-coverage gap to close per the requirements' "Add tests to CaptureShareTextTest" instruction.
  - Recommend using `Regex("\\u00A0")` (a literal NBSP match) rather than `\p{Zs}` for the NBSP-specific normalization step, since requirements scope this to NBSP only (see §6) — a literal-character regex is simpler, avoids any ambiguity about which other Zs-category characters get swept in, and sidesteps the `\p{Zs}`-vs-`\s` confusion entirely for this one substitution.

## Summary of concrete design/test requirements surfaced

1. Apply order: normalize line endings (`\r\n`/`\r` → `\n`) → normalize NBSP → collapse space/tab runs → collapse 3+ newlines → (optional) outer trim. NBSP-before-space-collapse and CRLF-before-newline-collapse are both hard ordering requirements, not stylistic choices.
2. `\n{3,}` alone misses CRLF-only newline runs — needs the line-ending normalization step first, which isn't explicitly called out in the requirements doc.
3. Code-fence/indented-content corruption is a real but narrow risk given the capture UI's short-note framing; not explicitly resolved by the requirements — worth flagging as an open question rather than silently deciding to skip or apply normalization inside code fences.
4. `.trim()` in `CaptureViewModel.save()` doesn't conflict with the new step (idempotent), but the normalization function should probably also end with its own trim so the *displayed* (not just saved) text has no stray leading/trailing blank lines.
5. Normalizing `shareContent.text` before concatenating the `[image: path]\n` marker means the "≤2 consecutive newlines" guarantee can still be violated in the final concatenated string if the body has leading blank lines — literally out of scope per the requirements' stated application point, but worth flagging.
6. Stick to NBSP only, per requirements — do not expand to `\p{Zs}`/other Unicode spaces; that's undiscussed scope creep with real semantic risk (e.g. French numeric narrow-no-break-space).
7. Use a literal ` ` match, not `\p{Zs}` or bare `\s`, for the NBSP step. Add an explicit NBSP test case to `CaptureShareTextTest.kt` — none exists today. `\p{Zs}` behavior on host-JVM unit tests is standard-library and should match on-device Android reliably if it were used, but literal-NBSP is simpler and sufficient for this scope.
