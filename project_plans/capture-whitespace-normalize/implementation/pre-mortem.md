# Pre-mortem: capture-whitespace-normalize
**Date**: 2026-08-10

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The plan's own accepted-risk gap — a lone space/tab between newlines (`"Para one\n \n \nPara two"`) — is *exactly* the motivating example in requirements.md ("repeated blank lines carried over from the source DOM/layout"), so the shipped fix does not close the case that justified the project. Users keep filing "still getting extra blank lines" after the fix ships. | A user reports stray blank-line runs from a browser share (empty `<p>`/`<div>` with whitespace text nodes) persisting after the release that claims to fix this. | Before implementation, either (a) reclassify AC3/the requirements' motivating example to explicitly exclude whitespace-only lines, getting sign-off that this is intentionally deferred, or (b) add a per-line horizontal-whitespace-strip step before the newline-collapse step (`\n[ \t]+\n` → `\n\n`) and a test for it, closing the gap the plan itself flags as unfixed. | P1 |
| 2 | The regex pipeline only normalizes literal NBSP (` `); real share payloads from HTML-derived clipboard/share text commonly carry other Unicode space variants (zero-width space U+200B, thin space U+2009, BOM U+FEFF, em/en space) that `[ \t]+` and the literal NBSP replace never touch, so "clean" journal entries still contain invisible/irregular whitespace for a meaningful fraction of real-world share sources. | A journal entry looks visually fine but search/matching or markdown rendering behaves oddly (invisible character), or a user pastes from a source (Google Docs, Slack, Twitter) whose share text still shows double-spacing after the fix. | Explicitly scope-check against 2-3 real share payloads from common apps (Chrome text-selection share, Twitter/X share, Slack share) before closing the story — if any contain non-NBSP Unicode spaces, decide in the plan (not post-hoc) whether to broaden matching or explicitly document as an accepted residual-risk with examples, rather than silently discovering it after ship. | P2 |
| 3 | Task 1.1.3b (CI wiring) is explicitly called out in the plan as having "no dependency" on the other tasks and can "land any time" — this makes it the easiest task to defer, split into a follow-up PR, or drop under time pressure, silently recreating the exact gap ("CI stays green if this test file is deleted") that an earlier adversarial review already caught once. | A future PR deletes or breaks `CaptureShareTextTest`/`CaptureViewModelTest` and CI's `android` job stays green — discovered only by manual code reading, not CI failure. | Require Task 1.1.3b to land in the *same PR* as 1.1.1a–1.1.3a (not a follow-up), and add an explicit merge/definition-of-done check: "PR is not ready to ship until `git diff` shows `:androidApp:testDebugUnitTest` present in ci.yml's android job command." | P2 |
| 4 | `buildShareText()` is unit-tested with hand-constructed strings, but the real production path is `parseShareIntent()` → `ClipData.Item.coerceToText()`, which performs Android's own HTML-to-text conversion (potentially inserting different whitespace patterns, e.g. multiple ` ` runs interspersed with real newlines from `<br>`/`<p>` tags) that the synthetic test fixtures may not replicate. The fix passes all 19 tests but the real share-intent flow on-device still produces mangled text for some source apps. | Bug reports continue after release specifically from users on real devices sharing from specific apps (browsers, Twitter), while all CI tests are green. | Before closing the story, capture 1-2 real `ClipData`/`EXTRA_TEXT` payloads from an actual device share (e.g. via a temporary log statement or adb) from a browser and one other app, and add them as literal test fixtures — not hand-typed approximations — so at least one test exercises what `coerceToText()` actually produces. | P2 |
| 5 | The accepted risk "code/markdown corruption" (leading indentation destroyed via blanket space-run collapsing) is rated "low probability" based on the capture UI's `minLines=3`/`maxLines=8` sizing, but that's a UI-affordance argument, not a measurement of what users actually share — a user who shares a code snippet or an indented list/quote via the same share sheet gets it silently corrupted with no opt-out, undo, or way to detect it happened. | A user complains their pasted code snippet or indented text lost its structure — likely reported as "capture ate my formatting" rather than connected to this change, so it may go unlinked to this fix for a while. | Add one test case with an indented code-like snippet (`"    def foo():\n        return 1"`) documenting the accepted behavior explicitly (even if the assertion is "yes, this is destroyed, and that's accepted"), so the corrosion is visible in test output rather than only in plan prose — makes the risk traceable if it needs revisiting later. | P3 |

## P1 Items (address before implementation)
- [ ] Failure #1 — Either narrow requirements.md's AC3/motivating-example language to explicitly exclude whitespace-only blank lines (with sign-off), or add a per-line horizontal-whitespace-strip step (`\n[ \t]+\n` → `\n\n`) before the `\n{3,}` collapse in Story 1.1.1's operation order, plus a corresponding test case, before starting Task 1.1.1a.
