## Test Stack

- **Unit**: `kotlin.test` (`@Test`, `assertEquals`/`assertTrue`/etc.) — the codebase does not use the Kotest Spec runner (see project `CLAUDE.md`). Android-specific unit tests (`androidUnitTest`) run under `@RunWith(RobolectricTestRunner::class) @Config(sdk = [29])`, matching `ShadowFileCacheTest.kt`'s existing pattern — this gives real `java.io.File` I/O against a Robolectric-provided `context.filesDir`, not a mock filesystem.
- **Integration**: same Robolectric harness, but exercising real JGit (`org.eclipse.jgit`) against the real shadow directory plus a `FakeExternalStorageProvider`-backed `FileSystem` fake standing in for SAF (per Task 8.2.1a) — this is "integration" in the sense of exercising two real subsystems (JGit + the shadow-worktree sync machinery) together, not mocked in isolation, while still running in a JVM unit-test process rather than on-device.
- **Manual/E2E**: Task 8.3.2a's real-device checklist — the only tier that touches an actual Android SAF provider, actual `MANAGE_EXTERNAL_STORAGE` permission states, and actual low-storage conditions; explicitly out of automated-suite scope per the plan.
- **Desktop non-regression**: plain `kotlin.test` under `jvmTest`, no Robolectric — `JvmGitRepositoryTest.kt` (Task 7.1.2a), plus the pre-existing `GitSyncServiceTest.kt`/`GitSyncServiceRateLimitRetryTest.kt` (`businessTest`, `StubGitRepository`-based) re-run as a regression gate (Task 7.1.2b).

## Coverage Targets

- Unit test coverage: ≥80% line coverage on all four new collaborators (`GitShadowWorktree`, `GitWriteBackQueue`, `GitShadowFlushActor`, and the shadow-mirror-specific branches added to `AndroidGitRepository`).
- Every public method on `GitShadowWorktree`/`GitWriteBackQueue`/`GitShadowFlushActor`: happy path + at least one error/edge path — **now true across the board**: the `StatFs` guard (Tasks 8.2.3a/8.2.3b) and SSH/HTTPS transport (Tasks 8.4.1b/8.4.1c) were the two gaps in this claim; both are closed (see the Gaps section below for the two remaining implementation-time-only unknowns on the transport tests, which do not affect this coverage claim itself).
- Every external integration (SAF, JGit, git remotes) has at least one integration-tier test: SAF — yes (`AndroidGitRepositoryShadowWorktreeTest.kt` via `FakeExternalStorageProvider`); JGit working-tree ops — yes (same file, real JGit); **git remotes (SSH/HTTPS/local-file) — yes, as of this update**: Task 8.4.1a (local `file://`), Task 8.4.1b (SSH, via an embedded `SshTestGitServer`), Task 8.4.1c (HTTPS with Basic auth, via an embedded `AppServer`/`GitServlet`) each exercise a real `clone()`→`commit()`→`fetch()`→`push()` round trip against a real embedded test server, confirmed against the *remote* bare repository's actual ref state, not just a non-error return. The manual device checklist (Task 8.3.2a) remains the only tier that reaches an actual on-device SAF provider, real `MANAGE_EXTERNAL_STORAGE` permission states, and real low-storage conditions — it is a complement to these automated tests, not a substitute any more.
- All three `DomainError.GitError` variants this project introduces (`WorkingTreeSyncFailed`, `WorkingTreeWriteBackFailed`, `WorkingTreeConcurrentEditDetected` — **correcting this document's earlier miscount of "four," which double-counted "the storage-guard error" as distinct from `WorkingTreeSyncFailed` when Task 6.2.1a's own text constructs the storage-guard failure as a `WorkingTreeSyncFailed` instance, not a fourth type**) now all have at least one test asserting the typed error is returned: `WorkingTreeConcurrentEditDetected` via 8.1.2b, `WorkingTreeSyncFailed` via 8.2.3a (storage guard), `WorkingTreeWriteBackFailed` via 8.1.2c (paired with the new production task, 3.1.2c, which specifies where this error is actually constructed — the original Phase 3 task list defined the error type in Task 0.1.2a and referenced it from Task 3.2.1b's caller-side handling, but never specified its construction site until now).

## Gaps — status after adding Phase 3/Phase 8 gap-closing tasks (this update)

The 7 gaps found by cross-referencing the original plan.md's Phase 8 are addressed below. Per the
user's explicit decision, closure means **new tasks now exist in plan.md**, not that manual QA was
substituted — but honest tracking requires calling out the two places where the new tasks
themselves carry an implementation-time unknown, rather than claiming those are settled too.

1. **SSH/HTTPS transport — closed, with two implementation-time unknowns flagged, not settled.**
   New Epic 8.4 (Story 8.4.1) adds three real end-to-end transport tests: Task 8.4.1a (local
   `file://`, via `org.eclipse.jgit.junit.LocalDiskRepositoryTestCase`/`TestRepository` — fully
   pinned down), Task 8.4.1b (SSH over `mwiede/jsch` against an embedded
   `org.eclipse.jgit.junit.ssh.SshTestGitServer` — constructor/`start()`/`stop()` signatures
   verified against JGit's published API this pass, but the exact on-disk key-file format its
   `testKey: Path` parameter expects was **not** verified and is flagged in the task text as needing
   confirmation against JGit's own SSH test suite at implementation time), Task 8.4.1c (HTTPS with
   Basic auth against an embedded `org.eclipse.jgit.junit.http.AppServer` + `GitServlet` — `AppServer`'s
   own methods verified, but the exact servlet-wiring call shape was **not** verified beyond citing
   JGit's own `SmartClientSmartServerTest.java` as the implementation-time reference). All three
   test-support artifacts (`org.eclipse.jgit.junit`, `.junit.ssh`, `.junit.http`) were confirmed to
   exist on Maven Central at exactly `7.3.0.202506031305-r`, matching JGit core/Desktop's version
   and (per Task 0.1.1a) Android's post-bump SSH transport version — no version-skew risk. Story
   0.1.1's acceptance criteria (plan.md) was also updated to cross-reference Task 8.4.1b by number,
   closing its dangling forward reference.
2. **No dedicated test for the original bug's literal symptom — closed.** Task 8.2.1d adds `` `resolveForJGit never returns unresolvable saf scheme string when shadow worktree is active` `` (using validation.md's own proposed name), asserting directly against `resolveForJGit()`'s return value rather than only inferring correctness from 8.2.1a's ops succeeding.
3. **`StatFs` storage-space guard — closed.** New Story 8.2.3 (Tasks 8.2.3a/8.2.3b) covers both the insufficient-storage error path and the sufficient-storage happy path, using Robolectric's `StatFs` shadow — the exact shadow-registration API name was not verified against Robolectric's docs this pass and is flagged in the task text for implementation-time confirmation (a narrower unknown than gap #1's — the shadow class is known to exist in Robolectric, just not its exact call signature).
4. **Initial-clone reconciliation — closed.** New Story 8.4.2 (Task 8.4.2a) constructs the exact "pre-existing SAF markdown, then `clone()`/`init()`" scenario from Open Question 5, asserting the first `status()` call afterward shows the pre-existing files as uncommitted — covering both call sites Task 1.2.3e's fix touches, not just `clone()`.
5. **Cross-subsystem mutual exclusion, behavioral not just structural — closed.** New Story 8.4.3 (Task 8.4.3a) extends `GitWorktreeLocksSharedKeyTest.kt` with a real interleaved-coroutine ordering assertion (marker-append sequence proving non-overlap), on top of Task 5.2.1c's existing same-`Mutex`-instance structural check.
6. **Path-mapper adversarial-input coverage — closed.** New Story 8.4.4 (Task 8.4.4a) extends `GitShadowWorktreeTest.kt` with path-traversal, empty-string, and unrelated-prefix inputs, asserting the composition of the lenient path mapper and `safeWorktreeFile`'s strict traversal guard never resolves outside `worktreeRoot`.
7. **`DomainError.GitError` variant coverage — closed, and a related plan gap fixed en route.** Auditing this gap surfaced that `WorkingTreeWriteBackFailed` had no construction site specified anywhere in the original plan (Task 3.1.2a's `flushPage` never described the non-race write-failure branch) — a real gap in the *implementation* plan, not just its test coverage, that a test alone couldn't close. New Task 3.1.2c adds that missing production logic; new Task 8.1.2c tests it. `WorkingTreeSyncFailed` is covered by Task 8.2.3a (storage guard); `WorkingTreeConcurrentEditDetected` was already covered by 8.1.2b. This document's Coverage Targets section also corrected an earlier miscount that described these as "four" variants — there are three, and "the storage-guard error" is a `WorkingTreeSyncFailed` instance, not a fourth type.

**Net**: all 7 gaps have a concrete task now backing them. Two of the new tasks (8.4.1b's SSH key
format, 8.4.1c's servlet wiring shape) carry a named implementation-time unknown about a
third-party library's exact API surface — a materially smaller kind of open question than "no task
exists at all," but real enough that this document should not claim those two are fully settled
until implementation confirms them.
