# Plan: Kotlin wasmJs (and JS) compilation under Bazel for SteleKit, carried as a rules_kotlin patch

Status: plan only, no repo changes besides this file. Date of research: 2026-11-21.
Goal: replace the `//kmp:web_dist` genrule (`kmp/BUILD.bazel:72-101`, shells out to `./gradlew :kmp:wasmJsBrowserDistribution`) with native Bazel actions. Spike scope first: commonMain + wasmJsMain compiled to a klib / Wasm for the `wasmJs` target with a hand-written dependency list, diffed against the Gradle output. Native/iOS out of scope.

## 1. Architecture decision (what we build)

Two new Starlark rules and one macro, in a **stelekit-local overlay first, upstream-shaped second**:

- `kt_wasm_library` (klib producer, `.kt` -> `.klib`; providers `KtKlibInfo{klib, transitive_klibs}` named after #1351 so that a later upstream convergence is a rename).
- `kt_wasm_binary` (link + wasm-opt; outputs `.mjs`, `.wasm`, import-object, builtins, and a `files` tree).
- `kmp_wasm_dist` macro/rule (bundle + assets + resources, yields `web_dist.tar.gz` with the same layout as the Gradle output so `//kmp:web_app` and `e2e/run_e2e.sh` stay unchanged).
- JS target (`kt_js_*`) reuses the same compiler invocation with `-target=es2015` and no `-Xwasm`; **build it as a thin flag variant, but gate it behind a real consumer** (no jsMain in this repo today: `kmp/src` has no `jsMain`, only `wasmJsMain`). The macro is written target-parametric so JS costs one flag set plus its stdlib klib (`kotlin-stdlib-js.klib` is in the distribution).

Rule placement (decision, with reasons):
1. Spike + early items: files live in the SteleKit repo at `third_party/rules_kotlin_wasm/` as a local Bzlmod module (`local_path_override`) that loads `@rules_kotlin//kotlin:*` public symbols and reads `kotlin_home` from the existing toolchain. Reason: no re-patching of a 2.4.10 archive for each iteration, and the existing patch mechanism (`single_version_override` + unified diff) is awkward for new multi-file additions. **Constraint (INFERRED):** the overlay can only see what rules_kotlin exports; `KtJvmInfo`-style private providers and the prebuilt worker are not extensible from outside.
2. Items that need rules_kotlin internals (toolchain attribute exposing the wasm stdlib klib / compiler jar classpath; any KotlinBuilder worker change) become a **small patch** `third_party/patches/rules_kotlin_wasm_hooks.patch` appended to the existing `single_version_override.patches` list (`MODULE.bazel:27-31`).
3. Once S1-S4 pass, port the overlay into a branch of bazel-contrib/rules_kotlin shaped to the API decision in #1684 (see section 7).

### W1. Compiler integration (needs: W0)
1. **Invocation mechanism - recommendation: a thin `java_binary` launcher that runs `org.jetbrains.kotlin.cli.js.K2JSCompiler` from the toolchain's compiler jar, one non-persistent action per target, behind a single Starlark function `_kotlinc_js_action()` (the seam).** Reasons: (a) the released rules_kotlin archive ships `kotlin_worker.jar` as a prebuilt binary (`src/main/kotlin/kotlin_worker.jar`), so a `Platform.JS` worker executor means rebuilding the worker from upstream source; (b) BTAPI at 2.4.10 appears JVM-only (0.1, INFERRED), and #1481 itself is unfinished and stale-flagged; (c) cgruber chose the same "thin seam, swap for BTAPI later" shape for native (#1682 section 2, item 2) so the seam stays upstream-compatible; (d) workers give incrementality we do not need yet: the wasm compile is one large action (commonMain is 1537 files).
   - Classpath for the launcher: `kotlin-compiler.jar` and its dependencies from the toolchain's `kotlin_home`/compiler repo (the same jar set that compiled the JVM targets). UNVERIFIED which target exposes just the jars; S2 resolves this and decides whether the hook patch (2) is needed.
2. **Klib action** (`kt_wasm_library`): flags `-Xwasm -Xwasm-target=js -Xir-produce-klib-file -ir-output-dir <d> -ir-output-name <n> -Xir-module-name <name> -libraries <klib1:klib2...> -nostdlib` + explicit `-libraries` entry for `kotlin-stdlib-wasm-js.klib` so the stdlib is a declared input (hermeticity, same rationale as #1682 section 3 "explicit stdlib as a declared input"), `-Xklib-relative-path-base=<execroot>` for cache-friendly klibs, `-Xmulti-platform`, `-Xexpect-actual-classes`, `-opt-in=...` (the opt-ins at `kmp/build.gradle.kts:28-32`), `-Xplugin=<compose.jar>` + `-P plugin:androidx.compose.compiler.plugins.kotlin:...` and `-Xplugin=<serialization.jar>`. Final exact list is the W0 capture; do not freeze this one.
3. **Common sources:** commonMain + wasmJsMain must compile in **one** invocation, because `expect` and `actual` must be in the same module (cgruber's point, #1682 section 4; same rationale as `kmp/src/commonMain/kotlin/BUILD.bazel:1-12`). Two ways, pick one in S1: (i) extend the existing `common_srcs` idea with `-Xcommon-sources=<files>` exactly as the current patch does for JVM (the K2JS compiler accepts `-Xcommon-sources`, 0.3); (ii) K2 fragments (`-Xfragments`, `-Xfragment-sources`, `-Xfragment-refines`) which model commonMain/wasmJsMain as real fragments and are what the Gradle plugin uses for K2 metadata/KMP compilations (INFERRED). ### W2. KMP dependency resolution (needs: W0 for the closure; independent of W1 until link)
Problem (VERIFIED): `@maven` is a JVM-only `maven.install` with a lock file (`MODULE.bazel:~163-180`, `rules_jvm_external++maven+maven_install.json`). For wasmJs we need the `-wasm-js` klib artifacts. The root KMP module's `.module` redirects through `available-at`: e.g. `kotlinx-coroutines-core-1.10.2.module` has variants `wasmJsApiElements-published` and `wasmJsRuntimeElements-published` with `org.jetbrains.kotlin.platform.type=wasm`, `org.jetbrains.kotlin.wasm.target=js`, whose `available-at.url` is `../../kotlinx-coroutines-core-wasm-js/1.10.2/...module`; that module's variant lists `files: kotlinx-coroutines-core-wasm-js-1.10.2.klib` and dependencies `atomicfu-wasm-js:0.26.1`, `atomicfu:0.26.1`, `kotlin-stdlib:2.1.0` (fetched and parsed from Maven Central). The `.klib` files exist at predictable URLs (`kotlin-stdlib-wasm-js-2.4.10.klib`, `ktor-client-core-wasm-js-3.1.3`, `runtime-wasm-js-2.3.2` (SQLDelight), `arrow-core-wasm-js-2.2.1.1`, `org/jetbrains/compose/runtime/runtime-wasm-js/1.10.3` all listed on Maven Central). rules_jvm_external has no wasm-variant selection today (#1357 resolves the JVM runtime classpath; smocherla's `additional_kmp_platforms` is an unbuilt idea).

Options compared:
| Option | Pros | Cons |
|---|---|---|
| A. Hand-curated `http_file` per klib | Zero tooling; right for the spike | Transitive closure is large and silently drifts; no version-conflict logic; Compose/Coil/Ktor umbrella modules are exactly where resolvers are reported buggy (Dolfik1) |
| B. Custom module extension walking `.module` files in Starlark at repo-rule time | Fully Bazel-native | Re-implements Gradle variant matching and conflict resolution; slow repo rule; every new library is a possible divergence |
| C. rules_jvm_external Gradle resolver / `additional_kmp_platforms` (#1357 follow-up) | Upstream-aligned long-term | Not built; Gradle resolver reported slow; we would be blocked on a third party (smocherla-brex lacks bandwidth) |
| **D (recommended). Gradle as the lockfile generator, Bazel as the hermetic consumer** | Gradle already performs correct variant selection and conflict resolution for this exact project; the output is a committed JSON lock `{group, artifact, version, url, sha256, scope}` consumed by a tiny module extension that emits `http_file` repos + a `kt_klib_import` target per entry; build-time is hermetic and cacheable; CI freshness check mirrors the existing "SQLDelight generated sources" gate | Gradle remains a dev-time dependency (it is anyway: iOS, benchmarks, SQLDelight codegen per `CLAUDE.md`); lock refresh is a manual command |

**Recommendation: D, with A used for the first spike (S1) and D as W2 proper.** The lock file shape is deliberately the same information `additional_kmp_platforms` would produce, so we can swap the generator for #1357 later without touching the consumer.
- Generator: a Gradle task `dumpWasmJsKlibLock` registered in `kmp/build.gradle.kts` (this is a code change, done in implementation, not now) that resolves `wasmJsCompileClasspath` and `wasmJsRuntimeClasspath` and writes `third_party/kmp_klibs/wasmjs.lock.json`.
- Consumer: module extension `kmp_klibs` (in the overlay module) -> `@kmp_wasm//:<mangled-gav>` targets providing `KtKlibInfo`; dependency edges taken from the lock so `kt_wasm_library.deps` can name only direct deps (the repo's `maven.install` precedent for per-GAV target naming is at `MODULE.bazel:~196`).
- Not-on-Maven items: `kotlin-stdlib-wasm-js.klib` comes from the toolchain's `lib/` (VERIFIED present) or Maven; **skiko** wasm runtime (`skiko.wasm`, `skiko.mjs`) is an `org.jetbrains.skiko:skiko-js-wasm-runtime` artifact the Compose Gradle plugin unpacks into `build/compose/skiko-runtime-processed-wasmjs` and then post-processes ("processed": `js-reexport-symbols.mjs`, `skikod8.mjs`) (listing VERIFIED locally). Treat skiko as an explicit lock entry plus a copy step; the "processing" step content is UNVERIFIED (S3).

### W9. Leaf test modules so Bazel's cache picks what runs (owner principle; applies to every W8 row)
Principle: a test target depends only on the small production library it exercises, so a change re-runs only the tests downstream of it. VERIFIED today (counted 2026-11-21): `commonMain` has 1537 `.kt` files but `kmp/src/commonMain/kotlin/BUILD.bazel` defines 0 library rules (the library lives in `kmp/BUILD.bazel`), and ~1455 `*Test.kt` files sit behind only ~17 rule targets (`jvm_tests` is one `glob(["**/*.kt"])`, `kmp/src/jvmTest/kotlin/BUILD.bazel:35-38`). So any edit to commonMain rebuilds the whole library and reruns the one giant test target; leaf test modules alone change nothing until production code is split too.
Work order: (1) derive the package dependency graph from imports (`sg`/Grep; kibitzer `architecture_assessment`) and pick cut lines along the existing layers (`model`, `parser`/`outliner`, `repository`, `db`, `merge`, `jobs.schedule`, `ui`); (2) split production into `kt_jvm_library`s along those cuts with `visibility` and strict deps, enforcing the existing direction rules (e.g. `jobs.schedule` must not import `git/ui/db/merge`) as Bazel visibility instead of only `JobsScheduleImportDirectionTest`; (3) give each library a sibling test target holding only its tests; replace the `AllBusinessTests`/`AllJvmTests` registries with per-target globs (retiring the explicit-list registration step in CLAUDE.md); (4) keep the cross-cutting audits (`WiringCompletenessTest`, `TestPlacementAuditTest`) as their own targets that depend on source filegroups; (5) expensive suites (W8) become leaf targets too, with `tags` only for resources (display, emulator), not for grouping. The same split applies to wasmJs: a wasm klib per library lets wasmJsTest run per leaf instead of one Karma run.
Gate G7: touching one file in a leaf library re-executes only its dependents' tests (`bazel test //... --explain`/`--execution_log` shows the executed set; mutation-prove with a file outside the dependency cone). Cost: L x2 (graph analysis + split), M x3 per layer migration; the dominant risk is import cycles between layers, which the split will surface as build errors.

## 6. Risks and unknowns (ranked by expected impact x probability)

1. **R1: expect/actual + K2 + Compose on wasmJs outside the Gradle plugin** (S1). Gradle uses K2 multiplatform compilation structures that a flat `-Xcommon-sources` invocation may not reproduce (fragments, `internal` visibility between source sets, `@OptIn` args). Mitigation: fragments flags as plan B; fall back to `-Xfriend-modules` for tests.
2. **R2: dependency closure correctness** (W2). Aggregator modules, Compose/Coil/Ktor variants, version alignment (BOMs). The Gradle-generated lock removes most of this; residual risk is lock staleness and the unconfirmed number of klibs (not counted; W0 counts it).
3. **R3: bundling parity** (S5). Webpack behaviors (classic script output, wasm asset hashing, dynamic `import(name)` in `import-object.mjs`, `webpackIgnore` comments for `node:module`) may not be reproduced by Bun's bundler; esbuild+rules_js is the fallback.
4. **R4: wasmJsTest without Karma** (S6). Kotlin/Wasm test registration with a JS test framework; headless Chrome provisioning.
5. **R5: build size and performance**: one compile action for ~1632 sources (1537 common + 95 wasm) and the 36 MB unoptimized wasm; no worker incrementality; JVM memory of a non-persistent compiler. Mitigation: split into libraries later (each carries its own klib), `timeout 30m` wrapper per `CLAUDE.md` on unattended runs.
6. **R6: language/API level mismatch** (`BUILD.bazel:36-38` 2.1 vs Gradle 2.4 default) and Compose plugin version-check suppression (`BUILD.bazel:43-55`).
7. **R7: upstream drift**: rules_kotlin #1682 restructures APIs (kt_library vs kt_native_library naming, #1684 undecided); our overlay API will need a rename. Mitigated by using their provider names.
8. **R8: resource and font parity**: Res generation; the JVM stub already shows the app tolerates missing fonts but wasm web may not.
9. **R9: Gradle-only generators** (version/demo-fs) must be reimplemented as genrules; drift if the Gradle logic changes (`kmp/build.gradle.kts:533-742`). Add a test comparing generated output.
10. **R10: Bazel server orphaning** from long wasm compiles in agent worktrees (see `CLAUDE.md`): always wrap in `timeout` and `bazel shutdown`.
