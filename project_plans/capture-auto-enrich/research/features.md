## 2. Critical architectural gap: no shared matcher/index reaches `CaptureViewModel`

`PageNameIndex` is instantiated **exactly once in the whole codebase**: `StelekitViewModel.kt:516`, inside the main app's screen ViewModel (`val pageNameIndex = PageNameIndex(pageRepository, scope)`). It is not owned by `GraphManager` or `RepositorySet` (`RepositoryFactory.kt:47`) — those only expose `pageRepository` itself. `ImportViewModel` gets its matcher by receiving `viewModel.suggestionMatcher` (i.e. `StelekitViewModel.pageNameIndex.matcher`) as a constructor parameter from `ScreenRouter.kt:260` — it never builds its own.

`CaptureActivity` is a **separate Activity with its own `AndroidViewModel`** (`CaptureViewModel(app: Application)`), launched directly from the share sheet/widget/tile — it does not go through `App.kt`'s composition tree or `StelekitViewModel` at all. It only touches `SteleKitApplication.graphManager` and `GraphManager.getActiveRepositorySet()` for `pageRepository`/`writeActor`/journal service. **If the main app (`MainActivity`) isn't already running, there is no live `PageNameIndex` anywhere in the process for `CaptureViewModel` to consume.** This confirms the requirements' "Stack" research dimension is a real open question, not a formality — the two realistic options are (a) `CaptureViewModel` builds its own throwaway `PageNameIndex` per capture (full trie rebuild cost, same OOM-guard needed), or (b) `PageNameIndex` gets hoisted to graph scope (owned by `RepositorySet`/`GraphManager` instead of `StelekitViewModel`) so both entry points share one warm instance — the latter is a bigger, cross-cutting change than this feature's stated scope ("no new algorithms").

## 3. Edge cases already identified by prior features (re-checked)

From `project_plans/stelekit-import/requirements.md`: encoding issues, large-paste performance, URL fetch failure modes, false-positive tag matching on common words (addressed later via `DEFAULT_STOPWORDS`/`MIN_NAME_LENGTH` in `PageNameIndex`).

From `project_plans/import-topic-suggestions/requirements.md`: false-positive rates for heuristic NLP on technical text, rate limiting/latency for the Claude call, suggestion list overwhelming the user (resolved via the 15-cap/8-visible + 0.2 confidence floor in ADR-004). None of these three prior-feature documents anticipated a **non-interactive, externally-launched, translucent-overlay** consumer — both assume the full-screen in-app `ImportScreen` with `StelekitViewModel` already warm.

## 4. Edge cases and failure modes specific to this share-sheet-capture variant

These do not apply to `ImportScreen` (a full-screen destination reached only after the main app and its `StelekitViewModel`/`PageNameIndex` are already warm) but are load-bearing here:

- **No warm matcher on cold share.** Covered in §2 — the common case (share from another app while SteleKit isn't running) has no `PageNameIndex` to await. `ImportViewModel.init` deals with a matcher that's *initially* null and arrives later via `matcherFlow.collect`; `CaptureViewModel` needs the same "matcher not ready yet, skip enrichment silently" tolerance baked into its very first scan, not just as a race-condition edge case.
- **Trie-build cost inside a translucent overlay.** `focusRequester.requestFocus()` runs in a `LaunchedEffect(Unit)` immediately on composition — any synchronous or blocking matcher build on the UI/main path would visibly delay the keyboard opening, which is the entire point of the "lightweight overlay" UX. `PageNameIndex`'s existing rebuild already targets `Dispatchers.Default` off the calling thread for exactly this reason in the main app; the capture path must not accidentally build on `viewModelScope` in a way that contends with `requestFocus()`.
- **User backgrounds/dismisses the app mid-enrichment.** `CaptureActivity.onDismiss = { finish() }` and the dim-layer tap (`if (captureText.isBlank()) onDismiss() else viewModel.save()`) can fire while an enrichment/scan coroutine is in flight. `AndroidViewModel.viewModelScope` is cancelled automatically on `onCleared()`, so an in-flight `withTimeout` Claude call is safely torn down — but if any accept/save logic assumes the coroutine ran to completion (e.g. writing a stub page then updating in-memory state), a cancellation mid-write could leave a stub page created with no corresponding wiki-link folded into the (now-unsaved) block, an inconsistency `ImportViewModel` avoids by keeping stub-page creation entirely inside `confirmImport()`, which is a single user-triggered suspend call, not a background timer.
- **Save must never wait on enrichment — but `save()` is also the `BackHandler`/dim-layer auto-save path**, not just a button tap. Unlike `ImportScreen`'s explicit two-stage input→review flow, `CaptureScreen` conflates "leave the screen" with "save," so the timeout/fallback path (raw-text save if scan/suggest doesn't finish in budget) has more trigger points to cover: explicit Save button, back-press, and tap-outside-to-dismiss all currently call the same `viewModel.save()`.
- **Multiple rapid captures in sequence (`singleTop` reuse).** `onNewIntent` → `initializeText()` only writes if the field is currently empty; a second share while the first is unsaved is dropped today. Once a scan/enrichment pass exists, a second intent arriving while the first capture's `scanJob`/enrichment coroutine is still running needs the same cancel-and-restart discipline `ImportViewModel.onRawTextChanged` already applies (`scanJob?.cancel()` before starting a new one) — otherwise a stale suggestion set from capture 1's text could be displayed against capture 2's text, or a stale `topicEnricher.enhance()` result could land after the second capture's `Save` already fired.
- **Bare URL with no article body.** Share intents from browsers frequently populate `EXTRA_TEXT` with just a URL (`CaptureActivity.buildShareText` already special-cases the "subject + URL, joined with newline" pattern). `AhoCorasickMatcher`/`TopicExtractor` have nothing to extract from a bare URL string — the enrichment pass should degrade to "no suggestions" quickly rather than running the (comparatively expensive) full NLP heuristic over a string that's mostly punctuation and a hostname. Unlike in-app `ImportViewModel`, which has a dedicated URL tab that fetches and extracts real article text via `UrlFetcher`/`HtmlBlockConverter` before scanning, this feature is explicitly scoped to the raw shared text only (`ImportService.scan()` on whatever `EXTRA_TEXT` contains) — a shared URL here gets zero enrichment value versus doing the same share via in-app Import, which is a real capability gap worth naming even though URL-fetch enrichment is out of scope for v1.
- **Very short text** (e.g. a single word or short phrase shared from a dictionary/reference app) — `TopicExtractor`'s noun-phrase/confidence heuristics were tuned against "a 10 KB technical article" (import-topic-suggestions success criteria); on a 3-word capture, confidence scoring has far less context to work with, likely either suppressing everything below the 0.2 floor (fine) or, worse, treating the entire short string as one high-confidence "novel term" with no basis. This should be verified against `TopicExtractor.extract()`'s scoring inputs (frequency/capitalization/POS context) at very small N during implementation.
- **Very long text** (a full article body pasted via clipData) — the <500ms/10KB budget from `import-topic-suggestions` was set for the in-app review stage, which has no competing responsiveness requirement as strict as "keyboard must open immediately." A capture-sheet scan needs its own explicit timeout distinct from that budget, since the sheet's perceived-responsiveness bar (time to first frame, time to editable field) is a *harder* constraint than Import's.

## 5. Unstated user needs beyond the explicit requirements

- **Undo after accepting a wrong suggestion.** `ImportViewModel` already has this exact feature: `onUndoStubCreation()` + `undoBuffer: List<Page>` + `showUndoSnackbar` + `undoLinkedText` (the pre-accept text snapshot), wired through `PageDeleter`. The requirements doc doesn't mention undo at all for the capture-sheet variant, but per ADR-004 ("Accept All requires a dialog; single-item Accept does not, since undo is available") the *entire reason* single-chip accept can skip a confirmation dialog in the reference UX is that undo exists as the safety net. If the capture sheet mirrors "accept chip → stub page created immediately, no confirmation" (as the requirements imply — "no silent page creation" just means *explicit accept*, not *confirmable/undoable*) without also mirroring undo, it inherits the low-friction accept UX without the safety net that justified it. This is a gap worth flagging back to requirements/planning, not silently resolving here.
- **Seeing which text got auto-linked before it's too late to fix.** Existing-page matches auto-apply with zero confirmation in both `ImportService.scan()` and this feature's Must-Have scope ("existing-page mentions are auto-converted to `[[wiki links]]`... matching in-app Import behavior"). In `ImportScreen`, the user sees a full review stage (linked-text preview, matched-page chip row) *before* confirming — there's a deliberate look-before-you-leap step. The capture sheet's `OutlinedTextField` shows the *raw* editable text (`captureText`), not the linked/enriched version — ADR-004's "Should Have" distinction ("Visual/haptic distinction between matched-existing-page links... and new-page suggestion chips") is the intended fix, but simply appending suggestion chips below the input field doesn't by itself show the user *where in their text* the auto-links landed, since the raw text field and the linked output potentially diverge. Given the sheet's minimal chrome (3-8 line text field, no separate preview stage), inline highlighting or a lightweight indicator of "N terms were auto-linked" is worth calling out as a UX need even though it's not explicit in Should/Must Have.
- **Confidence that a capture that appears saved is actually saved before enrichment runs.** Because `save()` is reachable from three different UI triggers (button, back, tap-outside) and finishes the Activity via `onSaved()`, a user has no way to know, after the sheet closes, whether enrichment ran, timed out, or was skipped for that capture — there is no post-hoc surface (e.g. a `[[wiki link]] added` toast, or a marker in the saved block) distinguishing "raw fallback save" from "enriched save." `ImportViewModel`'s review stage makes this visible *before* commit; the capture sheet's speed-first design makes it invisible *after* commit, which could silently erode trust in the auto-linking feature if it fails frequently without any signal.

## Summary of what to mirror vs. what needs new design

**Mirror directly**: `ImportService.scan()` call shape, `TopicSuggestion`/confidence-dot/15-cap chip semantics from ADR-004, `withTimeout` fire-and-forget enrichment pattern with stale-result discarding by text-hash, scanJob-cancel-on-new-input discipline, `PageNameIndex`'s `Throwable`-catching OOM guard.

**Needs new design (no existing analogue)**: how `CaptureViewModel` obtains a matcher/`PageNameIndex` at all (§2 — the single biggest open question), how the raw-text-save timeout/fallback interacts with three different save triggers instead of one, whether undo (§5) and post-save enrichment visibility (§5) are in scope given the sheet's minimal-chrome constraint.
