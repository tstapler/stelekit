# Pre-mortem: capture-auto-enrich
**Date**: 2026-08-10

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | A user with a large graph (8k+ pages) fires several captures in a session; each `CaptureEnrichmentCoordinator`'s `scanJob`/`launchLlmEnrichment` coroutine runs uninstrumented on `viewModelScope` (no `CoroutineExceptionHandler`, only `catch (e: Exception)` not `Throwable`), and a matcher-rebuild `OutOfMemoryError` — already documented as plausible at this scale in `PageNameIndex.kt:52-56` — escapes uncaught and kills the process. | App shows "keeps stopping" / crashes shortly after a capture on a large graph, reproducing this repo's own prior incident pattern (see memory: `stelekit_pages_backlink_count_migration_crash.md`) — not a hang, a hard process kill. | Make the `CoroutineExceptionHandler` on the coordinator's scope mandatory in plan.md (not Task 2.2.3a's "if time permits"), change `catch (e: Exception)` to `catch (e: Throwable)` (re-throwing `CancellationException`) in both `scanJob` and `launchLlmEnrichment` per adversarial-review.md's Blocker #2, and add an 8k-page matcher-build stress test to validation.md mirroring the existing `LargeGraphWarmStartCrashTest` pattern. | P1 |
| 2 | A user shares several related links back-to-back (a plausible "batch triage" session). The non-atomic `coordinatorFor` build (architecture-review.md Blocker #1) lets a second keystroke spin up a second `CaptureEnrichmentCoordinator`/`PageNameIndex` before the first finishes suspending on `resolveTopicEnricher()`; separately, `createAcceptedStubPages` has no per-suggestion failure isolation and sits between the DB block write and the Bug-8 markdown flush (adversarial-review.md Blocker #1). Either path produces two pages for the same term, or a stub-page exception that aborts the flush after the DB write already landed. | User notices two similarly-named pages in the sidebar/search after a rapid-share session, or a captured note's block content and its on-disk markdown file disagree (DB says saved, file wasn't flushed) — the exact desync class Bug 8 was built to prevent. | Resolve architecture-review.md's Blocker #1 (make `coordinatorFor` single-flight via `Mutex` or a memoized `Deferred`) and adversarial-review.md's Blocker #1 (wrap each stub-page creation so one failure degrades that suggestion, never the surrounding `performSave()`/flush) before implementation; add a validation.md test that races two real `CaptureActivity`/coordinator instances against the same repository concurrently, not just sequentially. | P2 |
| 3 | Share-sheet capture is the highest-frequency entry point by design; a user shares 10+ links in one sitting with an LLM provider configured. Nothing bounds *how often* captures trigger a call (only a per-call 8s timeout exists) — pitfalls.md's explicit P1 ask to "size the capture-in-a-burst cost scenario" was never actioned in plan.md. | Unexpectedly high API spend shows up on the configured provider's billing page for that month, or several captures in a row visibly stall near the 8s timeout / return 429s. | Add a session-level debounce or max-concurrent-enrichment cap to `CaptureEnrichmentCoordinator`, and record the decision explicitly in plan.md's Risk Control section (accepted risk with a stated bound, or an actual cooldown) instead of leaving pitfalls.md's ask unaddressed. | P2 |
| 4 | `LlmProviderRegistry.availableForFeature()`'s network-I/O cost was never verified by reading `checkAvailability()`'s implementation — carried as an open assumption through research, architecture, and adversarial review. If it does any network round-trip and `resolveTopicEnricher()`/`coordinatorFor` call it unconditionally on every capture-sheet open, it directly threatens the one hard success criterion this feature has ("perceived responsiveness... is not regressed"). | Capture sheet occasionally feels sluggish to open or Save occasionally hesitates, especially on a slow/metered connection — intermittent and easy to misattribute to "Android being Android" rather than to this feature. | Before implementation, actually read `checkAvailability()`'s implementation (not just its doc comment) and add a validation.md assertion that enricher resolution never blocks on network I/O beyond a small bounded timeout; if it can, resolve providers once at graph-load time instead of per capture. | P3 |
| 5 | Unresolved Question #1 ("should capture-tier LLM enrichment have its own on/off toggle?") is marked "blocks Story 1.2.2" but the plan immediately proceeds to spec Story 1.2.2 against a hardcoded "always Auto" default with no gate that actually waits on an answer. If "always Auto" turns out to be the wrong call, every capture — even a two-word note — silently attempts an LLM call by default. | User notices every quick-capture, regardless of length or intent, triggers a network/on-device LLM call and the associated battery/data/cost, contradicting capture's own "fastest, lowest-friction" framing in requirements.md. | Resolve Unresolved Question #1 with an actual decision before implementation starts (not a default carried through planning), and fix the plan's self-contradictory "blocks Story 1.2.2" language so the dependency graph doesn't claim something is blocked when it was already decided. | P2 |

## P1 Items (address before implementation)
- [ ] #1 (crash-loop from uncaught Throwable/OOM) — plan.md must make the coordinator's `CoroutineExceptionHandler` mandatory (drop "if time permits" from Task 2.2.3a) and change `catch (e: Exception)` to `catch (e: Throwable)` in Tasks 1.1.2a/1.2.1a per adversarial-review.md's Blocker #2, plus add an 8k-page matcher-build stress test to validation.md.
