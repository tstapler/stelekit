# UX Research: Depth Model Download Stall

Agent 5 (UX) — SDD Phase 2 research for backlog item `505fb733-9621-4621-b7fc-27712e36d084`.

## Code grounding (read before drafting recommendations)

- `kmp/src/androidMain/kotlin/dev/stapler/stelekit/platform/ml/DepthModelDownloader.kt` — `downloadModel()` hardcodes `ModelState.Downloading(progress = 0)` at enqueue (line 78) and never updates it again until the terminal `ACTION_DOWNLOAD_COMPLETE` broadcast fires. There is **no periodic `DownloadManager.Query()` poll** in the current code, which is the direct mechanism gap behind AC1.
- Cancellation plumbing **already exists** at the coroutine layer: `continuation.invokeOnCancellation { ... downloadManager.remove(downloadId); _modelState.value = ModelState.Absent }` (lines 120-125). Nothing in the UI currently cancels the coroutine, so this code path is dead today. Wiring a Cancel button to `job.cancel()` on the collecting scope is most of AC3 for free — no new DownloadManager-removal logic needed, just a UI trigger.
- `kmp/src/commonMain/kotlin/dev/stapler/stelekit/ui/annotate/AnnotationEditorScreen.kt` — `DepthEstimationPanel` (~line 1318-1427) is a **small floating `Surface` overlay**, not a full-screen modal or blocking dialog. It sits on top of the photo canvas alongside other annotation controls. This matters for Q2/Q5 below: the download is not currently gating the rest of the editor UI at the layout level, even though the copy/mental-model treatment doesn't communicate that.
- The `Downloading` branch (lines 1382-1397) renders `CircularProgressIndicator` + `"Downloading model… $pct%"` (or without `%` if `pct < 0`) with **no button, no `Modifier.clickable`, no semantics** — confirmed no cancel affordance exists today, matching the requirements doc's stated root cause #2.
- `Failed` branch (lines 1400-1415) is a `TextButton` wrapping icon+text — this is the retry precedent to match stylistically for the new Cancel button and for the stall→Failed transition copy.
- **Direct precedent for the fix already in this codebase**: `kmp/src/commonMain/kotlin/dev/stapler/stelekit/ui/components/settings/FolderSyncReconciliationProgress.kt`. Its `ConnectingState` and `SummaryState` composables apply `Modifier.semantics { liveRegion = LiveRegionMode.Polite }` to the progress row, with inline comments citing an AC number (`design/ux.md AC24`) for "announced on entry" / "announced again on completion." Its `FailedState` uses plain-language copy ("Couldn't finish comparing your files") plus a paired `Button("Try again")` / `OutlinedButton("Cancel")` row — zero technical jargon, no mention of underlying mechanism. This is the pattern to replicate for the depth-model download, both structurally (`liveRegion`) and tonally (copy).
- No other `contentDescription`/`semantics`/`liveRegion` usage in the repo targets a *numeric progress* announcement — `FolderSyncReconciliationProgress` announces state-entry/completion, not intermediate percentage ticks. That's a new pattern this feature would introduce (see Q3).

## 1. Comparable UX patterns for first-use large-asset downloads

Patterns that work well, and why, drawn from established mobile conventions (Google Photos/Maps offline regions, Play Store asset delivery, game asset packs, ML Kit/Gemini Nano on-device model downloads):

- **Determinate progress + byte counter together** (e.g. `"42.3 MB / 98 MB"` alongside a percentage or bar) outperforms percentage-only. A byte counter keeps advancing even when percentage rounding makes the number feel static (44% → 44% → 45% over several seconds reads as stalled; "61 MB / 98 MB" → "63 MB / 98 MB" reads as progress). Given AC1 only requires proportional percentage updates every 200-500ms, pairing it with a compact byte string is a low-cost addition worth flagging to product/plan even though it's not a hard requirement.
- **Background-continues messaging** ("Downloading in background — we'll notify you when the depth model is ready") is standard for asset packs and offline maps, and directly satisfies AC5 (leaving the screen mid-download shouldn't strand the user). Since `DownloadManager` already survives process death and shows a system notification (`VISIBILITY_VISIBLE` is already set in the code), the in-app copy should say so explicitly rather than leaving the user to infer it — otherwise they'll assume navigating away cancels the download.
- **Wi-Fi-only toggle** is common for >50MB downloads (Play Store, most game launchers) but is explicitly out of scope per the requirements' non-goals (`setAllowedOverMetered(true)` is already set, deliberately allowing cellular). No recommendation to add this now, but worth a one-line note: if stall reports correlate with cellular networks, a "download over Wi-Fi only" checkbox is the standard mitigation, not a URL/hosting change.
- **Indeterminate spinner without a fake percentage** (AC2) is the correct fallback per Android/Material and iOS HIG guidance alike — a frozen "0%" is worse than no number at all because it implies precision that isn't there. Material's own progress-indicator guidance: use determinate only when you can report real proportional progress; otherwise use the indeterminate circular spinner with a text label, no digit.

## 2. User mental models — does this need to block the editor?

The current implementation already keeps `DepthEstimationPanel` as a small floating overlay rather than a full-screen gate, so nothing in the layout currently forces a hard block. But the copy and interaction model don't communicate that today, and a first-time user staring at a static "0%" on a photo-editing screen will reasonably assume one of two things: (a) the whole feature is broken, or (b) they must wait before doing anything else. Given the feature's actual role — an *assistive* scale estimate, not a required step (users can presumably still add manual measurements/annotations without AI depth) — the "keep working, we'll tell you when it's ready" framing is the better fit:

- Recommendation: change the panel copy while downloading from a bare progress readout to something like `"Downloading depth model… you can keep annotating — we'll let you know when AI estimates are ready."` This directly reduces the "stuck" feeling named in the backlog item's title, without requiring any layout change, since the panel already doesn't block other controls.
- This only holds if manual annotation truly doesn't depend on the depth model — confirm with the product/engineering research legs whether any other `AnnotationEditorScreen` control is gated on `DepthModelUiState != Absent/Downloading`. If some other control silently requires `Ready`, the "keep annotating" message would be misleading and should be scoped to "keep working on manual measurements."
- Regardless of framing, AC4 (distinguish "actively downloading" from "stalled") is the higher-priority fix for the "stuck" perception specifically — an accurately advancing percentage is the single strongest signal that something is happening, more effective than reassurance copy alone.

## 3. Accessibility (TalkBack)

Current state: the `Downloading` `Row` (`AnnotationEditorScreen.kt` ~1382-1397) has **no `contentDescription` and no `Modifier.semantics`**. TalkBack today would read the `CircularProgressIndicator` (typically silent or announced as "progress bar," no context) and the `Text` composable's literal string once, at whatever moment focus happens to land there — it will **not** re-announce percentage changes as the download proceeds, since Compose text changes don't auto-announce without an explicit live region.

Findings from scanning existing accessibility patterns in this codebase (`Grep` for `semantics`/`liveRegion`/`contentDescription`):
- `FolderSyncReconciliationProgress.kt` is the only file in the repo using `Modifier.semantics { liveRegion = LiveRegionMode.Polite }`, applied at state-entry and state-completion boundaries (not per-tick).
- Everywhere else, `contentDescription` is used conventionally for icon-only buttons/images (e.g. `ImageAnnotationBlockItem.kt`, `TopBar.kt`, `VoiceCaptureButton.kt`) — standard practice, not additive here.

Recommendation:
- Apply `Modifier.semantics { liveRegion = LiveRegionMode.Polite }` to the `Downloading` row's container, matching the `FolderSyncReconciliationProgress` precedent — but **do not** announce every 200-500ms tick verbatim (that would spam TalkBack users with a new announcement several times a second, which is worse than silence). Throttle announced text changes to a coarser cadence, e.g. update the semantics-visible text only every 10 percentage points or ~3-5 seconds, independent of the visual progress bar's finer-grained redraw cadence.
- Announce state *transitions* unconditionally and immediately (Downloading → Failed, Downloading → Ready, Downloading → Absent via cancel) — these are the moments `FolderSyncReconciliationProgress` treats as live-region boundaries, and they're the moments a TalkBack user most needs to know about.
- Give the Cancel button (new, per AC3) a `contentDescription`/label that names the action plainly — e.g. `"Cancel model download"` — following the codebase's existing convention of descriptive, jargon-free labels on icon buttons.

## 4. Error states, cancel button, and editor availability on cancel

**Cancel button label/placement**: match the `Failed` state's existing `TextButton` treatment (icon + text, same row alignment, `labelSmall` typography) for visual consistency — precedent at `AnnotationEditorScreen.kt` lines 1400-1415 and mirrored again in `FolderSyncReconciliationProgress.kt`'s `FailedState` (`Button`/`OutlinedButton` pair). Suggested copy: a plain `"Cancel"` `TextButton` or icon (Material `Icons.Default.Close`) placed inline in the `Downloading` row, next to the spinner/percentage — no jargon, no mention of "DownloadManager" or "request."

**Stalled-state copy**: avoid technical terms entirely. Something like:
- Timeout-driven transition: `"This is taking longer than expected."` + retry button reusing the existing `Failed` branch's `"Download failed — tap to retry"` treatment (or a variant: `"Download stalled — tap to retry"`), not `"DownloadManager query timed out"` or similar internals.
- The requirements doc's own AC4 language ("timeout-driven transition to Failed with retry") suggests reusing the *existing* `Failed` UI state/branch as the terminal target for a stall timeout, rather than inventing a fourth UI state — simpler state machine, and the retry button/copy already exists and is tested.

**What happens to the editor on cancel**: Per the Q2 finding, the `DepthEstimationPanel` doesn't block the rest of `AnnotationEditorScreen` today — canceling should simply return `ModelState`/`DepthModelUiState` to `Absent`, which the `when` block in `DepthEstimationPanel` already handles (`else -> "Download depth model (~100MB)"` button, lines 1417-1425). No new terminal UI state is needed for "cancelled" distinct from `Absent`; AC3's "returns state to Absent" already matches an existing render branch. The rest of the annotation editor (manual measurement tools, drawing, whatever doesn't depend on `DepthModelUiState.Ready`) should remain fully usable before, during, and after a cancel — confirm this is actually true today by checking whether any other composable in the file gates on `depthModelUiState` beyond this panel (flag to the engineering research leg if so).

## 5. Jobs-to-be-done

- **Functional job**: "Get an accurate scale/measurement estimate from a single photo without manually measuring a reference object." The depth model is a means to that end, not the end itself — reinforces that it should be positioned as an optional accelerant, not a gate.
- **Emotional job**: "Don't feel like the app is broken or like I've lost control." A frozen 0% with no way to cancel or verify activity is the single biggest emotional-trust violation named in the backlog item's own title ("kinda sucks... stuck... never improves"). Determinate progress (AC1), a visible stall→Failed timeout (AC4), and a Cancel escape hatch (AC3) each independently restore a sense of control; together they're the core of the fix. Framing the download as backgroundable/resumable (Q1, AC5) further reduces "I have to babysit this" anxiety.
- **Social job**: not applicable — this is a solitary, in-the-moment task (photographing and annotating on-site), no sharing/collaboration dimension surfaced in the requirements or the screen's code.

## Summary of UX-driven recommendations for the plan phase

1. Pair the required percentage (AC1) with a byte-progress string if cheap to source from `DownloadManager.Query()` (`COLUMN_BYTES_DOWNLOADED_SO_FAR` / `COLUMN_TOTAL_SIZE_BYTES`) — stronger "it's alive" signal than percentage alone.
2. Reframe `Downloading` copy to make clear the rest of the editor remains usable (subject to confirming no other control gates on `Ready`).
3. Add a Cancel `TextButton` to the `Downloading` row styled like the existing `Failed` retry button; wire it to cancel the coroutine job that already has working `invokeOnCancellation` cleanup in `DepthModelDownloader.kt` — this is the cheapest AC3 implementation path.
4. Route the AC4 stall timeout into the existing `Failed` UI branch/copy rather than adding a new state.
5. Add `Modifier.semantics { liveRegion = LiveRegionMode.Polite }` on state transitions (not per-tick) following `FolderSyncReconciliationProgress.kt`'s exact pattern; throttle any live percentage announcement to avoid TalkBack spam.
6. Keep all user-facing copy free of implementation terms (no "DownloadManager," no "request ID") — match the plain-language tone already established in `FolderSyncReconciliationProgress.kt`'s `FailedState`.
