## Problem Statement

1. **Crash.** On Android the app dies when the user places several annotation points back to back in the annotation editor. **Reported, not yet reproduced.** Owner's report (answer to Phase 2 gate): the termination reason was **excessive CPU usage** (Android process kill/exit reason, not an OOM); the exit-reason text has not been seen by the agent (Unresolved Question W1). Earlier suspicion of OOM is unconfirmed; the emulator repro (100 rapid presses on 12 MP/48 MP images) showed flat memory and did not crash, and the later CPU run showed no runaway (Amendment 2).
2. **No memory safety net for image-heavy features (suspected risk).** Whether memory contributes to the reported kill is unproven; the gap is that memory gating exists for the asset pipeline (`AssetPipelineHeapGateTest`) and for the shared Coil cache (`SteleKitImageLoaderMemoryTest`), but nothing measures or bounds memory in the annotation editor, the loupe, or the capture → annotate → export path. Every loupe press currently triggers a separate Coil decode (`loupeDecodeSize`, up to `MAX_LOUPE_EDGE_PX`) in addition to the main image, and the Coil memory cache plus decoded bitmaps are shared across Assets, Gallery and the editor. A regression here only shows up as a crash on a user's phone — desktop JVM never reproduces it (see CLAUDE.md "Uncaught coroutine Throwables kill the process on Android").
3. **Unclear navigation.** The sidebar exposes **Gallery** (`Screen.Gallery`) and **Assets** (`Screen.AssetBrowser`) as two separate destinations (`ui/components/Sidebar.kt:340-341`) with no explanation of when to use which, and the navigation as a whole has no grouping or descriptions. A user cannot tell which one holds their photos, their annotated images, or their attached files.
4. **Feature quality is unknown.** The annotation feature (editor, loupe, select/move, calibration, export) was built incrementally (PRs #514, #556, #558, #560) and has had several correctness bugs found by the owner on-device, not by tests. There has been no end-to-end review of whether it is well implemented.

## Baseline

- Crash: reproducible by the owner on their phone by placing points quickly; no stack/exit reason captured. The app persists `filesDir/logs/current.log`, `previous.log`, `last-crash.txt` and replays Android's recorded exit reason (OOM / ANR / native, API 30+) in the in-app Logs screen on next launch (`AndroidFileLogSink`, `AndroidCrashRecorder`, `PreviousSessionLog`). The owner cannot run `adb logcat`.
- Memory measurement today: heap gate on the asset pipeline (instrumented), a Coil cache-size unit test (JVM), CI-job memory sampling (`mem-sampler`, "ci-memory" benchdiff comments — these measure CI runner memory, not app memory), and load/WriteLatency benchmarks. No annotation-editor memory data exists.
- Navigation: Gallery and Assets are separate items; no section headers or descriptions in the sidebar.
- Loupe: PR #560 (open at the time of writing) fixes loupe misalignment and adds the first on-device annotation test (`LoupeAlignmentE2ETest`), which is not run in CI.

### Jobs to be done (stated, Amendment 4)

1. **Annotate now, find later.** *When* I have measured or marked up a photo on site, *I want to* get back to that photo later, from the app's navigation alone and without remembering which of two screens holds it, *so that* I can reuse the measurements without re-doing the work. This is the job the merged Library, the Annotated filter, annotation-label and tag search, and the sidebar/phone navigation exist for (Success Metrics 4 and 5; plan Epic D).
2. **Place a measurement point exactly, one-handed, on a phone.** *When* I am measuring on a photo with a finger, *I want* the app to let me aim precisely and undo mistakes, *so that* the number is right the first time (Success Metric 5; plan Epic C).
3. **Trust the app not to die while I work.** *When* I place several points quickly, *I want* the app to stay alive and, if it does not, to tell me why (Success Metrics 1, 3 and 6; plan Epics A and B).

## Success Metrics

1. **Crash mitigated and monitored, with gates proven able to fail (Amendment 2, OD-5).** Placing ≥ N points back to back (and sustained rapid input for ≥ T seconds) keeps CPU time per gesture and sustained process CPU within a measured budget (no excessive-resource-usage exit reason in `getHistoricalProcessExitReasons`), and completes on the Pixel_Fold AVD and on a low-memory emulator profile with no `OutOfMemoryError`, ANR, excessive-CPU kill or process death (N chosen in planning, at minimum well beyond the count that crashes today). The kill was not reproduced (stock Android applies the excessive-CPU kill only to cached/HOME processes; research/cpu.md section 1), so an automated test cannot "reproduce the pre-fix failure". The criterion is therefore: (a) every gate that guards the crash class is proven able to fail by the pre-fix proof procedure in plan Story B.5 (probe-only PR on unfixed behaviour, revert of the single fix commit, or a test-only mutation flag), with the red result recorded in the PR; (b) a positive-control repro (task A.3d) shows the harness can observe the background/cached state the stock rule uses, or the background phase is renamed "idle CPU after burst"; (c) production diagnostics (Epic A, Story A.0) ship first; (d) the wording is "mitigated and monitored", never "fixed", until the owner's Logs `importance=` line and a post-fix soak (Success Metric 6) support it. *Original wording (superseded, kept for history): "... an automated on-device test reproduces the pre-fix failure and passes after."*
2. **Memory budgets exist and are measured.** Peak Java/native heap and bitmap bytes are recorded for these scenarios, each with a numeric budget calibrated against a measured baseline: (a) open annotation editor on a large photo, (b) 50 back-to-back point placements with the loupe, (c) loupe press/release cycles, (d) select/move drags, (e) capture → annotate → export, (f) scrolling the Gallery and Assets screens with a large image set, (g) switching between Assets, Gallery and the editor repeatedly (cache churn/leak check).
3. **Regression protection in CI.** Per metric, research recommends hard gate vs report-only (owner decision: "mix, decided in planning", based on noise on the 16 GB CI runner / emulator). At least the crash-class scenario (b) is guarded so a reintroduced crash fails CI or a required check. **Where the per-metric Gate / Report-only table lives**: the budgets file `benchmarks/budgets/annotation-resource-budgets.json` (plan Story B.5, task B.5b: deterministic metrics gate, noisy ones report-only; ADR-001) and its promotion record (plan Story B.7, task B.7b, after >= 10 valid runs). Owner decision "mix, decided in planning" is satisfied by that table.
4. **Navigation is self-explanatory.** The owner can state, from the nav alone, when to use Assets vs Gallery; navigation destinations are organised into labelled sections with short descriptions. Measured as: a written IA decision (ADR) plus a UX review that finds no unlabeled/ambiguous destination, and the first-open smoke tests (`first-open-screens.txt`, `FirstOpenSmokeTest`) updated.

Starting from the nav alone (sidebar on desktop; bottom bar plus More on phone) with no prior knowledge, the driver must (a) reach "my annotated photos" and (b) reach "a file attachment" with **zero wrong taps**, where a wrong tap is opening any destination other than Library, or reaching Library and then needing more than one further tap (the Annotated filter chip) to see annotated photos. The same two tasks are also run by the owner on the phone once after release (device evidence).

Gallery is the annotated-only subset of Assets (ux.md section 1): annotating an asset makes it appear in both, so "my annotated photos" is findable in two places while "a file attachment" is findable in one, and neither name says so. The owner reports being unable to tell from the nav when to use which. 5. **Annotation feature review completed.** A written end-to-end review lists correctness, state-management, persistence, accessibility and test-coverage gaps with severities; every BLOCKER/CRITICAL is either fixed in this project or has a tracked follow-up. **Outcome evidence**: the Epic C story tests are green (plan Stories C.1-C.9, validation.md) and the C-findings checklist (plan section Verification checklist, one line per C1-C3/M1-M7/m-finding with its fixing task or follow-up link) is fully closed; the owner reviews that checklist.

6. **Post-release outcome for the crash (Amendment 3)**: on a build containing the PR-0 diagnostics and the Epic A fixes, the owner's phone shows **zero** `EXCESSIVE_RESOURCE_USAGE`, `ANR` and `LOW_MEMORY` exit reasons in `PreviousSessionLog` across **at least N = 10 annotation-editor sessions over at least M = 14 days** of dogfooding. (**"bad exit" is defined as any abnormal non-user exit after an editor session**: any exit reason other than a user swipe-away or a normal `USER_REQUESTED`/`EXIT_SELF` exit, in particular `EXCESSIVE_RESOURCE_USAGE`, `ANR`, `LOW_MEMORY`, `CRASH`, `CRASH_NATIVE`, `SIGNALED`, `INITIALIZATION_FAILURE`; the three named reasons are the ones the owner reported or the plan targets, the rest are counted as bad exits too.) A session is one app launch in which the editor was opened and at least 5 points were placed; sessions are counted from the persisted `DiagnosticsSample` lines, so a session with no sample does not count. **Calibration of N**: the owner's observed kill frequency is **unknown** (the report gives no rate), so N = 10 over 14 days is a starting value justified by the soak calibration (B.7: >= 10 samples is the smallest count at which the plan treats a rate as measured), not a derived sensitivity; the escalation clause below covers the case where it proves too small or too large. **Who evaluates**: the owner, at day 14, on the phone, reading the in-app Logs screen (`PreviousSessionLog` replay plus the `DiagnosticsSample` rows); the agent only tallies pasted lines. Missing data is "not yet satisfied", never "zero". Meeting this metric supports the words "no recurrence observed"; the owner decides whether it also earns "fixed". Until then the vocabulary stays "mitigated and monitored" (Amendment 2).
   **End condition and escalation (Amendment 4)**: the soak window is evaluated 14 days after the first release containing PR-0 and the Epic A fixes. (i) If at that date there are >= 10 qualifying sessions and zero bad exit reasons, the metric is met. (ii) If there are fewer than 10 qualifying sessions (insufficient data), the window is **extended once by 14 days** and the owner is told how many sessions were counted. (iii) If after the extension the data is still insufficient, or any bad exit reason appears at any time, the metric is not met and the project **escalates to an owner decision** with the evidence in hand (the `importance=` line, `DiagnosticsSample` rows, session count): continue monitoring with a stated end date, run a scripted-use soak on the phone, or accept "mitigated and monitored" as the permanent wording. It never silently stays open.

## Rabbit Holes

- **Measuring memory reliably on an emulator in CI**: heap numbers are noisy (GC timing, `Debug.getNativeHeapAllocatedSize`, bitmap pools, hardware bitmaps). Planning must pick metrics with acceptable variance (e.g. post-GC retained heap, peak bitmap bytes via a Coil/`ImageLoader` listener, `ActivityManager` exit reason) rather than raw RSS.
- **The crash may not be in image code**: back-to-back placement also triggers DB writes, undo-stack snapshots of the whole editor state (`pushUndo` stores full `AnnotationEditorState` copies, max-history bounded), repeated `saveMeasurements`, haptics and state flows. OOM may be Coil/loupe, but unbounded undo/redo history, `committedAnnotations` copies, or a coroutine leak are alternative suspects — research must test the loupe hypothesis, not assume it.
- **Per-press loupe decode**: caching/reusing one loupe bitmap vs. decoding per gesture changes memory/latency tradeoffs and interacts with the image-aspect layout fix (#558) and the `layout`-based placement (#560).
- **IA scope creep**: "organized sections and descriptions" can expand into a full navigation redesign across desktop sidebar, Android bottom bar, command palette, and first-run onboarding.
- **Gallery vs Assets semantics**: they may overlap by design (Gallery = photo-oriented view over capture/annotation images; Assets = file-oriented view of everything in the graph's assets folder). Merging them has data-model, deep-link and test-fixture implications.

## Alternatives Considered

- **Fix crash only, no benchmark suite** — rejected: memory regressions in this feature class only surface on-device and have recurred (#480, depth-model OOM work, this crash).
- **JVM-only memory tests** — rejected for crash-class coverage: desktop JVM does not reproduce Android's OOM-kills-process behavior and has different bitmap/native memory characteristics.
- **Third-party profiling in CI (Perfetto/Macrobenchmark memory traces)** — to be evaluated in research; the repo already runs an API 30 emulator benchmark job and benchdiff reporting, so extending those is the baseline option.
- **Merge Assets and Gallery into one destination** vs **keep both with sections + descriptions** vs **rename/re-scope each** — **DECIDED 2026-11-08 (Amendment 3): merge into one "Library" destination**; the other two options are rejected (history in ADR-006).

## Feasibility Risks

- **Riskiest assumption (Amendment 3): the reported kill is addressable through the app's own gesture path.** The plan assumes the "excessive CPU usage" kill comes from CPU the editor burns during or right after a placement burst (or from residual work after backgrounding) and can be reduced by the Epic A fixes. The alternatives, each of which the Epic A fixes would not cure, are: (1) the stock OS rule, which applies only to **cached/HOME processes** (>= 25% of a core over ~5 minutes; foreground apps are exempt, VERIFIED in AOSP android14 source, research/cpu.md section 1), so the kill would then be caused by work that continues after the app is backgrounded; (2) a non-stock OEM battery/CPU watchdog on the owner's phone, which no CI harness can reproduce. Evidence so far: no runaway CPU on the AVD (~100 ms CPU per press, 2-4% idle afterwards), so the assumption is unproven. Detection: the owner's Logs `importance=` line (W1), `DiagnosticsSample` rows from PR-0, the positive control (task A.3d) and the post-release metric (Success Metric 6). Mitigation: PR-0 ships diagnostics first; A.4e cancels depth estimation on `onStop` (the path that can burn CPU while cached); wording stays "mitigated and monitored".
- Emulator memory numbers may be too noisy for hard gates (mitigation: calibrate; gate only high-signal budgets; mixed policy chosen by the owner).
- The crash may need a physical low-RAM device profile to reproduce; the Pixel_Fold AVD might have more RAM headroom than the owner's phone (mitigation: AVD with constrained RAM / `-memory` flag, Coil cache pressure scenarios, `largeHeap` off).
- Instrumented tests are not in the required CI path today (the new `LoupeAlignmentE2ETest` is not run in CI); wiring them into CI affects runtime and flakiness budget.
- Nav IA change touches many call sites and the wiring/first-open gates; risk of regressions in deep links and onboarding.

## Observability Requirements

- Every benchmark scenario emits a machine-readable record (scenario, metric, value, budget, build SHA, device profile) consumed by the existing benchdiff PR-comment flow.
- Production-side: image-related OOM and low-memory signals are captured in the persisted logs (`AndroidFileLogSink`, `AndroidCrashRecorder`) with enough context (screen, image dimensions, cache size, undo depth) to diagnose without logcat; Android's exit reason continues to be replayed by `PreviousSessionLog`.
- Alert/oncall: none (single-owner app); the "alert" is a failing CI gate or a regression flagged in the PR comment.

## Risk Control

- Crash mitigation ships behind no flag (it is a bug fix) but lands with its proven-red gates (Amendment 2 criterion; plan Story B.5) and a bounded-resource invariant (e.g. cap on loupe decode size/frequency, bounded undo history) that can be rolled back by reverting one PR.
- New CI gates start **report-only** for noisy metrics and are promoted to **hard gate** per metric after calibration (policy decided per metric in planning).
- Navigation IA changes are shippable independently of the memory work (separate PR/epic) and reversible by reverting the nav PR; no data migration.
- Rollback procedure: revert the specific PR; benchmark gates can be switched back to report-only via a single config/threshold file.
