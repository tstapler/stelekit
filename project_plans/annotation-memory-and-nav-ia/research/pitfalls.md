The sources are downsampled to the view size (canvas measured 1768x1326), so the 8000x6000 case costs the same as 4000x3000. (VERIFIED for these numbers; the causal reading is INFERRED.)

## Code-reading findings relevant to the crash (VERIFIED by reading source)

1. **A new `ImageLoader` is built per loupe press.** `LoupeOverlay` is only composed while `loupeOffset != null` (`AnnotationEditorScreen.kt:476-478`) and calls `rememberSteleKitImageLoader()` (line ~1646), which does `remember(notesPath, fileSystem, context) { buildSteleKitImageLoader(...) }` (`SteleKitAssetFetcher.kt:~115`). Each press therefore builds a fresh Coil `ImageLoader`. The shared `MemoryCache` bounds cache bytes (comment in `SteleKitAssetFetcher.kt:70-76` says Coil keeps each built loader reachable via a registered ComponentCallbacks), but loader objects, their fetcher/decoder/OkHttp-like components and callback registrations accumulate. Measured effect over 100 presses: negligible (Java heap flat), but it is an unbounded-object-count smell and the likely place to hoist to a single `remember` at screen scope. (INFERRED that Coil 3 does not shut loaders down on dispose; observed flat memory contradicts a large cost.)
2. Main image `AsyncImage` has no explicit `size`, so Coil sizes to the composable (fillMaxSize), which is fine; loupe uses explicit `size(Size(w,h))` capped at 2048 long edge.
3. Coil memory cache keyed by (data, size): loupe entry (~2048 wide) and main entry are separate bitmaps cached concurrently (INFERRED from Coil key semantics).
4. No `onTrimMemory` / `onLowMemory` handling anywhere in androidMain (`grep` returned nothing). Coil registers its own ComponentCallbacks2 on Android to trim its cache (INFERRED, documented Coil behaviour), but app-owned caches (e.g. undo states) are not trimmed.
5. Undo stack holds up to 50 full `AnnotationEditorState` copies. `committedAnnotations` is an immutable List, so snapshots share elements structurally; cost per snapshot is the list array (O(n) refs), not point data (INFERRED from Kotlin immutable list copy semantics). Measured: flat at ~48 annotations.

## Part A - Known pitfalls checklist (INFERRED unless noted; general Android/Compose/Coil knowledge)

- **Coil 3 memory cache + large decode**: Coil downsamples to the target `size`; unspecified size on `AsyncImage` inside unbounded constraints decodes at full source size (48 MP ARGB_8888 = ~192 MB, OOM at 192 MB heap limit; bitmaps live on the native heap from API 26, but still count against RAM/lmkd). Always give an explicit bounded size for any non-layout-driven request (as the loupe does).
- **Per-gesture AsyncImage decodes**: a request keyed on gesture state (offset) re-decodes per move; keying on stable inputs (as `loupeModel` does) avoids it. Decode off-main is Coil's default, so ANR from main-thread decode is unlikely unless a custom synchronous fetcher/`SteleKitAssetMapper` does IO on main (not checked).
- **Recomposition allocating bitmaps**: `remember` keys that include fast-changing values (offset, canvasSize during animation) rebuild ImageRequests/loaders; hoist loaders and requests.
- **Hardware bitmaps**: Coil enables hardware bitmaps by default on API 26+; they cannot be read via `getPixels`/`copy` and have a per-process FD/GL texture limit (~ a few thousand, lower on some devices); bitmaps used for export/encode/pixel readback (`AnnotationExporter`, `PixelBufferConverter`, depth input) must request `allowHardware(false)`. Also hardware bitmap memory does not appear in Java heap or `Debug.getNativeHeapAllocatedSize` - use PSS/`summary.graphics`.
- **onTrimMemory**: respond to `TRIM_MEMORY_RUNNING_LOW/CRITICAL` by clearing app caches; Coil handles its own.
- **Undo-stack growth**: bound by count AND by size if snapshots hold bitmaps or large byte arrays; here count is bounded (50).
- **Coroutine/Flow leaks and StateFlow copy storms**: every `_state.update { copy }` per pointer move allocates; keep gesture-frequency state in `remember`/`mutableStateOf` and commit on up. Long-lived scopes need `CoroutineExceptionHandler` (CLAUDE.md rule).
- **Uncaught OOM kills the process on Android** and an lmkd kill leaves no stack; only `ApplicationExitInfo` (API 30+) reveals it - already replayed by `PreviousSessionLog`.
- **Emulator vs device memory**: emulator PSS/heap behave differently (software GL, no hardware-bitmap pressure; x86_64 host-allocated RAM; my AVD ignored `-memory 2048`). Physical low-RAM phones also have lmkd killing background-priority processes under pressure that an emulator with 3 GB free never exercises. Use `hw.ramSize` in the AVD `config.ini` and `dalvik.vm.heapgrowthlimit` to emulate; do not treat an emulator pass as proof.
- **Flaky memory assertions in CI**: raw PSS and uncollected Java heap are noisy (here Java heap swings 6-11 MB and PSS spiked +56 MB once at press 30 in v3, returning by press 35). Gate on post-`System.gc()` retained Java heap and native-allocated deltas across N presses (slope), with generous margins; report PSS peak as report-only. Observed noise floor: ~+-5 MB Java, ~+-3 MB PSS steady state, occasional 50 MB PSS transients.
- **Test harness gotcha (VERIFIED)**: `connectedDebugAndroidTest` uninstalls the app after the run, so files written to `cacheDir` are gone and cannot be `adb pull`ed; return data via the assertion/failure message (or `additionalTestOutputDir`).
