### Existing harnesses

1. **`AssetPipelineHeapGateTest`** (instrumented, `kmp:connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.class=...`): hand-rolled. `System.gc()` then `totalMemory-freeMemory` baseline; a daemon thread polls used Java heap every 20 ms (`SAMPLE_INTERVAL_MS`) and keeps the max (`:119-134,141-159`); asserts `peak < min(100 MB, 0.85*maxMemory)`; budget was set "from the first measured run on the Pixel_Fold AVD (run2 peak 49 MB of a 192 MB cap), about 2x headroom" (`:244-246`). Results go through `AndroidSpikeSupport.record` as `SPIKE-RESULT k=v` lines written to Logcat AND a MediaStore Downloads file (`console/spike/AndroidSpikeSupport.kt:76-95`). It is **not run in any CI workflow** (grep of `.github/workflows` finds only `SqliteCapabilityTest` and `AndroidGraphBenchmark` by class name, plus `:androidApp:connectedDebugAndroidTest` smoke). So today it is a local hard gate only.
2. **`SteleKitImageLoaderMemoryTest`** (jvmTest, pure): asserts all loaders share one `MemoryCache` instance and `maxSize in 1 until maxMemory/4` (`:21-33`). Static config check; says nothing about actual decode bytes.
3. **`android-benchmark.yml`**: `reactivecircus/android-emulator-runner@v2`, **api-level 30, x86_64, profile pixel_3a**, no `-memory` option (`:46-50`), runs `SqliteCapabilityTest` + `AndroidGraphBenchmark`; the benchmark prints JSON via `android.util.Log.i("ANDROID_BENCH", {...})` (`AndroidGraphBenchmark.kt:90,164`), the workflow does `adb logcat -d -s ANDROID_BENCH:I` in CI (`:54`), parses into `benchmarks/android-history/<ts>_<sha>.json`, `scripts/benchdiff-export.js --kind android` maps fields to benchdiff schema 1 (`benchdiff-export.js:24-33`, specs are `[field, group, unit, better]`), then `tstapler/benchdiff@v0.1.0` posts a sticky PR comment with tag `android-load-benchmark`. Report-only today: no step fails on a regression. Extending = add fields to the summary dict, add rows to the `android:` spec list in `benchdiff-export.js`, and add a metric emitter in the new test. NOTE the CI logcat read is the pipeline's existing mechanism and runs on the CI emulator, not the owner's machine; to honor the "no logcat" constraint for agents, a new emitter should ALSO write to an app-private/instrumentation file (see 5.4) so local runs never need logcat.
4. **`ci.yml` smoke job** uses API 29 with `-memory 2048` (`:342-348`); **android-benchmark.yml uses API 30**. The requirements say API 30: the memory gate belongs in/next to `android-benchmark.yml`, and its AVD RAM should be pinned explicitly (see 6).
5. **CI "ci-memory" / `mem-sampler`**: `tstapler/gha-actions/mem-sampler` wraps the Gradle command and `mem-sampler/report` posts the "CI memory (Gradle diff-coverage job, 16 GB runner)" comment (`ci.yml:236-272`). ## 2. Coil 3.2.0 levers (INFERRED unless a repo line is cited)

- **Memory cache sizing.** `MemoryCache.Builder().maxSizePercent(context, p)` (used at `SteleKitAssetFetcher.kt:80-82`) and `.maxSizeBytes(n)`. On Android the percent is applied to the app memory class (largeMemoryClass when `largeHeap`) — INFERRED; this means with `largeHeap=true` the 10% is of a larger number than in the heap-gate test config. Prefer an absolute `maxSizeBytes` cap derived from `min(percent*maxMemory, fixed ceiling)` so the budget is the same on emulator and phones. `MemoryCache.size` / `maxSize` are readable at runtime (`maxSize` is used in `SteleKitImageLoaderMemoryTest:30`; `size` INFERRED present in the same interface) -> cheap, deterministic "cache bytes" metric.
- **Per-request decode bounding.** `ImageRequest.Builder.size(Size(w,h))` (already used for the loupe), `.precision(Precision.INEXACT)` (default; lets Coil pick a cached larger/smaller entry and `inSampleSize` decode, the memory-friendly choice), `.scale(Scale.FIT)`. Memory-cache key includes the requested size, so each distinct `(w,h)` is a distinct entry -> loupe at a new canvas size or a rotation adds ~up to 2048xN x4 B (about 8-16 MB) entries. Mitigation: quantize the loupe size (e.g. round to 256 px steps) so presses reuse one entry.
- **Bitmap config.** `ImageRequest.Builder.bitmapConfig(Bitmap.Config.RGB_565)` halves bytes (2 B/px) but is lossy/banded; acceptable for the loupe magnifier only if the owner accepts it; keep ARGB_8888 for the annotated image and export (INFERRED: coil3 exposes `bitmapConfig` via `coil3.request` extension on Android).
- **Hardware bitmaps.** `allowHardware(true)` is Coil's default on API 26+ (minSdk is 26: `androidApp/build.gradle.kts:41`); hardware bitmaps live in graphics memory, do NOT count against the Java heap (so a Java-heap-only gate will not see them), and **cannot** be read with `getPixel`/software `Canvas` drawing. Consequence: (a) Java-heap metrics undercount the image cost; the gate must also read native/graphics memory (section 3); (b) the export path (`AnnotationExporter`, `ImageEncoder`) must decode its own software bitmap, never reuse the Coil one. Setting `allowHardware(false)` on a request is the switch if any pixel-reading code path consumes Coil output. Whether the editor currently receives hardware bitmaps is UNVERIFIED -> spike item.
- **Disk cache.** Not configured here (no remote images: local files via `SteleKitAssetMapper`, SAF). A disk cache brings no memory benefit; leave it off (INFERRED).
- **Measuring decode bytes without a profiler.** Register `ImageLoader.Builder.eventListenerFactory { EventListener ... }` (coil3 `EventListener`: `onStart`, `decodeStart/decodeEnd`, `onSuccess(request, SuccessResult)`; `SuccessResult.image` implements `coil3.Image` with `width`, `height`, `size: Long` bytes — INFERRED API shape, verify in 3.2.0 jar with `javap`). Accumulate `{count, sumBytes, maxBytes, maxW/H}` per scenario in a test-only singleton; assert "no single decode > N MB" and "decodes per press <= K". This is deterministic (depends on code paths, not GC timing) and is the highest-signal, lowest-noise gate for the loupe hypothesis. Also usable on JVM (Skia `Image`; `size` semantics differ, INFERRED) so a commonTest/jvmTest variant can guard decode-request counts.
- **Cache hit-rate / churn.** Count `onSuccess` with `result.dataSource == DataSource.MEMORY_CACHE` vs not (INFERRED field) to quantify churn for scenario (g).

## 3. Android memory metrics: what each really measures

| API | Measures | Noise | Use |
|---|---|---|---|
| `Runtime.totalMemory()-freeMemory()` after `System.gc()` | Java heap used (excludes hardware bitmaps; since API 26 pixel data of software bitmaps is in the *native* heap, so it ALSO excludes bitmap pixels) | Medium; `System.gc()` is a hint, run it 2-3x with short sleep | Retained-after-GC for leak/growth trend. Repo precedent `AssetPipelineHeapGateTest:141-144` |
| Peak sampler thread (repo precedent) | Peak Java heap | Medium-high: sampling interval misses spikes; 20 ms | Report-only or generous budget |
| `Debug.getNativeHeapAllocatedSize()` | malloc'd native bytes, includes software-bitmap pixel buffers (API 26+) | Medium; includes Skia/sqlite/ART internals | Good proxy for bitmap bytes on software-bitmap paths |
| `Debug.getMemoryInfo(Debug.MemoryInfo)` / `ActivityManager.getProcessMemoryInfo(pid)` -> `getTotalPss()`, `getMemoryStats("summary.graphics")`, `summary.native-heap`, `summary.java-heap` | PSS by category; `summary.graphics` includes GL/hardware-bitmap memory | Higher; vendor/kernel dependent; the call costs ~tens of ms | The only in-process way to see hardware-bitmap/graphics cost. Take AFTER settling (sleep 500 ms + gc) |
| `/proc/self/status` VmRSS, `VmHWM` | resident set; `VmHWM` is a kernel-tracked peak (no sampling gap) | High on emulator (page cache, shared libs) | `VmHWM` is the best cheap *peak* metric; still report-only |
| `Bitmap.getAllocationByteCount()` on bitmaps the test owns (export result, loupe) | exact | None | Hard gate: assert exported/decoded bitmap bytes <= budget |
| `ComponentCallbacks2.onTrimMemory` (existing `MemoryPressureListeners`) | OS pressure signal | Event-based | Production breadcrumb; in tests, call `ComponentCallbacks2` manually to assert caches shrink (`MemoryCache.trimMemory`) — a deterministic hard gate |
| `ApplicationExitInfo` `REASON_LOW_MEMORY` / `REASON_EXCESSIVE_RESOURCE_USAGE` / `REASON_SIGNALED` (SIGKILL) | why the OS ended the previous process (API 30+) | n/a | Already replayed in prod (`SteleKitApplication.kt:166-186`). In CI instrumentation, use for a "process did not die" check: after the scenario, query `getHistoricalProcessExitReasons` and assert no entry newer than test start. Caveat: a Java `OutOfMemoryError` shows up as `REASON_CRASH` (uncaught), not LOW_MEMORY; the lmkd kill shows as `REASON_LOW_MEMORY` or `REASON_SIGNALED` (INFERRED) |

Android caveat to carry into the root-cause analysis: with `largeHeap=true` a Java `OutOfMemoryError` is less likely than an lmkd kill (native/graphics pressure) — the owner's "abrupt close, no error screen" matches an lmkd SIGKILL or native OOM at least as well as a Java OOM (INFERRED; hypothesis, not evidence). A Java-heap-only harness would therefore miss the real failure; the harness MUST record native + PSS (graphics) and the exit-reason check.

## 5. Recommended measurement design (stack-level)

1. **`MemoryProbe`** test helper (androidInstrumentedTest; Kotlin, no new deps): `settle()` = 3x(`System.gc()`, `Runtime.runFinalization()`, sleep 100 ms); `snapshot()` returning `{javaUsed, nativeAllocated, pssTotalKb, pssGraphicsKb, vmHwmKb}`; `PeakSampler` as in `AssetPipelineHeapGateTest:119-134` plus native heap and a final `VmHWM` read; `exitReasonsSince(startMs)`.
2. **`CoilDecodeStats`**: test `EventListener.Factory` installed through a seam in `buildSteleKitImageLoader` (e.g. an optional `eventListenerFactory` param, default null) so tests observe decode count / max bytes / cache hit ratio.
3. **Scenarios (a)-(g)** from the brief, each: warmup pass (discard), `settle()`, baseline snapshot, N iterations, `settle()`, end snapshot. Record `retained = end - baseline` (stable), `peak` (noisy), decode stats (deterministic), exit-reason (binary).
4. **Emission** (no logcat dependency): write one JSON file per scenario to the instrumentation's `externalCacheDir`/`filesDir` and also `Log.i("ANDROID_BENCH", ...)` for the existing CI pipeline; CI step `adb pull` (or `adb shell run-as`) the file; fields: scenario, metric, value, budget, sha, device profile. The existing emitter `AndroidSpikeSupport.record` writes MediaStore Downloads and requires a pull from `Download/` (`:83-95`); either reuse it or write app-private files. Use `InstrumentationRegistry.getInstrumentation().sendStatus` is NOT needed.
5. **Wire into benchdiff**: extend the summary dict in `android-benchmark.yml` ("Parse results" step) and add specs to `scripts/benchdiff-export.js` `android:` list (e.g. `['annotRetainedMb','android/AnnotateMemory','MB','lower']`). Note the benchdiff spec is `[field, group, unit, better]` (`benchdiff-export.js:24-33`); the test `benchdiff-export.test.js` must be updated.
6. **JVM side**: keep `SteleKitImageLoaderMemoryTest` (static config) and add JVM tests only for pure logic (`ImageSampling`, decode-request quantization, undo-history bound) in `commonTest` per CLAUDE.md. JVM heap numbers are not a crash proxy (brief, "Android crash class is invisible on desktop"); do not gate on JVM RSS.

## 6. Emulator/CI configuration (INFERRED unless cited)

- Existing job: API 30 x86_64, profile `pixel_3a`, default AVD RAM (`android-benchmark.yml:46-50`). The smoke job sets `-memory 2048` (`ci.yml:348`). For crash-class reproduction pin RAM explicitly (e.g. `-memory 2048`; test a 1536 low-RAM variant) via `emulator-options` and `ram-size` (reactivecircus input; INFERRED name) so budgets are reproducible; also disable the Java heap growth limit differences: `adb shell getprop dalvik.vm.heapgrowthlimit/heapsize` and record `ActivityManager.memoryClass`/`largeMemoryClass`/`isLowRamDevice` in every record so budgets are interpretable.
- `-gpu swiftshader_indirect` (used in ci.yml smoke) makes graphics memory/hardware-bitmap behavior differ from a real GPU: graphics PSS numbers from CI are not comparable to the phone. Treat `summary.graphics` as report-only.
- x86_64 emulator on a GitHub runner has no lmkd pressure unless AVD RAM is small and the test pushes it; to *force* the crash class deterministically, prefer assertions on decode-request counts/bytes (deterministic) plus a stress test that exits cleanly, rather than hoping the emulator kills the process.
- Instrumented tests are not currently required checks; running them in `android-benchmark.yml` (API 30, already on PRs and push) matches requirement Open Question 7 with the least new infrastructure (add a third `./gradlew :kmp:connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.class=...` line, or `...class=a,b` / `package=` form). Each extra Gradle invocation re-installs the APK; batching classes into one invocation saves emulator time.

## 7. Hard gate vs report-only (recommendation)

| Metric | Stability | Policy |
|---|---|---|
| Max single decode bytes / px per request (Coil listener) | Deterministic | **Hard gate** (e.g. loupe <= 2048-edge budget; main image <= `MAX_DECODE_PIXELS` x4) |
| Decode count per N placements / per press (Coil listener) | Deterministic | **Hard gate** (catches per-press decode regression) |
| `MemoryCache.size` after scenario; `MemoryCache.maxSize` config | Deterministic | **Hard gate** |
| Undo/redo stack depth, committed-annotation count bounds (domain counters) | Deterministic | **Hard gate** (JVM + Android) |
| Exported/owned `Bitmap.allocationByteCount` | Deterministic | **Hard gate** |
| Process survived scenario (no new `ApplicationExitInfo`, instrumentation not crashed) for 50 back-to-back placements | Binary | **Hard gate** (scenario b = the crash-class guard) |
| LeakCanary / weakref "no retained editor VM/Activity" after N open-close cycles | Binary | **Hard gate** |
| Post-GC retained Java heap delta over N iterations | Medium (calibrate; repo precedent budgets at ~2x measured, `AssetPipelineHeapGateTest:244`) | Report-only for 5-10 runs, then gate at ~2x median or growth-slope-per-iteration ~0 (slope is more stable than absolute) |
| Retained native heap delta (`getNativeHeapAllocatedSize`) | Medium-high | Report-only -> maybe gate with wide margin |
| Peak Java heap (sampler) | Medium-high (sampling gaps) | Report-only (or generous gate like the existing 100 MB) |
| `VmHWM`, total PSS, `summary.graphics` | High on emulator (swiftshader, shared pages) | Report-only trend in benchdiff comment |
| Macrobenchmark `MemoryUsageMetric` | High | Report-only, optional |
| Wall-clock/latency | n/a | Existing SLOs (`kmp/TESTING_README.md`) |

Promotion rule matching the brief ("promoted after calibration"): keep thresholds in one checked-in file (e.g. `kmp/src/androidInstrumentedTest/resources/memory-budgets.json`, hypothetical path), tests read `budget` and `mode: gate|report`; collect >=5-10 CI runs, set budget = max(observed) x 1.5-2, flip `mode`. Rollback = flip the file entry.

## 8. Risks / unknowns for the plan

1. Are Coil's returned bitmaps hardware bitmaps in the editor (UNVERIFIED)? Decides whether Java-heap tests can see them at all.
2. The editor decodes via `AsyncImage` constrained by layout size, but the export path (`AnnotationExporter`, `ImageEncoder`, `PlatformImageDownscaler`) was not read in this run; their allocation behavior is out of this document's verified scope.
3. `largeHeap=true` in the shipped manifest vs the heap-gate test asserting it off: pick one config per gate and document it; record `memoryClass`/`largeMemoryClass` in every record.
4. `Coil 3.2.0` API shapes in section 2 (`Image.size`, `EventListener` hooks, `bitmapConfig`, `MemoryCache.size`, default `allowHardware`) are INFERRED; first plan task: `javap` the 3.2.0 `coil-core`/`coil-compose-core` jars (java-api-discovery skill) or write a 20-line spike test.

6. `adb logcat` is used by the existing CI parse step (`android-benchmark.yml:54`); acceptable on CI, but new emitters should not depend on it locally.
