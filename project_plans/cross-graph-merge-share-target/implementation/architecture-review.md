# Architecture Review: cross-graph-merge-share-target
**Date**: 2026-10-07
**Verdict**: CONCERNS (re-review 2 of N1, 2026-10-07: N1 RESOLVED in design; no remaining blockers; 3 new non-blocking concerns, see 'Re-review 2' at the end)

Constitution check: `docs/adr/ADR-000-architecture-constitution.md` does not exist; no constitution violations. kibitzer is on PATH and `.claude/inspect.json` exists, but its architecture export covers Go/TS/JS only, so Kotlin was reviewed by direct code reads (cited below).

## Blockers
- [ ] **ADR-001 / Story 2.1.1c / Story 2.3.2 (Router + `GraphWriteLock`) - the "lock makes the active-vs-off-graph choice race-free" claim does not hold against the real `switchGraph`.** `GraphManager.switchGraph` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/db/GraphManager.kt:804`) is a non-suspend `fun`. It synchronously updates the registry's `activeGraphId` and tears down the old graph. It then launches DB init on an IO coroutine, and `_activeRepositorySet` stays null until init completes. A `Mutex` cannot be taken in the synchronous part. If it is taken only inside the init coroutine, there is a window where the registry says "B is active" but no `RepositorySet` exists. `TargetWriterRouter` would then pick `ActiveTargetWriter` with nothing to write through, or pick `MarkdownTargetWriter` while init is reading the same files. The plan has no definition of "target is active" that is safe under this. Remediation: (a) define the router predicate as "`activeRepositorySet != null` AND `activeRepositorySet.graphId == target`", not registry `activeGraphId`. (b) If the target is the registry-active graph but not yet ready, the router awaits `awaitPendingMigration()` (`GraphManager.kt:974`), then uses the active writer. (c) The init coroutine takes `GraphWriteLock(id)` before its first read of graph files, and the lock hold covers "open + initial `loadDirectory`". Make this a named task, e.g. a new 2.1.1d "router readiness predicate + test: switch-in-flight", with a test that starts the merge while init is in flight. Also document that `forceReinit`/relocation also goes through the lock.
- [ ] **ADR-002 item 3 / Story 1.2.1 / Task 1.2.1a - the `isTakenInTarget` oracle is unavailable for off-graph targets.** The ADR keeps the source UUID when it is "free in the target" and remaps only on collision, because `blocks.uuid` is globally UNIQUE. For an inactive target, `MarkdownTargetWriter` only sees the one page file it is rewriting. The target DB is closed (ADR-001 deliberately avoids opening it), so a UUID used on a *different* page of the target is undetectable. The file then reconciles on next open into a UNIQUE conflict, which at best silently drops or replaces a block and at worst breaks load. Spike 0.1.3 measures what the repository does on collision, but nothing designs around it. Remediation: make the decision explicit in ADR-002. For off-graph targets, either (i) always apply the deterministic remap `uuid'` to every inserted block, rewriting `((ref))` within the selection and accepting that refs to un-selected blocks go stale; or (ii) pass a `TargetUuidIndex` port into `UuidRemap.compute`, implemented from a bounded filesystem scan of `id::` values. Pick (i) as the default because it is O(1) and fits the property-test model. Add an acceptance criterion to Story 1.2.1: "no input produces a UUID already present on a different target page without an index". Update Spike 0.1.3's output to feed this choice.

## Concerns
- [ ] **Task 2.1.1a/c, Task 4.4.1b, Story 4.4.1 Files list (debt deepening on the `GraphManager` hotspot).** The disposition says "only `GraphLocator` + `GraphWriteLock`; all new logic in new classes", but the file lists put the `GraphLocator` implementation and a `ShareInbox` drain hook in `GraphManager.kt` (1 478 lines, 51 commits in 6 months). The drain hook references `GraphActivated`, which does not exist: a grep of `kmp/src/commonMain` finds no such symbol. Task 4.4.1b says "observe `activeRepositorySet`" while the Files line says "call drain after `GraphActivated`". Recommendation: implement `GraphLocator` as a separate class that takes `graphRegistry` as a `StateFlow`; keep `GraphManager` edits to the single lock acquisition. Put the drain in a new `ShareInboxDrain` collector wired in `StelekitAppDependencies`. Remove `GraphManager.kt` from the 4.4.1 Files list. Note that "`activeRepositorySet` non-null" is not "initial load complete", so the drain should wait on a readiness signal (`awaitPendingMigration` or the loader's idle state).
- [ ] **Story 2.5.1 / Task 2.3.1a - the `TargetWriter` port is too narrow for Undo.** The port is `readExisting` + `write`. Undo must delete created page files (hash-checked) and remove blocks by UUID, and the plan says undo goes "via `TargetWriter`". Either `write` is overloaded with deletion semantics, which is a hidden contract, or the port grows ad hoc. Recommendation: define the port up front as `readExisting`, `write`, `deletePageFile(page, expectedHash)`, and `fileHash(page)`. Have `ActiveTargetWriter` implement delete through `GraphWriter`/`DatabaseWriteActor`. Add the new methods to the TargetWriter contract test shared by both implementations (Liskov: one contract-test suite run against both writers, which the plan currently lacks).
- [ ] **Story 2.4.1 - the picker's filters cannot be satisfied by "existing queries only".** Filters (journal/page, date range, namespace prefix, tag via page properties) plus search and a total count are specified as "SQL-bounded" (Glossary `SelectionFilter`). Task 2.4.1b implements them over `getPages(limit, offset)` with an in-memory `SelectionFilter` predicate. That means scanning all 8 000 pages in 100-row batches on every filter or search change, and the count query does not exist. The AC "each call returns <= 100 rows and total count via a count query" is therefore unsatisfiable without new queries. Recommendation: decide now. Either add bounded `.sq` queries (with `RestrictedDatabaseQueries` stubs where needed, `QueryPlanAuditTest`, and regenerated sources, so the "no schema change" claim must be restated as "queries only, no table"), or use the existing FTS/`getPageNameEntries` projection for name/namespace/journal-date filtering and restrict tag filtering to a second, bounded pass. Do not leave it as "preferred, otherwise".
- [ ] **Story 4.1.3 Task 4.1.3b vs Story 2.3.2 `TargetWriterRouter`.** There are two routers (active / off-graph / inbox for share, and active / off-graph for merge), each with its own lock handling. Recommendation: one `TargetWriterRouter`, with the inbox as a share-only fallback decorator (`InboxFallbackAppender`). Otherwise the lock and readiness logic from Blocker 1 will be implemented twice.
- [ ] **Task 1.2.2 `PageFileResolver.supportsOffGraphWrite` and Task 4.5.1a `TargetWriterCapabilities`.** Capability policy (crypto, SAF grant, platform FS reach) is split across a path resolver and a separate capabilities class. A pure path function should not carry a policy predicate. Recommendation: `PageFileResolver` resolves paths only; `TargetWriterCapabilities` owns all "can I write there" checks (crypto layer, SAF grant, platform), consumed by the router. Story 1.2.2's second AC moves to 4.5.1 (or an earlier Phase 2 story), since the router needs it before Phase 4.
- [ ] **Story 1.2.2 / Unresolved Questions - journal file naming.** Verified: `GraphWriter.getPageFilePath` (`GraphWriter.kt:790`) uses `FileUtils.sanitizeFileName(page.name)` and has no journal-date-to-filename logic. Story 4.1.3 and Story 1.2.2's AC use `journals/2026_10_07.md` and "Oct 7th, 2026 resolves under /g/journals/". Off-graph journal creation for a target with a different date format is exactly where the off-graph writer can diverge from `GraphLoader`'s expectations. Recommendation: make Task 1.2.2a's first step to read the journal-name-to-file mapping used by `GraphLoader` and the existing capture path, and record it in the Resolver's KDoc. Add a round-trip test: resolver path -> `GraphLoader` parses it back to the same journal date.
- [ ] **Dangling plan references.** "Stories 1.1.4" appears in Unresolved Questions and the Spike 0.1.3 gating, but no Story 1.1.4 exists (the converters story is 1.1.3; "Task 1.1.4c" also has no parent). Fix the references so the gate map is checkable.

## Nitpicks
- Story 4.1.3: routing a one-block append through the full `mergePage` machinery is heavier than needed. It is acceptable only because it reuses the identical idempotence path; keep the call, but avoid a separate `OffGraphJournalAppender` hierarchy beyond a single class.
- Story 4.2.1 Files: `androidApp/src/test/kotlin` does not exist (verified); the plan says "confirm existing test dir via Glob". Settle this before the task starts.
- `PageSelection` is a good value class; consider also a `CaptureId` value class (currently a raw String in `JournalAppender.append`) given idempotence depends on it.
- Glossary says `PageMergeService` "replaces `GraphMergeService`" while the disposition says it remains as a deprecated adapter until Story 3.4.2; pick one sentence.
- Observability: an explicit `merge.apply` lock-wait-time metric would make Blocker 1's mitigation observable.

## Re-review (scoped to previously BLOCKED items) - 2026-10-07
Verified against `GraphManager.kt` (switchGraph 804-968, tearDownActiveGraphResources 508-518, awaitPendingMigration 974-977) and the revised plan.md / ADR-001 / ADR-002.

**Original blocker 1 (lock vs `switchGraph`): RESOLVED in design.** Plan's code facts match the code: `switchGraph` is non-suspend (804); `_activeRepositorySet` nulled synchronously (514); init coroutine sets it (904) and completes `deferred` in `finally` (957-959); registry `activeGraphId` is set at 964 after the launch. Taking the lock inside the init coroutine (Task 2.1.1c), the `readyGraphId` predicate (Story 2.1.2) and awaiting `awaitPendingMigration()` are all sound shapes, and in-flight tests exist in both directions.

**Original blocker 2 (UUID oracle off-graph): RESOLVED.** Always-remap with no `isTakenInTarget` (ADR-002 rev. 2, Story 1.2.1); no stale references remain (grep: only the withdrawal text). Clobber guard against `INSERT OR REPLACE` is specified (Task 1.2.1c).

### New blocker introduced by the repair
- [x] **N1 (RESOLVED, see Re-review 2) - deadlock if the router awaits `awaitPendingMigration()` while holding `GraphWriteLock(B)`.** Task 2.1.2b and Story 2.3.2 say the router decides and awaits "under `GraphWriteLock`". But the init coroutine takes `GraphWriteLock(B)` before creating the repo set and completes `_pendingMigration` (`GraphManager.kt:958`) only after releasing it. A router that holds lock(B) and awaits the deferred waits on init, which waits on lock(B). Remediation (spec only): the router must await readiness OUTSIDE the lock, then take the lock and re-check `readyGraphId == target`; if it changed, loop (bounded). Add a test: `switchGraph(B)` returns, router called before init finishes, with the lock-holding order asserted. Also state a lock order (never hold lock(X) while acquiring lock(Y); the init coroutine's previous-graph close and incoming-graph open must not nest) so two concurrent switches cannot deadlock.

### New concerns (non-blocking)
- `awaitPendingMigration()` awaits the *current* `_pendingMigration`, which each `switchGraph` replaces (line 845). A router that grabbed it for B can return the repo set of C after a second switch; re-check `readyGraphId == target` after the await (covered by the N1 fix).
- Story 2.1.2 active-to-inactive AC assumes lock(A) alone protects an in-progress `ActiveTargetWriter` batch. `switchGraph` also cancels A's `activeGraphJobs` scope synchronously (825) before any lock is taken. Whether `DatabaseWriteActor` lives in that scope was not verified (CLAUDE.md says it owns its scope; `createRepositorySet` is passed `scope = graphScope`). The retryable-error fallback in the AC covers it; keep that test.
- `readyGraphId` set at 904 precedes migrations (910-931); safe only because the init coroutine holds lock(B) through them, as the plan specifies. Keep that ordering explicit in Task 2.1.1c.
- Other concerns from the first review are marked addressed in the plan's Repair log but were out of scope here and not re-verified.

## Re-review 2 (scoped to N1 and the R1-R4 edits) - 2026-10-07
Verified against `GraphManager.kt` switchGraph (804-968) and `awaitPendingMigration` (974-977) and the repaired plan.md (Story 2.1.2, Tasks 2.1.1c/2.1.2b, Story 2.3.2) plus ADR-001 rev. 3 and ADR-002 rev. 3.

**Verdict: CONCERNS. N1 is RESOLVED; no blockers remain.**

Why the new algorithm does not deadlock (checked against code):
- The router awaits `_pendingMigration` with no lock held. The init coroutine can therefore take `lock(B)`, and `deferred.complete(Unit)` runs in its `finally` (957-959), outside the lock (Task 2.1.1c releases "just before `deferred.complete`"). The wait-for cycle router -> init -> lock(B) -> router is gone.
- Cancellation is safe: `switchGraph(C)` cancels B's scope; `Mutex.withLock` releases on cancel and the `finally` still completes B's deferred, so a router awaiting B's deferred is always released. `awaitPendingMigration()` reads `_pendingMigration` at call time, so a router entering after C sees C's deferred; either way the in-lock re-check decides.
- Lock order is normative and acyclic (one graph lock at a time; previous-graph close and incoming open are separate sections). Retries are bounded (3) and end in a retryable `Left`, so no livelock.
- Wrong-graph return: the router ignores the `RepositorySet` that `awaitPendingMigration()` returns and gates on `readyGraphId == target` under `lock(target)`. While the router holds `lock(B)`, a concurrent `switchGraph(C)` can null `_activeRepositorySet` (synchronous teardown, line 514) but C's init cannot publish C's set until it has passed `lock(B)` for the previous-graph close, so the set seen under `lock(B)` is B's or null, never C's.
- R1-R4 / ADR-002 rev. 3: no new blocker. The conflict-sibling uuid (`merge-conflict:` hash) is deterministic, distinct from `uuid'`, and the "any block under matched parent with equal src-id and content" rule keeps repeat copies idempotent. ADR-001 rev. 3 text matches the plan's lock protocol.

### New concerns (non-blocking, fix in plan before Phase 2 starts)
- [ ] **C-1 (must-fix wording, same deadlock class).** Task 2.4.2d says `apply()` runs "per page under `GraphWriteLock`", while the router (Task 2.3.2b) also takes `lock(target)` per write. `Mutex` is not reentrant, so a service that holds the lock and then calls the router self-deadlocks, and it contradicts the one-lock-at-a-time rule. Fix: reword 2.4.2d to "per page through `TargetWriterRouter` (which owns the lock)"; state that `GraphWriteLock` is non-reentrant and only the router/init coroutine acquire it. The Task 2.1.1c assertion helper should be wired into the router tests to catch this.
- [ ] **C-2 (atomic snapshot).** `readyGraphId` and `_activeRepositorySet` are two reads. Require the accessor to return a single `(GraphId, RepositorySet)` pair (or the router to capture the set once under the lock and treat null as "retry"), since the synchronous teardown at 514 is not covered by any lock.
- [ ] **C-3 (which id's lock guards the close).** Task 2.1.1c says to lock `previousId` around `factoryToClose?.close()`. `previousId` must be captured synchronously (registry `activeGraphId` at ~822), and under rapid B-then-C switches the factory handed over by `tearDownActiveGraphResources` may belong to A, not B. Key the lock by the graph that owns the factory being closed (track the owner id next to `currentFactory`), else a batch on A is not protected.
- Unverified (carried over): whether `DatabaseWriteActor` senders unblock when A's `graphScope` is cancelled while a batch holds `lock(A)`; if not, init blocks on `lock(A)` indefinitely. The planned `withTimeout` two-switch test with an injected cancel should cover it; keep it.
