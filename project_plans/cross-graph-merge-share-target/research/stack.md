## Bottom line
No new third-party dependency is needed. Everything builds on existing commonMain code (Arrow, okio, kotlinx-coroutines/serialization, SQLDelight, kotest-property already on classpath). ## Cross-graph write design options (decision for the plan; constraint is verified)

1. Multi-open `GraphManager` (second `RepositorySet` for the target, own driver and write actor). Cleanest for DB consistency; largest change (`GraphManager` is 1478 lines, with `currentFactory`, `activeGraphJobs`, coordinator caches, git/vault services keyed to the active graph). Risk: pooled JDBC driver opens 8 connections per graph (CLAUDE.md, JVM), and the file watcher / `GraphLoader` for the target must not fight the active graph's watcher.
2. Short-lived "side-open" of the target: create a throwaway `RepositorySet` via `RepositoryFactory` for the target `GraphId`, perform the bounded write, close it. Keeps `GraphManager` single-active semantic; fits both merge and share. Needs a new narrow API (e.g. `GraphManager.withGraph(id) { repoSet -> }`) that refuses the active id (reuse active set) and serializes against `switchGraph`. INFERRED: DB-level feasibility depends on `DriverFactory` allowing a second driver on a different file; per-graph DB URLs suggest yes, but not run.
3. Direct markdown write to the target's files (via `GraphWriter`/`FileSystem`), index lazily when that graph is next opened. No DB needed, works when the graph is closed; but the loader must reconcile externally added files (existing `externalFileChanges` path) and duplicate-block/idempotence logic must work from parsed markdown rather than DB rows. Best fit for share-to-inactive-graph on Android where `CaptureActivity` may run before any graph is open.
4. Queued inbox consumed on next switch: weakest for the "lands in the chosen graph in one step" metric (not visible until switch).

Recommendation (INFERRED, to be confirmed in architecture research): option 2 for merge (needs block UUID/DB reads on both sides), option 3 or 2 for share; avoid option 1 unless required.

## Patterns that apply
- Pure merge function in `commonMain` (`mergeBlocks(targetBlocks, sourceBlocks): MergeResult`) with match order UUID then trimmed-content; property union; conflicts as a separate list. Tested with kotest-property (`Arb`/`checkAll` in `runTest`), per CLAUDE.md; invariants: idempotence (`merge(merge(t,s),s) == merge(t,s)`), no target block lost, no duplicate UUIDs. Reference example: `HostReconciliation.kt` / `HostReconciliationTest.kt`.
- Arrow `Either<DomainError, T>` at service boundaries; extend `GraphMergeResult` with merged/unchanged/conflicted counts and a `DryRunSummary` (new/merged/unchanged).
- Writes only via the target's `DatabaseWriteActor`; `saveBlocksDiff(toInsert, toUpdate)` for additive writes; chunked <=500 per `IN` clause; no new `@DirectSqlWrite` surface unless a new query is added.
- Staging for large selections: stream per-page (read source page, read target page, merge, write) rather than snapshot; if two-step across graph switches is retained, stage to a directory (cf. `RelocationStagingDirectory`) instead of memory (not opened; name from requirements).
- `Logger` counts per Observability section; failures to snackbar via existing `NotificationManager` (desktop controller already uses `notificationManager.show(..., NotificationType)`).
- Coroutine scope: any new long-lived merge/share class owns its scope (no `rememberCoroutineScope` leak); attach `CoroutineExceptionHandler` for long-lived scopes.

## Dependencies
- None required. Already present: Arrow, okio 3.17.0 (kmp/build.gradle.kts:129; fakefilesystem for tests :156), kotlinx.serialization (used by `GraphManager`), kotest-assertions/property, SQLDelight 2.3.2.
- ZXing (`com.google.zxing:core:3.5.4`) is QR-only and irrelevant here (only retained because merge currently reuses `QrImportService`; the new block merge should not depend on the QR package).
- Optional for iOS/Web share (open question): no library; iOS needs a native Share Extension target (Xcode, app-group container to hand data to the main app); Web needs a PWA manifest `share_target` entry plus a service-worker/route handler. Both exceed "cheap" for this scope (INFERRED; not researched in depth).

## Schema/migration impact
Selection/staging can be in-memory or file-based; no new table is required. If a persisted inbox or merge-history table is added, it must appear in both `SteleDatabase.sq` and `MigrationRunner.all`, SQLDelight sources must be regenerated and committed (CLAUDE.md), and `MigrationRunnerSchemaSyncTest` will enforce it.
