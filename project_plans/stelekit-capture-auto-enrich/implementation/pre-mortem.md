# Pre-mortem: stelekit-capture-auto-enrich
**Date**: 2026-08-27

Both `architecture-review.md` and `adversarial-review.md` are CLEAN with no open blockers/concerns —
the concurrency and graph-identity bugs they found (coordinator race, save/accept race, scan-collector
death, graph-switch TOCTOU) are genuinely fixed. This pre-mortem intentionally does not re-litigate
those; it looks at product, data-quality, operational, and field-environment risks a code-level review
wouldn't surface.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The chip tray (AC #2/#3, the feature's only value-add beyond auto-linking) goes unused: quick-capture is optimized for a single Save tap under time pressure (Success Metrics explicitly promises "zero additional taps... when the user just hits Save"), so most captures never get a topic-suggestion tap even when good candidates are shown; the feature quietly reduces to "auto-link only" for the median user. | Anecdotal — bug reports or user comments noting "I never even notice the chips," with no way to confirm or refute at scale (see #3: no telemetry exists to measure chip-tap rate vs. capture count). | Add a lightweight, privacy-safe local counter (not server telemetry — matches Observability Plan's "no metrics" scope but at least gives dev-mode visibility) or, at minimum, explicitly note in validation.md that adoption cannot be measured post-ship and decide up front whether that's acceptable for a v1 ship gate. | P2 |
| 2 | AC #1's auto-link path (`ImportService.scan` → save `linkedText` directly) has **no review step** — unlike Import's full-screen review or the chip tray's explicit-tap requirement — and `AhoCorasickMatcher`/`ImportService.scan` (verified: `kmp/src/commonMain/kotlin/dev/stapler/stelekit/domain/AhoCorasickMatcher.kt`, `ImportService.kt`) has no minimum-term-length or common-word guard. On a real, messy personal wiki with short/generic page names ("Today", "Ideas", "Review", "1:1", a person's first name also used as a common word), ordinary captured sentences get silently rewritten into wrong `[[links]]` before the block ever reaches disk. Story 3.2.1's read-only preview caption is the only mitigating signal, and it is muted/secondary-styled text below the field in a sheet optimized for a single fast Save tap — easy to never look at. | A journal page accumulates unexpected backlinks to unrelated stub/existing pages; user notices only when browsing a page's "Linked References" much later and can't recall which capture caused it, since nothing in the UI ever asked for confirmation. | Before implementation, decide a minimum-match-confidence or minimum-term-length floor for the *auto-apply* path specifically (distinct from the chip-suggestion path, which already requires a tap) — e.g., require matched page names ≥2 words or above a length threshold to auto-link, falling back to a suggestion chip (review-gated) for single short-word matches. Document the chosen floor and its rationale in plan.md/ADR, and add a regression test asserting a short/common existing page name is *not* auto-linked without review. | P1 |
| 3 | Observability Plan is log-only ("no existing capture-specific telemetry event API... out of scope") and Risk Control explicitly rejects a feature flag ("would violate the 'no new abstractions beyond what the task requires' constraint"). If any of the above (or an unanticipated matching/performance regression on a large real graph) ships, there is no metric, alert, or kill switch — only user bug reports, and the stated rollback procedure is "revert the wiring commit(s)" via a fresh release. | A cluster of GitHub issues describing vague, hard-to-reproduce symptoms ("random links appearing," "capture feels slower than before") with no server-side signal to correlate them, days-to-weeks after the release that introduced the regression. | Add a minimal local (on-device, not server) debug log ring buffer or a `BuildConfig`-gated verbose log level so a filed bug report can be paired with `adb logcat` output naming the exact `Logger("CaptureViewModel")`/`Logger("CaptureEnrichmentCoordinator")` lines already planned — cheap addition that doesn't add a new abstraction, just makes the already-planned logs retrievable from an affected user. Separately, reconsider the "no feature flag" call given #2's blast radius — a `Settings`-backed boolean gate for the auto-link *write* path (not the whole feature) is a small addition that turns a full-release rollback into a remote-config-free but still user-toggleable off-switch. | P1 |
| 4 | AC #3's opt-in on-device tier assumes `LlmProviderRegistry.availableForFeature(CAPTURE_ENRICHMENT)` reliably reflects real usability. Per `research/pitfalls.md`'s cited `llm-service` §2.1/§0 findings, ML Kit/AICore's `checkEligible()`/`format()` tri-state can report `DOWNLOADABLE`/`DOWNLOADING` inconsistently, and `GraphManager` builds its *own* lazily-constructed `LlmProviderRegistry` (Pattern Decisions table, plan.md:51) separate from the one `App.kt`/`TagSuggestionEngine` use — so a user who has the on-device tier "working" in `MainActivity` for tag suggestion can still get a silently-never-firing `CaptureEnrichmentCoordinator.enhance()` (quota contention between two live registries, or a `DOWNLOADABLE`-but-treated-as-available provider) with zero distinguishing signal between "no provider configured" (by design, not an error) and "provider configured but non-functional" (a real bug indistinguishable from the default state). | A user believes they configured on-device enrichment (it works elsewhere in the app) but capture's chip tray only ever shows local-heuristic suggestions — silent, un-diagnosable without reading debug logs, and easy to write off as expected behavior. | Log resolution outcome distinctly at coordinator-construction time — not just enrichment failure — so `Logger("CaptureEnrichmentCoordinator")` records *which* branch `resolveTopicEnricher()` took (`NoOpTopicEnricher` because empty registry vs. because every available provider's `checkEligible()` returned non-`AVAILABLE`) per capture session. This turns an indistinguishable silent-degrade into a diagnosable one without adding user-facing UI or a new abstraction. | P2 |
| 5 | `CaptureActivity` only reads `EXTRA_TEXT`/`EXTRA_SUBJECT`/`clipData` (confirmed: no URL-fetch/article-body extraction anywhere in `CaptureActivity.kt`/`CaptureViewModel.kt`, unlike `ImportState`'s `urlInput` path referenced in the Pattern Decisions table). Requirements.md's Success Metrics showcases "a shared article/URL... lands in today's journal with existing-page mentions already linked" as the flagship scenario, but many Android apps' share sheet for "share this article" sends only the bare URL (and sometimes a title) as `EXTRA_TEXT`, not the article body. Against a bare URL string, `PageNameIndex` matching has nothing to match and `TopicExtractor`'s heuristic noun-phrase extraction has no article text to extract from — the flagship use case can routinely produce zero auto-links and zero useful suggestion chips, while still looking, to the implementer, like it "worked" against the test fixtures used during development (which likely used prose text). | Early user feedback along the lines of "I shared an article and got nothing — thought this feature was broken," specifically for browser share-sheet captures, while manually-typed or copy-pasted prose captures work fine. | Before implementation, verify what real Android apps (Chrome, a few popular RSS/read-it-later apps) actually put in `EXTRA_TEXT` for "Share" on an article, and add an explicit test fixture using a bare-URL `EXTRA_TEXT` (not just prose) to `CaptureViewModelTest`/`CaptureEnrichmentCoordinatorTest` asserting the *expected* (even if "no suggestions" is the honest expected result) rather than assuming prose-only input. If bare-URL shares turn out to be the common case, scope-note this explicitly as a known v1 limitation in requirements.md rather than letting the Success Metrics implicitly overpromise. | P2 |

## P1 Items (address before implementation)

- [x] Failure #2 — Addressed in `implementation/plan.md`: added an auto-apply/confirm-first
  partition (`partitionForAutoApply()`, Task 1.1.1b) — multi-word matches, or single-word
  matches ≥6 characters, auto-apply unchanged; shorter single-word matches are withheld from
  `linkedText` and instead surface as a reviewed "confirm existing link" chip reusing the
  existing suggestion-chip UI (Epic 3.1/3.2, Task 4.1.4a). Regression tests: Story 5.1.1
  (coordinator-level partition test, e.g. "Today" withheld vs. "Kotlin Multiplatform" unaffected)
  and Story 5.2.10 (`CaptureViewModel`-level accept/dismiss coverage).
- [x] Failure #3 — Addressed in `implementation/plan.md`'s Risk Control section: Failure #2's
  precision floor substantially reduces the blast radius that motivated the flag suggestion
  (the highest-risk case — silent auto-link of short/generic names — is now review-gated, not
  silently written), so the existing "no feature flag" decision stands, with this reasoning now
  stated explicitly. The already-planned `Logger("CaptureViewModel")`/
  `Logger("CaptureEnrichmentCoordinator")` calls are retrievable via standard `adb logcat` —
  no separate debug-log abstraction was added, per the "no new abstractions" constraint.

## Summary

2 P1, 3 P2, 0 P3. Top failure mode: AC #1's auto-link write path has no review gate and no minimum-match
threshold, so on a real, messy personal wiki it will silently rewrite ordinary sentences into wrong
`[[links]]` with no confirmation step and no way to detect the resulting damage after the fact — the one
finding here that plausibly causes real data-quality harm rather than just "the feature underdelivers."
