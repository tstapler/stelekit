# Research: Similar Features & Capture-Specific Gaps

**Agent**: 2 (Features)
**Date**: 2026-08-27

## Summary

`ImportViewModel` and `TagSuggestionEngine`/`TagSuggestionViewModel` between them cover
almost every mechanical piece this feature needs (debounced scan, local-first + async LLM
enrichment, confidence-tiered chips, per-request cancellation). What neither one has ever
had to solve is: **(a)** building a `PageNameIndex` on demand instead of receiving an
already-running one, **(b)** a hard save-not-blocked-by-scan contract, **(c)** writing a
suggestion's effect into a block *after* that block is already persisted. All three are
required by this feature's acceptance criteria (AC 4, AC 8, AC 9) and none of them has
precedent in the existing code.

---

## 1. What Import and Tag-Suggestion already solve (reuse as-is)

### `ImportViewModel` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/ui/screens/ImportViewModel.kt`)

- **Debounced scan pattern** (`onRawTextChanged`, lines 174–195): 300ms `delay()` + `scanJob?.cancel()` on every keystroke, then `runScan(text, matcher)`. Capture's text-change handler needs the same shape.
- **Matcher-becomes-available reactivity** (`init`, lines 163–172): if `matcherFlow.value` was null when the debounced scan ran, nothing re-triggers it *except* this collector — it watches `matcherFlow` and re-runs the scan once a non-null matcher shows up, provided `rawText` is still non-blank. This is exactly the shape capture needs for its cold-start case (matcher not built yet when text arrives) — but Import gets `matcherFlow` as an already-live `StateFlow<AhoCorasickMatcher?>` constructor parameter (built by `StelekitViewModel` before `ImportViewModel` ever exists). Capture has no such parameter to inject — it must build the `PageNameIndex` itself, which is the new problem (see §2.1).
- **Local-first + async LLM merge** (`runScan`, lines 216–267): scan+local suggestions land synchronously in state; if `topicEnricher !is NoOpTopicEnricher`, a second coroutine does `withTimeout(8_000) { topicEnricher.enhance(...) }` and merges non-destructively via `mergeEnrichedSuggestions` (dismissed-term tracking survives re-scans, capped at 15). Directly reusable for capture's opt-in LLM tier (AC 3).
- **Per-suggestion accept/dismiss state machine** (`onSuggestionAccepted`/`onSuggestionDismissed`, lines 309–331): flips `accepted`/`dismissed` flags and re-inserts `[[wiki links]]` into `linkedText` via `ImportService.insertWikiLinks`. Reusable for the chip tray's tap-to-accept.
- **Stub-page creation loop** (`confirmImport`, lines 403–418): `for (suggestion in acceptedSuggestions) { ...; pageSaver.save(stubPage, emptyList(), graphPath); ... }` — **note this loop is NOT try/caught per-iteration**. A `pageSaver.save` throw here aborts the whole loop and the page-name-collision-checked `pageSaver.save(page, blocks, graphPath)` a few lines below never runs. This is the exact gap the requirements doc calls out as "do not copy" (AC 7) — Import has never needed per-suggestion isolation because a stub-creation failure today aborts the *entire* import, which is merely bad UX; for capture it would also abort the Bug-8 markdown flush for an already-in-flight journal write, which is a correctness regression, not just bad UX.

### `TagSuggestionEngine` / `TagSuggestionViewModel` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/tags/`)

- **`checkAvailability` non-blocking probe pattern** (`TagSuggestionEngine.kt:26`, consumed in `TagSuggestionViewModel.runLlmSuggest`, lines 119–181): the reference implementation for talking to `LlmProviderRegistry` without blocking on a cold on-device model — poll `checkAvailability()` on a schedule, only call the real inference (`engine.llmSuggest`) once, then again after `Available` is observed. Directly reusable for capture's on-device LLM tier (AC 3, "including on-device tiers").
- **Local/LLM split with immediate local emission** (`requestSuggestions`, lines 207–271): `engine.directMatch(blockContent)` (AhoCorasick exact hits, confidence=1.0, always `autoApplied=true`) is emitted to state *before* the LLM coroutine is even launched — same "local floor is not a degraded state" principle the requirements doc states for capture (line 65, 86–87).
- **Cache keyed by block UUID, survives `dismiss()`** (lines 70, 330–334): lets a suggestion job finish in the background after the UI dismisses and serves instantly on reopen. Capture doesn't reopen the same block the way the editor does, so this exact cache isn't needed, but the *pattern* (don't cancel a job just because the UI navigated away) is relevant to AC 9 — see §2.3.
- **What it never does**: nowhere in `TagSuggestionEngine`/`TagSuggestionViewModel` is there a call that writes an accepted suggestion back into block content or into the database. The actual "fold accepted tag into block" write lives entirely at the UI call site (not found in these two files) — i.e. **there is no existing production code, in either Import or Tag-Suggestion, that writes a suggestion's effect into an *already-persisted* block.** Import's stub-page write happens as part of the *same* `confirmImport()` transaction that creates the parent page — nothing is persisted yet when suggestions are accepted. Tag-suggestion's engine only ever proposes; something else (not these files) applies. AC 9's "second `writeActor.saveBlock()` call on the same `BlockUuid`, after the first save already committed" is genuinely new — there's no reference implementation to copy, which is why the requirements doc requires this project write its own ADR-002 for it.

## 2. What's genuinely new for the capture context

### 2.1 Race-safe on-demand `PageNameIndex` construction (AC 8)

`StelekitViewModel` builds its `PageNameIndex` once, eagerly, at ViewModel construction (`ui/StelekitViewModel.kt:518`, `val pageNameIndex = PageNameIndex(pageRepository, scope)`) — by the time any screen (including `ImportViewModel`, which receives `matcherFlow` as an already-`stateIn()`'d parameter) needs it, it already exists and is warming up. **`CaptureActivity` has no such guarantee**: it's launched directly by the share sheet / tile / widget, and per `SteleKitApplication`/`GraphManager` wiring, `CaptureViewModel.performSave()` already has to null-check `graphManager.getActiveRepositorySet()` (`CaptureViewModel.kt:76`) because there may be no `StelekitViewModel` — and therefore no `PageNameIndex` — running in this process at all.

- `PageNameIndex`'s constructor (`domain/PageNameIndex.kt:35`) takes `(pageRepository, scope, ...)` and starts a `scope.launch` collector immediately (line 76) that debounces 500ms (`REBUILD_DEBOUNCE_MS`) before the first matcher build. Building one is not instantaneous even in the best case.
- Nothing in the existing code ever constructs a *second* `PageNameIndex` for the same graph concurrently, so there's no existing single-flight/memoization pattern to copy. The AC 8 requirement ("`Mutex` or memoized `Deferred`, not a plain nullable-field double-checked pattern") has no analog in Import or Tag-Suggestion — both receive their matcher pre-built.
- Concrete race window: `CaptureActivity.onCreate()` calls `viewModel.initializeText(...)` synchronously before `setContent {}` (line 79–86), but the coordinator/`PageNameIndex` build has to happen asynchronously off that path (see §2.4 below on first-frame budget). If the coordinator is built lazily on first text-change event and the user's paste/type produces two rapid text-change events before the first build finishes, whatever memoizes the coordinator must not start two `PageNameIndex` instances — each of which would independently subscribe to `pageRepository.getPageNameEntries()` and do redundant trie builds.
- `RepositorySet` (`repository/RepositoryFactory.kt:47-75`) has no `pageNameIndex` field today — confirmed by grep; `pageRepository` is present, so the coordinator can be built from `repoSet.pageRepository`, but the coordinator's own scope/lifetime is undefined by any existing type and needs its own design (see plan phase, not this doc).

### 2.2 Save-not-blocked-by-scan is a new contract, not an existing pattern (AC 4, AC 5)

- Import's `onRawTextChanged` decouples scan from typing via debounce+cancel, but there is **no code path where `confirmImport()` can be called while a scan is still in flight** — the user has to navigate past the review stage to reach Confirm, and by construction the review stage is what displays scan results. Import has never had to answer "what if the user commits before the scan finishes."
- `TagSuggestionViewModel` has a poll *deadline* (`pollDeadlineMs`) but that governs only the LLM-availability polling loop, not the local heuristic scan itself — there's no "abort the local scan and proceed anyway" mechanism anywhere in the existing code, because `directMatch()` (pure, synchronous AhoCorasick lookup) is assumed cheap enough to never need one.
- Capture's `Save` button is enabled purely off `saveState == Idle && captureText.isNotBlank()` (`CaptureActivity.kt:335`) — nothing today gates it on scan state, and the requirements explicitly forbid adding such a gate (AC 4: "Save still writes the text captured so far"). This means the new coordinator must expose something like "best available linked text right now, or raw text if no scan has completed" as a **non-suspending, synchronous** read at Save-time — a shape neither `ImportViewModel` nor `TagSuggestionViewModel` has, since both of their "commit" actions (`confirmImport`, `onSuggestionAccepted`) are only ever reached after a scan already landed in state.
- Consequence for the `<500ms/10KB` budget: this needs an explicit `withTimeoutOrNull` (or similar) wrapping the scan call with a fallback to unlinked raw text, which is new — `ImportService.scan()` itself is a synchronous pure function with no internal timeout, and nothing wraps it with one today.

### 2.3 `onNewIntent` idempotence — what it protects and what it silently doesn't

- `CaptureViewModel.initializeText()` (line 47): `if (_captureText.value.isEmpty() && text.isNotEmpty()) { _captureText.value = text }` — this is idempotent **only** in the sense that it prevents a second `onCreate`→`onNewIntent` cycle from clobbering user edits. It does **not** merge, append, or even acknowledge a second share's content once any text is already present — the second share's text is silently discarded from the UI's perspective. `CaptureActivity.onNewIntent` (lines 115–124) always calls `initializeText`, whose no-op branch is invisible to any listener.
- Since `CaptureViewModel` is `by viewModels()` (survives `onNewIntent`, same instance), any coordinator/scan state built in response to the *first* share's text is still valid and does not need to be rebuilt or invalidated on a second `onNewIntent` — because the second intent's text never actually changes `captureText`. This means the coordinator does *not* need an "intent changed, re-scan" path; it only needs the ordinary text-change-driven re-scan that already covers user edits.
- What **is** new: the coordinator/`PageNameIndex` build must be scoped to survive across `onNewIntent` re-entry (i.e., owned by the `CaptureViewModel` instance, which is what `by viewModels()` guarantees), not re-created per `onCreate`/`onNewIntent` call — otherwise a rapid double-share (see §2.5) could trigger the exact "two `PageNameIndex` instances" race AC 8 forbids, driven by Activity lifecycle rather than text-change events.

### 2.4 First-frame / time-to-editable-field budget (AC 5) has no existing analog

- `CaptureActivity.onCreate()` parses the share intent **synchronously** before `setContent {}` (comment at line 78: "Task 1.3: parse share intent before setContent (EXTRA_STREAM copy is synchronous)") — this is a hard existing constraint: whatever enrichment wiring is added must not add synchronous work to this path.
- `CaptureScreen`'s `LaunchedEffect(Unit) { focusRequester.requestFocus() }` (line 253–255) fires on first composition — today nothing blocks it. Building a `PageNameIndex` (trie construction over potentially thousands of page names, per `PageNameIndex.kt`'s own comment about "hundreds of thousands of nodes" on 8000+ page graphs) must be strictly off this path — it needs to start *after* first frame, not gate it. Neither Import nor Tag-Suggestion screens have ever had a "time to first frame" requirement stated for them; `StelekitViewModel`'s eager `PageNameIndex` construction happens once at app-level init, amortized over the whole session, which is not a constraint capture can rely on since it may be the *only* thing that runs in this process before the user expects to see a text field.

### 2.5 Rapid re-share while a capture is pending save

- Two related but distinct scenarios, neither of which existing tests cover:
  1. **Second share into the same still-open sheet** (singleTop `onNewIntent`): per §2.3, `initializeText`'s idempotence means the visible text doesn't change, so there's no new enrichment work triggered — but if the *first* text's scan hasn't finished (or coordinator hasn't finished building) when the second intent arrives, the coordinator-construction race (AC 8) is the same one already covered — just now with two triggers (an `onNewIntent` call and whatever kicked off the original build) landing close together instead of two keystrokes.
  2. **A second `CaptureActivity` instance while the first is still open** — not addressed anywhere in `CaptureActivity`/`AndroidManifest` launch-mode reasoning found in this pass (`singleTop` reuse is the documented mitigation for the *same* activity, but two independent shares racing to launch could theoretically produce two `CaptureViewModel` instances if launch mode doesn't dedupe fast enough, or if the OS treats them as separate tasks). This is an Android-lifecycle question outside what `ImportViewModel`/`TagSuggestionEngine` needed to solve (they run inside one long-lived app process/ViewModel), and is worth flagging to whoever does the architecture/pitfalls research as needing a manifest/launch-mode check rather than a coordinator-level fix — out of scope for this doc but noted as a gap.

### 2.6 Image-only shares — composite `[image: path]\ntext` block content

- `CaptureActivity.parseShareIntent`/`onCreate` (lines 80–86, 118–124): when `shareContent.imageLocalPath != null`, the saved text becomes `"[image: ${shareContent.imageLocalPath}]\n${shareContent.text}".trim()` — i.e. **the literal image file path becomes part of the block content that would be fed into `ImportService.scan()`** if enrichment naively scans `captureText` verbatim.
- Neither `ImportService.scan` nor `TopicExtractor` has ever been exercised against this shape of input — Import's inputs are pasted text/HTML/fetched URLs, none of which contain synthetic `[image: /data/user/0/.../cache/share_1234567890.jpg]` path tokens. Two concrete risks unique to capture:
  - **Wasted/misleading scan budget**: if `shareContent.text` is empty (a bare image share with no caption — the common case for a photo shared from a gallery app), the entire scanned string is just the image tag; `ImportService.scan` will run its `AhoCorasickMatcher.findAll` against a file path with no useful signal, and `TopicExtractor` will attempt candidate extraction against path segments/timestamps, both pure waste.
  - **False-positive matches on path fragments**: the file name `share_${System.currentTimeMillis()}.jpg` (line 147) is timestamp-derived, effectively random digits, but the `cacheDir` portion of the path is a fixed app-specific string that could theoretically collide with a short page name if `minNameLength` (3, per `PageNameIndex.MIN_NAME_LENGTH`) and stem-variant matching manage to hit a substring inside it (e.g., a page literally named "jpg" or "img" — pathological but not impossible for a personal wiki).
  - **Requirements doc doesn't resolve this explicitly** — "should image-only shares skip enrichment entirely?" is posed as an open question by the task, and this research confirms it is unresolved in the codebase: there is no existing convention for what counts as "image-only" (e.g., is `shareContent.text.isBlank()` sufficient, given `buildShareText`'s title/body fallback chain could produce a non-empty but junk `EXTRA_SUBJECT`-only string?). Recommend the coordinator scan only the free-text portion (i.e., `shareContent.text`, captured *before* the `[image: ...]` prefix is prepended) rather than the already-composited `captureText` — but that requires threading the pre-composite text through to the coordinator, which today only ever sees the final composited string via `CaptureViewModel.captureText`. This is a real wiring decision for the plan phase, not something existing code already handles.

### 2.7 Graph-switch / actor-lifecycle races specific to the post-save write (AC 9)

- `GraphManager.switchGraph()` (`db/GraphManager.kt:527`) sets `_activeRepositorySet.value = null` synchronously (line 555) before asynchronously reinitializing — and `CaptureViewModel.performSave()` already has to guard against this exact class of race for its *first* write via the `ClosedSendChannelException` catch (Bug 1 mitigation, lines 100–107: "graph-switch race"). AC 9's second write (folding a post-save chip accept into the already-persisted block) reuses "the same `writeActor`/`GraphWriter` instance from the original save" per the requirements — but if a graph switch happens *between* the first save and the user tapping a chip in the post-save "Done" state, that captured `writeActor` reference could now belong to a torn-down/replaced actor. Neither Import nor Tag-Suggestion has ever needed to reason about a write happening on a "held" actor reference across a gap of indeterminate user-driven delay (Import's writes are all within one synchronous `confirmImport()` call; Tag-Suggestion never writes at all in these two files) — the post-save AC 9 write is the first place this codebase would attempt a *delayed* second write against a possibly-stale actor handle, so it needs the same `ClosedSendChannelException` handling `performSave` already has, not a copy that skips it.
- `RepositorySet.writeActor` is nullable (`repository/RepositoryFactory.kt:56`) with an already-established fallback (`performSave`'s `else` branch at `CaptureViewModel.kt:108-111` uses `@OptIn(DirectRepositoryWrite::class) repoSet.blockRepository.saveBlock(...)` directly when there's no actor). The AC 9 second write must handle this same nullable-actor branch — a coordinator design that only accepts a non-null `DatabaseWriteActor` would silently be incompatible with whatever backend produced a null actor for the *first* save.

## 3. Cross-cutting notes for the plan/architecture phase

- **Confidence threshold reuse**: ADR-004 (`project_plans/import-topic-suggestions/decisions/ADR-004-suggestion-chip-tray-ux.md`) sets a 0.2 minimum confidence before a suggestion reaches the UI, and a 15-item cap with an 8-shown/"show more" split. The requirements doc explicitly wants the compact bottom-sheet version to skip "Accept All" and its confirmation dialog (single-item accept only), so ADR-004's "Accept All opens a confirmation dialog" and progressive-disclosure "Show N more" affordances are UX pieces that do **not** carry over — the compact tray needs its own (smaller) cap decision, not ADR-004's.
- **`ImportService.scan` and `TopicExtractor` are pure/synchronous** (confirmed: `domain/ImportService.kt:44-49`, `AhoCorasickMatcher.findAll(rawText)` — no suspension inside `scan()` itself) — the entire async/timeout/cancellation story for capture is therefore a wrapping concern the coordinator owns, not something inherited from these functions.
- No existing test exercises cold-start-without-`PageNameIndex`, save-during-scan, post-save chip acceptance, or image-only-share enrichment — `CaptureViewModelTest.kt` and `CaptureShareTextTest.kt` (the only two capture test files found) cover whitespace-normalization scope boundaries and nothing enrichment-related, confirming all of §2 is genuinely untested territory today.
