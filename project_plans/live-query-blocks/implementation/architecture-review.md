### Resolved from Prior Pass

- [x] **Story 1.1.1 (`SimpleQuery.kt`, Task 1.1.1a) — illegal nesting representable at the type level.** Resolved in repair pass. Verified against the current plan text (Domain Glossary, Task 1.1.1a's code block, and the "Query grammar nesting" row in Pattern Decisions): `And`/`Or.left`/`right` are now typed `QueryOperand` — a sealed interface implemented only by `QueryFilter` (bare filters) and `Not(filter: QueryFilter)`. `QueryOperand` does not itself implement `SimpleQuery`, and `Not` wraps `QueryFilter` (never `QueryOperand`), so `And(And(...), ...)` and top-level/double negation no longer compile — this is a genuine type-level fix, not a relabeling of the runtime check. `QueryExecutor`'s `And`/`Or` dispatch (Task 3.2.2f) now explicitly states it "only ever receives `And`/`Or` at the top level, or a `QueryFilter` — never a bare `Not`," which is now a compiler-enforced guarantee rather than a cross-module convention — the exact gap the original blocker named. `QueryParser`'s `parseOperand(): Either<ParseError, QueryOperand>` (Task 1.2.1f) also can no longer construct an over-nested value, closing the loop end-to-end (parser → type → executor). Internally consistent across Domain Glossary, Pattern Decisions, and Tasks 1.1.1a/1.2.1f/1.2.1g/3.2.2f/5.1.1a (which correctly enumerates 6 `SimpleQuery` dispatch branches: `Task`/`PageProperty`/`Between`/`PageRef`/`And`/`Or`, plus separate `Not`-as-operand coverage). No new problem found.

- [x] **Story 3.2.3 (`findReferencingBlocksReactive`, Task 3.2.3b) — dropped overfetch loop.** Resolved in repair pass. Verified against real source: the existing `getLinkedReferences(pageName, limit, offset)` overfetch loop is at `kmp/src/commonMain/kotlin/dev/stapler/stelekit/repository/SqlDelightBlockRepository.kt:892-935`, and `MAX_LINKED_REF_BATCH = 2_000` / `MAX_LINKED_REF_ITERATIONS = 50` are declared at lines 1186/1188 exactly as the plan cites. Task 3.1.1e now specifies extracting this loop into a shared `suspend fun overfetchLinkedReferences(limit, offset, patterns, loadBatch: suspend (batchSize, sqlOffset) -> List<Block>): List<Block>` in the new `LinkMatching.kt`, with `getLinkedReferences` repointed to call it (pure extraction, existing tests must pass unchanged) and Task 3.2.3b's new reactive method built as a lightweight SQLDelight `.asFlow()` invalidation trigger whose `.map{}` re-runs the same shared helper on every tick. This is a real shared-implementation fix, not a relabeling — both call sites now provably share one loop (Story 3.1.1's acceptance criteria include grepping for exactly one `MAX_LINKED_REF_ITERATIONS` definition site). The Dependency Visualization diagram correctly reflects the new sequencing (3.1.1 → 3.1.1e → 3.2.3, gated before 3.2.2 needs it). No new problem found — `selectBlocksWithContentLikePaginated` (used by both the trigger and the loadBatch lambda) is confirmed to exist in `SteleDatabase.sq:208`.

- [x] **Risk Control / Task 4.1.2a — feature flag never wired.** Resolved in repair pass, with the honesty caveat correctly preserved rather than fixed-by-overclaiming. Task 4.1.2a's dispatch arm is now `BlockTypes.QUERY -> if (liveQueryBlocksEnabled) { QueryBlock(...) } else { <literal-text fallback> }` — a real conditional, threaded as a `Boolean` parameter through `BlockItem`/`BlockRenderer`/`BlockList`/`PageView` (Tasks 4.1.2b-d) and sourced once via `debugFlagRepository.getFlag("live_query_blocks", default = true)` at the `PageView` call site (Task 4.1.2f). Verified against real source: `DebugFlagRepository.getFlag(key, default): Boolean` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/performance/DebugFlagRepository.kt:23-26`) is exactly the synchronous one-shot, non-reactive read the original blocker described — the repair pass did not change this mechanism, but the Risk Control section now explicitly discloses it ("Honest scope of 'kill-switch'": takes effect next composition/page reopen, not instantly) instead of the prior overclaiming "fast, in-place kill-switch" language. ## Concerns

- [ ] **Task 4.1.1c (unresolved from prior pass) + Task 4.1.2f (new instance of the same hazard) — `remember` keying depends on an ambiguously-sourced `activeRepositorySet`.** Still valid as originally recorded: Task 4.1.1c's `remember(content) { ... queryExecutor?.executeQuery(it) ... }` is keyed only on `content`, not `queryExecutor`, so a `QueryBlock` surviving a graph switch without a `content` change stays bound to the previous graph's executor (ADR-002's named stale-graph-subscription hazard). Re-verified: `GraphManager.getActiveRepositorySet(): RepositorySet? = _activeRepositorySet.value` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/db/GraphManager.kt:470`) is still a one-shot snapshot getter, distinct from the reactive `val activeRepositorySet: StateFlow<RepositorySet?>` at line 65 — unchanged by the repair pass. **New observation**: the repair pass's Task 4.1.2f (added to wire the feature flag) compounds this same ambiguity rather than resolving it — it reads `remember(activeRepositorySet) { activeRepositorySet?.debugFlagRepository?.getFlag(...) }` and its own prose claims this "re-reads the flag on graph switch rather than only once per process lifetime," but Task 4.1.2e (the sibling task sourcing `queryExecutor` at the same call site) says to pass `graphManager.getActiveRepositorySet()?.queryExecutor` — the one-shot getter — "or the equivalent already-established per-graph sourcing," without resolving which one the call site actually uses. If the call site follows Task 4.1.2e's literal first suggestion (the one-shot getter) rather than collecting the `StateFlow`, then `activeRepositorySet` in Task 4.1.2f is a plain `val`, `remember(activeRepositorySet)` never re-executes across recompositions, and Task 4.1.2f's own "re-reads... on graph switch" claim is false — the flag becomes stuck at whatever it was on first read, same failure mode as the `queryExecutor` staleness bug. **Recommendation**: resolve Task 4.1.2e/f's ambiguity explicitly — require `graphManager.activeRepositorySet.collectAsState()` (the `StateFlow`) at the `PageView` call site, not `getActiveRepositorySet()`, so both `queryExecutor` and `liveQueryBlocksEnabled` correctly re-derive on graph switch; also key Task 4.1.1c's `remember` on `(content, queryExecutor)` at minimum.

- [ ] **Story 3.2.2 (`QueryExecutor`, Tasks 3.2.2a/h) — `PropertyRepository` is still an unused constructor dependency.** Unaffected by the 3 fixes; still valid as originally recorded. `QueryExecutor`'s constructor (Task 3.2.2a) still lists `propertyRepository: PropertyRepository` as one of 4 dependencies, and no dispatch branch (`Task`/`PageProperty`/`Between`/`PageRef`/`And`/`Or`) calls it — `PageProperty` is still built on `PageRepository.getPagesWithProperty` + `BlockReadRepository.getBlocksForPage` per the Tech Debt Disposition table. **Recommendation**: unchanged — drop the parameter for v1 or document it as pre-wired for a fast-follow.

- [ ] **Task 3.2.1b's new SQL query still has no supporting index.** Unaffected by the 3 fixes; still valid as originally recorded. `SteleDatabase.sq`'s `blocks` table indexes remain unchanged by this plan (`uuid`, `page_uuid`, `parent_uuid`, `left_uuid`, `level`, `content_hash` — none on `content`), so `selectBlocksWithMarkerPrefix`'s `content = :marker OR content LIKE :marker || ' %'` is still a full-table scan, just executed in SQLite instead of Kotlin. **Recommendation**: unchanged — add an index or explicitly log this as deferred tech debt rather than implying it's fully solved.

- [ ] **Tasks 4.1.2b-d — threading `queryExecutor`/`pageRepository` through 4 composable layers, `pageRepository` still not pre-threaded.** Unaffected by the 3 fixes; still valid as originally recorded. Re-verified against real source: `pageRepository` remains a `PageView`-only parameter (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/ui/screens/PageView.kt:62`, used only internally at line 351) — grep confirms it is still not threaded into `BlockList.kt`, `BlockRenderer.kt`, or `BlockItem.kt`. **Recommendation**: unchanged — consider a `CompositionLocal` scoped near `GraphManager`/`PageView` instead of widening 3 composable signatures, especially since `research/features.md` §1 flags `{{embed}}` as a likely second consumer of the same service-access pattern.
