# Validation Plan: live-query-blocks

**Date**: 2026-09-15

## Happy Path Scenario

Given a graph containing a block with content `TODO write the quarterly report` and a page containing the block `{{query (task now later)}}` (Problem Statement, requirements.md: `{{query}}` blocks currently render as dead literal text), when the page loads, then the `{{query ...}}` block renders as a live, read-only list showing that block as a result — and when the block's marker is later edited to `DONE` anywhere in the graph, the visible result list and count update automatically, without the user reopening the page.

Everything below is a variation on this scenario: the four grammar forms and their combinators are alternative inputs to the same executor; the empty/fallback/truncation states are alternative outputs of the same render path; the accessibility and focus-safety criteria are constraints on how the same live update is allowed to behave.

## Test Stack

- **Unit**: Kotlin `kotlin.test` (`commonTest`), JUnit (`jvmTest`/`businessTest`) — this repo's existing convention (see `QueryParserTest.kt`, `BlockTypeMapperTest.kt`, `QueryExecutorTest.kt`). Arrow's `Either` is asserted via `assertEquals`/`assertTrue` against `Either.Left`/`Either.Right`, per the repo's existing repository test style (`BacklinkRepositoryTest.kt`, `DatalogBlockRepositoryTest.kt`).
- **Integration**: JVM tests against a real `SteleDatabase`/SQLite driver (`kmp/src/jvmTest`), following `PaginationEnforcementTest.kt`/`UpgradeResilienceTest.kt`'s pattern of constructing `SqlDelightBlockRepository`/`SqlDelightPageRepository` directly over an in-memory or temp-file SQLite driver — no mocking framework, real reactive `Flow` collection via `kotlinx-coroutines-test`'s `runTest`.
- **E2E / UX**: Compose Multiplatform UI testing — `androidx.compose.ui.test` JUnit4 `createComposeRule()` for interaction/keyboard/semantics assertions (model: `TopBarTest.kt`, `SuggestionContextMenuTest.kt`), and Roborazzi (`captureRoboImage`) for pixel/visual-state coverage across light/dark themes (model: `TableBlockScreenshotTest.kt`). Platform accessibility parity (screen-reader behavior on Desktop/Android/iOS/Web) is a manual checklist item, not automatable via `ciCheck` — see X-8 above.
