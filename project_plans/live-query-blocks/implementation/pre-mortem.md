# Pre-mortem: live-query-blocks
**Date**: 2026-09-15

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | v1's grammar (4 base forms + one level of `and`/`or`/`not`) is narrower than what real migrated Logseq graphs actually contain (2+-level nesting, raw Datalog `:find`/`:where` maps, block-level `property`), and the silent-literal-text fallback for anything outside v1 is visually identical to today's "dead text" — so users who point the feature at their existing, more complex queries see no change and conclude the feature doesn't work, rather than recognizing a scoped v1 limitation. This directly undermines the problem statement ("silent breakage today... expects them to render live results, not dead text"). | Users report "query blocks still don't work" after upgrading, pointing at queries that happen to fall just outside v1 scope (e.g. two levels of `and`, or a raw Datalog map) — the fallback gives them no signal that anything is different. | Add a distinguishable "unsupported query form" placeholder (distinct styling/icon from the pre-existing literal-text rendering) for `ParseError.InvalidSyntax`, so users can tell "not yet supported" from "still broken like before." `requirements.md` already names this option ("a clear 'unsupported query' placeholder") but `plan.md` (Task 4.1.1e, Story 4.1.1 AC) chose plain literal-text reuse instead — revisit that choice before implementation. | P1 |
| 2 | `PageRepository.getPagesWithProperty`'s `properties LIKE '%key:value%'` match (Task 3.2.4b) is an unanchored substring match against the unescaped, delimited `"key1:value1,key2:value2"` string (confirmed format: `research/stack.md:69-73`). It will silently return false positives whenever one page's `key:value` pair is a substring of a different key/value pair elsewhere in the same or another page's properties string — e.g. querying `(page-property type book)` (pattern `%type:book%`) also matches a page whose properties contain `subtype:book2` or `booktype:book`. Because there is no delimiter anchoring (`,` before / `,` or end-of-string after), this is a genuine correctness bug, not a performance one. | A `{{query (page-property type book)}}` dashboard silently includes pages that have a *differently-named* property whose key or value happens to contain "type:book" as a substring — wrong blocks appear in a "live" list with no error, and nothing in the UI signals the result set is untrustworthy. | Anchor the SQL pattern to delimiter boundaries, e.g. `properties = :kv OR properties LIKE :kv || ',%' OR properties LIKE '%,' || :kv OR properties LIKE '%,' || :kv || ',%'` (mirrors the existing `content = :marker OR content LIKE :marker || ' %'` boundary style already used for `findBlocksWithTaskMarker`), and add a `QueryExecutorTest`/`PageRepository` test case with two pages whose property strings are substrings of each other to prove no cross-contamination. | P1 |
| 3 | Each `QueryExecutor` branch that resolves to a page-level match (`PageProperty`, `Between`) fans out into one nested `combine()`-ed `getBlocksForPage` Flow *per matching page*, on top of the per-marker `combine()` already used for `Task`. On a real, larger graph with many query blocks open simultaneously (k) and queries that match many pages (M), a single write anywhere in the graph re-triggers all k query blocks' outer Flows, each of which re-subscribes to up to M nested per-page Flows — a k×M(+N) fan-out of live subscriptions, not just the k×N single-table rescan cost the plan's Pattern Decisions table explicitly reasons about. `DEFAULT_LIMIT`/`MAX_QUERY_RESULTS_DISPLAY` cap rendered *rows*, not the number of nested Flow subscriptions spawned to compute a `PageProperty`/`Between` result. | The desktop app becomes noticeably laggy or CPU-hot on a graph with a handful of `{{query (page-property ...)}}` blocks open on a page once the matched-page count climbs into the dozens-to-hundreds range, worsening with every keystroke-driven write anywhere in the graph — not reproducible on the small seeded fixtures typical of unit/business tests. | Before shipping, add one `businessTest`/benchmark case with a graph shaped like a real large vault (hundreds of pages, a property matching a meaningful fraction of them, several simultaneously-open query blocks) and measure recompute cost per write; if it's material, cap the *number of matched pages combined* (not just displayed rows) or flatten to a single SQL join instead of N nested per-page Flows, before Task 3.2.2c/3.2.2d ship as specced. | P2 |
| 4 | The "live" experience most likely to be the first thing users judge — checking off a task and watching it disappear from a `{{query (task now)}}` list on the same page — rides the existing 500ms block-save debounce plus write-commit plus Flow re-emission plus recomposition, and nothing in the plan measures or bounds that end-to-end latency. `requirements.md`'s "Live refresh granularity" open question was marked resolved by asserting the existing debounce is "already fine," without validating the perceived latency for the single interaction most likely to define first impressions of a feature literally named "live." | Early users report the query block "doesn't update immediately" or "feels laggy" when toggling a task marker, especially if the toggle itself routes through the same debounced-edit path rather than an immediate write. | Add a manual or automated latency check (e.g. a `jvmTest` timing a marker-toggle-to-Flow-re-emission round trip, or a note in `validation.md` to verify this interaction feels instant during manual QA) before calling the debounce assumption validated, rather than treating requirements.md's resolution as sufficient without measurement. | P2 |
| 5 | Every v1 filter form touches 6+ locations with no shared abstraction: a repository interface method, a `.sq` query, a SQLDelight backend impl, an in-memory fake impl, an `UpgradeResilienceTest` sweep entry, and a `QueryExecutor` dispatch branch (visible in the parallel structure of Stories 3.2.1/3.2.3/3.2.4). The plan's own Unresolved Questions section defers three concrete v2 items (relative-date `between`, block-level `property`, deeper `and`/`or` nesting) as "future backlog," each of which will repeat this same 6-location pattern with no registry/extension seam proposed anywhere in the plan. | Adding the first fast-follow filter form takes a full day instead of the ~30-45 minutes the v1 task estimates suggest, or a future contributor takes a shortcut (e.g., reusing an existing full-table-scan method like `getAllPages()` or `getBlocksWithPropertyKey`) to avoid repeating the pattern — quietly regressing the exact SQL-pushed-down discipline this repair cycle just enforced for `PageProperty`/`Task`. | Add a one-paragraph "Adding a new query filter form" checklist (the 6 locations, in order, with the reactive-Flow/`Either`/fake-parity constraints spelled out) to this plan or to `CLAUDE.md`'s Database section, so the next filter form has a documented seam to follow instead of re-deriving the pattern from three parallel examples. | P2 |

## P1 Items (address before implementation)
- [x] Failure #1 — Add a distinguishable "unsupported query form" render state to `QueryBlock` (Task 4.1.1e / Story 4.1.1 AC), instead of reusing today's literal-text fallback verbatim, so users can tell "v1 doesn't cover this yet" from "still broken." **Resolved in repair pass**: `DomainError.ParseError.UnsupportedForm` added as a sibling of `InvalidSyntax`; Story 4.1.1 now specs a 4th, visibly-distinct render state (ux.md Surface 4b) for recognized-but-unsupported shapes.
- [x] Failure #2 — Anchor `selectPagesWithPropertyPair`'s `LIKE` pattern (Task 3.2.4b) to `,`/string-boundary delimiters instead of an unbounded substring match, and add a cross-contamination test case before Story 3.2.4 is implemented. **Resolved in repair pass**: Task 3.2.4b now uses a 4-branch delimiter-anchored query mirroring `findBlocksWithTaskMarker`'s boundary style; Task 3.2.4f adds the `sub-type:bookmark` vs `type:book` cross-contamination test.

## Summary

2 P1 items, 3 P2 items, 0 P3 items.

Top failure mode: the v1 grammar subset is real-world-narrower than the problem statement implies, and the chosen fallback (identical literal-text rendering) makes "not yet supported" indistinguishable from "still silently broken" — the exact failure the feature was built to eliminate.
