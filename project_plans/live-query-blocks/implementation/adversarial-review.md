## Concerns

- [ ] **New, minor: `catch (e: Exception)` (not `Throwable`) leaves `StackOverflowError`/similar `Error` subclasses uncaught, and the fuzz test's "deeply repeated parens" input is exactly the shape that could trigger one in a naive recursive-descent implementation.** The plan explicitly rejects a bare `catch (e: Throwable)` "which would also swallow real `Error`s" (plan.md:258) — a reasonable general principle, and consistent with this repo's convention of not catching `Throwable` outside the one documented exception (`SteleKitApplication.onCreate`, which exists specifically for native-library-load errors, not applicable here). As specced, the grammar's recursion is bounded by fixed grammar depth (top-level dispatch → one level of `and`/`or` → `parseOperand` accepting only a bare filter or `Not(filter)`, never nested `and`/`or` — Task 1.2.1f, plan.md:254), not by input length, so an unbounded-recursion stack overflow from something like 10,000 open-parens looks unlikely by design. But this reasoning isn't stated in the plan, and the tokenizer (Task 1.2.1a) is only specified at the level of "splits on whitespace and parens... same recursive-descent/manual-`advance()` idiom as `InlineParser.kt`" — recursive enough in name that it's worth confirming, not assuming. — **Recommendation**: either state explicitly (a one-line note near Task 1.2.1a or 1.2.1g) that the tokenizer/parser is iteration-bounded and cannot recurse on input length, or extend Task 1.2.2c's fuzz corpus to include a very large repeated-parens input (e.g. 10,000+) so the no-crash guarantee is empirically exercised, not just asserted for the shorter garbage strings currently implied.
- [ ] **`Between`'s `JOURNAL_SCAN_LIMIT` is still referenced but never defined, and its boundary is still untested.** Unchanged from the original pass — Story 3.2.4 only added `getPagesWithProperty` and did not touch the `Between` branch (Task 3.2.2d, plan.md:479-480), which still filters journal pages in Kotlin over `pageRepository.getJournalPages(limit = JOURNAL_SCAN_LIMIT, offset = 0)` with `JOURNAL_SCAN_LIMIT` undefined anywhere in the plan (only occurrence: plan.md:480). Recommendation unchanged: define the constant explicitly and add a test where the range falls past the scan window.
  - **Resolved in round-3 triad repair** — `JOURNAL_SCAN_LIMIT` is defined and pinned at `= 500` in the Domain Glossary and on `QueryExecutor`'s companion object (Task 3.2.2a), with its accepted-boundary behavior documented in Task 3.2.2e. The boundary is now also tested: Story 5.1.1's acceptance criteria and Task 5.1.1a (plan.md:750-751, 758) add a `QueryExecutorTest` case for a `Between` range whose journal dates fall entirely outside the 500-page scan window, asserting `Either.Right(emptyList())`/undercounted results rather than a crash or hang. Both halves of this concern are now closed.
- [ ] **`Not` semantics inside `Or` are still unspecified/still incorrect if implemented as written.** Unchanged from the original pass — Task 3.2.2f (plan.md:488) still generalizes a single formula ("execute the inner filter and complement it against the *other* operand's result set") across both `And` and `Or`, worked out only for the `And` case ("`tag2Results - tag1Results`", matching `research/features.md`'s `And`-only example). Applying the same "complement against the other operand" formula to `Or(x, Not(y))` produces `x - y`, which is not valid `OR NOT` semantics (a true `Or(x, Not(y))` needs a graph-wide complement of `y`, not one bounded by `x`). No acceptance criterion exercises `Or` combined with `Not`. Recommendation unchanged: either define and test the intended `Or`+`Not` semantics explicitly, or restrict `Not` to `And`-operand position only as a documented v1 grammar restriction.
  - **Resolved in round-1 triad repair** — see Domain Glossary (`QueryOperand`, `Or`) and Pattern Decisions ("`Or`+`Not` combination"), plan.md. `Not` is now restricted to `And`-operand position only, enforced at the type level: `Or.left`/`Or.right` are typed plain `QueryFilter` (not `QueryOperand`), so `Or(_, Not(_))` is a compile error, not a runtime ambiguity — matching this concern's own second recommended option. `QueryParser`'s `or`-operand parser (Task 1.2.1f) accordingly returns `Either<ParseError, QueryFilter>` (never `QueryOperand`) and classifies an `(or ... (not ...))` shape as `UnsupportedForm`. `QueryExecutor.executeQuery`'s `Or` branch (Task 3.2.2f) documents explicitly that it can never receive a `Not` operand and does not reuse the `And`+`Not` set-difference formula.
