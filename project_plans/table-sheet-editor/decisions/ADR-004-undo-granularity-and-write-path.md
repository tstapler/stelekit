# ADR-004: One commit is one `updateBlockContent` call; snapshot undo; echo-loop gate

**Status**: Proposed (accepted when Tasks 4.3b and 5.1c are green; revised in review rounds 2 and 3)
**Date**: 2026-11-24

## Context
`BlockStateManager.updateBlockContent` (`ui/state/BlockStateManager.kt:1064`) records one undo pair per call through `applyBlockContentUpdate`, debounces the disk write through `queueDiskSave`, and `GraphWriter` is the only sanctioned write path. `BlockUndoManager` is a 100-entry closure stack with no grouping and no entry labels. VERIFIED by reading `BlockStateManager.kt:1080-1100`: the undo and redo closures recorded by `applyBlockContentUpdate` end with `requestEditBlock(blockUuid, ...)`, which flips the block into the raw `BlockEditor` (`BlockItem.kt:360`) and unmounts the inline table; and they re-apply `oldVersion`, which the `pageBlocks[idx].version <= version` guard (`:1128-1130`) rejects after a higher-version edit (INFERRED, proven or disproven by the failing-first test in Task 0.5a, which ships with its fix in one commit). The existing `remember(content) { parseTableContent(content) }` would re-parse on every content change and reset cell state while typing (pitfalls section 5, "echo loops").

## Decision
- A table edit is `updateBlockContent(uuid, TableSerializer.serialize(newDoc), version, restoreEditFocus = false)`: one commit, one undo entry, whole-string snapshot. No new persistence path, no second debounce, no `BlockUndoManager` grouping or label API (not needed, not added speculatively); undo/redo announce the generic "Undone"/"Redone".
- **`BlockStateManager` and `BlockEditingPort` get one additive, default-valued parameter** (Task 0.5a, a single red-then-green commit; tech-debt disposition: isolate via seam). `restoreEditFocus: Boolean = true` is declared on `BlockEditingPort.updateBlockContent` (`ui/state/BlockEditorPorts.kt:19`; `BlockStateManager` is the only implementer, and `JournalsViewModel.kt:153` calls positionally, so the change is source-compatible) and threaded through `applyBlockContentUpdate`. Table commits pass `false`; then the manager stores `max(passedVersion, current.version + 1)` and the recorded closures skip `requestEditBlock` and re-apply with a fresh `block.version + 1`. Text-block behaviour is unchanged by default. `BlockUndoManager` itself stays untouched. (The earlier "no change needed" claim was wrong.)
- **Version spaces (R2-B1).** There are two, and they are never compared. The UI space is `BlockStateManager`'s in-memory `block.version`: commits, undo and the `<=` guard live there, and for table commits the manager mints the stored version itself (`max(passedVersion, current.version + 1)`), so a stale inline `++localVersion` cannot be rejected. The DB space is the row counter (`version = version + 1`, `SteleDatabase.sq:317`), which is what `getBlockByUuid` emits and which `BlockStateManager.kt:777-783` says cannot be matched against the UI version. The sheet observes `getBlockByUuid`, so the sync policy reads `content` only. Inline commits go through `LocalTableCommitAction` (lower bound `localVersion`, fallback `onContentChange(s, max(++localVersion, block.version + 1))`); sheet commits go through `TableCommitter` with a lower bound of 0. Only one editor is live per block: while the sheet is open the inline `TableBlock` for that block is read-only (`LocalTableSheetOwner`), opening the sheet first commits any inline draft, and "Edit as markdown" commits first too.
- Commit points are explicit only: cell Enter/Tab/arrow/blur to another cell (not while composing), each structural or bulk op (insert/delete/move, sort, paste, alignment, clear), sheet close, maximize, Edit as markdown and `onStop`. `onStop` commits only when the host is not changing configuration (Android `isChangingConfigurations` false, INFERRED mechanism; Web `visibilitychange` to hidden; Desktop window close); a rotation, fold or resize keeps the draft uncommitted in the in-memory state holder (ux.md 3.11, iteration 7), and a draft held by a conflict is not committed but becomes a `RecoveredDraft`. There is no commit on dispose: the `CellDraft` is hoisted above the lazy item, so an item leaving composition keeps its text and no commit is needed; this removes the conflict with the IME rule. At close/`onStop` with `composition != null` the draft text is committed with the composition cleared (documented, tested). Per-keystroke typing stays in the draft; `CellDraft` owns the in-cell undo history (iteration 7: Ctrl+Z, Ctrl+Shift+Z, Ctrl+Y and the strip and edit-bar Undo and Redo during `Edit` revert draft steps only, never commit and never reach `BlockUndoManager`; if Task 4.3b shows the platform text state's undo is usable, `CellDraft` wraps it instead). Esc discards the draft.
- `TableSyncPolicy.classify(content: String)` classifies each observed content against an `OwnCommitLedger`, never a single "last serialized string" (commits are separate `scope.launch`es, so echoes arrive out of order, `BlockStateManager.kt:1113-1118`) and never a version. The ledger keys states by content hash plus length (no strings stored) and assigns each its own monotonic `seq` at commit, load, adoption or first observation; `currentSeq` is the displayed state; entries are `InFlight` or `Acked`; capacity is 128 (the undo stack holds 100, `BlockUndoManager(maxHistory = 100)`, plus redo and in-flight), and an evicted state reads as external, which is lossless because every rebuild uses the observed content. Order: (1) equals the displayed content: `Echo`; (2) matches an `InFlight` entry: `Stale` if that entry's `seq` is below `currentSeq` (a newer commit or adoption happened since; a late S1 cannot regress S2 and the next commit never builds from S1), else `Adopt` (it is not the displayed content, so an expected undo target had moved the display below it, P5-5); (3) matches an `Acked` or loaded state: `Stale` when its `seq` is below `currentSeq` (superseded; the display never moves backwards, P5-5), else `Adopt` (rebuild keeping selection, no conflict) unless a draft is pending (`ConflictKeepDraft`); (4) otherwise external: while an own commit is `InFlight` the content is held (`Defer`) and `markDone` releases it as below; no draft, `Rebuild` keeping the selection by (row, col) when still in range; pending draft, keep the draft and show the sheet's own conflict banner (Keep mine / Take theirs / Edit as markdown). A hash collision can only turn `Rebuild` into `Adopt`, and both rebuild from the observed content. Round 3 additions: (a) the sheet registers undo/redo results itself: `TableCommitter.undo()/redo()` joins pending commit `Job`s, runs the manager's undo/redo, joins it, reads the resulting content and calls `ledger.expectAdopt(content)`; only an expected state older than `currentSeq` is adopted (an unexpected superseded `Acked` match is `Stale`, P5-5), so a late echo of an old acked state can no longer be mistaken for an undo, and an undo is never swallowed (R3-C1; cases "undo then immediate re-commit" and "Tab, Tab, Ctrl+Z"). (b) The ledger holds at most one entry per hash; a re-commit overwrites it with a new `seq` and `InFlight`; "retired" means `Acked`, never removed, and echoing a state marks every older `InFlight` entry `Acked` (R3-C2). (c) A commit's completed `Job` marks its entry `Acked` (`markDone`), so a commit the manager silently dropped cannot leave a permanent `InFlight` entry (R3-C5). `markDone` returns the foreign decision that was deferred behind the commit, if any (P5-5). (d) Eviction is LRU by `seq`; 100 commits plus 28 external observations may evict the deepest undo state, which reads as external (`Rebuild`, or `ConflictKeepDraft` with a draft), lossless and accepted. Tests: scripted sequences (Task 3.2b), a skewed-DB-version equivalence test that fails if any version is read, and a real-manager plus real-SQLDelight two-quick-commits test (Task 5.1c) with a recorded mutation proof. The page-level `DiskConflict` (`ui/AppState.kt:276`) has no per-block flow and is not reused. Never discard in-progress text silently.
- Flush: on sheet close and on `onStop`, launch the existing `suspend fun BlockStateManager.flush()` (`:1231`) on the manager's scope (never `rememberCoroutineScope`, which is cancelled when the dialog leaves composition) so the 500 ms debounce cannot lose the last edit.
- Lifecycle: the sheet host observes the single block; deletion, a non-Table or unparsable content change, page unload or graph change closes the sheet after flushing with a one-line message, and no commit is issued for a block `findBlockOrNull` cannot find.
- The sheet runs inside a `Dialog` window, so the app-level `onGraphKeyEvent` Ctrl+Z/Y (`ui/App.kt:725`) does not reach it (INFERRED, verified in Task 5.1a). The sheet binds Ctrl+Z / Ctrl+Shift+Z / Ctrl+Y itself and calls `BlockStateManager.undo()/redo()`, so inside and outside the sheet there is one stack. In edit mode Ctrl+Z belongs to the text field.
- **Sheet undo is scoped to the sheet's own entries.** (Round 3: the manager records the undo entry only after the DB write, `BlockStateManager.kt:1081-1097` inside a `scope.launch`, so `TableCommitter` joins pending commit `Job`s before any undo and derives depth from the manager side, counting a commit only when the manager's content changed across the `Job` and cross-checking against the additive `undoRecordCount` flow added in Task 0.5a; depth is clamped to the 100-entry cap, extra undos are no-ops with the notice. Foreign entries pushed while the sheet is open raise `undoRecordCount` without a sheet commit: the sheet flushes and closes with "The page was edited elsewhere" rather than undo a foreign entry, R3-C3/C4.) `BlockUndoManager` is page-wide with no tagging, and an undo closure of another block ends in `requestEditBlock`, which would open a raw editor under the Dialog. The sheet therefore counts its own content-changing commits (`sheetUndoDepth`, `sheetRedoDepth`, kept by `TableCommitter`) and calls `undo()`/`redo()` only while the matching depth is above zero; otherwise it shows "Nothing more to undo in this table". A new commit clears the redo depth. Inline edits made before the sheet opened are undone after it closes. As a backstop, `editingBlockUuid` becoming non-null for any block while the sheet is open flushes and closes the sheet. No `BlockUndoManager` tagging API is added (rejected: more surface for one caller). INFERRED that the manager records no entry for an unchanged-content commit (`oldContent == newContent` early return); Task 5.1c tests it.
- **One `TableUndoScope` for both surfaces (iteration 7).** The inline strip no longer reads the page stack directly (the earlier rule let inline Undo revert another block's edit). A pure `TableUndoScope` (plan Task 3.2c) holds `undoDepth`, `redoDepth` and a label stack (`edit B3`, `paste`, `sort`...; the manager still keeps no labels, so labels live in the table's own scope and name the button, "Undo: edit B3"; the live-region announcement stays the generic "Undone"). A commit adds depth only when its serialized content differs from the current content; undo and redo move one step between the depths; a new commit clears redo; depth is capped at 100. Inline: the scope starts at 0 when the strip appears, resets to 0 when it hides, and resets on a foreign `undoRecordCount` rise (Undo dims with "Nothing more to undo in this table"; the inline surface does not close, because it holds no dialog). Sheet: `TableCommitter` owns the scope, which starts at 0 on every open (a reopen never undoes an earlier open's commits, so the old `sheetUndoDepth` is this scope's `undoDepth`). Inline Undo is enabled only while `undoDepth > 0` and the read-only `canUndo` of Task 0.5a is true. Edits made before a scope began are undone with the page's own Ctrl+Z.
- No new long-lived coroutine scope: sheet state classes expose state and take commit lambdas; transient work uses `rememberCoroutineScope()` for event handlers only. Anything that must outlive composition (the commit) is launched by `BlockStateManager.scope`, which already carries the `CoroutineExceptionHandler`.
- Failure modes log through `Logger` (never `android.util.Log`) and show a cell or sheet error, never throw.

## Consequences
Accepted limitations (round 3, R3-C6): sheet commits are issued one at a time (each joins its predecessor), so their DB write order equals commit order; inline commits, foreign writers and external edits are not ordered by this plan, so the DB row can transiently or finally differ from the display in those cases, and the manager's `maxOf` guard protects `_blocks` and the disk save, not the DB row. Not a regression. Test criterion: the real-feed test (Task 5.1c) asserts DB equals display after all sheet commits quiesce. An external edit equal to an `Acked` state is adopted silently; one equal to an older `InFlight` state is ignored and overwritten by the next commit (last-writer-wins).

Memory: 100 snapshots of a 200x12 table is a few MB at most (INFERRED; Task 8.5a measures). Undo after sort restores order and formula text exactly. No cell-level merge in v1.

## Degraded mode and simplification trigger (iteration 4, pre-mortem P1-1)
If the policy returns `Stale` for the same content more than twice in a row, or `sheetUndoDepth` disagrees with `undoRecordCount` after joining the pending commit `Job`s, the sheet flushes, closes with a one-line message and reopens from DB content; nothing is displayed from a guess. Tests are built from the recorded emission trace (Task 0.6a) and a randomized model test. If Tasks 5.1b or 5.1c need a third repair round, stop and record the decision whether to simplify (sheet-exclusive commits, or undo disabled inside the sheet) before continuing.

## Alternatives rejected
Per-keystroke commits (floods the 100-entry stack); a sheet-local undo history (two stacks to reconcile); `BlockUndoManager.beginGroup/endGroup` (extra surface with no v1 use).
