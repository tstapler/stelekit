# Adversarial Review: excalidraw-sketch-engine

**Date**: 2026-11-14
**Verdict**: CONCERNS (re-review 2026-11-14; was BLOCKED. The three blockers' designs hold; sequencing and wording defects R1-R6 below must be fixed before `5-implement`)

Evidence base: `plan.md` and `requirements.md` read in full. Code facts checked against the worktree: `SidecarFileState.kt:26,41`, `ProjectSidecarStore.kt:80-96`, `ProjectModelJson.kt:54,138-204`, `SidecarReconciler.kt:191-213`, `model/SketchModels.kt` (`ProjectBundle`, `SketchDimension`), `benchmarks/budgets/`.

## Blockers
- [x] (repaired, see Re-review) **The sidecar write path is v1-shaped and will silently drop a v2 sheet.** `ProjectBundle` is `(project, sheets, primitives, dimensions)`. `ProjectModelJson` regenerates `sheets/<uuid>.json` from `primitives`, and `SidecarReconciler` builds the bundle from the DB by paging `getPrimitives` (`SidecarReconciler.kt:191-213`). Any project-level write after a sheet becomes `schema:2` (a dimension edit, post-sync coordinator, DB restore) would re-emit that sheet as a v1 primitives-only file, or decode it to zero primitives. Story 1.1.1 covers only the v1 codec dispatch, and Task 1.4.2c is a single line ("Reconcile with `SidecarReconciler` three-way hashes on schema:2"). No story defines how `ProjectBundle` carries a v2 sheet (opaque passthrough bytes?), which side is authoritative on DB restore, or how `fileSha256` is computed for v2. This is a data-loss risk against success metric 6. **Recommendation:** add a refactor-first story before 1.4.2. It must make `ProjectBundle` and the writer pass v2 sheets through untouched, with tests in which every existing bundle-write trigger leaves a v2 sheet byte-identical, and a DB-restore test for a v2 sheet. Also state what the `sketch_elements` cache is for (see the cache concern below) and who writes it.
- [x] (repaired, see Re-review) **v1 dimensions, zones, named dimensions and sum/equal constraints have no home in v2.** `SketchDimension` and the zone/dimension pipeline are what the fusion, CSV and digest paths consume (requirements Baseline, constraint 1). The glossary and element model have no Zone or NamedDimension. `V2ToV1.project` projects only primitives, and `ProjectionFusionTest` (4.2.4) tests one rounding case. Task 6.2.4b says "every v1 ... zone ... behaviour exercised through v2", but no story builds or migrates that behaviour. Story 1.4.2's conversion AC covers "12 primitives" only. Metric 6 ("opens, edits and exports unchanged") cannot be met for any sheet that has dimensions or zones, and conversion can lose them. **Recommendation:** add a story (Phase 1, before conversion) that defines where dimensions and zones live in `SketchDocumentV2` (a `technical` section carried verbatim, or a typed model), how the sum/equal constraints interoperate with the new solver, and a conversion golden over fixtures that contain dimensions and zones. Until it lands, conversion must refuse sheets with dimensions or zones (fail-safe), not convert them.
- [x] (repaired, see Re-review) **Conversion and the router are sequenced before fusion and projection are wired.** Stories 1.4.2/1.4.3 can convert a sheet on first open once the flag is on. Fusion and digest consumers read the DB `sketch_primitives`, and the wiring that keeps them correct for v2 sheets is Story 4.2.4, "read-only consumer wiring" in Phase 4. The plan never says who writes the projected primitives into `sketch_primitives` for a v2 sheet. After a dark Phase 1-3 rollout, a converted sheet would feed fusion zero or stale dimensions and so give wrong LLM digests. **Recommendation:** move the projection writer and fusion surfacing (4.2.4a) into Phase 1 directly after 1.4.2, or gate conversion and the flag from being user-enable-able until it lands. Add the dependency to the visualization (it is absent today).

## Concerns
- [ ] **Dependency graph omits real prerequisites.** Phase 3 is "after 1.3.x, 2.1.1", but 3.3.3 and 3.4.1 need 2.1.2 (text metrics), 3.4.2 needs 2.1.4 (freehand), 3.3.2 needs 2.1.1b (arrowhead geometry), 3.5.5 needs 1.3.3, and 3.4.3 needs the asset writer. Phase 4.2.2 (auto-constrain) needs 3.2.1 and 3.5.5, and 4.2.x as a whole needs the tools, though Phase 4 is listed "after 0.1.2 + 1.3.2". Wave W6 fans out Phase 2/3/4/5 in parallel. Several of those shared files (`SketchSceneV2`, `V2/commands/*`) are acknowledged, but the cross-phase story dependencies are not. **Recommendation:** replace the phase-level arrows with story-level edges.
- [ ] **Image assets break cross-graph copy and export.** Story 3.4.3 stores image bytes in the graph assets by SHA-256 `fileId`. Story 6.1.2 copies only the sketch bundle, so it leaves dangling image references in graph B. Story 5.1.3 export never states that `files` (image data) is emitted, and the importer needs the same store. **Recommendation:** add an AC to 6.1.2 (copy referenced assets, refuse or placeholder if missing, no modification of existing files) and to 5.1.3 (image round trip).
- [ ] **No bound or untrusted-input handling for native v2 sheets.** Only the `.excalidraw` importer has caps and fuzzing (5.1.1). `SheetCodecV2` decodes sidecar files that arrive via git sync from other devices or conflict merges, and it has no size/depth/element caps (5,000 elements, 200 constraints), no fuzz test and no `reconcile` on load. A hostile or corrupt sheet could OOM the app on open. **Recommendation:** apply `ImportLimits` plus `reconcile` in `SheetCodecV2.decode`, and add a fuzz AC.
- [ ] **The 200-constraint cap (NFR) has no story.** Only the 5,000-element cap has an AC (1.2.1). **Recommendation:** add `CommandError.ConstraintCapExceeded` and a test in 4.2.1a.
- [ ] **`sketch_elements` / `sketch_constraints` cache tables are unjustified.** The file is authoritative, the scene is loaded whole into memory (at most 5,000 elements), and the spatial index is in memory. Nothing reads the `bbox_*` columns. The only reads are paged (`selectSketchElementsBySheetPaged`), and loading a full scene through 500-row pages adds cost. Every autosave then rewrites up to 5,000 rows through `DatabaseWriteActor`. This looks like scope drift plus write amplification. **Recommendation:** state the concrete reader of the table (search? fusion? cold-start thumbnail?), or drop it for v1 and keep only `schema_version`. If kept, specify diff-based writes keyed on `ElementBase.version`.
- [ ] **Metric 7 is only partly verifiable.** Metric 7 says `export(import(x))` preserves the supported subset. Story 5.1.3 tests only `import(export(generated))`, and the real fixtures (5.1.2) are import-only. PNG export (5.2.2) asserts only decoded dimensions, not that all new element kinds actually render (metric 7 says "SVG and PNG export render all new element kinds"). **Recommendation:** add an `export(import(fixture))` round trip over the Task 0.1.5a fixtures, and a PNG pixel/non-blank check per element kind against the draw-list render.
- [ ] **Performance gates are partly not CI-verifiable.** The AC in 2.1.3 requires p95 ≤ 24 ms on the Pixel_Fold AVD, but Story 6.2.2 gates "in CI" with a JVM harness and the AVD is a manual owner step (OD-2). A headless software-rendered AVD (`-no-window`) is also an unreliable frame-time source. The wording "within 16 ms ... relative to the empty-canvas baseline" mixes an absolute and a relative threshold. **Recommendation:** define one rule (relative ratio, for example ≤1.5x empty canvas), say which gate runs where, and mark the AVD number as an owner-run advisory.
- [ ] **Cross-target pixel parity on Android relies on Robolectric.** Task 2.1.3c plans "JVM/Robolectric/wasm" tolerances, but Robolectric's native-graphics Canvas fidelity for Compose text and paths is a known weak spot. Metric 4 names Android. The spike set (0.1.x) has no spike for this. **Recommendation:** add an Android pixel-render feasibility check to Spike 0.1.3, with a fallback to draw-list equality plus an on-device owner check.
- [ ] **Text determinism vs CJK.** Spike 0.1.3b measures "データ" with the bundled font, but the "Hand-drawn / Normal / Code" fonts (OD-4) likely lack CJK glyphs. Fallback fonts differ per target, which undermines the 1 px tolerance and the cross-target line-break claim. **Recommendation:** state the fallback policy (bundled CJK subset, or documented per-target divergence excluded from goldens).
- [ ] **Solver moves and bindings, and solver vs transforms.** Story 4.1.4 covers vertex drag only. Unspecified: moving or resizing or rotating a constrained element, group transform with constraints, and arrows bound to a shape the solver moved. The latter must be recomputed in the same transaction, and the redo "replays the stored patch" claim needs to include the binding-derived geometry. **Recommendation:** add ACs for transform-with-constraints and binding recompute after a solve.
- [ ] **Spike 0.1.5 needs network and manual steps.** Capturing five scenes "exported from excalidraw.com", checking `types.ts` against the repo source and running the JS originals need network, Node and (for the exports) UI interaction an agent run may not have. **Recommendation:** make the fixtures hand-authored from `types.ts`, or name the manual step and its owner as a blocker.
- [ ] **SVG export injection.** Story 5.2.1 writes user text into `<text>/<tspan>` and `fileId` or image data into SVG. There is no AC for XML escaping or for refusing `svg+xml` image payloads in output. **Recommendation:** add an escaping property test (text containing `<`, `&`, `"`, `]]>`).
- [ ] **Scale between Excalidraw pixels and scene units.** ADR-002 sets 1 unit = 1/16 inch, so a 100 px Excalidraw rect becomes about 6 inches. Import and export need a stated scale factor, and the export round trip requires scale 1. Story 3.2.x tests treat units and px as interchangeable. **Recommendation:** pin the import/export scale and hit-tolerance semantics in ADR-002 and add an AC.

## Minors
- OD-1 (blocks 1.4.2), OD-3 (4.1.2) and OD-4 (2.1.2) are Tyler decisions on the critical path. The plan correctly lists them, but OD-3 should be settled before Spike 0.1.2 commits any code, so the spike code is not contaminated.
- Story 0.1.4 records the input matrix "inside ADR-007", which is about dependencies. A dedicated research note would be more discoverable.
- Elbow arrows are stored-only and rendered as polylines. This is a visible gap against the "Excalidraw baseline" claim. It is not in an OD, so add it as one.
- Story 1.4.2's model-level "single bundle write switching the reference" does not name the field in `ProjectModelJson` that holds a sheet's schema or reference. The router needs it without parsing the sheet.
- The effort table lists 70 stories and 151 tasks, but several epics' task cost-class mixes ("5M 3S 1M", "1S" repeated) are inconsistent, so the totals cannot be re-derived. Recount before use.

## Re-review of blockers 1-3 (after repair)

Scope: blockers 1-3 only, against the repaired `plan.md` (Stories 1.1.3, 1.1.4, 1.4.5, 4.2.5, rewritten 1.4.2). Checked: story/task cross-references (every cited Story and Task id exists), epic/story/task counts (19/77/165 recomputed from headings, per-epic rows 1.1, 1.2, 1.4, 4.2 and the 40-term glossary match), ADR-001/005 wording, and code facts in `ProjectModelJson.kt`, `ProjectSidecarStore.kt`, `SketchModels.kt`, `ZoneConstraints.kt`.

**Verdict per blocker**
- Blocker 1 (v2 sheet dropped by v1-shaped bundle pipeline): HOLDS. `SheetPayload.V2Opaque` passthrough, per-schema dispatch in codec/reconciler/both `replaceProjectContents`, byte-identity goldens for every project-level write trigger, DB-restore and corrupt-v2 `KeepCorrupt` ACs. Cache tables are dropped with a stated reason, and no stale reference to them remains (plan, ADR-001 4b).
- Blocker 2 (dimensions/zones have no home): HOLDS in design (technical data stays in `project-model.json`; v2 sheet file holds only the scene; conversion refuses with `HasTechnicalData`; legacy editor stays a coherent fallback via router row `(on,1,Failed)`). Verified in code that zones live in `sheetRef.zones` and dimensions in the model's `dimensions[]`. Wording defects R4/R5 below.
- Blocker 3 (conversion before projection wiring): HOLDS in intent (1.4.5 before 1.4.2; flag cannot be enabled until `ConversionReady`; projection never written to `sketch_primitives`). Ordering defects R1/R2 below.

**Remaining issues (none is a design blocker; R1-R3 make the stated order unexecutable and must be fixed before Phase 5)**
- [ ] **R1. 1.4.5 depends on `SheetCodecV2`, which is Task 1.4.2a, inside the story that waits for 1.4.5.** `SheetProjectionSource` must decode a v2 sheet from the sidecar file, and the mixed-project golden needs v2 fixture bytes. Move `SheetCodecV2` (Task 1.4.2a incl. limits/fuzz) into its own story before 1.4.5 and add it to the 1.4.5 row in the dependency table (which also omits 1.4.1, the `schema_version` mirror that the per-sheet dispatch reads).
- [ ] **R2. Story 1.1.4's ACs cannot run at its position.** AC1 needs the converter (1.4.2, which needs 1.1.4) and fusion/CSV/digest projection (1.4.5); AC2 needs the router (1.4.3). 1.1.4 also needs 1.2.2 (lift), yet wave W2 schedules 1.1.4 before W3 (1.2.x). Split: keep layer-mirror and accessors in 1.1.4; move the "carried verbatim" and "refusal" goldens to 1.4.2/1.4.3 (or a late task), and fix the wave text.
- [ ] **R3. Sheet path convention is defined twice.** 1.1.3 and 0.1.1 fixtures put a v2 sheet at `sheets/s2.json`; 1.4.2 puts it at `sheets/<uuid>.v2.json` and adds `sheetRef.file`/`schema`. Today `sheetPath(uuid)` is derived from the uuid at encode and decode (`ProjectModelJson.kt:48,57,174`). 1.1.3 must own `sheetRef.file`/`schema` in `SketchSheet`/`ProjectBundle` (and the `Unreferenced` rule in 0.1.1b depends on it), otherwise 1.4.2 re-opens the bundle pipeline that 1.1.3 closed.
- [ ] **R4. The claim "named dimensions keep referencing primitive ids ... every dimension's primitive ids resolve" is not true of the code.** `SketchDimension` has no primitive reference (fields: key, kind, value, precision, sourceKind, sourceRef, tolerance, locked; `sourceRef` is a label ref or `png:...`), and `Zone` is a named typed-length row resolved by the fusion solver, independent of geometry. Consequence: conversion cannot break them, the refusal is more conservative than needed, and the AC assertions in 1.1.4 and 4.2.5 about "ids still resolve" are untestable. Replace with: output equality through fusion/CSV/digest, and state what a v2 delete or edit of a labelled element does to a dimension whose `sourceRef` points at it (nothing, or a warning).
- [ ] **R5. The refusal predicate "any dimension referencing [the sheet]" is undefined.** Dimensions are project-scoped (no sheet uuid). Define it as either "sheet has zones" only, or "project has any dimension", and put that in `ConversionPolicy` and the router reason text (`SketchReasonText` must carry `HasTechnicalData`). Also state the user path for a NEW v2 sheet before 4.2.5: it has no zone/dimension surface, and 4.2.5 is not in `ConversionReady`; either gate the flag on 4.2.5 or say new sheets are v2 with that gap (parity gate 6.2.4 already blocks rollout).
- [ ] **R6. `ConversionReady` is a hand-set constant.** Add a test that fails when it is true while the named tests (`BundleV2PassthroughTest`, `ReconcilerV2GoldenTest`, `MixedProjectFusionGoldenTest`) are absent from `AllBusinessTests`, and make the converter (not only the router) refuse when it is false. Also add 1.4.2 to the 4.2.5 dependency row (it edits a converted sheet) and note that 4.2.5 must re-run `ZoneConstraints.resolve` after each commit as v1 does.
