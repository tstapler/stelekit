# ADR-004: One draw list, a Clean/Sketchy style strategy, both shipped in v1

**Status**: Proposed (stays Proposed: the default style for new sheets is owner decision OD-5; CJK/fallback-font policy comes from Spike 0.1.3b)
**Date**: 2026-11-14

## Context
Owner decision (2026-11-14): both Clean and hand-drawn (Sketchy) styles ship in v1. Targets: Desktop, Android and Web first (Web stores sheets through OPFS atomic replace, owner decision D-104; Sketchy availability is per target); iOS compile-only and storage-unavailable. Elements carry Excalidraw's `roughness` and `seed`.

## Decision
- Pipeline: `SceneElement -> DrawOp list (scene space) -> {Compose painter, SVG writer, PNG writer}`. Parity of export with screen is structural. Draw lists are asserted in `commonTest` (golden), not pixels; pixel tolerance is a separate per-target check.
- `StrokeStyleProvider` interface with `CleanStrokeStyle` (identity geometry) and `SketchyStrokeStyle` (seeded double stroke, midpoint bow, hachure/cross-hatch/zigzag fill, per the MIT rough.js algorithm family, own implementation of a subset: line, rectangle, ellipse, polygon/path, curve). A per-element `roughness` of 0 renders Clean; a per-sheet default style chooses the starting value for new elements (Sketchy is Excalidraw's default feel; default for new sheets = Clean, owner can flip, OD-5).
- PRNG: an in-repo xorshift/mulberry-style generator seeded from `ElementBase.seed`; `kotlin.random.Random` is not relied on for cross-target identity. Goldens generated from the JS originals are fixtures (Spike 0.1.5).
- Freehand uses a clean-room Kotlin port of the MIT perfect-freehand algorithm with the notice kept in the file header and a `NOTICE` entry; golden outputs generated from the JS original.
- Fonts: bundled via `compose.components.resources`; no system fallback for diagram text; measured width/height/line breaks persisted per element and re-measured only on edit (`TextMetricsProvider` seam, fixed-advance fake for tests).
- Degradation near the 5,000-element cap: disable Sketchy, skip shadows, cull off-screen (non-blocking banner).
- No new runtime dependency; no WebView; no Skia in commonMain.

## Alternatives rejected
Clean only (contradicts owner decision); rough.js via JS bridge (no on all targets); render per-element composables (recomposition cost).

## Consequences
Sketchy on wasmJs/iOS needs rendering checks (Story 2.2.3). iOS is compile-only for v1.

## Spike 0.1.3b/c/e decisions: text metrics, CJK, offscreen render (2026-11-16)
Evidence: `research/determinism-spike.md` (VERIFIED by `DeterminismSpikeJvmTest`, `DeterminismSpikeWasmTest`, `AndroidPixelSpikeTest`; every number printed by those tests).
1. **Latin text with a bundled font is cross-target stable.** With identical font bytes (a 10 KB DejaVu Sans Latin subset standing in for the OD-4 font) widths differ by 0 px and line breaks at a 120 px wrap are identical on JVM, wasmJs and Android Robolectric, so the "persisted metrics authoritative" pivot is NOT triggered. Android lines are 1 px taller (24 vs 23 at 20 px). Platform default fonts differ by up to 5 px ("Auth Service": 117 JVM, 112 wasm, 114 Android), so no layout may use a platform font. Caveat: the subset had kerning and GSUB/GPOS removed, so shaping differences are unmeasured and Story 2.1.2 repeats the check with the real OD-4 font.
2. **CJK policy (b) is adopted**: CJK text uses the platform fallback font; its metrics are persisted per element, excluded from cross-target goldens, and wrap points for CJK are not asserted across targets. Reason: "データ" measures 60 px on JVM and Android but 27 px (default font) or 37 px (bundled Latin font) on wasmJs, which has no CJK glyphs. Policy (a), a bundled CJK subset, was not measured (no CJK font available here, OD-4 open) and stays an owner option that would replace this policy if the measurement later passes.
3. **wasmJs offscreen `ImageBitmap` and PNG encode work.** The rect-plus-text fixture renders non-blank on wasmJs with the same pixel hash as JVM, and `Image.makeFromBitmap(...).encodeToData(PNG)` returns 1,250 bytes on both. Story 5.2.2 uses the skiko path on wasm and does not need the Canvas-element seam (the PNG signature and a decode on wasm were not checked; byte equality with JVM is INFERRED from the equal size). iOS compile was not run on this host.
4. **Robolectric native graphics is usable for Android pixel parity of shapes and strokes** (0 of the shape-region pixels differ from JVM) and drifts on text (306 of 20,000 pixels, max channel delta 204, consistent with the 1 px line height). Task 2.1.3c keeps Robolectric with the tolerance: shapes exact, text at most 2% differing pixels or compared by draw list; on-device parity (Story 6.2.4c) is not covered by this run. Single run, so determinism across reruns is INFERRED.

## OD-4 bundled fonts and licences (Task 2.1.2b, 2026-11-16)
Owner accepted the recommended default (OD-4): bundle OFL fonts for the style panel's "Hand-drawn / Normal / Code" set; the agent picked the families. All three are SIL OFL 1.1, bundled unmodified (no subsetting, so Reserved Font Names stay valid), files in `kmp/src/commonMain/composeResources/font/`, licence texts in `.../composeResources/files/font-licenses/`, entries in `NOTICE`.

| Normal | Source Sans 3 Regular (`sketch_normal.otf`, 334,924 bytes) | OFL 1.1, (c) 2010-2024 Adobe, RFN "Source" | 2, 4, 6, 7 and any unknown id |
| Code | Source Code Pro Regular (`sketch_code.otf`, 131,128 bytes) | OFL 1.1, (c) 2023 Adobe, RFN "Source" | 3 (Cascadia), 8 (Comic Shanns) |

- Bundled-font coverage (cmap read with fontTools, VERIFIED): all three cover Basic Latin, Latin-1, U+2013-2014, U+2018-2019, U+201C-201D, U+2022, U+2026 and U+20AC; none covers CJK, and Kalam lacks Latin Extended. `ComposeTextMetricsProvider.hasGlyph` reports exactly that set, so any other code point (CJK included) takes the platform-fallback path of policy (b) above and its persisted per-element size stays authoritative.
- The Spike 0.1.3b caveat (kerning and GSUB/GPOS were stripped from the stand-in subset) still applies to cross-target shaping: only the JVM measurement of these real fonts has run (`ComposeTextMetricsProviderTest`); the JVM/wasm/Android equality check with the real files is UNVERIFIED until Task 2.1.2c's entry-point tests and the web pass run.
- Bazel does not generate the Compose resources class, so the Bazel build compiles `kmp/src/commonMain/bazel_stubs/SketchFontResources.kt` (state `Failed`, no bundled fonts) in place of the Gradle-only loader; the bundled fonts are therefore available in Gradle builds only until Bazel gains Compose resources support.

## Sketchy availability per target and large-drawing degradation (Story 2.2.3, 2026-11-16)
- **Rule (restated by the owner, 2026-11-17).** `SketchyAvailability` (`sketch/v2/render/SketchyAvailability.kt`) marks a target `Unavailable` when its Sketchy render of architecture-15 differs from the JVM render in more than `PIXEL_TOLERANCE_FRACTION` (2%) of pixels, or its Sketchy draw-list build for 500 elements takes more than `SKETCHY_BUILD_BUDGET_MS` (4 ms, absolute) on that target. This replaces the original "more than 2x the Clean build on the same host" rule: Clean is so cheap that a ratio trips on builds that are well under 2 ms, so the owner chose an absolute budget. The Sketchy/Clean ratio is still measured and printed (`SketchyMeasurement.ratio`) but is informational and never switches a target. `StrokeStyleProvider.forTarget` resolves an `Unavailable` target to Clean; stored `roughness` and `seed` are untouched and the user sees "Hand-drawn style is not available on this device yet".
- **Recorded state (updated 2026-11-17; the 2026-11-16 Web-off entry is reversed).** No target is `Unavailable`; `SketchyAvailability.RECORDED` is empty. The JVM render is the reference mask (`Architecture15Golden`, checked by `LargeSceneDegradationTest`); wasmJs matched it with 0.0 differing pixels (`ARCH15_WASM_DIFF`, `LargeSceneDegradationWasmTest`), so the pixel half of the rule passes on every measured target, and Android shapes were pixel-exact in the Spike 0.1.3 Robolectric run. Web's 500-element Sketchy build measured about 1.1 ms, under the 4 ms budget (below). iOS is UNVERIFIED: `compileKotlinIosArm64` is a no-op on a Linux host and BUG-001 blocks the CI compile, so neither its Sketchy render nor its build time has run; a macOS or CI run must compile the iOS target and then run the architecture-15 pixel check and the 500-element build on a device before iOS can be claimed either way.
- **Build time and ratio, JVM.** `LargeSceneDegradationTest`: 500 roughness-1 rectangles, each sample 25 builds with a fresh `DrawListBuilder` per build (the builder caches per element id, so a sample must not reuse one), min over 15 rounds after warm-up, divided by 25. Three runs on 2026-11-18: sketchy 505,291 ns vs clean 230,300 (2.19x, first run after compile), 371,191 vs 134,138 (2.77x), 325,529 vs 129,927 (2.51x); all about 0.3 to 0.5 ms against the 4 ms budget. The earlier figure of 1.28x (754,260 vs 587,298 ns) was a correction owed: it came from single-build samples dominated by fixed per-call overhead, which hid the real ratio of about 2.2x to 2.8x. The ratio is informational now; the assertion is the budget.
- **Build time and ratio, wasmJs (Task 6.2.9a).** `SketchyBuildRatioWasmTest` (`:kmp:wasmJsBrowserTest`, ChromeHeadless 146, best of 9 timings of 20 fresh builds each, 500 roughness-1 rectangles) printed `SKETCHY_BUILD_RATIO_WASM`: 2.17x (1,085,000 vs 500,000 ns), 2.26x, 2.29x and 2.18x in four runs on 2026-11-16, and on 2026-11-18 sketchy 1,160,000 vs clean 520,000 ns (2.23x, 1.16 ms). Under the original 2x ratio rule that marked Web `Unavailable`; under the restated rule (absolute 4 ms budget) 1.16 ms passes with about 3.4x headroom, so the Web entry was removed and the web build draws Sketchy. The browser clock is about 0.1 ms, which is why the test batches. The test asserts the budget and pins `RECORDED` for Web to the measurement. These are software Chrome on a 24-CPU desktop; a device may be slower, so the budget is the figure to re-check on real hardware.
- **Degradation.** One threshold: `SceneLimits.softElementThreshold` (4,000) or `softConstraintThreshold` (160). `LargeSceneDegradation` turns on the UX steps in order (Sketchy drawn as Clean, shadows skipped, culling, low-res thumbnails, constraint glyphs hidden), raises the `LargeDrawing` banner once, and "Re-enable effects" restores the three effect steps for the session.
