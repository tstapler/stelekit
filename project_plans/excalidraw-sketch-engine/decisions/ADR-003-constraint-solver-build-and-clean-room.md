# ADR-003: Bespoke pure-Kotlin LM/DogLeg constraint solver, clean-room from planegcs

**Status**: Accepted (2026-11-16, Story 4.1.3: the spike exit criteria of item 6 are met by the production solver on JVM and wasmJs; see "Story 4.1.3 results")
**Date**: 2026-11-14

## Context
Success metric 3 needs a FreeCAD-style 2D solver on all targets. Candidates (research/build-vs-buy.md): planegcs (LGPL-2.1+, C++/Eigen/Boost, no Kotlin/wasm build found), SolveSpace libslvs (GPL-3.0+), Multik (alpha), EJML (JVM only).
The repo license is Elastic License 2.0 (`LICENSE`, source headers `SPDX-License-Identifier: Elastic-2.0`), which is not LGPL/GPL-compatible for linking or derivative code. VERIFIED by reading `LICENSE` and a source header.

## Decision
1. Build the solver in `kmp/.../sketch/constraints/` (commonMain, pure Kotlin, dense `DoubleArray`), no new dependency. Contract: `solve(ConstraintProblem) -> SolveResult` = `Solved | Conflict(ids) | Redundant(ids) | NoConvergence`, per-component, with iteration and wall-time caps; never throws to the UI.
2. Algorithms: Levenberg-Marquardt with analytic Jacobians as the baseline; DogLeg and BFGS fallbacks only if Spike 0.1.2 shows need; QR with column pivoting for rank (DOF, redundancy, conflict); connected-component decomposition; warm start from the last solution during drag.
3. **Clean-room boundary**: the implementer reads planegcs/SolveSpace documentation and the published algorithm names (DogLeg, LM, BFGS, constraint list from `Constraint.h`) but does not copy or translate source. The spike and implementation tasks record "no planegcs source open while writing" in the task notes. Planegcs/SolveSpace may be used only as an offline test oracle in the spike (results captured as fixtures; no linking, no vendoring). Any direct port is out unless the owner makes a licensing decision (OD-3).
4. Package import direction: `sketch.constraints` imports nothing from `ui`, `db`, `repository`, `merge` (`SketchSolverImportDirectionTest`, mirrors `JobsScheduleImportDirectionTest`).
5. v1 constraint set: coincident, point-on-object, horizontal, vertical, parallel, perpendicular, tangent (line-circle, circle-circle, line-arc, endpoint), equal, symmetric, fixed/block, distance (+X/Y), angle, radius, diameter, driven (reference) dimensions. Geometry: point, line, circle, arc, rect (4 lines + implicit constraints), polyline. Out: ellipse/conics, B-splines, external geometry. **Scene mapping (consistency B1, owner decision OD-8)**: a circle is an `EllipseElement` with equal radii (an ellipse with unequal radii is NOT a constraint target), and `PointElement` and `ArcElement` are added to the `SceneElement` hierarchy as technical geometry so every geometry kind above has a scene element. If OD-8 is declined, arc, free point and the line-arc/circle-arc tangent cases are dropped from this list (and from success metric 3's tangent wording).
6. Spike exit criteria: maximum constraint residual under 1e-6 scene units after every successful solve over the randomised property corpus (a solve that stops above it is `NoConvergence`, never committed as solved; the solver's own stop tolerance is 1e-9 relative to sketch scale); 100-constraint solve under 50 ms on JVM and under 150 ms on wasmJs (hard bars; 50 ms on wasmJs is an advisory target, owner-confirmable D-30); no NaN on a degenerate fuzz corpus; redundancy and conflict ids correct on generated cases; no branch flip across a 200-step scripted drag; JVM vs wasm max abs difference under 1e-6.

7. **Fallback acceptance (iteration 9, P4) and per-target tier (iteration 15, D-114)**: the spike decides a `SolverTier` (`Full`, `GeometricOnly` or `Hidden`) PER TARGET (JVM, standing for desktop and Android, and wasmJs): a miss of a target-independent criterion (residual, `Redundant`/`Conflict` classification, branch flip, NaN) selects `GeometricOnly` on every target, a time miss only on its own target, so a wasmJs time miss never takes the full solver from desktop and Android; the geometric-only set is re-measured on the missing target and that target is `Hidden` if it misses too. For a target whose tier is `GeometricOnly` (Coincident, Horizontal, Vertical, Equal, Distance), the acceptance scenario is the "fallback plate" of requirements metric 3 (plate 6 x 4 in plus a square pocket; analytic DOF 4; conflicting Distance rejected with both ids named), because the bracket plate needs Fixed, Radius and Parallel. Metric 3 keeps every numeric bar under the fallback; only the named scenario changes, and it changes back when Fixed, Radius and Parallel each pass their randomised property test.

## Alternatives rejected
Port planegcs (LGPL derivative); link libslvs (GPL + cinterop on 4 targets); Multik/EJML (alpha / JVM-only, unneeded at 200x200); WebView solver (no).

## Consequences
First-release robustness may trail FreeCAD; non-convergence returns the last good geometry plus diagnostics, so failure is visible, not corrupting.

Code (deleted after Story 4.1.3, once the production solver replaced it; the recorded results below are kept): `kmp/.../sketch/constraints/spike/*.kt` (clean-room dense LM + pivoted Householder QR; no planegcs/SolveSpace source opened), tests `SolverSpikeTest.kt` (also deleted; 8 tests, all pass on JVM `:kmp:jvmTest` and wasmJs `:kmp:wasmJsBrowserTest` in ChromeHeadless 146). The machine had load average 20-75 from parallel agents, so wall times are upper bounds. All figures VERIFIED by those runs.
- 100-constraint sketch (40 lines: 39 Coincident, 30 H/V, 16 Equal, 15 Distance; start perturbed +/-0.4), seed 1: JVM cold 8.0 ms, steady median 7.6 ms, max 13.2 ms (bar 50 ms: met); wasmJs cold 60 ms, steady median 38.5 ms, max 43 ms (hard bar 150 ms met; advisory 50 ms met for steady state, missed cold). Residual 4.4e-9 (bar 1e-6 met). JVM-vs-wasm max abs difference of the solution vector 3.6e-13 (bar 1e-6 met).

Under a quiet machine these would be lower, but the iteration count is machine-independent, so the JVM bar is met on typical starts and missed on the tail. Mitigations not yet tried: Dogleg, analytic-Jacobian row scaling, component decomposition and warm start (real drags warm-start, which the 200-step test shows converging in few steps).

- Degenerate QR fuzz (zero, 1e300, 1e-300, rank-k random matrices): no NaN, rank correct.
- Not done: oracle fixtures from planegcs/SolveSpace (neither is installed or allowed to be read; analytic expectations were used instead), Bazel run, Android device timing.

## Story 4.1.2 note: production equations and the open tail risk (2026-11-16; status stays Proposed)
- Production residuals and analytic Jacobians for the v1 set are in `kmp/.../sketch/constraints/constraints/` (`ConstraintEquation`; Coincident, Orientation, Tangent, Dimensional, Symmetric). Each Jacobian matches central differences to under 1e-6 over 25 random configurations per type (`JacobianFiniteDifferenceTest`, JVM and wasmJs). Parallel, Perpendicular, PointOnLine and Symmetric are polynomial rows, so they stay finite for zero-length geometry; angle and tangent rows freeze their branch (side, tangency kind, `AnglePolicy`) at creation.
- OPEN RISK (not addressed by 4.1.2): the spike's damped-plateau tail (seeds 111 and 127, 45-61 LM iterations, 52-78 ms on JVM against the 50 ms bar) belongs to the solve loop. Story 4.1.3 (Tasks 4.1.3a loop, 4.1.3b components, 4.1.3c Dogleg) must try Dogleg, Jacobian row scaling (the production rows are deliberately unscaled so a per-row normalisation in the loop can be measured) and component decomposition, and measure the 30-seed corpus before this ADR can flip to Accepted. Float storage cannot meet the 1e-6 bar (research/determinism-spike.md), so storage stays Double.

## Story 4.1.3 results: the plateau tail is closed; status flips to Accepted (2026-11-16)
Code: `kmp/.../sketch/constraints/{Solver,Components,Diagnosis,SolverTier}.kt` (clean-room: textbook LM and dogleg trust-region steps, no planegcs/SolveSpace source opened). Tests: `SolverCorpusTest`, `SolverPropertyTest`, `SolverDeterminismTest`, `FallbackPlateScenarioTest`, `BracketPlateScenarioTest`, `SolverTierTest` (all pass on JVM `:kmp:jvmTest` and wasmJs `:kmp:wasmJsBrowserTest`, ChromeHeadless 146). The machine had load average 12-17 from parallel agents, so wall times are upper bounds; the tests assert the best of 5 runs, iteration counts are machine independent. Figures VERIFIED by the `SOLVER ...` lines those runs print.
- Open risk (seeds 111 and 127 of the 30-seed corpus), measured per algorithm on the production equations:

| algorithm | seed 111 | seed 127 | JVM ms (111 / 127) | wasm ms (111 / 127) |
|---|---|---|---|---|
| LM (Marquardt scaling, gain-ratio damping; the spike's loop) | 61 it | 45 it | 56 / 40 | 79 / 61 |
| LM + Jacobian row scaling | 63 it | 24 it | 51 / 20 | 93 / 46 |
| LM, no component decomposition | 61 it | 45 it | 51 / 37 | 75 / 60 |
| DogLeg (Gauss-Newton + Cauchy point, trust region) | 5 it | 5 it | 8.2 / 5.2 | 23 / 23 |

  The LM plateau reproduces exactly (61 and 45 iterations). Row scaling helps one seed and not the other; decomposition changes nothing because the 40-line chain is a single connected component (it pays on sketches with independent parts: the fallback plate and its pocket solve as two components). DogLeg clears the plateau in 5 iterations, so it is the default first algorithm and LM the fallback (`SolverOptions.DEFAULT_ALGORITHMS`); the result names the algorithm that succeeded. BFGS was not needed and is not built.
- Corpus and bars, all 30 seeds (100..129) Solved, worst final residual 7.1e-9 (bar 1e-6): JVM worst best-of-5 solve 8.1 ms (bar 50 ms); wasmJs worst 27.8 ms (hard bar 150 ms, advisory 50 ms also met); seed 1 cold JVM 58 ms under load (the first call JIT-compiles the solver; the spike measured 8 ms cold with a simpler loop, so JVM cold start is the one figure to re-measure on a quiet machine) and wasmJs cold 26.8 ms.
- JVM vs wasm: max abs difference of the seed-1 solution vector 6.7e-9 (bar 1e-6). Finding behind that number: with a Gauss-Newton ridge of 1e-10 a 4e-16 relative perturbation of the start moved a corpus solution by 5e-4 (the ridge amplifies last-bit noise into the null space of an under-determined sketch, DOF 21 here), so the two targets would have disagreed by more than the bar; the ridge is 1e-6 (relative to the Gram diagonal), which moves the solution by under 2e-8 on both targets (`SolverDeterminismTest`; ridge sweep 1e-10 to 1e-5 on JVM: worst difference 5.2e-4, 9.7e-4, 5.6e-6, 2.1e-5, 1.9e-8, 7.0e-9, worst iterations 18, 21, 18, 20, 15, 15). The earlier spike figure of 3.6e-13 was one seed where both targets happened to take identical paths.
- Classification and DOF: `Redundant([c3])` for H, V, duplicate H with DOF 2; `Conflict([c4, c5])` for H plus Distance 10 and 12; an impossible triangle is not `Solved`; DOF equals `variables - rows` on 40 random primitive-only chains; conflict ids are read at the stall point of the failed component, not at the start. Degenerate input (a zero-length line under a Distance, non-finite start) is `Degenerate` with finite values and the start parameters returned, never an exception. A Parallel on a zero-length line stays a finite, already-satisfied row (its polynomial gradient is non-zero) and solves; the plan's "Redundant/Degenerate" wording does not apply to that row alone. A fuzz of 200 random four-constraint mixes on near-zero geometry returns only finite values.
- Tier (D-114): all target-independent criteria met (residual, classification, branch flip on the 200-step drag with the production tangent equations, NaN), both time bars met, so `SolverTier.Full` on JVM (desktop and Android) and wasmJs. `SolverTierPolicy` encodes the per-target rule and `SolverTierTest` its matrix. The fallback plate (6 x 4 in plus pocket, DOF 4, conflicting Distance names both ids, drag translates the plate with 6 x 4 intact to 1e-6) passes on the geometric-only set, and the bracket plate (Fixed, Radius, Parallel, DOF 0) passes on `Full`; Fixed, Radius and Parallel each pass their randomised property test, so `BracketPlateScenarioTest` is enabled.
- Why Accepted: every exit criterion of item 6 is now met by the production solver on both targets. Not done and not blocking: oracle fixtures from planegcs/SolveSpace (clean-room: analytic expectations only), an Android device timing (the JVM figure stands for Android, D-114), a quiet-machine re-run of the cold JVM start.

## Note after Story 4.2.7d (solver ridge floor)
- Symptom: a centre-to-edge `PointLineDistance` on a near-vertical line made a free circle coordinate jump (cy to 5074), and a later distance put the circle on the mirrored side.
- Cause: DogLeg's Gauss-Newton ridge `ridge * max(diag, 1e-9)` barely damps a coordinate whose gradient is near zero.
- Change: the ridge floor is the named constant `GAUSS_NEWTON_DIAGONAL_FLOOR = 1.0` in `Solver.kt`. The LM damping floor stays 1e-9, because raising it breaks `SolverCorpusTest.dogLeg_should_ClearTheDampedPlateau...`, which documents that LM crawls on seed 111.
- Evidence: the 30-seed corpus (worst best-of-5 6.1 ms JVM, 28.2 ms wasm), the property tests and the Jacobian finite-difference test pass.
- NOT re-done: the JVM-versus-wasm comparison of the printed seed-1 solution (the earlier figure was 6.7e-9 against a 1e-6 bar). Verification must re-run it before this ADR's cross-target claim is repeated.

## Note after review fix D (ridge and trust radius scale)
- Symptom: an absolute ridge floor of 1.0 over-damps a large sketch. An angle row at L = 9,600 units has gradient ~1/L, so its Gram diagonal is ~1e-8 against a ridge term of 1e-6: DogLeg's Gauss-Newton step is a few percent of Newton, the 100-iteration budget runs out and Levenberg-Marquardt takes over (`SolverScaleTest`: 104 iterations on LM before, 11 on DogLeg after). The initial trust radius of 1 unit has the same absolute-scale flaw.
- Change: both are multiplied by the component's extent over `RIDGE_REFERENCE_EXTENT` (256 units), clamped at 1: the ridge floor becomes `1 / scale^2`, the initial radius `scale`. A component whose coordinates stay under 256 units sees no change at all, so the earlier 4.2.7d fix (near-vertical centre-to-edge, `JacobianFiniteDifferenceTest`) is untouched there.
- Evidence: `SolverCorpusTest` and the other `sketch.constraints` JVM tests pass. wasm: see the review-fix report. Sketches above 256 units across with a barely coupled coordinate are the one place the 4.2.7d protection weakens (by `scale^2`); that trade is not measured beyond `SolverScaleTest`.

## Note after the integration pass (solver surface)
- The tier is read, not assumed: `SolverTierFacts.Recorded` (kmp/.../sketch/constraints/SolverTierFacts.kt) holds the Story 4.1.3 measurements and `HostServices.tier` takes `tierOf(target)` from it (`SketchEditorSession` picks `WasmJs` for the browser keymap, `Jvm` otherwise). A target with no measurement is `Hidden`; iOS has no v2 editor, so it never asks. Re-measuring edits `Recorded` and `SolverTierFactsTest`.
- `DistanceX` and `DistanceY` are reachable as the kinds `ConstraintKind.DistanceX` and `DistanceY` (Constrain items "Horizontal distance" and "Vertical distance", `Full` tier only); the equation is built with the pair ordered so the start pose is positive, so the typed value is an unsigned length.
- `TangentLineArcEndpoint` and `TangentArcArcEndpoint` are the Tangent kind over a segment and an arc's start or end, or two arcs' ends; the shared end is joined by a Coincident of the user's own, as the equations document.
- The spike code and `SolverSpikeTest` were deleted; the results recorded above stay as the record.
