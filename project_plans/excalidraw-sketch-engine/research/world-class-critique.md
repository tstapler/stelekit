# World-class critique: SteleKit v2 sketch editor (phone-first measured sketching)

Scope: `kmp/src/commonMain/kotlin/dev/stapler/stelekit/sketch/v2/`, `.../ui/sketch/v2/`, `.../units/`, plans in `project_plans/excalidraw-sketch-engine/` and `home-project-sketching/`. Read-only review at commit 06890bb2a9 plus branch state. No builds were run.

Confidence labels: VERIFIED = file opened or grep run (cited). ABSENT = a case-insensitive grep over `sketch/v2` and `ui/sketch/v2` returned zero hits for the term (a naming miss is possible). INFERRED = reasoning from code, not run.

Benchmark cross-reference: `research/world-class-benchmark.md` did not exist when this was written, so nothing below is compared with named competitors. Re-check once it lands.

Paths below are relative to `kmp/src/commonMain/kotlin/dev/stapler/stelekit/` unless they start with `project_plans/`.

Cost classes (price-weighted agent work, not human time): XS under 1 agent wave and cheap; S one worker wave; M several waves with review; L multi-wave with a cross-cutting schema or UI migration.

## Verdict

The engine is a strong Excalidraw clone with a real constraint solver, but it is not yet a measured-drawing tool. A phone user drawing a room cannot (1) work in metric, (2) get a dimension string onto an exported image, (3) draw walls and doors, (4) trace over a photo or plan, or (5) print to scale. Those five gaps matter more than any further polish of the existing tools. The strongest parts (determinism, schema, conflict copies, import/export of Excalidraw, constraint model) are real, but the whole editor ships behind a default-Off flag with its adoption gate waived, so none of it is yet proven in use.

Pinned: deterministic codec, solver correctness on the constraint set, draw-list goldens, snap maths, dimension edit state machine, import/export round trip of Excalidraw.

NOT pinned or UNMEASURED:
- Real phone use: usability sessions not run (`usability-results.md:3`), Pixel_Fold frame time not measured (`pivots.md`), A1 gate waived.
- Export contains dimensions: no test can pass because the feature does not exist (#3).
- Metric entry and rounding to 1/32: no test; behaviour is "round to 1/16 with a notice".
- Touch hit areas and gestures: the headless render tests show layout only (per `CLAUDE.md` UI section); emulator checks are owner-run.
- Large-scene behaviour on Android and iOS: iOS has no sketch storage at all in this release (requirements preface).
- Multi-device conflict behaviour beyond "keep a copy".

## Open questions only the owner can answer

1. Is the stored unit allowed to change? Metric and 1/32 exactness are cheap as display-only conversions but are lossy at 1 mm; an exact store (integer micrometres or rationals) is a schema change touching the codec, solver tolerances, and the v1 bridge.
2. Is metric a real requirement for you, or only for other users? If only you and imperial, E2 can shrink to 1/32 and 1/64.
3. Is v2 the editor you intend to make the default? The flag is Off and the A1 gate was waived; roadmap items E4 to E7 assume yes.
4. What is the first real drawing you want to finish on the phone (a floor plan, a cabinet cut list, a wiring diagram)? It sets whether E6 walls or E7 print comes before E5.
5. Is a PDF at a chosen scale a requirement, or is sharing a PNG/SVG with dimensions (E1) enough?
6. Do you want agents to write into sketches, or only read them? Write access needs a command-level audit trail.
7. Is multi-device simultaneous editing a real use (E14), or is the lease plus conflict copy acceptable?
8. May iOS stay without sketch storage for this roadmap?
