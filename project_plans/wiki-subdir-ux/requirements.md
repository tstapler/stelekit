# Requirements: wiki-subdir-ux

**Date**: 2026-10-01
**Type**: feature addition
**Complexity**: 4 — high-stakes / cross-cutting (touches GraphManager, all four platform filesystems, git sync, and the on-disk reconciliation path for user notes; large appetite confirmed)

## Problem Statement

A graph's effective content root (repo root + "notes subfolder") can silently diverge from where the user's actual pages/journals live on disk — for git-backed graphs because `detectGitRoot()` can only infer a subfolder by walking *upward* from the graph path to find `.git`, which is always empty right after a fresh clone (the graph path *is* the clone root at that point); for SAF-mounted graphs because the equivalent detection is skipped entirely (`GraphManager.kt:998-1001` bails out for `saf://`/`content://` paths outright). When this happens, the app looks empty (0 pages) with no indication of why, the fix (the "Notes subfolder" field) is buried inside a multi-step wizard nobody opens unless they already suspect a config problem, and any writes that happen in the meantime (e.g. new journal entries) land at the wrong location and get silently orphaned once the subfolder is corrected.

This was discovered via a real diagnostics export (`stelekit-diagnostics-*.txt`, generated by the feature shipped in #376) showing exactly this: `pages/ exists=false`, `journals/ exists=true files=2` at the configured root, a `NESTED GRAPH CANDIDATE` correctly identified at `logseq/` but never surfaced to the user, and 11 DB journal entries with no corresponding file because they were indexed before/after the misconfiguration.

## Baseline

Today, a user with this problem has no path to self-diagnosis beyond: notice pages are missing, export a diagnostics `.txt` file (a feature that itself has to be known about and triggered manually), read raw log/path dump text to spot a `NESTED GRAPH CANDIDATE` line buried mid-file, manually open Git Setup → Step 2, type the correct subfolder by hand, save, and then manually find and relocate any stray files that were written to the wrong location in the meantime — with no tooling to even identify which files those are. This entire sequence happened in a live support conversation before this project existed.

## Users / Consumers

Single-user personal note-taking app (SteleKit); the person affected is whoever owns the graph — currently Desktop (JVM) and Android users with git-backed graphs, and SAF-mounted Android users, per this project's expanded scope. No external/third-party consumers — this is entirely first-party UI + `GraphManager`/platform-filesystem code.

## Success Metrics

- A misconfigured subfolder (content root has zero/near-zero pages+journals while a sibling folder has both) is surfaced **proactively in-app** (banner/badge) within one app session of the mismatch existing — not only via a manually-triggered diagnostics export.
- Changing the "Notes subfolder" setting with pre-existing content at the old effective root **never silently orphans files**: the user is always shown what would be left behind and given an explicit choice (move / merge / leave) before anything changes.
- The "Notes subfolder" value and the currently-configured repo root are visible from at least one place outside the Git Setup wizard (baseline today: zero places).
- Freshly cloning a repo whose content is nested one level down (the `logseq/`-style layout this project's own graphs use) no longer requires the user to manually discover and type the subfolder — baseline today: always blank, always manual.

## Constraints

- Solo-developer project — no dedicated QA, no staged/gradual rollout infrastructure (no feature-flag system exists in this codebase today — confirmed by searching `kmp/src/commonMain` for `FeatureFlag`/`GrowthBook`, no hits).
- Must not regress the existing, already-shipped Git Setup wizard (`project_plans/git-setup-ux/`, file pickers + OAuth) or the existing disk-conflict resolution flow (`project_plans/disk-conflict-dialog-ux/`) — both are reused/extended, not replaced.
- Must work across every platform that currently supports git sync or SAF mounting today: JVM/Desktop, Android (git + SAF), Web/Wasm (git write service exists per `WasmGitWriteService.kt`). iOS has no git repository implementation yet (per `git-setup-ux/requirements.md`'s own context) — out of scope by platform absence, not by choice.

## Non-functional Requirements

- **Performance SLO**: candidate/mismatch detection must not add perceptible latency to warm reconcile (today's `GraphLoader` warm reconcile completes in ~150-200ms per the diagnostics log sample; a filesystem scan 1-2 levels deep should stay well under that budget, but confirm in Phase 2 research for SAF document-tree enumeration, which is a remote content-provider call per level and may be materially slower).
- **Scalability**: not applicable — this operates on directory-listing scale (tens to low hundreds of entries), not per-page content.
- **Security classification**: internal/personal — all data stays on-device or in the user's own git remote; no new network surface.
- **Data residency**: not applicable.
- **Data safety**: this is the dominant NFR for this project. Any move/merge operation touches the user's actual notes; see Risk Control below.

## Scope

### In Scope

Full brainstorm scope (`project_plans/wiki-subdir-ux/brainstorm.md`, categories A–E, all 29 ideas), **including SAF-mounted graphs**, per explicit scoping decision:

- **A — Discoverability**: live mismatch banner (extending `GitDetectionBanner`/`GraphContentMainArea.kt`'s banner system to fire when config exists but content doesn't match), persistent repo/subfolder display outside the wizard, reused "Notes in X" subtitle in the graph switcher, empty-state card naming the searched path, auto-fill-on-clone default, first-run coachmark, inline "Validate now" action, content-path breadcrumb, reordered/highlighted diagnostics export, WARN-level logging on mismatch, warning badge in multi-graph switcher.
- **B — Smarter detection**: downward candidate scan at clone time (git) and at initial SAF folder pick (SAF), filtering out app-internal folders (`.stelekit`, `.git`), periodic re-scan on warm reconcile (not just setup time), git-history cross-check for configured-but-never-existed subfolders.
- **C — Move/merge UX**: three-way choice dialog (Move / Merge / Leave-as-is) modeled on `StorageMoveChoiceDialog.kt`'s existing pattern, dry-run manifest before any disk write, per-file conflict resolution reusing `DiskConflictDialog`/`DiskConflictBlockMatcher`, diff preview for same-filename conflicts, verify-after-fix re-scan, symmetric handling of the flatten-back-to-root case. Covers both git-backed (plain filesystem move) and SAF-mounted (document-tree move/copy via platform SAF APIs) graphs.
- **D — Safety guardrails**: three-way path validation on save (doesn't exist / exists-empty / exists-with-conflicts), soft-delete holding area instead of immediate delete on "Move", single atomic git commit for the reconciliation when git sync is on, resumable/idempotent move (crash-safe marker file), explicit (non-silent) logging of a dismissed move/merge dialog as "left in place."
- **E — Scope/audit**: structured "last reconfigured" history entry in the exportable diagnostics file (old root, new root, strategy, files moved).

### Out of Scope

- iOS — no git repository implementation exists yet on that platform; nothing to extend.
- Changing how `detectGitRoot`/candidate-detection works for graphs that have **no** `.git` and are **not** SAF-mounted (e.g. a plain local-path non-SAF, non-git graph) — not a case that currently exists in the registry model per `GraphInfo`/`GraphManager` review.
- Building a general-purpose file-sync/merge engine — the move/merge dialog is scoped specifically to reconciling the *old vs. new effective content root* after a subfolder change, not an arbitrary two-directory diff tool.
- Any new feature-flag/staged-rollout infrastructure — none exists today and this project does not introduce one (see Risk Control).

## Rabbit Holes

- **SAF document-tree move semantics**: Android's `DocumentsContract` has no atomic "move" primitive on all API levels/providers — a move may require copy-then-delete with partial-failure handling, which interacts directly with the "resumable/idempotent move" (D) and "soft-delete holding area" (D) requirements. Flag for Phase 3 planning to pin down per-API-level behavior before committing to a design.
- **Git commit atomicity (idea 22)** when a reconciliation move overlaps with an in-flight auto-sync cycle — needs explicit sequencing with `DatabaseWriteActor`/`GitSyncService` rather than assuming the move and the next sync tick can't race.
- **Candidate-scan depth/cost on SAF** — each directory listing is a remote content-provider round-trip, not a local syscall; "scan 1-2 levels down" could be much more expensive on SAF than on a plain filesystem. Needs a concrete latency measurement, not an assumption, before deciding default scan depth.
- **Re-scanning on every warm reconcile (B)** risks becoming the kind of unbounded/O(graph) read this codebase has explicit rules against (see this repo's `CLAUDE.md` section "Graph-scale reads must be paginated, projected, or chunked") — the candidate scan is a *directory listing*, not a page read, but Phase 3 must confirm it's bounded (fixed shallow depth, not recursive) before implementation, not assume it's safe by analogy.

## Alternatives Considered

- **Fix only via smarter auto-detection (B), skip the move/merge dialog (C) entirely** — rejected: auto-detection can reduce *new* misconfigurations but does nothing for the files already stranded at a wrong location by the time detection improves, and does nothing for a user who deliberately restructures their repo later.
- **Generic two-directory diff/merge tool** (reusable beyond this one scenario) — rejected as over-engineering for this project's actual need; the scoped version (old effective root vs. new effective root, for this one graph) is enough, per the "Out of Scope" note above.
- **Feature flag / staged rollout** for the move/merge logic given its destructive potential — considered, rejected: no existing flag infrastructure in this app, and as a solo-dev project the realistic risk control is dry-run preview + soft-delete + manual testing before each tagged release, not a staged population rollout.

## Feasibility Risks

- SAF move/copy reliability varies across device OEM document providers (a long-standing Android SAF pain point) — the move/merge feature's SAF path may need a more conservative "copy, verify, then prompt to manually delete the old" fallback rather than true move on providers where copy-then-delete-source proves unreliable.
- Soft-delete holding area adds a new on-disk artifact (`.stelekit/trash/<timestamp>/`) that itself needs lifecycle management (retention/cleanup) — scope creep risk if not bounded explicitly in Phase 3.
- Expanding scope to SAF (per the scoping decision) roughly doubles the platform-specific implementation surface for category C/D versus git-only — confirm during Phase 2 research that the Large appetite genuinely covers this before Phase 3 commits to a task breakdown.

## Observability Requirements

- WARN-level log line (not just the existing INFO-level diagnostics-export-only visibility) whenever warm reconcile finds near-zero content at the configured root while a nested candidate exists (idea A.10) — must be greppable in the normal app log without the user needing to know to export anything.
- The diagnostics export (`GraphDiagnostics.kt`) gains a structured "reconfiguration history" section (idea E.29): each subfolder change logged with old root, new root, strategy chosen (move/merge/leave), and file counts affected — so a future support conversation has history instead of a single snapshot.
- No new metrics/alerting pipeline — this is a single-user local app; "observability" here means log lines and the diagnostics export, not a dashboard.

## Risk Control

- No feature flag — ship behind normal release-please versioning (`version.txt`/`CHANGELOG.md`), consistent with how every other feature in this app ships.
- Destructive-operation safety nets are the actual risk control, not a rollout mechanism: dry-run manifest before any write, soft-delete holding area instead of immediate delete, resumable/idempotent move with a crash-safe marker, and the "verify-after-fix" re-scan that proves the result before the dialog closes.
- Regression tests mirroring the existing `WikiSubdirUriGuardTest` pattern, covering move/merge correctness on both JVM and Android filesystems (per brainstorm idea D.26), are a hard requirement for Phase 4 validation to confirm exists in the plan — not optional polish.

## Open Questions

- Exact SAF move/copy fallback behavior per Android API level/provider — needs Phase 2 research, not an assumption.
- Whether the soft-delete trash retention window should be time-based, count-based, or "until next successful git sync" — Phase 3 planning decision.
- Whether the "re-scan candidates on every warm reconcile" (B) should be gated behind a lightweight heuristic (e.g. only when page/journal count is below some threshold) to bound its cost — Phase 3 planning decision, informed by the SAF latency rabbit hole above.
