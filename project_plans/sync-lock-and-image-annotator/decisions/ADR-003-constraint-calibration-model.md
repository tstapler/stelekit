# ADR-003: Multi-distance calibration extends the existing scale and plane models

**Status**: Accepted pending owner review (Phase 4 patch, 2026-11-14; was Proposed, revised after architecture and adversarial review, iteration 2)
**Date**: 2026-11-14
**Project**: sync-lock-and-image-annotator (Epic 3)

## Context

The repo already has tick-based scale fit with division `k` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/calibration/MultiPointCalibration.kt`), a normalised DLT `HomographyFitter` (`calibration/Homography.kt`), and `GeometryCalibration.plane` (`model/GeometryCalibration.kt`). Prior art ranks error terms: tilt, short reference, depth, endpoint, lens last (`annotation-lens-distortion/design.md`, `research/pitfalls.md` section 3). Ticks are collinear, so they cannot constrain a second axis. OpenCV and EJML are JVM or Android only and rejected for runtime (`research/build-vs-buy.md`).

Facts that constrain where a fit can live (VERIFIED this pass):
- `LensMeasurement.distanceMeters` (`calibration/LensMeasurement.kt:51-60`) returns `hypot(...) / pixelsPerMeter` only when `geometry.plane` is absent; whenever a plane exists `pixelsPerMeter` is ignored and the homography result is used. A scalar fit written to `pixelsPerMeter` while a plane exists has no effect.
- The homography maps `RadialLens.undistort`ed native pixels to metres (`LensMeasurement.kt:42-68`, `planeOf` L62-63), so a fitted metric homography can be stored there.
- `keepingGeometry` (`AnnotationEditorViewModel.kt:~1221`) drops `plane` on any new line/ruler calibration and keeps the rest of the geometry; `setGeometry` (L~1204) keeps `plane` through height-offset edits.
- `PlaneCalibration` requires non-null `referenceName`, `widthMeters`, `heightMeters` (`model/GeometryCalibration.kt:30-37`) and `MeasurementAdvisor.kt:93-100` renders "Plane reference: <name>" and a centre-check percentage of the long edge when `checkResidualMm` is set.
- `CalibrationMethod` is `NONE, BLE_LASER, MANUAL_REFERENCE, ARCORE_DEPTH, LIDAR_DEPTH, EXIF_FOCAL, MONOCULAR_ML` (`model/ImageAnnotation.kt:25-40`). Both loaders map an unknown name to `NONE` (`db/sidecar/ImageSidecarManager.kt:175`, `repository/SqlDelightImageAnnotationRepository.kt:148`) and `usableScale` requires `method != NONE` (`AnnotationEditorViewModel.kt:~1217`), so **a new enum value would make a 0.113.3 build read the fit as uncalibrated.** `MANUAL_REFERENCE` is documented as "user drew a line over a known-length reference" and is already written by `MultiPointCalibration.kt:131`, `PlaneReference.kt:95` and `CalibrationService.kt:60`.
- `setGeometry` builds `cleared = merged.takeIf { heightOffsetMeters > 0.0 || cameraDistanceMeters != null || plane != null }` (`AnnotationEditorViewModel.kt:~1213`): once a SCALE fit has cleared the plane, clearing the height offset nulls the whole `GeometryCalibration`, constraints and fit included.
- `HeightOffset.focalPixels(focal35mmEq, widthPx, heightPx) = f35 / 43.2666 * hypot(w, h)` already exists (`calibration/HeightOffset.kt:36-38`, "assuming an uncropped frame"), so f in pixels needs only a 35 mm-equivalent focal length, never a sensor width. `ImageSensorData.focalLength35mmEq` is a DB column; `CaptureLensRecord` has no column (ADR-004), so the editor (which loads through `SqlDelightImageAnnotationRepository`) does not see it at fit time.
- `GeometryCalibration` is persisted both in the sidecar and in the DB column `calibration_geometry_json` (`GeometryCalibrationCodec`, `GeometryCalibration.kt:39-52`), decoded with `ignoreUnknownKeys = true`, degrading to null on failure. Constraints therefore need no new column, but they ride in that JSON column too and need the same compat treatment.

## Decision

1. **Provenance.** `CalibrationConstraint(id, p1, p2, distanceMeters, label, source, measurementUuid?)` (non-collinear known distances) is stored additively as `GeometryCalibration.constraints`, plus `GeometryCalibration.fit: ConstraintFitRecord?` = `{tier, n, residualMeanPct, looPct, worstId, focalSource, priorBasis}`. `priorBasis` snapshots the calibration the fit replaced (method, `pixelsPerMeter`, plane, lens `k`) so deleting the last constraint restores it exactly. No new table; no `MigrationRunner` change for calibration.
2. **Where the fit result lives, as a precedence table.** The constraint fit is *derived state*; `ConstraintFitApplier` (pure) is the only code that writes it, and the table is the contract (each row has a test):

   | Flow | Writes | Clears | Keeps |
   |------|--------|--------|-------|
   | Constraint fit, tier SCALE | `pixelsPerMeter`, `method = MANUAL_REFERENCE` (an existing value, so old builds still measure; the new provenance is `fit != null`, never a new enum value) | `plane` (else `pixelsPerMeter` would be silently ignored), prior fit record | height offset, lens |
   | Constraint fit, tier GRADIENT or PER_AXIS | `plane = PlaneCalibration(kind = CONSTRAINT_FIT, homography)` (undistorted native px to metres), `pixelsPerMeter` = scale at the image centre, `method = MANUAL_REFERENCE` | previous plane | height offset, lens |
   | Constraint fit, tier GRADIENT_AND_K | as above plus `lens.k` | previous plane, previous `k` (in `priorBasis`) | height offset |
   | New line / ruler / two-point reference (`keepingGeometry`) | `pixelsPerMeter`, method | `plane`, `constraints`, `fit` (stale provenance would no longer match the scale) | height offset |
   | Paper plane | `plane(kind = PAPER_REFERENCE)`, `pixelsPerMeter` | `constraints`, `fit` | height offset |
   | Height offset (`setGeometry`) | `heightOffsetMeters`, `cameraDistanceMeters` | nothing | plane, constraints, fit (the "nothing to keep" test is `merged != GeometryCalibration()`, so a new field can never be dropped by a hand-written predicate; this also fixes `setGeometry` nulling constraints and fit on the SCALE tier, adversarial C7). The `(D-h)/D` factor multiplies the metric result of whichever basis is active; Task 3.2a confirms by reading `HeightOffset.kt` how it composes with a plane and writes a test for the constraint-fit plane. |
   | Delete last constraint | restores `priorBasis` | `constraints`, `fit` | height offset |

   `method` is set to `MANUAL_REFERENCE` for every fit tier and `confidencePercent` comes from the same mapping `MultiPointCalibration` uses for ticks (Task 3.3c reads `MultiPointCalibration.kt:131` first; UNVERIFIED until then), so the existing badge keeps working; the pill text comes from `fit` (Story 3.6). Replacing a paper plane or a legacy scale by a constraint fit goes through the existing `CalibrationChangeWarningDialog` and one undo entry.
3. **`PlaneCalibration` gains `kind: PlaneKind = PAPER_REFERENCE`** (`PAPER_REFERENCE`, `CONSTRAINT_FIT`) rather than reusing `referenceName`. For `CONSTRAINT_FIT`: `referenceName = "Known distances"`, `widthMeters`/`heightMeters` = the metric bounding extent of the constraint endpoints (non-zero, so old builds never divide by zero), `checkResidualMm = null`. `MeasurementAdvisor` branches on `kind`: `CONSTRAINT_FIT` prints "Scale from N known distances (tier T), +/-R%" and skips the centre check.
4. **Solver.** Pure `ConstraintCalibrator` in `commonMain/.../calibration/`: normalised coordinates, `Double`, typed failures (`TooFewConstraints`, `Collinear`, `ZeroLengthSegment`, `NonPositiveDistance`, `ConflictingConstraints`, `IllConditioned`, `NoMeasurableTilt`, `DidNotConverge`, `LegacyBasis`), no number on degenerate input. Taps are undistorted with the calibration's current `k` before tiers SCALE, PER_AXIS and GRADIENT, so the fit is consistent with the `k` used at measure time. `HomographyFitter`'s private Gaussian `solve` is made `internal` and reused.
5. **Model ladder, focal-free first, with per-tier identifiability gates** (values live in `ConstraintTuning`, provisional until Story 3.8). Degrees of freedom were recomputed in iteration 2 (adversarial C8/C9).
   *Why the tilt path is focal-free.* For a plane tilted by tau, the image-to-plane map is `(d/f) * [[1,0,0],[0,1/cos(tau),0],[0,-tan(tau)/f,1]]` (derived for tilt about the image x axis; any azimuth is a rotation of the image frame). The projective row `g = tan(tau)/f` is a **scale gradient** (metres per pixel varies as `1 + g.p`) and needs no focal length; f only converts `g` into an angle and supplies the second-order anisotropy `1/cos(tau)` (0.38 percent at 5 degrees, 1.5 percent at 10 degrees). So the tilt tier is a three-parameter homography `w0 * [[1,0,0],[0,1,0],[gx,gy,1]]` in normalised pixels (principal point at the centre), stored as the existing `PlaneCalibration.homography` after conversion to undistorted native pixels; it works on every existing photo.
   - SCALE (P = 1, `w0`; any N >= 1; N = 1 is "approx", N = 2 reports the disagreement of the two, N >= 3 uses LOO).
   - GRADIENT (P = 3: `w0`, `gx`, `gy`, equivalently scale, tilt magnitude and azimuth; roll about the optical axis is a gauge and has no parameter). Needs `N - P >= 2`, so **N >= 5**. Identifiability gates: **position spread** (the normal matrix of the design `[1, mx, my]` over segment midpoints is well conditioned: midpoints must span at least 40 percent of the image diagonal along the fitted gradient direction, because the information is the scale difference between places) and a **significance gate** (Phase 4 patch, pre-mortem P1-5, adversarial C8i): the test is a Student-t test with `N - P` degrees of freedom, not a fixed `3 SE`. With N = 5 and P = 3 there are 2 degrees of freedom and `P(|T| > 3) = 2 * (1 - (0.5 + 3 / (2 * sqrt(11)))) = 0.0955` (closed form for 2 dof, computed this pass), so a fixed 3 SE passes about 1 in 10 pure-noise fits; the gate is `|g| > t_{0.995, N-P} * SE(g)` (2 dof: 9.925, computed in closed form this pass; 3 dof: 5.841; 4 dof: 4.604, standard table values, INFERRED until the test computes them), with the covariance scaled by the fitted residual variance, and a tap-noise prior may replace the fitted sigma only where it is larger. The **leave-one-out comparison can veto**: GRADIENT is rejected unless its LOO error beats SCALE's by the tuned margin, whatever the t-test says. `GradientNoiseFalsePositiveRateTest` (500 pure-noise scenes at N = 5, then N = 6) asserts at most 1 percent accepted. The report says "no measurable tilt" when ineligible. **Validity bound (adversarial C8ii):** the tier drops the anisotropy `1/cos(tau)` (0.4 percent at 5 degrees, 1.5 at 10, 10 at 25) and a measured gradient does not bound `tau` without `f` (the same 15 percent half-frame gradient is about 8 degrees on a wide lens and 27 degrees on a tele lens). The EXIF 35 mm-equivalent focal is used **only as an order-of-magnitude bound, never as a correction**: if `atan(|g| * f_px_exif)` exceeds 10 degrees, the result is "tilt too large for this model", SCALE is kept and no plane is written; with no EXIF focal the bound cannot be checked and the report says so. The SNR figures below assume a 0.3 percent per-segment tap error, which holds for a 200 px segment at 0.6 px taps; for a segment that is 5 percent of the frame at 1 px taps it is about 0.7 percent, which cuts the 5-degree SNR from 23 to about 10 and the 2-degree SNR below the gate (the tier then degrades to SCALE, correctly). **Crop and zoom (adversarial C9):** the map assumes the principal point at the image centre; a cropped or digitally zoomed photo adds an uncorrected term of order `|c| * |g|` (about 2.8 percent at `c` = 1000 px, 0.14 percent at 50 px). GRADIENT is therefore refused (`CroppedOrZoomedFrame`, SCALE kept) when the sidecar lens record has `zoomRatio != 1`, when the EXIF 35 mm-equivalent focal and the sensor aspect indicate a crop, or when the image aspect is not 4:3 or 3:2 within 2 percent (the code already assumes an "uncropped frame", `HeightOffset.kt:36`). **GRADIENT ships default-off (`ConstraintTuning.GRADIENT_DEFAULT_ON = false`, Settings `calibration_gradient_tier` for the owner to try it) until the Story 3.8a real-photo study shows it beats SCALE on withheld distances;** it is computed and logged for the study either way, the pill shows the tier and "estimated accuracy +/-R%" (the LOO figure), never a bare check. Direction spread is **not** required here (adversarial C9: first-order information is position spread; direction spread only constrains anisotropy). Recomputed magnitudes (INFERRED, assuming 0.3 percent per-segment tap noise, 4000x3000 photo, f = 3100 px): the gradient across the half-frame is `tan(5 deg) * 2000/3100 = 5.6 percent` (2 degrees: 2.3 percent); with N = 6 segments whose midpoint x has RMS 0.5 half-frame, `SE ~ 0.003 / (sqrt(6) * 0.5) = 0.25 percent`, so SNR is about 23 at 5 degrees and about 9 at 2 degrees. Story 3.1 verifies this with the golden scene; it is why the tier is identifiable on the owner's existing photos.
   - GRADIENT_AND_K (P = 4, adds division `k`): `N >= 6`; additionally needs **radial spread** (segment endpoints at least one beyond half the half-diagonal from the principal point) and a noise-floor gate (the predicted effect of the largest plausible `|k|` on the longest span must exceed twice the assumed tap error, else the tier is ineligible; at `k = -0.01` the effect is about 0.5 percent at mid radius, near the 1 px tap noise floor for short segments).
   - PER_AXIS (P = 2: `wx`, `wy`; **optional, off by default**): `N >= 4` and **direction spread** (angle spread of segments). With square pixels it has no physical source; its only value is as an anisotropy proxy, so it is reported separately in Story 3.8 and never auto-selected unless the study shows a gain.
   - **Optional focal refinement (upgrade, not a tier).** When a trusted `FocalSource` exists, GRADIENT applies the exact foreshortening `1/cos(tau)` with `tau = atan(|g| * f_px)` and `f_px = HeightOffset.focalPixels(f35, w, h)`; it adds no parameters and changes results by at most 0.4 percent at 5 degrees, so it **ships disabled** until Story 3.8 shows a gain. `FocalSource` is `{USER_CONFIRMED (35 mm-equivalent value in the existing height-offset focal field), PROFILE (a matched `CameraProfile` whose 35 mm-eq is present), SIDECAR_LENS_RECORD (Task 3.9c re-reads the sidecar lens record when E4 data exist), EXIF_ONLY}`; `EXIF_ONLY` never enables the refinement. A `PROFILE` match compares EXIF focal to the profile's EXIF focal, so it adds no protection against a wrong EXIF value and is labelled "EXIF-consistent", not "trusted"; only `USER_CONFIRMED` and a lens record at zoom 1 are trusted.
   A tier is accepted only when leave-one-out mean absolute error beats the simpler tier by a margin tuned in Story 3.8; otherwise the simpler tier is kept and the report says so.
6. **Report per fit**: model tier, N, per-constraint residual percent, LOO error, worst offender, and a "may be on different surfaces" flag when residual signs are bimodal (at least 2 each beyond 3 percent), which replaces the single-bad-tap wording. Log tier, N, residual when saved. Legacy basis 0 images are never rescaled (`Left(LegacyBasis)`); the UI shows the known-distances action disabled with the reason "calibrated with an older method" and links to the existing Calibrate flow.
7. **Sidecar and DB**: keep `schemaVersion` readable (the 0.113.3 reader uses `ignoreUnknownKeys = true`, `ImageSidecarManager.kt:35`, and never checks the version). The writer emits version 2 only when v2 data are present, through one `SidecarVersion.forContent` helper owned by Task 3.2c (E4's lens keys call it, they do not re-implement it); a v2-aware reader overlays the raw `JsonObject` so unknown top-level and per-annotation keys survive a save. `constraints` and `fit` also ride in `calibration_geometry_json`.
8. **Old-build behaviour (precise).** An older build reading a new sidecar or DB row decodes without error (unknown keys ignored), measures with the stored `pixelsPerMeter`/`plane` (the method is the existing `MANUAL_REFERENCE`, so `usableScale` accepts it and the old pill reads it as a manual reference), and shows the plane as "Known distances" (non-zero extents, no centre check). It loses editability: on its next re-save the `constraints`, `fit`, `kind` and measurement `valueSource` keys are dropped, and any calibration change there recomputes every measurement by the old rules (overrides are lost). "Remain correct" holds only until such a re-save. A test decodes a new fixture with a frozen copy of the 0.113.3 data classes (including `CalibrationMethod.valueOf` as the old loaders call it) and asserts the above, in particular that the SCALE-tier fit is not read as `NONE`.
9. Constraint normalisation: entered distances stored in metres, unit kept per constraint; a constraint implying a scale more than 2x from the median is flagged as a probable unit or typo error.

## Consequences

- The measurement-accuracy pipeline order is unchanged; the solver only produces inputs to it.
- Whether GRADIENT or GRADIENT_AND_K ever wins on the owner's photos is empirical; Story 3.8 decides thresholds and may leave K disabled by default. The ladder is the plan, not a promise.
- **Success Metric 3 is not met by synthetic tests alone.** SCALE-from-N is a noise-averaging gain over the existing tick/ruler/paper calibration, not by itself "multi-dimension calibration to correct distortion". Story 3.8 therefore requires (a) an out-of-model-class synthetic suite (heights above the plane, two-plane scenes, 1-2 px systematic tap bias) because synthetic truth drawn from the solver's own model class is circular, and (b) a real-photo hold-out on the owner's photos against both single-scale and the best existing calibration. The metric may be recorded as met only if (b) passes; otherwise the study records "not met for distortion; SCALE-with-LOO shipped" and the owner is told explicitly.
- Calibration history must hold the constraint list and fit record, not only the last snapshot (Story 3.7, via a named `CalibrationHistory` collaborator).

## Alternatives Considered

- **Full lens intrinsics (K, k1, k2, p1, p2) from taps**: under-determined with a handful of taps; rejected, OpenCV stays an offline oracle for test fixtures only.
- **New table for references**: adds migration risk for no query need. Rejected.
- **OpenCV or EJML at runtime**: not commonMain, APK growth. Rejected (`research/build-vs-buy.md`).
- **Per-device `LENS_DISTORTION` applied to JPEGs**: double-correction risk, measurement-accuracy ADR-004. Rejected.
- **Write the fit only into `pixelsPerMeter`**: silently ignored when a plane exists. Rejected by decision 2.
- **Reuse `referenceName` as the discriminator**: string-typed, advisor already renders it. Rejected for `kind`.
- **Pitch/roll/scale tilt parametrisation**: roll about the optical axis is unobservable (a gauge). Rejected for scale and gradient (equivalently tilt magnitude and azimuth).
- **Tilt tier that requires a trusted focal length in pixels (the first revision)**: unsatisfiable on existing photos (PROFILE adds no trust against a wrong EXIF focal, the lens record has no DB column, mm to px was undefined) and unnecessary because the first-order information is the focal-free scale gradient. Rejected; the focal path is an optional refinement.
- **Add `CalibrationMethod.KNOWN_DISTANCES`**: old builds map the unknown name to `NONE` and show the photo as uncalibrated (`ImageSidecarManager.kt:175`). Rejected in favour of `MANUAL_REFERENCE`.
