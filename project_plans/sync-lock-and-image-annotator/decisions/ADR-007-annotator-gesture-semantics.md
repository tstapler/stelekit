# ADR-007: Annotator gesture semantics for an armed tool

**Status**: Accepted pending owner review (Phase 4 patch, 2026-11-14; was Proposed, revised iteration 2)
**Date**: 2026-11-14
**Project**: sync-lock-and-image-annotator (Epic 2)

## Context

Today an armed placement tool uses a **loupe-aim** gesture: press shows a loupe, the finger moves to the crosshair, release places exactly one point "at any distance" (`ui/annotate/AnnotationGestureLayer.kt:186-209`, comment at L205). `AnnotationEditorViewModel.addPoint` appends to `inProgressPoints` and commits when the tool's point count is met (DISTANCE: 2), so "tap, tap" already creates a two-point measurement, each point loupe-aimed. A second pointer during placement drops the aim and hands over to `viewGesture` (L190-194). `AnnotationNonDragMode.kt` is the opt-in crosshair mode: `AnnotationPlacementSession` plus a nudge pad (`NudgeStep { ONE_PIXEL, TEN_PIXELS, ONE_PERCENT }`, `session.moving` for a move-existing-point mode); `AnnotationEditorViewModel.kt:453` resets the session when the tool becomes SELECT. ADR-005 (draft) said "one `Drag(start, end)` creates a two-point measurement", which would make a long drag unreachable as an aim and the first point the raw, finger-occluded press position; the adversarial review (B4) found no decision covering this.

The owner wants: tap a tool button, drag from A to B once, get the measurement, return to Select automatically. They also need precision (the loupe) and an accessible alternative to dragging (WCAG 2.5.7).

## Decision

1. **Two placement paths, chosen by what the armed tool and the pending state allow.**
   - **Aim-place (existing behaviour, unchanged)**: a press shows the loupe and follows the finger; release places **one point** at the release position. This is used for every tool that is not DISTANCE (AREA, ANGLE, LABEL, GRID_REF ticks, plane corners) and for DISTANCE **when a first point is already pending** (`inProgressPoints.size == 1`), at any travel distance. Tap, then tap again is therefore the loupe-precise path and is unchanged.
   - **Drag-measure (new)**: only for DISTANCE with **no pending point** and **only when the view scale is at or above Fit (`viewScale >= FIT_SCALE`, ADR-006)**. Below Fit one dp is 4 or more image pixels (at 0.25 a 10 dp contact error is about 40 image px per 4x scale step, against about 1 px for a loupe-aimed point), so the raw, finger-occluded point A is least trustworthy exactly where the owner works for edge reach (adversarial C10): below Fit a long drag is aim-place (one point at the release position, loupe-aimed) and the strip reads "Tap point A", not "drag from A to B". Tap-tap is the edge-reach path at low zoom. A press at A followed by travel greater than `DRAG_COMMIT_DP = 48` (3x the 16 dp tap slop) before release is a **drag**: the release commits a two-point measurement from the press position A to the release position B. Release within 48 dp of the press is the existing aim-place (the user fine-adjusting the first point with the loupe). The threshold is evaluated on the **release** position, so dragging out and back inside 48 dp before lifting reverts to aim-place and no measurement is made.
2. **Feedback during the drag.** While down, the loupe follows the finger as today. Once travel exceeds 48 dp a marker appears at A and a ghost line A to finger, which is the visible signal that release will create a measurement (not a single point). A is the raw press position, finger-occluded; this is an accepted tradeoff for one-drag speed at or above Fit. **Mitigation, verified in code:** the committed measurement is selected with draggable handles, and dragging a vertex shows the loupe (`AnnotationGestureLayer.kt:264-271`, `applyEdit` `AnnotationHit.Vertex` calls `onLoupe(handle.touch(...))`), so A can be refined immediately with loupe precision as one undo entry. After a drag-measure commit the strip reads "Drag an end to fine-tune" (first three times); the loupe-precise path (tap, tap) and the crosshair mode remain. This tradeoff is documented in the strip hint the first three times ("Drag A to B, or tap two points for precision").
3. **Pure classifier.** `classifyPlacement(pressPx, releasePx, thresholdPx, pendingPoints, tool, viewScale): PlacementGesture` is a pure function in `commonMain` (`PlacementGesture = AimPlace(point) | DragMeasure(start, end)`); the gesture layer only measures pixels and calls it. The layer stays policy-free about tools after commit; auto-return is ADR-005's `ToolPolicy`, called by the ViewModel.
4. **Cancel and abandon.** A second pointer at any time discards **only the in-flight gesture** (the press that is down: no point, no measurement), hands over to `viewGesture`, and **the tool stays armed** (as today); an already-placed pending first point is kept, so the user can pinch to zoom before placing B (Phase 4 patch, consistency BLOCKER: this is the single behaviour; ux.md and ADR-005 decision 7 previously also listed a two-finger gesture as a disarm path and are corrected). A pending first point is discarded by: tapping the active tool chip (disarms to Select), tapping Select, Back/Esc, or `discardFirstPoint()`. A drag cancelled by the system-gesture inset rule is tested with an injected non-zero inset **and** with a zero inset (desktop, three-button navigation), so the cancel path is exercised in both. A drag that ends off-canvas or outside the system-gesture inset rectangle (the canvas viewport is laid out inside `WindowInsets.systemGestures`, ADR-006 decision 6, so a drag can also **start** at the outermost image pixel at Fit without the system back gesture claiming it) cancels without creating anything, **keeps the tool armed and any placed first point** (triad repair 1, OC-9: one rule, only tapping the active chip, tapping Select and Back/Esc disarm; this replaces the earlier default that returned to Select, and the single constant `disarmOnOffCanvas` flips it if the owner prefers Select) and shows a one-line "Cancelled" strip. Identical points (distance below 2 image px) are rejected with the strip message "Choose a second point away from the first" and the first point is kept. Mouse (desktop) uses the same threshold; the middle button remains pan.
5. **Pointer-input restarts.** The `pointerInput(currentTool)` key restarts the pointer coroutine when the tool changes. Auto-return happens in the ViewModel after the commit; the gesture iteration has already ended (`awaitEachGesture` returned) because commit is triggered at release. The gesture layer is keyed on `Unit` and reads the tool through `rememberUpdatedState` so a tool change between iterations cannot drop an event; a test releases and immediately starts a new gesture.
6. **`AnnotationNonDragMode` changes (small, explicit).** (a) The crosshair session is already reset when the tool returns to SELECT (`AnnotationEditorViewModel.kt:453`); with auto-return that now also ends crosshair placement after each commit unless `stickiness == LOCKED`, and a test pins it. (b) Tapping an existing handle in Select opens the nudge pad in `moving` mode (the 2.5.7 alternative for moving a point); if that entry point is absent, Task 2.3d adds it. (c) The step set stays `ONE_PIXEL`, `TEN_PIXELS`, `ONE_PERCENT`; the UX document is aligned to it (it said 1 px / 5 px). (d) The nudge pad targets are already 48 dp (`PAD_CELL`). No new "inspector strip" is built.
7. **Hit targets** are screen dp and unchanged by zoom (`hitTestAnnotations` already maps through the view transform; ADR-006).

## Consequences

- ADR-005 no longer names `PlacementGesture` (its decision 6 only points here); the earlier draft's `Drag(start, end)` was replaced by `DragMeasure`, which this ADR owns. `InProgressAnnotationCanvasGestureTest` (pins aim behaviour) must keep passing and gains drag-measure cases.
- The Settings toggle `annotator_auto_return_to_select` does not affect gestures; drag-measure is always available for DISTANCE.
- Drag-measure is a Fit-or-closer gesture; the strip text, the first-three-times hint and the Story 2.3 tests are scale-dependent.
- Reaching the outermost pixel: A is clamped to `[0,1]` like every point (ADR-006); the loupe shows the clamped point.

## Alternatives Considered

- **Snap A through the loupe at every zoom (dwell before the drag)**: ambiguous with aim-place and adds a timer; rejected, the scale gate plus post-commit loupe refinement covers the precision gap.
- **Loupe on both ends of the drag (A aimed by holding still, then drag)**: adds a dwell timer and an ambiguous gesture; rejected for v1, revisit if A occlusion proves a problem on the owner's phone.
- **Loupe-aimed A then drag-to-B**: indistinguishable from today's aim-drag without a mode; rejected.
- **Threshold on peak travel instead of release distance**: makes a wobbly aim create a measurement; rejected.
- **Make drag the only path (remove tap-tap)**: breaks accessibility and the existing aim precision; rejected.
