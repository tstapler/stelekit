# ADR-001: One per-repo single-flight gate, plus owner-record lock recovery

**Status**: Accepted pending owner review (Phase 4 patch, 2026-11-14; was Proposed, revised after architecture and adversarial review, iteration 2)
**Date**: 2026-11-14
**Project**: sync-lock-and-image-annotator (Epic 1)

## Context

Every `GitSyncService.sync()` runs step 3b, `removeStaleLockFile`, which returns `Left(StaleLockFile)` when `.git/index.lock` is 60 s old or less and deletes it when older (`kmp/src/androidMain/kotlin/dev/stapler/stelekit/git/AndroidGitRepository.kt:676-686`, same logic in `kmp/src/jvmMain/kotlin/dev/stapler/stelekit/git/JvmGitRepository.kt:568-585`). `deleteLockFileIfStaleForRetry` deletes any lock older than the retry loop start (`kmp/src/jvmCommonMain/kotlin/dev/stapler/stelekit/git/GitOperationSupport.kt:287`). Nothing excludes two syncs (`research/architecture.md` A.1, `research/pitfalls.md` 1.1). A second press during a live run therefore fails with the logged "Stale git lock file", and a slow run (over 60 s) has its live lock deleted. JGit's `LockFile` writes no owner, so the file cannot say who holds it (`research/stack.md` 1.2). A killed process (the log shows `EXCESSIVE_RESOURCE_USAGE` kills) leaves a true orphan.

Manifest check (VERIFIED by grep for `android:process` in `androidApp/src/main/AndroidManifest.xml` and `kmp/src/androidMain/AndroidManifest.xml`, zero hits): no component declares a separate process, so the WorkManager worker, the foreground service and the UI share one process. An in-process mutex covers every live Android trigger. Two cross-process writers exist on the JVM: the previous process's corpse and `kmp/src/jvmMain/kotlin/dev/stapler/stelekit/cli/SyncMain.kt` (VERIFIED: builds its own `JvmGitRepository` at L59 and runs `stageSubdir/commit/fetch/merge/push` with no `GitSyncService`, no gate, no record).

Facts re-verified for this revision (all in `kmp/src/`):
- `enum class SyncTrigger { Manual, Automatic }` already exists (`commonMain/.../git/FirstSyncConfirmation.kt:42`) and gates first-sync-review skipping and `liftMassChangeGuard && trigger == Manual` (`GitSyncService.kt:286,297`).
- `GitSyncService.sync` writes `_syncState` (Offline L304, `CredentialVaultLocked` L311, config error L319, `DetachedHead` L331, `refuse` via `guards.repositoryState` L336) and calls `rateLimitRetry.cancel()` (L296; also L542 in `fetchOnly`) before step 3b, so the gate cannot be acquired "at step 3b".
- `AndroidGraphMoveQuiesceStrategy.quiesce` (`androidMain/.../db/GraphMoveQuiesceStrategy.android.kt:93-101`) takes `GitWorktreeLocks.lockFor(shadowKey)` and then `gitSyncBusyCounter.awaitIdle()`, while a running sync holds the busy counter and needs the same worktree lock inside fetch/merge (`GitShadowWorktree.kt:198`, `GitShadowFlushActor.kt:48`). Today this is a wait cycle bounded only by the quiesce timeout.
- `merge()` returns at `GitSyncService.kt:~394` and the `try { ... } finally { reloadMergedFiles(...) }` that PR #676 added starts at ~L413; `reloadMergedFiles` (L255-264) only protects `endGitMerge` with `NonCancellable`.
- `ScheduledSyncRunner.runFull` (`:107-118`) maps every `Left` other than `Offline`/`FirstSyncReviewPending` to `consecutiveFailures++`, a backoff and `TickOutcome.Failure`; `ColdSyncRunner.run` (`:51`) uses a waiting `withLock`; `RateLimitRetry.schedule` (`:19-22`) runs the retried `sync` after a delay while the failing run may still hold the lease.

## Decision

1. **Types.** `SyncTrigger` is untouched. A new `SyncOrigin { UiPress, FollowUp, Scheduled, Worker, Cold, Resume, RateLimitRetry, Resolve, Repair, Deepen, Setup, Clone, Cli, Quiesce }` is used for logging, `SyncRunInfo` and rerun bookkeeping only. `SyncOrigin.toTrigger()` is total over the origins that call `sync()`: `UiPress, FollowUp -> Manual`; `Scheduled, Worker, Resume, RateLimitRetry -> Automatic`; the others (including `Quiesce`) have no mapping (they call their own methods). A test pins the guard cases (`Worker/Scheduled/Resume/RateLimitRetry` never skip the first-sync review wrongly and never lift the mass-change guard).
2. **`RepoOpGate`** (successor of `NamedLocks`, `commonMain/.../git/`), one instance per process, a **required, non-defaulted** constructor parameter of `GitSyncService`, `ColdSyncRunner`, the scheduler factory, `AndroidGraphMoveQuiesceStrategy` and the clone worker (no `?: Gate()` fallback; `GraphContentGitSyncSetup.kt:464` and `StelekitAppDependencies.kt:215` currently do this for the busy counter and must not be copied). Recount (grep, iteration 2): `GitSyncService(` is constructed in 25 files, 1 production (`GraphContentGitSyncSetup.kt:448`) and 24 test files (15 businessTest, 5 jvmTest, 4 androidUnitTest, including the fixtures `GitSyncServiceTestFixtures.kt:52` and `GitSyncServiceJvmFixtures.kt:33`). Tests keep their assertions and add exactly one constructor argument `gate = RepoOpGate()` (shared explicitly where a test needs two components on one gate) by a single mechanical `sg` codemod in Task 1.3d; no default is added to the production constructor, and a source audit (`NoGateFallbackAuditTest`) fails if `RepoOpGate()` is constructed in `commonMain`/`androidMain`/`jvmMain`/`iosMain` outside the `WiringRoots` composition roots. "Unmodified" in the plan therefore means "assertions and fixtures unchanged apart from that one argument". It is threaded through `StelekitAppPlatformIntegrations`/`StelekitAppDependencies` and built once in `androidApp/src/main/kotlin/dev/stapler/stelekit/SteleKitApplication.kt` and `jvmMain/.../desktop/Main.kt`. **Key (Phase 4 patch, pre-mortem P1-1): `RepoOpGate.keyFor(gitDir: File)` = SHA-256 (first 16 hex) of `gitDir.canonicalFile.path`, where `gitDir` is the resolved `.git` directory** (`shadow.resolveForJGit(repoRoot)` on SAF graphs). `GitWriteLockNaming.lockNameFor` is a *remote-URL* normaliser (`GitWriteLockNaming.kt:32`: strips protocol, trailing `/`, `.git`, sanitises characters; no `canonicalFile`/`toRealPath` anywhere in it, grep this pass), so it cannot alias a symlink, `..` or a second graph registration of one repo, and it collapses `/a-b` and `/a/b`; `RepoOpGate` therefore no longer wraps it. A `.git` that is a file (linked worktree, submodule) is resolved through its `gitdir:` line when parseable, otherwise key resolution returns `Unreadable` (fail closed). Canonicalisation `IOException` is `Unreadable`, never a divergent fallback key. The clone path computes the same key from `<destination>/.git` (`canonicalFile` resolves a not-yet-existing leaf through its parents, so it equals the later config key). API: `tryAcquire(key, info): GateLease?`, `isHeld(key)`, `heldBy(key): SyncRunInfo?`, `awaitFree(key)`, `acquire(key, info): GateLease` (suspending, cancellable, quiesce only), and `releaseOrHandOff(lease): FollowUp?`, which is a plain **non-suspending** `fun` (an internal `synchronized`/atomic section, never a coroutine primitive) so it can run in a cancelled coroutine.
3. **Ownership rule (one rule).** The gate is acquired **only at the entry of a pipeline entry point**: the public mutating methods of `GitSyncService` (`sync`, `fetchOnly`, `commitLocalChanges`, `resolveConflicts`, `applyJournalMerge`, `abortActiveMerge`, `deepen`, `repairBranch`, `changeBackBranch`), the confirm-gated `forceRemoveLock` (Phase 4 patch, pre-mortem P1-3: gate, then the recovery lock and a re-decide, see decision 12), `ColdSyncRunner.run`, the clone entry points, `GitSetupScreenSaveLogic`'s fetch, the quiesce strategy, and `SyncMain`. Runners (`ScheduledSyncRunner`, `GitSyncTask`, `PeriodicSyncDriver`, `GitSyncCoordinator`) **never** acquire; they call the service, and read `isHeld` only as an advisory pre-check. The public method wraps a private `...Locked` body (the coroutine `Mutex` is not reentrant); `...Locked` bodies call only each other.
4. **Acquisition point and release.** The first statement of every entry point is `resolveGateKey(graphId)`, a read-only config read (no `_syncState` write, no `rateLimitRetry.cancel()`, no counter begin); the gate is acquired immediately after, before any state write. `resolveGateKey` catches `Throwable` (rethrowing `CancellationException`), retries the read once, and returns `Resolved(key = RepoOpGate.keyFor(resolvedGitDir))` (canonical path, decision 2) or `Unreadable` (config unreadable, `.git` unresolvable, or canonicalisation failed). `ResolveGateKeyFailureTest` pins that a config-read failure while another run holds the repo key never reaches the repository. **Unreadable fails closed: it never selects a different key for any git operation** (iteration 2, architecture R3: a `graph:<id>` key does not exclude a run holding `keyFor(repoRoot)`). On `Unreadable` the service (one instance per graph) returns coalesced if its own `inFlight != null`; otherwise it runs only the existing step-2 config-error path (reads config, writes the error state, calls no repository method) under a service-local `graph:<id>` lease whose sole purpose is to serialise that path with itself. The clone path derives its key with the same `RepoOpGate.keyFor(String)` normaliser as `repoRoot`. A coalesced call returns `Left(GitError.SyncInProgress(heldBy))` with no state change. **Release is unconditional (adversarial C2, the PR #662 never-stuck class).** Structure: `val lease = gate.tryAcquire(...) ?: return coalesced`, then
   ```
   try { beginOwnedOperation; counter.begin(); body }
   finally {
       try { withContext(NonCancellable) { counter.end(); endOwnedOperation() } }   // record end BEFORE release
       finally { gate.releaseOrHandOff(lease)?.let(::launchFollowUp) }              // non-suspending, always runs
   }
   ```
   Nothing that can throw sits between acquire and the `try`. `endOwnedOperation` deletes the record only if its `instanceId` and `startedAtMs` equal this run's (so a late end can never delete the next run's record), and ends before release so the next holder never sees our corpse. A record-write failure is logged and the run continues. `RepoOpGateReleaseStructureTest` pins this: `releaseOrHandOff` is not `suspend` (reflection), a fake whose `endOwnedOperation` throws `CancellationException`/`RuntimeException` still leaves the gate free, and a source audit asserts every `tryAcquire`/`acquire` result is released in a `finally` whose last statement is `releaseOrHandOff`.
5. **Coalesce, never cancel; one follow-up, atomically.** A second trigger returns without touching `SyncState`. A `UiPress` that loses the race sets one `rerun` bit **inside the gate's own lock**; `releaseOrHandOff` checks and clears the bit under the same lock and, if set, hands the lease to a follow-up run launched on the service's own supervised scope (exceptions handled, never `rememberCoroutineScope`), so a press can neither be lost nor produce two runs. The first caller's result is its own run's result; the follow-up publishes through `syncState`. `Scheduled`, `Worker`, `Cold`, `RateLimitRetry` that lose are dropped and logged (`SkipReason.Busy`). A press that loses to a lease whose origin is `Quiesce` (a graph move in progress) returns `SyncInProgress(heldBy = Quiesce)` and **never sets the rerun bit**: a follow-up fired at release would run against possibly relocated storage, so the UI shows "Moving your graph storage. Sync resumes afterwards." and the user (or the next scheduled tick, which re-resolves config) syncs once the move ends. A press with `liftMassChangeGuard = true` that loses is **refused** (`SyncInProgress`, copy "Wait for the running sync to finish, then confirm again") and never sets the bit; a follow-up never carries the flag, because the typed-count confirmation was against a tree that may since have changed (`GitChangeGuards.kt:148-150` skips the whole guard, not a count).
6. **`SyncInProgress` is a non-failure everywhere.** It is added to `GitError`; every consumer maps it: `DomainError.toUiMessage` and `toSyncErrorMessage` (exhaustive `when`s without `else`), `DomainErrorTest` lists, `ScheduledSyncRunner.runFull` and its `fetch` path (`TickOutcome.Skip(SkipReason.Busy)`, **no** `consecutiveFailures++`, no backoff), `GitSyncTask.liveTick`, `GitSyncCoordinator`, `SyncSafetyActions`, `BranchRepairService`, `TaskOutcomeMapping`. `GitCloneWorkerData.encodeFailure` has an `else` (safe). No new `SyncState` variant. `inFlight: StateFlow<SyncRunInfo?>` (`origin, startedAtMs, graphId, followUpQueued`) is written only by the gate holder.
7. **Lock order, one order: gate, then worktree; no re-entrant worktree lock.** Everything that takes `GitWorktreeLocks.lockFor(shadowKey)` and can also be a sync participant takes the gate first. `AndroidGraphMoveQuiesceStrategy.quiesce` is changed to: `gate.acquire(key, info(origin = Quiesce))` (waiting, bounded by the existing 30 s quiesce timeout), then `GitWorktreeLocks.lockFor(shadowKey).lock()`, then `awaitIdle` (immediate), then drain; both are stored together in one `QuiesceHold(lease, worktreeLock)` released by `release`. Acquisition is exception-safe: the worktree `lock()` is a suspension point, so it sits in `try { ... } catch (t: Throwable) { gate.releaseOrHandOff(lease); throw t }`, and any exception or timeout cancellation after the hold exists releases both before propagating (architecture R1; today's code has the same leak shape for the worktree lock alone). **Self-deadlock fix (architecture R1, VERIFIED):** `quiesce` holds the non-reentrant worktree mutex (`GraphMoveQuiesceStrategy.android.kt:96-97`) and `drainWriteBack` calls `target.flush()` (`:124`), which in production is `GitShadowFlushActor.flush`, which takes the same mutex (`GitShadowFlushActor.kt:47-48`), so a non-empty queue would block until the 30 s timeout. `GitShadowFlushActor` gains an `internal flushLocked()` (the body of `flush`, caller must hold the worktree lock; `flush() = lock.withLock { flushLocked() }`), `ShadowWorktreeQuiesceTarget` gains `flushWhileLocked`, and the drain uses it. The key comes from an injected `gateKeyFor: suspend (StorageMoveOperation) -> String?` constructor parameter (null: no git config for the graph, no gate), supplied by the composition root from `GitConfigRepository` and `RepoOpGate.keyFor`, so quiesce and sync use one key (architecture R5). `gitSyncBusyCounter` stays only as a secondary signal (balanced begin/end, never begun on a coalesced return); with the gate held `awaitIdle` is immediate. The background flush paths that take only the worktree lock (`GitShadowFlushActor.kt:48`, `PlatformFileSystem.kt:1005`) never take the gate, so no inversion exists; `GateBeforeWorktreeOrderTest` is a source audit that no `GitWorktreeLocks` scope calls into gate APIs and that no function holding the worktree lock calls `GitShadowFlushActor.flush` (use `flushLocked`). A regression test drives the real `GitShadowFlushActor` with a non-empty write-back queue through `quiesce` and must finish well inside the timeout. Never `await` `DatabaseWriteActor` idle or `awaitPendingMigration` while holding the gate if a path from them can request a sync; git paths never take `GraphWriteLock`.
8. **Cold path does not wait.** `ColdSyncRunner` uses `tryAcquire` and returns `ColdSyncOutcome.Skipped(Busy)` when held (the next periodic run retries). Only the quiesce strategy waits.
9. **Gate is released only when the blocking JGit call returns**, not on coroutine cancellation (`withContext(IO)` already does not return to a cancelled caller until the block returns). Cooperative cancellation is checked at step boundaries **except** inside the merge unit: `merge` + `beginGitMerge` + auto-resolve + the `finally { reloadMergedFiles }` block form one `NonCancellable` unit, with no cancellation check between `merge()` returning and the end of the reload (PR #676 invariant). **The unit is extracted, not wrapped (Phase 4 patch, pre-mortem P1-4, adversarial C5).** `GitSyncService.kt` has `return@withContext` at L429, L456 and L464 inside the merge region (VERIFIED by grep this pass, along with about 45 others in the file); a nested `withContext(NonCancellable) { ... }` would rebind those labels to the inner lambda and the pipeline would fall through to `push` with unresolved conflicts, and it compiles because the block type widens to `Any`. The unit therefore becomes `private suspend fun mergeUnit(...): MergeUnitOutcome` (sealed: `Continue(remoteCommitsMerged, autoMergedPaths)` / `Exit(result: Either.Left)`), whose body contains no `return@withContext`, and the pipeline translates it at exactly one call site (`when (val o = mergeUnit(...)) { is Exit -> return@withContext o.result; is Continue -> ... }`). Tests: after a conflict or commit failure in the unit `push` is never called (assert on the recording fake, in `GitSyncServiceConflictResolutionTest` and `GitSyncCancelBoundaryTest`), and `NonCancellableReturnAuditTest` (source audit) fails if `return@withContext` appears inside any `withContext(NonCancellable)` block of `GitSyncService.kt`. The edit to the pipeline body is therefore limited to the named seams: (a) step 3b replaced by the claim call, (b) the extracted `mergeUnit` call site, (c) `ensureActive()` calls before `commit`, before `fetch`, before `push`, **immediately before the unit (step 7, after `fetchResult` and before `_syncState = Merging` / `merge()`; adversarial C4)**, and after the unit completes, (d) `rateLimitRetry.cancel()` moved to after acquire. The pre-unit check is outside `NonCancellable` and strictly before `merge()` is called, so it can only stop a run that has not touched the working tree; a cancel arriving after that check lets the whole unit (merge, begin, auto-resolve, reload) finish, which is the #676 invariant. Everything else, including the reload-in-`finally` and the #662 never-stuck guards, is unchanged; `GitSyncConflictReloadE2ETest` and `DiskAppliedStateTest` must pass with only the Story 1.4 constructor argument added, plus new tests that cancel during `fetch` (no merge happens) and immediately after `merge()` returns (the DB reflects the merged files).
   **Bound and failure policy for the unit (adversarial C3).** No wall-clock timeout inside the unit (a timeout between merge and reload is the #676 bug). Instead: (i) `reloadMergedFiles` reloads in chunks of at most 200 paths, logs `reload progress done=<n>/<m>` per chunk and a `gate heldMs` warning above 30 s; (ii) every non-cancellation `Throwable` from `beginGitMerge`/`reloadFiles` (notably the closed-driver `IllegalStateException` when `GraphManager.switchGraph`/`shutdown` closes the DB mid-unit, `GraphManager.kt:1614`) is caught inside the unit, logged as `reload aborted reason=<class>`, and recorded as `reloadIncomplete = true`; the merged files are already on disk, so the next graph open reconciles them (Task 1.5b pins this with a real `GraphLoader`), and nothing escapes to the platform uncaught-exception handler; (iii) `GraphManager.shutdown()` stays synchronous and does not wait, and `GitSyncService.shutdown()` stops the periodic job and the follow-up scope but never cancels the unit; (iv) waiters are bounded elsewhere: quiesce by its existing 30 s timeout (a long reload surfaces as `QuiesceTimedOut` with the message "a sync is still finishing"), the Cancel button by the "Stopping..." state.
10. **Rate-limit retry is not dropped.** `RateLimitRetry`'s job calls `gate.awaitFree(key)` before invoking the retried operation (so a short `Retry-After` cannot fire while the failing run still holds the lease); if the retry then coalesces, another run owns the outcome and nothing is lost. `rateLimitRetry.cancel()` moves to after a successful acquire, so a coalescing press leaves a scheduled retry intact.
11. **Confirm before gate.** `abortActiveMerge(graphId, confirm)` awaits `confirm` **before** acquiring; after acquire it re-checks that the repository is still mid-merge. The gate is never held across a user dialog.
12. **`LockRecovery`: read, decide, act under an exclusive recovery lock, then write ours.** Pure `decide(existingRecord, lockFiles, liveness, self)` and the types live in `commonMain`; file access is behind a `LockFiles` port implemented once in `jvmCommonMain` (java.io/NIO, shared by JVM and Android); `JvmProcessLiveness` (uses `ProcessHandle`, Java 9) lives in `jvmMain`, `AndroidProcessLiveness` in `androidMain`. The service reaches it through new `GitRepository` methods with default implementations (strangler; iOS, wasm, `StubGitRepository` and test fakes keep compiling): `beginOwnedOperation(config, info): Either<GitError, LockVerdict>` (the only name; the earlier alias `recoverStaleLock` is dropped), `endOwnedOperation(config)`, and `forceRemoveLock(config)` (the confirm-gated manual path). `removeStaleLockFile` loses its age rule. The record carries `{instanceId, pid, processStartTicks, pidNs, host, bootId, op, origin, startedAtMs}` (`pidNs` = `readlink /proc/self/ns/pid`, e.g. `pid:[4026531836]`, VERIFIED readable on the dev machine this pass; null where unreadable). **Publication is atomic (Phase 4 patch, pre-mortem P1-2, adversarial C4i):** the content is written to a temp file in `.git/`, flushed, and published with `Files.createLink(record, temp)` (atomic and exclusive: fails if the record exists), then the temp is deleted; where hard links are unsupported the fallback is `CREATE_NEW` then write, and the reader's rule below covers the window. **An empty, partial or unparseable record is `OwnerUnknown(reason = TornRecord)`, never `Dead`, never `NoRecord`** (a reader between `CREATE_NEW` and the write must not delete a live owner's lock). While a run holds the lease the owner **heartbeats** by updating the record file's last-modified time every 5 s (a touch, no content change; `GitRepository.touchOwnedOperation`, started and stopped by the entry point that calls `beginOwnedOperation`); the record's mtime is therefore the owner's last proof of life, used by step 5.
    **Verdicts (iteration 2).** `host` is the hostname (JVM) or a constant (Android, app-private shadow directory); a different `host` on a shared folder stays `Unknown`. `bootId` is `/proc/sys/kernel/random/boot_id` where readable, else `Settings.Global.BOOT_COUNT` on Android (API 24+; minSdk is 26), else null. **Same host and both boot ids non-null and different is `Dead`** (adversarial C1: a record from another boot proves its writer is gone, and tick counts are only comparable within one boot; it also covers the pid-collision corner after a reboot). A null on either side falls through to the pid/start-tick probe. **Liveness probe rules (Phase 4 patch, pre-mortem P1-2, adversarial C3).** (a) On Linux and Android (JVM and ART alike) the start time is the raw `starttime` field 22 of `/proc/<pid>/stat` in clock ticks since boot (VERIFIED parseable on the dev machine: `awk '{print $22}' /proc/self/stat` printed 90761690), compared for equality; it involves no wall clock, so an NTP step or resume cannot make two JVMs disagree, which `ProcessHandle.info().startInstant()` can (it adds the process ticks to a boot time read from `/proc/stat` `btime` and so inherits any wall-clock step; INFERRED from the JDK implementation, not run). `startInstant()` is used only on macOS and Windows, and compared with a tolerance of 2 s. (b) **PID namespaces:** if the record's `pidNs` and ours differ, or either is null, a pid that is absent is `Unknown`, never `Dead` (a sandboxed desktop app and a host CLI see different pid spaces; `PidNamespaceAbsentPidTest`); `Dead` by pid requires the same non-null `pidNs`. (c) The liveness probe is run once to decide (step 2) and **again under the recovery lock** (step 4), so a probe that flips is caught. Evidence on Android: AOSP sepolicy made `/proc/sys/kernel/random/*` (label `proc_random`) readable to every domain after an `untrusted_app` denial on `boot_id` (Bug 69294418, [gerrit change](https://gerrit.omnirom.org/plugins/gitiles/android_system_sepolicy/+/9d9c370f31556c33f62e7889f64ad3a2728f1863%5E%21), 2017, so Android 9+); on Android 8.x the read may be denied, which is why the `BOOT_COUNT` fallback exists. INFERRED for the owner's device until Task 1.8c records it.
    **Order inside `beginOwnedOperation`, executed while holding the in-process gate** (cross-process exclusion is the record's `CREATE_NEW` plus the recovery lock below):
    1. read the existing `.git/stelekit-sync.owner`; 2. `decide` the verdict over the allow-list (`index.lock`, `shallow.lock`, `HEAD.lock`, `packed-refs.lock`, `config.lock`, `refs/**/*.lock`, never `objects/`); `ClearedOwn` means the record's `instanceId` equals this process **and this process has no active run registered for that canonical record path** (Phase 4 patch, pre-mortem P1-1, adversarial C1: an in-process `ActiveRunRegistry` keyed by the canonical record path is filled by `beginOwnedOperation` and emptied by `endOwnedOperation`; if an entry exists the claim returns `Left(SyncInProgress)` and nothing is deleted, so `ClearedOwn` is reachable only for a corpse, never for a live run that arrived through a different key spelling), `ClearedDeadOwner` means the writer is provably dead (pid absent, start ticks differ, or boot id differs);
    3. **only on a deleting verdict, take the recovery lock** (adversarial B1). The earlier "delete by path" step was not compare-and-delete: two JVM processes (desktop app and `SyncMain`) could both decide `ClearedDeadOwner` on the same dead record, P1 delete the locks and the record, create its own record and start JGit (creating a live `index.lock`), and P2, still at step 3, delete P1's live `index.lock` and P1's fresh record by path, after which P2's `CREATE_NEW` succeeds and both run. The fix is a kernel-held advisory lock, `FileChannel.tryLock()` (POSIX `fcntl`, Windows `LockFileEx`) on a permanent, never-deleted file `.git/stelekit-sync.recover`, taken with `tryLock` (non-blocking) through the `LockFiles` port. The kernel releases it when the holder dies, so unlike a `CREATE_NEW` claim token it needs no staleness rule and no delete (a token would reintroduce the same race one level down). `tryLock` returns null or throws `OverlappingFileLockException` (another recoverer, possibly in this JVM): return `Left(SyncInProgress(heldBy = null))` (an out-of-process recoverer has no `SyncOrigin`) and re-read on the next trigger. **The JVM lock table excludes only across processes' view of one channel, not as an in-process protocol (Phase 4 patch, adversarial C6): a plain in-process `tryLock` on a `ReentrantLock`/`Mutex` keyed by the canonical recovery-file path is taken first, so two recoverers inside one JVM never reach `FileChannel.tryLock`; `OverlappingFileLockException` stays as a backstop.** The recovery file is opened `CREATE` + `WRITE` (an exclusive `tryLock()` on a read-only channel throws `NonWritableChannelException`). Unsupported (`IOException`, for example some network or FUSE mounts): fail closed with `OwnerUnknown(reason = RecoveryLockUnsupported)`, nothing deleted. The channel is opened only inside this step and closed in a `finally` (so the POSIX close-releases-lock caveat cannot affect another channel on the same file);
    4. **re-read and re-decide under the recovery lock.** If the record is no longer byte-identical to the one decided on (instanceId, startedAtMs), release the lock and return the new verdict (usually `OwnerAlive`, because the winning claimer already wrote its own record). Only a re-confirmed dead record proceeds;
    5. **foreign-lock rule (Phase 4 patch, pre-mortem P1-3, adversarial C2; the iteration-2 lower bound alone was not enough).** Every allow-listed lock found must satisfy all three: (i) `lock.mtime >= record.startedAtMs - 2 s` (older than the dead owner's start cannot be its lock); (ii) `lock.mtime <= record.mtime + 10 s`, where the record's mtime is the owner's last heartbeat (see the record paragraph above): a lock created after the owner's last proof of life plus slack was created by someone else, for example a terminal or IDE `git` run today while a week-old dead record sits in `.git`; (iii) `lock.mtime <= now - 5 s`, because a live writer touches its lock while it works. If **any** lock fails any of the three, **nothing is deleted** (neither locks nor the record) and the verdict is `OwnerUnknown(reason = ForeignLockSuspected)`, which takes the paused-retry path and finally the confirm-gated manual removal. Only when all pass: delete the locks, then the dead record, in that order (locks first, record last, so any observer that sees no record also sees no dead lock). *Deviation from the pre-mortem's wording:* it proposed "a lock newer than the dead record's `startedAtMs` is foreign". That cannot be adopted, because the dead owner's own lock necessarily postdates its `startedAtMs` (the record is written at begin, JGit creates the lock later), so that rule would never clear a real corpse. The heartbeat gives the missing upper bound: death time is unknown, but last proof of life is not. Cost: one 5 s touch per owned run; if heartbeats are starved (the `EXCESSIVE_RESOURCE_USAGE` kills in the owner's log), the lock postdates the stale heartbeat and the claim fails closed to `OwnerUnknown`, which is the safe direction;
    6. write our record with an **exclusive, atomic publish** (temp file then `Files.createLink`, fallback `CREATE_NEW`; see the record paragraph), register the run in the `ActiveRunRegistry`, start the heartbeat, then release the recovery lock. If `CREATE_NEW` loses (another process with no record to recover created first), re-read and return `OwnerAlive`. After the create, re-read the file once and treat a record that is not ours as `OwnerAlive`.
    The no-record case needs no recovery lock (nothing is deleted): `CREATE_NEW` alone arbitrates, and `NoRecord` with a lock present deletes nothing. `OwnerAlive` returns `Left(SyncInProgress)`; `OwnerUnknown` and `NoRecord` return `Left(StaleLockFile(verdict))` with nothing deleted (fail closed). On Android SAF graphs the record, the recovery file and the locks live under `shadow.resolveForJGit(repoRoot)`, not `repoRoot`. After any deletion `status` plus `repositoryHealth` run before committing; a corrupt index routes to the existing repair error, never an auto reset.
    *Proof sketch.* Deleting a record or a lock requires holding the recovery lock (step 3), at most one process holds it, and every deleter re-validates the exact record it decided on under that lock (step 4). A record created after a deleter's decision is therefore never deleted by that deleter: the deleter either sees it at step 4 (and backs off) or created it itself. In-process, the gate already serialises. Creation races are arbitrated by `CREATE_NEW`. Interleavings re-walked: (a) two or three claimers over one pre-existing dead record: exactly one wins `tryLock`; the others return `SyncInProgress` or, if they acquire the lock after the winner finished, re-decide at step 4 and get `OwnerAlive`; (b) WorkManager worker vs UI in one process: the gate excludes them before step 1; (c) pid reuse: start ticks differ, so `Dead`, then the same protocol; (d) force-stop leftovers: new `InstanceId` and, after a reboot, a different `bootId`, so `ClearedDeadOwner`; (e) a corpse whose `recover` file lock was held at death: released by the kernel, so the next claimer proceeds; (f) a non-participating git (terminal, IDE) taking `index.lock` before step 5: its lock is created after the dead owner's last heartbeat (or within 5 s of the verdict), so rule (ii) or (iii) of step 5 fails, nothing is deleted and the verdict is `OwnerUnknown(ForeignLockSuspected)`; one taking it between steps 5 and 6: JGit reports a lock failure on its own create and nothing of theirs was deleted. (The iteration-2 text of this sketch said "nothing of theirs was deleted unless its mtime preceded the dead owner's start", which is backwards: step 5's old rule deleted exactly the locks that did **not** precede the dead owner's start. Corrected here.) (g) `forceRemoveLock`: same protocol, see decision 12a.
    **12a. `forceRemoveLock` (the user-confirmed path) is a gated entry point, not a bypass (Phase 4 patch, pre-mortem P1-3, adversarial C4ii).** Order: gate (`tryAcquire`, else `SyncInProgress`), `tryLockRecovery` (contended or unsupported: refuse), re-read the record and re-decide; **refuse on `OwnerAlive`** (and on a live record of this process in the `ActiveRunRegistry`); otherwise delete only the allow-listed locks, and the record if it is dead or absent. The user's confirm therefore cannot delete the live lock of a CLI or desktop run that started while the dialog was open. `ForceRemoveRacesLiveRunTest` pins it. A `.git` that is a file (linked worktree) resolves through its `gitdir:` line or is `OwnerUnknown` and out of scope for recovery.
13. **`SyncMain` participates.** `SyncMain` builds its own process-local `RepoOpGate` and claims through the same `beginOwnedOperation`/`endOwnedOperation` (its own `InstanceId`, origin `Cli`); on `OwnerAlive` it exits with a new "another sync is running" code, and the desktop app seeing the CLI's live record gets `OwnerAlive` and coalesces. This makes the record protocol the cross-process arbiter and the gate the in-process one.
14. **Amber is not a dead end.** `OwnerUnknown`/`NoRecord` publish `SyncState.Error(StaleLockFile(verdict))` which the presentation model renders as Paused (amber). The service schedules two automatic retries (first after 30 s, second after 2 min; values in a `PausedRetryPolicy` constant) published as `pausedRetry: StateFlow<PausedRetryInfo?>`; after the second failure the model renders Failed (red) with "Sync now" and Details (one start label; "Try again" is not used for sync). The retry never runs while the gate is held (it uses `awaitFree`). **Triad repair 1:** the paused sheet offers an enabled `Retry now`, which cancels the pending timer and runs one attempt through the normal gate; it is an extra attempt that does **not** consume the automatic budget (triad repair 2: the try counter does not move and a failed manual attempt re-arms the pending automatic try, so only the two timed failures reach Failed), never adds automatic retries, and coalesces like a second press. "Sync now" from Failed is a fresh user-initiated run and restarts the two-try budget if it again meets an unknown owner. The timer is an in-process coroutine (same mechanism as `RateLimitRetry.kt:22`) and is not persisted: after process death the paused state is simply gone and the next launch or WorkManager periodic tick (`WorkManagerTaskScheduler.kt:158,185`) re-runs the claim; an overdue retry runs once on first observation. The sheet copy is cause-neutral because `OwnerUnknown` means the owner could not be determined, not that another operation is running.
15. **UX**: our own live run is never an error ("Syncing..."); unsure is amber "Sync paused - retrying automatically"; manual removal only behind a confirm in the details sheet.

## Consequences

- Finding 1 (second press fails with stale-lock) and F1 (live lock deleted) are structurally impossible in-process; cancel then immediate re-press closes via decision 9; the cross-process CLI case closes via decisions 12-13.
- The first stale lock left by a pre-upgrade kill has no owner record and needs the manual confirm once. Accepted.
- `GitSyncService.sync()` body is not refactored (Isolate via seam). It is edited only at the four named seams in decision 9; "byte-identical" is retracted. #676 and #662 guards stay (tests above).
- Adds a small file write per run inside `.git/` (app-private shadow on Android, not SAF).
- A new mutating entry point that skips the gate is caught by the Story 1.8 guard tests.
- Quiesce can now wait for a long foreground sync (bounded by its existing timeout); this is acceptable because it is user-initiated and rare, and it removes the wait cycle. The real-flush self-deadlock in the old quiesce (worktree lock then `flush`) is fixed by `flushLocked`.
- A reboot between runs is `Dead`, not `Unknown`; the manual confirm remains only for a lock with no record, a different host, an unreadable liveness probe, or a filesystem that cannot lock.
- One new permanent file `.git/stelekit-sync.recover` (empty, never deleted) next to the record.
- Phase 4 patch costs: a 5 s heartbeat touch per owned run, a `pidNs` field, an in-process `ActiveRunRegistry`, an extracted `mergeUnit()` and a canonical-path gate key (a `.git` that is a file is `Unreadable`/`OwnerUnknown`, out of scope). Stale locks that postdate the owner's last heartbeat now take the amber path instead of auto-clearing; that is deliberate (fail closed).
- Until owner checklist 1.8c is ticked the Android `/proc` behaviour is unverified; the verdict table already treats every unreadable probe as `Unknown`, so the CI-green E1 merge cannot delete on a guess.

## Alternatives Considered

- **Serialize inside `GitSyncService` only**: misses the cold worker, the quiesce path and the CLI. Rejected.
- **Decorator on `GitRepository` (per-call lock)**: wrong grain; two pipelines interleave between calls. Rejected; the runtime assertion fake in Story 1.8 reuses the idea as a test.
- **Lock-file protocol as the in-process mutex**: polling cost, pid reuse. Kept only as the cross-process arbiter and recovery layer.
- **Extend `SyncTrigger` with five values**: silently changes `== Automatic` checks in 12 call sites. Rejected; `SyncOrigin` is separate.
- **`runInterruptible` to cancel JGit**: can close the index channel mid-write (`research/pitfalls.md` 1.3). Rejected.
- **Add `SyncState.Coalesced` or `Joined`**: breaks exhaustive consumers for non-pipeline information. Rejected.
- **Runners pre-acquire with `tryAcquire` then call `sync`**: self-coalesces. Rejected by decision 3.
- **Carry `liftMassChangeGuard` through a coalesce**: reuses a stale typed-count confirmation. Rejected by decision 5.
- **Delete by age (status quo)**: root cause. Rejected.
- **A `CREATE_NEW` recovery-claim token (`.git/stelekit-sync.claim`)**: needs its own dead-holder rule, and deleting a dead token by path has the same compare-and-delete race one level down. Rejected for the kernel-held lock.
- **Rename the record to a tombstone and verify, restoring on mismatch**: restoring is not atomic (a third claimer can `CREATE_NEW` in the gap). Rejected.
- **Content/mtime-checked delete without a lock**: the check and the delete are separate syscalls (TOCTOU). Rejected; the mtime filter is kept only as a secondary scope limit (step 5).
- **"A lock newer than the dead record's `startedAtMs` is foreign" (pre-mortem wording)**: the dead owner's own lock always postdates its `startedAtMs`, so this would never clear a real corpse. Replaced by the heartbeat upper bound (decision 12 step 5).
- **Wrap the merge unit in `withContext(NonCancellable)`**: rebinds `return@withContext`. Rejected for the extracted `mergeUnit()` (decision 9).
- **Key the gate by the remote-URL normaliser**: cannot alias symlinks or `..`. Rejected for the canonical `.git` path (decision 2).
- **Use an OS lock for the whole run instead of a record**: loses the diagnostic record and the Android `InstanceId`/boot semantics, and does not survive filesystems without locking. Rejected; the lock is used only for the short recovery step.
