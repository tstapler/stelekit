## 1. Sync lock handling

### 1.1 Evidence trail: how "sync/fetch start" can become "Stale git lock" 0.36 s later

Code facts (VERIFIED, files read):

- `GitSyncService.sync()` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/git/GitSyncService.kt:278`) has **no mutual exclusion**. No `Mutex`, `tryLock` or in-flight flag exists in the file (grep for `Mutex|withLock` returned nothing). `gitSyncBusyCounter` (`GitSyncBusyCounter.kt`) is a counter used for relocate quiesce and scheduler "busy" checks. It does not exclude a second caller.
- Step 3b of `sync()` (`GitSyncService.kt:338-342`) calls `gitRepository.removeStaleLockFile(config)`. On `Left` it publishes `SyncState.Error` and returns.
- `AndroidGitRepository.deleteStaleLockFile` (`androidMain/.../git/AndroidGitRepository.kt:676-685`) uses only age. If `index.lock` exists and is **<= 60 s old** it returns `Left(StaleLockFile)`. If it is **> 60 s old** it deletes the lock with no liveness check. JVM has the same logic (`JvmGitRepository.kt:568`). The error string "Stale git lock file — tap to retry" is `DomainError.kt:450`.
- The first-party code never maps a JGit `LockFailedException` to `StaleLockFile` (grep: `StaleLockFile(` is only constructed in `deleteStaleLockFile` and `removeStaleLockFile`'s error mapper). So the 0.36 s error can only come from step 3b, not from `add`/`commit`.
- Entry points that reach `sync()` or git:
  - `GitSyncCoordinator.triggerSync()` (`ui/GitSyncCoordinator.kt:138`), a UI press with no guard.
  - `SyncSafetyActions.kt:101`, which calls `sync(liftMassChangeGuard = true)`.
  - `PeriodicSyncDriver.runTick` (`PeriodicSyncDriver.kt:172`), which has `isBusy()` plus a `tickLock` Mutex. That Mutex is **per driver instance**, so it covers only periodic ticks of one service.
  - `ScheduledSyncRunner.run`, which reads `busyCounter.isBusy` and then calls `fullSync`. This is a check-then-act race (TOCTOU) against `begin()` inside `sync()`.
  - `GitSyncWorker` → `GitSyncTask` → `GitSyncServiceRegistry.getService(graphId)?.scheduled?.run`. With a live service this is the same path as a tick.
  - `triggerFetchOnly()` (`GitSyncCoordinator.kt:151`) → `fetchOnly`.
- The cold path (no live service) uses `ColdSyncRunner` with `NamedLocks` (`ColdSyncRunner.kt:24`, process-wide `ColdSyncLocks` at `WorkManagerSyncScheduler.kt:325`). **Only the cold fetch takes that lock.** The live `GitSyncService` never takes it, so a worker that starts the cold path while the app is mid-launch and a live service becoming registered is not excluded from `sync()`. INFERRED.
- Cancellation: the UI registers `onCancel = { run.cancel() }` with `jobTracker` (`GitSyncCoordinator.kt:141`). `sync` runs inside `withContext(PlatformDispatcher.IO)`. On `CancellationException`, `SyncRunGuard.cancelled()` only resets state to Idle (`SyncRunGuard.kt:21`).

### 1.2 What must be designed against

1. **Single flight at the service, not the caller.** One per-repo (keyed by canonical repo path, not graphId and not instance) lock/flag that every entry point takes, including the cold `ColdSyncRunner` (currently has its own private `NamedLocks`). `NamedLocks` today is process-wide per name, which is the right keying. The live service must use the same registry.
2. **Non-reentrant `Mutex` pitfall.** `kotlinx.coroutines.sync.Mutex` is not reentrant. If `sync()` takes the lock and calls an inner method (`fetchOnly`, `commitLocalChanges`, `resolveConflicts`) that also takes it, it deadlocks. Split public (locking) and private (`...Locked`) functions, or pass a token. Do not wrap `ScheduledSyncRunner.fullSync` (calls `sync`) in the same lock unless `sync` is the inner unlocked variant.
3. **Per-instance vs per-repo.** `tickLock` in `PeriodicSyncDriver` is per instance, so it is not a repo-level guard (H5).
4. **Coalesce, don't cancel.** Use `tryLock` and a "joined running sync" result. Pitfall: coalescing can hide a failure from the second caller. The joiner must observe the same final outcome (await the in-flight `Deferred`, or read the terminal `SyncState`), not return `Success`/`Skipped` immediately. A UI press that returns instantly with "already running" is fine; a worker/tick that records `Skipped` and then never retries after the first run failed hides a real failure. Log each decision (`started | coalesced | skipped`) with source, per the Observability requirement.
5. **Fail closed on lock ownership.** Never delete by age alone. Options (decide in planning): (a) write an app-owned sidecar marker (pid, instance id, start time, heartbeat) next to the repo, and treat a lock as stale only if no live holder is recorded in this process and the marker's process is gone (on Android the marker's pid can be reused; use the process start time or an app-launch nonce, not a bare pid); (b) delete only a lock that predates this process's start AND whose holder token is not in the in-process registry. If neither can be established, report "another sync is running / lock present" and delete nothing.
6. **Own-lock clean-up on cancel/failure.** JGit releases `index.lock` in its own `finally` (via `DirCacheCommand`/`LockFile.unlock`, INFERRED from library design, UNVERIFIED for this version). The app should not delete the lock on cancel; it should join the coroutine's blocking call (see 1.3) and let JGit unlock.
7. **TOCTOU.** `ScheduledSyncRunner` reads `busyCounter` and then calls `sync`. Replace with the atomic `tryLock`.
8. **Check order.** Today lock removal (step 3b) precedes `graphWriter.flush()` and `editLock.awaitIdle()`. Acquire the single-flight lock before 3b, so the first sync's lock cannot be seen by the second as "stale".

### 1.3 Cancellation vs blocking JGit

- `withContext(PlatformDispatcher.IO)` plus blocking `git.add().call()` etc. Coroutine cancellation is cooperative: it does not interrupt a blocking call. The coroutine is marked cancelled, but the JGit call runs on to completion on its thread, and `.use { }` closes the repo only after it returns. Meanwhile `runGuard.cancelled()` has already set `Idle`, so the UI shows idle while git still holds `index.lock`. A new press then sees a live lock (H1). This is exactly the "cancel leaves a lock" symptom, without anything being left behind.
- Pitfall: the opposite fix, `runInterruptible`, interrupts the thread. JGit's `LockFile`/`FileChannel` operations are interruptible channels. An interrupt mid-write can close the channel (`ClosedByInterruptException`) and abort a half-written index while the lock is being committed. Treat commit/merge/checkout/push phases as **non-cancellable** (`withContext(NonCancellable)`), and make only the pre-flight and network phases cancellable. JGit transport has `setTimeout`, which is the right bound for network calls (it is already set via `GIT_TRANSPORT_TIMEOUT_SECONDS`).
- Keep `SyncRunGuard.cancelled()` from reporting `Idle` while a non-cancellable phase is still running.

### 1.4 Android process lifecycle

- `EXCESSIVE_RESOURCE_USAGE` kills a **cached** process (VERIFIED, log lines 1, 5, 11, 13, 17, 19). Nothing runs `finally` on SIGKILL, so any lock held at that moment is orphaned (H2). Design for it, don't try to prevent it: the next launch must recognize "lock older than this process's start and no registered holder" safely.
- Reducing the CPU that triggers the kills (e.g. `loadDirectory 23.7 s` at 09:17:34) lowers exposure but is a separate concern.
- WorkManager can run `GitSyncWorker` while the app is foregrounded or starting. The worker takes the live path if `GitSyncServiceRegistry` already has the service and the cold path otherwise (`WorkManagerSyncScheduler.kt:228-233`). The live-service check and the cold fetch are not under the same lock (see above). A worker started by process launch at 09:16:42 overlaps the app's own startup in the log.
- A WorkManager worker has a ~10 min execution limit and is stopped (`CancellationException`) on constraint loss. This relies on cancellation behavior from 1.3. Cite: Android WorkManager docs (not fetched this pass, UNVERIFIED here).
- Doze defers work but does not kill a running process. OEM killers act on cached/background processes. Foreground-service use (git-sync-resilience prior art) reduces both. `project_plans/git-integration/research/pitfalls.md:13` (Doze) and `:358` (stale lock, "older than 1 minute... remove them") are the prior art. **The 60 s age rule in that document is the source of the current heuristic and conflicts with the requirements; the plan should supersede it explicitly.**

### 1.5 Test matrix to require (feeds the plan)

Overlap (two `sync()` concurrently, with a fake `GitRepository` that holds a real file lock for N ms); UI press during a tick; tick during a worker; worker cold path vs live service; cancel at each phase (pre-lock, mid-add, mid-commit, mid-push); simulated kill (leave a lock file, create a new service, assert no deletion if age < threshold and holder unknown, and assert eventual safe clear when provably orphaned); lock older than 60 s with a live in-process holder (must not delete); coalesced caller observes the failure of the shared run.

Sources: JGit stale-lock reports confirm that a killed process leaves `index.lock` and JGit throws `LockFailedException` (Eclipse forum / Jenkins JENKINS-65277, web search 2026-11-14; no source found on coroutine-cancellation vs JGit specifically, so 1.3 is INFERRED from Kotlin coroutine semantics and should be verified with a test).

## 2. Compose gesture pitfalls (INFERRED unless noted; the annotator files were not opened this pass)

- **Pointer-input conflict, drag-to-measure vs pan/zoom.** Two `pointerInput` blocks (or `detectTransformGestures` and a drag detector) on the same node both see events unless one consumes them. Auto-return to Select changes which handler is active between the first and second pointer-down. Design a single gesture owner keyed on tool state, and decide the mode at pointer-down (not mid-gesture). A tool change mid-drag must not re-route the in-flight gesture. Multi-touch: a second finger during a measurement drag should cancel the measurement (or promote to pinch), never leave a dangling half-created point.
- **Restart keys.** `pointerInput(toolState)` restarts the block when the key changes, cancelling an in-flight gesture. Use `rememberUpdatedState` and key on `Unit` for the handler.
- **One-shot tool state and process/config change.** "Tool armed for one drag" held in `remember` is lost on rotation/process death. Hold the tool and the lock flag in the ViewModel / `rememberSaveable` and decide the restore policy (arguably restore to Select, since a half-armed tool surprising the user after a restart is worse than losing it). Reset to Select on every "completion or cancel" path: finished drag, zero-length drag below slop, pointer cancel, navigating away, undo.
- **Undo after auto-return.** One undo step per measurement creation. After auto-return the undo stack should still hold the create entry and redo must not re-arm the tool. Undo of "edit value" is its own entry. Verify the interaction with `annotate-ui-test-coverage` tests (`project_plans/annotate-ui-test-coverage/`) which likely encode today's modes.
- **Edge hit targets with a larger canvas.** A canvas larger than the image means points may legally sit outside the image. Decide the clamp policy (clamp to image bounds, or allow outside and store normalized coordinates outside 0..1). The sidecar stores normalized points (`annotation-lens-distortion/design.md`: "Stored geometry stays normalized pixel points"), so out-of-range values must round-trip and must not break `LensCalibration` undistortion (radius > 1 half-diagonal). Touch slop and handle radius should be in dp, not image pixels, so hit targets don't shrink as zoom changes. System gesture insets near screen edges steal drags at the viewport edge (Android back gesture); add safe margin.
- **Zoom range.** Allowing zoom-out far past fit needs a min scale clamp (so the image can't vanish) and pan bounds. A 12 MP bitmap drawn at small scale must use a downsampled/mipmapped draw or recomposition cost rises (the SLO is 60 fps). UNVERIFIED baseline.
- **Exported image coordinate space.** Export/overlay code that assumes viewport == image will be wrong once the canvas is bigger. Keep one transform (image px ↔ canvas px) and test export on a measurement outside the image bounds. Don't change what existing export tests treat as the origin.
- **Toast overlap** (`Depth model ready` over the image): lay the transient banner out in a layout slot (or `Scaffold` snackbar host), not as an overlay on the image canvas, otherwise it also intercepts pointer events at the top edge.

## 3. Calibration pitfalls

Prior art (VERIFIED, `project_plans/annotation-lens-distortion/design.md:9-26`; `project_plans/measurement-accuracy-and-camera-profiles/requirements.md:20`): on an 18 cm object, 1% barrel distortion contributes 0.05 cm, 2% contributes 0.10 cm. Plane tilt of 5 degrees contributes about 0.66 cm and 1 cm of depth mismatch about 0.30 cm. A 60 px reference line with ±1 px endpoint error contributes 0.60 cm. Ranking, largest to smallest: tilt, short reference, depth, endpoint, lens. The existing model already has a one-parameter division model `k`, a minimum evidence rule (3+ ticks, at least 1 px residual, 60% reduction), and additive sidecar key `calibrationLens`.

Pitfalls to design against:

1. **Ill-conditioned fits.** Collinear or all-short reference distances fit scale along one axis only. Fitting per-axis scale or a homography from fewer than 4 well-spread coplanar points is under-determined. Require a spread/conditioning check (e.g. angle diversity of the reference segments, condition number of the normal matrix) before accepting a multi-parameter model, and show the residual to the user. Fall back to the simpler model rather than extrapolate.
2. **Over-fitting 3-4 distances.** Each added parameter (per-axis scale, k, tilt) can absorb tap noise. With N distances and P parameters keep N - P >= 2 degrees of freedom, and use leave-one-out error, not training residual, to decide acceptance. The existing "does the fit remove 60% of residual" rule is a good pattern to extend. Without a held-out distance the "mean absolute error improves" metric (requirement 3) will be self-fulfilling.
3. **Confounds.** Lens distortion, perspective (tilt), and depth (off-plane objects) produce similar residual patterns along a line. A fit that attributes tilt or depth to `k` is wrong in a different region of the photo. The prior art ranks lens as the smallest term, so a multi-dimension calibration should model **tilt (homography) before** more lens parameters, or at minimum report which term explains the residual. A wide-angle phone shot (the owner's door-frame photo) may show larger k than the 1-2% simulated; measure it before assuming.
4. **Mixed units.** Known distances may be entered in mixed units (in/cm). Normalize to one internal unit at entry; store the unit with each reference; guard against typos that differ by a factor of 2.54 or 10 (flag a reference whose implied scale deviates strongly from the others).
5. **Silent change to saved measurements.** Existing annotations store normalized points plus a calibration. Re-fitting must not silently change displayed values on already-saved measurements. Keep the old calibration in the sidecar/DB and change a measurement's displayed value only when the user re-saves a calibration, with a visible "recalculated" indication; preserve a user-edited override value as an override (so the displayed value does not drift back to the computed one).
6. **Edited values vs computed values.** If the owner edits a measurement's value directly, store it as an override with its provenance, so a later recalibration does not overwrite it unnoticed.
7. **Sidecar schema skew.** `ImageSidecarSchema` has `schemaVersion = 1`, `calibrationBasisVersion`, `calibrationLens` (VERIFIED, `db/sidecar/ImageSidecarSchema.kt:20,41,43`). Rules: additive keys only; unknown keys ignored by the reader (confirm `ignoreUnknownKeys` in the JSON config, UNVERIFIED); a new reader must accept a v1 sidecar with the new key absent; an old reader (older app version, or a second device) reading a newer sidecar must not drop the new key on re-save (round-trip preservation, otherwise git sync of a sidecar from the phone to an older desktop erases the calibration). Add a version field for the new model and a test that loads a fixture sidecar from v0.113.3.
8. **DB column.** `calibration_lens_json` already exists. A new column triggers the `MigrationRunner.all` rule and SQLDelight regeneration from CLAUDE.md.
9. **Camera lens metadata feeds calibration.** Different lenses have different `k`. A calibration made with the ultra-wide lens must not be reused for a main-lens photo (see 4.6).

## 4. CameraX pitfalls

Current code (VERIFIED): `CameraViewfinderDialog.android.kt:105-108` calls `unbindAll()` then `bindToLifecycle(..., CameraSelector.DEFAULT_BACK_CAMERA, ...)`. `AndroidCameraPreviewBinder.kt:54` also binds `DEFAULT_BACK_CAMERA` on `ProcessLifecycleOwner` and explicitly avoids `unbindAll()` so it composes with the concurrently-bound viewfinder. Switching lens by rebinding the dialog's use cases with `unbindAll()` would tear down the other binder's preview. Scope the unbind to the dialog's own use cases.

1. **Physical-camera selection differs by OEM.** Per CameraX developer threads (accessed 2026-11-14), `CameraSelector.Builder.setPhysicalCameraId()` exists since CameraX 1.4.0 and the same physical ID has to be applied to every bound use case (otherwise it silently has no effect): https://groups.google.com/a/android.com/g/camerax-developers/c/BsXJGFjGFQg and https://groups.google.com/a/android.com/g/camerax-developers/c/ZLumxx1sW3o. Verify the CameraX version in `kmp/build.gradle.kts` (UNVERIFIED).
2. **Ultra-wide hidden behind the logical camera.** On some phones Camera2 lists only the logical back camera and the ultra-wide is reachable only through zoom ratio below 1.0 (https://groups.google.com/a/android.com/g/camerax-developers/c/QNbqnwfKbhc); on others, `getPhysicalCameraIds` of the logical camera lists several IDs. Identify a lens by its focal length (`LENS_INFO_AVAILABLE_FOCAL_LENGTHS`) and sensor size, not by ID order or ID number. Ultra-wide can show up under more than one ID (https://groups.google.com/a/android.com/g/camerax-developers/c/gQUeQh2DCHU). Android foldables doc says apps must track the active physical ID because the logical camera switches itself: https://developer.android.com/media/camera/camera2/foldable-devices. The owner's device is a foldable-class "multi-lens" phone, and the Pixel_Fold AVD does not have real multi-lens hardware (requirements, UNVERIFIED).
3. **Some physical IDs are not openable by third-party apps** (OEM-restricted, or require a vendor permission), and the failure surfaces at bind time as an exception or a never-starting preview. Design a per-lens "unavailable" state and a fallback to the logical camera; do not hide a lens whose open fails without logging it.
4. **zoomRatio vs lens switch.** Moving the zoom ratio on a logical camera may make the HAL switch physical lens mid-zoom (so the lens that took the photo is not the lens chosen at preview time). Record the **actual** lens from the capture result metadata (`LENS_FOCAL_LENGTH`, `LOGICAL_MULTI_CAMERA_ACTIVE_PHYSICAL_ID`) at capture time, not from the UI selection. Fix zoom ratio to a known value for calibration-grade capture, and record it.
5. **Binding/unbinding races.** Rapid taps on the lens selector, `unbindAll()` followed by `bindToLifecycle` on a not-yet-released camera (the camera is closed asynchronously), and a capture in flight while rebinding. Serialize lens changes through a single state machine on the main thread, disable the shutter while a rebind is in progress, and drop in-flight capture results that belong to the previous binding. Target of "switch within ~1 s" is UNVERIFIED.
6. **EXIF lens fields.** Samsung/Pixel EXIF has `FocalLength`, `FocalLengthIn35mmFilm`, `LensModel`; some devices write wrong or logical-camera values for physical-lens shots. Don't trust EXIF alone: store the lens ID, focal length and zoom ratio from capture metadata in the sidecar/annotation. `ExifOrientationFixer.fixOrientation` (`CameraViewfinderDialog.android.kt:252`) rewrites the JPEG after capture; make sure it preserves the added lens fields (it does a decode/rotate/encode of the file, so any EXIF written before it can be lost). Write the EXIF after the fix, or write to the sidecar instead. Prior art `measurement-accuracy-and-camera-profiles/research/single-view-metrology.md:24` already warns that `DigitalZoomRatio` > 1 may or may not scale `FocalLength`.
7. **Permission and rotation.** Camera permission revoked while the dialog is open, "ask every time" permission, and a rotation recreating the activity mid-bind. Hold the selected lens in `rememberSaveable`/ViewModel. Set target rotation from the display rotation for both `Preview` and `ImageCapture`; foldables change aspect when folding/unfolding.
8. **Front-facing camera.** Out of scope for measurement but the selector may list it. Exclude it from the lens list (no calibration value, mirrored preview).
9. **Emulator limitations.** The AVD gives a virtual back/front camera only, so lens enumeration, physical-ID binding and zoom-ratio switching are not testable in CI. Unit-test the pure lens-classification function against recorded `CameraCharacteristics` fixtures (collect from the owner's phone once), and make the real-hardware verification an explicit owner step (requirements wall-clock blocker (a)).

Sources (web search, accessed 2026-11-14): CameraX developers group threads listed above; Android docs, multi-camera API (https://developer.android.com/media/camera/camera2/multi-camera) and foldable devices (https://developer.android.com/media/camera/camera2/foldable-devices), found in search results but not opened in full.
