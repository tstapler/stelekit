## 1. Git sync: JGit locking, cancellation, single-flight

### 1.1 Versions (VERIFIED, `kmp/build.gradle.kts` lines 92-147, 319-324)
JGit `7.3.0.202506031305-r`; kotlinx-coroutines 1.10.2; arrow-fx-coroutines 2.2.1.1; CameraX 1.4.1 (core, camera2, lifecycle, view); WorkManager present.

### 1.2 How JGit takes and releases `index.lock` (VERIFIED: LockFile.java @ v7.3.0.202506031305-r, https://raw.githubusercontent.com/eclipse-jgit/jgit/v7.3.0.202506031305-r/org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/file/LockFile.java)
- `lock()` -> `createLockFile()` -> `FS.DETECTED.createNewFileAtomic(lck)`; existence of `<name>.lock` IS the lock. No owner PID/host is written, so ownership/liveness cannot be read from the file.
- `unlock()` deletes the file (delete failures only logged). `commit()` renames lock over target.
- Internal write paths catch `IOException | RuntimeException | Error`, call `unlock()`, rethrow. A JVM **shutdown hook** (`ShutdownHook.INSTANCE`) unlocks on clean JVM exit only. No finalizer.
- Consequences: (a) an exception inside JGit releases the lock; (b) a process kill (Android low-memory kill, swipe-away; shutdown hooks do not run) leaves a true orphan lock; (c) two threads/processes racing yields `LockFailedException` for the loser, which is the correct "someone else holds it" signal, and the loser must NOT delete the file.
- Repo already maps this: `LockFailedException` is classed "local, short retry or distinct message" in `git-sync-resilience/research/stack.md` s.4 (line 136, 153).

### 1.3 Coroutine cancellation does not interrupt blocking JGit (INFERRED from the code shape + standard coroutines semantics; needs a test to VERIFY)
- `AndroidGitRepository` runs every op as `withContext(PlatformDispatcher.IO) { ...git.fetch()...call() }` (e.g. lines 133-338, 418-643) and `GitSyncService.sync` itself is `withContext(PlatformDispatcher.IO)` (GitSyncService.kt:278-288). `.call()` is a blocking, non-suspending call; coroutine cancellation is cooperative, so cancelling the Job does not stop the thread. The block keeps running to completion (or to a JGit `ProgressMonitor.isCancelled()` / socket timeout) and its result is discarded.
- Therefore "cancel + restart" produces **two live JGit operations on one repo**, the second hitting the first's `index.lock` (the 0.36 s `Stale git lock file` in the log). JGit's own cancel hook is `ProgressMonitor.isCancelled()` -> `CanceledException` (listed, never retried, in git-sync-resilience stack.md line 129/152); it is not wired to coroutine cancellation today (UNVERIFIED by grep; check `ProgressMonitor` use in AndroidGitRepository).
- `runInterruptible` would call `Thread.interrupt`, which JGit file I/O handles inconsistently (can throw `InterruptedIOException` mid-lock; the catch/unlock above then runs). Do not rely on it as the primary cancel path. Safer: do not cancel at all (the owner's requirement) and make the git section `NonCancellable`-style (run to completion, only the waiter is cancellable).

### 1.5 Recommended pattern (INFERRED design; pure kotlinx.coroutines, no new dependency)
- **Single-flight with join, not mutex-queue**: keep `private val inFlight = AtomicReference<CompletableDeferred<Either<...>>?>` (or a `Mutex` guarded `Deferred?`) inside `GitSyncService`. A second `sync()` caller finds the running deferred, logs `coalesced (joined running sync) source=...`, and `await()`s it (cancelling the *waiter* only cancels its await, not the run). Run body launched in the service's own `scope` (not the caller's), so caller cancellation cannot abort JGit mid-op. This matches "second press must not cancel or restart".
- A plain `Mutex.tryLock()` also works for "skip" semantics (scheduled tick should skip, not join); `Mutex.withLock` alone would queue duplicates after the first finishes (a pointless second sync) and `withLock` waiters are cancellable but the holder is not, which is fine.
- Cross-process (WorkManager worker may run in the same process but with no live service -> `ColdSyncRunner`): in-process `NamedLocks("git-<repo>")` is enough because WorkManager workers and the app share one process (INFERRED; a `:remote` process would break this, check manifest). Make `GitSyncService.sync` and `ColdSyncRunner` take the **same** `NamedLocks` key, today they cannot because `ColdSyncLocks` is private to the scheduler file.
- Liveness for lock handling (fail closed): since the lock file carries no owner, decide ownership by *our own* state: in-process single-flight holder == the only legitimate lock owner. If the single-flight is free and `index.lock` exists, it is an orphan from a killed process (or a foreign tool, e.g. a desktop git on a shared dir: UNVERIFIED whether the repo is ever shared) -> safe to clear once, logged with reason. If the single-flight is held, never delete. Optionally write a sidecar `.git/stelekit-sync.owner` (pid, start time, boot id) before sync and delete after; presence + dead pid (check `/proc/<pid>` or process start time) distinguishes a crash orphan from a foreign holder. INFERRED, not required for the first cut.
- Replace age-based `deleteLockFileIfStaleForRetry` use inside the retry loop with "single-flight free -> safe" check; keep the age check only as a second condition.
- Tests: use `kotlinx-coroutines-test` (1.10.2, already in commonTest) with a fake `GitRepository` whose fetch suspends on a `CompletableDeferred` to reproduce overlap deterministically (no real JGit). For real-lock behaviour use `JvmGitRepository` against a temp repo in `jvmTest` and pre-create `index.lock` to assert fail-closed; crash simulation = create the lock file and a stale owner file. Register tests in `AllBusinessTests`/`AllJvmTests` per CLAUDE.md.

### 2.2 Implication for "larger canvas / zoom out past fit" (INFERRED)
- No new library. Three code points define the limit: (1) `MIN_VIEW_SCALE` (lower to e.g. 0.25-0.5; `isFit` and `Fit` identity logic key off it, so `Fit` must stay "scale = fit scale" and the clamp must stop special-casing `s <= MIN`), (2) `clampAxis`/`slack` (make slack proportional to viewport, e.g. 0.5x viewport per side, so any image pixel can be centred under the finger/loupe), (3) the [0,1] point clamps stay correct: points must still be inside the image; edge pixel placement becomes possible because the viewport can pan the edge away from the screen border. So "canvas larger than image" is slack + lower min scale, not a bigger bitmap.
- Rendering: the image already draws through the view transform; Compose `graphicsLayer { scaleX; scaleY; translationX; translationY }` (hardware layer) is the cheap path if not already used (UNVERIFIED which the screen uses; grep `graphicsLayer` in AnnotationEditorScreen). For 12 MP at scale <1, downsample risk: Coil should decode to a bounded size (INFERRED); `ImageEncodeGuards.kt` exists for export only.
- Gesture-routing rules to preserve (from AnnotationGestureLayer structure): auto-return-to-Select = after `placeGesture` returns a "created" `GestureEnd`, the ViewModel sets `currentTool = Select` (one state change; `pointerInput(currentTool)` restarts its coroutine on key change, so do the switch *after* the gesture's `awaitEachGesture` iteration ends, never mid-gesture, or the restarted pointer scope drops the in-flight pointer: INFERRED from `pointerInput` key semantics, known Compose behaviour). Sticky "lock" = a boolean on tool state, no gesture change. Multi-step tools (Area, Angle) must return to Select only on completion; Label/Reference are single-shot.
- Test seams already present: `AnnotationNonDragModeTest`, `InProgressAnnotationCanvasGestureTest`, `AnnotationPlacementTest` (androidUnitTest/Robolectric, per CLAUDE.md "Compose-behavior tests belong in androidUnitTest"). `AnnotationViewTransform` is pure -> property tests in `commonTest` (kotest-property is available): invariants "toCanvas(toView(p)) = p", "any normalized point is reachable inside viewport at some legal transform", "pinch about a centroid keeps that point fixed".
- Editing a measurement value: no gesture work; pure model (see 3.4).

## 3. Calibration math

### 3.1 What the repo already has (VERIFIED)
- `model/LensCalibration.kt`: `LensCalibration(k, ticks: List<CalibrationTick(x,y,positionMeters)>, residualPercent, kEstimated, profileId, profileLabel)` + `LensCalibrationCodec` (JSON, `ignoreUnknownKeys`, undecodable -> null). One-parameter division model `undistorted = c + (p - c)/(1 + k r^2)`, r normalized by half-diagonal (annotation-lens-distortion/design.md).
- `model/GeometryCalibration.kt`: `GeometryCalibration(heightOffsetMeters, cameraDistanceMeters, plane: PlaneCalibration?)`; `PlaneCalibration(homography: List<Double> (9), referenceName, widthMeters, heightMeters, checkResidualMm)`; codec. So a **4-point plane homography is already modelled and stored** (ADR-002 step 3, v1c).
- `model/MeasurementAnnotation.kt`: `MeasurementAnnotation(uuid, imageUuid, annotationType, normalizedPoints, valueMeters, valueDisplay, label, ...)`; `pixelDistanceToMeters`, `polygonAreaMeters`, `angleBetweenThreePoints`. `valueMeters` and `valueDisplay` are stored values -> "edit the dimension" is a data edit on these two fields plus a recompute policy (see 3.4).
- Calibration persistence: column `calibration_lens_json` and sidecar keys `calibrationLens`/geometry (prior art; ADR-002 "additive block, no basis bump").
- Pipeline order already decided (ADR-002): native px -> undistort (k) -> homography H or scalar scale -> distance -> height offset -> uncertainty. Multi-tick fit already exists for one ruler ("least-squares scale along fitted axis", #638/#640, residuals exposed).
- Error ranking (annotation-lens-distortion/design.md table; measurement-accuracy requirements): lens distortion 0.05-0.14 cm on 18 cm; plane tilt 5 deg ~0.66 cm; depth 1 cm ~0.30 cm; endpoint +-1 px on 300 px ~0.12 cm. Phone JPEGs are probably already distortion-corrected (camera-intrinsics-distortion.md s.2), so a **homography-first** answer to "calibrate in multiple dimensions" is what the data supports, not a richer radial model.

### 3.2 Options for "several known distances in different directions" (INFERRED analysis on the above)
| Model | Params | Min known distances | Fixes | Library need |
|---|---|---|---|---|
| Per-axis scale (sx, sy) | 2 | 2 (one horizontal, one vertical) | anisotropic scale only; cannot correct tilt | none, closed form least squares |
| Affine (6 dof) | 6 | 3 non-collinear segments (each gives 1 equation on a metric tensor; affine from distances alone is under-determined up to rotation, fine for lengths) | shear + anisotropy | 2x2/3x3 normal equations |
| Metric-rectification homography (distances only) | 8 | A homography needs 4 coplanar point correspondences (existing path), **or** from distances only >=5 independent length constraints on a shared plane (nonlinear, ill-conditioned with phone taps) | tilt/perspective (dominant term) | small Gauss-Newton |
| Division-model k (existing) | 1 | 3 ticks | residual barrel | already in repo |
| Combined k + H | 9 | k from ticks + 4-pt rectangle | all terms | already composable per ADR-002 |
Recommendation (INFERRED): extend the existing plane path rather than add a new family: let the user supply >=2 known segments in different directions; if the 4 endpoints (or a rectangle) are coplanar, build H by DLT (existing PlaneCalibration), else fall back to per-axis scale; report `checkResidualMm` / leave-one-out error. N (success metric 3) should be set so the model is over-determined by at least 1 constraint (>=3 segments for per-axis+residual; 4 points for H + 1 check distance). The metric of record is mean absolute error on a held-out distance, computed with a golden-scene test (the repo has `LensDistortionSimulationTest`-style synthetic tests).
- Homography DLT = solve an 8x8 (or SVD of 2n x 9) linear system. For n=4 it is an 8x8 solve; n>4 least squares via normal equations with Hartley normalization. Pure Kotlin is ~60-100 lines (INFERRED); the SVD route needs a decomposition. Check whether the H solver already exists before writing one (grep `homography` in `calibration/`; not done in this pass: UNVERIFIED).

### 3.3 Libraries (INFERRED; nothing verified online this pass)
- KMP-friendly options are thin: `org.jetbrains.kotlinx:multik` (JVM/native only, no wasm/Android-first), `org.ejml` (JVM/Android only, not commonMain), OpenCV (Android/JVM only, heavy, native). The repo targets commonMain + wasm; adding a native/JVM-only dep violates the shared-code rule for a <=9x9 system. **Recommend: no new dependency**; hand-rolled Gaussian elimination with partial pivoting / normal equations in `commonMain/.../calibration/`, covered by `kotest-property` round-trip tests (generate random H, project points, recover H). Existing conventions in `commonTest` apply.
- Numerical stability caveat: normalise coordinates (centre, scale to mean distance sqrt(2)) before DLT; use `Double`.

### 3.4 Editing a measurement's value (INFERRED design on VERIFIED model)
`MeasurementAnnotation.valueMeters`/`valueDisplay` are persisted separately from `normalizedPoints`. An edited value is either (a) a manual override flag (`valueMeters` set by user, points untouched, shown as "manual") or (b) a **calibration constraint**: "this segment = X m", fed to 3.2 as another known distance. (b) is the one that serves the stated goal; (a) is the minimal edit. Both need an additive field (e.g. `valueSource`) with a default so old sidecars (`ImageSidecarSchema`) still load, same pattern as `calibrationLens` ("additive, ignoreUnknownKeys").

### 4.2 Selecting lenses
- VERIFIED (same page): `PhysicalCameraInfo` on `CameraInfo` and a physical camera ID on `CameraSelector` appeared in **1.4.0-alpha05**; 1.7.0-rc01 added a `CameraSelector` obtained from `CameraInfo.getPhysicalCameraInfos()` and binding use cases to physical cameras (so first-class physical-lens binding is a 1.7 feature, still RC today). 1.7.0-alpha03 added `CameraInfo.cameraId` / `cameraCharacteristics` and deprecated the old `Camera2Interop.Extender`/`Camera2CameraInfo` in favour of `Camera2Interop.forUseCase` etc. (VERIFIED, same page). The page did not describe CameraSelector filters for ultra-wide (stated "not covered").
- VERIFIED (https://developer.android.com/media/camera/camera2/multi-camera, 2026-11-14): multi-camera API is Android 9 / API 28; Android best practice is that OEMs expose a **logical** camera for same-facing physical cameras plus (usually) the physical ones; "Often, only one of the physical cameras is exposed" on older/privileged-only OEM setups; what the logical camera does is "entirely dependent on the OEM HAL" (e.g. Pixel 3 picks a physical camera by focal length and crop region). Detection: `CameraCharacteristics.REQUEST_AVAILABLE_CAPABILITIES` contains `REQUEST_AVAILABLE_CAPABILITIES_LOGICAL_MULTI_CAMERA`; members via `getPhysicalCameraIds()`; per-physical `LENS_INFO_AVAILABLE_FOCAL_LENGTHS` (page's own sample compares them). Physical streams are chosen per output via `OutputConfiguration.setPhysicalCameraId` in a Camera2 `SessionConfiguration`.
- INFERRED (CameraX behaviour; verify on the owner device): CameraX 1.4.x enumerates **camera IDs the framework lists** via `ProcessCameraProvider.availableCameraInfos`; a back "wide + ultra-wide + tele" phone may show (a) one logical back camera where lens switching is done with `CameraControl.setZoomRatio` (ultra-wide at zoomRatio < 1 when `ZoomState.minZoomRatio < 1`), or (b) several back camera IDs. Two plan paths: **A (portable, 1.4.1)** list back `CameraInfo`s, label each with focal length from `Camera2CameraInfo.from(info).getCameraCharacteristic(LENS_INFO_AVAILABLE_FOCAL_LENGTHS)` and `CameraSelector.Builder().addCameraFilter { infos -> pick by Camera2CameraInfo.cameraId }`; plus a zoom-ratio chip row (0.6x/1x/2x) from `ZoomState`. **B (physical IDs)** requires 1.7.x (RC) or raw Camera2. ### 4.3 Calibration-relevant characteristics (VERIFIED in prior art, https://developer.android.com/reference/android/hardware/camera2/CameraCharacteristics, access 2026-11-11 per camera-intrinsics-distortion.md)
