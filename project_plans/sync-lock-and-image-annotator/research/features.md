## 1. Git sync: entry points and what each does when a sync is already running

Root-cause finding (VERIFIED): `GitSyncService.sync()` (`commonMain/.../git/GitSyncService.kt:278`) has NO single-flight. It only does `gitSyncBusyCounter.begin()` (:292) / `end()` (:517); the counter is a plain increment (`git/GitSyncBusyCounter.kt:30-37`), so two overlapping `sync()` calls both run the whole pipeline. Nothing is cancelled by a second press; the two runs interleave.

Then step 3b (`GitSyncService.kt:339`) calls `removeStaleLockFile`, which on Android (`androidMain/.../git/AndroidGitRepository.kt:663-683`) does: lock absent -> OK; lock age <= 60 s -> returns `StaleLockFile` error; lock age > 60 s -> DELETES it. So:
- Overlap within 60 s: run B sees run A's LIVE lock and fails with "Stale git lock file" (matches the log: error 0.36 s after a `sync/fetch start`). Run B also does `_syncState.value = Error(...)` (:340), which overwrites run A's Fetching/Merging state in the UI while A is still running. INFERRED but strongly consistent with the log; the owner's "cancel leaves lock" theory is not needed.
- Overlap after 60 s (a slow sync: log shows 7.5 s deletes + 6.8 s loads): B DELETES A's live lock -> index corruption risk. This is the data-safety hazard; "stale" is decided by age only (requirements Rabbit Hole confirmed in code).
- `rateLimitRetry.cancel()` (:296) at the top of every sync cancels only the pending delayed retry, not a running sync.

Per entry point:

| Entry | Code | When a sync is already running |

Second tap in that window starts a second `sync()`. Also Error/Idle states re-enable it. INFERRED window; UI file not read. |

Good. Caveat: busy only true after `begin()`; a tick landing in the instant before is a TOCTOU race (INFERRED). |
| ScheduledSyncRunner (the tick body) | `git/ScheduledSyncRunner.kt:73` feeds `busy = busyCounter.isBusy.value` into `ScheduledSyncPolicy`; `skip()` maps Busy -> `SkipReason.Busy` (:~95) but `reason.fetchesAnyway` may run a `fetch()` anyway | A fetch-only path (`fetchOnly`, GitSyncService.kt:~535-592) also begin()/end()s the counter but is not mutually exclusive with `sync()` either. Design implications (feature-level, not final design):
- One single-flight gate at the very top of `sync()`/`fetchOnly()` (before `begin()` and before step 1), keyed per graph/repo, shared by all entry points via the live `GitSyncService`; plus take `NamedLocks(repoName)` inside it so the cold WorkManager path is covered. Second caller: return a distinct "joined running sync" result (Observability req) without touching `_syncState`.
- Second press must not call `_syncState.value = Error` (:340 and similar) for a lock it does not own.
- Replace age-based deletion with ownership/liveness: write an owner token file or in-process held-lock registry; delete only a lock we created (cancelled/crashed own run) or one whose owner process is provably gone (across process death: WorkManager worker killed). Fail closed: unknown owner -> "another sync is running".
- Edge cases to test: UI double-tap; tick during manual sync; worker cold-start during foreground sync; rate-limit retry firing during manual; cancellation during commit/merge (`withContext` cancel, JGit blocking call ignores cancel until it returns); process kill mid-index write (real stale lock, must self-heal on next sync after liveness proof); app swiped away while worker runs (second process? no, same process, but WorkManager runs in app process so in-process registry is sufficient; separate `:remote` process not used - UNVERIFIED); graph switch while syncing; lock held by an external git CLI/other tool (Syncthing/termux) -> must NOT delete.
- Regression test must fail on today's code: launch two `sync()` calls on a fake `GitRepository` whose `commit` suspends; assert the second returns joined/coalesced and `removeStaleLockFile`/lock never touched, `_syncState` not Error. Existing seams: `GitSyncServiceConflictResolutionTest`, `GitSyncBusyCounterTest`, `GitSyncWorkerGateAndRecordTest`, `WorkManagerSyncSchedulerRetryOwnerTest` (note `WorkManagerSyncSchedulerRetryOwnerTest` and `...UniqueWorkTest` already cover owner/unique concerns - read before adding).

Industry analogue (general knowledge, UNVERIFIED): git itself uses `O_EXCL` lockfile with no owner info; GUI clients (Working Copy, Tower) serialize operations per repo via a queue/"operation in progress" and disable the button; file-sync tools (Syncthing) coalesce triggers (a trigger while running sets a "rerun needed" flag). Coalesce-with-one-pending-rerun is the common pattern and fits "do not cancel, do not duplicate".

## 2. Annotator tool modes

Current (VERIFIED):
- `AnnotationTool` enum (`ui/annotate/AnnotationEditorViewModel.kt:74`): SELECT, DISTANCE, AREA, ANGLE, LABEL, GRID_REF (reference). Default tool in state is `DISTANCE` (:108), not SELECT.
- `selectTool()` (:445) just swaps `currentTool`, clears `inProgressPoints`; leaving GRID_REF drops ruler/plane sessions (:451-452) - switching tools silently discards a half-marked ruler calibration (an edge case for auto-return too).
- Auto-commit when point count reached (:565-566): DISTANCE=2, ANGLE=3, LABEL=1, GRID_REF=2 (`requiredPointCount` :86-92). After commit the tool stays active - no auto-return exists. AREA is open-ended, closes on tap of first point or `closeArea` (:570-575); needs an explicit "done".
- Gestures: `AnnotationGestureLayer.kt` routes two-finger pinch/pan (:148-156), one-finger pan when not placing (:167), mouse-wheel zoom (:172); `AnnotationNonDragMode.kt` covers tap-placement alternatives. In a placing tool one finger draws/places, so pan requires switching to SELECT - this is exactly the owner's complaint. Two-finger pan/zoom works in any tool (INFERRED from :148; verify in layer).
- View scale clamped to `MIN_VIEW_SCALE = 1f` .. `MAX_VIEW_SCALE = 8f` (`AnnotationViewTransform.kt:13,16,79,110`) and offset clamped to content with `slack` (:129). So zoom-out past Fit is impossible by constant; a canvas larger than the image requires lowering MIN_VIEW_SCALE below 1 and a margin/"slack" so offscreen-of-image points are placeable in normalized coords (annotation geometry is normalized [0,1] per `AnnotationViewTransform.kt:53`; points outside [0,1] need an explicit policy: clamp to image edge or allow outside; sidecar/validators/exporters may assume [0,1] - check `ImageAnnotation` validation and `AnnotationExporter`).
- Toast: `AnnotationEditorScreen.kt:1687` "Depth model ready - estimation coming in a future update" (overlap fix is layout-only; the text is explicitly "silently do nothing" replacement per comment at :187). Check `annotator-unit-prefs-ux-fixes` for what shipped.

Conventions (general knowledge, UNVERIFIED): Photoshop/Figma/Canva use sticky tools by default with Esc/V to return; Google Markup / Samsung Notes pen use sticky pen but one-shot for shapes; Apple Markup is sticky; Sketch/Figma "shape" tools are one-shot (return to move tool after one draw) with double-tap-the-tool or Shift-hold for sticky ("tool lock"); CAD (AutoCAD/Fusion) repeats the last command on Enter/Space and Esc cancels. Measure apps (Google Measure, iOS Measure) are continuous: tap to start/finish then a new segment begins. The owner's spec (one-shot, auto-return, opt-in lock) matches Figma's convention.

State-machine edge cases to design:
- States: Select (pan/zoom/select/drag handles) | Placing(tool, pointsSoFar) | Locked(tool) | AwaitingInput(label text / reference length dialog). Transitions: commit success -> Select (unless locked); cancel (Esc/back/tap Select) -> Select; AREA closes -> Select; GRID_REF dialog confirm -> Select, dialog cancel -> stay or Select (decide).
- "Tap tool, drag once": the requirements describe a drag gesture creating a 2-point measurement (press = P1, release = P2); currently placement is tap-per-point (`AnnotationPlacement.kt`, `AnnotationNonDragMode`). Need both: drag-to-create and tap-tap (accessibility / TalkBack / precision with loupe `LoupeGeometry.kt`). Drag-vs-pan conflict: in a placing tool one finger = place; two fingers = pan/zoom must cancel any in-progress one-finger placement (second pointer down mid-drag -> discard in-progress point, not commit it). Once back in Select, one finger on empty canvas = pan, on a handle = drag point (hit-test `AnnotationHitTest.kt`); overlap of pan vs handle drag resolved by hit radius, at larger zoom-out the handle hit target must stay constant in screen px, not scale with view.
- Failed/accidental drags: zero-length drag (< N px) must not create a degenerate measurement; treat as "stay in tool, place first point".
- Undo of a just-made measurement: after auto-return to Select, undo must remove exactly that measurement (history `UndoHistory.kt`) and should NOT also restore the previous tool; decide whether undo re-arms the tool (probably no). Redo after tool switch. Undoing a reference/GRID_REF measurement must also revert the calibration - there is a separate single-level `calibrationHistory` (:397-403, `canUndoCalibration`) so undo/redo of the annotation list and of calibration are two different stacks (edge case: undo reference measurement leaves calibration in place).
- Persistence race: measurement commit is debounced via `AnnotationPersistenceQueue`; auto-return must not wait on it.
- Settings: "auto-return default on, lock opt-in" per Risk Control; lock affordance candidates: double-tap tool button (Figma-style), long-press, or a toolbar "pin" toggle. Show active mode clearly (highlighted chip + hint strip `MeasurementAdviceStrip`/coach marks `CoachMarkOverlay.kt`); first-run coach mark for the new behaviour.
- Editing a measurement's value (item 3a): selecting a DISTANCE annotation (`selectAnnotation`, ViewModel :992) + an edit-value dialog. Semantics choice is the key edge case: (a) edit = "this segment is actually X" -> a new reference/calibration constraint that rescales ALL measurements (and triggers `CalibrationChangeWarningDialog`, which says "Changing scale will update all measurements", `ui/annotate/CalibrationChangeWarningDialog.kt:13-42`), or (b) edit = override the stored label for this one annotation only (breaks consistency with geometry; value drifts from points if dragged later, need an `isOverridden` flag shown in UI, cleared on point drag). Recommend surfacing both: default (b)-safe? No - product decision; flag to design. Industry: Canvas/Polycam let you retype a dimension and the model re-solves (constraint-based); Moasure and ruler apps treat the number as derived. Also units: typed value uses the current display unit chip, converted via the same parser as the reference-length dialog (`HeightOffsetForm`/unit prefs from `annotator-unit-prefs-ux-fixes`); accept `5'3"`, fractions, mm/cm/m; reject <=0, NaN, absurd magnitude.
- Editing with existing values: `computeMeasurement` (:1073) recomputes on drag (:1017). If an override exists, dragging a point must either clear it or ask.

## 3. Multi-reference calibration (item 3b)

Current model (VERIFIED): `Calibration` + `CalibrationMethod` + `CalibrationTick` list on `LensCalibration` (`model/LensCalibration.kt:10-43`) - one RULER with >=2 ticks along ONE line, `MultiPointCalibration.fitScale` (`calibration/MultiPointCalibration.kt:69`, requires >=2 ticks; `estimateK` needs `MIN_TICKS_FOR_ESTIMATE = 3` :54 and only accepts k if it measurably reduces residual :104-106). One-parameter division-model k + one scale. `GeometryCalibration` (`model/GeometryCalibration.kt:15-36`) adds height offset, camera distance and a `PlaneCalibration` homography from a known rectangle (paper/card; `PlaneReferencePanel`). So "one-dimensional" = one line of ticks; a plane homography from a rectangle already exists for planar targets. Requirement 3 must reconcile with prior art ranking (lens distortion smallest of four error terms; depth/plane mismatch, short refs, tilt dominate) - the feature that most likely moves error is plane/homography with multiple non-collinear distances on the SAME plane, not more radial terms. Per-profile `CameraProfile` (matched by make/model/focal length +-0.15 mm tolerance, `calibration/CameraProfile.kt:24-26,83`) already exists, which is directly relevant to item 4's lens recording.

Industry (general knowledge, UNVERIFIED): Google/ARCore Measure uses VIO scale, no user calibration; Moasure/Canvas use depth/LiDAR; photo-measure apps (e.g. "Photo Measures", PlanGrid) use one reference object or a rectangle -> perspective rectification (the homography already built); OpenCV camera calibration uses a checkerboard (>=10 views) - not feasible per photo. Typical consumer flow: "tap two ends of a known object and enter its length"; advanced: "add more references to improve accuracy", residual shown per reference with outlier highlighting.

Edge cases the design must handle:
- Too few points: 1 reference -> scale only (existing single-scale baseline); distortion/homography terms need more; define N (suggest: >=2 non-collinear for per-axis scale, >=4 point correspondences for plane homography, >=3 ticks for k - matches existing). Never silently fit more parameters than data supports; show "needs N more".
- Collinear references: all references along one line cannot constrain the perpendicular axis or a homography (degenerate). Detect via the same `principalAxis` check style (`MultiPointCalibration.kt:144`) / rank of design matrix; fall back to scale-only and say so. Near-collinear (angle between refs < ~15 deg) -> warn.
- Conflicting distances: two references imply scales differing by >X% (typo, wrong unit, different depth plane). Show per-reference residual %, flag worst offender, allow exclude/edit; do not average blindly; use robust fit (median / drop-one) if >=3. `CalibrationConfidenceBadge.kt` and `CalibrationNudgeBanner.kt` exist to display residual.
- Different depth planes: references not on the plane of the measured object give a wrong scale regardless of model (prior-art top error term); warn using `PlaneReferencePanel`/`MeasurementAdviceStrip`.
- Units mixing: store references in metres canonically (as now `valueMeters`); input parsed per entry in its own unit; display in the unit chip; never store display strings as truth. Imperial fraction rounding in display must not round-trip into calibration (store the metres the user typed, exactly).
- Re-calibration: all existing measurements recompute (annotations store normalized points, `AnnotationViewTransform.kt:53`); `CalibrationChangeWarningDialog` (existing, shows count) must fire before applying a new fit, and the single-level `calibrationHistory` (ViewModel :397-403) is insufficient once references are individually editable -> history of calibration needs references list, not just last snapshot. Editing/deleting one reference = recalibration = same warning. Overridden (hand-edited) measurements must be excluded from or flagged by recalibration.
- Persistence: additive to `ImageSidecarSchema`/`ImageAnnotation` with version field; old sidecars (no references list) load as single-scale; newer file opened by older app must not drop the field silently (Json `ignoreUnknownKeys = true` in GeometryCalibration codec means older readers DROP unknown keys on re-save - data-loss hazard on downgrade; INFERRED, call out in design).
- Verification: success metric needs the owner's door-frame photo + measured ground-truth distances; the prior research already defines error terms - reuse its harness if any (`measurement-accuracy-and-camera-profiles/research/single-view-metrology.md`).
- Residual communication: show mean error across references, not just max; log model, N refs, residual (Observability req).

## 4. Multi-lens camera (item 4)

Current (VERIFIED): all three camera paths hard-code `CameraSelector.DEFAULT_BACK_CAMERA`: `androidMain/.../ui/components/CameraViewfinderDialog.android.kt:106-108`, `platform/sensor/AndroidCameraProvider.kt:116`, `platform/sensor/AndroidCameraPreviewBinder.kt:54`. No lens enumeration, zoom, flash, or lens metadata exists. `CameraProfile` (calibration/CameraProfile.kt:24-26) matches on make/model/focal length so recording focal length feeds straight into existing profile matching; `ProfileRejection` line 60 message says a photo with no make/model/focal-length cannot get a profile.

Feature landscape (general knowledge, UNVERIFIED - verify against CameraX release notes before design): stock/Google Camera and Samsung/OnePlus apps present a zoom-ratio strip (0.5x / 1x / 2x / 5x) rather than lens names; the logical multi-camera zooms continuously and the OS switches physical sensors internally. CameraX exposes: `CameraInfo.zoomState` (min/max ratio), `CameraControl.setZoomRatio`, `ProcessCameraProvider.availableCameraInfos`, `Camera2CameraInfo` to read per-camera `LENS_INFO_AVAILABLE_FOCAL_LENGTHS` and physical IDs (`CameraCharacteristics.getPhysicalCameraIds`, API 28+), and `CameraSelector.Builder().addCameraFilter{}` for custom picking; since CameraX 1.4-ish, `SessionConfig`/physical-camera selection (`setPhysicalCameraId` on use cases is experimental/UNVERIFIED). Many OEMs hide ultra-wide/tele behind ONE logical back camera (zoom 0.6x gets ultra-wide) and some expose the physical IDs only to system apps or via vendor extensions; some devices list physical cameras as separate `availableCameraInfos` entries and some don't. Therefore "list every rear lens" must be defined as: (a) logical zoom presets derived from `ZoomState` min/max + focal-length ratios, and (b) additionally any separately-bindable back camera infos. Don't promise per-physical-ID capture.

Edge cases:
- Lens unavailable/ not bindable: `bindToLifecycle` throws `IllegalArgumentException`/`CameraUnavailableException`; camera in use by another app; thermal throttling; fall back to previous lens + inline notice, never leave a black preview (existing code already guards wedged futures at AndroidCameraProvider.kt:80).
- Lens switch is a re-bind (preview freezes/flickers ~0.3-1 s; target ~1 s in NFR UNVERIFIED): keep last frame, debounce rapid taps, serialize switches (single-flight again), preserve zoom/flash state, rotate handling.
- Front camera: out of scope for measurement (distortion/profile differ, mirrored preview) but a flip button users expect; decide: hide (measurement app) - recommend hide, say so.
- Zoom ratio per lens: digital zoom on a lens degrades calibration validity (focal length effectively changes). Record BOTH lens identity and effective zoom; if zoom != the lens's native ratio, mark photo "cropped/zoomed - profile not applicable" so `CameraProfiles` matching (+-0.15 mm focal tolerance) doesn't wrongly match.
- EXIF: CameraX `ImageCapture` writes EXIF `FocalLength`, `FocalLengthIn35mmFilm`, `Make`, `Model`, and (device-dependent) `LensModel`/`LensMake`; ultra-wide/tele via logical camera often report the effective physical focal length but not always. Don't depend on EXIF alone: also persist the app-side record (camera id, physical id if known, requested zoom ratio, focal length from Camera2 characteristics) in the sidecar/ImageAnnotation. Existing EXIF reader `ExifOrientation.kt` is orientation-only; need a focal-length reader (check what `CameraProfiles` already reads).
- Photo imported from gallery (not in-app) has only EXIF: calibration must handle missing lens info (the requirement "record lens" cannot cover these).
- Permissions: CAMERA already handled (`PermissionRationaleDialog.kt`); no new permission.
- Testing: AVD has virtual front/back only (UNVERIFIED, Open Question 6) -> unit-test lens selection logic against a fake `CameraInfo` list; flash/zoom/lens-switch need owner-device run. Per CLAUDE.md the owner cannot use logcat: log selected lens list + bind result via `Logger` to persisted logs.

## 5. Users' unstated needs
Sync
- A visible "sync already running" indication (spinner stays; second tap gives a brief "already syncing" toast, not an error).
- After fix, the existing stale-lock banner should still offer safe recovery for a genuinely dead lock, with liveness reasoning shown ("no sync running; lock 3 h old").
- Slow syncs (7.5 s DB ops in the log) widen the overlap window - perf of `batchDeleteBlocks`/`loadFullPage` is a contributing cause but out of scope; note it.
- Never lose pending notes: coalesced trigger should leave one pending rerun so edits made during sync are pushed.
Annotator
- Undo for every action including value edit and recalibration; visible mode indicator; Esc/back to cancel an in-progress measurement; keep two-finger pan/zoom always available.
- Zoom-out should not make hit targets tiny; recenter/Fit button remains.
- Measurement value edit should be reversible and should show original computed value.
- Export (`AnnotationExporter`, `AnnotationDriveExporter`) must render edited/overridden values and points outside the image bounds (canvas margin) correctly; decide whether margin is cropped.
- Calibration confidence visible per reference; "why is my measurement off" guidance (depth plane, tilt) via `MeasurementAdviceStrip`.
- Sidecar backward/forward compatibility and sync-ability across devices (annotations sync via git: schema change must not break the desktop reader).
Camera
- Remember last-used lens; show focal length/zoom label; tap-to-focus, flash/torch, grid/level (a level/tilt indicator is directly valuable because tilt is a top error term in prior art - INFERRED opportunity: record gyro tilt at capture); exposure lock; orientation lock; shutter feedback; ability to retake; keep resolution high (12 MP) since annotator perf assumes it.
- Record device make/model/lens id so a calibration learned on the ultra-wide is reused only for that lens (profile store).
