## 1. E1 recovery protocol: interleaving walk (focus of this pass)

Setup: processes P1 and P2 are any two of {desktop app, `SyncMain`}; W is the WorkManager worker (same process as UI); R is a dead record; L is `index.lock`.

| # | Interleaving | Outcome under decision 12 |
|---|---|---|
| 1 | P1, P2 both read R, both decide `ClearedDeadOwner` | One wins `tryLock`; the other gets null or `OverlappingFileLockException` and returns `SyncInProgress`. If it acquires after P1 finished, step 4 re-reads: the record is now P1's (P1 writes it at step 6 **before** releasing the lock), so it returns `OwnerAlive`. Safe. |
| 2 | P1 deleting locks, P2 reads "no record" in the gap after P1 deleted R | P2 `CREATE_NEW` may win. P1 already deleted the locks (locks first, record last), so P2's new JGit lock is never touched; P1's own `CREATE_NEW` loses and it returns `OwnerAlive`. Safe. |
| 3 | P1 killed while holding the recovery lock, at any step | Kernel releases it. Steps are idempotent (delete locks, delete record, create). Next claimer re-decides. Safe. |
| 4 | P2 arrives while P1 runs normally (live record) | `OwnerAlive` without taking the recovery lock; nothing deleted. Safe, provided liveness is right (see C3). |
| 5 | `endOwnedOperation` (compare, delete) racing a recoverer | A recoverer only deletes a record whose owner it judged dead; the ending owner is alive. TOCTOU in the end-delete is harmless. Safe. |
| 6 | W vs UI in one process | Same gate key excludes before step 1. Android has one process (no `android:process` anywhere; plan Task 1.1c re-verifies). Safe. |
| 7 | Force-stopped leftover record, new `InstanceId`, same boot | pid absent or start ticks differ: `Dead`, normal recovery. Safe. |
| 8 | Reboot | Different non-null `bootId`: `Dead` without the pid probe. Also covers pid reuse after reboot. Safe. |
| 9 | Two gate keys for one directory in one process (path alias) | **Not safe**, see C1. |
| 10 | Non-participating git (terminal, IDE) takes `index.lock` between decide and delete | **Not fully safe**, see C2. |
| 11 | P1 judged alive/dead wrongly by the liveness probe | **Not safe**, see C3. |

Java semantics (VERIFIED against the JDK contract, not run): `FileChannel.tryLock()` returns null when another process holds it, and throws `OverlappingFileLockException` when this JVM already holds or is acquiring an overlapping lock on the same file, from any channel and any thread. So two threads or two gate instances in one JVM are excluded by the JVM's own table, and the ADR handles both outcomes (ADR-001:46). An in-process mutex is also specified (the `RepoOpGate`), so the JVM-level exception is a backstop, not the only guard. POSIX caveat (closing any fd of the file in the process drops the process's locks) is handled by opening the channel only inside the step. The lock releases on process death on Linux and Windows; on Android app-private ext4/f2fs it behaves the same. NFS and FUSE: an unsupported lock raises `IOException` (fail closed, specified); a mount that silently grants non-exclusive locks across machines is already excluded because a different hostname is `Unknown`. JGit's `LockFile` creates `index.lock` atomically; it can interleave with our deletes only through a non-participating tool (C2) or a mis-keyed gate (C1), never through another participating claimer (row 2).

## Concerns

### E1 Sync

- [ ] **C1 `ClearedOwn` deletes a live lock when two gate keys alias one directory.** `ClearedOwn` is decided by "record `instanceId` equals this process, and with the gate held it can only be our own corpse" (ADR-001:45, plan:242). The premise holds only if every in-process run on a directory takes the same key. `RepoOpGate.keyFor` wraps `GitWriteLockNaming.lockNameFor`, which is a *remote-URL* normaliser: strip protocol, trailing `/`, `.git`, sanitise characters (`GitWriteLockNaming.kt:32-53`). It does not resolve symlinks, `..`, bind mounts or case. Two graph registrations of one repo through different spellings give two keys; run A holds `index.lock` with its record (instanceId = this process); run B passes the gate, reads A's record, sees its own `instanceId`, decides `ClearedOwn`, takes the free recovery lock (A released it at step 6), deletes A's live `index.lock` (mtime is after the record's start) and A's record, and both run. Probability is low (aliasing plus overlapping runs); consequence is the corruption this epic exists to prevent; fix is cheap. Fix: key the gate and the in-process "records I currently own" set by `File.canonicalPath` of the resolved `.git` directory (Task 1.3a), and make `beginOwnedOperation` return `SyncInProgress` if this process already has an active run registered for that canonical record path, so `ClearedOwn` is reachable only for a corpse with no active run. Add a test with a symlinked second path. Task 1.1d only pins "same repo shares one key" for the spelling cases it names.
- [ ] **C2 The mtime filter does not protect a foreign lock created after the dead owner started, and the proof sketch states it backwards.** Step 5 deletes locks whose mtime is **not before** `startedAtMs - 2 s` (ADR-001:48). A terminal or IDE `git` that took `index.lock` today, while a dead record from last week still sits in `.git`, has a newer mtime and is deleted. The sketch (f) says the opposite ("nothing of theirs was deleted unless its mtime preceded the dead owner's start", ADR-001:51), and Story 1.2's last bullet (plan:250) tests only the older-lock case. Status quo deletes any lock older than 60 s, so this is narrower than today, but the claim in (f) is wrong. Fix: correct the text; add a test with a foreign lock newer than the dead record; narrow further by also requiring the lock's mtime to be no later than the moment the verdict is taken minus a small margin, and by treating a lock modified within the last few seconds as `OwnerUnknown` (a live writer touches the lock while it works only briefly, so this is a heuristic, say so).
- [ ] **C3 Liveness can misjudge a live owner as dead.** Two sources. (a) JVM start time: plan Task 1.2b uses `ProcessHandle.info().startInstant()` (plan:262). On Linux the JDK computes this as boot time (read from `/proc/stat` `btime` once per JVM) plus the process start ticks, so two JVMs started on opposite sides of a wall-clock step (NTP step, resume) disagree about the same process's start. INFERRED from the JDK implementation; I did not run it. A mismatch reads "start ticks differ" and yields `Dead` for a live owner, which then loses its `index.lock`. Fix: on Linux read raw start ticks from `/proc/<pid>/stat` field 22 on the JVM too (the Android adapter already does), use `startInstant` only on macOS and Windows, and compare `Instant`s with a tolerance of a few seconds. (b) PID namespaces: a sandboxed desktop app and a host CLI see the same repo with different pid spaces; an absent or unrelated pid reads `Dead`. Note it in the verdict table and treat "pid absent but same host and same boot" as `Dead` only after the recovery lock is held and the record is re-read (step 4 already does this; also re-run the probe there). Neither (a) nor (b) is covered by Task 1.2f, which uses a fake liveness.
- [ ] **C4 Record read and write semantics are unspecified (torn record) and `forceRemoveLock` has no protocol.** (i) The record is created with `CREATE_NEW` and then written, so a reader can see an empty or partial file. The plan never says what an unparseable record means (grep of ADR-001 and plan: no "corrupt", "partial" or "atomic" for the record). If a reader treats it as `NoRecord`, the `CREATE_NEW` loses and it returns, fine; if as dead, it deletes a live owner's record and locks. State: unparseable or empty record is `OwnerUnknown`; write the content to a temp file and publish with `Files.createLink`/exclusive rename semantics, or write then `fsync`, and add a test that reads between create and write. (ii) `forceRemoveLock` (the user-confirmed path, plan:240,274) is not in decision 3's list of gated entry points and no step says it takes the gate, takes the recovery lock, or re-reads the record. A user confirming while a CLI run starts would delete that run's live lock. Specify: gate, `tryLockRecovery`, re-decide, refuse on `OwnerAlive`, delete only the allow-listed locks.
- [ ] **C5 Wrapping the merge unit in `withContext(NonCancellable)` silently changes the meaning of `return@withContext`.** The pipeline body is one `withContext(PlatformDispatcher.IO) { ... }` (`GitSyncService.kt:284`) and the unit contains `return@withContext` at L429, L456 and L464 (conflict and commit-failure exits). A nested `withContext(NonCancellable) { ... }` makes the label bind to the inner lambda; those returns then exit only the unit and the pipeline falls through to the push step with unresolved conflicts or a merge in progress. It compiles, because the block's type widens to `Any`. Task 1.5a says "wrap" and "no refactor" (plan:376). Fix: extract the unit as a private `suspend fun mergeUnit(...): MergeUnitOutcome` (sealed: `Continue(remoteCommitsMerged, autoMergedPaths)`, `Exit(Either.Left)`) and translate at the one call site, or give the inner block a distinct label and `return@unit` plus an explicit outer return. Add an AC: after a conflict in the unit, `push` is not called (the existing `GitSyncServiceConflictResolutionTest` family would catch it only if it asserts no push; make that explicit).
- [ ] **C6 Real concurrency is tested only inside one JVM.** Task 1.2f's 200 seeded interleavings run claimers as threads of one JVM with a barrier decorator, where exclusion comes from the JVM's `FileLockTable`, not the kernel (plan:270). The only cross-process test is "second JVM holds the lock then is killed". Add one genuinely cross-process test: two spawned JVMs racing `beginOwnedOperation` over a pre-existing dead record, repeated a few dozen times, asserting one winner and a surviving simulated `index.lock`. Also state that the recovery file is opened `CREATE` plus `WRITE` (an exclusive `tryLock()` on a read-only channel throws `NonWritableChannelException`) and that a `.git` that is a file (linked worktree) is out of scope or handled.
- [ ] **C7 Wave order: a task uses a fake that a later wave creates.** Story 1.4's AC and Task 1.4a (W5) test with `GateAssertingGitRepository` (plan:326), which Task 1.8b (W8) introduces (plan:451). Move the fake into 1.3d or 1.4a (it is small), or reword the 1.4a AC to a hand-rolled recording fake and let 1.8b generalise it. The remaining wave checks hold: 1.3d (W3) needs only `RepoOpGate` from 1.3a (W2); 1.3c (W3) adds required parameters to `AndroidGraphMoveQuiesceStrategy`, which production never constructs (grep: only tests construct it, `createAndroidGraphMoveQuiesceStrategy` has no production caller), so W3 compiles before 1.3b wires it in W4; 1.4a (W5) uses `SyncOrigin` (1.4e, W2), `beginOwnedOperation` (1.2d, W4) and the gate parameter (1.3d, W3); 1.2e (W5) follows 1.2d (W4).

### E3 Measurements and calibration

- [ ] **C8 The GRADIENT tier's significance gate is mis-calibrated at the minimum N, and its validity range depends on the unknown focal length.** The math of the claim holds (see section 2). Two gaps. (i) At N = 5 and P = 3 the residual variance has 2 degrees of freedom, so `|g| > 3 SE` is a t-test with df = 2: `P(|T| > 3) = 0.095` (t CDF for df = 2 is `0.5 + t / (2 sqrt(2 + t^2))` = 0.952 at t = 3), i.e. about 1 in 10 pure-noise fits would pass; df = 3 (N = 6) gives about 0.06. The "3 SE" gate therefore does not mean 99.7 percent. Use the t quantile for the actual df, or fix sigma from a prior on tap noise, and let the LOO comparison veto, as the ADR already requires. (ii) The tier drops the anisotropy `1/cos(tau)` (0.4 percent at 5 degrees, 1.5 percent at 10, 10 percent at 25). A measurable gradient does not bound tau without `f`: the same 15 percent gradient across the half-frame is about 8 degrees for a wide lens (half-width/f near 1) and about 27 degrees for a tele lens (0.3). Add a validity bound from the EXIF 35 mm-equivalent focal, used only as an order-of-magnitude bound (not a correction, so the "EXIF is untrusted" objection does not apply): if `|g| * f_exif` implies tau above about 10 degrees, mark the result "tilt too large for this model" and keep SCALE. Also the SNR figure assumes 0.3 percent per-segment noise; for a 5 percent-of-frame reference (200 px, 1 px taps) it is about 0.7 percent, which cuts the 5-degree SNR from 23 to about 10 and the 2-degree SNR below the gate. The tier degrades to SCALE correctly, but the SNR sentence should name its length assumption.
- [ ] **C9 Principal point and crops.** The 3-parameter map assumes the principal point at the image centre. For a cropped or digitally zoomed photo the offset `c` adds an uncorrected term of order `|c| * |g|`; with `|g| = tan(5 deg) / f = 2.8e-5 per px`, `c = 1000 px` is 2.8 percent, `c = 50 px` is 0.14 percent. Negligible for full-frame photos; gate or warn when the photo's aspect or EXIF crop indicates a crop (the code already assumes "uncropped frame", `HeightOffset.kt:36`).

### E2 Annotator

- [ ] **C10 The 0.001 snap in `clamped()` can make Fit sticky during a slow pinch-out.** With `abs(scale - FIT_SCALE) <= 1e-3` (ADR-006 decision 1), `transformed()` derives `newScale` from the current, already snapped scale. A pinch whose per-event factor is within 0.999 to 1.001 re-snaps to 1.0 on every event and never leaves Fit; the floor made this harmless above Fit, but below Fit it is a detent the user feels. Event factors for a slow pinch are 0.997 to 0.999 per frame (1 px over a 300-800 px finger span), so the effect is real but small. Fix: accumulate the unsnapped scale in gesture state and snap only for `isFit` display and `toggledAt`, or drop the snap for scales below 1. Add a test with 200 events of factor 0.9995.

## 2. Re-check of the other iteration-2 edits

- **ADR-003 GRADIENT identifiability (focal-free claim): sound to first order.** For a plane `n . X = c` and image point `p = (x, y)` with focal `f`, the ray `lambda (x, y, f)` meets the plane at `lambda = c / (n_x x + n_y y + n_z f)`, so metres per pixel is proportional to `1 / (1 + g . p)` with `g = (n_x, n_y) / (n_z f)`. That is exactly the projective row of the stored homography (`[[w0,0,0],[0,w0,0],[gx,gy,1]]`), `|g| = tan(tau) / f`. It is measurable from the variation of known-length scale across the frame, with no focal length, and the parameters are scale plus a 2-vector (3 parameters, roll a gauge). Identifiability needs midpoints that are not collinear (the design `[1, mx, my]` must be full rank), which is what the position-spread gate checks. The only thing a missing `f` costs is the second-order anisotropy and the conversion of `g` to an angle (C8). A scale gradient can also come from radial distortion, from objects at different heights above the plane, or from a non-planar scene; the plan's out-of-model suite and LOO check address those, and no focal length can separate them.
- **Old builds and the gradient (the question asked): an old build can evaluate it.** `LensMeasurement.distanceMeters` requires `pixelsPerMeter` finite and positive, then, when a plane exists, applies the stored 9-number homography through `Homography.apply` (`LensMeasurement.kt:51-60`, `Homography.kt:19-26`; division by `w`, `null` only if `|w| < 1e-12`). A GRADIENT fit is a 3x3 matrix with a non-trivial third row, so it is evaluated correctly; `pixelsPerMeter` is only a validity gate in that branch. Both loaders accept `MANUAL_REFERENCE` (`ImageSidecarManager.kt:175`, `SqlDelightImageAnnotationRepository.kt:148`) and `usableScale` passes (`AnnotationEditorViewModel.kt:1217`). `PlaneCalibration` has no extra required fields beyond the existing four (`GeometryCalibration.kt:30-37`); ADR-003 supplies non-zero extents. The remaining requirement is a unit test that the stored matrix maps **undistorted native pixels** (conversion from the normalised, centre-origin fit frame), which ADR-003 decision 4 implies and Task 3.3a/3.3c should pin with the frozen-copy decoder.
- **ADR-007 (drag-measure gated to `viewScale >= FIT_SCALE`; systemGestures inset): consistent.** Aim-place at `AnnotationGestureLayer.kt:186-209` is unchanged for pending-point and all non-DISTANCE tools; the layered scale gate does not interact with the second-pointer hand-off. The inset API exists (section Resolved). Cost accepted by the plan (about 48-64 dp of width at Fit on gesture navigation) is an owner decision and listed as such.
- **ADR-006 `abs(scale - FIT_SCALE)`:** correct; see C10 for the detent side effect.
- **Task 1.3d / 1.4a wave order and the one-argument codemod:** order holds (C7 aside). The codemod claim is accurate (24 test files plus 1 production; fixtures at `GitSyncServiceTestFixtures.kt:52` and `GitSyncServiceJvmFixtures.kt:33` listed). One practical note: `GitSyncService` has about 20 defaulted parameters and several tests pass them by position; `sg` must add `gate =` as a named argument, and the codemod diff should be checked for any positional call.
