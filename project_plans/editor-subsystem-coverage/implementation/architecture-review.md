## Concerns
- [ ] Tech Debt Disposition / Story 1.2 — **Post-deletion, `ICommandSystem` and `ICommandRegistry` each have exactly one implementer and zero consumers.** VERIFIED: `grep ICommandSystem kmp/src` hits only `editor/Editor.kt:40` (a deleted file), `CommandSystem.kt:15` (sole implementer) and its own declaration. `ICommandRegistry` is implemented only by `CommandRegistry.kt:57`, and `CommandSystem(private val registry: CommandRegistry)` and `CommandManager.kt:25-26` both depend on the concrete class, so the interface is never used as a seam. The plan's disposition table does not mention either interface, so deletion silently creates two single-implementer interfaces that look like extension points but are not. Remediation (within item scope, no production change): add one Tech Debt Disposition row "Extend as-is, observation only" for both, and note in the final report that they are now vestigial and are a candidate for a separate follow-up; do not remove them here (constraint: no production change to `editor.commands`). This also affects the plan's Pattern Decisions: tests construct `CommandSystem(CommandRegistry())` against the concrete type, which is correct and should stay so, not be rewritten against the interface.
- [ ] Story 1.2 / Domain Glossary `LiveSlice` — **The surviving package name `editor.commands` is misleading after the `editor/` root is emptied.** Post-deletion `editor/` holds only `commands/`, so `editor.commands` no longer sits under an "editor" in any meaningful sense, and there is already a sibling top-level `kmp/.../stelekit/command/` (`Command.kt`, `BlockCommands.kt`, `UndoManager.kt`) that is the real palette/undo command model. Two near-identical package names (`command` vs `editor.commands`) with unrelated types (`Command` vs `EditorCommand`) is a standing confusion risk. Remediation: do not rename (it is a production/import change across `StelekitViewModel.kt` and `CommandManagerCoordinator.kt`, out of scope). Instead record the observation in the Tech Debt Disposition table as "Extend as-is (observation)" and add a one-line note to the final report so Tyler can decide on a rename item.
- [ ] Task 2.4a / ADR-001 — **Test package `dev.stapler.stelekit.editor` for the two keeper tests will have no main-source package of that name.** `LinkInsertionTest.kt` is `package dev.stapler.stelekit.editor`; after deletion no `editor` root types remain (root `Editor.kt`, `EditorModels.kt`, `IEditor.kt` are deleted). Harmless to compile, and the plan correctly keeps them, but the plan's AC-1 census rule ("second segments subset of `{commands, LinkInsertionTest, ImageAttachCallbackContractTest}`") is written as if those are importable packages; clarify the census is over `import` lines in files outside `editor/`, so the test files (which are in `businessTest/.../editor/`) are not miscounted. Low risk, wording only.
- [ ] ADR-001 vs requirements.md constraint — **Requirements say `commonTest`; the plan puts tests in `businessTest` and AC-3 text says "commonTest-reachable".** The ADR's reasoning (Bazel only runs `AllBusinessTests`; `commonTest` is not globbed) is consistent with CLAUDE.md's "pure logic belongs in commonMain/commonTest" only if read as "no platform API". The plan deviates from the CLAUDE.md placement rule (`commonTest` is the default home for tests touching only `commonMain`), and the ADR status is still `Proposed`. VERIFIED: `kmp/src/businessTest/kotlin/BUILD.bazel:75` globs `**/*.kt` for `business_tests`, so the deviation is justified. Remediation: flip the ADR to Accepted when implementation starts, and add a line to requirements.md AC-3 (or the verification notes) that "commonTest-reachable" was resolved to `businessTest` by ADR-001, so AC-3 is not read as unmet on placement alone. Registering in `AllBusinessTests` (Task 2.4a) with both import and `@Suite.SuiteClasses` entry, enforced by `AllBusinessTestsCompletenessTest`, is correct.
- [ ] Task 1.3a — **Detekt baseline edit list matches the file but the Task text omits two lines.** VERIFIED against `kmp/config/detekt/baseline.xml`: stale entries are lines 41, 46, 110, 111, 112, 121, 123, 131 (8 entries; line 103 `AnnotationEditorViewModel` and 7 `BlockEditor` entries are live).
