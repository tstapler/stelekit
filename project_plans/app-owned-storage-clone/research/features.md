# Research: Feature Landscape — app-owned-storage-clone

## 1. Industry comparables — how others expose "app-owned storage"

No competitor calls it "app-owned storage" in its UI. Each frames it as a *location* choice, not a storage-class label, and none of them proactively warn about uninstall data loss the way this project's requirements ask for — that's a gap this project would be first to close well.

| App | UI term for on-device-only | Warnings surfaced | Migrate-later flow |
|---|---|---|---|
| **Obsidian** | "On My iPhone/iPad" vs iCloud Drive vs Obsidian Sync | No warning at selection time; guidance instead focuses on not running two sync systems on one vault ([Switch to Obsidian Sync](https://obsidian.md/help/sync/switch)) | Manual, OS-level: move the vault folder in the iOS Files app, "then delete the old vault folder... " — no in-app verify-before-delete ([forum thread](https://forum.obsidian.md/t/obsidian-sync-location-of-vault-on-ios/38867)) |
| **Joplin** | No distinct label — "sync target" is filesystem/Nextcloud/S3/etc.; local-only is simply "no sync target set" | **Fail-safe**: blocks a sync operation that "is about to delete 100% of the data" unless the user explicitly overrides it ([GitHub #6025](https://github.com/laurent22/joplin/issues/6025)) — a real precedent for "verify before destructive action," worth reusing as a design pattern (a copy/move that looks like it would wipe more than it copies gets blocked, not silently trusted) | Plain settings change, no wizard — forum reports show this is risky in practice ("lost all notebooks" after changing sync target, [Joplin Forum](https://discourse.joplinapp.org/t/change-sync-target-lost-all-notebooks/20784)) |
| **Logseq** (this codebase's upstream) | No distinct label; user just picks a folder | None found | Not a guided feature |
| **Notesnook** | No local-only mode surfaced; sync-by-default with local encrypted copies | None found | Backup/restore exists but is not a relocation flow |
| **Standard Notes** | "Offline copy" (implicit, always present alongside sync) | None found | Encrypted backups can target an arbitrary folder — closer to a backup-target picker than relocation |

**Most load-bearing finding**: Logseq's own upstream issue tracker has a repeated, ongoing pattern of *total graph loss* tied directly to Android storage-location ambiguity — "Logseq folder (All data) removed after restarting my android mobile" ([GitHub #11488](https://github.com/logseq/logseq/issues/11488)), plus multiple independent "lost all my data" reports ([#10949](https://github.com/logseq/logseq/issues/10949), [#11443](https://github.com/logseq/logseq/issues/11443), [#11025](https://github.com/logseq/logseq/issues/11025)) and directory-choice friction with Downloads/SD-card folders ([#5937](https://github.com/logseq/logseq/issues/5937)) and SAF-scoped-access confusion ([#7585](https://github.com/logseq/logseq/issues/7585)). This is the single strongest piece of evidence that this exact user base (Logseq-migration users, many switching specifically because of Android reliability complaints) will punish any storage-location design that doesn't make backup/uninstall risk and folder-choice consequences explicit. The requirement's "verify-before-delete" and explicit uninstall-risk warning directly target this failure mode — the research confirms it's not hypothetical.

Design implication: adopt Joplin's fail-safe idea (block/require override when a check suggests data would be destroyed, not just trust a raw file count — this also directly serves the requirement's "path-encoding edge cases already caused a real bug" rabbit hole) and Obsidian's manual pattern (copy first, confirm, only then offer to delete source) rather than inventing a novel flow.

## 2. Android uninstall / storage-pressure risk for `filesDir`

Confirmed from the existing codebase's own comments, not just platform docs: `filesDir` already hosts, silently, for every graph:
- the SQLite DB + WAL/SHM (`AndroidLibsqlDriver.kt:38`)
- a read-only shadow markdown cache (`ShadowFileCache.kt` — "Read-only cache that mirrors SAF-backed markdown files to `filesDir`... Invariants: SAF is the only write target; shadow is a read cache derived from SAF")
- for most git-sync users (no `MANAGE_EXTERNAL_STORAGE`), a full JGit working tree at `filesDir/graphs/$id/gitshadow` (`GitShadowWorktree.kt`), currently documented as write-backed to SAF asynchronously

None of this is excluded from `Context.clearApplicationUserData()` or uninstall today (`filesDir` is always removed on uninstall; only `getExternalFilesDir()`-class storage and Auto Backup–eligible paths can survive, and this repo doesn't use those for the shadow tree). The requirement's framing is correct and the risk is real *today*, not just hypothetically once app-owned storage becomes primary — the only reason it hasn't caused visible data loss yet is that `filesDir` currently holds only a *cache* (SAF is authoritative). The moment app-owned storage is promoted to *primary* storage for a graph (per this project's explicit scope), uninstall becomes a genuine, first-time, total-data-loss vector for that graph, on par with the Logseq upstream incidents above. This must be a blocking warning at the point the user selects app-owned storage as primary (not a one-time tooltip), distinct in tone from SAF-folder storage, which survives uninstall by construction (SAF is a content:// grant into another app's/provider's storage, not `filesDir`).

No existing Android low-storage-pressure handling was found for the shadow cache/DB path itself; the only insufficient-space guard in the codebase is `AndroidGitRepository`'s `MIN_SHADOW_FREE_BYTES = 200L * 1024 * 1024` (200 MB) `StatFs`-based check before a git clone into `gitshadow` (`AndroidGitRepository.kt:112,799`, exercised by `AndroidGitRepositoryStorageGuardTest`). That check exists purely to fail fast before `Git.cloneRepository()` — it is not reusable as-is for a bulk markdown-only relocate (different operation, different failure point), but it is the direct precedent for "check available bytes before starting a large filesystem operation into `filesDir`," and its 200 MB constant/rationale comment is a good starting point for sizing the same guard on the new relocate-to-app-storage path.

## 3. Existing UI patterns to reuse for the move/relocate confirmation

Two directly reusable precedents already exist in `kmp/src/commonMain/.../ui/`:

- **Destructive-action confirmation** — `Sidebar.kt`'s graph-removal `AlertDialog` (~line 550): title, one-sentence consequence statement, red-colored destructive `TextButton` ("Remove", `MaterialTheme.colorScheme.error`) alongside a plain "Cancel" `TextButton`. Exact copy: `"Remove \"${graphToRemove?.displayName}\" from the graph list?\n\nThe graph files will not be deleted."` — note it already reassures the user about *what does not happen*, which is the right tone model for a relocate confirmation ("your files are not deleted until you confirm the copy is verified").
- **Multi-choice resolution dialog** — `DiskConflictDialog.kt`: a stacked-button `AlertDialog` offering several named resolution paths (Keep mine / Use disk / Save as new / Manual resolve) plus small-print consequence text under the riskiest option. This is the better template for the relocate flow specifically because relocate is not binary (confirm/cancel) — it needs to present "Relocate (move + delete source)" vs "Link (keep both, continuous mirror)" as distinct, clearly-differentiated choices, matching the requirement's explicit relocate-vs-link split.
- **Existing "move" entry point, already wired but primitive**: `Sidebar.kt`'s "Edit Graph" dialog (~line 577) already exposes `GraphManager.updateGraphPath()` through a bare `OutlinedTextField` for the path, with copy: `"Internal graph path. Changing this moves \"${editingGraph.displayName}\"'s database to a different location on this device."` — this is the mechanism this project should replace with the shared picker component, not a parallel one. Its result-handling `when` in `App.kt` (~line 1441, `UpdateGraphPathResult` sealed results: `Success`, `GraphNotFound`, `DemoGraphImmutable`, `PathNotFound`, `PathUnchanged`, `AlreadyTracked`, `DatabaseMoveFailed`) is a template for the richer result type a full relocate/link operation will need (it will need additional cases: insufficient space, verify-failed, interrupted/resumable, in-use/needs-unload).

No dedicated `project_plans/disk-conflict-dialog-ux/` findings were needed beyond confirming `DiskConflictDialog.kt` is the canonical multi-option pattern — it is already the reused precedent behind `web-local-folder-livesync`'s own conflict UX decision (see below).

## 4. Edge cases for the relocate operation

**Critical existing-code gap**: `GraphManager.updateGraphPath()` — the only relocate-like mechanism that exists today — does **not** move markdown files at all. It:
1. requires the destination directory to already exist and be non-empty-of-graph (`fileSystem.directoryExists(expandedNewPath)`, `GraphManager.kt:555`),
2. re-keys the graph's identity (`GraphId = sha256(canonicalPath)`) and *renames* the SQLite DB/WAL/SHM and telemetry DB via `fileSystem.renameFile()` (same-volume rename, not copy — `GraphManager.kt:600-618`, with WAL/SHM rollback on partial failure),
3. never touches the markdown files themselves — it assumes the user (or some other process) already relocated them.

For this project's "relocate between app storage and SAF/real-folder storage" requirement, this is necessarily a *different, new* operation — bulk file copy across possibly-different storage backends (SAF ↔ `filesDir` ↔ OPFS), not a same-volume rename. Confirmed by inspecting `FileSystem.kt` (the shared interface, `kmp/src/commonMain/.../platform/FileSystem.kt`): there is **no existing recursive-copy, checksum/verify, or resumable bulk-transfer primitive** anywhere in the codebase — only `renameFile` (single file, same volume) and per-file `readFile`/`writeFile`/`readFileBytes`/`writeFileBytes`. The relocate feature must design and build this primitive from scratch; it cannot be assembled from existing pieces beyond the DB-rekey half of `updateGraphPath`.

Specific edge cases, mapped to what already exists vs. what's missing:

- **Graph open/in-use during move**: `GraphManager.updateGraphPath()` already handles the "active graph" case by calling `switchGraph(newId)` after the DB rename, and cancels `activeGraphJobs` in `removeGraph()` — but this is DB-rekey-time, after files are assumed already moved. A markdown-bulk-copy relocate will take much longer (seconds to minutes for a large graph) and must decide whether to keep the graph "live" (read-only?) during copy or force an explicit unload step first — no existing precedent for a long-running foreground bulk operation while a graph's `RepositorySet`/`CoroutineScope` stays alive. Given "graph-scale reads must be paginated... never O(graph)" is already a hard codebase rule (per CLAUDE.md), the copy step itself must not hold the DB write actor or block Compose recomposition — model it as a distinct background operation with its own progress state, analogous to `FolderSyncSettings`' `ReconciliationUiState` (Connecting → Summary/Failed) rather than a synchronous suspend call.
- **Interrupted mid-copy** (app killed, tab closed, device rotated): no existing resumable-transfer or checkpoint mechanism in this codebase to model this on. The closest analog is `web-git-writeback`'s dirty-file tracking checkpoint (`.stele-dirty-set.json`, per `web-local-folder-livesync/requirements.md`) — worth reusing that pattern (a small on-disk manifest of "already copied" paths) so a resumed relocate can skip completed files rather than restart, and so a half-finished relocate is detectable and recoverable/abandonable on next launch rather than silently leaving two partial copies with neither marked authoritative.
- **Concurrent git-sync during a move**: directly named as a rabbit hole in requirements.md. `GitShadowFlushActor`/`GitWriteBackQueue` (Android) and the OPFS-to-git write-back path (`web-git-writeback`) both have in-flight async writers that must be paused or drained before a relocate touches `.git` — no existing "pause sync for maintenance" primitive was found; this needs new coordination, likely a mutex/flag the relocate operation acquires and the sync actors check before each write cycle.
- **Insufficient destination space**: Android has exactly one precedent (`MIN_SHADOW_FREE_BYTES` / `StatFs`, see §2) and it is git-clone-specific, not generalized. No `filesDir`-quota check exists for a plain markdown-graph copy. Web has **no `navigator.storage.estimate()` call anywhere in the codebase** (confirmed by search) — only `navigator.storage.persist()` is used (`HostDirectoryInterop.kt:222`, best-effort persistent-storage grant, unrelated to quota checking). A pre-flight `estimate()` call (`{usage, quota}`) before starting an OPFS-bound copy is new work, not a reuse of existing plumbing.
- **Path-encoding edge cases**: requirements.md correctly flags commit `e087959cb1` ("phantom conflict auto-resolve for underscore/encoded page titles") as prior evidence that filename encoding (underscore-escaping, URL-encoding of page titles) has already caused a real correctness bug in this codebase. Any "verify" step for copy-then-delete must compare by decoded logical page identity, not raw byte-for-byte filename match, or it risks the same class of false-negative/false-positive as that fixed bug.

## 5. Unstated user needs and existing team tone/copy precedent

- **Git users expect `git push`/`pull` to keep working after choosing app-owned storage.** This is implicit but real: the requirements explicitly note the Android git-shadow-worktree is *already* `filesDir`-backed for most users today (invisible plumbing) — so a user choosing "app-owned storage" explicitly for a git-cloned repo is, in effect, asking for what already silently happens for permission-constrained users. The design should confirm (in Phase 3 planning) that "promoting the shadow worktree from cache to primary" (requirements.md's own phrase) doesn't change any observable git behavior — same push/pull, same conflict UI (`ConflictResolutionScreen`/`JournalMergeReviewScreen`), same credential handling. No evidence in-code that this is already broken, but it's an explicit non-goal drift risk: don't let "storage relocation" quietly change git semantics.
- **Users likely expect to "graduate" from app storage to a real folder as a graph grows** — this is exactly Obsidian's and Standard Notes' unstated norm (start local/simple, move to synced storage later) and matches this project's own explicit in-scope "relocate" operation. The existing `updateGraphPath` UI copy already gestures at this ("Changing this moves... to a different location on this device") but undersells it as a niche "internal path" edit rather than a first-class supported growth path — worth promoting to equal visual weight with the initial storage choice, not buried in an "Edit Graph" advanced dialog.
- **Existing team tone/copy to reuse** (from `FolderSyncSettings.kt`, the most comparable existing storage-tradeoff UI):
  - Plain, concrete, non-jargon: *"This graph is stored in your browser only. You can connect it to a folder on your computer so edits made here are written straight to your files — no export, no git required."*
  - Explicit "nothing is lost" reassurance stated *before* the action button, called out in-code as "Load-bearing reassurance copy... must be shown verbatim, before the button is ever clicked, and must never be cut for space": *"Existing edits in this graph are kept — nothing is overwritten when you connect."*
  - This is the tone bar for the new app-owned-storage warnings and relocate confirmations: state the tradeoff plainly, put the reassurance/risk statement before the point of no return, and treat it as non-negotiable copy (not a nice-to-have) when it addresses a previously-real data-loss finding — exactly analogous to how this project's uninstall-risk warning should be treated as load-bearing, not optional microcopy.
- **Web's "link can silently break" risk is already named in requirements.md and has direct precedent**: `web-local-folder-livesync/requirements.md` documents that File System Access API directory-handle permissions are session-scoped and the accepted UX (already shipped for git's session-scoped PAT in `web-git-writeback`) is a one-click "resume access" re-grant per session — not silent, not blocking. This project's "link" operation (continuous mirror) should reuse that exact accepted pattern rather than re-litigating it, and should surface the same `HostAccessState`-driven UI (`FolderSyncSettings.kt` already models `NotApplicable`/`Granted` states) for a broken/needs-re-grant link.
