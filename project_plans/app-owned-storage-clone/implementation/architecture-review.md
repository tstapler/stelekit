# Architecture Review: app-owned-storage-clone
**Date**: 2026-09-12
**Verdict**: CONCERNS

## Constitution Violations
- None — no `docs/adr/ADR-000-architecture-constitution.md` found in the repository (confirmed via directory listing; `docs/adr/` still contains no ADR-000/constitution file).

## Blockers

None. Both prior blockers are resolved, verified against the actual plan.md text (not the repair summary):

- **Former Blocker 1 (`GraphRelocationCoordinator` calling Android-only types in `commonMain`) — RESOLVED.** Story 3.1.3 defines `interface GraphMoveQuiesceStrategy { quiesce, release, releaseSourceGrant }` in `commonMain` (Task 3.1.3a), with `AndroidGraphMoveQuiesceStrategy` (`androidMain`, wraps `GitWorktreeLocks`/`GitSyncBusyCounter`/`GitWriteBackQueue`) and `WasmJsGraphMoveQuiesceStrategy` (`wasmJsMain`, initial no-op, extended by Story 3.3.2) as the two implementations, plus a `FakeGraphMoveQuiesceStrategy` businessTest double with a configurable never-completes mode (Task 3.1.3d). Story 3.1.5's `GraphRelocationCoordinator(quiesceStrategy: GraphMoveQuiesceStrategy)` in `commonMain` references only the interface — no Android-only type appears in its Files list or acceptance criteria. Tasks 3.1.5d/e/f (`businessTest`) inject the fake, resolving the original "breaks its own businessTest plan" objection.
- **Former Blocker 2 (Tasks growing `GraphManager.kt`'s hotspot functions in place) — RESOLVED.** Story 3.1.4 extracts `moveGraphFilesAndCredentials`'s rename-with-rollback logic into a standalone `AtomicFileRelocationStep` (Extract Method), with an explicit acceptance criterion that the function's own line count must be "equal or smaller... not larger" after the change, and `updateGraphPath()` is now stated as "left untouched" entirely (the coordinator does its own sequencing rather than modifying it). Task 1.1.3f adds one narrow `onGraphLocationDetermined(graphId, location)` seam plus an optional `location` parameter on `addGraph()`; the renumbered Tasks 2.2.1c/2.2.2c/2.3.1c/2.3.2b each now explicitly state "No `GraphManager.kt` edit here" and call only the existing `addGraph(..., location = ...)` parameter. This matches the Tech Debt Disposition's "Isolate via seam" choice instead of compounding it.

## Concerns

- [ ] **Story 3.1.5 — coordinator steps (3) "close the DB driver" and (7) "reopen driver and `switchGraph()`" have no corresponding `GraphManager` seam, and the one public method that does both (`switchGraph()`) has a guard that defeats this exact use** — Verified against the real `GraphManager.kt`: `switchGraph(id)` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/db/GraphManager.kt:670-687`) is the only public method that closes-then-reopens a driver, but its own idempotency guard (`if (currentGraphId == id && (_activeRepositorySet.value != null || activeGraphJobs.containsKey(id))) return`) explicitly *skips* re-initialization when switching to the graph that is already active — exactly the case a relocate needs (close driver for the graph you're currently in, then reopen the same graph id at its new location). `tearDownActiveGraphResources()` (the actual close step `switchGraph` calls) is `private`. Story 3.1.5's Files list contains only `GraphRelocationCoordinator.kt` (new) — no `GraphManager.kt` entry — yet as written the coordinator cannot perform steps 3/7 through any existing public API. Left as-is, an implementer will either add ad hoc new public methods to `GraphManager.kt` undocumented by this plan (quietly re-growing the exact hotspot file Blocker 2's fix was designed to avoid touching further) or hack around the guard. **Recommendation**: add a second narrow seam analogous to `onGraphLocationDetermined` — e.g. `closeDriverForRelocate(graphId)` / `reopenAfterRelocate(graphId)`, explicitly bypassing the same-graph-id guard — call it out in Story 3.1.5's Files list and add a task for it now rather than leaving it to be improvised during implementation.

- [ ] **Story 3.1.5's `quiesceStrategy` instantiation description contradicts Story 3.1.3's own type declaration** — Story 3.1.5 states `quiesceStrategy` "is instantiated... via a uniform no-arg constructor call from commonMain (mirroring `DriverFactory()`'s expect/actual-constructor convention)." But Task 3.1.3a declares `GraphMoveQuiesceStrategy` as a plain `interface` (not an `expect class`), and its platform implementations are differently-named concrete classes (`AndroidGraphMoveQuiesceStrategy`, `WasmJsGraphMoveQuiesceStrategy`) rather than `actual` implementations sharing one name. An interface has no constructor `commonMain` can call directly, and this repo's real `DriverFactory` precedent (`expect class DriverFactory()` in `kmp/src/commonMain/kotlin/dev/stapler/stelekit/db/DriverFactory.kt:8`, with identically-named `actual class DriverFactory actual constructor()` per platform) requires same-name expect/actual, which this design does not use. No task specifies where/how `GraphRelocationCoordinator(strategy)` is actually constructed on each platform. This does not block compilation of the core Strategy-pattern fix (ordinary per-platform constructor injection at a composition root works fine and doesn't need expect/actual at all), but the plan's own prose describes a mechanism that cannot work as written and should be corrected, and the missing "who constructs the coordinator" task should be added so this isn't improvised per-platform inconsistently.

- [ ] **Concern (from prior review), partially addressed — `storage_locations` table vs. `GraphInfo.path` still lacks a stated authoritative-field rule or transactional guarantee** — ADR-001's new addendum adds a real, useful invariant: `StorageLocationResolver` derives a location once and persists it via `onGraphLocationDetermined` "before anything reads it as a source... every consumer still only ever reads a value that came from the table" — this closes the specific risk of a caller inferring a location ad hoc at point of use. It does **not** address the two more specific asks from the original finding: (1) no statement of which of `GraphInfo.path` / `storage_locations.kind` is authoritative when they could disagree (e.g. what `GraphInfo.path` contains for an `AppOwned` graph), and (2) no transactional guarantee or documented recovery rule for the registry-save vs. `storage_locations`-upsert pair — Task 1.1.3f invokes `onGraphLocationDetermined` only "near" `addGraph()`'s registry-save point, not stated as atomic with it, and `GraphRelocationCoordinator`'s own post-relocate call to it (step 6) has no stated behavior if it fails after files have already moved. The plan's own "absence = not `AppOwned`" fail-safe default (ADR-001/ADR-002) mitigates the *missing-row* case, but not a *disagreeing* row. **Recommendation**: state explicitly in ADR-001 which field is authoritative for path resolution, and add one sentence to Task 1.1.3f / Story 3.1.5 documenting what happens if the registry write and the `storage_locations` write disagree after a partial failure (e.g., "on next read, a `storage_locations` row that names a destination different from `GraphInfo.path` is treated as an incomplete relocate and re-surfaces the staging-sweep/retry path," or similar).

- [ ] **Unaddressed — `StorageMoveOperation` still has no smart constructor; illegal states remain constructible** — Confirmed unchanged in Story 1.1.1: `Relocate`/`Link` are still plain data classes with public constructors; nothing prevents `source == destination`, `graphId` mismatched against `source.graphId`/`destination.graphId`, or (per the next item) a `Link` targeting a plain Android graph. No `DomainError.StorageError` leaf exists for this class of invalid construction, and no `create(...): Either<DomainError.StorageError, StorageMoveOperation>` factory was added anywhere in the plan. **Recommendation** (unchanged from prior review): add a smart constructor validating `graphId` consistency and `source != destination`, with a new `DomainError.StorageError.InvalidMoveOperation` leaf, per `type-driven-design`'s "parse, don't validate."

- [ ] **Unaddressed — Android plain-graph `Link` restriction (ADR-003) still enforced only in the UI layer** — Confirmed unchanged: Task 4.2.1a is still "Disable/hide 'Link' in `StorageMoveChoiceDialog` for plain Android graphs" — a presentation-layer check only. `StorageMoveOperation.Link` itself still carries no information distinguishing a git-cloned graph from a plain one, and `GraphRelocationCoordinator`/`AndroidGraphMoveQuiesceStrategy` have no domain-level guard rejecting this combination if reached through any path other than this one dialog. **Recommendation** (unchanged): add a coordinator-level precondition (or fold into the smart-constructor above) that rejects `Link` for a plain Android graph with a domain error.

- [ ] **Unaddressed — Task 1.1.1c's exhaustiveness check still uses JVM-reflection `sealedSubclasses` in shared `commonTest`** — Confirmed unchanged: "assert `StorageLocation::class.sealedSubclasses.size == 4`" is still the specified mechanism, still placed in `commonTest` (shared by `jvmTest`/`androidUnitTest`/`wasmJsTest` per this repo's testing conventions), still reflection-backed and not reliably supported on Kotlin/JS. **Recommendation** (unchanged): replace with a local `when (loc: StorageLocation)` with no `else` branch, which fails to *compile* (not run) on any KMP target the moment a leaf is added without updating the test.

## Nitpicks
- `StorageLocation.SafFolder.treeUri`, `DirectAccessFolder.realPath`, and `HostFolder.displayName` remain raw `String` fields rather than newtypes — unchanged from prior review, still not blocking, still the primitive-obsession shape `type-driven-design` flags.
- `storage_locations`'s `tree_uri`/`real_path`/`display_name` columns are still all nullable with no `CHECK` constraint enforcing "exactly one populated per `kind`" — unchanged from prior review.
- Dependency Visualization lists Story 3.1.4 (`AtomicFileRelocationStep` extraction) as needing "3.1's copy step," but the extraction is a refactor of `moveGraphFilesAndCredentials`'s existing rename logic and has no real dependency on `BulkCopyVerifier` (Story 3.1.1) — the two could run in parallel. Not a correctness issue, just an overly conservative/imprecise sequencing note worth tightening.
