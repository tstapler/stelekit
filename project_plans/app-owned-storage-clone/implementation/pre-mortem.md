# Pre-mortem: app-owned-storage-clone
**Date**: 2026-09-12

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Appetite runs out after Phase 2 (the "usable slice"). Web users who picked "App storage" for a plain graph now have **no way out**: Phase 2's own design (ADR-003) explicitly drops zip-export for Web, and the only escape hatch — relocate/link — is Phase 3/4, which never ships. This makes the app strictly worse for those users than before the project, when OPFS was only a rare auto-fallback, not an actively-promoted peer choice. | A Web plain graph created in "App storage" cannot be extracted via any in-app action; the only way out is browser devtools OPFS inspection, or the browser purging site data deletes it outright. | Move a minimal Web export affordance (download-as-zip/folder) into Phase 2 itself, as a prerequisite of Story 2.3.3's warning dialog, rather than deferring any move-out path to Phase 3/4 — so the "usable slice" is actually safe to ship standalone, per requirements.md's own Success Metric that a move-out path exists. | P1 |
| 2 | The coordinator's cleanup guarantees (driver reopen, flag clear) run via a coroutine `finally`/`NonCancellable` block, which never executes on real Android process death (OS reclaiming memory while backgrounded during a multi-minute SAF copy of a large graph) — not just coroutine cancellation, which is all the plan's tests cover. A death after Step 5 (files already moved to final destination) but before Step 7 (repoint) leaves a fully-copied, unreferenced duplicate at the destination forever, with `storage_locations` still pointing at the source — and a retried relocate creates yet another duplicate. | Unexplained storage consumption, or a full duplicate graph copy discovered at the destination folder that the app never references, after a relocate that appeared to silently do nothing. | Add a post-staging orphan sweep (distinct from the existing pre-staging `RelocationStagingDirectory` sweep) that detects a destination fully populated but unreflected in `storage_locations`, and resumes the repoint or offers cleanup on next app start. | P2 |
| 3 | `BulkCopyVerifier` has no time bound on the copy+verify phase itself — only `QUIESCE_TIMEOUT_MS` bounds the quiesce step. A graph with large binary assets (images/PDFs in Logseq's `assets/` folder) on a slow or cloud-backed SAF `DocumentsProvider` (Google Drive/OneDrive-backed folders are a common real-world SAF choice) could run relocate for tens of minutes with the DB driver closed and `activeRepositorySet` null the whole time (per the architecture review's already-flagged UI-blanking concern), with no cancel affordance. | The app appears frozen far longer than the markdown-only 8,000-page benchmark implies; the user force-quits mid-operation, triggering failure mode #2. | Benchmark relocate against a graph with realistic binary-asset sizes (not just markdown file count), and add a real cancel affordance plus a user-facing time estimate during `Copying`/`Verifying`. | P2 |
| 4 | Every planned test for relocate/link is a `businessTest`/Robolectric/`wasmJsTest` fake or synthetic fixture. No task requires running an actual relocate against a real Android device with a real (especially cloud-backed) SAF folder — a class of provider known to diverge from Robolectric's `ContentResolver` shadows on tree-traversal performance, permission-revocation timing, and error codes — before this touches the developer's own non-recreatable graph. | A relocate that passed all automated tests hangs, fails, or corrupts data the first time it runs against a real device and a real graph — exactly the scenario requirements.md's "no dedicated QA" constraint has no other safety net for. | Add an explicit manual-verification checklist item (not just automated tests) requiring a dry-run of both "Relocate" and "Link" against the developer's own real graph on a real device with a real SAF folder before Phase 3 is considered done, matching requirements.md's own stated verification method. | P2 |
| 5 | The new `storage_locations` SQLDelight table requires the mandatory regenerate-and-rsync codegen step this repo's own CLAUDE.md flags as a known footgun ("forgetting this step causes unresolved reference errors in Bazel CI even though Gradle builds succeed"). Across 115 tasks and a multi-week solo effort, it's plausible this is missed on a later `.sq` edit (e.g., a Phase 3 query tweak) and drift is committed, or hand-patched to unblock CI and then silently reverted by the next real codegen run. | Bazel CI fails with unresolved-reference errors on a PR that built fine under Gradle, or a hand-patched fix silently disappears after an unrelated `.sq` change. | Treat the regenerate+rsync step as its own checklist item on every task touching `SteleDatabase.sq` (not just Task 1.1.3b), and confirm the existing "SQLDelight generated sources" CI job actually diffs committed output against fresh codegen. | P3 |

## P1 Items (address before implementation)
- [x] Failure #1 — Add a minimal Web export/download affordance to Phase 2 (Epic 2.3 / Story 2.3.3) as a required prerequisite for shipping the "App storage" option for plain graphs on Web, so a Phase-2-only release leaves no user with data they cannot get out of the app. **Resolved**: Story 2.3.3 now includes Tasks 2.3.3c-e (hand-rolled stored-ZIP writer + `WasmJsShareProvider` binary download + round-trip test), marked as a Phase-2 blocking task; ADR-003 amended to reverse its original "Web gets warning copy only" decision.
