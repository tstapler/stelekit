## Concerns
- [ ] **Task 2.1.2d (`CloneDepthState` enum + `shallowDepth: Int?`) — illegal states are representable.** The domain glossary defines `CloneDepthState` as a plain 3-value `enum class` plus an *independent* nullable `GitConfig.shallowDepth: Int?` field, persisted as two independent SQL columns (`clone_depth_state TEXT`, `shallow_depth INTEGER`). Nothing stops `NONE` with a non-null `shallowDepth`, `FULL_HISTORY` with a stale `shallowDepth = 50` still lying around, or `SHALLOW` with `shallowDepth = null`. This is exactly the primitive-obsession/illegal-state pattern the `type-driven-design` skill flags, and the codebase's own `GitAuth` sealed class three lines above `GitConfig` in the same file family (`SshKey`/`HttpsToken` carry their own data, `None` carries none) already establishes the idiom this plan doesn't reuse. It also weakens the compile-time safety this plan is trying to buy: an `enum class` used in a `when` *statement* (not expression) compiles fine with missing branches — a `sealed interface CloneDepthState { data object None; data class Shallow(val depth: Int); data object FullHistory }` would force exhaustive handling at every call site and make "shallow but depth unknown" unconstructible. Remediation: model as a sealed type with depth embedded only in the `Shallow` variant; at the SQL boundary, parse the two raw columns into the sealed type with a fail-closed default (e.g., `shallow_depth` present but `clone_depth_state='NONE'` → log and treat as `None`), and never let `shallow_depth` outlive a transition out of `Shallow`. Story 2.1.4 (unshallow) should explicitly null out `shallow_depth` on the `FULL_HISTORY` write for the same reason.
- [ ] **`GitTransportRetryState`/`CloneDepthState`/`GitCloneWorkerLauncher` additions to `dev.stapler.stelekit.git` — deepens an already-flagged coupling violation.** `kibitzer run kmp/src/commonMain/kotlin/dev/stapler/stelekit/git --trigger batch` (run live against this checkout) reports: `[coupling] dev/stapler/stelekit/git imports 24 distinct packages (over 10) — consider splitting its responsibilities` and `[coupling] dev/stapler/stelekit/git/model is imported by 24 distinct packages (over 10) — changes to it have a wide blast radius`. This is exactly the "component-deps/layering finding already present on a package" scenario the review brief calls a bad "Extend as-is" candidate. The plan's Tech Debt Disposition table addresses `AndroidGitRepository.kt`/`JvmGitRepository.kt` (different source sets, correctly "Extend as-is" per their own decomposition) but says nothing about this flat `commonMain/git` package's pre-existing coupling problem — and then adds to it anyway: a new `GitTransportRetryState.kt`, a new `GitCloneWorkerLauncher.kt` interface, a new `CloneDepthState` type, and two new `GitConfig` fields, all landing flat in the already-over-threshold package/model files. Remediation: add a disposition-table row for this pre-existing coupling finding (Isolate via seam is cheap here — this plan already has a natural seam) and place the new retry/resume-specific types in a new `dev.stapler.stelekit.git.resilience` subpackage, mirroring the existing `git/merge/` subpackage precedent, rather than flat into `git/`.
- [ ] **Task 2.1.2e — two independent, hand-duplicated `Git_config → GitConfig` mappers must be kept in sync by hand.** `SqlDelightGitConfigRepository.toModel()` and `WorkManagerSyncScheduler.toGitConfig()` (`kmp/src/androidMain/kotlin/dev/stapler/stelekit/git/WorkManagerSyncScheduler.kt:171`) are two separately-written copies of the same row→model mapping — confirmed by reading both. The plan correctly identifies both call sites and updates both (good — this avoids a silent gap), but perpetuates the underlying duplication rather than fixing it, which is exactly the case the `code-architecture-best-practices` skill's Reuse Check exists to catch: "the canonical failure mode... copy-pasted across sibling functions, each with its own chance to get it wrong." A third field added later (by someone who finds only one of the two mappers) reintroduces the exact bug class Story 2.1.2 exists to avoid. Not blocking this project, but worth a one-line disposition ("Isolate via seam: extract one shared `Git_config.toModel()` extension both files call") rather than silently doubling the duplication.
