# Pre-mortem: git-sync-resilience
**Date**: 2026-09-23

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `GitCloneWorker`'s `setForeground(dataSync)` ships without ever running on a real device/emulator — no Android device was available during requirements/research (requirements.md's own Feasibility Risk) and Phase 3's only test coverage is Robolectric (Tasks 3.1.2f, 3.1.6b/c). Real OEM battery managers (Xiaomi, Samsung, Huawei, OnePlus, Asus) kill network/CPU for a "foreground" service that isn't on their allowlist regardless of `setForeground()`/notification correctness — this is a distinct mechanism from Doze that a correctly-coded foreground service does not defeat. The project ships the *appearance* of a fix (correct manifest, correct notification, correct `Result.failure()` semantics) while the underlying OS/OEM kill still happens, just now hidden behind a "syncing" notification that goes stale instead of an immediate error. | A user on an affected OEM device reports the exact original bug — clone/sync silently stops progressing after backgrounding — but now there is no error at all: the notification sits at some stale progress percentage indefinitely (WorkManager's process was killed, so `onStopped()`/the `catch(Throwable)` teardown never runs) instead of surfacing "Software caused connection abort." | Add a hard release gate to `validation.md` for Phase 3: manual test on ≥2 real OEM devices (e.g. one Samsung, one Xiaomi/Huawei) with screen off / app backgrounded for a multi-minute transfer, confirmed via `dumpsys` or a completed sync that the transfer actually finished — CI/Robolectric green is explicitly insufficient to mark Phase 3 "done." Also add a wall-clock watchdog (a scheduled follow-up check, e.g. via the already-scheduled periodic `GitSyncWorker`) that detects a `GitCloneWorker` whose `WorkInfo` has been stuck `RUNNING` past a threshold and surfaces "Sync may have been stopped by battery optimization — check your device's battery settings for SteleKit" — the one failure mode with no thrown exception to classify at all. | P1 |
| 2 | The shallow-history merge-base guard (Story 2.1.5) only detects an *absent* merge base, not a *wrong-but-present* one — JGit's own documented caveat (cited in `research/pitfalls.md` §2.3, echoed in the adversarial review) is that shallow-history merge-base computation "cannot be counted on to work as expected," implying `RevWalk` can return a spurious ancestor rather than cleanly failing. Compounded by `CloneDepthState`/`shallowDepth` being two independently-settable columns (architecture review concern) with no invariant enforcing they stay consistent, diagnosis of *which* graphs are at risk from local `git_config` state is unreliable. | A user's shallow-cloned graph merges cleanly (no error shown) after the remote has diverged past what the local shallow history actually covers — no crash, no warning — and inconsistent/duplicate content or a wrong-ancestor merge commit shows up in the wiki later, discovered only by the user noticing corrupted notes, with no log entry pointing at the cause since the merge "succeeded." | Extend Task 2.1.5b's guard beyond "no merge base found" to validate the found merge-base commit is not itself sitting at or past the shallow boundary (e.g. reject if the merge-base commit's parents aren't all present in the local object database, not just the commit itself). Extend Task 2.1.5d's regression test to construct a "wrong-but-present" merge-base fixture, not only the "absent" case. Separately, adopt the architecture review's sealed-type remediation for `CloneDepthState` (embed `shallowDepth` only in a `Shallow` variant) so state used for UX/diagnosis can't silently drift from the JGit-level truth Task 2.1.5b actually reads. | P1 |
| 3 | The 93-task, Large (3-6 week) appetite ships Phase 1-2 only (exception-taxonomy fix + shallow clone) — each phase is explicitly designed as "independently shippable" and Phase 1 alone already fixes the reported bug's *visible symptom* (the wrong "auth failed" message). Once the error message looks correct and clones are faster (shallow), the project reads as resolved from the outside, and Phase 3 (the actual Android backgrounding-survival fix the original bug report needed — a clone failing because the user locked their screen) quietly slips, deprioritized behind other work, without anyone re-opening the original ticket to check whether *that* specific scenario was ever fixed. | The original bug reporter (or someone with the same repro) re-tests by backgrounding the app during a large clone on Android weeks after "git-sync-resilience" is marked shipped, and hits the same stall/failure — while the team's records show the project as complete because Phase 1-2's regression tests are green. | Explicitly record in `plan.md`/`validation.md` that Phases 1-2 do **not** close the original bug report — the reporter's literal repro (backgrounded app, screen-locked, mid-transfer) is a Phase 3+4 fix, not a Phase 1-2 one. Gate the originating issue/backlog item's closure on Phase 3's real-device validation (Failure Mode 1's prevention) landing, not on Phase 1-2 merging, so "done" for this project requires the OS-kill scenario specifically re-tested, not just inferred from unit tests. | P1 |
| 4 | `classifyGitFailure`'s taxonomy (Task 1.1.1b) was built from generic JGit/JDK exception research, not from exception shapes actually observed on the OEM devices most affected by network/battery throttling. An OEM-specific exception (e.g. a vendor-patched Android networking stack throwing something other than `SocketException`/`SocketTimeoutException`/`UnknownHostException`/`EOFException` in the cause chain) falls into the fail-closed "everything else → Permanent" bucket. This is the safe *direction* (no infinite-retry battery drain) but means the exact population the bug report came from may still get zero retry benefit while the classifier's test suite reports 100% coverage of the *documented* taxonomy. | Local logs (per the Observability Plan) show a clone/fetch failing after exactly one attempt with a `Permanent` classification for an exception type/message that doesn't match any documented taxonomy row, on a device/OEM known for aggressive battery management — i.e., today's exact bug, unfixed, for that user, despite the project having shipped. | Since this can't be fully closed before real-world exposure, make it an explicit fast-follow rather than an implicit assumption: add a task to `plan.md`'s Unresolved Questions (or a tracked follow-up) to review early production/beta logs specifically for `Permanent`-classified failures with unrecognized exception shapes within N weeks of release, and extend `classifyGitFailure`'s taxonomy from that real data rather than treating Task 1.1.1b's table as final. | P2 |
| 5 | Disk-full (`IOException`/ENOSPC) during a clone has no explicit branch in `classifyGitFailure` (adversarial review concern, unaddressed in the current plan) — it falls into the fail-closed "Permanent" bucket, so it is correctly never retried, but Story 2.1.3's directory cleanup (`beforeRetry`) only runs ahead of an *automatic retry*, which a Permanent classification never triggers. The user is left with a partially-written target directory on an already-full disk. | A user on a space-constrained device (exactly the population most likely to hit ENOSPC on this project's own reference "large graph" scale) gets a clone failure, taps "Try again," and gets the identical failure every time — no automatic or app-driven cleanup ever runs, and there's no in-app path to recover without manually deleting files outside the app. | Add an explicit `IOException`/ENOSPC branch to `classifyGitFailure` that maps to (or wraps) the existing `DomainError.StorageError.InsufficientSpace`, and extend the cleanup logic so a disk-full *Permanent* failure on clone also triggers the same partial-directory cleanup Story 2.1.3 only wires ahead of a retry today — cleanup should be keyed to "was this a clone that left a partial target directory," not "is another attempt about to happen." | P2 |

## P1 Items (address before implementation)
- [ ] Failure #1 — Add a real-device (≥2 OEMs) manual validation gate for Phase 3 to `validation.md`; do not let CI/Robolectric-only signal mark `GitCloneWorker`'s foreground survival as verified. Add a stuck-`WorkInfo` watchdog + user-facing "battery optimization may have stopped sync" message for the silent-kill case that has no exception to classify.
- [ ] Failure #2 — Strengthen Task 2.1.5b to reject a "wrong-but-present" merge base (not just an absent one), add the corresponding fixture to Task 2.1.5d, and adopt the architecture review's sealed `CloneDepthState` remediation so diagnosis state can't drift from JGit's actual shallow-boundary truth.
- [ ] Failure #3 — Record explicitly in `plan.md`/`validation.md` that Phases 1-2 do not close the original bug report (which requires the Phase 3 backgrounding scenario specifically), and gate the originating issue's closure on Phase 3's real-device validation, not on Phase 1-2 merging.

## Summary
3 P1, 2 P2, 0 P3.

Top failure mode: Phase 3's Android foreground-service survival — the part of this project that most directly answers the original bug report — is architected and coded but never validated against real OEM Doze/battery-manager behavior (no device was available during research), so the project can ship "green" while the exact backgrounding failure the user reported is still unfixed, now hidden behind a stale notification instead of a visible error.
