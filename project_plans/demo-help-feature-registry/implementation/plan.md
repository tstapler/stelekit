## 1. Design summary (see ADRs for rationale)

- **Hybrid registry (ADR-001, ADR-002).** Obligations are *derived* from existing sources of truth through explicit candidate lists cross-checked by `getPermittedSubclasses` (no kotlin-reflect; registry in jvmMain, Amendment A-3). Feature rows are *declared* as typed Kotlin data, one file per area, so parallel worktrees rarely collide.
- **Two axes, different strictness (ADR-003).**
  - Axis 1, registration integrity: candidate has an entry or a valid exemption; entry covers a real candidate; exemptions have reason enum + owner + unexpired date; ids unique. Because the migration story registers all 15 + 13 + 24 existing candidates up front, "entry points at nothing", "bad exemption" and "duplicate id" can be hard failures from day one. "Candidate has no entry" is warn-only in Phase A and hard from Phase B.
  - Axis 2, content coverage and quality: `demoPage`/`sitePage` exist, are non-empty, parse, wikilinks resolve. Warn-only with a shrink-only baseline in Phase A, new-code enforcement in Phase B, ratchet in Phase C.
- **Where it runs.** Structural + content checks live in `businessTest` (Bazel PR gate + Gradle), registered in `AllBusinessTests.kt`. Git-diff staleness, id-baseline ratchet and DemoFileSystem drift are CI jobs. Detekt `MissingHelpPageAnnotationRule` stays until the registry test has covered Screens on both runners (Story B3.1).
- **Content strategy.** Two hand-written copies (demo, site) linked by registry rows; no demo-to-site generator (`research/architecture.md` section 3). Generated exception: keyboard-shortcuts page from `ShortcutTable` (Story C2.1).

Critical path in agent waves:
1. Wave 0 (parallel, 3 agents): S0.1, S0.2, S0.3.
2. Wave 1 (serial, 1 agent): A1.1 (model, candidates, rows, test, mutation proof, baseline; shared files `AllBusinessTests.kt`, `business_tests` BUILD). Agent-wave depth is about 5 for Phase A; calendar is set by W1/W2 (traffic-dependent) and D1-D4 (owner), not by agent runs.
