## Blockers

- [ ] **B1. "Green on the Gradle runner" is a promotion and deletion precondition, but no CI job ever runs Gradle jvmTest or businessTest.** `ci.yml` runs only `testDebugUnitTest`, detekt, wasm and sqldelight jobs (VERIFIED, grep of `gradlew` in `ci.yml`). `checkDocCoverage` is referenced by no workflow. Plan exit criteria ("registry test green on Gradle and Bazel for the last 10 main commits (read from Actions history)", the A-to-B criterion) and B3.1's precondition ("green on Gradle and Bazel on main") cannot be evidenced for Gradle. A1.3 also deletes the only Gradle-side Screen tests, which ran locally via `ciCheck`. Recommendation: either add a Gradle CI step (`./gradlew :kmp:jvmTest --tests '*registry*'`, which needs no X11 for businessTest classes), or restate every criterion as "Bazel `business_tests` green on main" plus a local Gradle run recorded in the PR, and say so in ADR-003.

- [ ] **B2. Success metric "a new git-sync state / shortcut with no declared coverage produces a warning" is not delivered by the design.** ADR-002 item 4 rolls all `SyncState` members into one candidate `sync:*`. A new state is therefore silently covered, and the only signal is an exhaustive-`when` compile error that never mentions docs. ADR-002 item 5 excludes `ShortcutTable` from derivation, and the plan generates only a site page for it (C2.1). Requirements were not amended and the plan never states the deviation. Recommendation: either amend requirements/ADR-003 to say "SyncState and shortcuts are guarded by compile-time `when` and `ShortcutTableConsistencyTest`, not by registry warnings", or add a `shortcut:*` candidate set and per-state sync candidates with roll-up `covers`.

## Concerns

- [ ] **C1. Phase A "warn-only" contradicts the compile-time gate, and the B1.2 proof cannot work as written.** T-A1.1.2 makes the `Screen` id function an exhaustive `when` in production commonMain. Adding a 16th `Screen` fails compilation of the whole app in Phase A. That is a hard failure with a Kotlin error, not the registry message. B1.2.2's proof ("a scratch PR adding a 16th Screen fails business_tests with the message from T-A1.1.4") would observe a compile error instead, so the message-quality guarantee (A5.1.3) is moot for Screens and SyncState. It also couples the app build to docs bookkeeping. Recommendation: choose one. Either keep the `when` and document that R1 for Screen/SyncState is compile-time from day one (and put a pointer to the registry file in a comment on the `when`), or drop the `when` and rely on the S0.1 `getPermittedSubclasses` cross-check so the failure carries the actionable message.

- [ ] **C2. Bazel package boundary: the planned root `filegroup` cannot reference `kmp/config/docs/*.txt`.** T-A1.2.1 and A2.1.2 put filegroups in the root `BUILD.bazel` that list `kmp/config/docs/...`. `kmp/BUILD.bazel` exists (VERIFIED), `kmp/config/` has no BUILD file, so those files belong to package `//kmp`. A root-package label would fail with "crosses package boundary". Existing idiom works only for `docs/journeys` and `project_plans`, which are root-package. Recommendation: put the baselines under a root-package dir (for example `docs/registry/`) or add `exports_files` in `kmp/BUILD.bazel` and reference `//kmp:config/docs/...`. Update A1.2.1, A2.1.2 and A3.2.2.

- [ ] **C3. The registry lives in `docs/`, which is Bazel Tier 1 (`tier_manifest.bzl` TIER_1_PACKAGES includes `docs`) but imports `ui`, `editor`, `git`.** `Screen` in `ui/` already imports `docs` (annotations), so `docs` is intended as a lower-tier leaf. Putting `FeatureCandidates` (imports `ui.Screen`, `SettingsCategory`, `EssentialCommands`) in `docs/registry/` creates a `docs` to `ui` back-edge. It would be a dependency cycle when `docs` is extracted as its own Bazel package (as `stats/` already was). INFERRED: only `stats/BUILD.bazel` exists today. Recommendation: place the registry in a new package outside Tier 1 (for example `featureregistry/`) or in jvmMain if C3.1 is not pursued, and add the package to `tier_manifest.bzl` deliberately.

- [ ] **C4. Registry shipped in production binaries for test and CI use.** The registry rows (page names, `sources` globs, exemptions) are in commonMain, so they ship in the Android, desktop and wasm artifacts. Only the optional C3.1 Help menu needs them at runtime. The `JvmOnlyApiInCommonMainRule` constraint also forces `expires` to be a lexicographically compared String. Recommendation: since businessTest sees jvmMain through `jvm_main_lib`, put registry data in jvmMain unless D4 = yes, and move it to commonMain then.

- [ ] **C5. Expiring exemptions are a Bazel time bomb.** R3 fails after `expires` using an "injected today". The production test must use the real date. Bazel caches test results (`--config=remote-cache`) so the test will not rerun on the day an exemption expires. It goes red on whichever unrelated PR next invalidates the cache, which makes the red appear unrelated and violates the noise budget. Recommendation: make expiry a warning (summary line) until within N days, fail only on a scheduled workflow or with `--nocache_test_results` for that test (`tags = ["external"]` on a separate small target), or compare against the PR's merge-base commit date.

- [ ] **C6. Warn-only output is invisible in PR CI.** A1.1 reports warnings by writing `kmp/build/reports/feature-registry/report.md` and passing the test. Under Bazel that path is in the sandbox and is not an artifact. `bazel-ci.yml` pipes `--test_output=all` to a log, but nobody reads it on green. Phase A content-axis warnings and the A6.1 FP measurement therefore have no surface. Recommendation: emit `::warning::` lines from the test (stdout is captured) and have the CI report step grep the Bazel log into `$GITHUB_STEP_SUMMARY`, or move content-axis reporting into the shell job.

- [ ] **C7. `sources` granularity and `EssentialCommands.kt`.** All 24 commands live in one file (`EssentialCommands.kt`), rolled into about 6 features. Any edit to that file maps to every command feature, so the staleness gate (A3.1) will flag several features per PR, and PR-level FP measurement (A6.1) will be noisy. The plan does not say how a changed file maps to one feature. Recommendation: specify per-feature `sources` that use shared files only with a line-range or symbol heuristic, or exclude shared files from staleness and rely on the structural gate for commands.

- [ ] **C8. `make docs-check` runs `:kmp:checkDocCoverage`, which depends on the full `jvmTest`** (`build.gradle.kts:1253-1258`, VERIFIED) and so needs X11 for the UI tests, per CLAUDE.md. This makes the "single local entry point" slow and unreliable on Wayland. Recommendation: point `docs-check` at `./gradlew :kmp:jvmTest --tests '*registry*' --tests '*DemoGraph*'` (headless-safe) plus the staleness script, and leave `checkDocCoverage` to `ciCheck`.

- [ ] **C9. `exportFeatureRegistry` needs a full Gradle compile of commonMain+jvmMain inside the `docs-staleness` job on every PR** (Compose, SQLDelight, etc. in a job that otherwise needs only git). The S0.3 spike only times it. Recommendation: pre-decide the fallback, for example `bazel run //kmp:feature_registry_export` using the Bazel cache already in `bazel-ci.yml`, or generate the JSON as a build artifact of the `business_tests` run. Put the budget threshold in S0.3's acceptance (the plan says "under one CI job's budget" without a number).

- [ ] **C10. A4.1 "runs only when `site/**` or the registry changes (paths filter)".** A job-level paths filter does not exist in GitHub Actions. A workflow-level `paths:` makes the job skip and, if it becomes a required check, leaves PRs pending. `ci.yml` has no filters (`ci.yml:3-8`) and `pages.yml` builds the site only on push to main. Recommendation: use a separate `site-ci.yml` with a workflow-level `paths:` filter (A4.1.2 already allows this) and say the check must not be made required, or use `dorny/paths-filter` with an always-green gate job. Pin the action by SHA per the plan's own rule.

- [ ] **C11. Worktree and merge hazards beyond the listed serialization files.** Several new tests each edit `AllBusinessTests.kt` (about 9 registrations), and `AllBusinessTestsCompletenessTest` fails if one is missed. Baseline `.txt` files are sorted-one-per-line, so parallel agent worktrees touching different features still conflict on adjacent lines when regenerated by `:kmp:writeFeatureBaseline`. Recommendation: have `writeFeatureBaseline` produce deterministic output and treat baseline conflicts as "rerun the task, do not hand-merge" in the CLAUDE.md section. Consider one suite file per package to reduce edits to `AllBusinessTests.kt`.

- [ ] **C12. Staleness gate edge cases.** (a) Squash-merge repos lose `Docs-Exempt:` trailers on the merge commit, but the script reads PR commits before merge, so it works. A trailer is in the PR commits only if the author adds it. A PR label alone is more practical for agents, and neither is verified for agent-authored PRs. (b) `feat` detection reads the PR title, which can be edited after the job runs. (c) Fork PRs get no `pull-requests: write` token, so the sticky comment falls back to summary only (noted by the plan, but the A5.1 notification promise then depends on the summary being read). Recommendation: re-run on `edited` for title changes (`types: [..., edited]` on the job, not the whole workflow, to avoid the duplicate-run concern in `ci.yml:6`).

- [ ] **C13. In-app help axis is undefined in the plan.** Requirements name three explainers (demo, in-app help, website) and "help-doc coverage" as a rule. The plan resolves in-app help as "the demo page" by default (D4, C3.1 optional) and plans to delete the Kotlin `*Docs` classes (B3.1), but never records that choice (Open Question 1) as an assumption in plan.md or an ADR. Recommendation: add an ADR-001 (or ADR-004) decision line "in-app help = demo-graph page; Kotlin `*Docs` retired" so the success metric "help-doc coverage" has a definition.
