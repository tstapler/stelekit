# Stack Research: commonmain-bazel-target-split

**Date**: 2026-09-04

## rules_kotlin version and capabilities

**Pinned version**: `rules_kotlin` **2.3.20** (`MODULE.bazel:16`, `bazel_dep(name = "rules_kotlin", version = "2.3.20")`), patched in-repo via `//third_party/patches:rules_kotlin_kmp.patch` to add a `common_srcs` attribute to `kt_jvm_library`/`kt_android_library` (passes `-Xcommon-sources` to kotlinc so expect/actual resolves — this patch is the entire reason the monolith exists today; see `MODULE.bazel:24-29`).

**rules_kotlin#567 confirmed real and still open.** VERIFIED via `gh api repos/bazel-contrib/rules_kotlin/issues/567`: titled "Kotlin Bazel Cross-Platform Roadmap", opened 2021-08-06, **state: open**, last activity 2026-07-28. There is no native `expect`/`actual`-across-real-KMP-targets support in rules_kotlin as of the pinned version or the latest release (v2.4.10, 2026-08-20) — the repo's `common_srcs` patch is a necessary workaround, and requirements.md's premise holds.

**`associates` (friend-visibility)** — what it does: adds `-Xfriend-paths` so a target can see the `internal` members of its associate's compilation. Confirmed by the one existing precedent in this repo: `kmp/src/commonTest/kotlin/BUILD.bazel`'s `common_test_fixtures` target, whose docstring explains it needs `associates = ["//kmp/src/jvmMain/kotlin:jvm_main_lib"]` (not `deps`) specifically to see the `internal` `TOML_PARSING_SUPPORTED` expect/actual declaration, and notes rules_kotlin **rejects a target listed in both `associates` and `deps` simultaneously** — a real constraint the macro must encode.

Known constraints/bugs at scale (from `gh api repos/bazel-contrib/rules_kotlin/issues|search/issues`, all VERIFIED via the GitHub API, not just search snippets):
- **#1467** (open, updated 2026-08-30): "Associate internal symbols not visible to java sources when associate target has public only ABI jars" — only bites if `experimental_use_abi_jars` + `experimental_treat_internal_as_private_in_abi_jars` are enabled; this repo does not currently set those flags (not found in `MODULE.bazel` or root `BUILD.bazel`), so it's a latent risk to watch if ABI-jar optimizations are adopted later, not an active blocker.
- **#1021, #1403, #1404, #1409, #1330, #1331, #1337, #1250** (all closed 2025-01 through 2025-06, i.e. before the pinned 2.3.20/2026-03-18 release): a long history of `associates`-classpath propagation bugs (missing transitive compile jars, dropped ABI jars when associating with multiple targets, `treatInternalAsPrivate` breaking associates). All are closed and predate the pinned version, so the specific bugs found are fixed in 2.3.20 — but the sheer number of historical bugs is itself signal that `associates` is a less-traveled, still-hardening code path, consistent with requirements.md flagging it as "unproven at this scale here."
- No open issue specifically about `associates` breaking at "18+ simultaneous small targets" scale — this appears genuinely untested territory upstream too, not just in this repo.

**`kotlinc_opts` propagation** — not actually a multi-target problem in this repo's existing design: `kotlinc_opts` is a **label reference** to a single `kt_kotlinc_options` target (`//:kmp_jvm_kotlinc_opts` / `//:kmp_android_kotlinc_opts`, defined once in root `BUILD.bazel:12-30`), not inlined flags. Every new per-package target just points at the same existing label — no duplication risk, and a macro can default this per platform trivially.

**Compiler plugin scoping** — `kt_compiler_plugin` targets (`//:compose_compiler_plugin`, `//:serialization_compiler_plugin`, root `BUILD.bazel:44-67`) are likewise defined once, but **every consuming target must redeclare which plugins apply** via its own `plugins = [...]` list (seen verbatim in both `android_main` and `jvm_main_lib`). Since only some of the 18 hub-touching packages use `@Composable` or `@Serializable`, this is exactly the boilerplate the proposed `stelekit_kt_common_library` macro should absorb — e.g. `uses_compose: bool = False` / `uses_serialization: bool = False` params that conditionally splice the two shared plugin labels into the underlying `kt_jvm_library`/`kt_android_library` call. Nothing about rules_kotlin blocks this; it's a plain Starlark macro wrapping problem.

**Worker startup / many-small-targets performance** — two concrete, evidence-backed findings from `gh api repos/bazel-contrib/rules_kotlin/issues` (search + issue bodies fetched directly):
- **#1653** "kt_android_library analysis: `_get_android_resource_class_jars` is O(N²), ~1050s self-time on a large build" (closed 2026-07-02, fixed by PR #1652 "perf: Optimize `_get_android_resource_class_jars` performance", merged same day). Root cause per the issue body: for every dependency of a `kt_android_library`, the helper independently flattens that dependency's *entire transitive* R-class-jar depset and wraps each element in a fresh `JavaInfo` — since these transitive sets overlap heavily (every target re-includes the same shared base/framework R jars), the cost is O(N²) in dependency-graph size and became "essentially the entire runtime" of `kt_android_library` analysis on the reporter's build (846-target set, Bazel 8.4.2). **This is directly relevant**: splitting `android_main` into ~600+ `kt_android_library` targets multiplies exactly the dependency-graph shape this bug punishes. **The fix landed after the pinned 2.3.20 (2026-03-18) and after v2.4.0 (2026-06-17)** — merged 2026-07-02 — so it is present in v2.4.10 (2026-08-20, the latest release) but very likely **not** in the currently-pinned 2.3.20 (INFERRED from release dates; not independently verified by diffing the tag, but the merge date postdates 2.3.20's release by ~3.5 months). **Recommendation: upgrade rules_kotlin to ≥ the first release containing PR #1652 (v2.4.x or later) before or during the pilot slice**, not after — doing the split first on 2.3.20 risks reproducing this O(N²) analysis-phase blowup on the Android side specifically, which is the same class of "looked fine, didn't scale" risk the Constraints section already calls out from the persistent-workers incident.
- **#1179** "Cold start times for KotlinCompile/KotlinKapt workers" (closed) confirms cold persistent-worker starts are ~2x slower than warm ones for `KotlinCompile` (16.9s cold vs 8.5s warm in the reporter's example) — relevant background for interpreting profiling noise across many small targets, but not itself a blocker: rules_kotlin already has persistent/multiplex worker support (`#297` "Optimize worker execution and lifecycle", closed), and this repo already runs persistent workers (per the `f8e7aa82e1`/`6842053f8d` history cited in requirements.md) — so this is an existing, already-tuned axis, not a new risk introduced by the split.
- No open issue found describing worker-pool exhaustion or scheduling overhead specifically from *target count* (as opposed to worker cold-start latency); this appears to be a real gap in upstream's own test coverage (`#840` "Add sample app to test how many targets were rebuilt" is closed but doesn't establish a public benchmark), reinforcing why the Success Metrics section is right to require the repo's own before/after profiling rather than trusting upstream numbers.

## Existing repo Bazel conventions (BUILD.bazel wiring, associates precedent)

Current wiring (read directly, not summarized from memory):
- `kmp/src/commonMain/kotlin/BUILD.bazel` — a `kt_srcs` filegroup (`glob(["**/*.kt"])`) exporting all of commonMain to both consumers.
- `kmp/src/jvmCommonMain/kotlin/BUILD.bazel` — a `kt_srcs` filegroup (all files) plus a **separate `kt_expect_srcs` filegroup** listing only the one file with a real `expect` declaration (`LibsqlNativeLoader.kt`) — this is the existing, working precedent for "some files in a source set are common, most aren't," which is the exact shape `:platform-core` needs to generalize.
- `kmp/src/jvmMain/kotlin/BUILD.bazel` — `jvm_main_lib` (`kt_jvm_library`): `srcs` = commonMain `kt_srcs` + jvmCommonMain `kt_srcs` + own glob; `common_srcs` = commonMain `kt_srcs` + jvmCommonMain `kt_expect_srcs`; `kotlinc_opts = "//:kmp_jvm_kotlinc_opts"`; `plugins = ["//:compose_compiler_plugin", "//:serialization_compiler_plugin"]`. A `kt_jvm_binary` (`desktop_app`) depends on it via `runtime_deps`.
- `kmp/src/androidMain/kotlin/BUILD.bazel` — `android_main` (`kt_android_library`), same shape, Android-flavored (`custom_package`, AndroidX/Compose-Android deps).
- `kmp/src/commonTest/kotlin/BUILD.bazel` — `common_test_fixtures` (`kt_jvm_library`), the **only existing `associates` usage in the repo** (see quote above). It also documents the "cannot be in both `associates` and `deps`" constraint the new macro must respect.
- No `//:kmp_jvm_kotlinc_opts`/plugin definitions are duplicated anywhere else — everything funnels through the single root `BUILD.bazel`.

**No existing `.bzl` macro files in the repo.** `find . -name '*.bzl'` (excluding `vendor/` and `.claude/worktrees/*`, which are vendored third-party rule sources / stale agent worktrees, not repo code) returned **zero results**. There is no natural existing macro file to extend — `stelekit_kt_common_library` would be the repo's first custom `.bzl` file, most naturally placed at repo root (e.g. `//:kotlin_macros.bzl` or a new `//tools/bazel/kotlin.bzl`) since it needs to reference the root-level `kotlinc_opts`/plugin targets by label.

## Tooling evaluation: internal-usage audit + cycle detection

### `mcp__kibitzer__architecture_assessment` — actually run, not just described

**Zero-config behavior (no `.claude/inspect.json`)**: confirmed both `list_checks` and `architecture_assessment` return only the literal string `"no .claude/inspect.json found above this path"` — **it does nothing at all without configuration**, not even a default cycle check. This directly answers the open question in requirements.md: yes, language-specific check configuration is required first.

**With a minimal config** (`{"checks": [{"name": "kotlin-import-cycles", "architecture_checker": "import-cycles", "severity": "advisory", "triggers": ["batch"]}]}`), run against `path=/home/tstapler/Programming/stelekit`, `scope=kmp/src/commonMain/kotlin/**`, `include_diagram=false`, kibitzer **did** work and found real findings (744 findings / 615 files; output exceeded the tool-result token cap and was saved to disk, then grepped):
- **Two real import cycles**, both genuinely concerning for the split:
  1. A tight, 2-package cycle: `dev.stapler.stelekit.git.merge -> dev.stapler.stelekit.git.model -> dev.stapler.stelekit.git.merge` (flagged at `kmp/src/commonMain/kotlin/dev/stapler/stelekit/git/merge/JournalMergeService.kt:4`).
  2. A **33-package cycle spanning nearly the entire commonMain tree** — starting and ending at `ui.gallery`, and passing through `migration, ui.onboarding, ui.screens.git, editor.blocks, editor.state, editor.text, editor, editor.commands, ui.transfer, transfer.qrcode, ui.components.tags, sections, ui.components.settings, ui.components, ui.screens, ui.state, domain, tags, voice, llm, git, export, ui, ui.annotate, platform.ml, calibration, platform.sensor, search, performance, repository, db.sidecar, db, asset` before closing back to `ui.gallery` (flagged at `GalleryViewModel.kt:8`). **This is a direct, concrete confirmation of Feasibility Risk #2** — a real bidirectional/indirect cycle exists today across most of the 18 "hub-touching" packages, which will need breaking (or a merged target boundary) before any of them can become independent Bazel targets, since Bazel forbids target-level cycles. This is exactly the kind of finding the coarse regex-based one-way import scanner referenced in requirements.md would likely have missed, since it's an indirect multi-hop cycle, not a direct A→B→A pair for most of the packages involved.
- **Also probed the `coupling` architecture_checker** (fan-in/fan-out > 10 packages) in a second run — not one of the two checks requirements.md asked about, but directly useful evidence for the "provisional 11/9/18 package split" Rabbit Hole: it corroborates the requirements' hub classification with real numbers, e.g. `model` is imported by **377** packages, `repository` by **119** (and itself imports 190), `db` is imported by **95** (and imports 174), `error` by **136**, `logging` by **67** — these are unambiguously hub packages. Notably, three of the nine "zero-risk pilot" packages already show significant **fan-in** despite presumably-low fan-out (`error`: imported by 136, `logging`: imported by 67, `parsing`: imported by 15) — none of them appear in the "imports N packages" (fan-out) list, meaning they're leaf/utility packages consumed widely but depending on little themselves. That's consistent with "zero-risk to extract" (their own compile unit has few inputs), but Phase 3 planning should note their high fan-in means many downstream targets will need a `deps` edge added, not that they're risky to split themselves.
- **Confirmed `internal`-usage auditing is out of scope for architecture_assessment.** `grep -i internal` and `grep -i "layering\|coupling"` (before adding the coupling check) on the saved output returned zero matches for internal-visibility findings, and reading kibitzer's own source (`/home/tstapler/code/github.com/tstapler/kibitzer/src/architecture_checks.rs`) confirms the complete `architecture_checker` registry has exactly three checkers: `import-cycles`, `layering` (requires a manually-declared `config.layers` ordering — not configured, and not naturally applicable here since this isn't a layered-architecture problem), and `coupling` (fan-in/fan-out counts). **There is no internal-visibility checker in kibitzer at all** — its own tool description ("import cycles, layering, coupling") is accurate and exhaustive; a bespoke script is required for the `internal`-usage audit regardless of how kibitzer is configured.
- Kibitzer is the user's own personal tool (source at `~/code/github.com/tstapler/kibitzer`, installed via Homebrew as `kibitzer` and also present in `~/.cargo/bin`), not a public/widely-used product — worth noting for the plan's tooling-dependency risk assessment (no upstream community, but the source is available and modifiable if a fourth `architecture_checker` type were ever needed).
- The exact validated config was removed from the repo after testing (this is a research task, not implementation) but is reproduced above verbatim so Phase 3/5 can drop it into `.claude/inspect.json` directly.

### Cross-package `internal`-usage audit — no existing tool fits directly

- **`stapler-scripts/` confirmed to have no existing Bazel/Kotlin cycle-detection or internal-visibility-audit script.** `ls` + `grep -rli "cycle\|internal.visibility\|bazel\|kotlin"` over `/home/tstapler/dotfiles/stapler-scripts/` found only unrelated hits: `kotlin-lsp-{installer,wrapper}.sh` (LSP tooling, unrelated), `intellij-localhistory-kt/` (a full separate Kotlin/Gradle CLI project — IntelliJ local-history forensics, unrelated to this audit), and Rust build artifacts under `claude-proxy-rs/target/`. None relate to Bazel target-splitting or Kotlin visibility auditing.
- **Repo script conventions**: `stapler-scripts/` is a flat mix of standalone Bash (`.sh`) and Python (`.py`) scripts (e.g. `memory-optimizer.py`, `jvm-optimizer.py`, `sdd-plan-audit.py`) — no precedent for a Kotlin-based analysis CLI as a standalone script (the one Kotlin project there, `intellij-localhistory-kt/`, is a full Gradle app, not a lightweight script). **A new internal-visibility checker should follow the Python-script convention** if it needs to live in `stapler-scripts/`, or — more in keeping with this repo's own stated tool priorities (`CLAUDE.md`: "prefer `ast-grep` over `grep` for structural code search") — be an `ast-grep`/gritql pattern plus a small driver script kept inside the SteleKit repo itself (e.g. `kmp/scripts/` or `tools/`), since it's specific to this migration and not a general-purpose dev tool.
- **Konsist** (WebFetch of `github.com/LemonAppDev/konsist`): a real, actively maintained Kotlin static-analysis tool, but it is fundamentally a **JUnit/Kotest-based architecture-linter library** consumed from Gradle/Maven test dependencies — its own docs show only Gradle and Maven dependency snippets, with no Bazel integration story. Adopting it would mean adding a new test dependency + a JVM test target purely to run a one-off pre-migration audit, which is heavier than the problem needs and cuts against "Bazel only" / minimal-tooling-scope-creep guidance in the Rabbit Holes section.
- **kotlinc compiler diagnostics** are the most rigorous option in principle (the compiler already refuses to compile code that references an inaccessible `internal` member across a real module boundary — this is exactly the error class `associates` exists to avoid) but using them as the *pre-migration* check is circular: you'd need to already have built the target split to get the diagnostic, which is the migration itself, not a check that runs *before* committing to a boundary.
- **Recommendation for this specific check**: a bespoke script, not a new dependency. Concretely: for each proposed package boundary, `grep`/`ast-grep` for `internal` declarations inside the package, then search the rest of `commonMain` (outside the package) for references to those identifiers. This is a same-shape problem to what `sg`/`ast-grep` is already the repo's stated preferred tool for structural Kotlin search, and fits the "few-hundred-line bespoke script" scope the Rabbit Holes section explicitly wants (not "a mini build-system linter").

### Public precedent for splitting a monolithic Kotlin Bazel target

- Slack Engineering's "Scaling Slack's Mobile Codebases: Modularization" (VERIFIED via WebFetch, https://slack.engineering/stabilize-modularize-modernize-scaling-slacks-mobile-codebases-2/) is a direct, large-org precedent: they state modularizing out of a monolithic app target was necessary to get any value at all from Bazel's shared build cache ("if most of our code still lived in a monolithic app target, any change in the app target would require a lengthy rebuild"), and that on iOS "moving a file into a module, with no other changes, could improve the compile time by seconds" — directly analogous to this project's 71s monolithic `commonMain` compile. The post doesn't detail their cycle/visibility migration mechanics in the fetched excerpt, so it corroborates the *motivation* for this effort more than it prescribes *how* to execute the split.

## Recommended stack for the extraction tooling

1. **Starlark macro** (`stelekit_kt_common_library`, new file, no existing `.bzl` to extend — this repo has none): a thin wrapper around `kt_jvm_library`/`kt_android_library` taking `uses_compose`/`uses_serialization` booleans (splicing in the two existing root-level `kt_compiler_plugin` labels), defaulting `kotlinc_opts` to the existing `kmp_jvm_kotlinc_opts`/`kmp_android_kotlinc_opts` labels per platform, and taking `associates = ["//kmp/...:platform-core"]` (never also in `deps`, per the `common_test_fixtures` precedent) plus a `visibility` default. Nothing here needs new rules_kotlin features — every piece (`kotlinc_opts` labels, `plugins` labels, `associates`) already exists and works in this repo today; the macro is pure boilerplate reduction, not new capability.
2. **Cross-package `internal`-usage audit**: bespoke `ast-grep`/grep-based script (Python, matching `stapler-scripts/` convention, or a repo-local script if it's migration-specific) — no existing tool (Konsist, kibitzer, detekt) covers this for Kotlin+Bazel, and a compiler-diagnostic-based check is circular for a pre-migration gate.
3. **Import-cycle detection**: **adopt kibitzer as-is** via `.claude/inspect.json`'s `architecture_checker: "import-cycles"` — already verified working against this exact codebase, already found a real 33-package cycle, requires zero new code. Also worth configuring `architecture_checker: "coupling"` (already verified useful) to keep the hub/non-hub package classification honest as packages get regrouped, even though the requirements only asked about cycles.
4. **Before committing to the pilot on the current rules_kotlin 2.3.20**: consider upgrading to a version ≥ the release containing PR #1652 (merged 2026-07-02, present in v2.4.10) to avoid the O(N²) `_get_android_resource_class_jars` analysis-phase cost (#1653) that many small `kt_android_library` targets would otherwise reproduce. This is a Phase 3 planning decision (with its own risk/testing needs, per this repo's "looked safe locally, broke CI" precedent), not something to action in research, but it should be an explicit line item.
