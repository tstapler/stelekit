## Concerns

- [ ] **Story 1.1.1 (`stelekit_kt_common_library` macro) — open/closed violation via boolean flags.** The macro hardcodes exactly two plugins (`uses_compose`, `uses_serialization` booleans) and two platforms (`platform == "jvm" | "android"`). A future package needing a third compiler plugin, or Tier 3's eventual merged-cluster target needing some other variant, requires *editing* the macro rather than *extending* it — the classic boolean-flag-parameter smell (Task 1.1.1b). **Remediation**: replace the two booleans with a single `extra_plugins = []` label_list parameter (with `uses_compose`/`uses_serialization` as sugar that append to it, if the ergonomics are wanted), so a new plugin never requires a macro edit — only a new call-site argument.

- [ ] **ADR-001 / plan.md tier tables — tier classification is primitive-obsessed (prose-only, not structured/checkable data).** Which packages belong to Tier 1/2/3 is recorded only in ADR-001's markdown and plan.md's tables — there is no Starlark list, JSON manifest, or other machine-checkable single source of truth. Rabbit Holes (requirements.md) explicitly anticipates the tier split may need revision post-audit; if it does, two prose documents must be kept in sync by hand with no drift check. **Remediation**: add a small checked-in manifest (e.g. `tier_manifest.bzl` defining `TIER_1_PACKAGES`, `TIER_2_PACKAGES`, `TIER_3_PACKAGES` as Starlark lists) that both `kotlin_common.bzl` callers and any future audit/CI script read, so "is package X Tier 2" has one answer, not two documents that can disagree.

- [ ] **Migration Plan's "same commit" rule (plan.md, and Epic 1.x generally) — the illegal state (a `.kt` file claimed by two compilation units) has no automated pre-merge check, only task-list convention.** `research/architecture.md` itself explicitly proposes "a natural candidate for a CI-time structural check (e.g. asserting no `.kt` file is claimed by more than one `kt_srcs`-derived compilation unit)" — this recommendation is never turned into a Phase 1 task. Today the only backstop is: (a) the human-authored task list says "same commit," and (b) a fail-fast `kotlinc` duplicate-declaration error *if and only if* something already depends on both the stale monolith glob and the new target at merge time. A newly created, not-yet-consumed target (e.g. `:stats` before anything references it) can merge clean with a stale monolith glob and the conflict surfaces only later, in whatever PR first wires a consumer to it — a confusing, delayed failure mode. **Remediation**: add a Phase 1 epic/task for a cheap script (reuse `sg`/glob logic, doesn't need to be sophisticated) that asserts every top-level `commonMain` package directory is claimed by *exactly one* of {the `kt_srcs` glob, a per-package target's own `srcs`}, run in CI on every PR touching `kmp/src/commonMain/kotlin/BUILD.bazel` or any package's `BUILD.bazel`.

- [ ] **Epic 1.4 / Story 2.3.1 — the `internal`-visibility audit is validated only against 6 already-known pairs and scoped one-directionally per phase.** `check_internal_visibility.py`'s acceptance test (Task 1.4.1c) reproduces the 6 pairs `research/features.md` already found by hand; Story 2.3.1 runs it "scoped to the 9 Tier 1 packages as *declaring* packages" only. Neither task establishes running the audit with each about-to-be-extracted package as the *consumer* (i.e., does this Tier 1/2 package need `internal` access *into* a still-monolithic Tier 3 symbol?) — a case the plan's own Rabbit Holes/Feasibility Risk #1 raises but Epic 4.2 only resolves for the 2 pairs already known from research, not by running the audit fresh in both directions per package. **Remediation**: make "run `check_internal_visibility.py` with `<pkg>` as both declarer and consumer, before writing its `BUILD.bazel`" an explicit step in the common per-package recipe (Epic 2.2/4.1's task (a)), not something inferred only from the two pairs research already happened to find.

- [ ] **`research/architecture.md`'s `:platform_core` design — every extracted package (including "zero-risk" Tier 1 leaves) needs a `deps` edge on the still-existing monolith purely to reach `:platform_core`, and whether this preserves the invalidation-scope win is unverified.** Because `:platform_core` is never independently compiled (it stays `common_srcs`-included in `android_main`/`jvm_main_lib`, per ADR-005's unchanged constraint), the worked example for `stats` — the simplest possible leaf package — still lists `deps = ["//kmp/src/jvmMain/kotlin:jvm_main_lib", ...]` "for platform-core symbols." Whether a change to an unrelated file still inside the monolith (87.8% of the codebase, per Tier 3) forces recompilation of every already-extracted package depends entirely on whether rules_kotlin's `kt_jvm_library`/`kt_android_library` produce ABI-stable interface jars for dependency-change detection — a question neither the plan nor the research documents address. This doesn't invalidate the plan's literal Success Metric (an isolated Tier-1-package edit not recompiling the monolith, which is structurally guaranteed by the glob-exclude alone), but it directly bears on the *aggregate* win most PRs care about, since most PRs will touch Tier 3. Story 3.1.1 (the go/no-go checkpoint) would eventually surface this — but only after all 9 Tier 1 packages are already built. **Remediation**: add a one-off Phase 1 spike (before Epic 2.2 starts) verifying rules_kotlin's ABI/interface-jar behavior for `kt_jvm_library`/`kt_android_library` — e.g., touch an unrelated file still in the monolith, rebuild `:stats` (or the Task 1.1.1c smoke target) with `--profile`, and confirm its `KotlinCompile` action is *not* re-executed, only re-analyzed. This is a ~10-minute check that de-risks the entire tiered-target premise before committing the Tier 1 pilot's PR budget to it.

- [ ] **ADR-001's Tier 3 "(a) merge" decision — real technical debt, well-documented in the ADR, but with no tracked remediation path beyond a recommendation.** ADR-001 explicitly recommends "(b) [dependency-inversion refactor] be scoped as its own, separately-chartered follow-on project," but no issue/ticket is opened for it — the only record is the ADR's prose "Reconsideration triggers" section. Absent a tracked item, this is the kind of debt that silently disappears once this migration ships and attention moves on. **Remediation**: open a tracking issue now (referencing ADR-001) for the Tier 3 dependency-inversion follow-on project, even with placeholder scope, so it survives past this project's own closure.

## Nitpicks
- `research/architecture.md`'s two illustrative code snippets (`stats` and `search` worked examples) both write `load("//:kt_common.bzl", "stelekit_kt_common_library")`, but plan.md's Domain Glossary and every Story 1.1.1 task consistently name the file `kotlin_common.bzl`. Harmless (research snippets are illustrative, not authoritative), but worth a one-line fix so nobody copies the stale filename when Epic 1.1 actually authors it.
- The common per-package extraction recipe (Epic 2.2/4.1's task (c), and Stories 2.2.3–2.2.9 / 4.1.3–4.1.11's compact tables) verifies only via the full `bazel build //kmp:desktop_app //kmp:android_app ... && bazel test //kmp:jvm_tests //kmp:business_tests` — it drops the cheaper isolated `bazel build //<pkg>:<pkg>` step that Task 1.1.1c used for the macro's own smoke test. Re-adding it as recipe step 0 gives a faster, more localized failure signal before the full-graph build.
