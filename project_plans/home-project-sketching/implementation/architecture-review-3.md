# Architecture review, round 3: home-project-sketching

Scope: `implementation/plan.md` (read in full to Story 6.5b; Sections 12, 13, 17 skimmed; the 6.x carry-over lane after 6.5b not reviewed) and `decisions/ADR-001..009`. Findings were formed from the code BEFORE `implementation/*review*.md` was opened. Labels: VERIFIED = opened or ran in this repo; INFERRED = reasoned, not run. Paths are relative to `kmp/src/commonMain/kotlin/dev/stapler/stelekit/` unless prefixed.

**Verdict: BLOCKED** (1 BLOCKER, 6 MAJOR, 10 MINOR). `plan.md` was not edited.

## BLOCKER

### B1. The synced sidecar carries no sketch geometry, so "a sketch drawn on one device reaches the others" is false (ADR-005, Stories 2.1, 2.5, 3.7)
- ADR-005 Consequences: "A sketch drawn on one device reaches the others through normal git sync of `assets/`." Story 2.5's `ProjectModelJson` lists display strings, `modelRevision`, registry, observations, zones and `sources[]`. It lists no `sketch_sheets` or `sketch_primitives`.
- Section 5 makes the DB tables a cache of the sidecar and says `SidecarReconciler` "rebuilds `sketch_*` rows from it". A device that rebuilds from the sidecar therefore loses every drawn primitive.
- Story 3.7 puts the model into SVG `<metadata>` under `exports/`, which Story 0.3 makes a Skip subtree, so that is not a sync path either.
- Fix, before Story 2.1 merges (a later change costs a migration plus a `schema` bump): either (a) add `sheets[]` (kind, unit, scale, view direction, layers, zones) and `primitives[]` (sixteenth coordinates, name, layer, z) to `ProjectModelJson` `schema:1`, with the 10 000-primitive cap giving a size bound and a per-sheet file such as `sheets/<sheetuuid>.json` if one file is too large for git merges; or (b) state in ADR-005 that primitives are device-local, and drop "authoritative" for the drawing. Option (a) matches the stated intent.

## MAJOR

### M1. Reconcile cannot detect "both changed": there is no base marker (Story 2.5, Section 5 `sketch_projects`)
- The AC resolves three cases: "sidecar newer", "DB newer and sidecar unchanged since last write", and "BOTH changed". `sketch_projects` has `model_revision`, `source_hash` and `last_digest_hash`, and nothing that records the last sidecar revision or hash this device synced.
- Two devices that each edit once from revision 5 both reach revision 6, so a bare counter compares equal while the contents differ. Without a base, the "keep pulled, save local as `project-model.conflict-<hash8>.json`" branch cannot fire, and the second device silently loses (or overwrites) work.
- Fix: add `last_synced_sidecar_hash` (and the base `model_revision`) to `sketch_projects` in Story 2.1 (the table is created there, so this is free now). Decide three-way: local DB hash vs base vs pulled-file hash. Make `modelRevision` informational only.
- Also specify what happens when the reconcile rebuilds rows while `SketchViewModel` holds in-memory state with a 500 ms autosave: the stale state would write back over the rebuilt rows. The ViewModel must reload on a reconcile signal and drop its pending autosave.

### M2. `PostSyncProjectJob` "owned by `StelekitViewModel`" has no way to obtain what it needs (Stories 5.7a, 5.4c)
- VERIFIED: the one `TargetWriterRouter` is built inside a Composable `DisposableEffect` (`ui/App.kt:117-141`) from `captureDeps.shareInbox`/`copyHost`, and only when `fileSystem as? PlatformFileSystem` is non-null. It is therefore null on some platforms and has composition lifetime.
- VERIFIED: `StelekitViewModel` is 2 522 lines and takes `StelekitViewModelDependencies` (`ui/StelekitViewModelDependencies.kt`, 111 lines), which carries no router, no `GraphManager` and no sketch repositories. `RepositorySet` is a `data class` with defaulted fields (`repository/RepositoryFactory.kt:47,74`), so adding three sketch repositories is cheap, but the job still needs a path to them.
- The plan's Files list for 5.7a edits only `StelekitViewModel.kt`. The spine will either grow the hotspot or stall at 5.4c.
- Fix: add to 5.7a an explicit `PostSyncProjectCoordinator` collaborator (the pattern of `GitSyncCoordinator`/`LlmSuggestionCoordinator`, which exist for exactly this reason: ViewModel decomposition), constructed from new nullable `StelekitViewModelDependencies` fields (`routerProvider: () -> TargetWriterRouter?`, `sketchRepositories`, `projectSidecarStore`). State what the job does when the router is null (wasmJs, no share config): skip with a visible "digest unavailable on this platform" entry, never a silent no-op. The `StelekitViewModelDependencies` edit belongs in the Files list.

### M3. No barrier between `SyncState.Success` and the pulled files being imported into the DB (Stories 5.7a, 5.9b, 5.7b)
- `SyncState.Success` is published at the end of `GitSyncService.sync` (`git/GitSyncService.kt:480-492`). Pulled files reach the DB later, through the file watcher (`db/GraphFileWatcher.kt`, `externalFileChanges`). I found no `awaitIdle`/drain barrier in `GraphLoader` or `GraphManager` (INFERRED from a grep; not exhaustively searched).
- The job reads bound pages "from stored page metadata" (5.9b) right after `Success`. It can read the pre-pull content, compute an unchanged `ProjectRelevanceHasher` hash, run nothing, and then never run again for that pull. Worse, it can write a digest from stale sources.
- Plan handles `isContentLoaded = false` stubs (`unloaded=N`) but not stale-but-loaded pages.
- Fix: in 5.7a define the settle condition (for example: wait until the watcher/loader reports no pending external changes for the graph, or compare the bound pages' `contentHash` against the file's hash on disk before trusting the DB), and add a test with a fake sync that publishes `Success` before the import completes. Also handle `Success` being replaced by `LfsActionRequired` (`GitSyncService.kt:489`): the job would miss that sync entirely; trigger on `lastSyncAt` from `syncState` or `gitLastSyncAt` rather than only the `Success` subtype.

### M4. `AtomicFileWriter` as specified cannot run on several platforms and inverts layering (Story 2.0, ADR-005, Story 2.5)
- VERIFIED: `FileSystem.writeFileBytes` defaults to `throw UnsupportedOperationException` (`platform/FileSystem.kt:195`); overrides exist only in `jvmCommonMain` (`AppPrivateFileSystem`), `androidMain` and a test fake. None in `wasmJsMain` or `iosMain` (grep of `override fun writeFileBytes`). `renameFile` defaults to `false` (`FileSystem.kt:123`), and the Story 2.0 fallback ("delete plus rename") depends on it.
- So on wasmJs (and iOS) the sidecar store cannot write. The sidecar is JSON text, so the text path `writeFile(path, String)` is the portable one; the API should take `String`.
- The extraction is too narrow: `MarkdownTargetWriter.replaceFile` (`merge/MarkdownTargetWriter.kt:206-240`) also does the symlink check, a `changedSinceRead` compare-and-swap between temp write and replace, and restores the deleted original on a failed rename. `write(path, bytes)` has no place for the CAS or `original`, so the "existing tests stay green unchanged" claim needs a `precondition`/`original` parameter.
- Layering: `StaleTempSweeper` is `internal` in `merge/PageUuidOwnership.kt:73` and `SAF_ATOMIC_REPLACE_VERIFIED` is in `merge/TargetWriterCapabilities.kt:14`. A `platform/AtomicFileWriter` that uses either makes `platform` depend on `merge`. Move the sweeper into `platform/` (rename file) and pass the SAF flag in as a parameter.
- Also: a crash-leftover `*.tmp` in `assets/stelekit-sketch/<slug>/` is a git-trackable file (sweep only after 10 minutes, `StaleTempSweeper.MAX_AGE`). State the `.gitignore`/LFS rule, since ADR-005 defers "LFS path rules" to implementation time.

### M5. The graph-derived denylist in `OutboundLlmGate` will block almost every payload (ADR-007, Story 5.5b)
- The gate fails on "any token in the graph-derived denylist (page names, aliases, tokens the user's graph defines)". A real wiki graph (this one is 8 000+ pages per `CLAUDE.md`) has pages named for ordinary words, and the payload's labels come from the registry in the same vocabulary (`Rod`, `Shelf`, `Width`, the project's own digest page title `<display name> Digest`). The closet-fixture test passes against a synthetic denylist and would not show this.
- A hard block that fires on ordinary labels trains the owner to switch the feature off, or to add exemptions that hollow out the control.
- Fix: scope the denylist to what is actually sensitive: tokens from pages tagged or aliased as people/places (or an owner-maintained list), multi-word page titles only, and exclude any token that is a registry label or a fixed payload keyword. Alternatively invert the control: build the payload only from a closed vocabulary (slug, opaque ids, registry labels, numbers, status enums) and test that the builder cannot emit anything else, keeping the structural patterns (path, URI, email, address) as the gate. Add a test that runs the gate against a denylist built from a synthetic 8 000-page graph and still passes the closet payload.

### M6. Two `OwnedPageWriter` implementations for a path the hook cannot reach (ADR-006, Stories 5.4a, 5.4b, 5.7b)
- Story 5.7b states "the hook only fires for the ACTIVE graph". The router picks the off-graph `MarkdownTargetWriter` only when `ready?.id != target` under the lock (`merge/TargetWriterRouter.kt:94-109`), which for this job is a graph switch mid-job. Yet 5.4a builds the Markdown implementation first (byte-faithful, CRLF, atomic replace, `Conflicted`) and `TwoDeviceConvergenceTest` runs "device B on the off-graph writer". Device B is also running the app with the graph open, so it would use the Active writer; the test premise is not a real deployment.
- Real constraints that remain: `activeTargetWriterFor` returns `RefusingWriter` when there is no path or write actor (`capture/ActiveWriteHooks.kt:55-58`); an `as? OwnedPageWriter` on it yields null, and the plan never says what null maps to.
- Fix: either (a) make the Active writer the only production implementer, have the Markdown writer return `Retryable("switch in progress")` for `replaceOwnedPage`, and re-aim the convergence test at two Active-writer devices with a fake file system; or (b) keep both but justify why in ADR-006. In both cases: `as? OwnedPageWriter == null` must map to the existing `MergeError.Retryable` (the `RefusingWriter` meaning), not to `NotOwned`. This also shrinks 5.4a and removes the CRLF/byte criteria from the critical path.

## MINOR

- **m1. Reachability claim, verified and weakened.** `scripts/ci/reachability-scan.py` (read in full) matches the plan's description: production sources only (`kmp/src/*Main/`, `androidApp/src/main/`), column-0 non-private types are candidates, a type is live if its name token appears in any other production file, `@Serializable` and `*UiState` types are filtered, `--check-baseline` exits 1 for a type absent from the baseline. Two things the plan does not say: (1) `live_names` also treats every top-level `fun`/`val`/`var` segment as a live root, so a type mentioned by a top-level function in its own file passes with no outside referrer; (2) nested (indented) types are never candidates. The scan therefore proves less than "an honest consumer exists". The slices SL-A and SL-B rest on the collector shell (an empty `CollectedSources`) "calling `parseLength`" and "`FusionEngine`", which is a code mention with no data flowing. Acceptable for a dormant flag, but say so, and add Story 5.7a to the `Deps` of the SL-A/SL-B members (and to the mermaid edges): the collector shell must exist before they can reference it, and nothing in `Deps` says so.
- **m2. `WriteRefusedReason` file and count.** The sealed interface lives in `merge/TargetWriter.kt:11`, not `error/DomainError.kt`; Stories 5.4a/5.4b list `DomainError.kt` but not `TargetWriter.kt`, and state "TargetWriter ... do not change" (true for the interface, false for the file). ADR-006 says "two NEW variants" (`NotOwned`, `EditedByUser`); Story 5.4a adds three (`Conflicted`). `capture/RouterOffGraphRoute.kt:138-150` has an `else` arm, so no exhaustive `when` breaks there, but record that new variants are classed `permanent = true` deferrals. No `toUserMessage` exists on `WriteRefusedReason` (grep); ADR-006 says one does. Reconcile the three texts.
- **m3. Repository write pattern is ambiguous (Stories 2.2, 2.3).** The cited precedent `SqlDelightAssetRepository` calls `database.steleDatabaseQueries` directly and has no `@OptIn(DirectSqlWrite)` (it is absent from `DirectSqlWriteOptInAllowlistTest.expected`); `AssetIndexService` opts into `@DirectRepositoryWrite` inside `writeActor.execute`. Plan Story 2.2 instead adds `RestrictedDatabaseQueries` stubs and 2.3 adds a `DirectSqlWrite` opt-in. Pick one. If the stub route stays: the allowlist test counts LINES containing `OptIn(DirectSqlWrite` per file (`DirectSqlWriteOptInAllowlistTest.kt:48`), and `SqlDelightBlockRepository` already has 8, so a three-repository file will likely have more than one line, and the "41 becomes 42" total (also asserted by `baseline_should_BeFortyOne`, which the plan does not list as edited) will be wrong.
- **m4. Gate type.** `GatedPrompt` must not be a `data class`: `copy()` is generated for it and is not covered by an `@RequiresOptIn` on the primary constructor, so any caller could forge one. Make it a plain class (or private-constructor plus a companion factory marked `@GateIssued`). Also, `GatedPrompt`/`OutboundLlmGate`/`GateIssued` sit in `projectbridge/` while `ProjectAnalysisService` is in `llm/` and the job in `projectbridge/` calls it: a package cycle (`llm` -> `projectbridge` -> `llm`). Put the gate types in `llm/` (they are not project-specific).
- **m5. Flagged-screen gates.** `@HelpExempt` has SOURCE retention; `DemoGraphCoverageTest` mirrors it with a hand-kept `KNOWN_EXEMPT_SCREENS` set (`jvmTest/.../docs/DemoGraphCoverageTest.kt:88`). Story 3.3 should add `"Sketch"` there (the test is informational, so a miss does not fail, but the list is then wrong). The `first-open-screens.txt` comment-block approach is consistent with how Console and Drive are handled there (VERIFIED, file read). Story 3.3's Files list omits `SteleKit` `Sidebar.kt`/`GraphDialogLayer.kt`/`StelekitViewModel.kt`, which also reference `Screen.AssetBrowser`; check whether `Screen.Sketch` needs a sibling entry in each (grep shows one reference per file).
- **m6. Bazel registration beyond `AllBusinessTests`.** `//kmp/src/androidUnitTest/kotlin:android_unit_tests` runs only `AllAndroidUnitTests` (28 entries) although 81 files use `setContent`; Compose tests are Gradle-only today (the BUILD file says the Bazel target has "no Compose compiler plugin"). Section 13 lists eight androidUnitTest classes as if Bazel ran them. State: Compose AU tests run under `./gradlew testDebugUnitTest` only; any non-Compose AU test is added to `AllAndroidUnitTests`.
- **m7. Name collision.** `ui/screens/ImportViewModel.kt` already exists (URL import). Story 4.4's `CM/ui/sketchimport/ImportViewModel.kt` shares the simple name, which the name-based reachability scan treats as one name and Kotlin imports as ambiguity. Rename to `SketchImportViewModel`. (A sweep of the other planned type names found no collision; `Calibration` exists in `model/ImageAnnotation.kt` and is used as intended.)
- **m8. Downgrade claim.** Story 0.3 says tolerant decode means "a downgraded app does not crash on a `DRAWING` row". `SqlDelightAssetRepository` lines 52 and 91 use `AssetMediaType.valueOf` in every already-released build, so a downgrade past the release that carries 0.3 still crashes. This is safe only because the flag is off by default; say that, and ship 0.3 at least one release before graduation.
- **m9. Privacy ordering.** The plan text under `project_plans/home-project-sketching/` already contains the real closet constants (136, 69 3/16, 11.0638, 34.2289, 8/10/12, the D1-D12 list) while OD-H1 ("may we commit a sanitised snapshot?") is still open. The private-string guard checks structural patterns only. If OD-H1 is "no", the plan itself has published the numbers. Either treat OD-H1 as decided "yes" in Section 8, or replace the constants in plan prose with fixture-parameter names. The directory is untracked today (`git status`), so this is fixable before commit.
- **m10. Trigger edge.** `PostSyncProjectJob` is triggered "plus once at graph open". The VM is rebuilt per graph switch in some paths; confirm it cannot double-trigger on a switch (the router's `readyGraph` pair, not `activeGraphId`, is the readiness signal per `TargetWriterRouter` KDoc) and that the graph-open trigger waits for the same settle condition as M3.
