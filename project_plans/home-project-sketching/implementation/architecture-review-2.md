## BLOCKER

### B1. Asset backfill defeats the `DRAWING` cloud exclusion, and sidecar files land in the asset index
Evidence:
- `AssetIndexService.backfillGraph` walks `<notes>/assets/` recursively (`asset/AssetIndexService.kt:175-190`, `walkFiles` at ~249-262) and `buildAssetEntry` derives the class only from the sniffed MIME: `AssetMediaType.fromMimeType(mime)` (`:110`; `AssetModels.kt:12-21`: `image/*` -> `IMAGE`). It sets `mlProcessed = false`.
- `CloudClaudePlugin.canProcess` admits `IMAGE` with `mlProcessed`/consent conditions (`pipeline/CloudClaudePlugin.kt:46-48`); `OcrPlugin`/`OnDeviceLabelingPlugin` admit `IMAGE` too.
- Story 4.4 introduces `DRAWING` only in the `registerAsset` path and tests "register a floor-plan PNG and an SVG and assert zero provider calls". That test passes while the real path leaks: on any other device (the sketch dir is git-synced) or after a re-index, backfill re-classifies the same SVG/PNG as `IMAGE` and queues it for OCR, labeling and, with consent granted, the cloud plugin. This is the plan's stated hard privacy guarantee (risk register row 8).
- Separately, ADR-005/Story 2.5 put `project-model.json`, `sources/yaml-*.yaml` and `project-model.conflict-*.json` under `<graph>/assets/stelekit-sketch/<slug>/`. Backfill will register each as a `DOCUMENT`/`FILE` asset (Library clutter, a content hash recomputed per autosave, orphan accounting). The yaml snapshot is the owner's raw source text sitting in the asset index.

Fix:
1. Classify by location, not only at import: in `AssetIndexService.buildAssetEntry` (and any other constructor of `AssetEntry`), anything under `assets/stelekit-sketch/` is `DRAWING` (drawings) or skipped entirely (sidecars: `*.json`, `sources/*`). Add a `walkFiles` exclusion for the sidecar subtree so they are never rows.
2. Add a test that runs `startBackfill` over a `FakeFileSystem` containing an SVG and PNG under the sketch dir, with the cloud plugin enabled and consent granted, and asserts zero provider calls and class `DRAWING`. This replaces, not supplements, the register-time test.
3. Make this a DIRECT story that lands first (see M7); it edits only existing production types, so it has no reachability problem.
4. `SqlDelightAssetRepository` decodes with `AssetMediaType.valueOf(media_type)` (`repository/SqlDelightAssetRepository.kt:52,91`), which throws on an unknown value. Decide the downgrade story (tolerant decode to `FILE`) in the same change, and note the exhaustive `when (mediaType)` sites in `ui/assets/AssetItemCard.kt:201`, `AssetBrowserViewModel.kt:334`, `AssetBrowserScreen.kt:282` belong to screens that Story 6.7 deletes (gated on PR #565), so 4.4a touches code that is about to go.

### B2. PRs into the integration branches run no `ci.yml`; the plan's mitigation for the two mega-PRs does not exist
Evidence: `.github/workflows/ci.yml:3-8` triggers `pull_request: branches: [main, master]`. `bazel-ci.yml:3-7` has no branch filter, so `//kmp:business_tests` and `//kmp:jvm_tests` do run, but the `reachability` job, `sqldelight-sync` (generated-source drift), Gradle Android, and `diff-coverage` (`ci.yml:214`, `timeout-minutes: 60`) do not run on a PR into `feat/home-sketch-core`. Section 10a says each constituent story is "reviewed and CI-green there, except the `reachability` job which is advisory", and Section 15 accepts the large PR "mitigated by reviewing every constituent PR on its integration branch". Two of the named gates (SQLDelight drift, reachability) are exactly the ones the plan relies on and they will first run on the single ~20-story PR to `main`. That PR will also feed `diff-coverage` (changed-files coverage plus mutation) a diff roughly an order of magnitude beyond what its 60-minute cap was sized for (INFERRED from the cap; run time not measured).

Fix (pick one, state it in Section 10a):
- Preferred: replace the integration-branch model with a walking skeleton merged to `main` incrementally. The scan is NOT transitive (VERIFIED, `scripts/ci/reachability-scan.py` `live_names`: a type is live if its name appears in ANY other production file; only same-file liveness is propagated). A type therefore needs one textual reference from another production file, not a path from a root. Land `PostSyncProjectJob` early as a thin, flag-gated shell wired in the composition root, with `ProjectSourceCollector` as a stub that each later story extends (each extractor/story adds its own call into the collector in its own PR). Every story then merges to `main` with full CI and no unit PR.
- Alternative: add `feat/home-sketch-*` to the `ci.yml` `pull_request.branches` list in a first DIRECT PR, and add a path-scoped timeout for `diff-coverage`. State that the unit PR to `main` will still need a `diff-coverage` run and give its expected runtime.

### B3. `replaceOwnedPage` cannot meet its own acceptance criteria on `ActiveTargetWriter`
Evidence:
- `ActiveTargetWriter` is a re-rendering writer: it serialises the whole page through `LogseqPageSerializer` and `GraphWriter.savePage` (`merge/ActiveTargetWriter.kt:85-125`), and `TargetWriterContractSuite` states "Cases compare BLOCK DATA ... not file bytes: the active path re-renders the whole page" (`businessTest/.../merge/TargetWriterContractSuite.kt:36-37`). Story 5.4a/5.4b require, against BOTH writers, "replace-unchanged = byte-identical" and "CRLF preserved" (LF/CRLF "taken from the existing file"). `GraphWriter`/`LogseqPageSerializer` use `appendLine` and have no CRLF input; the Active path cannot honour either.
- The marker `stelekit-digest-hash:: <sha256 of the body>` is checked by `OwnedFileGuard` against the on-disk body. On the active graph the on-disk bytes are the serializer's output, so the hash must be defined over serializer output, and any later re-save by the app (a normalisation or an editor open/close that touches the page) changes bytes without a user edit and yields a false `EditedByUser`.
- ADR-005 and Story 5.7 promise byte-identical digests across devices (`TwoDeviceConvergenceTest`, "zero diff"). Device A on the active path writes `LogseqPageSerializer` bytes; device B on the off-graph path writes `MergeRenderer.renderNewPage` bytes (`MarkdownTargetWriter`). Different renderers, different bytes, so a git conflict on a generated file is the expected outcome whenever both devices regenerate before syncing.
- Story 5.4a also has two hashes with no stated relation: `expectedPriorHash` (the `fileHash` of the file bytes) and the in-file `stelekit-digest-hash` (body hash).

Fix: define one canonical rendering and one hash.
1. The digest hash covers a canonical block-data form (like `BlockContentHash.of`, `merge/TargetWriter.kt:66-72`), not bytes. `Unchanged` is decided on that form on both writers.
2. The contract-suite cases for owned pages compare block data plus the marker, as the suite already does. Drop "byte-identical" and "CRLF" from the Active case; keep them for `MarkdownTargetWriter` only, which really is byte-faithful.
3. For cross-device convergence either render the owned page through one renderer on both paths (the Active writer writes the exact bytes through a `GraphWriter` raw-file method if one exists; otherwise accept that the Active path cannot be byte-identical) or make the git-merge of an owned page a non-event: add a `.gitattributes` `merge=ours`-style rule for the digest path, or treat a pulled conflict as "regenerate". Pick and test one; `TwoDeviceConvergenceTest` must run device A on the Active writer and device B on the off-graph writer.
4. Spike 5.1 should answer this first; its AC (c) asks about `MergeUndo` but not about byte stability.

## MAJOR

### M1. `DirectSqlWriteOptInAllowlistTest` and `@DirectRepositoryWrite` are missing from Stories 2.2/2.3
`DirectSqlWriteOptInAllowlistTest` pins every production `@OptIn(DirectSqlWrite` line per file with a total of 41 (`businessTest/.../db/DirectSqlWriteOptInAllowlistTest.kt:18-40,60-62`, `baseline_should_BeFortyOne`). Any new `SqlDelightSketch*Repository` or helper that opts in fails it, and the sum assertion needs bumping. Repository write methods are also annotated `@DirectRepositoryWrite` (`repository/AssetRepository.kt:35,61-65`, `DirectRepositoryWrite.kt`). Neither appears in 2.2/2.3 Files lists. Fix: add both edits to 2.2/2.3, and prefer `writeActor.execute { ... }` lambdas in the repository over five new typed `DatabaseWriteActor` methods (the actor is already large and `AssetIndexService` uses the lambda form); that keeps the opt-in count at +1 file.

### M2. The post-sync hook is placed in a Composable file that does not hold the coordinator
Story 5.7 puts the subscription in `ui/GraphContentGitSyncSetup.kt` and says it subscribes to `GitSyncCoordinator.syncState`. That file is `@Composable` wiring that owns a `GitSyncService` (`rememberGraphContentGitSyncStack`, `:84-127`), is torn down per active graph via `DisposableEffect`, and has no `GitSyncCoordinator`; the coordinator is a `private val` inside `StelekitViewModel` (`ui/StelekitViewModel.kt:436`), exposed only as `viewModel.syncState` (`:449`). A heavy job (repositories, `TargetWriterRouter`, `LlmSettings`, `JobTracker`) built inside a composable has composition lifetime, not app/graph lifetime, and cannot meet the CLAUDE.md rule that long-lived classes own their scope. Fix: make `PostSyncProjectJob` a plain class owned by `StelekitViewModel` (or `GraphManager`) with its own `SupervisorJob + CoroutineExceptionHandler` scope, started from `GitSyncCoordinator.observeSyncState()` through an injected callback; keep only the registration call in `GraphContent*` if a hook there is unavoidable. `SyncState.Success(localCommitsMade, remoteCommitsMerged, lastSyncAt, ...)` is the right trigger (`git/model/SyncState.kt:32-37`). Correct the "digest writes for a graph that is not active" AC: the coordinator only reflects the active graph's service, so the inactive-graph case arises only from a graph switch mid-job.

### M3. The writer API diverges from the existing error/outcome taxonomy and breaks every `TargetWriter` implementer
- Plan: `Either<WriteRefusal, WriteOutcome>` with new `NotOwned`/`EditedByUser`/`Retryable(PageBeingEdited)`. Actual convention: every method returns `Either<DomainError, ...>`; refusals are `DomainError.MergeError.WriteRefused(WriteRefusedReason)`; retryable is `DomainError.MergeError.Retryable(message)` produced from `WriteRetryReason.PageBeingEdited` (`error/DomainError.kt:297-305`, `merge/ActiveTargetWriter.kt:35-45`). The router's retry loop keys on `MergeError.Retryable` (`TargetWriterRouter.kt:115`); a separate `Retryable` type would bypass it.
- `WriteOutcome` is a sealed interface (`Created(path, contentHash)`, `Updated`, `Unchanged`); adding `Replaced` forces updates at every exhaustive consumer (`PageMergeService`, `capture/RouterOffGraphRoute.kt`, tests).
- Adding an abstract method to `TargetWriter` breaks: `MarkdownTargetWriter`, `ActiveTargetWriter`, `RoutedTargetWriter`, `capture/ActiveWriteHooks.kt` `RefusingWriter` (`:67`), and the test fakes `FakeTarget` (3 files), `FaultyTarget`, and `object : TargetWriter by real` in `MergeUndoTest`. None of these are in the 5.4a/5.4b file lists.
Fix: add `NotOwned` and `EditedByUser` as `WriteRefusedReason` variants and reuse `Retryable`; return the existing `Created`/`Updated`/`Unchanged` (an owned replace is `Updated`); put `replaceOwnedPage` on a new small interface `OwnedPageWriter` that only the two real writers and `RoutedTargetWriter` implement, obtained through `TargetWriterRouter.withWriter`, so the shared contract and its fakes are untouched. List the added `when` sites for the new `WriteRefusedReason` variants (`toUserMessage` mapping at `DomainError.kt:424`).

### M4. "Share the atomic-write helper of `ImageSidecarManager`" refers to code that does not exist
`ImageSidecarManager.writeSidecar` calls `fileSystem.writeFile(path, json)` (`db/sidecar/ImageSidecarManager.kt:52-56`): no temp file, no rename. The real atomic mechanism is `FileSystem.supportsAtomicReplace` / `replaceFileAtomically` (`platform/FileSystem.kt:126-132`, default `false`) plus `MarkdownTargetWriter`'s temp+rename with `StaleTempSweeper`. `SAF_ATOMIC_REPLACE_VERIFIED = false` (`merge/TargetWriterCapabilities.kt:14`), so on an Android SAF graph (the main mobile case) neither atomic replace nor off-graph writes are available. Stories 2.5/3.7 and ADR-005 depend on an atomic sidecar write and a "pulled sidecar is never overwritten silently" guarantee. Fix: Story 2.5 extracts the temp+rename+sweep logic from `MarkdownTargetWriter` into a shared `AtomicFileWriter` (or states the non-atomic fallback and its crash window explicitly, with reconcile treating a truncated JSON as "no sidecar"), and says what happens on SAF graphs. Sidecar writes also bypass `GraphWriteLock`; say so deliberately (it is not markdown) or take the lock.

### M5. How a project finds its source pages and files is unspecified, and the extractors ignore the repo's graph-read rules
`ProjectSourceCollector` (5.8) is tested only on `FIX` text. Nothing says where production inputs come from: which pages belong to a project (the registry holds aliases, not page identity; fixtures must not name pages), how the sidecar records the binding (page uuids?), whether text comes from the DB blocks or the files, and how `source_hash` (5.7 relevance check) is computed without reading all of it each sync. Consequences:
- Pages loaded as index-only stubs (`isContentLoaded = false`, `GraphLoader.kt:1444-1470`; `ActiveTargetWriter` handles this via `WriteRetryReason.PageNotLoaded`) would silently contribute no tables.
- CLAUDE.md "Graph-scale reads must be paginated, projected, or chunked" applies: use `getPagesByNames`/uuid point lookups, never a scan.
- `BlockParser.tryParseTable` is `private` (`parsing/BlockParser.kt:215`); Story 5.2 says "consumes `TableBlockNode`" and "characterization test of `tryParseTable`", but the public entry is the block parse, not that function.
Fix: add a Story (before 5.8) "Project source binding": sidecar `sources[]` of `{kind, pageUuid | assetUuid, hash}`, a `ProjectSourceReader` that reads bounded and handles stubs (retry on the next trigger, count `unloaded=N`), and name the public parse entry point 5.2 uses.

## MINOR

1. **Schema merge-queue wording.** "The two never conflict textually" is false for generated sources: `SteleDatabaseQueries.kt` is a single 8,551-line file and `kmp/SteleDatabaseImpl.kt` 487 lines (VERIFIED by `wc -l`); every new query and `CREATE` lands in them, and 6.2a changes the generated `Image_annotations` row class, which ripples into mappers. Rule to state: on a rebase conflict under `kmp/src/generated/`, take main's copy and re-run the generator, never hand-merge. With integration branches (B2) the "second PR to merge" is the unit PR, possibly weeks later; the ordering "6.1, then 2.1, then 6.2a" has no meaning then. Moot if B2's skeleton option is taken.
2. **Story 5.1 "a failing probe test per writer".** A deliberately failing test in a DIRECT PR to `main` makes CI red. Land it as a characterization test of the current behaviour (asserts today's `ExistingContentChanged` refusal) and let 5.4a flip it.
3. **`MergeUndo` "ignores owned pages" (5.4b).** `MergeUndo` replays a `MergeManifest` of merge runs (`merge/MergeUndo.kt:45-96`); `DigestWriter` writes through `router.withWriter`, not `PageMergeService`, so nothing records an owned page in a manifest. Drop the requirement or state which manifest could include it.
4. **LLM settings semantics.** (a) The picker and settings paths in Story 5.6a are wrong: they are `ui/components/settings/PerFeatureProviderPicker.kt` and `ui/components/settings/LlmProviderSettings.kt`, not `ui/settings/`. (b) `PerFeatureProviderPicker` offers "Auto" for every `LlmFeature` (`:90-97`), and `LlmProviderSettings` iterates `LlmFeature.entries` (`:121`), so `PROJECT_ANALYSIS` appears automatically with an "Auto" item whose stored value (blank) the new rule treats as disabled; remove "Auto" for this feature and give the resolution one home, because four call sites already copy the `null -> registry...firstOrNull()` pattern (`LlmSynthesisService.kt:61-69`, `VoicePipelineFactory.kt:56-58`, `CaptureEnrichmentCoordinator.kt:136-138`, `GraphContentTagVoiceSetup.kt:127-132`). (c) `LlmCredentialMigration` writing the disabled sentinel is redundant with "unset = disabled" and would make the picker show "Disabled" rather than "Not configured"; and its steps are one-shot, marker-guarded (`KEY_*_MIGRATED`), so it would not even cover existing installs without a new marker. Drop it. (d) Where the per-provider acknowledgement is persisted and when it is invalidated (provider or model changes) is unspecified; a custom OpenAI-compatible provider can be local, so the "leaves this device" text must depend on the provider kind. (e) `GatedPrompt` with a private constructor: in Kotlin an outside class (`OutboundLlmGate`) cannot call it, so a factory must exist, and any factory visible to the module weakens the guarantee; use the repo's own pattern (`@RequiresOptIn(Level.ERROR)` annotation as in `DirectSqlWrite`/`DirectRepositoryWrite`) on an `internal` constructor that only the gate opts into, plus the planned reflection test.
5. **No entry-point test for the hook.** R-NOWIRE correctly adds no catalog line, but the hook is the single integration point of 20 stories and the repo's own wiring philosophy (`WiringAudit` KDoc: text match "cannot see dead code behind a live name") says reachability alone does not prove it runs. Add one test that drives `WiredAppFixture` (or `StelekitViewModel` with a fake `GitSyncService`) through `Success` and observes a digest write.
6. **`SidecarReconciler` has no named caller.** Story 2.5 says it runs "at graph open and on `syncState` Success"; Story 5.7's job description does not call it. Reachability will pass (any mention counts) but the behaviour may never run. Name the call in 5.7.
7. **Pure logic placed in `businessTest` (JVM-only).** `SvgReader`, `LabelBinder`, `SheetCalibration`, `GeometryExtractor`, the extractors, `DigestRenderer`, `LlmPayloadBuilder` and `OutboundLlmGate` are pure commonMain code but their tests (fixture-bound) run only on JVM; Story 4.1a/4.1b claim wasmJs readiness on compile-only evidence. CLAUDE.md prefers `commonTest` for pure logic and `./gradlew :kmp:wasmJsBrowserTest` now runs a real browser (project memory). Add a small inline-string SVG and table case in `commonTest` (registered under R-REG) so wasm actually executes the reader and extractors once.
8. **Reachability coverage of Section 10a is more conservative than the script requires, and one claim needs a caveat.** Because liveness is name-in-any-other-file (not rooted), the unit model is sufficient but not necessary (see B2). Two traps to document: KDoc/comment mentions count as references, so a type mentioned only in a comment passes the scan while being dead; and `@Serializable` DTOs and `*UiState` types are filtered out (`filter_reason`), so `ProjectModelJson` and `SketchUiState` never need a referrer.
9. **ADR consistency nits.** ADR-006 says `Created` goes "through the normal new-page path" while 5.4a's `OwnedFileGuard` is "checked under `GraphWriteLock(target)` with a `fileHash` precondition" for replace only (state the Created path's collision handling: `NotOwned` if the file appears between check and write). ADR-009 item 1 still lists the order "6.1, 2.1, 6.2a" as a rule while item 6 makes the second merger the unit PR (see MINOR 1). ADR-005's "atomic-write helper ... generalised" repeats M4's false premise. The plan's Section 18 states "45 findings: 5 BLOCKER, 22 MAJOR, 18 MINOR" but the table lists fewer rows than that count (not recounted here; it is not a correctness issue).
