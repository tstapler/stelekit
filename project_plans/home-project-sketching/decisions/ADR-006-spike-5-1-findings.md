# ADR-006 amendment: Story 5.1 spike findings (owned-page replace on the active writer)

Status: findings for ADR-006 (still PROPOSED; OD-H7 answered YES, scoped exception: replace only app-owned digest pages whose canonical-block hash still matches) | Evidence: `kmp/src/businessTest/kotlin/dev/stapler/stelekit/merge/OwnedPageReplaceSpikeTest.kt` (12 characterization tests, synthetic data only). Labels: VERIFIED = a test in that file pins it; READ = read in code, not executed.

## Verdict

The ADR-006 recognition rule "marker in the page properties OR in the first block" is half wrong for the active writer. **A page-property marker does not round-trip.** It exists only in the live DB row until the page is next loaded from disk; after that it is a run of body blocks. **A marker on a visible first block round-trips** through write, reload and no-op re-save, byte-stably. Decision for 5.4a/5.4b: the marker is the properties of a first block with non-empty visible text, recognised by `stelekit-owned:: true` on block 0; `OwnedHash` is over the blocks after block 0.

## Findings

(a) READ and VERIFIED. `TargetWriter` has no replace method. `RoundTripGuard.verifyBytes` (`merge/RoundTripGuard.kt:167`) requires the original to be a subsequence of the output, so a splice cannot replace a block. On the active writer, `write` of a page with one changed existing block returns `WriteRefused(NotRoundTrippable(ExistingContentChanged))` and writes nothing (`writeRefusesToReplaceAnExistingBlock`).

(b)(i) Marker placement. All VERIFIED:
- `write` with `properties = {stelekit-owned, ...}` renders bare `key:: value` lines above the blocks (`pagePropertyMarkerIsDemotedToBodyBlocksOnReload`). The live DB row keeps them as page properties. A fresh `GraphLoader` over the same file returns `properties = {}` and the lines as the first body blocks (`stelekit-owned:: true`, ...). This is the case the code comment at `ActiveTargetWriter.kt` ("the loader reads them back as a block, not as properties") predicts.
- Of four on-disk shapes, only an empty bullet followed by indented properties (`-` then `\tkey:: v`) is read back as page properties (`onlyAnEmptyBulletWithPropertiesIsReadBackAsPageProperties`). The active writer cannot emit it: a block with empty content is refused as `InsertedContentChanged` (`activeWriterCannotProduceTheEmptyBulletForm`).
- A first block with visible text (`Generated by SteleKit. Edits are overwritten.`) carrying the marker as block properties renders as `- text` plus tab-indented `id::`, `stelekit-owned::`, `stelekit-digest::`, `stelekit-digest-hash::`. It survives write, fresh-loader reload and a no-op re-save with identical file bytes (`markerOnAVisibleFirstBlockSurvivesWriteReloadAndResave`).

(b)(ii) Canonical hash. VERIFIED. Over the body blocks after the marker block, with content, sorted properties minus `id`, and children, uuid-free, the sha256 is identical after write, fresh reload and a no-op re-save (`canonicalBodyHashIsStableAcrossWriteReloadResaveInBlockForm`). A uuid-bearing `BlockContentHash.of` is also stable here because the writer labels every block with `id::`; prefer the uuid-free form so the hash does not depend on labelling. A hash over the whole page in the page-property form differs between the live DB and the reload (the marker lines become blocks), which would be a false `EditedByUser` on the first restart (`hashOverTheWholePageIsNotStableInPropertyFormBecauseReloadAddsMarkerBlocks`). A user edit changes the hash (`aUserEditChangesTheCanonicalHash`). Re-save bytes are stable on the active writer, so the "no byte criterion for the Active writer" rule in ADR-006 still holds but is not needed for the hash.

(b)(iii) Replace path.
- Composing the existing public primitives works: `removeBlocks` (all blocks, hashes from `BlockContentHash`) then `write` of the new page returns `Updated` and the new marker value (`stelekit-digest-hash:: h1`) reaches the DB and, after reload, the file. Replacing the marker block means removing it too, because `write` refuses any change to an existing block (`replaceComposedFromPublicPrimitivesWorksButLeavesAnEmptyWindow`).
- It is two calls with an empty page between them (0 blocks, 0 bytes of file; the marker is gone too). A crash or lock release in that window leaves an empty page that `NotOwned` would then refuse. So 5.4b needs ONE method on `ActiveTargetWriter` that deletes and re-inserts inside one `GraphWriteLock` hold with the existing `rollbackPage` pattern. It must live inside the class: `findPage`, `loadExisting`, `deleteBlocks` and `rollbackPage` are private.
- `Retryable(PageBeingEdited)` applies on the remove path unchanged (`pageBeingEditedIsRetryableOnTheRemovePath`); the replace method must check `isPageDirty` first, as `write` and `removeBlocks` do.

(b)(iv) VERIFIED. `GraphWriter` has no raw-file write for a page: its page entry points are `savePage`, `deletePage`, `queueSave`, `renamePage`, `movePageToSection` (`graphWriterOffersNoRawPageWrite`). Informational: convergence rests on the canonical hash either way.

(c) Conflicting digest file. READ, with the import side VERIFIED. `LogseqMergeDriver` returns lines with `<<<<<<<` markers when it cannot merge (`git/merge/LogseqMergeDriver.kt`), `ConflictMarkerGuard` refuses to commit such files (`git/ConflictMarkerGuard.kt`), and `GraphLoader` (`db/GraphLoader.kt:1853`) refuses to import a file with markers. The test feeds a conflicted file to the live loader: the DB keeps the pre-conflict blocks and the file keeps the markers (`aConflictedFileIsNotImportedSoOnlyTheFileRevealsTheConflict`). Consequence: `OwnedFileGuard` must classify `Conflicted` from the FILE text (`ConflictMarkerDetector.hasConflictMarkers`), before it trusts the DB-derived hash; the DB alone looks clean.

(d) Files that change. READ (not built; the spike adds a test, not production code):
- `ActiveTargetWriter`: add the `OwnedPageWriter` implementation (single locked replace).
- `merge/TargetWriter.kt`: the three new `WriteRefusedReason` variants.
- `TargetWriterRouter`: NO change. `withWriter(target) { it as? OwnedPageWriter }` already receives the `ActiveTargetWriter` from `activeWriterFor`; ADR-006 lists the router as changing, this finding removes it.
- `RoutedTargetWriter`: changes only if a caller holds the routed wrapper; the production digest job can use `router.withWriter` directly, which would remove this file as well (decide in 5.4b).
- Unchanged by construction: the `TargetWriter` interface, `MarkdownTargetWriter`, `RefusingWriter`, and the 10 test fakes, because `OwnedPageWriter` is a separate interface; the whole `businessTest` source set compiles with the spike test alongside them.

## What changes in ADR-006 and the stories

- Decision section: replace "page properties `stelekit-owned:: true`, ... Recognition accepts the marker in the page properties OR in the first block" with "the marker is the properties of block 0, a block with visible text; recognition is `block0.properties["stelekit-owned"] == "true"`; page properties are not used." Story 5.2's self-exclusion of pages "whose page properties OR first block carry `stelekit-digest::`" reduces to the first-block test (keep the page-property test only as a harmless extra).
- `OwnedHash` is the uuid-free canonical form over blocks 1..n, excluding block 0 (the marker block carries the hash itself). It cannot include `stelekit-digest-hash` without circularity, which this form avoids.
- 5.4a: `OwnedFileGuard` takes file text and the parsed blocks; order is conflict markers (file), marker present (block 0), hash compare. Add a test that a page-property-only marker is NOT recognised, so nobody reintroduces it.
- 5.4b: stays L. The single locked replace is the real cost; the spike removes the router and likely the `RoutedTargetWriter` edit but adds the delete-all-including-marker-then-insert detail and the empty-window rollback test. Flip `writeRefusesToReplaceAnExistingBlock` and `replaceComposedFromPublicPrimitivesWorksButLeavesAnEmptyWindow` there.
- 5.4c and 5.7b: the digest page's first line is user-visible ("Generated by SteleKit. Edits are overwritten.") and must be in the generated body template; `DigestSelfFeedTest` must cover it.
- OD-H7 is YES, so 5.4x is not built; the CLAUDE.md scoped-exception paragraph is still a separate owner-approved commit in 5.4a.
