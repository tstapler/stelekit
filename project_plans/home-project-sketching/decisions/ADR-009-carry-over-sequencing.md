# ADR-009: Carry-over work is a separate lane; schema edits use a merge-queue rule; E1-E5 merge incrementally as a walking skeleton behind `homeSketch`

Status: ACCEPTED (replaces the two-integration-branch design of the first patch) | Date: 2026-11-09 | Epic: E6

## Context
PR #564 (bench harness) and #565 (Library, +4390/-130, 67 files) are open drafts; both touch areas this project extends. C.1 and the sketch schema both edit `MigrationRunner.kt`, `SteleDatabase.sq` and generated sources. CI runs `scripts/ci/reachability-scan.py --check-baseline`, which is NAME-BASED, not rooted: a production type is live if its name appears in any OTHER production file (same-file liveness propagates), so a type needs one textual reference from another production file, not a path from a root (VERIFIED in the script). `.github/workflows/ci.yml` triggers only for `pull_request: branches: [main, master]`, so a PR into an integration branch would run no `reachability`, `sqldelight-sync` or `diff-coverage` job.

## Decision
1. WALKING SKELETON, no integration branch. Every story is a PR to `main` with full CI. The skeleton spine lands first (Stories 5.0 and 5.7a, one slice in W0 with no story dependency; every collector-stage story declares 5.7a in its `Deps`): a default-off `homeSketch` flag, `ProjectBridgeSettings`, and a thin `PostSyncProjectJob` owned by `StelekitViewModel` with a `ProjectSourceCollector` shell. Each later story's PR ends with the single production reference that mentions its topmost type (a collector stage, a repository registration, a screen-host entry or a writer implementation), listed per story in plan Section 10a. A leaf chain with no honest consumer yet merges as a slice of at most three stories in one PR (the slices are named in Section 10a). Because no integration branch remains, no `ci.yml` trigger change is needed.
2. Schema edits are NOT a story dependency. `MigrationRunner.all` is append-only; sketch SQL goes at the END of `SteleDatabase.sq`; C.1 is an `AddColumn` in the `image_annotations` section. Generated sources conflict (single large generated files): on a rebase conflict under `kmp/src/generated/`, take main's copy and re-run the generator, never hand-merge. With every story merging to main separately, the merge order 6.1, then 0.3 (it adds one UPDATE query to the asset section of `SteleDatabase.sq` and regenerates sources), then 2.1, then 6.2a is a real queue.
3. Do not duplicate #565 work: stories 6.7, 6.8, 6.10 are blocked until #565 is merged. Same for 6.9/6.11 and #564. Story 0.3 edits `AssetItemCard`, `AssetBrowserViewModel` and `AssetBrowserScreen` (exhaustive `when` sites that 6.7 deletes) minimally and rebases onto #565; it ships at least one release before `homeSketch` can graduate because already-released builds decode `media_type` with `valueOf` and would crash on a `DRAWING` row.
4. The Epic C stories run as one serial lane (shared `ui/annotate` files, loupe code) in parallel with E1-E5. The sketch no longer waits on the lane: `PlacementController` is built new in Story 3.0 with the sketch as its first consumer, and Story 6.5a adopts it in the annotate editor afterwards.
5. Story 6.0 first audits which C.* tasks already shipped and rewrites 6.2a-6.6 to the remainder.
6. Owner-gated items (A.4/A.5 behaviour changes, v0.107.0 asset recovery, B.7b promotion) stay at the end of the lane and never start their mutating steps without their gate evidence.

## Consequences
Feedback (CI, `diff-coverage`, mutation, `reachability`) arrives per slice instead of at one end-of-project PR. Everything is dormant behind the flag until graduation. The critical paths are recomputed by script in plan Section 10c.
