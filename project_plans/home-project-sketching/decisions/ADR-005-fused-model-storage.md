# ADR-005: Fused model storage: in-graph sidecar bundle (synced, authoritative, sheets and primitives included), DB rows as cache, owned digest page in the wiki

Status: ACCEPTED (amended by plan review patches 1, 2 and 3; the refTable placement depends on OD-H8) | Epic: E2, E5

## Context
Answers requirements open question 2. The `.stelekit/` directory is documented as NOT committed to git (`SidecarManager` KDoc), so a sidecar there is authoritative only on one device (architecture review M6). Two devices syncing the same graph must see the same sources and produce the same digest bytes, or the digest page conflicts in git (adversarial review M8). Round 3 found that the first sidecar design carried no sketch geometry, so "a sketch drawn on one device reaches the others" was false (R3-A B1), that reconcile had no base to detect "both changed" (R3-A M1) and that a git conflict in the JSON was read as "absent" (R3-V M4).

## Decision
- Authoritative: the sidecar BUNDLE under `<graph>/assets/stelekit-sketch/<slug>/`, inside the graph so it syncs: `project-model.json` (`schema:1`: registry, observations, project zones, `sources[]`, and a `sheets[]` index of `{uuid, kind, viewDirection, unit, scaleSixteenthsPerUnit, layers, zones, position, sourceAssetUuid?, fileSha256}`) plus one `sheets/<sheetuuid>.json` per sheet holding its primitives in sixteenths. Per-sheet files keep two devices that edit different sheets from touching the same file; the 10 000-primitive cap bounds each file and a test asserts a full sheet encodes under 2 MiB. `modelRevision` is informational. `.stelekit/` holds caches only. The alternative "primitives are device-local, drop the word authoritative for the drawing" was considered and rejected: the stated intent is that a sketch reaches the other devices.
- Writes go through `platform/FileSystem` using the shared `AtomicFileWriter` (Story 2.0, `platform/`): temp file, `replaceFileAtomically` when `supportsAtomicReplace`, else temp plus read-back hash plus rename, with the compare-and-swap precondition and original-restore of `MarkdownTargetWriter.replaceFile` preserved. It runs on jvm and android only. Where `writeFileBytes` is unsupported (wasmJs, iOS: no override exists and `renameFile` defaults to false, VERIFIED) its `mode` is `UNSUPPORTED`, the store reports `SidecarUnavailable` and the project stays device-local with a visible note; there is no unsafe direct-overwrite fallback. `SAF_ATOMIC_REPLACE_VERIFIED` is false, so on an Android SAF graph the temp-plus-rename fallback is the normal path. `ImageSidecarManager.writeSidecar` is a plain `writeFile` and is NOT the model. Sidecar writes deliberately do not take `GraphWriteLock` (JSON under `assets/`, not markdown); `ProjectSidecarStore` serialises them with its own mutex and defers them while a git sync or merge is in flight.
- File state: every sidecar file read is `Absent`, `Valid` or `Corrupt(ConflictMarkers | Truncated | InvalidJson | InvalidUtf8 | NewerSchema)`. Only `Absent` means "no sidecar". A `Corrupt` file is never overwritten: the local state is saved beside it as `project-model.conflict-<hash8>.json` and the conflict is surfaced.
- `<slug>` is the opaque generated id `proj-<6 hex>`; the display name is a column and a sidecar field but never appears in a path, a ref or an LLM payload.
- Cache: `sketch_*` tables, including `fusion_results_json`, `source_hash`, `last_digest_hash`, and the reconcile base `base_revision` and `last_synced_sidecar_hash` on `sketch_projects` (single definition in plan Section 5).
- Reconcile (Story 2.5) is three-way over bundle hashes: L = hash of the bundle serialised from the local database, B = `last_synced_sidecar_hash`, P = hash of the files on disk. P = L: record B. L = B, P different: rebuild the database from the pulled bundle. P = B, L different: write the bundle. All three different, or B null with both present and different: keep the pulled files, save the local state as a conflict file, surface it. P absent with B set: restore from the database. A pulled sidecar is never overwritten silently. After a rebuild the repository revision token changes and the open editor reloads and drops its pending autosave.
- `closet.yaml` is chosen once through a file picker, but its CONTENT is snapshotted into the sidecar as `sources/yaml-<hash8>.yaml`; no path, SAF URI or filename is stored, so every device derives the same observations. The app never scans the wiki repo.
- YAML parsing: a hand-written minimal commonMain subset parser (Story 5.3a), no dependency and no build-file change. Rejected: a KMP YAML library (none in the build; the existing TOML dependency is already excluded from wasmJs).
- Human copy: one OWNED digest page per project, written per ADR-006 (or, if OD-H7 is "no", an asset digest under `exports/`).

## Layout, asset indexing and privacy of the synced files
`<graph>/assets/stelekit-sketch/<slug>/` holds `project-model.json`, `sheets/`, `sources/`, `exports/` and `drawings/`. The asset index skips everything except `drawings/` (Story 0.3, by path inside `AssetIndexService`), and files under `drawings/`, or any `.svg` carrying the `stelekit-sketch-export` marker wherever it was copied, are classified `DRAWING` so they never reach the cloud pipeline. `*.tmp` leftovers are skipped by the index and ignored by git. The synced bundle maps opaque ids to wiki page UUIDs and content hashes but NOT to page titles: the `refTable` (opaque id to human locator, including titles) is a device-local cache under `.stelekit/` rebuilt from the local database (default of OD-H8: no titles in anything git-synced). The yaml snapshot is the owner's raw source text and lives only under `sources/`, which is not indexed.

## Consequences
A sketch drawn on one device reaches the others through normal git sync of `assets/`, sheets and primitives included; two devices that edit different sheets merge cleanly in git. A text conflict in one file is surfaced rather than lost. Schema lives in `ProjectModelJson` and `SheetJson` with golden tests; any field change needs a `schema` bump. The first task of Story 2.5 checks the graph's `.gitattributes` for an LFS rule that would capture these JSON files.
