## 1. Kotlin/Wasm ↔ JS binary-data interop pitfalls

- Kotlin/Wasm's JS interop is `JsAny`-based (not the direct `unsafeCast` available in Kotlin/JS/IR). Per the Kotlin docs (`kotlinlang.org/docs/wasm-js-interop.html`) and community reports (Kotlin Slack, kotlinx-browser `arrayCopy.kt`), there is **no zero-copy view** from a Kotlin `ByteArray` into a JS `Uint8Array` the way Kotlin/JS could `unsafeCast`. `kotlinx-browser`'s own `arrayCopy.kt` implements element-by-element copy loops for typed-array conversions — that's the sanctioned approach, not a shortcut.
- Concretely: converting a `ByteArray` of ~24M bytes (3000×2000×4 RGBA, or ~18M for the eventual JPEG-quality-scaled buffer) into a `Uint8Array` for `putImageData`/`toDataURL` must go through either (a) a per-element copy loop across the Wasm/JS boundary, or (b) a single `js("...")`-declared bulk-copy helper that operates entirely on the JS side (e.g., allocate the `Uint8ClampedArray` in JS, then write into it from a single `js()` snippet that loops in JS, not Kotlin) so the 6M-call problem the project brief already flags doesn't just move from "one call per pixel" to "one call per byte" (4x worse).
- Watch for accidental JsAny boxing: every value crossing the `external fun ... : JsAny` boundary is boxed. A loop that calls a `js("...")`-declared setter function once per element (as `SqliteWorkerInterop.kt`'s `jsArrayPushString` pattern does for small arrays) is fine for dozens of calls but is exactly the anti-pattern the brief warns against at pixel-buffer scale — the fix must batch the entire buffer into a single `js()` call (e.g., pass the `ByteArray` as an `Int8Array`/similar bulk transfer, or build the pixel buffer JS-side from typed-array APIs and pass only handles/offsets across the boundary).
- No first-party fast path currently ships in Kotlin/Wasm stdlib for `ByteArray -> Uint8Array` (as of the Kotlin version pinned in this repo — confirm exact version in `gradle/libs.versions.toml` before implementation; not checked here). Plan for a hand-rolled bulk-copy helper and benchmark it, don't assume stdlib parity with Kotlin/JS.

## 2. Canvas 2D `toDataURL`/`putImageData` pitfalls for large images

- **Size limits are real and browser-specific.** Multiple browsers cap canvas *area* (not just width or height) — Chromium enforces `width * height <= 16,777,216` px (~4096×4096 for a square canvas; a 3000×2000 image is 6,000,000 px, well under this, but the brief's plan should still validate against this ceiling since Logseq image annotations could plausibly exceed it for very large source images). Firefox and Safari have historically had different per-axis limits (~32,767px per axis on some engines) and different area caps; there's no single authoritative cross-browser number, so any implementation should clamp/scale before hitting canvas and treat overflow as a produce-empty-image failure mode (canvas silently returns a blank/empty result on overflow rather than throwing).
- **`toDataURL()` is synchronous and blocks the main thread**, including the encode step itself — for a multi-megapixel image this can visibly freeze the UI (jank/ANR-style stall) for hundreds of milliseconds to seconds depending on device. The documented, non-blocking alternative is `canvas.toBlob(callback, 'image/jpeg', quality)`, which is asynchronous. Given this repo already ships COOP/COEP cross-origin isolation (`index.html:18-20`), `OffscreenCanvas` inside a Web Worker (mirroring the existing `SqliteWorkerInterop.kt` worker pattern) is the more scalable option if blocking becomes a measured problem — but adds real complexity (worker message-passing, transferable `ImageBitmap`/`ArrayBuffer`) that should be scoped as a stretch goal, not baseline.
- **Data-URL size and memory overhead.** `toDataURL()` returns a base64 string held entirely in memory in addition to the source canvas pixel buffer and the browser's internal JPEG-encode scratch buffers — for a 3000×2000 RGBA source that's ~24MB raw, plus the encoded JPEG (base64 is ~33% larger than binary), plus whatever intermediate buffers the browser's encoder allocates. Multiple browsers cap data-URL string length (Chrome/Firefox ~2GB nominal but practically constrained well below that by available heap; Safari has historically been much stricter, closer to ~100MB) — unlikely to be hit for a single JPEG export at this resolution, but worth a defensive check/catch rather than assuming success.
- **`putImageData` batching correctness**, not just performance: `putImageData` writes raw, non-premultiplied pixel data directly, bypassing any canvas compositing/color-management the `drawImage` path would otherwise apply — if the plan uses `putImageData` for speed (avoiding `drawImage`'s slower path), verify that skips any color-space conversion needed if the source `ImageBitmap`'s color space differs from the canvas's (usually sRGB, generally fine, but confirm Skia's `ImageBitmap` doesn't tag a wide-gamut/P3 buffer that would then get silently reinterpreted as sRGB).

## 3. Base64 encode/decode pitfalls for large byte arrays

- The classic `btoa(String.fromCharCode.apply(null, bytes))` or `String.fromCharCode(...bytes)` pattern **throws `RangeError: Maximum call stack size exceeded`** once the array exceeds roughly 65,000–100,000 elements (call-stack argument limit, not a base64-specific limit) — well below the ~6-24MB buffer sizes involved here. This is a well-documented recurring bug (see `mathiasbynens/base64#13`, `unjs/undio#41`, `ollama-js#89`) and is exactly the kind of thing that will pass on small test images and blow up in production on a real 3000×2000 photo.
- The safe pattern is chunked conversion: iterate the `Uint8Array` in fixed-size chunks (commonly 8K–32K elements per chunk) building up the string incrementally, or better, avoid manual base64 entirely if `toDataURL()` is used (the browser does the base64 encode internally and correctly) — manual base64 is only needed if bytes are produced by a JS JPEG encoder (jpeg-js path) rather than obtained via `toDataURL()`.
- If going the `toDataURL()` route, the resulting string still needs decoding back to a `ByteArray` on the Kotlin side (strip the `data:image/jpeg;base64,` prefix, `atob()`/manual base64 decode, then copy into a `ByteArray`) — same chunking/bulk-copy discipline from pitfall #1 applies to this decode step too, it's not a one-way concern.
- Newer engines (2025+) expose `Uint8Array.prototype.toBase64()`/`fromBase64()` natively (Baseline-adjacent but not universal as of this research — verify actual browser support matrix against this repo's stated minimums, `index.html:26`: "Chrome 119+, Firefox 120+, or Safari 18.2+", before relying on it; those minimums predate the native base64 methods' shipping versions in at least Firefox/Safari, so a polyfill or manual chunked implementation is likely still required for the stated support matrix).

## 4. Color space / alpha channel pitfalls (JPEG has no alpha)

- **Straight vs. premultiplied alpha mismatch is the single most common silent-corruption bug in this kind of pipeline.** `ImageData`/canvas `getImageData`/`putImageData` contract is *straight (non-premultiplied) alpha* per spec — but Skia (which backs Compose Multiplatform's `ImageBitmap` via Skiko on wasmJs) commonly stores bitmaps as *premultiplied* alpha internally for its own compositing. If `ImageBitmap.toPixelMap()` returns premultiplied values and they're written directly into an `ImageData`/`Uint8ClampedArray` without un-premultiplying first, mid-tone colors near transparent edges will look wrong (dark fringing) once converted to JPEG's opaque RGB — this is a known cross-engine footgun (see WHATWG `html#5365`, Firefox bug 389366 on `getImageData` premultiplication history) and is easy to miss because fully-opaque images (alpha=255 everywhere) hide the bug entirely — a naive test with an opaque screenshot will pass while a transparent-background annotation image will show fringing.
- **JPEG has no alpha channel at all** — the encoder (browser's built-in JPEG encoder via canvas, or jpeg-js) will either flatten alpha against a compositing color (commonly black, sometimes white, engine-dependent — MDN doesn't guarantee which) or reject/ignore it. If the source `ImageBitmap` has meaningful transparency (e.g., an annotation overlay on a transparent background), the plan needs an explicit flatten-to-opaque-background step (draw onto a white/black-filled canvas first via `drawImage` compositing, *before* JPEG encode) rather than relying on implicit browser behavior, which is inconsistent and undocumented across engines.
- jpeg-js (the candidate npm library) specifically expects a flat RGBA `Uint8ClampedArray`/`Uint8Array` input already in the format `{data, width, height}` — same premultiplication question applies to whatever buffer it's fed; check jpeg-js's own README/source for its alpha-handling assumption (not confirmed in this research pass — flagged as an open question for the planning phase, since jpeg-js's own documentation should be read directly before committing to that library).

## 5. npm-dependency-bundling risks (jpeg-js option)

- This repo has exactly one precedent for an npm dependency in `wasmJsMain` (`@sqlite.org/sqlite-wasm`, `kmp/build.gradle.kts:157`), and it required a custom `doLast` post-processing step on `wasmJsBrowserDistribution` (`kmp/build.gradle.kts:334-350`) to manually copy non-JS-bundle assets into the distribution directory, plus explicitly opting out of configuration-cache compatibility for that task. **Any new npm dependency should be assumed to need similar manual verification of the production `wasmJsBrowserDistribution` output**, not just a successful compile — Kotlin/JS's default webpack-based bundling doesn't necessarily handle every npm package's asset/worker files or `package.json` `exports` conditions correctly out of the box.
- jpeg-js itself is pure JS (no `.wasm`/worker assets), which reduces this specific risk relative to sqlite-wasm, but tree-shaking/bundle-size still needs verification: confirm the production distribution build (`wasmJsBrowserDistribution`) doesn't pull in jpeg-js's full source (including any Node-specific code paths, e.g. Buffer polyfills) if the library isn't purpose-built for browser/ESM bundling. Check the package's `package.json` for `browser`/`module`/`exports` fields before adding it.
- CI reproducibility: confirm CI actually builds with `-PenableJs=true` (this target is opt-in per `build.gradle.kts:32`) so any npm-dependency regression is caught before merge, not just locally. Not verified in this research pass — check the GitHub Actions workflow that runs `wasmJsBrowserDistribution`/`wasmJsTest`.
- Given pitfalls #1-#4 make the pure-canvas path (`toPixelMap` → canvas → `toDataURL('image/jpeg', quality)`) viable without any new dependency (browsers have built-in, battle-tested JPEG encoders), bundling jpeg-js is arguably solving a problem (encoder correctness/control) that the platform already solves for free, at the cost of bundle size and an unverified alpha-handling contract. This tradeoff should be made explicit in the plan phase, not defaulted into silently.

## 6. Testing pitfalls — wasmJsTest infra

- **VERIFIED**: `kmp/build.gradle.kts:161-165` shows `wasmJsTest` currently only depends on `kotlin("test-wasm-js")`. There is no Karma configuration file in the repo (`find . -iname "karma*"` under `kmp/` returns nothing outside `build/`/`node_modules/`), meaning the project relies entirely on the Kotlin Gradle plugin's *default* Karma+headless-browser setup for `browser()` targets — untouched/uncustomized.
- Per Kotlin's own docs and community reports (Kotlin Slack `wasmjs-unit-testing`, kotlinlang discuss thread on wasm unit tests), **wasmJs browser tests genuinely run inside a real (headless) browser via Karma** — they are not JVM-simulated. This means canvas/DOM APIs (`document.createElement('canvas')`, `getContext('2d')`, `toDataURL`) *can* execute in `wasmJsTest`, unlike JVM-based `jvmTest`. That's the good news.
- The bad news, per multiple community reports: **default Karma+ChromeHeadless setups for Kotlin/Wasm have documented flakiness** — hangs, "0 tests completed" before timeout, browser-launch failures requiring retries. This repo has zero prior wasmJsTest track record to lean on (it's a from-scratch test source set for this feature), so expect first-time setup friction: verifying a headless Chrome/Chromium binary is available and discoverable in the CI environment (not just locally), and budgeting real debugging time if tests hang rather than fail cleanly.
- No Roborazzi-equivalent (screenshot/pixel-diff) tooling exists for wasmJs in this repo — `jvmTest`'s Roborazzi dependency (`kmp/build.gradle.kts:145`) has no wasmJs counterpart. This means **pixel-level correctness of the exported JPEG (e.g., verifying no alpha-fringing regression, verifying correct dimensions/colors) cannot be screenshot-tested the way desktop UI is** — testing strategy will likely need to fall back to decoding the produced JPEG bytes back into pixels (in JVM test code, using a JVM JPEG decoder against bytes captured from a wasmJs run, or via a golden-byte-comparison) rather than a visual diff, or accept that this path is exercised primarily via manual/e2e browser testing (Playwright is available as an MCP tool in this environment — worth considering as an alternative to native `wasmJsTest`/Karma for at least the canvas-integration-level testing, since it sidesteps the Karma flakiness reports entirely and this environment already has `mcp__playwright__*` tools).
- Recommendation for the plan phase: keep the pure encode-math/buffer-marshaling logic (chunked base64, premultiply/unpremultiply, size-limit clamping) in platform-agnostic `commonMain`/`commonTest`-testable functions wherever possible, and reserve actual `wasmJsTest`/Karma or Playwright-driven testing for the thin canvas-interop glue layer that can't be tested any other way. This minimizes exposure to the Karma flakiness risk.

## Summary of biggest risks (ranked)

1. **Alpha premultiplication mismatch (pitfall 4)** — silent, easy-to-miss correctness bug that only manifests on images with real transparency; needs an explicit test case with a non-opaque source image, not just a smoke test.
2. **Base64 stack-overflow on large arrays (pitfall 3)** — will pass on tiny test fixtures and fail on real ~3000×2000 exports if the naive `String.fromCharCode(...bytes)` pattern is used anywhere in the implementation or its dependencies.
3. **wasmJsTest/Karma infra is unproven in this repo (pitfall 6)** — budget real time for first-time flakiness; consider Playwright (already available via MCP) as a fallback for canvas-level integration coverage.
