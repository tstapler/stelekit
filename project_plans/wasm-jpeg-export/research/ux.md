# UX Research: wasm-jpeg-export

## Actual entry point (found in code, not assumed)

- `AnnotationExporter.bakeAndEncode()` ([`kmp/src/commonMain/.../ui/annotate/AnnotationExporter.kt:62`](../../../kmp/src/commonMain/kotlin/dev/stapler/stelekit/ui/annotate/AnnotationExporter.kt#L62)) returns a plain `ByteArray` ("empty array on failure" per its own doc comment) — no `Either<DomainError, T>`, breaking from the rest of the repo's error convention (see root `CLAUDE.md` Arrow section).
- The only UI consumer of that byte array is `DriveExportService.exportToDrive()` ([`kmp/src/commonMain/.../platform/google/DriveExportService.kt:111`](../../../kmp/src/commonMain/kotlin/dev/stapler/stelekit/platform/google/DriveExportService.kt#L111)), which uploads to Google Drive — there is **no plain "download JPEG to disk" path** in this codebase. `ShareProvider` ([`export/ShareProvider.kt`](../../../kmp/src/commonMain/kotlin/dev/stapler/stelekit/export/ShareProvider.kt)) is text/HTML-only and is a no-op stub on wasmJs ([`PlatformShareProvider.js.kt`](../../../kmp/src/wasmJsMain/kotlin/dev/stapler/stelekit/ui/PlatformShareProvider.js.kt)), unrelated to image bytes.
- The button UI already exists — `DriveExportButton` in `AnnotationEditorScreen.kt:608-659`, driven by `DriveExportUiState` (`Idle`/`Loading`/`Success`/`Error`, lines 593-598), shown when `onExportToDrive` is non-null (line 458).
- **Finding, not assumption**: `AnnotationEditorScreen(` is instantiated exactly once, in [`ScreenRouter.kt:278`](../../../kmp/src/commonMain/kotlin/dev/stapler/stelekit/ui/ScreenRouter.kt#L278), and that call site does **not** pass `onExportToDrive` — it defaults to `null`, so the export button is currently unwired/invisible in the live app on every platform, not just wasmJs. The bug (0-byte JPEG) is real and worth fixing at the `ImageEncoder` layer regardless, but there is no currently-reachable UI surface displaying its failure today. Flag this gap to the planning phase: either the fix should also wire the button (scope creep beyond the stated bugfix), or the acceptance criteria should target the encoder + its existing test (`AnnotationExporterTest.kt`, jvmTest) rather than a live UI path.
- Existing precedent for user-facing status in *this exact screen*: `snackbarHostState.showSnackbar(message, actionLabel, duration)` is already used for calibration messages (`AnnotationEditorScreen.kt:188-199`), backed by a `SnackbarHost` in the `Scaffold` (line 223). This is the natural, already-proportional mechanism to reuse for an encode-failure message — no new toast/dialog component needed.

## 1. Comparable UX patterns

- **Measurement/annotation apps** (iOS Measure, MeasureKit, CamScanner-style scan export): export is a single tap that either (a) completes near-instantly with a share sheet, or (b) shows a brief indeterminate spinner overlaid on the button itself (not a full-screen blocker) followed by the OS share/save sheet. Failure states are rare and handled with a short toast ("Couldn't save image — try again"), not a modal.
- **Photoshop/Lightroom-style export dialogs**: reserved for *configurable* exports (format, quality, destination) with a progress bar for genuinely long operations (batch export, large files). A single-image JPEG export with fixed quality (as here — `quality: Int = 90` hardcoded call site) does not warrant a full dialog; a quality=90 default with no user-facing quality picker means this is a "fire and confirm" action, not a "configure and wait" action.
- **Browser download UX**: the platform-native pattern is an `<a download>` click or `showSaveFilePicker()` triggering the browser's own download UI (toolbar chip, "File saved" notification) — the *browser* owns the progress/success affordance once bytes are handed off. The app's job is only to (a) not block the main thread while producing those bytes, and (b) tell the user clearly if byte-production itself failed, since the browser never sees a failed encode.

## 2. What users expect from "Export"/"Save" on web

- Immediate acknowledgment that the tap registered (button state change within ~100 ms — the existing `Loading` FAB variant already satisfies this).
- For anything taking more than ~1 second, a progress indicator that's clearly tied to the action (the disabled spinner FAB at `AnnotationEditorScreen.kt:624-636` already does this correctly — keep this pattern for the encode step, not just the Drive upload step).
- A visible confirmation the file is ready (download started / "Saved to Drive" chip) — users do not trust silence. The current 0-byte-file bug is the worst case of this: total silence with an apparently-successful action.
- No expectation of a preview dialog for this class of app (measurement tool, not a photo editor) — a preview step would be scope creep per the requirements' non-goals ("General annotation-editor feature work beyond the export path").

## 3. Accessibility requirements

- Material3 `Snackbar`/`SnackbarHost` (already in use in this screen) announces via platform-native live-region semantics on Android/iOS/Desktop automatically — no extra work needed on those targets if the error is routed through `snackbarHostState.showSnackbar()`.
- **Open risk for wasmJs specifically**: Compose Multiplatform's web accessibility-tree/semantics support is less mature than the other targets (this is the platform where the bug lives). Do not assume the Snackbar's live-region behavior reaches a screen reader on web without verification — flag for the plan/validate phase to either verify with a screen reader (VoiceOver+Safari or NVDA+Chrome) or accept degraded-but-visible (non-announced) feedback as sufficient for this bugfix's scope.
- The `Loading` FAB (`CircularProgressIndicator`, line 631) currently has no `contentDescription`/semantic label distinguishing "exporting" from decorative — add one (e.g. `Modifier.semantics { contentDescription = "Exporting image" }`) since the icon disappears during loading and a screen-reader user loses the button's identity.
- Any new error text must be real text content (not color-only, e.g. not just turning the FAB red) — colorblind-safe per `ui-web-design-guidelines` conventions already referenced elsewhere in this repo's skills.

## 4. Error states requiring graceful handling

| Failure | Likely cause | Where surfaced today | Recommended handling |
|---|---|---|---|
| Canvas/2D context unavailable | Browser blocks canvas (privacy mode, exotic embed) | Nowhere — `encodeToJpeg` just returns `ByteArray(0)` silently | Encoder should signal failure distinguishably (e.g. `Either<DomainError.ExportError, ByteArray>` — `ExportError` already has `SerializationFailed`/`ShareFailed` variants at [`DomainError.kt:104-107`](../../../kmp/src/commonMain/kotlin/dev/stapler/stelekit/error/DomainError.kt#L104); a new `EncodeFailed` case fits the same shape). Route through the existing Snackbar. |
| Encode failure (JS exception, malformed image data) | Bad pixel data, library throw | Nowhere | Same as above — catch at the JS interop boundary, map to `DomainError.ExportError`, do not let it crash the coroutine. |
| Huge image (3000×2000+) causing slow encode / possible jank | Synchronous canvas/JS work on the main thread | Not handled — no dispatcher offload visible in the stub | This is the one case that needs *design*, not just error handling: confirm in the implementation plan whether the chosen encode path (Canvas `toDataURL` vs `npm` JPEG library) can run off the JS main thread (Worker) or is inherently synchronous. If synchronous and slow, the `Loading` FAB state (already built) is the correct — and sufficient — mitigation: it already disables interaction and shows progress, so a multi-second freeze reads to the user as "working," not "broken," as long as the tab doesn't fully hang. If it risks a true freeze (>3-4s of blocked main thread), that's an implementation-plan concern, not a UI one — no UI change can fix a blocked JS thread. |
| Bug's own repro case: silent 0-byte success | The bug being fixed | Nowhere (looks identical to a successful `Idle`/no-op) | Covered by the `EncodeFailed` error path above; must not be reachable post-fix since acceptance criteria require detecting this. |

Existing gap worth flagging to the plan phase even though it's pre-existing, not newly introduced: `DriveExportButton`'s `Error` branch (line 614) is visually **identical** to `Idle` — same FAB, same icon, same color. The `DriveExportUiState.Error.message` field is captured in the sealed class but never read/displayed anywhere in `DriveExportButton`. If this bugfix threads a new error state up from the encoder, don't repeat that gap — the error text needs to actually reach the user (Snackbar, using the existing `snackbarHostState`), not just silently revert the button to its idle look.

## 5. Jobs-to-be-done

- **Functional**: "Give me a JPEG file of my annotated measurement so I can attach it elsewhere (report, email, ticket, Drive)." Currently fails silently on web — the functional job is simply not done, with no error to explain why.
- **Emotional**: "Confidence that what I measured was captured correctly." A 0-byte file with no error is the worst outcome for this job — it actively erodes trust because the user has no idea their data wasn't captured (they may act on the assumption it was exported, e.g. delete the source or move on). A visible, honest failure (even a plain "Export failed, try again" Snackbar) is strictly better for this job than silence, even though it's not a "fix."
- **Social**: "Share this with a colleague/client as proof of a measurement." This job is currently served only through Drive export (unwired, per the finding above) — there is no local-download path at all. Worth noting to the planning phase that "annotation export" as a user-facing feature may be broader than this bugfix's scope (encoder correctness); the social job isn't fully served until some UI actually calls the fixed encoder end-to-end.

## Scope guidance for the plan phase

This is a bugfix to a byte-producing function, not a new UI surface. The minimum UX-complete fix:
1. Make `ImageEncoder.encodeToJpeg` (wasmJs) actually encode, and make failure distinguishable from success (some `Either`/nullable/exception contract — plan.md should pick one consistent with `DomainError.ExportError`).
2. Do **not** design new dialogs, previews, or progress UI — the `Idle`/`Loading`/`Success`/`Error` states and the `SnackbarHost` already exist in `AnnotationEditorScreen.kt` and are sufficient once wired to real failure signals.
3. Treat "wire `onExportToDrive` at the `ScreenRouter.kt:278` call site" as a separate decision for the plan phase to make explicitly (in scope or explicitly deferred) — it is currently dead code, and the acceptance criteria in `requirements.md` can be satisfied at the encoder/test level without touching it.
