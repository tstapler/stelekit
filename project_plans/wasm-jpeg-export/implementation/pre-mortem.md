# Pre-mortem: wasm-jpeg-export
**Date**: 2026-09-22

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `bakeAndEncode()` ships fully fixed and tested, but no production code path calls it — verified via `grep -rn "bakeAndEncode" kmp/src`: the only hits outside `AnnotationExporter.kt` itself are `AnnotationExporterTest.kt` and a KDoc `@param`/comment reference in `DriveExportService.kt`, never an actual call. `grep -rn "ImageEncoder\." kmp/src` shows its single caller is `bakeAndEncode` itself. So the entire encode pipeline is unreachable from any UI/ViewModel on any platform today, not just web. | QA/Tyler opens the annotation editor on web after the fix ships, taps whatever export affordance exists, and observes no change in behavior — because nothing wires to `bakeAndEncode()` at all, the "bug fix" has no user-observable effect. | Add a Story requiring at least one production call site (e.g. the annotation editor's existing export/share action) to invoke `bakeAndEncode()`, or add an explicit, Tyler-signed Unresolved Question stating this ships with zero call sites by design and naming the follow-up ticket that wires it up. Add a `grep`-based check to `validation.md` that fails if `bakeAndEncode` still has zero non-test, non-KDoc callers post-implementation. | P1 |
| 2 | The straight-vs-premultiplied alpha assumption in `flattenToOpaqueRgba` is validated only by synthetic unit tests (Task 2.1.1b/c) plus an ad hoc, ungated implementer-time comparison (Task 2.1.1d, "adjust the formula" with no persisted regression test) — yet the feature's actual annotation overlays exercise semi-transparent paint on nearly every export: `AnnotationExporter.kt:109` draws AREA fills at `color.copy(alpha = 0.3f)`, and `drawLabel` (called whenever any annotation has a label/value, i.e. the common case) fills its background at `Color(0xCC000000)` (~80% alpha). If the assumption is wrong, every export with an AREA annotation or a labeled measurement — the typical case — ships with subtly wrong fill colors that pass every automated check (non-empty, correct MIME prefix, correct magic bytes), because all of those checks are colorblind. | Users report exported images' annotation fills/label backgrounds look a different shade than what was shown live in the editor — a visual bug easy to miss in a quick "does it export" smoke test. | Promote Task 2.1.1d from prose to a required Story 2.1.1 acceptance criterion: a checked-in `wasmJsTest` fixture that bakes a real AREA (alpha=0.3) or LABEL (0xCC) annotation, encodes it on wasmJs, decodes the result, and diffs it (within tolerance) against the already-correct `ImageEncoder.jvm.kt` output for the same input — not just the synthetic `0x80FF0000` single-pixel case. | P2 |
| 3 | The 500ms/3000×2000 timing budget (Task 3.2.1c) wraps only the `canvasToDataUrl` call. It excludes `toPixelMap()`, the 6M-iteration `flattenToOpaqueRgba` loop, and the subsequent `Base64.decode` of a multi-megabyte data-URL string — so the plan's own CI gate can go green while the full `encodeToJpeg`/`bakeAndEncode()` call the user actually waits on blocks the main thread well past the stated "no unacceptable UI-thread blocking" bar (requirements.md AC2). | A user exporting a large annotated image on web sees the export button freeze noticeably longer than what the (green) CI timing test would suggest, with no CI signal ever having caught it. | Widen Task 3.2.1c's instrumentation and its acceptance criterion to wrap the entire `encodeToJpeg` body (pixel read → flatten → canvas write → `toDataURL` → `Base64.decode`), not just the `canvasToDataUrl` sub-call. | P2 |
| 4 | Phase 4's only automated browser coverage runs via Karma's default `ChromeHeadless` launcher — a single rendering engine. Canvas/JPEG-encoder behavior (whether the `quality` parameter is honored, output determinism, per-tab canvas memory ceilings) is documented to vary across Chromium/Firefox/WebKit, and iOS/macOS Safari in particular is known for materially tighter canvas memory limits than Chromium. Nothing in the plan runs, or even names as an explicit gap, a second engine. | A Safari or iOS Safari user hits a broken/degraded export (crash, ignored quality slider, or an area cap lower than Chromium's `MAX_CANVAS_AREA_PX`) while CI stays fully green because it never exercised that engine. | Add an explicit plan.md line scoping Phase 4's coverage to Chromium-only, and either add a WebKit/Firefox Karma launcher to CI or record it as a named, Tyler-visible gap with a follow-up ticket — mirroring the treatment Task 4.1.1b already gives Karma-flakiness fallback. | P2 |
| 5 | The per-call pipeline holds up to ~5 full-size copies of the image simultaneously in memory (packed-ARGB `IntArray`, flattened RGBA `ByteArray`, the browser's internal `ImageData`, the base64 data-URL `String`, and the decoded output `ByteArray`). For an image well within `MAX_CANVAS_AREA_PX` (e.g. 4096×4096 ≈ 16.4M px, ~64MB per raw-RGBA copy alone), this multiplier is a distinct memory-pressure risk from the already-addressed canvas-*dimension* ceiling and is undiscussed anywhere in plan.md, the ADRs, or the pitfalls research. | On a memory-constrained device (low-end Android, or iOS Safari's stricter per-tab memory budget) a single large export crashes or reloads the browser tab, with no prior signal. | Add a peak-memory note to the Domain Glossary/ADR-001 documenting the ~5x-copy multiplier, and add a soft memory-delta check (e.g. Chrome's `performance.memory`) to the Story 3.2.1 timing fixture for a near-ceiling image size, so a future OOM incident has a documented root cause instead of a mystery. | P3 |

## P1 Items (address before implementation)
- [x] Failure #1 — Resolved via the "Tyler sign-off required" Unresolved Questions entry added to `plan.md` (scoping zero-production-callers as an explicit, named decision rather than an oversight, with a follow-up ticket to wire the UI call site separately). A `grep`-based "fails if zero callers" check was deliberately *not* added to `validation.md`, since that would contradict the explicit scope decision to ship the encoder fix without wiring — zero callers is the intended, signed-off state until the follow-up lands.
