# Validation Plan: wasm-jpeg-export

**Date**: 2026-09-22

## Happy Path Scenario

Given a user has annotated a source image in the browser (wasmJs target) and clicks export, when `AnnotationExporter.bakeAndEncode()` bakes the overlays onto the bitmap and calls the now-real `ImageEncoder.encodeToJpeg()`, then the call returns `Either.Right(bytes)` where `bytes` is non-empty and starts with the JPEG SOI marker (`0xFF 0xD8`) — a valid file a browser/image viewer can decode, instead of today's silent `ByteArray(0)`.

## Test Stack
- **Unit**: `kotlin.test` (`kotlin.test.Test`/`assertEquals`/`assertTrue`/`assertIs`), platform-agnostic across `commonTest` and `wasmJsTest`. `jvmTest` uses `org.junit.Test` (via the `kotlin("test-junit")` dependency at `kmp/build.gradle.kts:143`), matching `AnnotationExporterTest.kt`'s existing convention. `Either` results are asserted with `assertIs<Either.Right<T>>(result)` / `assertIs<Either.Left<T>>(result)` then unwrapped via `(result as Either.Right).value`, matching `ImageSidecarManagerTest.kt:50`'s idiom (repo has no kotest `shouldBeRight` matcher).
- **Integration**: Same `kotlin.test` framework, no separate integration runner. `jvmTest` integration tests exercise the real JVM `ImageEncoder` (`javax.imageio.ImageIO`) through `AnnotationExporter` — no mocking. `wasmJsTest` integration tests run in headless Chromium via Karma (`./gradlew :kmp:wasmJsBrowserTest -PenableJs=true`), exercising the real browser Canvas 2D API (`document.createElement('canvas')`, `putImageData`, `toDataURL`) — this is the only way to get real coverage of the JS interop boundary that is this bug's actual root cause.
- **E2E / UX**: N/A
