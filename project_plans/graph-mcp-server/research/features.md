# Research: Comparable Features & Edge Cases — graph-mcp-server

Scope: what existing "external tool operates on personal knowledge base" products and MCP
servers do (search/pagination/conflict/approval patterns), and what SteleKit-specific data
model edge cases the MCP server's tool/resource design must account for. Research only — no
code changes.

## 1. Comparable local-API products (Obsidian, Logseq, Trilium)

| Product | Auth | Search | Pagination | Conflict handling |
|---|---|---|---|---|
| **Obsidian Local REST API** ([coddingtonbear/obsidian-local-rest-api](https://github.com/coddingtonbear/obsidian-local-rest-api)) | Bearer token, localhost-bound, HTTPS w/ self-signed cert | `POST /search/simple/` — built-in fuzzy search, returns filenames + scored context snippets. `POST /search/` — JsonLogic expression evaluated against each note's metadata (structured query, not full-text). | Directory listing takes `limit`/`offset` explicitly to bound response size ("prevent context overflow" — same rationale as this repo's `PageRepository` bounded-read rule). | File-based; last-write-wins on disk, no ETag/version check surfaced through the API itself. |
| **Logseq local HTTP API** (plugin-API proxy, default `localhost:12315/api`) | Bearer token | No search endpoint of its own — callers use `logseq.Editor.getPageBlocksTree` and similar plugin methods and implement search client-side ([ergut/mcp-logseq architecture doc](https://github.com/ergut/mcp-logseq/blob/main/LOGSEQ_API_ARCHITECTURE.md)). | None built in — a thin proxy over the plugin API, one call per plugin method (`logseq.Namespace.methodName`), each request forwarded over IPC to the renderer process. | None — writes (`insertBlock` etc.) apply immediately through the live Logseq app instance; there is no external-process concurrent-write story because the API *is* the running app. |
| **Trilium Notes ETAPI** (referenced by this repo's issue #232) | Token-based, localhost-bound, CRUD over notes/branches/attributes | Simple text search endpoint | Standard `limit`/`offset`-style params on list endpoints | Not surfaced in issue #232's summary; ETAPI's own docs describe optimistic concurrency via note `utcDateModified` comparison, not directly confirmed here (unverified — flagging as a gap) |

**Takeaways for SteleKit:**
- Bearer-token + localhost-bind is the converged pattern across all three — but note open question 5 in `requirements.md` is still unresolved: stdio-transport MCP (this project's chosen v1 transport) has no HTTP request to attach a token *to*. The precedent argues for token auth on any *future* HTTP/loopback transport (#232), not necessarily v1 stdio, where process-parentage already scopes access to whoever launched the subprocess.
- **Obsidian's two-tier search (fuzzy filename/snippet vs. structured JsonLogic) maps directly onto what SteleKit already has**: `SearchRepository.searchWithFilters(SearchRequest)` (BM25 full-text + `propertyFilters`/`dateRange`/`scope` structured filters) already covers both tiers in one call — the MCP server doesn't need to invent a second query language, just expose `SearchRequest` as the tool's input schema.
- **Pagination-to-prevent-context-overflow is exactly this repo's existing bounded-read discipline** (`CLAUDE.md`: "Graph-scale reads must be paginated, projected, or chunked"). The MCP tool schema should require/default `limit`+`offset` on every list-shaped tool, mirroring `SearchRequest.limit`/`.offset` (default 50) and `PageRepository.getPages(limit, offset)` — no unbounded "search everything" tool should exist, matching the codebase's existing absence of `getAllPages()`.
- **Logseq's "the API is the live app, no conflict story" model is the one SteleKit should avoid** if the MCP server runs as an independent process (open question 3 in requirements.md) rather than talking to the already-running desktop app's in-memory state — a second process writing SQLite/markdown concurrently with the desktop app *does* need a conflict story, and one already exists in this codebase (see §3 below) — it should be reused, not reinvented.
- Trilium's ETAPI ships zero MCP wrapper of its own as of this research (2026-09-14) — no MCP-specific complaints to mine from its issue tracker for this project.

## 2. MCP servers for note-taking/PKM tools — de facto tool shapes and failure modes

Surveyed via [morphllm.com/obsidian-mcp-server](https://www.morphllm.com/obsidian-mcp-server), [cyanheads/obsidian-mcp-server](https://github.com/cyanheads/obsidian-mcp-server), [StevenStavrakis/obsidian-mcp](https://github.com/StevenStavrakis/obsidian-mcp), [mcp-obsidian.org](https://mcp-obsidian.org/), and the official [Notion MCP supported-tools doc](https://developers.notion.com/guides/mcp/mcp-supported-tools).

**Converged tool shape across Obsidian/Notion MCP servers** (this is the de facto standard the requirements.md "success metrics" tool list — search, read, list-backlinks, propose-write — already matches):

- **Read**: `search` (full-text/fuzzy), `get_file_contents` / `retrieve-page-markdown` (single-resource read), `list_files_in_dir` (directory/namespace browse).
- **Write**: `patch_content` / `update-page-markdown` (targeted edit, not whole-file replace), `append_content` / `append_to_note` (additive, lower-risk write), `create-note` / `create page`.
- **Structure/graph-specific**: `add-tags`/`remove-tags`/`rename-tag`, `move-note`, `create-directory` — no PKM MCP server surveyed exposes a dedicated "list backlinks" tool by that name, but several fold it into `get_file_contents`'s metadata response (Obsidian's file metadata includes inbound-link counts). **SteleKit's explicit `list backlinks` tool (requirements.md success metric) is more explicit than the current de facto standard** — this is a point in its favor, not a gap; the closest existing precedent is `ReferenceRepository.getIncomingReferences`/`getAllReferences`, which already returns structured backlink data no Obsidian MCP server exposes as directly.
- **Multi-vault**: `StevenStavrakis/obsidian-mcp`'s alternative tool list includes `list-available-vaults` — direct precedent for the "which graph" ambiguity this project's requirements.md flags as unaddressed (see §4).

**Write-confirmation patterns found (directly relevant to the approval-gate design already speced in `project_plans/llm-service/research/architecture.md` §3):**

- **NotePlan MCP server**: two-step `dryRun` / `confirmationToken` flow for write actions — the model proposes, gets a token back describing the effect, then must resubmit with the token to commit. Reduces round-trips vs. a full human-in-the-loop review screen but still requires a second explicit call.
- **Apple Notes MCP servers** (`ailenshen/apple-notes-mcp`, `sweetrb/apple-notes-mcp`): destructive operations require an explicit `confirm: true` parameter plus a `reason` string in the same tool call — confirmation is caller-supplied, not server-enforced with a human review step.
- **Openlane "Guardian" approval flow** ([openlanelabs/openlane#146](https://github.com/openlanelabs/openlane/issues/146)): MCP write tools *never* write directly — every write tool call creates a pending `approvals` row (`status=pending, requested_by='agent'`) that a human approves/rejects in the product's existing staff UI. **This is the closest external precedent to what this project's requirements.md already specs** (approval-gated writes landing in the existing SteleKit UI, not a new confirmation-token round-trip) — it validates the "reuse the existing review surface, don't invent an in-protocol confirm step" design direction already chosen, over the NotePlan/Apple-Notes in-band-confirmation alternatives.
- No public "write happened without confirmation and destroyed data" *incident writeup* specific to a PKM MCP server surfaced in this search (as of 2026-09-14) — the pattern shows up as a *design feature* being marketed (dryRun tokens, confirm flags, approval queues), suggesting the industry learned this lesson before/without a widely publicized incident, or incidents exist but aren't documented publicly. Flagging as an evidence gap rather than asserting an incident that wasn't found.

**Implication for SteleKit's design**: the UI-review-queue approach (Openlane-style) is stronger than a stateless confirm-token because it survives the case where the MCP client itself is compromised or hallucinating — a `confirm: true` flag or `dryRun` token round-trip is still entirely inside the untrusted client's control, whereas a human physically looking at the SteleKit desktop app before accept is not. This matches (does not just parallel) the already-decided `project_plans/llm-service` approval-gate design — no design change indicated, just confirms it.

## 3. SteleKit-specific data model edge cases

Read `kmp/src/commonMain/kotlin/dev/stapler/stelekit/model/Models.kt:89-161` (Page/Block/Property) and the repository interfaces that read/write them.

- **Optimistic-concurrency fields already exist and should gate MCP writes.** Both `Page.version: Long` and `Block.version: Long`, plus `Block.contentHash: String?` (SHA-256 of normalized content), are present on the domain model ([Models.kt:96](https://github.com/tstapler/stelekit/blob/1528d06500fe52842787c367b2398000640f6fb2/kmp/src/commonMain/kotlin/dev/stapler/stelekit/model/Models.kt#L96), [:127](https://github.com/tstapler/stelekit/blob/1528d06500fe52842787c367b2398000640f6fb2/kmp/src/commonMain/kotlin/dev/stapler/stelekit/model/Models.kt#L127), [:130](https://github.com/tstapler/stelekit/blob/1528d06500fe52842787c367b2398000640f6fb2/kmp/src/commonMain/kotlin/dev/stapler/stelekit/model/Models.kt#L130)). An MCP "propose update" tool should capture the `version`/`contentHash` the LLM read *at propose time* and re-check it at accept time (mirroring `StelekitViewModel.acceptJournalMerge`'s documented re-validate-before-execute pattern in `project_plans/llm-service/research/architecture.md` §3) — otherwise a user edit made in the SteleKit UI between propose and accept is silently clobbered. This is a genuinely new edge case beyond what `llm-service`'s architecture doc discusses (it's designed around git-merge and LLM-sourced proposals, not "the human kept editing while the LLM's suggestion sat in the queue").
- **Duplicate/near-duplicate page names**: `PageRepository.getPageByName(name)` returns a single `Page?` — SteleKit's model does not appear to prevent two pages with names that differ only by case or normalization from both existing (page names are validated for non-blank/length via `Validation.validateName`, not uniqueness at the domain-model layer visible here). An MCP `search_pages`/`read_page` tool driven by an LLM-supplied name string should not assume exact-match-returns-one; it should route through the existing full-text `searchPagesByTitle`/`searchWithFilters` first and disambiguate, not call `getPageByName` blind. (Uniqueness enforcement, if any, lives in the SQL schema/DB layer — not confirmed in this pass; flag as open verification item for the planning phase.)
- **Journal-page date parsing is already a known fragile spot the codebase works around, not a hazard the MCP server would introduce.** `PageRepository.getJournalPageByDate(date: LocalDate)`'s own doc comment states: *"Format-agnostic — always use this instead of getPageByName for journal pages to avoid duplicate creation from name format differences (e.g. '2026_04_11' on disk vs '2026-04-11' created in-app)"* ([PageRepository.kt:36-41](https://github.com/tstapler/stelekit/blob/3b1a7aa4c38b005e825002ed512b25016406e4ef/kmp/src/commonMain/kotlin/dev/stapler/stelekit/repository/PageRepository.kt#L36)). `GraphLoader` resolves journal identity via `JournalUtils.parseJournalDate(title)`, not string match. **Direct implication**: if an MCP tool exposes "read/write today's journal page" as a convenience (likely, given the use case is LLM research capture), it must accept/derive a `LocalDate` and call `getJournalPageByDate`, never construct or match a journal page by guessing its name string — the same trap the app's own code was already patched to avoid.
- **Block hierarchy (parent/child + inter-block references) has two distinct reference types that a "read a page" tool must not conflate**: `Block.parentUuid`/`leftUuid` encode outline structure (tree position), while `ReferenceRepository.getOutgoingReferences`/`getIncomingReferences`/`getAllReferences` and `BlockSearchRepository.getLinkedReferences`/`getUnlinkedReferences` encode semantic `[[wiki-links]]` between blocks — independent of tree position. A "list backlinks" MCP tool almost certainly means the latter (semantic references), matching `ReferenceRepository.getIncomingReferences`, not a page's child blocks. The tool's naming/docstring needs to disambiguate this for the calling LLM, since both are plausible readings of "backlinks" and the wrong one silently returns an empty or wrong-shaped result rather than erroring.
- **Multi-graph "which graph" ambiguity is real and structurally unresolved for a UI-less client.** `GraphManager` maintains a `GraphRegistry(activeGraphId: GraphId?, graphs: List<GraphInfo>)` ([GraphInfo.kt:35-38](https://github.com/tstapler/stelekit/blob/da30a135c445cf1a0ecec01db650d41d6e837263/kmp/src/commonMain/kotlin/dev/stapler/stelekit/model/GraphInfo.kt#L35)) with exactly one `activeGraphId` at a time, switched via `GraphManager.switchGraph(id)`. An MCP client has no UI affordance to pick a graph and no reason to assume "whatever's currently open in the desktop app" is the graph the user means in a given research session — this is functionally identical to the `list-available-vaults` tool found in `StevenStavrakis/obsidian-mcp` (§2), which exists precisely because Obsidian MCP servers hit the same ambiguity with multi-vault setups. **Recommendation for planning phase**: expose a `list_graphs` tool backed directly by `GraphRegistry.graphs`, and require (not default-guess) a `graphId` parameter on every other tool once more than one graph is registered — silently operating on "whatever is active" risks the LLM reading/writing the wrong graph with no error, the worst failure mode (wrong-graph writes are not caught by the version/contentHash check in the first bullet, since that only guards *which version*, not *which graph*).

## 4. Unstated needs beyond the explicit requirements

- **Pagination/streaming for large result sets is already mandatory, not optional** — this isn't a new need to design, it's an existing hard constraint (`CLAUDE.md`: *"Graph-scale reads must be paginated, projected, or chunked — never O(graph)"*, enforced by `LargeGraphWarmStartCrashTest`/`QueryPlanAuditTest`). Every MCP tool that returns a list must carry `limit`/`offset` in its input schema with a bounded default (mirror `SearchRequest`'s `limit = 50`), and the JSON-RPC response should surface `hasMore`/`totalCount` (already present on `SearchResult`, [SearchRepository.kt:95-96](https://github.com/tstapler/stelekit/blob/0b1d9dcfbae90b27848399ea5066d9b1445e94e5/kmp/src/commonMain/kotlin/dev/stapler/stelekit/repository/SearchRepository.kt#L95)) so the calling LLM knows to page rather than assume a full result. This requirement is inherited "for free" from the existing repository contracts — no new pagination protocol needs inventing, but MCP tool schemas must not accidentally flatten `SearchResult`/`Either` in a way that drops `hasMore`.
- **Block-level vs. page-level read granularity**: the requirements.md success metric says "read a page (with blocks)" — but for a large page (deeply nested outline, hundreds of blocks) returning the full block tree in one MCP response risks the same context-overflow problem pagination solves for search. `Page.isContentLoaded` and `Block.isLoaded` already model partial-load state at the domain level, suggesting the read-page tool should support a block-level pagination/depth-limit parameter too, not just page-level list pagination — this is unstated in requirements.md and should be raised as a planning-phase question, not assumed away.
- **"Active graph" vs. "graph the MCP server was told to point at" is a decision requirements.md defers (open question 3) but §3 above shows it also has a *search-scope* consequence**, not just a data-consistency one: if the MCP server opens its own independent `GraphManager`/DB connection (one architecture option under open question 3), "active graph" as tracked by the *running desktop app* may not even be visible to the MCP process — the `list_graphs`/`graphId`-required design in §3 is necessary under either architecture option, not just the shared-process one.
- **Read-only vs. write capability negotiation**: none of the surveyed PKM MCP servers expose an MCP "capability" flag distinguishing a read-only connection from one with write tools enabled, but several (Apple Notes, NotePlan) gate destructive ops per-call rather than per-connection. Given SteleKit's writes are already fully approval-gated (queued, not applied), a per-connection read-only mode is lower priority than in tools with direct writes — worth noting as explicitly deprioritized rather than silently absent, since a reviewer will otherwise ask "why no read-only mode."

## Evidence gaps (flagged, not resolved)

- Trilium ETAPI's own conflict-handling mechanism (`utcDateModified`-based optimistic concurrency) was not opened/verified directly — issue #232's summary describes ETAPI only secondhand; if the planning phase wants to mirror ETAPI specifically, its docs should be read directly rather than relying on this summary.
- No specific "MCP write-without-confirmation incident" writeup was found for a PKM tool as of 2026-09-14 — the absence of evidence is not evidence of absence; this is a gap, not a clean bill of health.
- Whether SteleKit's DB schema enforces page-name uniqueness (vs. only domain-model non-blank/length validation) was not confirmed in this pass — relevant to the "duplicate page name" edge case and should be checked in planning before assuming `getPageByName` behavior.
