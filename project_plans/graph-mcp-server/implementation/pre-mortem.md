# Pre-mortem: graph-mcp-server
**Date**: 2026-09-14

Both `adversarial-review.md` and `architecture-review.md` are thorough on
implementation-level correctness (races, dangling references, SDK API
verification, stale-socket recovery, graph-switch-mid-session). This pass
looks past "does the code do what the plan says" to "does the shipped
feature solve the stated problem," and finds five failure modes neither
review touched.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `kotlin-sdk-server` is pinned at pre-1.0 `0.15.0` with no upgrade/compatibility policy; a future bump (needed for a security fix or a new Claude Desktop protocol revision) breaks the `ClientConnection`/`ServerSession`/`CallToolRequest` internals this plan's `McpClientIdentity`/provenance design depends on, verified against source at one specific commit | `./gradlew jvmTest` fails after an unrelated dependency-bump PR, or worse, compiles clean but `McpClientIdentity` silently stops capturing client names post-upgrade | Add a comment at the SDK dependency line + in `McpClientIdentity.kt`/`McpToolError.kt` pointing at the verified commit and stating what to re-verify (the four call-sites listed in the adversarial review) before any version bump; do not bundle SDK upgrades into unrelated dependency-bump PRs | P2 |
| 2 | No test exercises the full real path — external process → stdio → `McpLauncherMain` byte-proxy → Unix socket → embedded `Server` → real MCP client handshake. Every test in Phase 1/2/3/6 uses either `ChannelTransport` (in-memory, no real stdio/socket framing) or a synthetic launcher/socket test in isolation (Task 1.2.2d); nothing chains all the seams together with a real subprocess talking real stdio JSON-RPC | The feature passes CI end-to-end (Story 6.1.1/6.1.2 both green) but a real Claude Desktop/Code connection fails or hangs on first use — e.g. line-framing mismatch, partial-read handling in the byte-copy loop, or an `initialize` handshake quirk a real client sends that `ChannelTransport` never exercises | Add one manual (or, if feasible, automated) smoke test in the verification phase: run the packaged `stelekit-mcp-launcher.jar` as a real subprocess against a real running `McpSocketServer` and complete a real `initialize` + `tools/call` over actual stdio pipes, not `ChannelTransport`. Record the result in validation.md as a distinct check from Story 6.1.1/6.1.2 | P1 |
| 3 | Setup requires manually computing a launcher command from the Settings panel, pasting it into an MCP host's config file (typically hand-edited JSON), and restarting that host — repeated per graph, since the socket path is per-`graphId`. Given the toggle also defaults off, the realistic activation funnel is: discover the setting exists → enable it → find the host's config file → paste → restart the host → repeat if switching graphs. Every step is a drop-off point | Six months post-ship, `git log`/usage shows the toggle was flipped on once (by the implementer, for testing) and never touched again | Either (a) add a "copy to clipboard" affordance plus a link/instructions for the most common host (Claude Desktop's `claude_desktop_config.json` path, OS-specific), or (b) explicitly accept this as a power-user-only feature in requirements.md/ux.md rather than implying broad reach — scope the win narrowly instead of leaving it aspirational | P1 |
| 4 | Approval fatigue is only partially mitigated. `LlmSuggestionReviewScreen.kt:126-148` already has an "Apply all" bulk action, gated by `hasSeenBeyondFirst && pending.size > 1` and a tap-twice confirm — this plan reuses that screen **unmodified** for MCP-sourced suggestions per ADR-002. A user can arrow past N unread proposals (satisfying `hasSeenBeyondFirst`) and tap "Apply all" twice without reading any of them, which defeats the "human physically reviews each one" premise ADR-002 cites as the reason no token-based confirm was needed | A user reports (or a future bug report shows) an unwanted edit landed from an MCP session they don't remember reviewing carefully — indistinguishable after the fact from a deliberate accept | Either exclude `mcp:`-sourced suggestions from "Apply all" (require per-item accept for externally-sourced proposals specifically, since they carry less implicit trust than the internal page-scan matcher), or note this explicitly as an accepted, scoped risk in ADR-002 rather than relying on the cap/badge (Story 3.2.1/3.2.2) alone, since neither actually gates *reading before accepting* | P2 |
| 5 | No reconnection story for a session dropped mid-use. MCP hosts (Claude Desktop/Code) spawn `McpLauncherMain` once at startup and, per common MCP client behavior, do not automatically retry a broken stdio pipe. If the user closes SteleKit, or flips `mcpServerEnabled` off, while a host is connected, the launcher's socket-side connection breaks with no client-facing retry — the AC for "socket doesn't exist" (Task 1.2.2's 2-second-exit case) only covers the *initial*-connect failure, not a live disconnect | The user's MCP host reports "SteleKit tools unavailable" or the LLM just stops seeing search/read results mid-conversation, with nothing in SteleKit's UI/logs pointing at "your MCP host needs a restart" | Document the expected behavior explicitly (either in the Settings panel's status text or ux.md) — "if SteleKit closes or you disable this toggle, restart your MCP client to reconnect" — so the failure is at least named, even if actual host-side auto-reconnect isn't implementable from SteleKit's side | P2 |

## P1 Items (address before implementation)

- [x] #2 — Add a real-subprocess, real-stdio, real-socket end-to-end smoke test (or an explicit manual verification step recorded in validation.md) distinct from the `ChannelTransport`-based Story 6.1.1/6.1.2 tests, so the seams are proven to compose, not just proven individually. **Addressed**: plan.md Story 6.1.3 (`McpRealSubprocessSmokeTest.kt`) — real `ProcessBuilder` subprocess, real stdio, real Unix socket, real `initialize` + `tools/call` handshake.
- [x] #3 — Either add concrete in-app setup assistance (clipboard copy + host-config-path hints) to Story 4.1.2's Settings panel, or explicitly narrow requirements.md's ambition to "power-user opt-in" so a near-zero adoption rate isn't a surprised-after-the-fact failure. **Addressed**: plan.md Task 4.1.2d adds a Copy-to-clipboard button + host-config hint text.
