## Concerns

- [ ] **C1. The plan states `DomainErrorTest` is "already registered"; it is not, and three more extended tests have no registration task.** `plan.md:242` ("`DomainErrorTest` (existing, extended, already registered)"). VERIFIED: `grep -rn 'DomainErrorTest\|SecretRedactionTest' kmp/src --include=*.kt --include=BUILD.bazel` finds only the class definitions; neither is in `AllBusinessTests.kt` nor in any `srcs` of `kmp/src/commonTest/kotlin/BUILD.bazel` (`business_common_tests` holds three files). `PatLeakageAuditTest` and `SteleKitAssetMapperTest` are absent from `AllJvmTests.kt`, which is the Bazel `jvm_tests` `test_class` (`kmp/src/jvmTest/kotlin/BUILD.bazel:78`), so they never run under Bazel. `AndroidGitRepositoryStorageGuardTest` is absent from `AllAndroidUnitTests.kt`. Consequences: the E1.3 message-map acceptance, the E2.3e token-leak extensions and the E3.4c mapper extension have Gradle-only coverage, while Gate G1 and E7.4 talk only about `bazel test //kmp:business_tests`. E2.3e and E3.4c do not list `AllJvmTests.kt` in Files. Fix: delete "already registered" at `:242`; add `DomainErrorTest` and `SecretRedactionTest` to `business_common_tests.srcs` plus `AllBusinessTests` (E1.3a, E2.3e); add `AllJvmTests.kt` to E2.3e and E3.4c; keep the `AllAndroidUnitTests.kt` entry in E2.5e and state it is a first-time registration of an existing class. Round-1 validation already flagged this (validation.md G1); the planner fixed the E7.4 gap but not this claim.
- [ ] **C2. The service-level guard runs on web too and contradicts the Direct and Proxy write modes.** `GitSyncService` drives the web flow unmodified (`kmp/src/wasmJsMain/.../WasmGitRepository.kt:34`). Task E1.4d runs `LfsGuardCoordinator` with input `WorkingTree` for every repo whose `cleanFilterActive` is false, which includes wasm (ADR-003 section 2a lists "wasm/iOS: the working file is judged"). Consequences not addressed anywhere: (a) a raw pasted image is judged by the service guard and reported as `LfsActionRequired(held)` before the web write service has a chance to convert it through `WasmLfsWriter` (Task E4.2b substitutes pointers only for entries "held-as-LFS" inside `commitGitHub`), so the UI says "held" for a file that Direct mode then uploads; (b) `WasmGitRepository.stageSubdir` "ignores" `excludePaths` (E1.4c `:270`), so the service-level hold has no effect on web and only the second guard (E1.6b) is real; (c) the coordinator loads rules through `LfsRulesLoader(fileSystem)` from OPFS while E1.6a fetches rules from the remote at the base sha, two rule sources for one decision with no stated precedence. Fix: state in E1.4d which web rule source the coordinator uses (or that the coordinator is skipped on web and `WasmGitWriteService` is the sole guard), and add an acceptance case to E4.2 that `LfsActionRequired` is not raised for files successfully converted in `Direct` or `Proxy` mode and is raised for `ReadOnly`.
- [ ] **C3. Phase 1 depends on types and flags that Phase 2 defines; the Android flag has no owner.** E1.4d chooses `LfsGuardInput` from `LfsMode`, and Risk Control (`:107`) and the settings table (`:1103`) default modes per platform, but `LfsMode` and `LfsSettings` are created in Task E2.4a and mode resolution in E2.9b. Phase 1 "has no unresolved dependency" (`:5`) is therefore false as written; it also ships alone (Gate G1). Separately `lfs_android_enabled` has no definition: it is not in the `git_lfs_*_<graphId>` key list (E2.4a), `LfsModeResolver.effective` inputs (E2.9b) do not include it, E7.5a flips "the default ... in `AndroidGitRepository.kt`" (a code constant, not a setting), and the table says Android is `GUARD_ONLY` "until `lfs_android_enabled`" without saying who changes the stored mode when the flag flips. Fix: move `LfsMode` (and a minimal read of the per-graph mode, default `GUARD_ONLY`) into E1.4d, define the flag as a typed input of `LfsModeResolver` (platform capability, not a user setting) and state that Android's effective mode is `GUARD_ONLY` whenever the flag is false regardless of the stored value.
- [ ] **C4. Spike S5's GO outcome is not attainable with the stock filter, and the ADR-001 status path under NO-GO is undefined.** S5 GO requires "zero requests reaching the server" on a missing-object checkout (`:367`), but plan and ADR-001 both describe JGit's `SmudgeFilter` as downloading unauthenticated in that case, so the expected outcome is NO-GO and the custom `jgit://stelekit/lfs/*` filters become the baseline. Gaps: (a) E2.1f says ADR-001 flips to Accepted "if S1, S2 and S5 are GO" and otherwise "the task list is otherwise unchanged", with no rule for how ADR-001 becomes Accepted when S5 is NO-GO (the likely case), and the main decision text (item 2) still describes the builtin filters as the choice; (b) ADR-001's S5 hook row says a NO-GO on hook coexistence yields `LfsNotSupportedHere("hook")`, but no task detects a `git lfs` hook script or returns that error; (c) with S1 GO and S5 NO-GO the plan does not say whether clean uses the builtin filter and smudge the custom one or both are custom (the sequence "S5 NO-GO, custom filters for both" is implied by `:393` but untested by S1, which only exercises the builtin names). Fix: record the intended expected outcome, add the Accepted-with-fallback rule to E2.1f, add a hook-detection step to E2.3a or E2.9c, and make S1 also run against the custom filter names.
- [ ] **C5. `validation.md` is stale against the current plan.** It was written against the 860-line plan (header: "`implementation/plan.md` (860 lines)", headline 1 still says the plan is truncated) and references 16 test names absent from the current plan: `LfsGuardCoordinatorTest`, `LfsRulesLoaderTest`, `LfsRegistrationAuditTest`, `LfsMigrationConfirmationTest`, `LfsLocalObjectResolverTest`, `LfsProxyHealthCheckTest`, `WasmLfsRulesSourceTest`, `LfsFeatureRegistryEntryTest`, `LfsTransferringStateTest`, `LfsModeRollbackTest`, `LfsSettingsSectionWebDefaultsTest`, `AndroidNetworkMonitorMeteredTest`, `AndroidGitRepositoryLfsGuardTest`, `FakeLfsServerTest`, `FakeLfsServerRecordingTest`, `LfsRawBinaryNeverCommittedPropertyTest` (grep of `*Test` tokens, validation not in plan). The plan's Test Registry heading says "names that appear in validation.md", which is therefore untrue. Either the plan must adopt those tests or validation.md must be regenerated before `5-implement`. Several of them close real gaps (a coordinator unit test, a rules-loader test, a registry-entry test for PR #413).
- [ ] **C6. Round-1 C4 half-failed SAF flush is still untested.** `GitShadowFlushActorBinaryTest` (E2.5e `:569`) has no stated case for a flush that dies midway (partial SAF file, `LfsMaterialisedSet` persisted, shadow ahead of SAF). E2.5b `:557` protects materialised paths from `deleteOrphanedShadowFiles` but says nothing about restart recovery. Add the case to the test list and one sentence of recovery behaviour (re-flush from shadow on next launch, never delete the shadow copy until SAF size and hash match).
