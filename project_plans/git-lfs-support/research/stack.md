# Research: JVM/Android Git LFS stack

Date: 2026-10-11. Labels: VERIFIED = I opened the source/jar or ran a command; INFERRED = reasoned, not run.
Scratch artefacts: `.../scratchpad/lfsjar` (binary jar + pom), `lfssrc` (lfs sources jar), `coresrc` (jgit core sources jar).

## Headline

1. `org.eclipse.jgit.lfs:7.3.0.202506031305-r` exists, is tiny (81,728 B), and adds one transitive dep (gson, already in our Bazel lock at 2.8.9). VERIFIED.
2. **Its HTTPS path sends no credentials.** `LfsConnectionFactory` never reads a `CredentialsProvider`, never sets `Authorization` for https remotes; only the SSH `git-lfs-authenticate` path yields auth headers. Our auth model (PAT/OAuth via `UsernamePasswordCredentialsProvider`) therefore does not reach LFS batch/content calls. VERIFIED (source, below). This is the decisive finding: stock `BuiltinLFS` is unusable for private repos / any push to GitHub/GitLab over https.
3. Recommended: use JGit's LFS **filters + pointer/`Lfs` store** (smudge/clean/merge plumbing) but replace the network half (batch download/upload) with our own Kotlin client over Ktor in `commonMain` (shared with web). See section 4.

## 1. Artifact and API (VERIFIED)

Coordinates: `org.eclipse.jgit:org.eclipse.jgit.lfs:7.3.0.202506031305-r` (Maven Central, https://repo1.maven.org/maven2/org/eclipse/jgit/org.eclipse.jgit.lfs/7.3.0.202506031305-r/). Jar 81,728 B; contents listed with `unzip -l`. `org.eclipse.jgit.lfs.server` is separate and not needed (server side; used only for a test fixture, see below).
- POM deps: `org.eclipse.jgit:org.eclipse.jgit:${project.version}` and `com.google.code.gson:gson` (no version in child POM; MANIFEST `Import-Package com.google.gson;version="[2.8.2,3.0.0)"`). No httpclient: it uses `HttpTransport.getConnectionFactory()` (JGit's `HttpConnection`, default `HttpURLConnection`-based).
- `Bundle-RequiredExecutionEnvironment: JavaSE-17`; bytecode otherwise plain Java (no native code).

Classes (javap + source): 
- `BuiltinLFS` extends `util.LfsFactory`. `register()` = `LfsFactory.setInstance(new BuiltinLFS())`; its constructor registers filter commands `jgit://builtin/lfs/smudge` and `jgit://builtin/lfs/clean` in `FilterCommandRegistry`. `isEnabled(repo)` = repo config `filter.lfs.useJGitBuiltin=true` (default false). `getPrePushHook` returns `LfsPrePushHook` only if enabled. `getInstallCommand()` -> `InstallBuiltinLfsCommand` sets `filter.lfs.useJGitBuiltin=true` and `filter.lfs.required=true`, then best-effort shells `git lfs install` (ignored if absent).
- `LfsPointer`: `VERSION="https://git-lfs.github.com/spec/v1"`, legacy `https://hawser.github.com/spec/v1`, `SIZE_THRESHOLD=200`, `FULL_SIZE_THRESHOLD=8192`; `parseLfsPointer(InputStream)` (null if not a pointer), `encode(OutputStream)`. Oid type `lfs.lib.AnyLongObjectId` (SHA-256). Public, usable standalone.
- `Lfs(Repository)`: local store at `<gitdir>/lfs` (`getLfsRoot`, `getMediaFile(oid)` -> `lfs/objects/aa/bb/<oid>`, `getLfsTmpDir`, `createTmpFile`).
- `CleanFilter`: streams content to `lfs/tmp`, hashes (SHA-256), atomic-moves into `lfs/objects/..`, writes pointer. `SmudgeFilter`: parses pointer; if media file missing -> `downloadLfsResource` (batch POST then GET of `actions.download.href`); if the stream is not a pointer, passes through unchanged. Note `Files.exists(mediaFile)` short-circuit: **if the object is already in `.git/lfs/objects`, smudge never touches the network** (this is our seam).
- `LfsPrePushHook` (run by `PushProcess` via `Hooks.prePush`, which consults `LfsFactory`): walks new commits excluding `refs/remotes/<remote>/*`, collects blobs `< 200 B` that parse as pointers, batch POST `upload`, PUT each `actions.upload.href` from local media file; throws `IOException(missingLocalObject)` if object absent locally. Only `HTTP_OK` accepted; `actions.verify` is ignored. Runs inside `git.push()`.
- `LfsBlobFilter.smudgeLfsBlob/cleanLfsBlob`: used by `ResolveMerger`/`DiffFormatter`.
- `internal.LfsConnectionFactory`, `internal.LfsConfig` (see below), `Protocol` (batch DTOs; `Protocol.gson()`), `errors.*` (`LfsUnauthorized`, `LfsRateLimitExceeded`, ... exist as classes but the HTTP code paths only throw plain `IOException`).

### LFS URL derivation (VERIFIED, `LfsConnectionFactory.getLfsUrl`/`discoverLfsUrl`)
Order: `lfs.url` from `LfsConfig` (reads `.lfsconfig` from working tree, then index, then HEAD; falls back to repo config values) -> `lfs.<remote>.url` -> only for remote named `origin`: if remote URL scheme is null or `ssh`, run `ssh <host> git-lfs-authenticate <project> <upload|download>` (30-ish s timeout constant `SSH_AUTH_TIMEOUT_SECONDS`, result cached until `expires_in/at`) and use returned `href` + headers; else `nameWithDotGit(remoteUrl) + "/info/lfs"`. Batch endpoint = that + `/objects/batch`. Remote must be named `origin` for discovery (our `GitConfig.remoteName` is configurable: INFERRED risk, set `lfs.url` explicitly).
SSH: uses `SshSupport.runSshCommand` (JGit's configured `SshSessionFactory`; ours is Apache MINA on JVM, JSch on Android: INFERRED that the custom `SshdSessionFactory` is picked up through `SshSessionFactory.getInstance()` only if set globally; we set it per-transport via `setTransportConfigCallback`, so likely NOT used, UNVERIFIED).

### Auth (VERIFIED, decisive)
`getLfsConnection` builds the HTTP connection from URL + proxy + `http.sslVerify` only; adds `Accept`/`Content-Type: application/vnd.git-lfs+json` and (SSH path only) the headers returned by `git-lfs-authenticate`. `getLfsContentConnection` adds the `action.header` map from the batch response (e.g. S3 signed headers) and `Accept-Encoding: gzip`. A grep for `credential|Authorization` over the whole lfs source shows only the `HDR_AUTH` constant. No `CredentialsProvider`, no netrc, no `.git-credentials`, no `Authenticator`. Corroborated by the maintainers' thread ("LFS doesn't support HTTPS authentication yet", jgit-dev 2020-03-02: https://eclipse.org/lists/jgit-dev/msg03904.html) and tracking bug 535814 as cited by search results (https://www.eclipse.org/lists/jgit-dev/msg03802.html); I did not find a fix in 7.3.0 source (VERIFIED absent in code, bug status INFERRED).
Consequences: (a) public repos with anonymous download work; (b) private https repos and ALL uploads to github.com/gitlab.com over https fail with 401 (`serverFailure` IOException).
Possible patches of the stock path: `java.net.Authenticator.setDefault` (process-global, HttpURLConnection retries on 401 with it; works only if JGit's connection factory is the JDK one; leaks creds scope across the whole JVM, INFERRED, untested) or a custom `HttpConnectionFactory` via `HttpTransport.setConnectionFactory` (also global, and also used by plain git HTTP: INFERRED). Neither is clean.

### Transfer, timeouts, progress, resumability (VERIFIED)
- Basic transfer only (no `transfers` field is sent; no `Range`; no `multipart`/`tus`; `verify` ignored). Whole-file `Files.copy` from response to final media path (no temp-then-rename in download: a partial file at the final path on failure can later pass the `Files.exists` check and be smudged truncated; size is checked after copy but the file is not deleted on mismatch: INFERRED hazard from reading `downloadLfsResource`).
- No timeouts set on LFS `HttpConnection` (no `setConnectTimeout/ReadTimeout`; grep for `Timeout` finds only the SSH constant). `git.clone().setTimeout()` does not apply. No `ProgressMonitor` plumbing, no cancellation, no resume, no per-object retry, no parallelism, no concurrency across objects (one batch, sequential GETs).
- Download pulls via smudge at checkout time one object at a time, each doing its own batch POST (CheckoutCommand/DirCacheCheckout call the filter per file): N files = N batch requests (INFERRED from `SmudgeFilter` constructor calling `downloadLfsResource(lfs, db, res)` with a single pointer).

## 2. Behaviour in JGit core 7.3.0 (VERIFIED by reading core sources unless noted)

Hook points are config-driven, not `LfsFactory`-driven, for checkout/add:
- Checkout/clone/merge-fast-forward/reset: `DirCacheCheckout` (`:1232-1253`, `:1493-1499`) takes `walk.getSmudgeCommand(...)` (= git config `filter.<driver>.smudge` where driver from `.gitattributes filter=lfs`) and, if it is a registered `jgit://builtin/...` name, runs it in-process (`runBuiltinFilterCommand`); otherwise runs it as an external shell command (`git-lfs smudge`). Therefore smudge happens on every working-tree write of a path with `filter=lfs`.
- `AddCommand`/status/diff via `WorkingTreeIterator.filterClean` (`:479-513`): uses `getCleanFilterCommand()` (git config `filter.lfs.clean`); registered builtin -> in-process `CleanFilter`; otherwise tries to exec the string via shell. So clean runs on `git add` AND on status/dirty checks (hash comparison of working file through the filter, so a large binary is rehashed through SHA-256 + written to `lfs/tmp` each time `WorkingTreeIterator` computes the content id: cost INFERRED, correctness fine).
- **Both clean/smudge activation needs repo config `filter.lfs.clean = jgit://builtin/lfs/clean`, `filter.lfs.smudge = jgit://builtin/lfs/smudge`** (my reading of `FilterCommandRegistry` use above; the lfs module's `InstallBuiltinLfsCommand` writes only `useJGitBuiltin`/`required`, and JGit's own `DirCacheCheckout` resolves the builtin name from `filter.lfs.smudge`; check against EGit docs before relying on the exact keys: UNVERIFIED). If `filter.lfs.*` is already set by system `git lfs install` in the user's global gitconfig to `git-lfs clean -- %f`, JGit will try to run that via shell: works on Desktop with git-lfs installed, fails/ignored on Android (no shell git-lfs). Existing `.git/config` for repos cloned by system git+lfs contains exactly those external commands: relevant for Desktop users who also use the CLI.
- `ResolveMerger` (`:672`, `:1721`) uses `LfsFactory.getInstance()` (needs `BuiltinLFS.register()` + `filter.lfs.useJGitBuiltin=true` + `merge` attribute `lfs`): pointers are smudged to real content for text merge `getRawText`; if not enabled, pointer text is merged line-wise (both-sides-modified pointers conflict as text; one-side modified resolves cleanly to that side's pointer, which is the correct result). Binary LFS assets almost never need a 3-way text merge, so the unenabled behaviour is acceptable and avoids network during merge (INFERRED; also note enabling merge-smudge would trigger downloads of base/ours/theirs).
- `PushProcess` calls `Hooks.prePush` (`transport/PushProcess.java:168`) -> `LfsFactory.getInstance().getPrePushHook` only when `isAvailable()` and `isEnabled(repo)`; otherwise plain no-op hook. Cannot be turned off per push call except by not enabling.
- Shallow clone: pointers are ordinary blobs in the shallow pack; LFS objects are not part of git history/packs, so depth does not matter for LFS. `LfsPrePushHook.findObjectsToPush` excludes `refs/remotes/origin/*`; with shallow history `ObjectWalk` can walk to the shallow boundary only (INFERRED: fine, it enumerates pointers in new commits and any boundary-reachable blobs not excluded; may re-announce pointers already on the server, harmless: the server answers without upload actions). In a shallow clone, any ref that is not exclude-able (different remote name than `origin`, hard-coded via `remote()` default if `getRemoteName()==null`) could push many historical objects: our remote name is configurable, risk INFERRED.
- Known JGit LFS limitations (sources: lfs source above; lists above; 7.x release notes not found that change this): no https auth; no `lfs.locksverify`; no `.lfsconfig` URL rewriting beyond `lfs.url`; no ssh `lfs.sshtransfer` pure-ssh transfer; `git lfs pointer` extensions (`ext-*` lines) not supported by `LfsPointer` parsing: INFERRED; only the basic adapter; no `fetch`-without-checkout (`lfs fetch`) command; no `lfs prune`; no sparse-checkout interplay (ADR-012 notes JGit CheckoutCommand disables sparse state, orthogonal).
- `LfsPointer.parse` reads first 200 B; files with `filter=lfs` that were committed as raw binaries (pre-existing violations) are returned raw by smudge (passes through). Pointers with `hawser` legacy version accepted.
- DirCache/status: with the filter configured, `WorkingTreeIterator` compares the clean-filtered content id against the index entry, so pointer-in-index vs smudged-content-in-worktree is treated as clean (VERIFIED by reading `filterClean` use in `getEntryContentLength/idBuffer`). Without the filter configured, status treats a smudged file as modified and `git add` would commit raw bytes (this is exactly today's bug).

## 4. Alternatives compared

Options: A) stock JGit LFS (`BuiltinLFS`), B) hybrid: JGit filters/pointer/`Lfs` store + own Ktor client for batch/transfer, C) pure custom (own clean/smudge integration too), D) shell out to `git-lfs`.

D) shell out. ADR-012 (read: `docs/adr/ADR-012-system-git-sparse-checkout-processbuilder.md`) accepts system git via `ProcessBuilder` only for Desktop, explicitly no-op on Android ("System git is not reliably available on Android") and iOS/WASM; detection via `which git`, silent skip if absent. `git lfs` additionally needs the git-lfs binary and the user's credential helper; our PAT lives in the vault (`VaultCredentialStore`, `credentialAccess.retrieve`) not in git's credential store, so we would have to inject it (`GIT_ASKPASS`/`credential.helper` env: INFERRED). Android: not viable. Web: not applicable. Verdict: acceptable only as an optional Desktop fast path; not a foundation.

Comparison:

| Criterion | A stock JGit LFS | B hybrid (recommended) | C pure custom | D shell git-lfs |
|---|---|---|---|---|
| Code sharing | JVM+Android only | pointer model + batch/transfer client in commonMain, shared with web read path; JGit glue in jvmCommon (`jvmCommonMain/.../git/` already shares `GitOperationSupport`) | max | Desktop only |
| Auth | none for https (VERIFIED) -> fails on GitHub/GitLab push, private pull | we send `Authorization` from the same vault token already resolved (`preResolvedToken`, `configureTransportAuth`) | same as B | system helper, needs injection |
| Android | works for anon public only | works (Ktor OkHttp engine already on JVM `:180`; Android engine: INFERRED existing) | works | no |
| Correctness | pointer/clean/smudge from reference impl; no timeout/resume/verify/partial-file safety | JGit's tested clean/smudge/pointer; we own transfer: timeouts, temp+rename, SHA-256+size verification, batch of N objects, retry, progress, `verify` action | must replicate DirCache filter integration (JGit exposes it only via `FilterCommandRegistry`, so can register own `FilterCommand`s anyway) | reference impl |
| Maintenance | low code, high risk (upstream bug 535814 open for years) | medium: ~ batch API client + upload + download + tests | highest | low code, env fragility |
| Timeouts/progress/resume | none | ours | ours | git-lfs's |

B works because of two verified seams: (1) smudge checks `Files.exists(lfs.getMediaFile(oid))` before any network (`SmudgeFilter` constructor) and clean writes into the same store, so a client that downloads required objects into `<gitdir>/lfs/objects/aa/bb/<oid>` *before* checkout/merge/reset makes JGit's smudge purely local; (2) push needs no JGit hook if we upload before `git.push()` and leave `filter.lfs.useJGitBuiltin` unset (then `Hooks.prePush` returns the no-op hook and `ResolveMerger` does not smudge). Filter commands still need `BuiltinLFS.register()` (constructor registers the filter names) or our own `FilterCommandRegistry.register("jgit://builtin/lfs/clean", ...)`; calling `register()` also sets the global `LfsFactory` instance, which only takes effect when `useJGitBuiltin` is true per repo (VERIFIED `isEnabled`), so global registration is safe for non-LFS repos. INFERRED/UNTESTED: that `filter.lfs.clean/smudge` pointing at `jgit://builtin/lfs/*` works with `useJGitBuiltin` unset; a spike must prove it (also that "required" semantic is irrelevant).
Download timing for B: pointers are discovered by a pre-step (walk `HEAD`/target tree and `.gitattributes`, parse pointers with `LfsPointer.parseLfsPointer`, skip existing media) before `checkout`/`merge`/clone completion; for clone, clone with `setNoCheckout(true)`, fetch LFS objects, then checkout (JGit `CloneCommand.setNoCheckout` exists in core: INFERRED, verify). For merge: after `fetch`, collect pointers changed between HEAD and `FETCH_HEAD`/remote tracking tree (`TreeWalk` diff, size < 200 B check as `LfsPrePushHook` does), download, then `merge()`.
Upload in B: before `push()`, replicate `findObjectsToPush` (copy the ~40-line ObjectWalk logic; it is public API only through `LfsPrePushHook`'s private methods, so reimplement) then batch `upload`, PUT, `verify`.

Recommendation: B. Reasons: stock A is blocked by missing https auth (the owner's primary targets github.com/gitlab.com use PAT over https); C duplicates tested filter code for no gain; D excludes Android/iOS/web. Keep D as an optional Desktop accelerator only if wanted later (not needed). Cost: one commonMain `LfsBatchClient` (Ktor, kotlinx-serialization-json already present `:122-123`) shared with the web read path and with iOS later; web still blocked by CORS per `research/web-lfs.md`.
