### 1.0 Facts about JGit LFS 7.3.0 that shape the tests (VERIFIED)

Source: `org.eclipse.jgit.lfs-7.3.0.202506031305-r-sources.jar` from https://repo1.maven.org/maven2/org/eclipse/jgit/org.eclipse.jgit.lfs/7.3.0.202506031305-r/ (unpacked in the session scratchpad); POMs from the same Maven Central tree.

- Coordinates exist at the same version as the existing JGit pin (`kmp/build.gradle.kts:146,175,342`; `MODULE.bazel:311`): `org.eclipse.jgit:org.eclipse.jgit.lfs:7.3.0.202506031305-r`. Its only extra runtime dep is `com.google.code.gson:gson` (POM). Client side is light.
- Not active by default. `BuiltinLFS.isEnabled(db)` returns true only if git config `filter.lfs.useJGitBuiltin = true` (`BuiltinLFS.java:92-100`), and `BuiltinLFS.register()` must be called explicitly (there is no ServiceLoader file in the jar; `unzip -l` shows only `OSGI-INF/l10n/plugin.properties`). Neither string appears anywhere in `kmp/src` (`grep -ri "useJGitBuiltin\|BuiltinLFS"` returned nothing). So a test must assert both the registration and the per-repo config key, or LFS will silently be a no-op.
- JGit sends NO Authorization header on the batch or content endpoints except for SSH-discovered ones. `LfsConnectionFactory.getLfsConnection` (lines 73-96) sets only Accept/Content-Type plus `additionalHeaders`, which are filled only by `getSshAuthentication`. `grep -rn "Authorization\|Credential"` over the LFS sources hits only the `HDR_AUTH` constant in `Protocol.java:116`. Consequence: the PAT that SteleKit's `JvmGitRepositoryAuth` passes via a `CredentialsProvider` is not used for LFS. Private repos over https will get 401/403 from the LFS API unless credentials are embedded in `lfs.url` (userinfo) or a custom `HttpConnectionFactory` is installed. This is the single biggest implementation risk for the JVM/Android path; a test against an auth-requiring fixture is mandatory.
- Server URL discovery (lines 114-170): config `lfs.url`, then `lfs.<remote>.url`, then `remote.origin.url` + `.git/info/lfs` (https) or `git-lfs-authenticate` over SSH. `file://` or local-path remotes: `new URIish(path).getScheme() == null` routes to the SSH branch (`discoverLfsUrl`, lines 159-165) and fails with `LfsConfigInvalidException`. So LFS cannot be exercised against a bare-repo-on-disk origin unless the test sets `lfs.url` (or `lfs.<remote>.url`) to the fixture's http URL. That is the intended test design: git transport stays on a local bare origin (as `BareOriginFixtures` already does), LFS transport goes to an http fixture via the `lfs.url` override.
- Upload is a pre-push hook: `LfsPrePushHook.call()` walks all objects reachable from the pushed refs minus remote-tracking refs, collects blobs smaller than `LfsPointer.SIZE_THRESHOLD` (200 bytes) that parse as pointers, and batch-uploads them (lines 70-130 of `LfsPrePushHook.java`; `LfsPointer.java:54`). A shallow clone has no remote-tracking history to subtract, so first push after a shallow clone may re-offer every pointer (the server answers "already present", no upload action). INFERRED for server behaviour, VERIFIED for the walk.
- Pointer parser in JGit (`LfsPointer.java:142-215`): reads up to 200 bytes; if longer, requires a `version` first line and allows up to 8 KiB (`FULL_SIZE_THRESHOLD`). It is more lenient than the spec: it skips `#` comment lines and blank lines (lines 206-208), and its own comment says so. This leniency is a test oracle mismatch to design around: our common Kotlin parser must follow the spec, and the JVM adapter must not rely on JGit's parser to decide "is this a pointer" for the commit guard.

### 1.2 (b) Regression tests for "never commit a raw binary for an LFS-tracked path"

Layered, cheapest first:
1. Pure-logic property tests in `commonTest` (kotest-property, plain `@Test` + `runTest { checkAll(...) }` per CLAUDE.md, VERIFIED: `kmp/build.gradle.kts:157-162`): generate (`.gitattributes` content, path list); oracle = a deliberately naive reference matcher or a table of hand-labelled cases; assert `guard.violations(paths)` equals exactly the paths whose resolved `filter` attribute is `lfs`, for every combination of: nested `.gitattributes` in subdirectories (deeper wins), later line wins, `-filter` / `!filter` / `filter=other` unset-or-override cases, and the "pattern with no slash matches basename at any depth" rule. 2. Pointer-aware property: for any generated blob bytes and any LFS-matching path, `guard.allows(path, bytes)` is true iff `LfsPointer.parse(bytes)` succeeds (spec-valid pointer) or the file is exempt per config; every non-pointer is refused. Include the nasty cases: a text file that merely begins with `version https://git-lfs.github.com/spec/v1`, a pointer with CRLF, a >1024 byte pointer-looking file (must be treated as raw content, hence refused), an empty file at an LFS path (decision needed: git-lfs stores 0-byte files as raw empty blobs; INFERRED, decide in the ADR).
3. Service-level tests in businessTest using the existing doubles: `GitSyncServiceFirstSyncGateTest`/`GitSyncServiceConflictMarkerGuardTest` (VERIFIED present in `kmp/src/businessTest/kotlin/dev/stapler/stelekit/git/`) are the pattern: stub `StubGitRepository` (commonTest `testsupport/`) so `status()` reports a changed `assets/x.png` and a stub filesystem holding raw PNG bytes and a `.gitattributes`; assert `GitSyncService` refuses to stage/commit and surfaces a typed error before `commit()` is invoked. One test per entry point that can stage: normal commit, `markResolved` (the recent conflict-marker fix `5d00781169` shows this second entry point was missed once), conflict-resolution writes, share/capture appenders, and write-back queue flushes.
4. Real-JGit end-to-end in jvmTest/businessTest (needs 1.1 fixture): with LFS enabled, commit a new 3 MB `assets/a.bin`; assert the tree blob at that path is a pointer, `.git/lfs/objects/<oid[0:2]>/<oid[2:4]>/<oid>` exists, the fake received exactly that object, and the push left the origin with only pointer blobs (walk every blob of the origin: none at an LFS path is non-pointer). Second test with LFS support deliberately disabled: assert the commit is refused (the safety floor), never a raw commit.
5. Web: wasm test that the Data-API write path (`WasmGitWriteService`) throws/records a typed refusal for an LFS-matching path and never emits a `POST .../git/blobs` with that content (assert on MockEngine's request log, see 1.4).

### 1.3 (c) Pointer parse/serialise: spec and property tests

Spec fetched from https://github.com/git-lfs/git-lfs/blob/main/docs/spec.md (VERIFIED). Normative points:
- Text-only UTF-8; each line is `{key} {value}\n` with a single space; keys limited to `[a-z] [0-9] . -`; first key is always `version`; remaining keys alphabetically sorted; values contain no CR/LF; total size under 1024 bytes; ends with a Unix newline.
- Required keys: `version` (URL, case-sensitive string compare; canonical `https://git-lfs.github.com/spec/v1`), `oid` (`<method>:<hex>`, only `sha256` lowercase hex currently), `size` (bytes). Extension keys use the `ext-N-<name>` form from the extensions doc; not in this page (INFERRED: `ext-0-foo sha256:...` lines sort between `oid`/`size` alphabetically: `ext-*` < `oid` < `size`, so they come right after `version`; confirm against `docs/extensions.md` before coding).
- Also INFERRED from memory of git-lfs `lfs/pointer.go`, not fetched: the real parser also accepts the legacy version URLs `http://git-media.io/v/2` and `https://hawser.github.com/spec/v1`; decide whether to accept them on read (recommended) and always write the canonical one.

Properties to generate (kotest `Arb`):
- Round trip: `parse(serialize(p)) == p` for random sha256 (64 lowercase hex), size `0..Long.MAX_VALUE` (including 0 and values with 19 digits).
- Canonical form: `serialize(parse(bytes))` is byte-identical to `bytes` whenever `bytes` is spec-canonical; assert key order (`version`, extensions, `oid`, `size`), exactly one trailing `\n`, size < 1024.
- Rejection set (each must return null/typed error, never throw): missing `version`/`oid`/`size`; `version` not first; wrong-case version URL; oid with uppercase hex, wrong length (63/65), non-hex, `sha1:`/`md5:` method; negative, non-numeric, or overflowing size; duplicate keys; unsorted keys (spec says sorted; git-lfs is lenient on read, decide strictness and test the decision); no trailing newline; key with uppercase or `_`; value containing `\r`; >= 1024 bytes; BOM at start; NUL bytes; non-UTF-8.
- CRLF: a pointer whose line endings were rewritten to `\r\n` (the autocrlf failure mode, R2) must be detected as "corrupted pointer", distinct from "not a pointer", so the repair path can normalise it. JGit's reader (`BufferedReader.readLine`) would silently accept CRLF (VERIFIED by reading lines 206-215: `readLine` strips `\r\n`), so the oracle must be our own parser.
- Differential test (JVM only): for spec-canonical generated pointers, our parser and `org.eclipse.jgit.lfs.LfsPointer.parseLfsPointer` agree on oid and size; for the rejection set, document each divergence (JGit accepts comments, blank lines, and unsorted keys per its own comment at `LfsPointer.java:202-205`).
- Where: pure functions in `commonMain`, tests in `commonTest` per CLAUDE.md ("Test pure logic in commonMain/commonTest"; `HostReconciliationTest` is the cited reference). Runs under Gradle `jvmTest`, `testDebugUnitTest`, `wasmJsBrowserTest`. For Bazel, see 1.5.

### 1.6 `.gitattributes` semantics to be tested, and which matcher implementation

Semantics to encode (gitattributes(5); INFERRED from the manpage, not re-fetched this session; add a labelled table of expected results from `git check-attr` runs in a fixture generator so the oracle is real git, which is VERIFIED-able at test-author time):
- Attribute patterns follow gitignore wildcard rules with differences: no negative patterns (`!pat` is not supported); a pattern with a trailing `/` does not match anything (attribute patterns cannot target directories only); a pattern matching a directory does not recursively apply to its contents. A pattern with no `/` matches the basename at any depth; a pattern containing `/` is anchored to the directory of that `.gitattributes`; `**` works as in gitignore (`**/x`, `x/**`, `a/**/b`).
- States: set (`filter`), unset (`-filter`), unspecified (`!filter`, reverts a previous setting), value (`filter=lfs`). `filter=lfs diff=lfs merge=lfs -text` is what `git lfs track` writes; only the `filter` attribute value `lfs` matters for pointer handling.
- Precedence: within a file, last matching line wins per attribute; `.gitattributes` in a subdirectory overrides parent directories for paths below it; `$GIT_DIR/info/attributes` overrides all in-tree files; global/system files are lowest. Macros (`[attr]name ...`, notably built-in `binary`) are honoured only in the top-level `.gitattributes`, `info/attributes` and global files, not in subdirectories.
- Case sensitivity follows `core.ignorecase`; matching is on `/`-separated repo-relative paths; unicode normalisation (macOS NFD vs NFC) can desync a path from its pattern (INFERRED).
- Content source: git reads `.gitattributes` from the working tree (checked out) for add/status, from the index/tree for bare or checkout; an uncommitted edit to `.gitattributes` changes what `add` does, and a `.gitattributes` introduced by a merge takes effect only after checkout. Tests: guard must evaluate attributes from the same source the staging step will use (working tree plus index), not from `HEAD`.

JGit exposure (VERIFIED by `unzip -l` on the cached jar `~/.gradle/caches/modules-2/files-2.1/org.eclipse.jgit/org.eclipse.jgit/7.3.0.202506031305-r/.../org.eclipse.jgit-7.3.0.202506031305-r.jar`): `org.eclipse.jgit.attributes.{Attribute, Attributes, AttributesNode, AttributesRule, AttributesHandler, AttributesNodeProvider, FilterCommandRegistry}`, `org.eclipse.jgit.util.LfsFactory`, `org.eclipse.jgit.hooks.Hooks`. `TreeWalk.getAttributes()` is the public lookup (INFERRED API, standard since JGit 4.2; not exercised here) and handles nested files, macros and info/attributes. Usable on JVM and Android (same JGit 7.3.0 artifact in both source sets). It is not available in `commonMain`/wasm.

Existing matcher in repo: none. `grep -rilE "gitattributes|gitignore|AttributesNode|LfsPointer|lfs" kmp/src --include='*.kt'` hits only `SidecarManager.kt` (a doc comment), `GraphManager.kt:421-424,1330` (`checkGitignoreForDatabase`, which just inspects `.gitignore` text, not a matcher), and three tests that mention gitignore incidentally. So `commonMain` needs a new pure-Kotlin attribute matcher (wasm has to decide LFS-ness from a `.gitattributes` fetched over REST). Recommendation: implement the matcher once in `commonMain`, and in jvmTest run a differential property test against JGit's `TreeWalk.getAttributes()` and against `git check-attr` (if git on PATH) for generated attribute files; that is the evidence that the pure-Kotlin matcher equals the reference. Use JGit's lookup in production on JVM/Android only if it is the simpler path, but keep the common matcher as the guard of record so all platforms share one oracle.
