# ADR-004: Scheduled sync is a full sync only while the app is open; closed-app background work is fetch-only

**Status**: Accepted (owner decision 2026-10-10, final; mechanism chosen here) | **Date**: 2026-10-10 | **Amended**: 2026-10-10 (Phase 3 repair; re-review R1-R4, N1-N3, R5; **Phase 4 repair: cold full-sync path removed per owner decision (a)**)

## Context
Today WorkManager (`WorkManagerSyncScheduler.kt:137,143,213`) and the desktop timer only fetch and show a `MergeAvailable` badge. The owner first decided that scheduled sync includes merge and push, then (Phase 4, final) narrowed it: a full commit + merge + push runs while the app is open (within the interval) or on manual sync; with the app closed, background work only fetches and keeps a badge/behind-count fresh. The owner's active graph is the cloned app-private (non-`saf://`) graph; SAF graphs stay fetch-only for scheduled work.

Verified facts that shaped the decision:
- `GitRepository.abortMerge(config)` already exists (`GitRepository.kt:69`; Jvm `:358`, Android `:375`) and is a **hard reset** that discards uncommitted edits. It is reused unchanged and is only reachable from the user-initiated abort (Task 2.4i protects unrelated edits there); no background code calls it.
- `GitConfig.autoCommit` is stored (`GitConfig.kt:22`) but **nothing reads it**; `sync()` commits whenever there are local changes. Task 2.4d makes it honored.
- `GitSyncServiceRegistry` (`WorkManagerSyncScheduler.kt:252`) already exists and the worker's fast path reads it (`:137`), but **no production code calls `register`**; the fast path is currently dead. `GraphManager.registerGitSyncService` is wired in `GraphContentGitSyncSetup.kt:43`.
- WorkManager periodic work has a 15-minute minimum interval.
- The existing slow path builds `AndroidGitRepository(context, PlatformFileSystem())` with an uninitialized `PlatformFileSystem` because fetch never touches the working tree (`WorkManagerSyncScheduler.kt:173-183`). Keeping the closed-app path fetch-only keeps that premise true.

## Decision
- `ScheduledSyncPolicy` (commonMain, pure, unit-tested) decides what a tick may do: `Run` (full sync), `FetchOnly(reason)` or `Skip(reason)`. Inputs: online, vault unlocked, `EditLock` idle, `GitSyncBusyCounter == 0`, backoff after `Error`, in-memory `SyncState`, **repository state** (`MERGING`/unmerged/detached => `Skip(RepoState)`; git's own state survives process death, so no private markers exist), graph path mode via `isAppOwnedPath` (not app-owned => `FetchOnly(Saf)`), and the **first-sync confirmation** (`Skip(FirstSyncUnconfirmed)` until one manual, previewed sync has succeeded for the current `(remote, branch)`). `GitSyncService.runScheduledSync` = policy + `sync()`/`fetchOnly`; `sync()` is not given scheduling branches.
- **One registry**: reuse `GitSyncServiceRegistry` (promoted to commonMain, same API, thread-safe) and add the missing `register`/`unregister` calls beside `registerGitSyncService` in `GraphContentGitSyncSetup.kt`. The Android worker fast path calls `service.runScheduledSync(graphId)` instead of `fetchOnly`; the desktop timer is `startPeriodicSync` inside the service.
- **Android interval floor**: effective interval = `max(setting, 15 min)`; shorter settings are clamped and the settings text says so.
- **Live process (app open)**: `sync()` runs as today (commit per `autoCommit`, merge, existing conflict UI on conflict) with these guards on **every** commit and push path in `GitSyncService` (`sync()` commit/push, `commitLocalChanges`, `resolveConflicts` commit, `applyJournalMerge` commit and push; Tasks 2.3e, 2.3f): a repository-state precheck (refuse on `MERGING`/unmerged paths/detached HEAD with `SyncState.RepairNeeded`, except the paths that legitimately run in `MERGING`); a conflict-marker scan of the added lines of the **net tree diff** (`origin/<branch>` tree vs `HEAD` tree, never per-commit patches) and of the staged diff, over all text files, fenced blocks ignored, failing closed on the size cap; and a **mass-change guard** (deleted files > `max(20, 5% of previous tree)` or > 10 journals) that a foreground confirm may lift once per run but a scheduled run never lifts. With no remote-tracking ref the net-diff scans are skipped and push stays fail-closed through the unresolved-ref error. Force push is never used (source-audit test).
- **Closed app (no live service)**: `ColdSyncRunner` is **fetch-only**. It takes the `GitWriteLockNaming` lock, performs exactly one fetch, records `behindCount`, `lastFetchedAt` and the outcome in `SyncStaleness`, and returns `ColdSyncOutcome.Fetched(behindCount, reason)` or `Error(cause)` (`reason` is `AppClosed` or `Saf`; `Saf` appears only here). It never merges, commits, pushes, stages, checks out or calls `abortMerge` (spy-asserted), whatever the tree state. Because it cannot write the working tree, the earlier cold machinery is deleted: the in-core merge preflight (spike 0.1c), `git_merge_in_progress_<graphId>` and `git_pending_conflict_<graphId>` markers and their lifecycle, `MergeInProgressMarker`, the kill-point repair routine, the cold push guard (N1) and the live-`sync()` marker gate (N3). A process killed mid-merge in the *live* path is covered by the repository-state guard (`MERGING` => `RepairNeeded`).
- **Staleness is visible** (pre-mortem P1-2): a permanent chip "last merged <age> · behind <n>" (amber after 2x the effective interval), the last-10 background outcomes in `diag` and `git doctor`, a low-importance Android notification "N remote commits are waiting — open SteleKit to merge" (permission-gated, default on, cleared at `behindCount == 0`), and a launch banner. A graph classified fetch-only shows "fetch-only (<reason>)", never green.
- **First sync is confirmed** (pre-mortem P1-1): the first scheduled run for a `(remote, branch)` waits for a manual sync preceded by a read-only preview (ahead/behind, all remote branches with strays flagged, first 20 local-only commits, files-to-delete count). The confirmation key changes with the branch, so a repair re-arms it.
- **User-initiated abort (R5, Task 2.4i)**: `abortActiveMerge` still calls the hard-reset `abortMerge`, but first runs `status`; modified non-conflicted files are snapshotted to an app-private recovery dir (fail closed), confirmed by the user, and restored after the reset.
- `ColdSyncOutcome`: `Fetched(behindCount, AppClosed|Saf)` / `Error(cause)`.

## Alternatives rejected
Cold full sync with preflight, markers and repair routine (owner withdrew it; the machinery existed only to make a background tree write safe); auto-merge only on fast-forward; badge-only everywhere with the metric reworded (the owner wants open-app full sync); merge inside `GitSyncService.sync` scheduling branches (grows hotspot); a second registry; a new `abortMerge` signature or `MergeAbortResult`.

## Consequences
With the app closed the phone only learns that it is behind; commits are merged when the app is next open (within the interval) or on tap, so freshness of the working tree depends on opening the app, and the chip, notification and banner make that visible. Needs a real-device pass (Stories 7.1, 7.1b). The previously open owner question on cold-worker conflict behavior is closed by this decision.
