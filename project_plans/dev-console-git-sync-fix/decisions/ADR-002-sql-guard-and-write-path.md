# ADR-002: Engine-enforced read-only SQL (fail closed), actor-routed writes, deny-list, backup and restore

**Status**: Accepted pending spikes 0.2a/0.2b/0.2c | **Date**: 2026-10-10 | **Amended**: 2026-10-10 (Phase 3 repair, A1-A5 below; Phase 4 repair: swap order, DB-only guard)

## Context
Owner chose full-power console (raw SQL writes). CLAUDE.md forbids direct mutations outside `DatabaseWriteActor` / `@DirectSqlWrite`. The JVM driver is `PooledJdbcSqliteDriver` (8 pooled connections), so `PRAGMA query_only` on a shared connection leaks into app queries. `SqliteStatementAnalyzer.leadingKeywords` classifies only the first statement. `DriverFactory.createReadDriver` returns `null` on JVM (`jvmMain/.../db/DriverFactory.jvm.kt:143`) and iOS (`iosMain/.../DriverFactory.ios.kt:17`); only Android has one (`androidMain/.../DriverFactory.android.kt:174`).

## Decision
1. **Read path (A1, fail closed)**: tokenizer-based single-statement splitter (honours quotes/comments/`;`) routes statements. Reads run **only** on a console-owned, engine-enforced read-only connection (`SqlConsoleReader`), never on the app's pooled connections and never on the write path:
   - JVM: a dedicated `JdbcSqliteDriver`/`java.sql.Connection` opened on the same DB file with SQLite read-only open flags (`SQLiteConfig.setReadOnly(true)`), WAL permitting concurrent readers; spike 0.2a proves rejection of `UPDATE` and `WITH ... DELETE` and no leak into pooled connections.
   - Android: `createReadDriver` or `SQLiteDatabase.openDatabase(..., OPEN_READONLY)`.
   - iOS and wasm: no read-only connection unless spike 0.2a shows one; otherwise `sql` reads are **disabled with a reason**.
   - **If the connection cannot be opened or the spike fails on a platform, reads are disabled there. There is no classifier-only fallback**: the classifier is a router and error-message helper, never the security boundary. Writes remain available only through the gated actor path (item 2); because the write confirm needs a dry-run row count from the read connection, writes are refused too when no read connection exists (UX-55).
   - Row cap 500 by cursor iteration (no textual `LIMIT`), per-cell cap 2 KB, `withTimeout` plus driver-specific cancel.
2. **Write path (A2)**: only via `DatabaseWriteActor.execute { }` (so `processExecute` emits invalidation after `op()`). The CLAUDE.md-approved pattern is followed, not a class-level opt-in: `SqlConsoleWriter` injects `RestrictedDatabaseQueries`, and only its one private raw-exec function carries `@OptIn(DirectSqlWrite::class)`, called inside the `actor.execute` lambda. `RestrictedDatabaseQueries` gains one `@DirectSqlWrite` raw-exec forwarding stub. `DatabaseWriteActor.execute` returns `Either<DomainError, Unit>` (`DatabaseWriteActor.kt:761`), so rows-affected and the dry-run count are returned through a captured holder set inside the lambda (a `SELECT changes()` in the same lambda), not through the return value. Developer-mode flag is checked at the call site.
   - **No existing enforcement test exists** (`DirectSqlWrite` is only a compile-time `RequiresOptIn(level = ERROR)`, `db/DirectSqlWrite.kt`). Task 5.5a adds `DirectSqlWriteOptInAllowlistTest` (businessTest source audit): every `@OptIn(DirectSqlWrite::class)` site must be in an allowlist; `SqlConsoleWriter.rawExec` is added explicitly, so a new site fails CI.
3. **Hard deny (confirm cannot override)**: DDL (`CREATE/DROP/ALTER`), `ATTACH/DETACH`, `VACUUM` (user-issued), `load_extension`, writable PRAGMAs, writes to `*_fts*` tables and to migration bookkeeping. **Credential-bearing tables are denied for read and write** (not redacted on read: expression columns such as `substr()`/`hex()` defeat column redaction); they are simply not on the read allowlist.
4. **Backup (A3)**: a snapshot (`VACUUM INTO <appdir>/console-backups/<graph>-<ts>.db` as an internal operation after write-actor drain; runtime-detect support, fall back to `wal_checkpoint(TRUNCATE)` + copy) is taken (a) before the **first write of every write session** (first write after the console opens, or after 10 minutes without a write) and (b) before the first statement of each **destructive statement class** within a session (`DELETE`, `UPDATE`, `REPLACE`/`INSERT OR REPLACE`) and before any statement without `WHERE`. Keep the last 5. Never included in diagnostics export. Backups are **unencrypted full copies of the notes DB in the app directory**. The Android manifest sets no `allowBackup`/`dataExtractionRules`/`fullBackupContent` (verified: no match in `androidMain/AndroidManifest.xml`), so Auto Backup defaults on; Task 5.5f adds exclusion rules for `console-backups/`, `console-recovery/` and `git-abort-recovery/`.
   - **Restore (A3)**: `graph restore-backup <name>` (Task 5.5e). Mechanism for the live DB: validate the snapshot on a temp copy (`PRAGMA integrity_check`), drain the write actor, close the graph's drivers through a `DbRestoreView` adapter that uses the public `GraphManager.removeGraph(id)` / `addGraph(...)` (no new methods on the 1601-line class), rename the live DB (and `-wal`/`-shm`) to `*.pre-restore`, copy the snapshot in, re-add the graph, and run `graph reload` so disk wins. The console read connection is closed before the drain, stale `-wal`/`-shm` are deleted, and `integrity_check` plus a row-count comparison pass before reopening (spike 0.2b/`DbSwapSpikeTest` proves the order on a device); the checkpoint+copy fallback runs only on a quiesced actor. If any step fails the `*.pre-restore` files are renamed back and the failure is reported with the backup path. **Before the swap, `DbOnlyRowsGuard` (Task 5.6d) exports DB-only journal rows to `console-recovery/` and requires a typed confirm.** Restore is STATE_CHANGE with an explicit "later changes are lost" confirm.
5. **Markdown consistency and write cascade (A4)**: every write result is tagged "DB-only, not written to markdown". Analysis: scheduled sync stages and pushes *files*; a raw DB write reaches disk only if `GraphWriter` later serializes the touched page (user edit of that page, or a reconcile writer). Spike 0.2c proves whether `DatabaseWriteActor` invalidation itself triggers any `GraphWriter` path (expected: no; UNVERIFIED until the test runs). Policy: (i) console writes are tagged and recorded in a session `ConsoleDbDirty` list surfaced by `diag`/`graph active`; (ii) the confirm modal states that later edits to the touched pages can serialize the changed rows into markdown and be pushed; (iii) `graph reload` makes **disk win** (the sanctioned way to discard a console DB write), but only after `DbOnlyRowsGuard` has exported DB-only rows (the 2026-10-07/09/10 journals) to `console-recovery/` and the user typed the confirm; the cascade test also covers trigger-maintained FTS tables; (iv) "make disk match DB" only through `GraphWriter` verbs (`graph journals-repair`), never raw SQL; (v) `ScheduledSyncPolicy` does not block on the dirty list by default (blocking would stall sync indefinitely and does not prevent the later-edit path), but Task 5.5d adds a regression test that a raw write alone produces no file change and no commit.
6. Seam: nullable `sqlConsole` field on `RepositorySet` (precedent: `perfExporter`), implemented in the `db` package; `RepositoryFactory` is not widened.

## Alternatives rejected
SQL parser library (JSqlParser: JVM-only, dialect gaps become bypasses); keyword regex guard alone or as fallback; authorizer callback (not exposed by drivers); separate raw connection for writes (skips actor ordering, UI goes stale); class-level `@OptIn` on the writer (contradicts CLAUDE.md "only approved class-level opt-in outside the actor is migration-time writers").

## Consequences
Near-zero LLM-authored security logic: engine guard or no reads. Risk: `RepositorySet` field addition may conflict with PR #397; mitigated by rebase before Story 5.4. Restore touches graph lifecycle and is the highest-risk console action; it ships last in Epic 5.
