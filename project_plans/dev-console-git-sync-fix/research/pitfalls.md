## 1. Git sync bug: what the code actually does

- VERIFIED: `doFetch` returns `FetchResult(false, 0)` silently when `repo.resolve("<remote>/<branch>")` is null (`jvmMain/.../JvmGitRepository.kt:183-202`, `androidMain/.../AndroidGitRepository.kt:196-214`, identical). `GitSyncService.sync` (`commonMain/.../GitSyncService.kt:284-304`) then skips merge because `hasRemoteChanges=false` and ends in `Success(…, 0, …)`. Merge itself already errors on a missing ref (`JvmGitRepository.kt:259-262`: "Remote ref … not found"; Android returns the less useful "Remote ref not found" with no name, `AndroidGitRepository.kt:275`), but it is never reached. Fix both: fetch must error, and Android's merge message must name the ref.
- VERIFIED: `hasChanges = remoteRef != headBefore` is true when local is AHEAD or diverged, not only when behind. This is a second false signal (spurious `MergeAvailable`, `remoteCommitCount` from `countRemoteCommitsBestEffort`). After the fix, compute behind/ahead with a RevWalk (`isMergedInto`/merge-base) rather than OID inequality, or the new regression test for "remote ahead" passes while "local ahead" mis-reports.
- VERIFIED: `GitConfig.remoteBranch` default `"main"` (`git/model/GitConfig.kt:15`), SQL column default `'main'` (`SteleDatabase.sq:972`, `MigrationRunner.kt:376`), and `GitSetupScreen.kt:185` falls back to `"main"`. `init()` forces `setInitialBranch("main")` for new repos (`JvmGitRepository.kt:70`). So the only path that produces a master/main mismatch is clone-from-remote-with-master plus the UI default `"main"`. The setup screen should prefill from the remote's HEAD symref.
- VERIFIED: `hasRemoteDivergedSinceShallowClone` (`jvmCommonMain/.../GitOperationSupport.kt:433-452`) returns `true` (diverged) whenever the local ref is null, and the advertised ref lookup is hard-coded to `refs/heads/<remoteBranch>`. With a wrong branch, unshallow/deepen would always claim "diverged". Same root cause, a second symptom: Open Question 2 can be answered "no, not independently" once the branch is right, but test it.
- INFERRED (JGit): `CloneCommand` with `setDepth` and no `setBranchesToClone`/`setCloneAllBranches` writes the standard wildcard refspec to config, but whether a depth clone fetches only the HEAD branch is not confirmed. If the device clone only has `refs/remotes/origin/master` and config says `main`, resolve is null (the hypothesis). If the stored refspec is single-branch for a branch other than the configured one, even a corrected `remote_branch` would not fetch it. Spike: on the temp repo, clone with `setDepth(DEFAULT_CLONE_DEPTH)` and print `config remote.origin.fetch` and `branchList`. UNVERIFIED until run.
- INFERRED: `repo.resolve("origin/main")` is a rev-parse, not a ref lookup. It can match `refs/heads/origin/main`, a tag, or an abbreviated name before `refs/remotes/origin/main`. Use `repo.exactRef("refs/remotes/<remote>/<branch>")` for the existence check and keep `resolve` out of correctness paths. Branch names containing `/` (e.g. `release/x`) also need `Repository.isValidRefName` validation before building the ref.
- Remote HEAD symref: use `git.lsRemote().setRemote(...).setHeads(true).setTags(false)` and read the `HEAD` ref via `Ref.isSymbolic`/`getTarget()`. Caveat (INFERRED): JGit's `lsRemote` `call()` returns a `Collection<Ref>` where HEAD is only symbolic when the server advertises `symref=HEAD:refs/heads/x` capability (protocol v2 `ls-refs symrefs`). Some hosts or bare repos with a detached/unborn HEAD give no symref. Fallback: if HEAD's objectId equals exactly one `refs/heads/*` OID, pick that; if several, prefer `main`, then `master`, else ask the user. An empty remote (no branches) must produce a distinct "remote is empty" state, not "branch not found".
- Android ls-remote auth: the app already has `testRemoteViaLsRemote(url, auth, authConfigurer::configureAuth)` and `TEST_REMOTE_TIMEOUT_SECONDS = 15` (`GitOperationSupport.kt:454-456`). Reuse that shape. Pre-resolve the token in the suspend context before entering JGit (as `clone` does at `JvmGitRepository.kt:102`). Never call `tokenProvider()` from inside a JGit callback. SSH on Android goes through `AndroidGitRepositoryAuth`; ls-remote must use `configureTransport`, not the clone-only `configureAuth` (check which one the diagnostics Git section uses).
- SAF shadow: `AndroidGitRepository.merge` goes through `shadow.shadowWorktreeFor(config.repoRoot)` and `fetch` uses `openGitWithoutFreshnessCheck(config)`. Ref resolution happens on the internal-storage shadow `.git`, while `config.repoRoot` is a SAF URI. Any new console `git` command or branch-correction code must go through the same `openGit(config)` variants rather than `File(config.repoRoot)`. Open question for the plan: does `status` use the freshness-checked open and `fetch` the unchecked one on purpose? A console `git status` that disagrees with sync's view would itself be a false diagnosis.
- `wikiSubdir=logseq`: `wikiSubdirFilteredChangedPaths(repo, config)` is where merged paths are filtered (`AndroidGitRepository.kt` doMerge). Sync's own `reloadFiles` only reloads those. A remote that moved files outside `logseq/` is invisible by design; verify the test repo has files both inside and outside the subdir, and that stored subdir has no trailing slash/leading `./` (`stageWikiSubdir` appends `/`).
- index.lock: `deleteLockFileIfStaleForRetry` runs only on retry (`beforeRetry`), and `removeStaleLockFile` is on the interface. A console `git` command that runs `merge`/`checkout` concurrently with the scheduled sync can create or hit `index.lock`. Console git mutations must take the same lock sync uses (`GitWriteLockNaming.kt`, `GitSyncBusyCounter`, `EditLock`) — otherwise they race the background WorkManager sync. Read-only console git commands (status/log/refs/ls-remote) are safe but status takes the index lock briefly in real git; JGit does not, so fine.
- Detached HEAD: interface has `hasDetachedHead`. If HEAD is detached, `merge` merges into a detached commit and the branch never advances — another false-green. The fix's post-merge check should assert `HEAD` is on a branch.
- Config migration of `remote_branch`: do not rewrite stored values blindly on startup (would hit the network at DB-open time and on every device). Plan: on the first sync after upgrade, if `exactRef(refs/remotes/<remote>/<branch>)` is null after fetch, run symref discovery, and if exactly one candidate exists, surface a "Switch to `master`?" prompt (requirements already say confirm via UI). Persist through `SqlDelightGitConfigRepository` (`:62`), which presumably routes through the write actor; re-read after the write (memory rule: read mutations back). No schema change needed, so `MigrationRunner` is not touched. Note `WorkManagerSyncScheduler.kt:230` builds its own `GitConfig` from the row, so background sync sees the fix only after the row is rewritten — test that path, not just the foreground one.
- False-green states to assert against (each should be a test): (a) unresolved ref, (b) local ahead only (should not show MergeAvailable), (c) diverged but fetch ok, (d) empty remote, (e) detached HEAD, (f) `Success` with `remoteCommitsMerged=0` when the remote tip != local tip after merge. Add a post-sync invariant: after successful sync, `remoteTip` is an ancestor of `HEAD`; otherwise return Error. Also note `GitSyncService.kt:238` returns `Success(0,0,…)` early on some branch; check what condition that is so it cannot mask the same bug.

## 3. Console: raw SQL

- Existing assets (VERIFIED): `DriverFactory.createReadDriver` exists (null on JVM/iOS/WASM, separate read connection on Android) and `SqliteStatementAnalyzer.leadingKeywords` (`db/SqliteStatementAnalyzer.kt`) is a comment-stripping tokenizer, but it stops at `;` so it only classifies the first statement. It cannot by itself prove single-statement.
- Do not trust a keyword-prefix guard for "SELECT only". Pitfalls (INFERRED from SQLite semantics): multiple statements (`SELECT 1; DROP TABLE blocks`) — JDBC `executeQuery` runs only the first on sqlite-jdbc, Android `rawQuery` also compiles one statement and rejects trailing text, but SQLDelight's `driver.execute`/`executeQuery` paths vary; a CTE can wrap a write (`WITH x AS (…) DELETE …`, `WITH … INSERT`); `SELECT load_extension(...)` (disabled by default, keep it disabled); `PRAGMA` with side effects (`PRAGMA writable_schema=1`, `journal_mode`, `foreign_keys`); `ATTACH DATABASE` creates files; `VACUUM INTO 'path'` writes a file; `SELECT` calling a user function with side effects (none registered here, but FTS5 `INSERT INTO blocks_fts(blocks_fts) VALUES('rebuild')` is an INSERT so is blocked as a write); `EXPLAIN` of a write is harmless.
- Stronger enforcement than parsing: run read-only queries on a connection opened `PRAGMA query_only=ON` (SQLite rejects every write at prepare/step time, including inside CTEs), or use `sqlite3_stmt_readonly` semantics (Android: `SQLiteStatement`/`SQLiteDatabase.isReadOnly`; JVM: sqlite-jdbc `Connection.setReadOnly(true)` sets `SQLITE_OPEN_READONLY` only at open). Practical plan: parse to split into exactly one statement (tokenizer that honors quotes/comments/`;`), classify, then ALSO set `query_only` on a dedicated console connection. Keep the allowlist of PRAGMAs read-only (`table_info`, `index_list`, `foreign_key_list`, `page_count`, `integrity_check`, `compile_options`, `database_list`). Deny `ATTACH`, `DETACH`, `VACUUM`, `load_extension`, and writable PRAGMAs in both read and write modes.
- On JVM the write driver is a `PooledJdbcSqliteDriver` with 8 connections, so a per-connection `PRAGMA query_only=ON` sticks to a pooled connection and leaks into later app queries (nasty: later app writes fail "attempt to write a readonly database"). Use a separate, console-owned connection, or set it and reset it in `finally` on the same connection. UNVERIFIED how the pool exposes a single connection — spike.
- Row cap: SQLDelight `executeQuery` returns a cursor; wrap with `LIMIT`-free reading: iterate `cursor.next()` up to cap+1 then close. Do not append `LIMIT` textually (breaks on `;`, comments, and compound selects). Wrap as `SELECT * FROM (<stmt>) LIMIT 501` only after the single-statement check. Large BLOB/TEXT cells (block content, up to MB) must be truncated per cell (e.g. 2 KB) as well as per row, or 500 rows OOM Compose. A `SELECT` full-scan on `blocks` (graph is 9.4k pages) can run seconds and hold the DB; cancel via `Job` does not interrupt SQLite — use `sqlite3_interrupt` (Android `SQLiteDatabase.cancel` via `CancellationSignal`; JDBC `Statement.cancel()`) wired to coroutine cancellation, and set a statement timeout.
- Raw SQL writes (the owner chose to allow them). Pitfalls, all grounded in this repo:
  - CLAUDE.md forbids direct mutation outside `DatabaseWriteActor`/`@DirectSqlWrite`. Route through `WriteRequest.Execute` (`DatabaseWriteActor.kt:148`, handler `processExecute:369`) so writes serialize with app writes and `blockInvalidations` fires. `processExecute` emits the wildcard invalidation AFTER `op()` (the ordering bug fixed earlier); do not bypass it by running on a side connection, or open UI pages stay stale. But note it emits the invalidation even if `op` returns Left — harmless.
  - Because the actor only takes `suspend () -> Either<DomainError, Unit>`, the raw statement needs a typed wrapper in the actor or a `@DirectSqlWrite` forwarding stub on `RestrictedDatabaseQueries` (rule: new write queries get a stub). A generic `execute(sql)` stub is a deliberate hole in the gate; keep it `internal`, annotate `@DirectSqlWrite`, and gate behind the developer-mode flag at the call site. Add it to whatever test enforces the write gating so the exception is explicit.
  - FTS triggers (`SteleDatabase.sq:130-158`): `blocks_ai/ad/au`, `pages_ai/ad/au` keep `blocks_fts`/`pages_fts` in sync only for `INSERT`, `DELETE`, `UPDATE OF content` / `UPDATE OF name`. A raw write that changes `blocks.content` is fine; `INSERT OR REPLACE` fires the delete trigger only if `recursive_triggers` is on (SQLite default OFF), so REPLACE can leave stale FTS rows. Writing to `*_fts` directly, or `DROP`/`ALTER` of a trigger or table, desyncs search. Add a console post-write hint ("run `diag` / rebuild FTS") or deny DDL and writes to `*_fts*` tables.
  - Markdown on disk is the source of truth; a DB-only edit will be overwritten or conflict on the next file reload (`GraphLoader` external-change path), and DB-only rows are exactly the "ghost journal" problem in Open Question 4. Console writes need a loud notice that the file on disk is not changed. Do not offer a "fix by SQL" workflow for content.
  - `MigrationRunner` and `MigrationRunnerSchemaSyncTest`: DDL from the console (`CREATE TABLE`) would bypass the runner; deny DDL, or at least `CREATE TABLE`/`DROP`/`ALTER`.
  - Pre-write backup: copying a live WAL database file is unsafe (copy `-wal` and `-shm` too, or use `VACUUM INTO`, which itself is a write-path file creation, or the SQLite online backup API). `VACUUM INTO` on a large DB can take seconds and doubles disk use; on Android check free space first. Do the backup through the same safe path regardless of the "no VACUUM" deny list, as an internal operation.
  - Repository-level invariants are bypassed: uuid uniqueness (`INSERT OR REPLACE` deleting another page's block, per cross-graph notes), cross-graph `src-id`, `pages` backlink counts (cf. `stelekit_pages_backlink_count_migration_crash` memory). Writes must run inside the actor's transaction and surface `DomainError.DatabaseError.WriteFailed`, never raw exceptions.
  - Confirm gate: show affected row estimate (`changes()` after execute, run inside a transaction and offer rollback: execute, report `changes()`, then commit only on second confirm) rather than a blind y/N.

## 4. Console: shell / process exec

- Android: `Runtime.exec`/`ProcessBuilder` runs as the app uid with the system `PATH`, with no `/bin/sh` guarantee in the sandbox's view and with SELinux limits on `/data/data`. Scoped storage hides SAF trees from any child process. Recommendation: ship an in-process interpreter only (the `fs`/`sql`/`git` families) and treat `sh` as desktop-only (`expect`/`actual` or a capability flag). If `Runtime.exec` is added on Android, restrict to a tiny allowlist (`ls`, `df`, `ps`, `getprop`, `logcat -d -t N`) with no shell metacharacter parsing (argv array, never `sh -c`).
- Desktop: `sh -c <user string>` runs with full user privileges. Output pipes: read stdout and stderr on separate coroutines or merge with `redirectErrorStream(true)`, or a full stderr buffer deadlocks the process. Enforce a timeout and kill the process tree (`ProcessHandle.descendants()`) on cancel (`destroyForcibly` kills only the parent). Environment inheritance leaks secrets: build a clean env instead of inheriting (`GITHUB_TOKEN`, `SSH_AUTH_SOCK`, 1Password vars may be present on the desktop). Working directory: default to graph root, not `$HOME`.
- Web (wasmJs): no process or git; the command registry must be capability-filtered, and commonMain must not import `java.*`. Reflect that via an `expect` `ShellCapability`.

## 5. Credential leakage

- VERIFIED sources of secrets: URLs with userinfo (`https://user:token@host/…`) in `GitConfig.remoteUrl`/`.git/config`; the diagnostics Git section (uncommitted, `GraphDiagnostics.kt`) already prints config and ls-remote output — check `remoteUrl` is stripped there (requirements say it is; add a test that feeds `https://u:ghp_x@h/r` and greps the whole export). `GitCredentialConnectionStore`/`VaultCredentialStore` hold tokens; SSH key paths are not secrets but key contents are.
- Console channels that leak: `git remote -v`, `fs cat .git/config` (raw `url =` with token — a path-based redaction on `.git/config` is not enough; redact by pattern on all output), `sql SELECT * FROM git_config`/credential tables (check schema for any token columns; `SteleDatabase.sq:~960-995` git config table; credentials live in the vault, but `GitCredentialConnection` rows may hold token hints), `settings` dump, `logs` (log lines from JGit exceptions embed URLs; JGit `TransportException` messages include the URI), exception stack traces from `HttpTransport`, shell `env`/`printenv`, and `fs cat` of any file under app dir (shared prefs, vault files, `~/.ssh`).
- Mitigation: one `Redactor` applied at the single output sink (the console's line emitter), not per command, covering: URL userinfo (`://[^/@\s]+@`), `Authorization:`/`Bearer`/`token=`/`ghp_`/`github_pat_`/`gho_`/`glpat-`/`AKIA…` patterns, PEM blocks (`-----BEGIN … PRIVATE KEY-----` through END), and every secret value currently held in the credential store (exact-string match, the strongest guard). Deny-list `fs` paths (vault dir, `.ssh`, `*.keystore`, shared_prefs, credential DB files) rather than relying on redaction. Apply the same redactor to the log file lines for console command arguments (`sql` statements may contain secrets), to export/share output, and to the diagnostics report. Test: a property test generating random secret-shaped tokens embedded in arbitrary text and asserting none survive the sink (kotest-property is available in commonTest).
- Export: share sheet or file in app-private cache must not land in a world-readable dir; on Android use `FileProvider` with a scoped path, delete after share. Console history is in-memory only by default (requirements); if persisted, redact first.

## 6. Android process-kill hazards in console coroutines

- VERIFIED rule (CLAUDE.md): an uncaught `Throwable` (notably `OutOfMemoryError`) in any coroutine kills the Android process. The console will run user-controlled workloads (large `SELECT`, `fs cat` of a big file, `git log` on 9k commits), so it is a prime OOM source.
- Mitigations: console gets its own long-lived scope owned by a plain class (not `rememberCoroutineScope`; CLAUDE.md forbids passing it into `remember{}` objects) with `SupervisorJob() + CoroutineExceptionHandler` that converts Throwables into a console error line; each command runs in a `try { … } catch (e: CancellationException) { throw e } catch (t: Throwable) { emit error }` wrapper. Catch `OutOfMemoryError` but do not allocate in the handler (preformatted message). Bound memory before it happens: stream lines, never materialize a full `String` for a large file; `fs cat` reads at most N bytes with a "truncated" marker; `git log` is capped (`maxCount` on the interface); no `readText()` on user paths.
- Cancellation: coroutine cancel is cooperative. JGit calls need the ProgressMonitor `isCancelled` hook (the repo already does this in `clone`, `JvmGitRepository.kt:121`) and fetch/ls-remote need the same; blocking `Process.waitFor` and SQLite steps need explicit interrupt (above). Use `runInterruptible` or a watcher coroutine for blocking calls. A "cancel" button that only cancels the Job while the thread keeps running will leave the command holding the DB read connection or `index.lock`.
- Dispatchers: DB reads on `PlatformDispatcher.DB`, files/processes/git on `PlatformDispatcher.IO` (CLAUDE.md matrix), never `Dispatchers.Main`; shell and file output parsing must not run on the UI thread.

## 7. Compose performance with large output

- Render scrollback as a `LazyColumn` of lines with stable keys (monotonic line id), not one giant `Text` or `TextField` (a single multi-MB `String` in `Text` makes measure/layout O(n) per frame and can ANR). Cap the in-memory scrollback (ring buffer, e.g. 5,000 lines or 2 MB), drop oldest with a visible "N lines dropped" marker; the full output goes to the export file/streaming sink rather than the UI buffer.
- Batch emission: collect output from the command into a `Channel`/`SharedFlow` and update UI state at a frame-ish rate (e.g. `conflate` + `sample(50ms)`); emitting a state update per line from a 500-row result recomposes hundreds of times. Do not use `mutableStateListOf` with per-line `add` from a background thread; publish immutable list snapshots (or a `PersistentList`) via `StateFlow`.
- Very long single lines (JSON blobs, block content) break `LazyColumn` item measurement and Skia text layout: hard-wrap or truncate per line at ~2,000 chars with "…(+N chars)" and offer the full value via copy.
- Selection/copy: `SelectionContainer` around a `LazyColumn` of 5,000 lines is expensive and lazy items outside the viewport are not selectable. Provide explicit "copy output / copy last result / copy line" actions instead of relying on text selection. Use `BasicTextField` only for the single-line input, not for output.
- Tables for SQL results: monospace pre-formatted columns computed on the IO dispatcher (column widths from the capped rows), not per-recomposition.
- Testing: a Compose test in `androidUnitTest` (Robolectric, headless) per CLAUDE.md "Testing best practices", asserting the 5,001st line evicts the first and the list composes without a display. Prefer testing the buffer/redactor/parser logic as pure `commonTest` code.

## 8. Other cross-cutting pitfalls

- Developer-mode gate must be enforced in the command dispatcher, not only by hiding the nav entry (deep links, `Settings` toggles, restored back stack).
- Audit logging: log command name, duration, counts at INFO, SQL writes at WARN with the statement, but run the statement through the redactor first (a `UPDATE settings SET token='…'` is a secret in the log).
- Web build: any new commonMain command code must avoid `java.io`/`System`; put process/exec/fs behind `expect`/`actual` or capability interfaces, and note detekt does not scan `wasmJsMain`/`wasmJsTest` (memory), so wasm compile of new commonMain code must be checked by the wasm compile step.
- `fs` family: path traversal. Canonicalize and verify the path is under allowed roots (graph roots, app dir) before access; reject symlinks that escape the root. On Android SAF, graph roots are `content://` URIs, not `File` paths; `fs` must go through the existing `FileSystem` abstraction (`StubFileSystem` exists for tests), not `java.io.File`.
- Shared repo hygiene: the working tree has uncommitted diagnostics changes and an untracked `GitRefDiagnostics.kt`; the first task should commit exactly those files by name (CLAUDE.md git-hygiene rule), and `benchmarks/history/*.json` is unrelated and must not be swept in.
