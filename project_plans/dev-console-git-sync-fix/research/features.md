# Feature landscape: dev console + git-sync fix

Labels: VERIFIED = opened in this repo this session; PRIOR-ART = from general knowledge of the named tools (no web lookup done, treat as INFERRED); INFERRED = reasoning.

## 1. Comparable in-app consoles / inspectors (PRIOR-ART)

| Tool | What matters | Take-away for SteleKit |
|---|---|---|
| Chrome DevTools console | History (up/down), autocomplete, live expression, copy-as, output grouping, `$_` last result, filter by level | History + scrollback + copy are table stakes; command-name tab-completion is high value on a phone keyboard. |
| Flipper (Meta, now deprecated) | Plugin-per-concern, desktop-side UI; DB browser, logs, network, shared prefs | Validates "registry of small probes"; its decline shows a separate desktop host is a maintenance burden. In-process is right given no adb. |
| Android Studio Database Inspector | Run SQL against live DB, results as table, live-updating queries, edit cells | Needs debuggable build + adb: the stated gap. Copy the UX: table output, row cap, queries saved. |
| Stetho | Chrome DevTools bridge over a socket; `dumpapp` plugins (CLI-style commands: `prefs`, `sqlite`) | `dumpapp` command-plugin shape is the closest model to the registry design. Socket exposure is the rejected part. |
| Obsidian dev console | Chromium console, `app.vault`, `app.metadataCache` global objects; users probe live state in JS | Strongest ergonomic precedent: owner wants "ask the running instance". We have no JS eval, so named commands (`graph`, `db`, `git`) stand in for the global objects. |
| Logseq dev tools | Electron DevTools + `logseq.api`/`logseq.db` datascript queries from console | Same pattern: query the DB + read files. Confirms `sql` + `fs` + `graph` families cover the real use cases. |

Ergonomics that matter, in priority order: (1) cancellable, streaming output; (2) row/line caps with explicit "truncated" marker; (3) history and tab-completion; (4) copy/export of last output or whole session; (5) read-first defaults with write behind confirm; (6) `help <cmd>` generated from the registry; (7) `--json` or table output toggle (low priority).

Command-set recommendation: ship the families already in requirements; add `help`, `history`, `clear`, `export`, `diag journals-diff` (disk-vs-DB, the owner's second question) and `git doctor` (one-shot: configured ref, resolved?, remote heads, symref HEAD, ahead/behind, shallow, suggestion). `git doctor` is the highest-value command for the current bug.

## 2. Existing SteleKit pieces to reuse (VERIFIED unless noted)

- **GitSyncService** `commonMain/.../git/GitSyncService.kt:47`: merge result goes to `graphLoader.reloadFiles(...)` at line 359 wrapped in `beginGitMerge/endGitMerge` (watcher suppression). ## 3. Git-sync bug: edge cases

### 3.1 Confirmed code facts
- `AndroidGitRepository.doFetch` (`androidMain/.../AndroidGitRepository.kt:196-217`): after `fetch`, `repo.resolve("origin/main")`; `hasChanges = remoteRef != null && remoteRef != headBefore`. Null ref => `hasChanges=false`, `FetchResult(false,0)`, no log. Jvm twin at `jvmMain/.../JvmGitRepository.kt:183-193`. VERIFIED.
- `doMerge` resolves the same `remoteName/remoteBranch` again at `AndroidGitRepository.kt:275`, so merge shares the failure mode (a null ref there needs its own check). VERIFIED line, behavior INFERRED.
- Note `repo.resolve("origin/master")` works by JGit short-name lookup (`refs/remotes/origin/master`); the failure is only the configured name being wrong, not the resolve syntax. INFERRED.
- Fetch uses `setRemote(...)` with no explicit refspec => default `+refs/heads/*:refs/remotes/origin/*`, unless the clone was single-branch (see shallow).
- `hasRemoteDivergedSinceShallowClone` (`jvmCommonMain/.../GitOperationSupport.kt:433`) already uses `refs/heads/${remoteBranch}` and treats null as "diverged" (conservative), so it does not mask the bug; it returns true -> an unshallow fetch may run each time (cost, not correctness). VERIFIED.

### 3.2 Edge-case checklist for the fix and tests (each should have a temp-repo JGit test)

1. **Unresolved remote ref** (configured `main`, remote only `master`): must return `GitError` with remote name, configured branch, available `refs/remotes/<remote>/*` and ls-remote heads. Regression test must fail on current code.
2. **Default branch rename** (remote renamed master->main later, or reverse): the remote-tracking ref `origin/master` goes stale locally; `fetch` without `--prune` keeps it, so a stale ref can resolve and give a false "no changes". Fix should set `setRemoveDeletedRefs(true)` or check the ls-remote head list, not only local resolve. Also decide behavior when both exist.
3. **Detecting actual default branch**: JGit `lsRemote()` returns the `HEAD` ref; its symref target is only available via `Ref.getTarget()` when the server advertises `symref` capability (GitHub does; some dumb/HTTP servers do not). Fallback: match HEAD's objectId against heads. Mark ambiguity (several heads same oid) as "ask user". INFERRED from JGit API; verify in a spike.
4. **Local branch vs remote branch name**: clone path comment at `AndroidGitRepository.kt:73`/`JvmGitRepository.kt:66` says JGit default initial branch is `main`. A clone of `master` checks out `master`; HEAD is `master` while config says `main`. Check merge target uses current local branch and push (`doPush`, uses `remoteBranch` per grep) pushes `HEAD:refs/heads/<remoteBranch>`; with the wrong name push could create a stray `main` branch on the remote. VERIFY `doPush` before shipping; this is a data-divergence risk.
5. **Shallow clone**: (a) single-branch shallow clones only fetch one branch's refspec, so a changed branch name cannot be resolved without widening the refspec; (b) `countRemoteCommitsBestEffort` on a shallow history may undercount or throw, giving `remoteCommitsMerged=0` even when merge happened (answers Open Q2 partly: count is best-effort, treat `remoteCommitsMerged` as unreliable, derive from HEAD before/after instead); (c) merge-base missing after fetch with insufficient depth -> JGit "no merge base" -> must surface, not swallow; (d) `CloneDepthState` interaction with `hasRemoteDivergedSinceShallowClone` above.
6. **wikiSubdir filtering**: `wikiRoot = repoRoot/wikiSubdir` (`GitConfig.kt:~24`). `status`/`stage` are path-scoped to the subdir (`buildGitStatus`, `stageWikiSubdir`), but fetch/merge are repo-wide. Check that `mergeResult.changedFiles` (line 359 feed to `reloadFiles`) are repo-relative vs absolute, and that files outside `wikiSubdir` are filtered or at least harmless. If paths are repo-relative but loader expects wikiRoot-relative or absolute, merged journals would be silently ignored; this is an independent candidate cause of "merged but not shown". Also `GraphManager` derives `wikiSubdir` from detection if config lacks it (`GraphManager.kt:466,742`) - config and detection can disagree.
7. **SAF shadow worktree** (`AndroidGitShadowSupport`, `AndroidGitRepositoryShadow.kt:27`): only for `saf://` roots without a direct path; AppOwned/direct paths skip it. For shadow graphs the merge lands in the shadow tree and must be copied back to SAF (`syncFromSafRoot` / post-merge reconciliation comments around line 386-390 of GitSyncService/Android repo). The owner's cloned graph is app-owned or direct (INFERRED: it is "a cloned repo"), so shadow is likely not involved; the console `git doctor` should print which path mode is in use so this is checkable. The two SAF `personal-wiki` registry entries are out of scope but should be labelled in `graph registry`.
8. **Detached HEAD**: `headBefore` may be a commit with no branch; merge into detached HEAD succeeds as fast-forward of nothing and push of `HEAD` goes nowhere useful. `git doctor` should flag it; fix may need to re-attach to the tracking branch (confirm via UI, never silent).
9. **DB-only journal rows never written to disk** (Open Q4): rows for 2026-10-07/09/10 exist in DB but not on disk. Causes to check: journal created via UI but file write skipped/failed (write-behind flush, `GraphWriter`), created in a different graph then registry-switched, or a path/subdir mismatch (writes to repoRoot/journals vs repoRoot/logseq/journals, see item 6). If it is a write-path bug, a later `git commit/push` also cannot publish them. Console needs `diag journals-diff` listing both directions (disk-only, DB-only) with a one-command "write DB-only to disk" repair (through `GraphWriter`, not raw fs, to respect watcher suppression).
10. **Index backlog**: "9414 pages awaiting index" + 35 DB journals vs 1578 on disk. `indexRemainingPages` drains in 100-row batches (CLAUDE.md); logs of `batchDeleteBlocks` 5.2s and `processChunk` 9.5s suggest the drain is slow, not necessarily stuck. Need a progress probe (`graph index-status`: `countUnloadedPages`, attempted set size, last batch time) before concluding. Ordering consideration: index journals first (newest-first) so the owner's primary use case is satisfied early. INFERRED.
11. **Auth/rate-limit and offline**: fetch failures already route via retry (`RetryExhausted`); ensure the new "unresolved ref" error is NOT retried (deterministic) so it does not burn the rate-limit budget.
12. **Migration of stored config**: existing rows keep `remote_branch='main'`. Migration = on next successful ls-remote, if configured branch absent and exactly one candidate default exists, propose correction via UI (requirements: confirmed, not silent). Add MigrationRunner entry only if a new column/table is added; a value correction needs no schema change.

### 3.3 Decision branches driven by the first device evidence
- configured=main, remote has only master => hypothesis confirmed: fix 1+3+12, no more investigation needed.
- configured=master and resolves => hypothesis wrong; look at 5(b), 6, 7, then the loader (reloadFiles got files but DB lacks them -> 10).
- ref resolves but `behind>0` after sync => merge not running (check `hasChanges` gating, `MergeAvailable` state needing user confirmation vs auto-merge on background path).

## 4. Console-specific risk notes
- Shell on Android: recommend in-process interpreter for all families, with `sh` as optional `Runtime.exec` (app uid, toybox PATH) gated by second confirm; no pty. Answers Open Q6 as "both, interpreter first". PRIOR-ART/INFERRED.
- Redaction: reuse the URL userinfo stripping already needed in the Git diagnostics; add a central `Redactor` applied to output, history and logs (tokens, `Authorization`, passphrase keys named in `GitConfig`: `httpsTokenKey`, `oauthTokenKey`, `sshKeyPassphraseKey`).
- Console coroutines need a `CoroutineExceptionHandler` scope owned by a console class (CLAUDE.md rules), not `rememberCoroutineScope`.
- Web: git/sh/fs families not registered; registry should filter by platform capability so `help` shows only available commands.
- Pre-write DB backup: SQLite file copy while the pool is open needs a checkpoint (`PRAGMA wal_checkpoint(TRUNCATE)`) or `VACUUM INTO`; unresolved, spike needed.
