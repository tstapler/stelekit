Story 6.2 (plan.md:772-777) carries all three requested ACs: zero HTTP and skipped-not-failed for NotAsked/Revoked/missing key; consent re-read per asset so mid-drain revoke stops calls and cancels the in-flight request; graph A `Granted` does not authorize graph B. `AssetPipelineService` does the per-asset gate check next to `EgressLedger` (plan.md:85, 188, 783, Task 6.2c). Structural audit `CloudStructuralAuditTest` covers plugin construction through the factory only (plan.md:801). Stack-level `CloudStackEntryPointTest` uses a MockEngine through `WiredAppFixture`.
  - **Residual concern (CONCERNS, not BLOCKED): the token is not forge-proof by type alone.** The plan says the `GrantedConsent` constructor is `internal` "to `CloudConsentGate`" (plan.md:62, 773; ADR-005:16). In Kotlin, `internal` means module-wide (all of `kmp` commonMain), not gate-scoped, so any class in the module, including a future plugin or a test, can call `GrantedConsent(...)`. The plan's claim "code that does not hold a token cannot compile a call" is true, but "cannot be forged outside the gate" holds only because of the source audit that asserts `GrantedConsent(` appears only in the gate (plan.md:773). That audit is a test, not a compile-time guarantee, and no task or Files list names the audit test explicitly (candidates: `CloudConsentEnforcementTest` or `CloudStructuralAuditTest`). Recommended tightening (plan.md edit, owner's call): give `GrantedConsent` a `private constructor` and make `CloudConsentGate` its only constructing scope (nested factory or companion `internal fun mint` called only from the gate file), and name the audit test in Task 6.2c's file list. Also state that tests use a test-only gate fake rather than constructing a token directly, otherwise the audit needs a test-source exemption.
  - Note: this re-review verified plan/ADR text and that referenced files (`AssetPipelineService.kt`, `CloudClaudePlugin.kt`, `PluginRegistry.kt` under `asset/pipeline/`) exist; `CloudConsentGate`, `GrantedConsent`, and `PeriodicSyncDriver` do not yet exist in source (grep returned no hits), which is expected for a plan awaiting implementation.

## Blockers

- [ ] **Story 2.1 / Task 2.1b / Story 2.3 / Tech Debt Disposition row `GitSyncService.kt`** — The plan chooses "Extend as-is" for a hotspot (VERIFIED: 786 lines, 12 commits in the last 3 months) and then adds five scheduling behaviors inside it: per-tick Throwable guard, `SyncTick` logging, busy skip, wall-clock last-success, immediate first tick. Story 2.3 then requires state that no task owns: "pause after 3 consecutive failed ticks", "Paused after 3 failures - tap to fix", and "Last synced 3 min ago · next in 12 min". Task 2.3a is UI-only and Task 2.1b does not mention pause or countdown state, so that state lands in `GitSyncService` by default. This deepens the God-object violation the table claims to avoid (Lens 4, item 12), and it adds a scheduling policy (pause/backoff) to the class dev ADR-004 says must not gain scheduling branches. Remediation: add a refactor-first task before 2.1a that extracts a `PeriodicSyncDriver` collaborator (own file, injected `tick: suspend () -> TickOutcome`, clock, and CEH-guarded scope). It owns the interval loop, busy skip, first-tick-after-load, consecutive-failure pause, and an exposed `StateFlow<ScheduledSyncStatus>` (lastSuccessAtMs, nextAtMs, paused). `GitSyncService.startPeriodicSync` becomes a thin delegation, and Story 2.3 reads the StateFlow. Change the disposition row to "Isolate via seam" and name the new task, so `runScheduledSync` in Story 2.4 swaps only the injected lambda.

- [ ] **Story 5.2 / 6.2 / 6.3 / ADR-005 (`PlatformCaps.cloud`, `defaultAssetPlugins`)** — The consent gate for confidential-image egress has no enforcement point at the call. Three problems:
  1. `PlatformCaps` is built once at process start (`SteleKitApplication`, `desktop/Main.kt`), but consent, the API key, and the switch are runtime, per-graph user state. The plan does not say who sets `caps.cloud` non-null, or how the plugin list changes when the user grants or revokes consent mid-session.
  2. No acceptance criterion says the pipeline refuses to invoke `CloudClaudePlugin` when `CloudConsent` is `NotAsked` or `Revoked` while the plugin is present. Story 6.2 only tests the dialog and revoke-drops-queue. Risk Control says gates are "enforced in the service entry point"; for the one third-party egress path that is not specified.
  3. The structural test "cloud plugin constructed only in `defaultAssetPlugins`" cannot hold together with runtime consent unless the plugin is constructed either always (then only the consent check protects privacy) or on the fly.
  Remediation: parse consent at the boundary. `CloudClaudePlugin` takes a `CloudConsentGate` (`suspend fun grant(graphId): GrantedConsent?`) and its `processAsset` requires the returned `GrantedConsent` token. `PlatformCaps.cloud` becomes a factory lambda, not a config. Add ACs: (a) `NotAsked`/`Revoked`/missing key means zero HTTP calls and the asset is skipped, not failed; (b) consent is re-read per asset, so revoke takes effect mid-drain; (c) `Granted` for graph A does not authorize graph B. Move the consent check into `AssetPipelineService`, next to `EgressLedger`, so it cannot be bypassed by a new plugin.

## Concerns

- [ ] **Task 2.2a / Files for 2.2, 5.2** — The plan names `commonMain/.../ui/StelekitAppPlatformIntegrations.kt`, which does not exist (VERIFIED). `StelekitAppPlatformIntegrations` is a `data class` inside `ui/StelekitAppDependencies.kt` (300 lines), and `StelekitAppDeps.platformIntegrations` defaults to `StelekitAppPlatformIntegrations()` (line 270). A field with no default (`backgroundSyncSchedulerFactory`, `platformCaps`) breaks that default and every construction site (7 call sites by grep) including tests, wasm, and any iOS host. The compile-error-on-omission intent is sound, but it needs an explicit sentinel such as `BackgroundSyncSchedulerFactory.None` / `PlatformCaps.NONE` that each host must name, with the default removed from `StelekitAppDeps`. Fix the file path and list the call sites in the task.

- [ ] **Story 0.4 / Task 0.4a vs Unit U0** — U0 ships Story 0.4a alone, but 0.4a says the test "lands red in the same PR as the Story 5.1 fix" and `@Ignore` is forbidden. U0 and U8 contradict each other: either U0 merges a red test onto `main` or the test sits unmerged. Remediation: move 0.4a into U8 with 5.1a (red commit first, fix commit second inside one PR), or have U0 carry the test plus the minimal fix.

- [ ] **Story 1.1 / Task 1.1a (`WiringCompletenessTest`)** — The primary enforcement mechanism reads composition-root sources, including `androidApp/.../MainActivity.kt` and `SteleKitApplication.kt`, from a `jvmTest` with a working-directory file walk (the `CaptureWriterSourceAuditTest` precedent resolves `src/...` or `kmp/src/...`). `androidApp/` is outside `kmp/`, and under Bazel (canonical) the sandbox needs the sources bundled as classpath resources. `kmp/src/jvmTest/kotlin/BUILD.bazel` already does this for `graph_content_wiring_test_sources`. Add a task to extend that genrule/filegroup to the root set (incl. `androidApp`) and make the test fail with "root not found" rather than pass with an empty root set. Otherwise the gate silently covers only `kmp/` under one runner.

- [ ] **Story 5.1 (`AssetPipelineService`) vs hard rule "no write outside `DatabaseWriteActor`"** — VERIFIED: `processAsset(asset, writeActor: DatabaseWriteActor?)` falls back to direct repository writes when the actor is null (`AssetPipelineService.kt:77-93`, with a `DirectRepositoryWrite` import). Wiring this service into a real root while the nullable bypass remains breaks the rule the plan restates in Risk Control. Add to Task 5.1b: make the actor a non-null constructor dependency and delete the fallback; tests use a real actor over in-memory repos.

- [ ] **Story 5.5 / Register row 20 (`PluginHost`, `Plugin`)** — The plan keeps two enable/disable registries: `PluginRegistry` for `AssetPipelinePlugin` and `PluginHost` for the Logseq-style `Plugin` (with `onEnable/onDisable` lifecycle, VERIFIED in `platform/PluginSystem.kt`), bridged by "register one `Plugin` per enabled pipeline plugin". That is an adapter whose only job is to feed a status-bar count, and it creates two sources of truth for "enabled". `research/architecture.md` §6 recommended deleting `PluginHost` unless an in-tree plugin exists. Recommendation: make `PluginRegistry` (or the new enabled-state model) the single source, have the status bar read its count, and delete `PluginHost`/`Plugin` along with `JsPluginBridge`, or record why two registries are justified.

- [ ] **Task 3.2b (Android read connection)** — VERIFIED: `DriverFactory.android.kt` `createReadDriver` returns a second normal WAL `AndroidSqliteDriver` (not read-only), and the JVM `createReadDriver` returns null. The plan's "Android `createReadDriver` / `OPEN_READONLY`" can be read as reusing it, which would not be engine-enforced and would contradict ADR-006 "no classifier fallback". State explicitly that the console opens its own `SQLiteDatabase.openDatabase(..., OPEN_READONLY)` handle (the same API `GitShadowWorktree.kt:465` already uses) and that `createReadDriver` is not reused. The bypass suite on the emulator then verifies the property.

- [ ] **Story 3.4 (restore) lock discipline** — CLAUDE.md requires never awaiting `GraphManager.awaitPendingMigration()` while holding a `GraphWriteLock`, and never nesting locks. The swap sequence (drain actor, close reader, rename DB files, `removeGraph`/`addGraph`, `graph reload`) is not tied to `GraphWriteLock`, `readyGraph`, or the router's in-flight writers. Add an AC and a stress test modeled on `GraphManagerSwitchLockStressTest` / `TargetWriterRouterInFlightSwitchTest`: a concurrent share or copy to the restoring graph neither deadlocks nor writes to a half-swapped DB.

- [ ] **Story 2.4 / metric 4** — Step 1 ships a fetch-only tick, which does not "pull remote commits" as success metric 4 requires. The plan admits metric 4 is met only at Step 2, which is blocked on unshipped dev-plan units outside this project. The status line "Ready for implementation" should say that metric 4 is not closable by this plan alone, or fund PR-A1/A2 here. As written, the requirements traceability row for M4 is overstated.

- [ ] **Tech Debt Disposition coverage** — Planned edits to `ui/ScreenRouter.kt` (510 lines; new `Screen.Console`, Drive route), `ui/AppState.kt` (293), `ui/components/SearchDialog.kt` (704; Assets section and Semantic toggle), `ui/StelekitAppDependencies.kt` (300), and `SettingsDialog.kt` (481) have no disposition rows. Churn is unmeasured in the research ("Churn figures are not re-measured here"). Add rows (likely "Isolate via seam": the Assets section as its own composable and `SearchSource`, routes registered in a table) and measure 90-day commits for them.

- [ ] **Epic 9 (conditional) Story 9.3** — "Chunks of at most 500 stored vectors with a running top-k" is bounded in memory but still O(all blocks) per keystroke-query on a 512 MB-heap phone with 9.5k pages. The CLAUDE.md pattern tolerates chunked scans for one-shots, not for interactive standing queries. Spike 9.1 should also record full-scan latency at graph scale, with an ANN or page-level pre-filter as the fallback if over budget.

- [ ] **Epic 12 / 11.3 gating** — T3 ratchet drop "warns only" and wave candidates come from stale data; acceptable, but confirm the nightly issue-filing job does not add to Bazel/CI memory (pitfalls E5) by running only against the cached Gradle artifacts.
