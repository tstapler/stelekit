# ADR-006: Console delivery: first slice, read-only default with guarded writes, cancel strategy, single redactor

**Status**: Accepted pending Spike 0.3a-e results (addendum below once run; merge gate for U4/U5/U6; amended by plan repair iterations 1 and 2) | **Date**: 2026-10-27 | Builds on `dev-console-git-sync-fix` ADR-001 and ADR-002

## Context
The dev plan's PR-C is unbuilt (no `console/` directory, no developer-mode flag). Owner decision 2026-10-27: first slice is read-only SQL plus guarded writes (ADR-002 confirm + automatic backup); read-only is the default mode. PR #397 (the `RepositorySet.sqlConsole` conflict) is merged.

## Decision (deltas only; the rest is the dev ADRs)
- **First slice**: dev plan Stories 4.1-4.6, 5.1 (`diag`), 5.4 (`sql` read), 5.5 (`sql` write, backup), 5.8, 6.1-6.4; restore (Task 5.5e) last. `git`, `fs`, `sh`, `graph` families and verbs that need PR-B stay in the dev plan.
- **`sql` is always read-only; `sql!` is the only write verb** (matches dev plan Story 5.5 and dev design UX-100; there is no Settings switch for writes). `ConsoleMode` is a sealed type derived per statement: `ReadOnly` is the default and the only mode of plain `sql`; `GuardedWrite` is entered for one statement by `sql!` after the modal confirm and a `ConsoleBackup`, then `ReadOnly` is restored. A write sent to plain `sql` returns the single string `Denied: plain sql is read-only. Use sql! for writes.` (mapped from the engine read-only error). Hard-deny list unchanged.
- **Merge gate and release exclusion (pre-mortem P1-1).** Spikes 0.3a-e are a merge gate for U4 and U5 and restore (U6); if Spike 0.3d shows neither interrupt nor abandon-and-close is safe on `requery`, Android ships without `sql!` in the first slice. The `sql!` write path and the restore command are compiled out of release builds (`ConsoleBuildFlags.WRITES_ENABLED`, Task 3.3e) until owner pass 12.1 succeeds on a COPY of the real DB; in such builds `help` lists `sql!` as `disabled: writes not enabled in this build`. Required tests: an emulator test of a concurrent `DatabaseWriteActor` write during a `VACUUM INTO` of a synthetic ~450 MB DB (Task 3.3f) and an FTS-consistency test for raw `INSERT OR REPLACE`/`UPDATE` on `blocks` that either rejects, or repairs FTS in the same transaction (Task 3.3g, pitfalls B4).
- **Bypass suite is an acceptance gate**: PRAGMA writable/query_only, ATTACH, VACUUM INTO, load_extension, CTE-wrapped writes, multi-statement, `RETURNING`, comment/case obfuscation, plus a generated-statement property test, on the JVM driver and the Android emulator.
- **Cancel and time cap**: `QueryDeadline` 10 s default, user Cancel; enforced by deadline checks in the cursor loop; if one `step` blocks, the console-owned connection is abandoned and closed (SQLite interrupt-on-close), then reopened lazily. Spike 0.3d records whether `Statement.cancel()` (xerial) or `CancellationSignal` (requery fork) is available so the fast path can be used.
- **One `Redactor`** consolidates the per-file scrubbers (12 production/test files matched on 2026-10-27) before the console depends on it; a source audit allows the secret-pattern literals in exactly one production file.
- **Developer category visibility** fix lands with the toggle (`SettingsDialog.kt:142`, `:229`).
- Web/iOS: `sql` listed disabled with a reason; no classifier-only fallback.
- **Scope of the no-classifier rule**: it applies to the READ guard only (read-only connection; the table-name/credential denial is never classifier-based). The `sql!` hard-deny check (`ConsoleMode.GuardedWrite`, dev ADR-002) is a statement classifier by design, applied only to `sql!` input; the verb routes writes, plain `sql` has no classifier, and the read-only engine connection rejects any write sent to it. The bypass suite is the acceptance gate.
- **The console owns its read connection.** It opens a new non-pooled `OPEN_READONLY` handle (JVM: `SQLiteConfig.setReadOnly(true)` JDBC connection; Android: `SQLiteDatabase.openDatabase(path, null, OPEN_READONLY)`, precedent `GitShadowWorktree.kt:465`, driver class chosen by Spike 0.3e). `DriverFactory.createReadDriver` is never reused: Android's (`DriverFactory.android.kt:174`) is a second read-write WAL driver and JVM/wasm/iOS return `null`. Abandon-and-close (Spike 0.3d) therefore closes only the console's handle and cannot disturb the app's pool.
- **"Credential tables unreadable" is replaced by what is provable.** A read-only connection cannot deny reads of specific tables, and a table-name classifier is bypassable (CTEs, subqueries, aliases, `SELECT * FROM (SELECT ...)`), which this ADR forbids. Spike 0.3e tests `sqlite3_set_authorizer` availability per driver (sqlite-jdbc, platform SQLite, `requery:sqlite-android:3.49.0`). If YES on a driver, column-level `SQLITE_DENY` on `git_config.{ssh_key_passphrase_key,https_token_key,oauth_token_key}` is installed on that driver's console handle and bypass-tested. If NO, the denial claim is dropped for that driver. Either way `CredentialColumnInventoryTest` fails when a credential-shaped column outside the committed list appears in `SteleDatabase.sq`.
- **Real exposure (verified from `SteleDatabase.sq:989-1005` and a grep for token/secret/password/api_key/credential columns)**: `git_config` is the only table with credential-shaped columns and they hold keystore **aliases** (`https_token_key`, `oauth_token_key`, `ssh_key_passphrase_key`), not secret values; secret values live in `CredentialStore`/`LlmCredentialStore`/`VaultCredentialStore`, never in `SteleDatabase`. The honest statement is therefore: aliases may be visible, secrets are not stored in the queried database, and all console output and CSV export pass through the single `Redactor`.
- **Backups are bounded for a 451 MB database**: require free space >= 1.2x the DB size before any write, show the backup size in the confirm modal, block the write if the backup fails or `integrity_check` is not `ok`, and keep the 2 newest backups by default (max 5) instead of 5.
- **Restore takes `GraphWriteLock(graph)`** for the swap, never nests another `GraphWriteLock`, never awaits `GraphManager.awaitPendingMigration()` while holding it, and is stress-tested against concurrent `TargetWriterRouter` writes (`DbRestoreLockStressTest`).

## Alternatives rejected
Writes blocked entirely (owner chose guarded writes); classifier-only guard (dev ADR-002); coroutine cancel as the time cap (does not interrupt SQLite).

## Consequences
Console can ship in four independent PRs (core, read, write, restore). Restore touches graph lifecycle and ships last. `ScreenRouter.kt`/`AppState.kt`/`SettingsDialog.kt` gain a route-table entry, a `Screen` value and a visibility-lambda list respectively, not inlined console code.

## Addendum (triad repair iteration 3, 2026-10-27)
- **Large writes escalate.** `ConfirmTier` is `Standard` or `TypedCount`: a dry-run count of at least 1,000 rows or at least 50% of the target table requires typing the exact count (thresholds INFERRED; owner may change them). Decided in one pure function (Task 3.3d).
- **Restore is quantified, visible and reversible.** The confirm states the backup's age, page/block counts versus now, the differing-row count and the DB-only rows exported first; the swap shows a blocking progress dialog with named steps; the `*.pre-restore` set is kept as one undoable copy that survives restart (Task 3.4d). The in-block `Restore backup` action lives in scrollback only; the Backups list is the durable entry.
- **Backup failure copy** is one string everywhere: "Backup failed: <reason>. Nothing was changed."

## Addendum 4 (triad repair iteration 5, 2026-10-27): the `sql!` dry run and the write-time re-check
- **Dry run = rolled-back execution.** The count shown in the confirm comes from executing the statement inside a `DatabaseWriteActor` transaction (the single-writer path, so no app write interleaves) that always ends by throwing a private `DryRunRollback` sentinel. Nothing is committed and no invalidation is emitted. It reads `changes()` (rows changed directly) and `total_changes()` (adds rows changed by triggers and `ON DELETE CASCADE`) before and after, and the tables touched. FTS triggers fire inside the transaction, so their cost counts toward the time and their writes roll back with it. It runs under the 10 s `QueryDeadline`; a timeout rolls back and refuses the write.
- **Escalate-or-refuse.** One pure function with `ConfirmTier`: one table and equal deltas use the count rules of Task 3.3d; a delta larger than `changes()` (triggers or cascades) lists each table and is at least `TypedCount`; a statement touching more than one table, or one the dry run cannot complete (error, timeout, `random()` or `datetime('now')` in the SET or WHERE), is `TypedCount` if a count was obtained and **refused** otherwise ("Can't count the rows this would change, so it won't run. Nothing was changed."). DDL, `PRAGMA`, `ATTACH` and `VACUUM` are hard-denied before the dry run.
- **Re-check in the real write.** The real write runs in one actor transaction and compares the actual counts with what was confirmed before commit; it rolls back (same sentinel) when a `Standard` confirm now needs `TypedCount`, or a typed count differs from the actual one, with "More rows would change than you confirmed (N now, M when you confirmed). Nothing was changed. Run it again to re-confirm." The backup already taken is kept.
- **Why not a classifier or `SELECT count(*)`:** a count query cannot see trigger and cascade effects or FTS cost, and a classifier would make the count a guess; the rolled-back execution measures what the real write does. Limit: a non-deterministic statement can differ between dry run and write, which the re-check catches. Tests: UT-161..UT-163, IT-97, IT-98.
