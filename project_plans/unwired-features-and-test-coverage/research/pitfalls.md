## B. Exposing a raw SQL console

Full analysis is already in `dev-console-git-sync-fix/research/pitfalls.md` section 3 (VERIFIED/INFERRED labels there). The points the plan must not lose:

- B1. A keyword/prefix guard is insufficient. `SqliteStatementAnalyzer.leadingKeywords` (`db/SqliteStatementAnalyzer.kt`) stops at `;`, so it classifies only the first statement. CTE-wrapped writes (`WITH x AS (...) DELETE`), `PRAGMA writable_schema`, `ATTACH DATABASE` (creates files), `VACUUM INTO 'path'` (writes a file), and `load_extension` all pass a SELECT-looking check. Enforce on the connection (`PRAGMA query_only=ON` on a console-owned connection) in addition to parsing; deny ATTACH/DETACH/VACUUM/load_extension in both modes.
- B2. Read-only differs per driver. VERIFIED: `DriverFactory.createReadDriver` returns null on JVM/iOS/WASM and a separate read connection only on Android. On JVM the write driver is a pooled 8-connection driver, so setting `query_only` on a pooled connection leaks into later app writes ("attempt to write a readonly database"). Needs a spike (dev-console pitfalls section 9 item 2). Web has no read-only connection (requirements Feasibility Risks): treat console as unsupported on Web rather than weakening the guard.
- B3. Write path: all writes through `DatabaseWriteActor` (`WriteRequest.Execute`, `processExecute` emits the wildcard invalidation after `op()`); a generic `execute(sql)` stub on `RestrictedDatabaseQueries` is a deliberate hole in the `@DirectSqlWrite` gate and must be listed explicitly in whatever test enforces write gating. Deny DDL (bypasses `MigrationRunner`; `MigrationRunnerSchemaSyncTest` will not catch runtime DDL).
- B4. Trigger/FTS side effects: `SteleDatabase.sq:130-158` triggers keep FTS in sync only for INSERT/DELETE/UPDATE OF content/name; `INSERT OR REPLACE` does not fire the delete trigger unless `recursive_triggers` is on, so raw REPLACE can leave stale FTS rows. Raw writes to `*_fts` or trigger DDL desync search. Markdown on disk is the source of truth, so a DB-only edit is overwritten by the next `GraphLoader` reload; show a loud notice.
- B5. Long queries: a full scan of `blocks` on the 9.5k-page graph can run seconds; coroutine cancel does not interrupt SQLite. Need `Statement.cancel()` / `CancellationSignal` wired to cancellation plus a timeout, and a bounded cursor read (cap+1 rows, per-cell truncation); do not textually append `LIMIT`. Actor starvation: a console write inside the single write actor blocks every app write for its duration, so cap write statements by time and row estimate and run reads on a separate connection.
- B6. PII/secrets in logs: statements and results contain note content and possibly credentials (git config rows, `UPDATE settings SET token=...`). Apply one `Redactor` at the single output sink and to log lines for command arguments; the classification is "confidential" (requirements NFR). Persisted `current.log` on Android is exportable, so redact before logging, not at export.
- B7. Unbounded results can OOM Compose and kill the process on Android (CLAUDE.md "Uncaught coroutine Throwables"). Own scope with `CoroutineExceptionHandler`, ring-buffered scrollback, `LazyColumn` (dev-console pitfalls sections 6-7).

## C. Scheduled sync on desktop

Existing decision to reuse: ADR-004 (`dev-console-git-sync-fix/decisions/ADR-004-scheduled-full-sync.md`): `ScheduledSyncPolicy` returns Run / FetchOnly / Skip, closed-app work is fetch-only, desktop timer lives inside `GitSyncService.startPeriodicSync`.

- C1. Overlapping runs. `DesktopSyncScheduler.schedule` does `delay(interval); onTick()` serially in one coroutine, so ticks cannot overlap each other, but a tick can overlap a manual sync, the Android-style fetch worker, or a second app instance. VERIFIED precedent: git-sync-resilience pitfalls 3.4 (periodic fetch vs user-initiated op on same repo, collision surfaces as `StaleLockFile`) and 4.2 (two Desktop instances into the same directory). Control: take the `GitWriteLockNaming` lock and check `GitSyncBusyCounter == 0` before each tick; treat a lock collision as Skip, not Error.
- C2. Drift vs fixed rate: `delay` after `onTick` completes means the period is interval + run time; harmless, but the first run is a full interval after launch, so "app open pulls remote commits" (metric 4) is not true until the interval elapses. Decide whether to run once at startup/graph open.
- C3. Laptop sleep. VERIFIED (git-sync-resilience pitfalls 4.1): JGit uses blocking sockets under `PlatformDispatcher.IO`; after wake, a socket read can hang for minutes unless read/connect timeouts are set. Also `delay` uses a monotonic clock that may not advance during suspend, so the next tick can fire late or immediately; do not trust "elapsed" for staleness. Control: explicit timeouts, and compute last-success from wall clock.
- C4. Auth expiry: token/SSH key expiry or locked vault produces repeated failures. ADR-004 inputs include "vault unlocked" and backoff after Error. Without backoff a timer re-hits the remote every interval and may trip host rate limits or account lockout. Surface "auth failed" distinctly from "network down" (git-sync-resilience 2.4: exception type alone is a coarse classifier).
- C5. Conflicts while editing. A scheduled merge writes the working tree under an open editor. VERIFIED mitigations in ADR-004: `EditLock` idle required, repository-state guard, conflict-marker scan, mass-change guard, first-sync confirmation, no force push. `abortMerge` is a hard reset that discards uncommitted edits and must never be called from background code. Keep the Skip-while-editing rule even though the policy is pure and testable; the failure mode is silent data loss.
- C6. Silent staleness: a timer that fails quietly looks the same as one that works. Requirements Observability asks for a per-tick log and last-success time; ADR-004 adds a staleness chip.
- C7. Test flakiness risk: time-driven loops. Inject a `TestScope`/virtual clock (`runTest` with `advanceTimeBy`) and test `ScheduledSyncPolicy` as pure commonTest; do not sleep in tests.

## D. OCR / labeling / cloud plugins

- D1. Heap/battery. VERIFIED: asset-management pitfalls section 1 (ONNX 50-100 MB activations; must not overlap a large image decode), section 3 (PDF to OCR memory on API < 26), and the Phase 6 background backfill concern (section 6, backfill performance on large graphs). Controls: one inference at a time (semaphore), bounded decode (use thumbnail/display tiers from commit 909acc0979, not originals), run only when charging/idle via WorkManager constraints on Android, cancellable, pause under memory pressure (`onTrimMemory`). Requirements NFR demands bounded and cancellable.
- D2. ML Kit has no KMP wrapper (asset-management section 2); keep behind `expect`/interface in androidMain, with a no-op JVM/Web actual so commonTest still runs.
- D3. Cloud cost: `CloudClaudePlugin`/`CloudVisionPlugin` bill per image. A backfill over a graph with thousands of assets could spend real money unattended. Controls: opt-in per graph, explicit estimated-cost confirmation before any batch, hard daily/monthly cap, dedupe by content hash (skip already-labeled), rate limiter, and no automatic retry loop on 4xx/5xx.
- D4. Egress consent. Classification is confidential (requirements). Images can contain faces, documents, screens. Controls: default off, per-plugin consent with a statement of what leaves the device and to whom, per-asset exclusion (private pages), never send in tests or CI without a mock, redact EXIF/GPS before upload, API keys from the credential vault (never `settings`/logs), and log only asset ids and counts, not image bytes or returned text.
- D5. Result trust and writes: OCR/label output written into notes is a write to user content. Route through the actor/GraphWriter; store derived text in an `assets` side table, not note blocks, unless the user opts in. New tables need `MigrationRunner.all` entries (CLAUDE.md; asset-management section 5 migration safety).
- D6. TOCTOU on asset moves (asset-management section 4): moving a file and rewriting references is two steps; `AssetMoveService` is test-only today, so its crash-between-steps behavior has not met the file watcher. Use write-ahead pending-move record and suppress watcher for the path during moves. Double-move guard in the ViewModel.
- D7. Plugin error containment: an exception from third-party SDK code on a long-lived scope kills the Android process; wrap plugin calls with Throwable guards and per-plugin circuit breaker.

## E. Comprehensive test coverage planning

- E1. Coverage theater. Existing gates measure diff coverage and mutation per PR (`kmp/build.gradle.kts` jacoco at ~1517, incremental gates at ~1535, PIT narrowed to classes with related JVM tests at ~1639, PIT mutates JVM bytecode only so `androidMain` is never a mutation target). Consequences: Android-only code can show green mutation by absence; a number alone does not show a feature is reachable. VERIFIED example of coverage that did not reflect reality: commit 0db1115132 (editor package 6.8% line / 0.4% branch because the code was dead) and a53809c374 (screen with passing unit tests crashed on first open). Control: pair numbers with the reachability metric (success metric 1) and E2E-through-entry-point tests; report coverage separately for reachable vs unreachable code so deleting dead code is not scored as a regression.
- E2. Mutation cost. Whole-repo PIT is likely too slow (requirements Rabbit Holes). Tier it: mutation required for Tier 1 (parsers, SQL guard, redactor, sync policy, write path), nightly or on-demand for Tier 2, none for UI. GAP: no run time measurement exists; requirement 2 says numbers must be run, not estimated, so schedule a timed baseline run before choosing tiers.
- E3. Placement and display. VERIFIED (CLAUDE.md): Compose-behavior tests belong in `androidUnitTest` (Robolectric, headless), reserve `jvmTest` for pixel rendering; run `scripts/jvm-display-check.sh -- ...` before treating a jvmTest UI failure as real; on native Wayland there is no X11 `DISPLAY` and a stale inherited `DISPLAY` produces dozens of identical `XToolkit` failures that are not regressions. CI uses `xvfb-run --auto-servernum` (`.github/workflows/ci.yml:219`, `bazel-ci.yml:89`, with a `/tmp/.X11-unix` mount quirk noted at `bazel-ci.yml:55`). Control: new coverage tests default to commonTest/businessTest/androidUnitTest; a UI test needing jvmTest must say why.
- E4. Flaky tests seen here (VERIFIED, with commits): `GraphSwitchInvalidationTest` leaked an uncaught `SQLiteException: no such table: blocks` from `GraphManager.updateGraphPath` into later tests (95cc735d2e, PR #493); `QrTransferCoordinatorTest` failed once in the coverage job, unexplained (e18a33f4a0, #485); `CaptureShareReviewTest` teardown race (efa8e4a44d); `DemoGraphPersistenceTest` (5221abd1f7); a real-engine Mermaid render test needed retry and adaptive timeouts (148e3f70e1, 72333ea1d2). Pattern: background coroutines or shared global state outliving a test. Adding hundreds of coverage tests multiplies exposure. Control: every new test uses an owned scope cancelled in teardown, no real clocks, no shared singleton state; follow CLAUDE.md "Root-cause failing tests before loosening assertions".
- E5. CI resource limits are a first-class constraint when adding tests (all VERIFIED unless noted):
  - Bazel Android build killed the runner ("received a shutdown signal" during dexing) five times in a row; hypothesis (INFERRED, not proven in the commit) is un-declared dex memory times 4 parallel dex JVMs; fix was `build:android --jobs=2` plus a `[mem]` sampler (82afcfdcfe, #495). Follow-up #498 added Desugar cap and trend tracking.
  - Release `test-kmp-jvm` hit an `OutOfMemoryError` (0.85.0) then a silent ~6 hour hang (0.85.1) after a heap cap was applied to the wrong workload; resolved by routing through Bazel `jvm_tests` (`.github/workflows/release.yml:125-140`).
  - Android release builds exhaust 512 MB Metaspace in `lintVitalAnalyzeRelease`/D8 (`release.yml:261-266`).
  - `gradle.properties:8` sets `-Xmx4g -XX:MaxMetaspaceSize=768m`; Bazel test JVMs are capped `-Xmx4g` (0f258de153, #483); `scripts/bazel-lowprio.sh` for local runs.
  - GAP: I found no repo record of the specific "Kotlin compiler OOM in `compileDebugKotlinAndroid`" beyond planning docs that name the task (for example `project_plans/editor-subsystem-coverage/research/pitfalls.md:72`); the asker's description is unverified here. Check CI run history before citing it.
  - Control: add test files to existing targets, do not add shards without a memory budget; keep `bazel test` under `timeout`; business_tests suite gap history (25 then 94 then 101 classes) means a new test class must be confirmed counted, not silently skipped by classpath bundling.
- E6. Coverage map accuracy: jacoco `exec` inputs differ between Gradle `jvmTest` and Bazel (`kmp/build.gradle.kts:1532`); numbers from one runner are not comparable with the other. Pick one canonical run for the map and record the command.
- E7. Scope creep: the repo already has six per-area coverage plans (requirements.md). Reuse their findings; do not re-audit areas they closed.

## Cross-cutting recommendations (ordered by risk)

1. Reachability E2E test per wired feature through the real entry point, plus a first-open smoke test (A6, E1).
2. Console guard enforced at the connection and the dispatcher, never by parsing or UI hiding alone (B1, B2, A7).
3. Bounded, cancellable, charging-gated background work with Throwable guards (D1, D7, B7, A5).
4. Scheduler is policy-gated and lock-aware; hard-reset paths unreachable from background code (C1, C5).
5. Cloud plugins default off with cost cap and consent (D3, D4).
6. Coverage map separates reachable from dead code, tiers mutation, and records the canonical runner (E1, E2, E6).
7. Run the open spikes (JVM pooled `query_only`, Android `CancellationSignal`) before committing to the console design (B2, B5).
