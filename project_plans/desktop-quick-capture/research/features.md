# Research: Comparable Quick-Capture Features (Codebase + Industry)

**Project**: desktop-quick-capture
**Scope of this doc**: prior art (in-repo and industry) and the edge cases / unstated needs it surfaces for the desktop OS-level capture feature.

## 1. In-repo prior art: Android capture surfaces

### `CaptureActivity` (`androidApp/src/main/kotlin/dev/stapler/stelekit/CaptureActivity.kt`)

Single translucent `Activity` shared by three entry points (widget, Quick Settings tile, `ACTION_SEND` share target) — see ADR-003 (`project_plans/android-features-integration/decisions/ADR-003-shared-capture-activity.md`). Key mechanics:

- **No-graph state**: `onCreate` collects `app.graphManager?.activeRepositorySet`; if null, renders `NoGraphPlaceholderContent()` instead of the capture sheet (`CaptureActivity.kt:90-96`). Desktop needs the direct analogue — capture UI must never assume a graph is open.
- **`singleTop` + `onNewIntent`**: because the Activity can already be on-screen when a second share arrives, `initializeText()` is deliberately idempotent — it only sets text if the field is still empty (`CaptureViewModel.kt:47-51`) — so a second incoming share doesn't clobber in-progress typing. Desktop's in-process hotkey popup has the same "popup already open, second trigger fires" case.
- **Text-source precedence** (`CaptureActivity.buildShareText`, tested exhaustively in `androidApp/src/test/kotlin/dev/stapler/stelekit/CaptureShareTextTest.kt`): `clipData` (with a `takeIf { isNotBlank() }` guard so an empty/whitespace clip doesn't eat the fallback) → `EXTRA_TEXT` → `EXTRA_SUBJECT`, with subject+body de-duplicated when identical and joined with `\n` when distinct. This is the browser-share pattern (page title + URL) — macOS Services-menu "Add to SteleKit" and a Nautilus "Send to" action will hit the same title/body shape.
- **`EXTRA_STREAM` (image) URI permission lifetime**: the OS grants the receiving `Activity` only temporary read permission on a shared content URI; ADR-003 explicitly calls out that forwarding it to a `CoroutineWorker` or other async context throws `SecurityException` once the permission is revoked. The fix is synchronous copy to app-private storage in `onCreate` before any coroutine launch (`copyStreamToPrivateStorage`, `CaptureActivity.kt:146-153`, wrapped in try/catch for both `SecurityException` and generic `Exception`). Desktop's OS-level surfaces (Share Extension, context-menu handler) will face an analogous "the OS handle you were given is short-lived" problem for dropped files/images, though the specific mechanism differs (macOS extension sandbox `NSItemProvider`, Windows shell handler process lifetime).
- **Save-path reuse**: `CaptureViewModel.performSave()` (`CaptureViewModel.kt:71-118`) is the concrete example of "reuse the existing write path" the requirements doc calls for — it calls `journalService.ensureTodayJournal()`, builds a `Block` with `FractionalIndexing.generateKeyBetween(existingBlocks.maxByOrNull{...}?.position, null)` (i.e. appends at end), writes via `DatabaseWriteActor.saveBlock()` (falling back to a direct `@OptIn(DirectRepositoryWrite::class)` write if the actor is null — e.g. during a graph switch), then flushes to Markdown immediately via a fresh `GraphWriter(fileSystem, writeActor).savePage(...)`. It also explicitly catches `ClosedSendChannelException` from a graph-switch race and rethrows a clearer `IllegalStateException`. Desktop's in-process hotkey popup should reuse this exact call sequence rather than re-deriving it.
- **Auto-save on dismiss**: `BackHandler` and the translucent scrim's tap handler both call `viewModel.save()` if `captureText.isNotBlank()` instead of silently discarding (`CaptureActivity.kt:233-251`) — an unstated-need pattern (see §4).
- **Save feedback**: on success the Activity just `finish()`s (no snackbar/confirmation — the overlay disappearing *is* the feedback); on failure a `Snackbar` shows `"Save failed — ${message}"` and the sheet stays open so the user doesn't lose their typed text (`CaptureActivity.kt:216-226`).

### `VoiceCaptureActivity` / `VoiceCaptureWidgetViewModel`

Same translucent-overlay shell as `CaptureActivity`, but state-machine driven (`Idle → Recording → Transcribing → Formatting → Done/Error`). Two details generalize to desktop:

- **Truncation warning as first-class state**: `VoiceCaptureState.Done.isLikelyTruncated` renders a distinct "⚠️ Saved — recording may be incomplete" title instead of silently truncating (`VoiceCaptureActivity.kt:271-285`). Desktop capture of very long pasted/dropped text should have an equivalent length-guard signal rather than a silent truncation.
- **Error taxonomy drives the recovery action, not just the message**: `VoiceErrorKind.PERMISSION_DENIED` → "Open Settings" deep link; `NO_GRAPH` → "Open SteleKit" (launches `MainActivity`); `GENERIC` → "Record Again" (`VoiceCaptureActivity.kt:332-355`). This is a reusable pattern for desktop: distinguish "no graph configured" (open main window to onboarding) from "transient write failure" (retry) from "OS permission missing" (open System Settings pane), rather than one generic error toast.
- **Destination transparency**: `DoneContent` always states where the note landed — `"Saved to today's journal"` or `"Saved to [[pageName]]"` (`VoiceCaptureActivity.kt:286-296`) — confirming the save target is itself a piece of required feedback, not optional polish.

### `CaptureTileService` (`androidApp/src/main/kotlin/dev/stapler/stelekit/tile/CaptureTileService.kt`)

`onClick()` routes to `MainActivity` instead of `CaptureActivity` in two cases: `graphId == null` (no active graph) and `graphInfo?.isParanoidMode == true` (**locked/encrypted vault must be unlocked through the main UI first** — `CaptureTileService.kt:38-46`). This is a concrete precedent for a desktop edge case not mentioned in the requirements doc: **what does the global-hotkey popup / Share-extension / context-menu handler do if the active graph is a locked paranoid-mode vault?** The Android answer is "don't even offer the lightweight capture UI — force the full unlock flow" — the same logic should carry over.

### `CaptureWidgetReceiver` / `VoiceWidgetReceiver` (`androidApp/src/main/kotlin/dev/stapler/stelekit/widget/`)

Not read in full for this doc, but structurally these are just additional Android-only triggers into the same `CaptureActivity`/`VoiceCaptureActivity` — reinforcing the "one capture surface, N triggers" principle ADR-003 states explicitly and that the desktop requirements doc already cites as the guiding precedent for context-menu/hotkey/Share-extension triggers.

### The "enrichment pipeline" the requirements doc references

Searched `project_plans/android-features-integration/` and `project_plans/tag-suggestion-trigger/` for "auto-link", "enrichment", "TagSuggestionEngine": **no wiring of an enrichment pipeline into `CaptureActivity`/`CaptureViewModel` exists yet.** `tag-suggestion-trigger`'s scope (`project_plans/tag-suggestion-trigger/requirements.md`) is a manual, per-block "Suggest tags" toolbar button on the full editor (`JournalsView`/`PageView`), explicitly **out of scope**: "Auto-triggering suggestions without user action." That is a different mechanism (manual trigger, full editor context) than what desktop-quick-capture's requirements doc describes ("auto-link + tag-suggest... being wired into Android capture"). **This confirms Open Question 4 in the requirements doc is correct to flag**: the enrichment pipeline desktop is meant to "reuse" does not exist in `CaptureActivity` today, so desktop v1 will ship without it regardless of sequencing choice.

## 2. Industry comparables

### Obsidian (plugin ecosystem — no native OS-level capture)

Obsidian community plugins **cannot register true OS-level global hotkeys** — the only API that would allow it (`electron.remote.globalShortcut`) is deprecated and forbidden by the community-plugin review guidelines. The standard workaround is to delegate to an external system-wide launcher (Raycast, Alfred, Hammerspoon, ULauncher) that shells out to Obsidian's URI scheme or a plugin's exposed command, rather than the app owning a hotkey itself. Raycast's "Obsidian Smart Capture" extension lets a user select text in any app, press a Raycast hotkey, then a second key combo to file it. A named limitation of the direct-hotkey approach: triggering capture switches focus to Obsidian itself, disrupting the user's original context — "harder to get back to what you were doing." [Obsidian Quick Capture](https://obsidian.rocks/obsidian-quick-capture/), [Raycast Obsidian Smart Capture](https://www.raycast.com/millin_gabani/obsidian-smart-capture), [Global Hotkeys plugin discussion](https://community.obsidian.md/plugins/floating-notes)

Implication for SteleKit: an in-process popup avoids the URI-scheme/external-launcher indirection entirely (per the requirements doc's key architectural fact), but should still take the "don't steal focus from what the user was doing" lesson seriously — the popup should be small, transient, and return focus to the previous foreground app on dismiss/save rather than raising the full main window.

### Logseq itself — repeatedly requested, still unshipped natively as of the most recent forum activity found

Logseq's own community has an open, multi-year feature request for exactly this ("Universal capture hotkey" — global `Ctrl+Space`-style popup from any app), explicitly citing Evernote/Todoist/Trello/TickTick as prior art that already do this. As of the search results, no evidence of Logseq desktop shipping a native global-hotkey popup — the closest shipped thing is a **Chrome extension** ("Logseq Quick Capture") that captures URL + title + selected text from the active browser tab and posts to a running Logseq instance over its local HTTP API. [Universal capture hotkey](https://discuss.logseq.com/t/universal-capture-hotkey/17597), [Logseq Quick Capture Chrome extension](https://chromewebstore.google.com/detail/logseq-quick-capture/hdpmdgiddmjppbeahnglgagndmahlanc)

Implication: this is close prior art for SteleKit's own #230 (Chrome web-clipper, explicitly out of scope here) and #232 (local REST API) — Logseq's extension is exactly the "thin client of a local API" shape the requirements doc anticipates for the out-of-process desktop surfaces. It's also evidence that "global hotkey popup, no local API needed" is the harder-to-ship variant industry-wide (Logseq hasn't shipped it either), which supports treating the in-process hotkey popup as the pragmatic v1 slice.

### Drafts (macOS/iOS, Agile Tortoise)

Drafts' whole product thesis is "always ready to capture" — the app is explicitly designed to launch fast into a blank canvas with keyboard focus, text capture first, filing/action decisions deferred. On macOS specifically it ships a **menu-bar quick-capture window** (type or paste text, assign tags/syntax, then save) reachable via a global keyboard shortcut, plus a separate shortcut to capture clipboard contents directly with no window at all. [Drafts for Mac](https://www.macstories.net/reviews/drafts-5-mac/), [Getting Started](https://docs.getdrafts.com/gettingstarted/)

Implication: two patterns worth adopting — (1) a **menu-bar/tray-resident entry point** as an alternative activation to the hotkey (macOS Services-menu item is already in scope; a menu-bar icon is a near-free additional trigger once the popup exists); (2) a **"capture clipboard, no UI" shortcut variant** for the fastest possible path when the user already has exactly the text they want on the clipboard — relevant to the "keyboard-only flow" unstated need (§4).

### Notion Web Clipper

On invocation, the clipper's popup makes the user **explicitly choose workspace and destination page/database** before saving — it does not silently default to one location, and it always attaches a `URL` property capturing provenance. [Notion Help: Web Clipper](https://www.notion.com/help/web-clipper)

Implication: directly relevant to SteleKit's multi-graph question (§3) and the "pick a destination instead of always today's journal" unstated need (§4) — Notion's answer is to always ask (or remember last choice) rather than hard-coding a single implicit destination, which is heavier than Android's `CaptureActivity` (always today's journal, no picker) but is the right comparison point given SteleKit already supports multiple simultaneous graphs, which Android's single-active-graph capture UI does not need to disambiguate as visibly.

## 3. Edge cases and failure modes the design should handle

Ranked roughly by how directly the codebase already answers them vs. how open they are:

1. **SteleKit not running when an out-of-process trigger fires** (Share Extension / Nautilus script / Windows context-menu handler). Android's share sheet always has a foreground `Activity` to launch into; desktop context-menu handlers have no such guarantee. Per the requirements doc's Open Question 3, this needs an explicit decision: silent background launch, queue-to-file-and-flush-on-next-launch, or explicit OS-level error. **Not yet decided — flag for the plan phase.**
2. **Locked/paranoid-mode vault as the active graph.** Direct precedent: `CaptureTileService.onClick()` routes to `MainActivity` instead of the lightweight capture UI when `graphInfo.isParanoidMode == true` (`CaptureTileService.kt:43-44`). Desktop's hotkey popup and OS-extension surfaces need the same short-circuit — do not offer a capture text field in front of an encrypted graph the process hasn't unlocked.
3. **Multiple graphs open simultaneously.** `GraphManager` supports multiple isolated `RepositorySet`s at once (per `CLAUDE.md`'s Multi-Graph Support section) — Android's capture surfaces only ever target the single `activeRepositorySet`, so this ambiguity doesn't arise there. Desktop must decide: capture always targets whichever graph is currently focused/active in the main window, or the popup lets the user pick (Notion's approach, §2). Needs a design decision, not just an implementation detail.
4. **No active graph configured at all.** Direct precedent: `CaptureActivity`'s `NoGraphPlaceholderContent()` render when `activeRepositorySet` is null (`CaptureActivity.kt:90-96`), and `VoiceErrorKind.NO_GRAPH`'s "Open SteleKit" deep link (`VoiceCaptureActivity.kt:342-350`). Desktop equivalent: popup shows a placeholder + "Open SteleKit to set up a graph" action instead of a broken/empty text field.
5. **Very long captured text.** No direct precedent in `CaptureActivity` (its `OutlinedTextField` is `minLines=3, maxLines=8` but text can still exceed that and scroll — no length cap or truncation observed). `VoiceCaptureActivity`'s `isLikelyTruncated` flag (§1) is the closest prior art for *signaling* a length problem rather than silently truncating. Desktop capturing a large clipboard paste or a dragged text file needs an explicit decision: cap + warn, or accept unbounded and let the block be long (SteleKit's data model doesn't appear to cap block content length elsewhere in what was reviewed).
6. **Rich text / HTML vs. plain text.** Android's `buildShareText()` only ever coerces to plain text (`clipData.getItemAt(0).coerceToText(this)`) — HTML formatting is deliberately discarded, not preserved as Markdown. macOS Services-menu selections and Windows/Nautilus file-manager captures will often carry rich text (e.g. selecting formatted text in Pages, or a `.docx`/`.rtf` file) — desktop needs an explicit plain-text-only policy (matching Android) or a Markdown-conversion step; the requirements doc's "no second bespoke enrichment path" principle argues for keeping this dumb (strip to plain text) rather than building a converter for v1.
7. **Captured image/file attachments.** Direct precedent: `EXTRA_STREAM` handling with synchronous copy-to-private-storage before any coroutine hop (§1, `CaptureActivity.kt:146-153`), because the OS-granted read permission is short-lived. The desktop analogue (a dropped file path from a Nautilus action, or an `NSItemProvider` from a macOS Share Extension) will have its own short-lived-handle behavior that needs the same "copy synchronously, first thing" discipline — the specific OS API differs but the *shape* of the bug (async handoff after the handle expires) is identical and should be treated as a known risk up front, not discovered later.
8. **Concurrent capture + editor open on the same journal page.** No explicit handling found in `CaptureViewModel.performSave()` beyond the general `DatabaseWriteActor` serialization and `ClosedSendChannelException` retry-on-graph-switch guard (§1). Because writes route through the same actor and `GraphWriter` flush path the main editor uses, this is likely already safe by construction (single serialized writer) — but it wasn't explicitly tested for the "capture from hotkey while journal page is open in the editor with unsaved local block-editor state" case. Worth a targeted test rather than assuming.
9. **Offline / filesystem-only graphs.** SteleKit's graphs are local Markdown directories, not cloud-synced by default (per architecture docs reviewed) — "offline" isn't a distinct failure mode the way it is for Notion's clipper; the closer risk is a graph whose directory is on a currently-unmounted network drive or removable volume, which is closer to failure mode 4 (no active graph reachable) than a true offline/online distinction.
10. **Popup already open when a second trigger fires (in-process case).** Direct precedent: `CaptureViewModel.initializeText()`'s idempotency guard (`if (_captureText.value.isEmpty() && text.isNotEmpty())`, `CaptureViewModel.kt:47-51`) so a second `onNewIntent` share doesn't clobber in-progress typing. The desktop hotkey popup needs the equivalent behavior: second hotkey press while the popup is already open should re-focus it, not discard typed-but-unsaved text or spawn a second window.

## 4. Unstated needs beyond the literal ask

- **Confirmation feedback that names the destination**, not just a generic "saved" toast — direct precedent in `VoiceCaptureActivity.DoneContent` always stating "Saved to today's journal" or "Saved to [[pageName]]" (§1). Users capturing blind (hotkey, Services menu) have no other way to know where their note went.
- **Never silently discard typed-but-unsaved text.** `CaptureActivity`'s auto-save-on-dismiss (back button, scrim tap) is the existing policy (`CaptureActivity.kt:233-251`) — any dismiss path (Escape key, click-outside, losing focus) on desktop should carry the same guarantee, or at minimum warn before discarding non-blank text.
- **Failure recovery that matches the failure type**, not one generic error state — `VoiceErrorKind`'s three-way branch (permission → Settings deep link, no-graph → open app, generic → retry) (§1) is the pattern to replicate for desktop's own failure modes (no graph, locked vault, write failure, IPC/cold-start failure for out-of-process surfaces).
- **Ability to choose a destination page instead of always today's journal.** Not present in Android's `CaptureActivity` at all (hard-coded to today's journal) but explicitly requested in the requirements doc's own "Out of scope" line ("Full Import UI parity (scope/format picker)") implying it was considered and deliberately deferred — and it's exactly what Notion's clipper treats as mandatory, not optional (§2). Worth flagging in the plan as a documented v2, not a silent gap, given how directly comparable products treat destination choice as core rather than an add-on.
- **Keyboard-only flow.** Implicit in both `CaptureActivity` (`windowSoftInputMode="stateAlwaysVisible"` per ADR-003, `focusRequester.requestFocus()` on launch, `CaptureActivity.kt:228-230`) and Drafts' "always ready... keyboard raring to go" philosophy (§2): the moment the popup appears, focus must already be in the text field with no click required, and Escape/Cmd+Return-style save-and-dismiss should work without touching the mouse. This should be a named acceptance criterion for the desktop popup, not assumed as a given of "just reuse Compose."
- **Not stealing focus from the source app longer than necessary.** Obsidian's named limitation (§2: hotkey capture "makes it harder to get back to what you were doing") argues the desktop popup should return focus to the previously-foregrounded window on save/dismiss (OS APIs permitting) rather than leaving SteleKit's main window raised.
- **A "capture clipboard directly, no popup" fast path**, mirrored from Drafts' second global shortcut (§2) — lower priority than the popup itself, but worth naming as a possible v1.5 given how cheap it is once the write path exists.
