# Research: Pitfalls — Desktop Quick Capture (OS-level)

## Summary

This feature has two structurally different failure surfaces: an **in-process** global-hotkey popup (macOS/Linux/Windows, JVM/Compose Desktop, reuses `GraphManager`/`JournalService`/`GraphWriter` directly) and **out-of-process** OS integrations (macOS Share Extension, Nautilus "Send to" script, Windows registry context-menu handler) that must hand off to a possibly-not-running SteleKit process. Nearly every hard bug in this class of feature comes from conflating the two: treating the hotkey popup as a "small window" (it is a long-lived coroutine host with its own crash risk, per this repo's documented patterns) or treating cross-process handoff as "just write to the same DB" (it isn't — SQLDelight/`DatabaseWriteActor` assumes single-writer-in-process).

No prior art exists in this repo for global hotkeys, system tray, IPC listeners, or macOS notarization/entitlements (`kmp/build.gradle.kts` and `kmp/src` have zero hits for JNativeHook, SystemTray, or codesign/notarization config — confirmed via grep). This is greenfield; the codebase's only directly relevant precedent is Android's `CaptureActivity` (`project_plans/android-features-integration/decisions/ADR-003-shared-capture-activity.md`) and the general coroutine-scope/write-path rules in the root `CLAUDE.md`.

## 1. Global hotkey libraries on JVM

**No cross-platform, actively-maintained option exists that "just works."** Every candidate has a structural limitation, not just a bug list:

- **JNativeHook** — installs a low-level native (JNI) keyboard/mouse hook. Works on X11 and Windows. Known issues:
  - Requires **macOS Accessibility permission** (`System Settings → Privacy & Security → Accessibility`) to receive *any* global key event. Without it, `NativeHook` registers successfully but silently receives zero events — there is no exception, no callback, just nothing. This is the single most common JNativeHook support-forum complaint.
  - The permission prompt is tied to the **exact binary path**. A `jpackage`-built app bundle, a `./gradlew run` dev JVM, and a re-signed release build are each treated as separate grantees by macOS TCC (`Transparency, Consent, and Control`) — users granting access once and then losing it after an update (new bundle identifier or re-signed binary hash) is a recurring failure mode across all JNativeHook-based apps, not specific to this one.
  - **On Wayland, JNativeHook effectively does not work.** It hooks via X11's `XGrabKey`/record extension or `evdev`; under Wayland compositors (GNOME Mutter, KDE KWin) there is no equivalent API exposed to arbitrary applications by design — Wayland's security model deliberately does not let one app observe another app's input. GNOME and KDE instead expose the **XDG Desktop Portal `GlobalShortcuts` interface** (`org.freedesktop.portal.GlobalShortcuts`), which requires a portal-aware D-Bus client, a user-facing grant dialog per shortcut, and (as of most 2024–2025 GNOME/KDE releases) still has gaps — GNOME only shipped portal-based global shortcuts in recent Shell versions, and older/other-DE users (Sway, i3, minimal window managers) may have no portal implementation at all.
  - Practical implication for requirement #2 in scope ("Linux: file-manager Send-to script OR a global-hotkey popup — whichever is lowest-effort first"): **the file-manager Send-to script is very likely the lower-effort, more-reliable option specifically because the hotkey path is Wayland-fragile**, not just because it's simpler to write. On X11-only setups (still common on older distros, i3/dwm users) JNativeHook global hotkeys work fine; assume a meaningful fraction of the Linux user base is on Wayland and will get either silent failure or a portal permission dialog they don't expect.
- **JIntellitype** — Windows-only, unmaintained since ~2011 (last release predates Windows 8), 32-bit-native-DLL-only in its original form (community forks exist but are unmaintained). Not viable for a modern Windows target without forking it yourself.
- **Alternative**: `java.awt.KeyEventDispatcher` / Swing's global key bindings **do not work for OS-level global hotkeys** — they only fire when the JVM app has focus, which is the opposite of what "global hotkey capture popup" requires. (Note: `kmp/src/jvmMain/.../desktop/Main.kt` already touches `KeyboardFocusManager` for in-app Tab handling — that mechanism is unrelated and cannot be extended to global scope.)
- **macOS-specific alternative**: register the hotkey via the OS itself (a Services-menu entry, or `NSEvent.addGlobalMonitorForEvents` from a small native/JNA shim) rather than JNativeHook, since macOS's own APIs handle the permission model more predictably than a JNI hook layer. This still requires Accessibility (or Input Monitoring, depending on API) permission and the same binary-identity-pinning problem above.

**Packaging/signing consequence**: any global-hotkey capability on macOS forces **notarization** (Gatekeeper blocks unsigned/unnotarized apps requesting Accessibility access with a generic, unhelpful "app is damaged" or silent-deny message rather than a clear permission prompt) and a **stable, unchanging code signature** across releases — a Developer ID certificate must be provisioned and CI must sign+notarize every build, or every update potentially re-prompts users for Accessibility access. This repo currently has no signing/notarization pipeline (confirmed: no entitlements/notarize files found in the repo). That's a new CI dependency, not just app code.

## 2. Single-instance / IPC pitfalls

The requirements doc is explicit that the OS-integration paths (Share Extension, Nautilus script, Windows context-menu) are **separate OS processes** needing IPC, and calls out that the full local REST API (#232) is intentionally out of scope — so whatever hand-off mechanism ships here must be a **narrower, purpose-built channel**, not a preview of #232.

Concrete failure modes:

- **Startup race**: SteleKit is launching (JVM cold start, `GraphManager.addGraph` still parsing markdown) when the external process (Nautilus script, Share Extension helper, registry handler) tries to hand off. If the hand-off channel (socket/pipe/lock-file) isn't listening yet, the sender needs a defined retry/backoff and a **cold-start path**: launch SteleKit if not running, then retry the hand-off after a readiness signal — not a fixed sleep, since graph load time scales with graph size (this repo already has an 8,000+ page graph as its benchmark ceiling; a fixed 1–2s sleep will be too short for large graphs and wastefully long for small ones).
- **Stale lock files after a crash**: if the mechanism to prove "an instance is running" is a PID/lock file, a hard kill (OOM kill, `kill -9`, power loss) leaves the file behind. A naive "if lock file exists, assume a running instance and hand off to it" check will silently drop the capture (send to a dead socket, or worse, block forever waiting for a listener that will never answer). Any lock-file design must verify liveness (check the PID is alive **and** is actually SteleKit, e.g. via a process-name or handshake check) rather than trusting file existence alone.
- **Port conflicts** if using a loopback HTTP/TCP listener: a fixed port collides with another local dev tool, another SteleKit instance (multiple graphs open in separate processes — this repo's `GraphManager` supports multiple *graphs* in one process, but nothing here prevents a user from running two SteleKit processes against different graphs), or a leftover process from a previous crash still holding the port. Mitigation options: OS-assigned ephemeral port + advertise the actual port via a well-known local file (with the staleness problem above), or a Unix domain socket / Windows named pipe instead of TCP, which sidesteps port collision entirely and is the better default given the local-only use case.
- **Security of a local listener**: per the requirements' explicit scoping (full REST API is separate, "more carefully scoped" work — #232), the quick-capture hand-off channel must not become a de facto unauthenticated local API:
  - **Bind to loopback only** (`127.0.0.1`/`::1`), never `0.0.0.0` — a TCP listener on all interfaces on a laptop connected to untrusted networks (coffee shop wifi) would let anyone on the LAN write arbitrary content into the user's notes.
  - **Prefer a Unix domain socket / named pipe over TCP where available** — filesystem/OS permissions on the socket file (or named pipe ACL) provide access control for free; a loopback TCP port is reachable by any local user/process on multi-user machines, which a socket with restrictive file permissions is not.
  - **Require a token/shared secret** even on loopback if TCP is used, written to a file only the current OS user can read (e.g. `~/.stelekit/capture.token` with `0600` perms) — defends against other local processes/malware on the same machine sending arbitrary capture payloads, since "loopback-only" alone does not mean "only SteleKit's own helper can talk to it" on a shared or compromised machine.
  - Payload validation: cap message size (a malicious or buggy sender could send gigabytes and OOM the listener thread), and treat all inbound text as untrusted input to the same markdown-parsing pipeline as any file-based import (i.e., no privileged/raw-SQL path just because it arrived over the socket).

## 3. Write-path pitfalls specific to this codebase

This is the part of the design most likely to be gotten wrong by someone unfamiliar with the repo's established crash history, because a capture popup is exactly the "new long-lived-ish UI surface with its own coroutine scope" pattern the root `CLAUDE.md` calls out.

- **`rememberCoroutineScope()` leaking into a long-lived object.** A hotkey-triggered capture popup is *not* a normal composable lifecycle — it may be shown/hidden repeatedly without full recomposition teardown, or implemented as a singleton `ComposeWindow` created once and shown/hidden via AWT rather than mounted/unmounted through Compose's `application {}` DSL (this is a common pattern for "instant popup" perf, since creating a fresh `Window` composable per hotkey press adds visible latency). If the popup's state holder (its own `CaptureViewModel`-equivalent) is built with `remember { CaptureController(rememberCoroutineScope()) }` inside a composable that gets torn down and re-shown, the scope is cancelled on hide and the *next* hotkey press's `saveBlock()` call throws `ForgottenCoroutineScopeException` — this is precisely the violation class described in the "Coroutine scope ownership" section of the root `CLAUDE.md`. The correct pattern here (matching `StelekitViewModel.scope` and `GraphLoader.parallelScope`) is a controller class that owns `CoroutineScope(SupervisorJob() + Dispatchers.Default)` internally, instantiated once for the process lifetime (e.g. held by `Main.kt` or a small `CaptureController` singleton alongside the hotkey registration), *not* re-created per popup show.
- **Missing `CoroutineExceptionHandler` on that scope.** Per the "Uncaught coroutine Throwables kill the process" section: on desktop this "only" prints instead of killing the process (unlike Android), but the effect here is still bad — an uncaught exception in the save-on-Enter coroutine means the user's captured text is silently lost with no UI feedback, and if it's an `OutOfMemoryError` mid-graph-load-plus-capture race, the process can still die. The controller scope needs the same `CoroutineExceptionHandler { _, e -> logger.error(...) }` pattern used in `StelekitViewModel.scope` and `GraphLoader.parallelScope`, plus a surfaced `fatalError`/toast state so "silently print to a log file no one reads" isn't the only outcome.
- **Writes must route through `DatabaseWriteActor`, never direct `SteleDatabaseQueries` calls.** A capture popup built as a "quick, separate, minimal" code path is exactly the kind of feature where someone reaches for a shortcut — e.g., calling `RestrictedDatabaseQueries` mutators directly "just this once" because the popup doesn't want to depend on the full `DatabaseWriteActor`/`JournalService` machinery. That breaks write serialization (a hotkey capture racing an in-app edit save on the same block/page) and violates the `@DirectSqlWrite` gating documented in root `CLAUDE.md`. The popup must call through `JournalService`/`GraphWriter` (or whatever thin wrapper is chosen) exactly as the in-app editor does, on `PlatformDispatcher.DB`.
- **The DB/actor may not be ready when the hotkey fires.** Unlike the in-app editor (which only exists once a graph is loaded), a global hotkey can fire the instant the app starts, before `GraphManager.addGraph()` has finished and before `activeGraphId` is set. The popup needs an explicit "graph not ready yet" state (queue the capture and flush once ready, or show a brief "loading…" state) rather than assuming `DatabaseWriteActor`/`JournalService` are non-null.
- **Cross-process hand-off writes must go through the same actor, not a bypass.** If the IPC listener (item 2 above) is implemented as, e.g., a raw socket handler that calls straight into `RestrictedDatabaseQueries` for speed/simplicity because "it's just appending one line," that's the same `@DirectSqlWrite` violation as above, just arrived via a different entry point. The IPC handler should deserialize into the same capture use-case function the hotkey popup and (eventually) Android's enrichment pipeline call — one write path, multiple triggers, matching the "all write logic in one place" rationale already used for Android's `CaptureActivity` (ADR-003).

## 4. macOS Share Extension pitfalls for a JVM app

A macOS **Share Extension** (`NSExtension` with `com.apple.share-services` point) is an Apple App Extension — it is fundamentally a **native, sandboxed, separate-binary** mechanism, and this is where the JVM nature of SteleKit collides hardest with the requirement:

- **A Share Extension requires a containing native macOS app.** Extensions ship *inside* a host app bundle (`.appex` under `Contents/PlugIns/` of a `.app`), and Apple's extension model assumes that host app is a normal, signed, App-Store-or-notarized-distributable native app. SteleKit's desktop distributable today is a `jpackage`-produced JVM app bundle (per `./gradlew packageDistributionForCurrentOS`) — it *can* technically be the host bundle, but the extension itself (the process macOS actually launches when the user picks "SteleKit" from a Share sheet) **must be a small native (Swift/Obj-C) binary**, because `NSExtension` processes are launched directly by `extensionkit`/`pluginkit`, not via a JVM bootstrap, and Apple's App Extension API surface (`NSExtensionContext`, `NSItemProvider`) has no JVM/JNI binding. This means: even in the "just a Share Extension" v1 scope, a small Swift helper target is unavoidable — there's no way to write the extension itself in Kotlin/JVM.
- **Entitlements and sandboxing**: Share Extensions run **App Sandboxed** by default and can't be opted out — this is enforced by the extension point, not a developer choice. The extension needs `com.apple.security.app-sandbox = true` plus explicit entitlements for whatever it touches (e.g. temporary file exceptions if it writes a hand-off file, or App Group container access if the extension and main app communicate via a shared container rather than a socket). If the hand-off mechanism chosen for item 2 (loopback socket) is used from inside the sandboxed extension, App Sandbox **blocks arbitrary outgoing network connections by default** — the extension's entitlements must include `com.apple.security.network.client` or the socket connection is silently denied at the sandbox layer (visible only in Console.app's sandbox-violation log, not as a Swift-level error most of the time).
- **App Group container** is the standard/simpler alternative to a live socket for this specific extension: extension writes a small file/plist into a shared `App Group` container; the main JVM app polls or watches that container for new captures. This avoids the sandboxed-extension-networking entitlement fight entirely but reintroduces the "SteleKit might not be running" cold-start problem from item 2 in a different guise (extension can write the file regardless of whether the host app is running; only the read side needs the readiness handling).
- **The Services-menu alternative** the requirements doc lists alongside the Share Extension ("Share Extension / Services-menu entry") is meaningfully lower-effort: a legacy `NSServices` entry (declared in `Info.plist`, `NSSendTypes`) can invoke a helper that talks to the running app via Apple Events or a simple hand-off file, without the App Extension sandboxing/entitlements/separate-binary machinery. Given the "whichever is lowest-effort first" framing already used for the Linux choice in the requirements, the same logic likely favors **Services-menu over Share Extension** for v1 unless Share-sheet visibility (appearing in other apps' native Share UI, not just a right-click Services submenu) is a hard requirement.

## 5. Windows registry context-menu handler pitfalls

- **HKLM vs HKCU and UAC**: a shell context-menu handler registered under `HKEY_LOCAL_MACHINE\Software\Classes\...` applies to all users but **requires admin elevation (UAC prompt) to install** — meaning the installer (or a manual "run as admin" step) must elevate, which is friction for a quick-capture feature that's supposed to feel lightweight. Registering under `HKEY_CURRENT_USER\Software\Classes\...` avoids the UAC requirement (per-user install, no admin needed) and is the standard recommendation for this exact scenario — this project's installer story should default to HKCU unless a specific reason requires machine-wide install.
- **Uninstall cleanup**: registry-based context-menu entries are not automatically removed by deleting the app's files — an uninstaller (or the packaging tool's uninstall hook, if using something like `jpackage`'s MSI/EXE output) must explicitly delete the registry keys it created, or the user is left with a dead "Add to SteleKit" entry in every right-click menu that errors out (or silently does nothing) after uninstall. This is a very common source of "ghost" context-menu entries reported against other apps; it needs to be a deliberate, tested step (verify via `reg query` after uninstall in CI or a manual checklist), not an assumption that the installer handles it.
- **Explorer context-menu handlers registered as a classic shell extension (COM-based, `IContextMenu`/`IShellExtInit`) run in-process inside `explorer.exe`** — a crash or hang in the handler can crash/hang Explorer itself. A **static registry verb** (the simple `shell\<verb>\command` registry approach that just launches an external `.exe`/script with the file path as an argument, no COM DLL loaded into Explorer) avoids this entirely and is almost certainly the right choice here given "context-menu registry handler" is explicitly the scoped mechanism (not a COM shell extension DLL) — worth confirming that's the intended design before any COM-based approach is considered, since COM handlers are drastically higher-risk and higher-effort.
- **Antivirus/SmartScreen false positives**: a shell-invoked handler that launches an unsigned executable (or one with a fresh/low-reputation code signature) from a registry `command` key is a pattern also used by malware persistence mechanisms, so AV heuristics and Windows Defender SmartScreen commonly flag new, unsigned, or low-download-count binaries doing this. Practical mitigations: sign the Windows binary (Authenticode) — the JVM app's `packageDistributionForCurrentOS` output isn't currently signed per the build files reviewed — and expect a "reputation warm-up" period on SmartScreen even after signing, where early adopters may see a warning regardless.

## 6. Multi-graph ambiguity

`GraphManager` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/db/GraphManager.kt`) explicitly supports multiple simultaneously-open graphs, tracked via `_graphRegistry.value.activeGraphId` and a per-graph `activeGraphJobs` map (`GraphManager.kt:94,108,539-564`). A capture triggered from **outside the app** (hotkey when the window isn't focused, or any of the cross-process hand-offs) has no inherent notion of "which graph the user meant":

- **"Active graph" from an external trigger is ambiguous by construction**: `activeGraphId` reflects whatever graph was last switched-to *in the running UI*, which may not match user intent if, e.g., the user has SteleKit open on a work graph in the background but fired the capture hotkey while thinking about a personal-graph task, or if no graph is currently active at all (`activeGraphId` can be `null` — see `GraphManager.kt:356,668,706`) because the app just started or the user closed all graphs.
- **A capture landing in the wrong graph is a silent-until-discovered data-placement bug** — unlike a crash, the user won't notice immediately; they'll go looking for the note later in the graph they *meant* and not find it, then have to search across graphs. This is a worse failure mode than an explicit error, because there's no immediate feedback loop prompting a fix.
- **Recommended mitigation** (design decision, not just an implementation detail — worth capturing as an ADR in this project): the capture popup should show (not silently assume) the destination graph/journal when more than one graph is registered, defaulting to `activeGraphId` but with a visible, quick way to change it before save — mirroring the "Choose page" secondary action already planned for Android's `CaptureActivity` (ADR-003) rather than a fire-and-forget write. If `activeGraphId` is `null` (no graph currently open), the popup must handle that explicitly (prompt to pick/open a graph, or refuse capture with a clear message) rather than crashing or writing to a stale/wrong `RepositorySet`.
