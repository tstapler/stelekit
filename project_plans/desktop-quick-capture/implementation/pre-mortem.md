# Pre-mortem: desktop-quick-capture
**Date**: 2026-09-05

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The feature only works while the SteleKit process is already running (ADR-002's v1 limitation), so it doesn't close the "capture without opening the app" gap the backlog item's title literally asks for — a user whose common case is "SteleKit isn't open right now" gets nothing, same as today. | Support/feedback thread within days of release: "the hotkey does nothing" — filed by users who don't realize SteleKit has to already be open, indistinguishable from a bug report. | Add a validation.md check that explicitly tests/documents the "SteleKit not running" case end-to-end (what actually happens today: nothing) and ship a companion low-effort mitigation identified but not yet adopted in architecture-review — the macOS custom URL-scheme handler (`research/build-vs-buy.md` §2, `Desktop.setOpenURIHandler()`, no Xcode/notarization needed) — or at minimum a "SteleKit must be running" caveat in the release notes/README so it isn't discovered as a bug. | P1 |
| 2 | The default hotkey combo is silently already claimed by another running app (common on Linux DEs and macOS) — JKeymaster's `register()` only catches *exceptions*, not "registered successfully but events never arrive," so there is no error path for this specific, very plausible collision. | User presses the hotkey repeatedly, nothing happens, no log entry is written (since no exception occurred) — looks identical to "SteleKit isn't running," so the failure is misdiagnosed as failure mode #1 and never reported as its own bug. | Add an acceptance criterion + manual smoke-test step to validation.md: after registration, fire the hotkey once programmatically (or via a documented manual step) and confirm the popup actually appears before declaring the hotkey "active" in logs; log a distinct "hotkey registered but not confirmed responsive" state distinguishable from "registration threw." | P2 |
| 3 | `PendingCapturePoller.scanOnce()` retries a permanently-unrecoverable capture (e.g., no graph ever configured on this machine) every 5s forever with no backoff or dead-letter, per adversarial-review's own logged Concern — this is unbounded background work with no user-visible signal that captures are stuck. | User discovers weeks-old captures suddenly land in today's journal (not the day they were captured) once a graph is finally configured — or notices CPU/log churn from an endless 5s poll loop that never terminates. | Add a max-retry-age or max-attempt cap to Story 2.2.1 (e.g., after N failed scans, rename to `.stuck` alongside the existing `.failed` quarantine path from Task 2.2.1b, and surface a "N pending captures could not be saved" indicator somewhere the user will see it — even a log line grep'd by a health-check test is better than silent infinite retry). | P2 |
| 4 | `CaptureSocketListener`'s stale-socket cleanup (Task 3.1.1d) can't distinguish a crashed process's leftover socket from a second live instance's socket (this repo explicitly supports concurrent instances against different graphs, `Main.kt:99-102`) — starting a second instance can delete-and-rebind a live first instance's socket out from under it. | A capture sent while two instances are running lands in the wrong graph's journal (or silently vanishes from the first instance's fast path) with no error surfaced to either process — reported as "my note went to the wrong graph" or "a capture just disappeared." | Add an acceptance criterion to Story 3.1.1: before deleting a socket file on `AddressAlreadyInUse`, attempt a connect-and-handshake probe first (a live listener will accept and respond; a genuinely stale file will refuse) — only delete-and-rebind when the probe fails, per the pattern most Unix daemons use for PID-file/socket staleness checks. | P3 |
| 5 | Escape always auto-saves non-blank text (mirrors Android's `BackHandler`, per plan.md's Minor-severity note in adversarial-review) — but desktop users' near-universal convention is Escape = cancel/discard, not save. A user who opens the popup to test the hotkey, types something exploratory, and hits Escape expecting to discard it instead pollutes today's journal with unintended content. | User notices stray, half-formed blocks in their journal they don't remember intentionally saving ("what is this text in my journal from last Tuesday"), eroding trust in the feature and in journal content quality generally. | Add a distinct discard affordance to Story 1.4.1 — e.g., only auto-save on Escape if the text has been present for > a short debounce window (avoids punishing an immediate "oops, wrong hotkey" tap), or require a second confirming keystroke for genuinely blank-adjacent trivial text, and add an explicit acceptance criterion + screenshot-test case for "type one character, hit Escape immediately" so the behavior is a deliberate choice, not an unexamined port from Android. | P2 |

## P1 Items (address before implementation)
- [x] #1 — Addressed during sdd:4-validate: validation.md now has an explicit manual test (`hotkeyPressWithNoRunningInstance_should_ProduceNoObservableEffect_DocumentedAsKnownV1Limitation`) confirming the no-op behavior, and plan.md's Risk Control section adds the release-notes-caveat mitigation plus a new Unresolved Question asking whether the macOS URL-scheme handler should be folded into v1 (left open for the implementer/owner, not silently dropped).
