# Adversarial Review: desktop-quick-capture

**Date**: 2026-09-05
**Verdict**: CONCERNS

## Blockers
(none — all three resolved, see verification below)

- Idempotency/dedup: RESOLVED. `plan.md` now threads an optional `captureId: String?` through `CaptureWriter.writeCapture`/`writeCaptureDirect` (Task 1.1.1b/c/f) — when non-null, the created `Block.uuid` is `BlockUuid(captureId)` instead of a fresh UUID, so a replayed write resolves through `insertBlock`'s `INSERT OR REPLACE` (`SteleDatabase.sq:335-337`) to a single row, not a duplicate (Task 1.1.1g adds a unit test for exactly this). Both concrete replay paths from the original blocker are covered with the same mechanism: `PendingCapturePoller.scanOnce()` (Task 2.2.1b, Story 2.2.1's third AC) passes the file's own `captureId` through on every scan, so a crash between a successful write and file deletion makes the next scan's replay a no-op; `CaptureSocketClient.trySend` (Task 3.2.1a) generates one `captureId` up front and `CaptureSocketListener`/the CLI fallback branch (Task 3.2.1b, Story 3.2.1's third AC) reuse that same id on a lost-ack fallback to `PendingCaptureWriter.write(text, captureId)`. ADR-001's Consequences section also states the mechanism explicitly. This is specific (exact field/type names: `captureId`, `BlockUuid`, `insertBlock` INSERT OR REPLACE), not just asserted.

- Error-state UI: RESOLVED. Task 1.4.1e (new) renders `saveState == SaveState.Error`: the `OutlinedTextField` stays visible with unchanged text (never cleared), a `Text` row shows `(captureResult as? CaptureResult.Failed)?.message`, and a "Retry" `Button(onClick = controller::save)` is added; `CaptureController.save()`'s failure branch (Task 1.2.1c) now explicitly sets both `saveState = Error` and `captureResult = CaptureResult.Failed(message)` while leaving `text` unchanged. Story 1.4.1 gained an explicit AC ("A failed save preserves the typed text and offers retry"). Task 1.4.1f's screenshot-test list now includes an `Error` (typed text retained + message shown) case alongside the previously-listed states.

- Silent window-close kill: RESOLVED, via documented v1 limitation (not background residency). ADR-002's Consequences section adds an explicit paragraph: closing the main window's `exitApplication()` terminates the hotkey listener and socket listener process-wide, undercutting "capture without switching windows" for as long as the window stays closed; the ADR explicitly weighs a `Tray`-based background-residency option against accepting the limitation, and picks the latter for v1, with a note to revisit once Phase 2's OS-native surfaces make idle-process residency valuable. `plan.md`'s Story 1.5.1 gained a matching AC ("Closing the main window's effect on capture is documented, not silent") and Task 1.5.1d now requires a code comment above `exitApplication()` pointing back to that ADR paragraph. This is a plain statement of a tradeoff, not a silent gap.

## Concerns
- [ ] Active-graph race between availability check and async save: `resolveCaptureAvailability`/`CaptureWriter.writeCapture` snapshot the active `RepositorySet` at call time, but `GraphManager.switchGraph()` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/db/GraphManager.kt:527-556`) nulls `_activeRepositorySet` synchronously while deferring the actual driver close to a background coroutine — a capture started against graph A can complete during/after a switch to graph B. The plan does port Android's existing `ClosedSendChannelException` mitigation (good — this is a previously-hit "Bug 1" on Android per `CaptureViewModel.kt:100-107`), but no acceptance criterion covers which graph a racing save actually lands in, or whether the user is told which graph received a capture when more than one is configured.
- [ ] `PendingCapturePoller` has no backoff or dead-letter policy: a capture that can never succeed (e.g., "no graph configured" on a machine with none) retries every 5s forever (plan.md Story 2.2.1's own stated behavior), with no cap, no exponential backoff, and no surfaced "N stuck captures" state for the user to notice.
- [ ] No per-item fault isolation specified for `PendingCapturePoller.scanOnce()` or `CaptureSocketListener`'s accept loop. If `Json.decodeFromString<PendingCaptureFile>` throws on one malformed/corrupted file (bad JSON, or schema drift once a future Phase-2 writer exists), the exception escapes the coroutine body that owns the `while (isActive) { scanOnce(); delay(5_000) }` loop (Task 2.2.1c) — the `CoroutineExceptionHandler` only logs, it doesn't restart the loop, so one bad file can silently kill the poller for the rest of the process's life, not just get skipped. Same class of risk applies to the socket accept loop surviving one bad connection. Needs an explicit per-file/per-connection try/catch plus a quarantine (rename to `.failed`) for permanently-malformed files.
- [ ] Global-hotkey conflict handling only covers the registration call throwing. It doesn't address the common failure mode where another already-running app has silently claimed the same combo (no exception, events just never arrive). There's no settings UI to let the user pick a different combo if the hardcoded default collides — Unresolved Questions flags the collision risk itself but the plan has no remediation path.
- [ ] Phase 2 (pending-captures format/poller) and Phase 3 (socket IPC) build a complete, tested, bidirectional IPC mechanism with zero real callers in this pass — every actual v1-requested OS surface (macOS Services menu, Nautilus script, Windows registry handler) is explicitly deferred by ADR-002 to a separate future project. This front-loads a protocol design (plain-text-only message shape, `--capture-text` argv contract) ahead of the deferred surfaces' actual needs (e.g., a Windows handler passing a file path, or a macOS Services entry passing rich text), and inflates this PR's diff/review surface with code that has no live consumer yet — a YAGNI risk plan.md's own Step 0.5 doesn't weigh against option 3. Recommend splitting Phases 2-3 into their own follow-up plan gated on Phase 2's OS-surface work actually starting.
- [ ] ADR-001's claim that Windows needs "a separate code path or a JNA-based library" for the socket fast path is unverified against the JDK's own documentation: `StandardProtocolFamily.UNIX` (JEP-380) is documented to work on Windows 10 (1803)+/Server 2019+ via the identical API, without a separate implementation, whenever AF_UNIX support is enabled (default on modern Windows). Before accepting ADR-001's "Windows Phase 2 has no fast path" consequence as fact, verify this against this project's actual minimum supported Windows version — the premise may be wrong in either direction (works today with no extra code, or genuinely doesn't on the oldest Windows version this repo still supports).
- [ ] Multi-instance socket collision: this repo already documents (`Main.kt:99-102`) that multiple JVM instances can run concurrently against different graphs in dev (`stelekit.devGraphPath`). Task 3.1.1d's stale-socket cleanup (delete-and-rebind on `AddressAlreadyInUse`) can't distinguish "genuinely stale from a crashed process" from "a second live instance is currently listening" — it will delete and steal the socket path out from under a live second instance, silently breaking that instance's fast path with no error surfaced to either process.

## Minors
- No metrics/span for capture latency — explicitly and reasonably deferred per the plan's own Observability Plan.
- No "discard without saving" affordance: Escape always auto-saves non-blank text (mirrors existing `CaptureActivity` `BackHandler` precedent), which may still surprise users of an always-on-top desktop popup who expect Escape to mean "cancel."
- `CaptureController.show()`'s "re-focuses existing popup" behavior (Story 1.2.1) is only asserted via state equality in the planned unit test, not via an actual OS-level focus-return check.
- `PendingCaptureWriter.write()` has no defined contract (return value, exit code, stderr message) for disk-full/permission-denied when invoked via the future `stelekit --capture-text` CLI mode that Phase 2's OS scripts will shell out to — worth nailing down before those scripts are authored against it.
