# ADR-005: Work names keep the git legacy name; new kinds use `stelekit_task_<kind>_<scope>`; orphans reconciled by tag

**Status**: Proposed, revised in repair loop 1
**Date**: 2026-11-10

## Context
`stelekit_git_sync_<graphId>` is shared by the periodic sync and `AndroidGitCloneWorkerLauncher` (pause, run clone, restore) and by `GraphMoveQuiesceStrategy.android.kt`. Changing its work type or name breaks that exclusion (`WorkManagerSyncSchedulerUniqueWorkTest`). No code cancels work when a graph is removed.

## Decision
- `TaskKey(git-sync, g).workName()` is exactly `stelekit_git_sync_g`, and its type stays periodic. The clone exclusion protocol is unchanged and covered by the existing tests running against the new adapter.
- `model-download` keeps `DepthModelDownloader.UNIQUE_WORK_NAME`. New kinds use `stelekit_task_<kind>_<stableId(scope)>` where `stableId(scope)` is ALWAYS the 16-hex FNV-1a hash of the scope (never the raw scope: a raw `b_c` scope would collide with kind `a-b` + scope `c`, and a scope that is itself 16-hex would collide with a hashed one). `TaskKind` ids are restricted to `[a-z0-9-]+`, which removes `_` from kinds. Settings and run-log keys use the length-prefixed `TaskKeyEncoding`, so they are injective independent of the work-name hash. Only the legacy `git-sync` name keeps the raw graph id.
- Every request carries the kind tag (when `TaskSpec.jobKind != null`) and the tags `stelekit-sched` and `stelekit-sched-scope:<scope>`. Only one-shot requests also carry `JobTags.ANY` (`stelekit-job`) and the title, so an enabled periodic graph never shows a permanent "Queued" row in the jobs list (`WorkManagerJobRegistry` maps `ENQUEUED` to `Queued`).
- Destructive-path rule (repair loop 1): known graph ids come from a `KnownScopes` provider that reads the persisted `graph_registry` Settings string (`GraphRegistryKnownScopes`, in `db/`). It returns `Known(ids)` only when the string parses and holds at least one non-demo graph; an empty string, a read exception, corrupt JSON or a demo-only registry returns `Unknown`. `GraphManager.loadRegistry` and `StelekitViewModel.kt:869` both legitimately reset the registry to empty, so empty must never mean "cancel everything". Startup `reconcile`, the `TaskWorker` unknown-scope self-cancel and any other orphan cancel act ONLY on `Known` and cancel only scopes absent from it; on `Unknown` they do nothing. Reconcile and the worker NEVER tombstone. Tombstoning happens only from `GraphManager.removeGraph` through an `onGraphRemoved` callback invoked at the end of its success path, after `saveRegistry()` (after every `return false` guard: not found, demo, active-but-not-last-real), and a refused removal must not cancel or tombstone anything. `removeGraph` is non-suspend: the callback only hands off to a root-owned guarded scope, a throwing callback never changes `removeGraph`'s return value, and startup `reconcile` (Known-only) is the backstop for a missed cancel. Only the `resume` path may use `CANCEL_AND_REENQUEUE` on the shared name; `apply` and startup re-apply use `UPDATE` and skip when non-periodic work (a running clone worker) holds the name. The 16-hex FNV-1a name is injective only probabilistically (64 bits); `apply` detects a different-scope collision on a hashed name and refuses rather than cancelling. Work enqueued by the pre-upgrade build has no scope tag and is retagged on its next `apply` (UPDATE replaces the spec); pre-upgrade orphans for already-removed graphs cannot be enumerated (no WorkManager name listing) and are documented as a known limit.
- Old and new names never coexist for git, so the "cancel old only after the new is enqueued" rollback rule is satisfied by not renaming.

## Consequences
Bounded names (graphs x kinds). A one-time `apply` per enabled key at app start retags legacy work.
