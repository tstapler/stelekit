# ADR-003: Per-(graph, kind) settings in a typed Settings-backed store; git interval moves in; idempotent marker migration

**Status**: Accepted (implemented; the Keystore-backed cold-worker path is PENDING OWNER verification, owner-verification.md M-4; Spike 0.1.2 proved only the plain-prefs fallback)
**Date**: 2026-11-10

## Context
`Settings` is a key-value store with no `remove` and no key enumeration (`platform/Settings.kt`). The cold WorkManager process already reads `Settings` (`PlatformSettings()`). `git_config.poll_interval_minutes` is the git interval today; `scheduled_sync_enabled` is one global boolean read fail-closed.

## Decision
- `TaskSettingsStore` in `jobs.schedule` persists one versioned string per key, with key families `task_entry_`, `task_default_`, `task_migrated_`, `task_applied_` (ledger) and `task_run_log_`. Keys are built by `TaskKeyEncoding` (`<prefix>_<kind>.<len(scope)>.<scope>`, kind restricted to `[a-z0-9-]+`), injective by construction and property-tested; the value does not repeat the kind. The entry is `TaskEntry(enabled, overrides?)`; `overrides == null` is "Using default" and follows `TaskDefaults` stored at `task_default_<kind>` (a distinct key family, so the UI default row never collides with the app-wide scope `""`). No DB table, so no `MigrationRunner` or SQLDelight regeneration. Decode failure or exception means `enabled = false` (fail closed).
- The git interval moves into this store. `git_config.poll_interval_minutes` is read only as the fallback/migration seed on first read of an absent key and retained, unmodified, for one release (rollback).
- Migration of `scheduled_sync_enabled` (revised, repair loop 1): lazy and platform-neutral inside `TaskSettingsStore.read`, through an injected `LegacyConfigSeed` (git implements it), so Desktop, the cold worker, `resume`, composition and tests all migrate through one path; `GitSyncScheduleController.ensureMigrated` and `ScheduleStartup` (active graph only) call the same read eagerly. Runs once per graph on first read of an absent key with no marker. `enabled = legacy && graphHasRemote`. Stated semantics: the old global switch applied to every graph with a remote, so a never-composed remote-bearing graph turns on; this is covered by a named test. A graph's `hasRemote`/`poll_interval_minutes` live in its own SQLite `git_config`; the seed reads through a `GitLegacyConfigSource` interface in `git/` (Android implementation promotes the cold DB read that is a `private fun loadGitConfigFromDb` in `androidMain/.../git/WorkManagerSyncScheduler.kt`, NOT a `GitSyncWorker` member; Desktop/active-graph implementation reads the open graph's `GitConfigRepository`), opening a non-active graph's DB lazily, one at a time, never all graphs at startup. The source returns `Found(hasRemote, pollIntervalMinutes)` or `Unavailable`; "cannot read" (DB unopenable, not yet open, or a throw) is `Unavailable`, never "no remote", so no marker is written and the read is retried (writing `enabled=false` for an unreadable graph would permanently lose the user's sync). The seed is invoked only when both the entry and the marker are absent, so a cold worker for a graph with an existing entry opens no DB. A per-graph marker key `task_migrated_<kind>_<scope>` makes it idempotent and stops a downgrade-then-upgrade from re-applying a stale global flag. A read that throws writes nothing and resolves to disabled for that session (no marker, so it retries next start). New graphs default to disabled.
- Defaults (Phase 4 repair): `git-sync` new graphs get interval 60 and jitter `JitterPreset.ALittle.minutesFor(60)` = 6 (the `ux.md` default spread "A little"), network `Any`; a graph migrated from the legacy flag keeps jitter 0 and its legacy interval (behaviour-preserving). `model-download` (one-shot, app-wide) defaults to `Unmetered`. Charging off, battery-not-low off. `TaskOverrides.schedule` and `TaskDefaults.schedule` are nullable (null for one-shot kinds); `enabled` is periodic-only and ignored for one-shot kinds, whose workers take the network policy from the enqueue-time input key, not from the store.
- `TaskSettingsStore.readResult` returns `Ok`/`ReadFailed` so workers and the status line can tell "cannot read" from "disabled"; `read` stays fail-closed. A plain-prefs `SettingsReadHealth` records the last failure so the status can say "Can't read settings" instead of Late.
- Migration rationale (C8): `enabled = legacy && graphHasRemote` is kept because composition-driven scheduling previously enabled every remote-bearing graph whenever it was opened with the global switch on; the seed reproduces that without requiring the open. It is an owner-confirm item (a never-opened graph starts background work).
- Required tests: truth table over (legacy unset | true | read-throws) x (has remote | none) x (has new key | none) run through `TaskSettingsStore.read`; Desktop legacy-true first read is enabled; tombstone never migrates back; idempotent on second run.
- Evidence limit: Spike 0.1.2 exercises only the plain-prefs FALLBACK of `PlatformSettings` (Robolectric has no Keystore); production is `EncryptedSharedPreferences`. The Keystore cold-worker path is on the owner device checklist (Story 5.1.3).

## Consequences
Rollback to the previous build re-reads the untouched global flag. Graph removal must delete keys; because `Settings` has no `remove`, deletion writes a tombstone value that decodes to disabled and stops `reconcile` from re-enabling. Because `GraphId = sha256(path)`, re-adding the same path yields the same key: an explicit `write(key, entry)` supersedes the tombstone, and a re-added graph that the user has not touched starts disabled (it does not inherit the old entry and the seed is not called).

Resume precedence (rev3): a pause-time snapshot of the live work beats an enabled store entry, because the snapshot records what was actually running (including pre-upgrade jobs that never went through `apply`); an explicit disabled entry or tombstone still beats the snapshot. Do not flip this without re-running `WorkManagerSyncSchedulerPauseTest` and `UniqueWorkTest`. Failure ordering (Phase 4 repair): `pause` writes the process-static copy first, then the ledger snapshot (each guarded), and ALWAYS cancels afterwards; a snapshot failure must never block the clone's shared unique name, and `resume` falls back snapshot -> in-memory -> ledger (last applied) -> store, with startup `reapplyAll` as the final backstop. A user change during a pause (`apply` while a snapshot exists) updates the snapshot instead of enqueuing, so `resume` never restores a stale config.
