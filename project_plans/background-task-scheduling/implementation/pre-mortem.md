# Pre-mortem: background-task-scheduling
**Date**: 2026-11-10

Inputs read in full: `requirements.md`, `implementation/plan.md` (1154 lines). Claims below cite plan sections; none were run (planning-stage review).

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The second consumer never downloads. `TaskWorker` reads `TaskSettingsStore.read(model-download, "")` first (Task 2.2.2b: "read config ... fail closed ... existing entry short-circuits `enabled=false`"), and a key with no entry resolves to `enabled=false` (Story 1.1.4 "Defaults"; Risk Control "default off"). Nothing says `enabled` is ignored for a `OneShot` task, which is user-initiated and has no Settings toggle. The worker returns `Skipped("disabled")` -> `Result.success()`, so the model never downloads. Every `TaskWorkerTest` and `OneShotSkipTest` AC covers metered skips only. | First tap of "Download model" on a fresh install: `ModelState` stays `Downloading` or flips to done with no file; the run log shows `Skipped:disabled` for `model-download`. | Add an AC to Story 2.2.2 and a case in Task 2.2.2a: for `TaskShape.OneShot`, `doWork` never consults `enabled` (only `NetworkGate`, attempt cap, the hooks), and a test with NO store entry must run the body. Add to Story 3.2.1 an end-to-end Robolectric test: fresh `FakeSettings`, `runOnce` -> `TestDriver` -> asserts the file exists and `ModelState.Ready`. State in `TaskSpec` docs that `enabled` is periodic-only. | P1 |
| 2 | Git, the primary consumer, bypasses the new worker's gate and run log. Plan N2 keeps `GitSyncWorker` as a thin wrapper with "no registry lookup, no `enabled` gate, no store read, no `NetworkGate`", and only `runTaskWork` (TaskWorker) calls `TaskRunLog.append` (Observability Plan: TaskWorker and InProcessTaskScheduler are "the only writer"). Spike 0.1.1 may also show `UPDATE` does not change the worker class, so `git-sync` stays on `GitSyncWorker` permanently. Then Android background git runs write no run record, the Logs screen (Story 4.1.3, device check 5.1.3) shows nothing for git, and the `enabled`/live `NetworkGate` checks only apply if the job happens to be a `TaskWorker`. | Device verification: Logs screen has no `TaskRun ... git-sync` rows after a scheduled run; success metrics "Logs screen records every scheduled run" and "live-connection check" fail for git specifically; behaviour differs between upgraded and freshly enabled graphs. | Decide now, not after the spike: make `GitSyncWorker.doWork` append a `TaskRunRecord` (result, constraint state, scheduled-vs-actual) through the same `TaskRunLog` and Logger line via a shared `recordRun(...)` function that both workers call (no registry dependency, so `RetryOwnerTest` still holds; wrap in try/catch so a log failure never changes the Result). Add an AC to Story 3.1.2: a `GitSyncWorker` run produces exactly one run-log record for success, skip and failure. Add a test asserting `enabled=false` entry + live `GitSyncWorker` job -> `Skipped("disabled")` (or document why not). Make Spike 0.1.1's class-change outcome a hard gate on Story 3.1.2 and state in the plan which class `apply` enqueues for `git-sync` (it is ambiguous today: Stories 2.2.1 vs 2.2.3b). | P1 |
| 3 | The pause/resume snapshot mechanism loses or corrupts the schedule. `pause` does a blocking WorkManager read plus a Settings write (Keystore-backed `EncryptedSharedPreferences` in production) before `cancelUniqueWork`, then `resume` prefers the snapshot over the store unless the store says disabled. (a) If the snapshot read/write throws, the plan does not say whether the cancel still happens; skipping it blocks the clone, performing it loses the job with no snapshot. (b) A user who changes interval/network during a long clone or graph move is overwritten by the stale snapshot, and the composition `LaunchedEffect` keyed on `(key, config)` will not re-fire because the config is unchanged. (c) Resume for a pre-upgrade job relies on constraints/tags read back from `WorkInfo`, which Spike 0.1.1 has not confirmed are readable. | After a clone or graph move, `WorkManager` shows no `stelekit_git_sync_<id>` work, or it runs at the old interval/network policy; the status line goes Late a few hours later. | Specify failure ordering in Task 2.2.3b: snapshot errors are caught, logged, and the cancel still proceeds; `resume` then falls back to the store, then to the in-memory copy, and `reapplyAll` at startup is the backstop. For (b): `setSchedule`/`setNetwork` writes while a snapshot exists must update or clear the snapshot (add AC + test). Add a Robolectric test where `Settings` throws on write during `pause`. Gate (c) on Spike 0.1.1 results before writing 2.2.3b. | P2 |
| 4 | Fail-closed settings plus a cold, possibly locked or Keystore-broken process silently disable background work. `TaskWorker` (model-download, and any new git enqueue) reads `EncryptedSharedPreferences` in a cold process. On direct-boot/before-first-unlock devices, after backup/restore, or on OEMs with Keystore faults, the read throws, which the store converts to "disabled default" and the run log write also fails. Spike 0.1.2 can only exercise the plain-prefs fallback under Robolectric; the real Keystore check is owner-run in Story 5.1.3 after the code is written. | Background syncs stop on a subset of devices with no Logs entries (the log write fails too) and no Late state until 2x interval; users report "sync stopped after reboot". | Distinguish `ReadFailed` from `Disabled` in the store's return type (`TaskReadResult`); on `ReadFailed` the worker returns `Result.retry()` (bounded) and logs via `Logger`, never a silent success. Move the Keystore cold-worker check from 5.1.3 to an early owner checkpoint (right after Story 2.2.2) so a bad assumption is found before stories 3.x build on it. Persist the last read failure in a non-Keystore location (plain prefs) so the status line can show "Can't read settings" instead of Late. | P2 |
| 5 | The jitter and "unmetered" semantics in copy do not match what WorkManager does, and `UPDATE` may not apply them to existing users. Periodic flex makes the run happen in the LAST `flex` minutes of each period (it moves runs earlier, not later), `UPDATE` generally retains the existing next-run time so a changed `initialDelay`/offset does not move already-scheduled work, while Desktop jitter is `[interval, interval + jitter]`. The UI summary promises "Runs 60-66 min apart" and Story 1.1.2 promises `interval + offset` bounds uniformly. Devices still cluster at the old cadence after upgrade. | Support/QA observation: gaps between runs of 54-60 min on Android versus 60-66 on Desktop; the offset change does not take effect until the next period; fleet-level clustering remains. | Make Spike 0.1.1 produce the actual observed run-time distribution on the `TestDriver` (periodic period/flex semantics, not only read-back fields) and make Story 1.1.2 and the Story 4.1.1 copy derive from per-adapter `describe(key)` output (`minGapMinutes`, `maxGapMinutes`) instead of a global formula. Add the "existing job keeps its next-run time after UPDATE" outcome to the ADR-002 acceptance list and to the UI copy ("takes effect after the next run"). | P2 |

## Also considered (not in the top 5)
- Migration enables background sync for every remote-bearing graph when the legacy flag is on (documented in ADR-003); Story 3.1.4's `reapplyAll` is stated as ledger-based but fed by `KnownScopes x kinds`, which could trigger the lazy seed (graph DB opens) for every graph at startup. Clarify it reads the ledger only.
- Scale and sequencing: 105 tasks, an 8-step strictly serial root-file chain, several line-number citations in `WorkManagerSyncScheduler.kt` not re-verified, and an open git-sync PR stack; expect merge conflicts in Story 3.1.2.
- Desktop `InProcessTaskScheduler` ships constructed but unused by git; the contract suite is its only production-like proof.
