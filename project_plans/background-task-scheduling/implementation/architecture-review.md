## Blockers
- [ ] **Story 3.1.4 / Task 1.1.4d / ADR-003 (Desktop silently loses sync)** — The legacy `scheduled_sync_enabled` migration runs only from Android `Application.onCreate` (`ScheduleStartup`, Task 3.1.4b/c). Desktop uses the same global flag via `GraphContentGitSyncSetup`, and Story 3.1.3 makes Desktop read `TaskSettingsStore`. A Desktop user with sync on finds an absent per-graph key, which reads as the fail-closed default `enabled=false`, so sync turns off after upgrade. This breaks the stated "never silently flip" rule and the requirement that existing users' enabled state is migrated. Remediation: make migration lazy and platform-neutral. Add `GitSyncScheduleController.ensureMigrated(graphId)` (or a `readOrMigrate`) in commonMain that calls `LegacyGitSyncMigration.migrate` when the key and marker are absent, and call it from the Desktop root and the settings glue as well as Android startup. Add a Desktop test (legacy true + remote, new key absent, assert enabled after first controller read). Add Story 3.1.4 AC "Desktop migrates on first graph open".
- [ ] **Story 2.2.2 (unknown scope AC), Story 2.2.3 `ScheduledTaskReconciler`, Story 3.1.4 reconcile (orphan cancel can cancel live work)** — These cancel work whose scope is "not a known graph", but the plan never names the source of known graph ids or what happens when that source is empty or unreadable. The only persisted list is the `graph_registry` Settings string (`GraphManager.kt:273,416`), and `StelekitViewModel.kt:869` deliberately resets it to `""` on a load failure. Reconcile or a cold worker would then cancel every graph's sync (and `cancelAll` plus tombstone makes it durable), which is a silent, hard-to-diagnose outage. This is the exact failure mode the fail-closed rules exist to prevent, applied in the destructive direction. Remediation: specify a `KnownScopes` provider read from `graph_registry`; if the read throws, is empty, or the JSON fails to parse, reconcile and the worker self-cancel are no-ops (never cancel on "unknown"). Cancel only for scopes positively absent from a non-empty parsed registry, and never tombstone from reconcile (tombstone only from `GraphManager.removeGraph`). Add tests: empty registry cancels nothing, corrupt registry cancels nothing, worker for an unknown scope under an empty registry still runs. Add ADR-005 text for this rule.
- [ ] **Story 1.2.1 / 1.2.2 / 4.1.2 (false "Late" while the app syncs fine)** — `lastSuccessAtMs` comes from `TaskRunLog`, whose only writers are `TaskWorker` and `InProcessTaskScheduler` (Observability Plan). On Android with the app open, the foreground `PeriodicSyncDriver` loop (kept unchanged, Story 3.1.3) and "Sync now" succeed without touching `TaskRunLog`; they update `SyncStalenessStore` instead. A device where Doze or OEM limits defer the worker, but the user is syncing in the foreground, will show "Hasn't run in N h" when sync is healthy. That is the user-facing honesty metric in requirements (Observability), and the plan's separate timestamp is never fed by those paths. Remediation: define a neutral `LastSuccessSource` consumed by `ScheduleLateness`, with the git consumer supplying `max(TaskRunLog.lastSuccessAtMs, SyncStalenessStore last success)`; or have `GitSyncScheduleController` and the foreground driver append a success record on every successful tick. Add a Story 1.2.2/4.1.2 AC: foreground-only success within the window yields `OnTime`.

## Concerns
- [ ] **Story 3.1.3 / Task 3.1.3c (Desktop `PeriodicSyncDriver` replacement)** — `research/architecture.md` section 5.8 recommended leaving the driver in place (Option A) as lower blast radius; the plan instead moves Desktop git onto `InProcessTaskScheduler`, replacing a tested hotspot (backoff, pause-after-3-failures, edit lock, "next in" status) with no requirement-listed gain, and carries two jitter implementations. Recommendation: make ADR-001's fallback (keep the driver on Desktop, fed by the same settings; `InProcessTaskScheduler` for non-git kinds) the default for this release, and promote the switch to a follow-up once the status-line parity test passes.
- [ ] **Story 1.1.1 / `TaskConfig` (illegal states)** — `TaskConfig.shape: TaskShape` admits `OneShot`, but `apply` is periodic-only (`runOnce` is the one-shot entry) and `enabled`/`lateMultiple` mean nothing for one-shots; `Schedule(Int, Int)` allows negatives until clamped. Recommendation: `apply` takes `PeriodicTaskConfig` (or `TaskConfig` holds a `Schedule` directly with `OneShot` only in `TaskSpec`); validate `Schedule` in an `init`/factory (non-negative, jitter bounded) so only the codec boundary and `clamp` handle raw numbers.
- [ ] **Task 1.1.4c / ADR-003 (settings key ambiguity)** — Key `task_config_<kind>_<scope>` is not provably injective: `TaskKind` ids can contain `_`, and scopes are arbitrary graph ids (the plan only tests `workName()` injectivity). The codec also embeds `kind` inside the value. Recommendation: validate `TaskKind` ids against `[a-z0-9-]+` at construction, add an injectivity property over (kind, scope) for settings keys and run-log keys, and drop `kind` from the value or assert it equals the key's.
- [ ] **Story 2.2.2 (cold-process network signal)** — The gate needs live `online`/`isMetered` in a cold WorkManager process, but the plan only says "live `NetworkMonitor.isMetered`". `AndroidNetworkMonitor` construction in the worker is unspecified, and the existing LFS path reads `ConnectivityManager` separately (`AndroidGitRepository.kt:85-93`). Recommendation: add a task naming the `NetworkSnapshotProvider` the worker uses (single implementation over `ConnectivityManager`, also used by LFS), with a test where the provider throws (skip as `UnknownNetwork`, never proceed).
- [ ] **Port signature, Task 2.2.1d / Story 3.2.1 (`runOnce` replace semantics)** — The port lists `runOnce(key, constraints)` but "Download now anyway" needs REPLACE while the default is KEEP, and the shim criterion shows `apply(key, enabled, Periodic, constraints)`, a different signature from `apply(key, config)`. Recommendation: fix the port in Task 1.1.1c: `runOnce(key, constraints, onConflict: OneShotConflict = Keep|Replace)`, and align contract-suite and shim wording to the final signature. Also note `describe(key)` used by the contract suite is not on the port; define it as a test-only adapter hook.
- [ ] **Story 2.2.3 Task 2.2.3d / `GraphManager.removeGraph`** — `GraphManager.kt` is 1663 lines and not in the Tech Debt Disposition table, though the plan adds another responsibility to it. `removeGraph` has early returns (not found, demo graph, last-real-graph rules), so the callback must fire only on the success path or it will tombstone a graph that was not removed. Recommendation: add a disposition row (Extend as-is, narrow callback only) and place the hook after all guards; add a test that a refused removal does not call `cancelAll`/tombstone.
- [ ] **Story 2.1.2 / Task 2.1.2b (Noop default in `StelekitAppDependencies`)** — The existing factory field deliberately has no default so every host names its value explicitly (`BackgroundSyncScheduler.kt` KDoc). A defaulted `NoopTaskScheduler()` reverses that convention, and a host that forgets to wire the real adapter compiles and silently does nothing, with `WiringCompletenessTest` satisfied by the default's own construction. Recommendation: no default; have each root (Android, Desktop, wasm, iOS) pass its adapter explicitly, and put the new fields in `StelekitAppPlatformIntegrations` where the factory lives rather than the 347-line top-level class.
- [ ] **Story 3.1.2 / Task 3.1.2c (legacy `GitSyncWorker` inputs)** — In-flight requests carry only `KEY_GRAPH_ID` and `KEY_INTERVAL_MINUTES` and no kind or tag. The redirect must derive `TaskKey(git-sync, graphId)` from legacy input data and read config from the store (not the stale input interval). Recommendation: state this in the task and test the stale-input-interval case in `LegacyWorkUpgradeTest`.
- [ ] **Story 3.2.2 (LFS gate shape)** — `NetworkGate.evaluate(policy, online, isMetered)` needs `online`, which LFS does not have; "equivalent to `Skip(MeteredNetwork)`" assumes `online=true`. Recommendation: expose a `NetworkGate.evaluateMetered(policy, isMetered)` helper (or pass `online = true` explicitly in the test and code) so the LFS mapping is explicit rather than a coincidence.
- [ ] **Sequencing, Dependency Visualization** — Stories 2.1.2b (W5) and 2.2.3d (W6) both edit `StelekitAppDependencies.kt`/`MainActivity.kt` and are marked parallel with each other and with 3.1.1; only 3.1.2 to 3.1.3 is serialized. Add 2.1.2b and 2.2.3d to the serialized-file list.

- Plan `Spot-checks` says line numbers for `WorkManagerSyncScheduler` were not re-verified; this review confirms `schedule`/`workNameFor`/`pauseFor`/`resumeFor`, `NetworkType.CONNECTED` and `UPDATE` match the plan's description, and `PeriodicSyncDriver.kt:245` `intervalMs()` is the single seam as claimed.

## New concerns

- [ ] **Task 1.1.4d / ADR-003 (`GitLegacyConfigSource` is unspecified and the cited reader is Android-private)** — The plan and ADR-003 say the seed uses "the existing `GitSyncWorker.loadGitConfigFromDb`". In the worktree that function is a `private fun` in androidMain `WorkManagerSyncScheduler.kt:210`; commonMain `LegacyGitSyncMigration` cannot call it, and no task defines `GitLegacyConfigSource` or its Desktop implementation (the plan's Files lists omit it). The Desktop AC passes only because the fixture injects a `configRepo`. Remediation: add a task defining `GitLegacyConfigSource` in `git/` commonMain with two implementations (Android: promote the cold DB read to an internal function; Desktop/active graph: over the open graph's `GitConfigRepository`). Contract: "cannot read" (DB unopenable, not yet open) must THROW or return an explicit `Unavailable`, never "no remote", otherwise the seed would write the marker with `enabled=false` and permanently lose the user's sync. Add a test for that distinction and fix the ADR-003 wording.
- [ ] **Task 2.2.3d / `GraphManager.removeGraph` (callback shape)** — `removeGraph` is non-suspend, while the callback must run `cancelAll` and `tombstone`, and `TaskSettingsStore.write`/`tombstone` are `suspend`. A `(GraphId) -> Unit` callback forces a fire-and-forget launch with no named scope or `CoroutineExceptionHandler`, so a failure or process death leaves an enabled entry with no cancel. Remediation: specify that the root's callback launches on a root-owned guarded scope (or make the callback `suspend` with `removeGraph` unchanged by launching inside the root), and rely on startup `reconcile` (Known-only) as the backstop for a missed cancel; add a test that a throwing callback does not fail `removeGraph` or change its return value.
- [ ] **Story 1.1.4 tombstone vs re-adding a graph** — `GraphId = sha256(path)`, so re-adding the same path after removal yields the same `TaskKey`. The tombstone "decodes to disabled and the seed is never called", but the plan never says `write(key, entry)` supersedes a tombstone. If it does not, the user cannot enable sync on a re-added graph. Remediation: state and test that an explicit `write` replaces the tombstone, and that a re-added graph starts disabled (default for new graphs) rather than inheriting the old entry.
- [ ] **Story 2.2.2 `runTaskWork` / `GitSyncWorker` shim (settings read in a cold worker)** — Order is registry -> `KnownScopes` -> `TaskSettingsStore.read` (lazy seed, which may open that graph's DB) -> hooks. A cold worker for a non-active graph therefore opens a graph DB on first run per graph before the network gate, bypassing the cheap skip. Remediation: run the network gate and `enabled`-from-entry short circuit first when an entry exists, and call the seed only when entry and marker are both absent (already the store behaviour; state it in 2.2.2b), plus a worker test that an existing entry never calls the seed.
- [ ] **Sequencing note carried over (prior concern 9, partly addressed)** — The serialization chain now covers 2.1.2b -> 2.2.3d -> 3.1.1c -> 3.1.2c -> 3.1.3c -> 3.2.1d, but Task 3.1.4c (`SteleKitApplication.kt`) is only noted "serialized after 2.2.2c/3.1.1c", and Task 3.1.3e edits both wired-app fixtures that 2.1.2b already changes. Add 3.1.3e and 3.1.4c to the serialized-file list.
