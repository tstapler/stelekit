# Adversarial Review: background-task-scheduling

**Date**: 2026-11-10
**Verdict**: BLOCKED

Method: every file path, test name, line reference and protocol claim the plan leans on was opened in this worktree. Findings below cite the file that contradicts the plan. Counts verified: 27 stories, 90 tasks, 3,170k raw tokens, 4,980k CU in the effort table (all match the plan's own totals).

## Blockers

- [ ] **B1. The plan's test-run commands and BUILD edits cannot run or register the new tests.** The Bazel test targets are curated suites, not globs.
  - `kmp/src/androidUnitTest/kotlin/dev/stapler/stelekit/AllAndroidUnitTests.kt` is an explicit `@Suite.SuiteClasses` list of about 50 of the 152 test files. It contains **none** of `WorkManagerSyncScheduler{Pause,RetryOwner,SlowPathYield,UniqueWork,Watchdog}Test`, `GitSyncSchedulingEntryPointTest` or `WorkManagerJobRegistryTest`. Plan Tasks 0.1.1c, 3.1.2b and 5.1.1d tell the agent to run `bazel test //kmp/src/androidUnitTest/kotlin:android_unit_tests --config=android` and paste the result. That command never executes the Spike 0.1.1 test (the gate for ADR-002), the "six existing test classes" baseline, or any new Robolectric test. It produces green output that proves nothing. The androidUnitTest `BUILD.bazel` is a `glob`, so the plan's per-story "add to `kmp/src/androidUnitTest/kotlin/BUILD.bazel`" edits are no-ops, and the real registration step is absent.
  - `kmp/src/businessTest/kotlin/dev/stapler/stelekit/AllBusinessTestsCompletenessTest.kt` fails CI when a businessTest `*Test` class is not in `AllBusinessTests`. Story 1.1.5's `JobsScheduleImportDirectionTest` and every other new businessTest class (including any added by 5.1.1) will fail that guard unless registered. The plan never mentions `AllBusinessTests`.
  - Every new pure test is placed in `commonTest` and added to `kmp/src/commonTest/kotlin/BUILD.bazel`. Under Bazel, commonTest tests run only via `business_common_tests`, and only if they are also registered in `AllBusinessTests`. The `common_test_fixtures` target that the plan's spot-check treats as the place to add them carries a warning in its own comment: adding `@Test` classes there leaks them into other targets' completeness guards.
  - **Recommendation**: rewrite the verification steps to use `./gradlew :kmp:testDebugUnitTest --tests '<fqcn>'` for Android/Robolectric (CI runs this; CLAUDE.md lists it). Add an explicit task per story: register new businessTest and `business_common_tests` classes in `AllBusinessTests`. Decide per test whether Bazel android coverage is wanted, and if so add it to `AllAndroidUnitTests`. Create a new android-flavoured fixture target for the contract suite, because `android_unit_test_lib` only depends on `git_testsupport_android`, `fake_file_system_android` and `observable_effect_android`.

- [ ] **B2. Story 3.1.3 silently breaks three existing entry-point tests, and the legacy migration trigger is inconsistent between ADR-003 and the plan.**
  - `GitSyncSchedulingEntryPointTest` (androidUnitTest/git) drives `rememberGraphContentScheduledSyncControls(wired.deps, null, configRepo, graphId)` with only `SCHEDULED_SYNC_ENABLED_KEY=true` in `FakeSettings`. It asserts one periodic job at 15 min (from `pollIntervalMinutes=5`), `controls.closedAppChecks`, `controls.minimumIntervalMinutes`, and cancel on `controls.setEnabled(false)`. `GitSyncStackEntryPointTest` and `ScheduledSyncOriginE2ETest` (jvmTest/wiring) also key off the global flag.
  - Story 3.1.3/3.1.3b moves the composable onto a `GitSyncScheduleController` that reads `TaskSettingsStore`, where an absent key means disabled. With only the flag set and no store entry, these tests enqueue nothing.
  - Story 3.1.2's AC says the tests stay green "unchanged", but 3.1.3's file list never mentions them. The `ScheduledSyncControls` shape (global `enabled`/`setEnabled(Boolean)`, no graph) is also what `ScheduledSyncSection` and `ScheduledSyncSettingsTest` consume.
  - ADR-003 says migration runs "once per graph on first read of an absent key". The plan runs it at Android app start (Story 3.1.4) and never on the composition or Desktop path. Desktop has no startup hook, so the legacy flag would never be migrated there.
  - **Recommendation**: pick one trigger. Run migration lazily inside `TaskSettingsStore.read` through the injected `GitLegacyConfigSource`, so every path (composition, cold worker, Desktop, tests) shares it. Also call it eagerly in `ScheduleStartup`. Add an explicit task in 3.1.3 to update or extend the three tests and the `ScheduledSyncControls` consumers, stating which assertions change and why.

- [ ] **B3. A store-driven `resume` breaks the existing `WorkManagerSyncSchedulerPauseTest` and strands unmigrated graphs.**
  - `resumeFor_should_RescheduleThePeriodicJob_When_SwitchGraphCompletes` calls `WorkManagerSyncScheduler(context, "g1").schedule(15)`, then `pauseFor`, then `resumeFor`, and expects an enqueued job. Plan Stories 2.2.3b and 3.1.2 make `resume` re-read `TaskSettingsStore`. The shim's `schedule(interval)` is specified (3.1.2 AC) as an `apply(...)` call and nothing says it persists a config. The store therefore holds no entry (disabled), `resume` enqueues nothing, and the test fails. The plan states this test is green "unchanged".
  - The same hole hits real users: `resumeFor` is a static `Context`-only function called from `GraphMoveQuiesceStrategy.android.kt` and `AndroidGitCloneWorkerLauncher`. For any graph that is legacy-enabled but not yet migrated, the post-clone restore re-enqueues nothing, so background sync is silently lost.
  - **Recommendation**: define precisely what `resume` restores. Either `apply` persists the last-applied config (store write or a tiny "last applied" record) so `pause`/`resume` is self-contained, or `resume` falls back to the legacy-seeded read from B2. Add the existing Pause test scenario to the new contract suite as an explicit invariant (schedule, pause, resume with no store entry).

- [ ] **B4. `TaskRegistry` is populated from two places and `register` throws on duplicates.**
  - Story 1.1.1 requires `register` for an existing kind to throw `IllegalStateException`. Task 2.2.2c populates the registry in `Application.onCreate` (needed for the cold worker). Tasks 3.1.1c and 3.2.1d also say to register in `MainActivity.kt` (the "Android root") and `Application.onCreate`. `MainActivity` runs on every Activity creation (rotation, process restore). Registering in both places, or twice in `MainActivity`, crashes the app at launch or on the second Activity.
  - **Recommendation**: state that Android registration happens only in `SteleKitApplication.onCreate` (inside the `Throwable` guard), and drop the `MainActivity` registration from 3.1.1c and 3.2.1d. Add a regression test that constructing both roots in sequence does not throw. Consider making `register` idempotent for an identical spec.

- [ ] **B5. A gate `Skipped` maps to `Result.success()` even for one-shot work, which loses the model download and hangs its waiter.**
  - Story 2.2.2's AC returns `Result.success()` for every skip. For `model-download` (`runOnce`, `KEEP`, unique name `UNIQUE_WORK_NAME`) that marks the work SUCCEEDED with no download done.
  - `DepthModelDownloader.downloadModel()` then waits in `awaitTerminal()` for `Ready | Failed | Absent`, and a skipped success leaves state `Downloading`, so the caller hangs.
  - Skips are reachable even with the WorkManager `UNMETERED` constraint satisfied: `AndroidNetworkMonitor.isMetered` returns `null` on `SecurityException` (`AndroidNetworkMonitor.kt:69-74`), and `NetworkGate` treats `null` as `Skip(UnknownNetwork)` for `Unmetered`. The model would never download and no retry would be scheduled.
  - Periodic work is fine, because the next period retries. One-shot is not.
  - **Recommendation**: for one-shot tasks, map `Skipped` to `Result.retry()` (bounded by the spec's attempt cap and backoff), or to a terminal `Failed` that updates `ModelState` so the waiter resolves. Add `TaskWorkerTest` cases for a one-shot skip and for `isMetered == null` with the constraint satisfied. Decide explicitly whether `null` should fail closed once WorkManager has already verified `UNMETERED`.

## Concerns

- [ ] **C1. Desktop loop replacement is riskier than the plan admits (Story 3.1.3).** The plan swaps `PeriodicSyncDriver` out on Desktop for `InProcessTaskScheduler` and only checks the "next in ~12 min" line. The driver also owns the pause-after-3-failures state (`PAUSE_AFTER_FAILURES`), `immediateFirstTick`, `tickInFlight`, busy and offline skips, a restart on a manual `Success`, and the `ScheduledSyncStatus` fields `scheduledSyncLine` renders (`Paused`, `CheckInProgress`, `Checked`, `FetchedOnly`). None has a counterpart in the new adapter's spec. Since the ADR-001 fallback (keep the driver on Desktop) already satisfies "Desktop adapter exists behind the port", decide now to keep the driver for git and use `InProcessTaskScheduler` for non-git kinds. Revisit when a second Desktop task exists.
- [ ] **C2. The contract suite is not adapter-agnostic.** Story 1.1.6 asserts `Schedule(5,0)` clamps to 15 with `clamped=true`, and that a one-shot records network `Unmetered`. Story 2.1.1 requires the same suite to pass on `InProcessTaskScheduler` with `minIntervalMinutes=1` and `supportsUnmetered=false`. Both cannot hold. Parameterize the suite by `capabilities` (assert the clamp relative to `capabilities.minIntervalMinutes`; assert the unmetered one-shot only when supported). Also define `describe(key)` and the status read API on the port, or document them as test-only; the UI's "effective value" and the Desktop status line need a read path the port currently lacks.
- [ ] **C3. Legacy migration semantics.**
  - The ADR-003 rule `enabled = legacy && graphHasRemote` turns background sync **on** for every remote-bearing graph, including graphs that never had a WorkManager job (only composed graphs were scheduled, per `rememberGraphContentScheduledSyncControls`). The plan's "never flips a graph off to on" test is written against the migration's own truth table, so it cannot catch this. State the intended semantics and cover them with a test.
  - `hasRemote` and `poll_interval_minutes` live in each graph's SQLite `git_config` table. The only existing cold read is `GitSyncWorker.loadGitConfigFromDb`, which opens that graph's DB driver. A startup migration over tens of graphs opens that many databases in `Application.onCreate` while the active graph's DB is also opening. `GitLegacyConfigSource` is never specified for this path.
- [ ] **C4. Reconcile and worker self-cancel have no fail-closed guard and no known-graphs provider.** `GraphManager.loadRegistry` resets to an empty `GraphRegistry()` and persists it on a corrupt registry. A `reconcile(knownScopes = {})` would then cancel every graph's work. Refuse to cancel when the registry is empty or failed to load, and cancel only scopes explicitly absent from a non-empty registry. Task 2.2.2's "scope not a known graph, worker cancels itself" has no stated source for the graph list in androidMain (`graphManager` lives in `androidApp`'s `SteleKitApplication`). Add an injected provider with the same guard.
- [ ] **C5. Work-name injectivity (Story 1.1.1a).** The generated-input property asserts `workName()` is injective, but ADR-005 joins `kind` and `scope` with `_`. Kind `a`/scope `b_c` and kind `a_b`/scope `c` both yield `stelekit_task_a_b_c`. A scope that is itself a 16-hex string collides with a hashed scope. Restrict `TaskKind` to `[a-z0-9-]` in its constructor (`require`), always hash non-trivial scopes, or length-prefix the scope.
- [ ] **C6. `GitSyncTask` cannot preserve all current `GitSyncWorker` behaviour from commonMain.** `GitSyncWorker.doWork` also runs `checkAndSurfaceStuckGitCloneWorker` (the watchdog), `notifyUpdatesWaiting` (`SyncNotifier`) and the `isGitCloneWorkerRunningFor` slow-path yield. All are androidMain. Story 3.1.1 mentions only the cold-path fetch via a `ColdPathRunner`. Specify where the watchdog, notification and yield live (an androidMain pre/post hook on `TaskSpec` or in the worker), or `WorkManagerSyncSchedulerWatchdogTest` and `SlowPathYieldTest` pass while the production behaviour is lost.
- [ ] **C7. The `GitSyncWorker` compatibility shim is under-specified.** The class is `final` Kotlin, so "a thin subclass/redirect to `TaskWorker`" does not compile without making `TaskWorker` open. The existing tests build it directly (`TestListenableWorkerBuilder<GitSyncWorker>`, `workerClassName == GitSyncWorker::class.java.name`, `GitSyncWorker.KEY_GRAPH_ID`). In-flight rows carry only `graph_id` and `interval_minutes` input, no kind or scope. Specify the key-to-`TaskKey` mapping. Add a spike case that `UPDATE` changes `workerClassName` from `GitSyncWorker` to `TaskWorker` (plan puts this in 3.1.2d, after the design is committed) and that `UPDATE` on a currently RUNNING periodic work behaves.
- [ ] **C8. Jobs-list noise contradicts its own acceptance criterion.** Story 2.2.1 requires every request to carry `stelekit-job` (`JobTags.ANY`). `WorkManagerJobRegistry` maps `ENQUEUED` to `Queued`, so each enabled graph shows a permanent "Queued" Git sync row. The plan lists this as an unresolved question owned by Task 2.2.1e, yet the AC asserts the tag unconditionally. Resolve before 2.2.1 (periodic: scheduling tags only; one-shot: job tags).
- [ ] **C9. LFS change touches files the plan does not list.** `LfsRepositorySupport.kt:45` (`isMetered: () -> Boolean = { false }`) and `:144` (`deferOnMetered && isMetered()`) are in `jvmCommonMain`, shared with Desktop, plus `LfsTransferPolicyTest.kt:81` (`it.isMetered = { metered }`). Making the signal nullable and fail-closed changes Desktop behaviour (the JVM monitor always returns `null`, so `deferOnMetered=true` users would never download LFS objects). Add these files, decide the Desktop semantics, and gate on `lfsMeteredDetectionSupported`.
- [ ] **C10. The "Noop default" contradicts a deliberate design.** `BackgroundSyncScheduler.kt` documents that every host names its value explicitly (no default), and the field lives in `StelekitAppPlatformIntegrations`, not `StelekitAppDependencies`. A default `NoopTaskScheduler()` silently hides a host that forgot to pass a scheduler. Follow the existing no-default pattern with an explicit `NoopTaskScheduler()` at each host (iOS, wasm, jvm `App.kt`, test fixtures).
- [ ] **C11. Spike 0.1.2 cannot validate what it claims.** `PlatformSettings` on Android is `EncryptedSharedPreferences` (Keystore) with a plain-prefs fallback. Under Robolectric the Keystore path is unavailable, so the round-trip tests the fallback, not production. It also requires `SteleKitContext.init`, which the AC's "no UI init" omits. Run-log writes from a cold worker through EncryptedSharedPreferences are also a cost nobody measured. Mark the spike's evidence as fallback-only and put the Keystore path on the owner device checklist (5.1.3).
- [ ] **C12. Scope drift and coupling to watch.** The plan changes the model-download default from `CONNECTED` to `UNMETERED`, adds a "Download now anyway" UI action, adds an LFS fail-closed behaviour change and a graph-removal callback in `GraphManager` (`db`). The first two are product behaviour changes with no requirement-level owner decision recorded beyond ADR-004. Confirm each with the owner, or defer them.

## New and remaining blockers

- [ ] **N1. The `AppliedConfigLedger` resume cannot work in the existing tests that motivated it, and `UniqueWorkTest` is newly broken.** (B3 residual)
  - `PlatformSettings` on Android is `actual class PlatformSettings` over `SteleKitContext.context`. Without `SteleKitContext.init`, the `prefs` lazy initializer throws inside `getString`/`putString`, and both wrap everything in `catch (e: Exception)` and return the default or no-op (`kmp/src/androidMain/.../platform/PlatformSettings.android.kt`). `WorkManagerSyncSchedulerPauseTest` never calls `SteleKitContext.init` (grep of `androidUnitTest/.../git/` is empty). Plan Story 3.1.2 builds the shim's ledger from `PlatformSettings()`. In that test the ledger write silently does nothing, `resumeFor` reads an empty ledger and an empty store, fails closed, and enqueues nothing. `resumeFor_should_RescheduleThePeriodicJob_When_SwitchGraphCompletes` fails, contrary to the plan's "green unchanged".
  - `WorkManagerSyncSchedulerUniqueWorkTest.launchClone over an existing periodic job ...restores the periodic job` enqueues the periodic request directly through `WorkManager` (`PeriodicWorkRequestBuilder<GitSyncWorker>` plus `enqueueUniquePeriodicWork`). No shim, no ledger, no store entry, no legacy flag. `AndroidGitCloneWorkerLauncher.launchClone` sets `resumePeriodic` from "any unfinished work exists under the name" (`AndroidGitCloneWorkerLauncher.kt:84-91`) and then calls `resumeFor` in `finally`. With ledger and store both empty, the plan's `resume` "enqueues nothing and does not throw", so the assertion `infos.any { !it.state.isFinished }` fails. The same hole applies in production to any periodic job enqueued by the pre-upgrade build that has not yet been migrated or re-applied, which is exactly the "stranded graph" case B3 raised.
  - Plan Story 2.2.3's "unmigrated graph" case only works when the legacy flag is on and the graph has a remote. It does not cover work that exists in WorkManager with no store, ledger or flag.
  - **Recommendation**: make `pause` snapshot what it cancels. Before `cancelUniqueWork`, read the live `WorkInfo` (`periodicityInfo.repeatIntervalMillis`, constraints, tags) and write it to the ledger; `resume` then restores from the ledger snapshot, falling back to the store only when no snapshot exists. That covers the Pause test, the UniqueWork test, pre-upgrade jobs and a clone launched on a job the user enabled before upgrade, with no dependency on the settings store. Independently, `resumeFor` and the shim must call `SteleKitContext.init(context)` before constructing `PlatformSettings()` (idempotent), or the ledger must take an explicit `Settings`. Add both existing test scenarios to Story 1.1.6 as named contract invariants with a `Settings` that is guaranteed live.

- [ ] **N2. `GitSyncWorker` delegating to `runTaskWork` breaks `WorkManagerSyncSchedulerRetryOwnerTest` and any test that builds the worker directly.** (new, from the B1/C7 redesign)
  - `RetryOwnerTest` builds the worker with `TestListenableWorkerBuilder<GitSyncWorker>(context).setInputData(workDataOf(KEY_GRAPH_ID to graphId))`, registers a service in `GitSyncServiceRegistry`, and asserts `assertIs<Result.Failure>` when the fetch returns `RetryExhausted`. It registers nothing in a `TaskRegistry`, writes no store entry and does not init `SteleKitContext`.
  - Plan Story 2.2.2 says `runTaskWork` first resolves the registry and, when the registry is empty, returns `Result.success()` with `Skipped("task-not-registered")`. The registry is populated only in `SteleKitApplication.onCreate`, which Robolectric tests do not run. Result: the test gets `Success`, not `Failure`. The same applies to the second `RetryOwnerTest` case. If `runTaskWork` also gates on the store's `enabled` (default disabled with no legacy flag) or on `NetworkGate`, it skips even when a registry is present. The old worker has no `enabled` check or network gate (WorkManager's constraint is the gate), so adding them to this path changes behaviour as well as test results.
  - **Recommendation**: keep `GitSyncWorker.doWork` as the thin wrapper it is today, calling the extracted `GitSyncTask` functions directly (fast path, slow path, `Throwable` guard) with no registry lookup, no `enabled` gate and no store read. Reserve `TaskWorker` and `runTaskWork` for new enqueues. If you want a shared body, give `runTaskWork` an explicit `RegistryLess` overload that takes the `BackgroundTask` directly. Add `RetryOwnerTest` with an empty registry to the Story 3.1.2 acceptance criteria.

## Concerns (new)

- [ ] **R-C1. Desktop acceptance criteria contradict each other (Story 3.1.3).** One AC says the glue "invokes `BackgroundTaskScheduler.apply` once", another says `InProcessTaskScheduler.describe(git-sync/g1)` is null so there is no double tick. On Desktop the explicit `backgroundTaskScheduler` is `InProcessTaskScheduler` and Task 3.1.1c registers `git-sync` in `Main.kt`, so the glue's `apply` would start a second loop beside `PeriodicSyncDriver`. State the rule: the controller calls `apply` only when `capabilities.runsInBackgroundWhenClosed` (Android), and drop the Desktop `git-sync` registration, since nothing runs it in-process this release. The planned `TaskSchedulerDesktopEntryPointTest` no-double-tick case would catch it, but the spec should say it.
- [ ] **R-C2. "Edit the fixture only" is under-specified (Story 3.1.3e).** The test-local `configRepo` is created after the fixture and passed only to the composable. The seed for the composition path therefore has to be built inside `rememberGraphContentScheduledSyncControls` from its `configRepo` parameter and `deps.platformSettings`, not in `WiredAppFixture`. Say so, otherwise the fixture cannot supply a seed that sees the test's remote and `pollIntervalMinutes=5`.
- [ ] **R-C3. `assumeTrue` is not available in `commonTest`.** The contract suite and fake live in `commonTest` (all KMP targets, including wasmJs) and Story 1.1.6 uses `assumeTrue(capabilities.x)`. That is `org.junit.Assume`; `kotlin.test` has no equivalent. The repo has a recurring "JVM-only API in commonTest" failure (see MEMORY: wasmJs test compile history). Use an early `return` guarded by the capability.
- [ ] **R-C4. Every androidUnitTest file compiles into the Bazel library regardless of registration.** `android_unit_test_lib` globs `**/*.kt` and has no `kotest-property` or other `commonTest`-only deps. A new androidUnitTest test that uses `Arb`/`checkAll` (or any dep not in that list) breaks the Bazel Android build even though it is deliberately not in `AllAndroidUnitTests`. Add a rule: androidUnitTest tests use plain `kotlin.test`, or the plan adds the dep to the library.
- [ ] **R-C5. `onTerminalFailure` setting `ModelState` is the wrong mechanism (Story 2.2.2/3.2.1).** `ModelState` is derived from the `WorkInfo` flow (`DepthModelDownloader.kt:57,99-124`); a cold worker has no downloader instance. Have the terminal `Result.failure(workDataOf(KEY_ERROR to "..."))` carry the error in output data and let the existing collector produce `Failed(reason)`. Drop the callback or make it log-only.
- [ ] **R-C6. `CANCEL_AND_REENQUEUE` detection is ambiguous (Story 2.2.3b).** "State is not an ENQUEUED/RUNNING periodic" also matches a RUNNING one-time clone worker holding the shared name. Restrict `CANCEL_AND_REENQUEUE` to `resume` (after the clone's `finally`) and have `apply` and startup `reapplyAll` use `UPDATE` only and skip when a non-periodic work holds the name.
- [ ] **R-C7. Ledger-first resume can resurrect disabled work.** If the store was disabled by a path that bypasses `apply` (tombstone from a failed removal path, a store write whose `apply` threw), a stale ledger entry re-enables it. Make `resume` check the store first when an explicit entry or tombstone exists, and use the ledger snapshot only when the store has no entry (this also fits N1's pause snapshot).
- [ ] **R-C8. `workName` property test vs raw git-sync scope (Story 1.1.1a).** The property asserts `workName()` only contains `[A-Za-z0-9_-]` over generated scopes, but git-sync keeps the raw graph id (`stelekit_git_sync_<id>`), so a generated scope with a space or `/` fails. ## New concerns

- [ ] **C2-1. The worker class and constraints used by a snapshot-restored job decide whether `UniqueWorkTest` passes, and the plan leaves them open.** In that test the periodic job has `setInitialDelay(1h)` and no constraints, and the test's `WorkerFactory` returns `null` for any class other than `GitSyncWorker` and `GitCloneWorker`. A snapshot holds interval, flex, constraints and tags, not the initial delay. If `resume` enqueues the restored job without a delay and without a network constraint, a `SynchronousExecutor` driver runs it at once. If the class is `TaskWorker`, the factory returns `null` and the work can end FAILED, so `infos.any { !it.state.isFinished }` could fail. If the class is `GitSyncWorker` (the stand-in succeeds), a periodic job re-enqueues as ENQUEUED and the test passes. Spike 0.1.1 is what decides the class, and it is a W1 spike whose outcome is recorded after the plan is committed. **Recommendation**: state in Task 2.2.3b that `resume` for `git-sync` enqueues `GitSyncWorker` unless Spike 0.1.1 proves `UPDATE` changes `workerClassName`, and add that case to Task 2.2.3a as an explicit assertion using the test's own factory. Also state whether the snapshot preserves the initial delay or applies the default constraints from the store when the snapshot has none.
- [ ] **C2-2. Plan Story 3.1.2 says the worker "ignores `interval_minutes` (the body never used it)". That is false.** `WorkManagerSyncScheduler.kt:140` reads `KEY_INTERVAL_MINUTES` and `:149` passes it to `notifyUpdatesWaiting(graphId, staleness, intervalMinutes)`. A wrapper that drops it changes the notification threshold. **Recommendation**: correct the AC; the wrapper keeps reading the key with the same 15-minute default, and new enqueues from the adapter must keep setting it (the effective interval), or the wrapper reads the stored schedule when the key is absent. - [ ] **C2-3. `pause` is now a blocking read with several unstated rules.** `pauseFor` is non-suspend (`WorkManagerSyncScheduler.kt:96`), and `GraphMoveQuiesceStrategy.android.kt:67,89` calls it through a plain `(String) -> Unit` lambda, so a `getWorkInfosForUniqueWork(...).get()` runs on whatever thread the quiesce runs on.
