Findings from the inventory:
- VERIFIED: there are two independent consumers of "unmetered" semantics already (LFS `deferOnMetered`, asset `CloudNetwork`) plus the hard-coded CONNECTED constraint in both git sync and model download. A shared `NetworkPolicy` is a consolidation, not a new concept.
- VERIFIED: `isMetered` is `Boolean?` with null on JVM; null must map to "unknown", and the policy decides fail-open or fail-closed per requirement (recommend: Unmetered-only + unknown => skip with reason, consistent with the repo's fail-closed rule).
- VERIFIED: the GitSyncWorker slow path constructs a throwaway `InMemorySettings`/`PlatformSettings` and does fetch-only, so per-run outcome logging in a closed-app run must go through persisted storage (Settings/log file), not in-memory state.
- INFERRED: `PeriodicSyncDriver` wall-clock `nextAtMs` can mis-display after a clock change; `delay` is monotonic but `nextAtMs` is wall-clock.

## 2. Second consumer candidates (entry points)

1. `DepthModelDownloader.downloadModel()` -> `DepthModelDownloadWorker` (DepthModelDownloader.kt:66-92). Best fit for proving the port: already a standalone WorkManager worker, already tagged `JobKind.ModelDownload`, has constraints (network + storage-not-low) and backoff, no git types. Gap: it is one-time and user-initiated, not periodic, so the port needs a `OneTime`/`Deferred` schedule shape in addition to `Periodic`. Wi-Fi-only maps to replacing `NetworkType.CONNECTED` (:76) with the policy. Existing test: androidUnitTest/.../platform/ml/DepthModelDownloadWorkerTest.kt.
2. LFS transfer: entry is `GitSyncService.kt:103` -> `setLfsTransferContext` -> `AndroidGitRepository.lfs.policy/isMetered` (:87-94). LFS is NOT scheduled work; it is a step inside a sync that consults `deferOnMetered`. Making it a port consumer would require extracting a deferred "LFS catch-up" task (INFERRED design cost: higher, touches git internals and the first-sync/edit-lock semantics requirements say to leave alone).
Recommendation (INFERRED): use model download as the proven second consumer; treat LFS as the consumer of the shared `NetworkPolicy` value (its `deferOnMetered` toggle collapses into the per-task policy), and leave LFS-as-scheduled-task as a follow-up.

## 3. Comparable apps (all INFERRED, recall only; verify before citing)

- Syncthing-Android: separate toggles "Run on mobile data", "Run on Wi-Fi", "Run on metered Wi-Fi", "Respect Android's Battery Saver", "Run only when charging", plus a per-Wi-Fi-SSID allow-list and time-of-day schedule; a persistent notification and status in-app; run conditions evaluated continuously (stop/start), not as polling. Takeaway: users expect network class and charging as independent switches and a visible "why not running" state.
- Nextcloud Android auto-upload: "Upload only on Wi-Fi", "only when charging", "only on unmetered"; per-folder rather than global settings. Takeaway: per-target rules.
- Obsidian Git (plugin): auto-pull/auto-push intervals in minutes, "pull on startup", status bar with last-sync time; mobile caveat documented: no background execution, runs only while open. Takeaway: users read the status bar as the truth; honest "runs only while the app is open" copy is accepted.
- Termux:Tasker / termux-job-scheduler: expose Android JobScheduler options directly (network type, charging, idle, period). Takeaway: power users want raw constraints; a generic port with constraints maps cleanly.
- Android conventions: labels "Wi-Fi only" are common but technically `UNMETERED`; "Only when charging" = `setRequiresCharging`; "Battery not low" is the default WorkManager-friendly option; Settings > Battery > "Unrestricted/Optimized/Restricted" is where OEM/standby is user-controlled.
- iOS Background App Refresh: system decides timing, no guarantee, user can disable globally and per app; BGAppRefreshTask gives ~30 s. Takeaway: "about every X" framing and a "last ran" line, never an exact promise. Out of scope here (iOS git is a stub) but copy should not promise exactness on any platform.

## 4. Edge cases and failure modes the design must handle

Platform timing (INFERRED unless noted):
- Doze / App Standby buckets: periodic work is deferred to maintenance windows; bucket (Active/Working/Frequent/Rare/Restricted) stretches runs to hours. Restricted bucket is already probed (VERIFIED WorkManagerSyncScheduler.kt:300-301). UI copy must show "approx every X, may run later".
- OEM killers (Xiaomi, Huawei, Samsung "sleeping apps"): can drop periodic work entirely; no API fix; product answer is visibility (requirements say so). Needs a "last successful run" timestamp independent of "behind" count (see staleness gap above).
- 15-min floor and flex: values below 15 clamp (VERIFIED :49); UI must disable and explain (factory `minimumIntervalMinutes` already does this, VERIFIED BackgroundSyncScheduler.kt:24).
- Jitter semantics: `PeriodicWorkRequest` has only flex (last portion of the period), no random delay. Options: (a) random `initialDelay` once at enqueue (spreads devices at install time, cheap, but cadence stays fixed after); (b) flex window as controlled early-run band; (c) chained OneTime work with random delay per run (true per-run jitter, but loses periodic-work guarantees, needs re-enqueue on boot/update and interacts with `UniqueWorkTest` invariants). Define jitter as "additive offset in [0, jitter], never earlier than the interval, never pushing the period past the max"; property test as requirements state. Jitter must be seeded from a per-install/per-graph value or a random source injected for tests.
- Thundering herd: many graphs enqueued at app start all fire in the same window; per-(graph,kind) random initial delay or stagger index; also WorkManager `UPDATE` on every app start must not reset the timer (INFERRED: UPDATE preserves schedule when unchanged, verify in test; `resumeFor` deliberately uses CANCEL_AND_REENQUEUE, VERIFIED :107-109, which does reset it).
- Clock changes / time zone / DST: use elapsed-time or WorkManager's own scheduling; avoid computing "late" from wall-clock deltas without a sanity bound (backwards clock => negative age; far-forward => false "behind"). `stalenessChipState` uses wall-clock `nowMs` (VERIFIED :12).

Network:
- Metered vs Wi-Fi: `UNMETERED` is not "Wi-Fi" (hotspot Wi-Fi may be metered, some cellular plans unmetered); copy must say "unmetered". The live check in the run must agree with the constraint because constraint and live state can diverge (network changed after the job started). VERIFIED the live check exists only for LFS (AndroidGitRepository.kt:90) and not in `ScheduledSyncInputs`.
- VPN: `isActiveNetworkMetered` reflects the underlying network under VPN in most cases but `NET_CAPABILITY_NOT_VPN` handling and VPN-over-cellular reports vary (INFERRED); the unknown (`null`) case needs a defined policy.
- Captive portals: `NET_CAPABILITY_VALIDATED` is already required for `isOnline` (VERIFIED AndroidNetworkMonitor.kt:62-66), so a portal reads offline => Skip(Offline). WorkManager's CONNECTED constraint does NOT check validation (INFERRED), so a worker can start behind a portal; the in-run `online` check is the real guard. Offline skip must not count toward failure backoff (verify existing behaviour: policy returns Skip(Offline), backoff counts failures only, VERIFIED ScheduledSyncPolicy.kt:56).
- Desktop: `isMetered` is always null (VERIFIED JvmNetworkMonitor.kt:32). Unmetered-only on desktop must degrade with a visible reason or be disabled; recommend disabled-with-reason, matching the repo's "disabled with a reason, not hidden" pattern (CLAUDE.md cross-graph section).

State and migration:
- Migration from global `scheduled_sync_enabled`: a user who has it true must end up with every existing git-configured graph enabled; false/absent => all off. Failure modes: new graphs added after migration inherit what? (recommend: off, with first-sync-confirmed gate still protecting); migration must be idempotent and run once (marker key) and keep the old key read-only one release (requirements). Settings read failures stay fail-closed (VERIFIED ScheduledSyncPreferences.kt:29-33).
- Graph removed while scheduled: `cancelUniqueWork` for every (graph, kind) name; also clear staleness key `git_sync_staleness_<graphId>` and per-graph settings; the worker must handle a missing config/graph by returning success-no-op and cancelling itself (VERIFIED worker returns `Result.failure()` when graph id missing, :133; slow path loads config from DB :210). Orphan unique-work names after uninstall-of-graph by a crash are the hazard; reconcile on startup (enumerate WorkManager work by prefix vs. registered graphs).
- Graph moved: existing `pauseFor`/`resumeFor` hooks (VERIFIED :96-109) must be generalized to all kinds of that graph and keep their ordering (pause before move, resume after).
- Unique-name collision: clone uses the same name as sync (VERIFIED launcher :38-41); new scheme `stelekit_<kind>_<graphId>` must keep the clone/sync exclusion intentionally, or replace it with explicit dependency. Old names cancelled only after the new request is confirmed enqueued (requirement; read back via `WorkManager.getWorkInfosForUniqueWork`).
- Per-run persistence: run log must survive process death; the closed-app path writes to Settings via a throwaway `PlatformSettings` (VERIFIED :178-181), so the run record should use the same store or the file log sink, via `Logger` (requirement).
- Boot/app-update: WorkManager reschedules after reboot; on app update persisted periodic work remains, but changed request params need explicit `UPDATE` (INFERRED).

## 5. Users' unstated needs

- Status: one line per graph and task: last success time, next expected window ("about 14:30, may be later"), and if not running, why (disabled, vault locked, offline, restricted background, waiting for Wi-Fi). Today skip reasons exist as enum (VERIFIED ScheduledSkipReason) but there is no persisted history of skips beyond `lastSkip` in the in-memory driver status (VERIFIED PeriodicSyncDriver.kt:214).
- "Sync now": already available as manual sync (GitSyncCoordinator); the schedule UI should link to it and show that manual runs reset "last run". INFERRED expectation.
- Last-run visibility when the app was closed: the user opens the app and wants to know "did it run overnight?". Needs the run log (requirement) plus staleness that is not gated on `behind > 0` (current gap, VERIFIED SyncStalenessPresentation.kt:16).
- Battery: charging-only / battery-not-low as opt-ins; default off for charging (Syncthing users split on it) with "battery not low" cheap to include. A restricted-background hint exists (VERIFIED probe) but links to settings are not provided; INFERRED value: add an action to the OS battery settings.
- Data cost: model download and LFS are the big transfers; a "Wi-Fi only for large downloads" default distinct from git fetch defaults (INFERRED: default unmetered-only for ModelDownload/LFS, any-network for small git fetch).
- Predictability and trust: "off" must truly cancel the work, and a visible count of active schedules avoids surprise background activity; cap per-graph rows in UI (requirements flag this).
- Notifications: avoid new noise; the existing updates-waiting notification (SyncNotifier) is the only one for sync (INFERRED from file list); model download keeps its foreground notification.

## 6. Open questions answered or sharpened

- Persistence: Settings key-value is sufficient (existing pattern: staleness store, LFS policy) and avoids the `MigrationRunner` and generated-SQLDelight obligations; a table is only justified if run history must be queried. INFERRED recommendation: key-value for settings, capped history string like `SyncStalenessStore` (history cap VERIFIED :25) for run log.
- Desktop unmetered: no JVM signal (VERIFIED null); do not try to approximate.
- Second consumer: model download (section 2).
- Charging/battery-not-low: include in v1 value type, expose network policy first in UI (matches requirements default).
