## 0. Baseline facts the design inherits (VERIFIED)

- `schedule()` clamps to a 15-minute floor, hard-codes `NetworkType.CONNECTED`, builds a `PeriodicWorkRequest` with no flex and no initial delay, and enqueues with `UPDATE` (`WMSS:44-70`). Unique name is `stelekit_git_sync_<graphId>` (`WMSS:83`).
- The same unique name is **shared with the clone worker** (`WMSS:81-83` comment; `AndroidGitCloneWorkerLauncher.kt:183`). `WorkManagerSyncSchedulerUniqueWorkTest.kt:120-135` and `:165` record the bug: a one-time clone chained behind a periodic job via `APPEND_OR_REPLACE` sits `BLOCKED` forever, so the launcher pauses the periodic job, runs the clone, then restores it.
- `resumeFor` re-enqueues at 15 minutes (not the user's interval) with `CANCEL_AND_REENQUEUE` (`WMSS:107-110`), explicitly "a safety net, `GitSyncService` re-applies the real interval later".
- Scheduling is driven from **composition**: `LaunchedEffect(scheduler, active, interval, loaded)` calls `scheduler.schedule(interval)` or `cancel()` (`kmp/src/commonMain/.../ui/GraphContentGitSyncSetup.kt:236-239`). Nothing schedules unless that graph's content screen is composed.
- Only three `cancelUniqueWork` call sites exist in androidMain (`WMSS:73,97`, `AndroidGitCloneWorkerLauncher.kt:183`); none is on a graph-removal path (grep, VERIFIED). See P-Orphan.
- `GitSyncWorker` returns `Result.failure()`, never `retry()`, after internal retries (`WMSS:150-158,196-199`); `WorkManagerSyncSchedulerRetryOwnerTest.kt:123-124,206-207` pins this (ADR-002 "one retry owner").
- No `Configuration.Provider` and no `WorkManager.initialize` in main sources (grep over `kmp/src`, `androidApp`; only `WorkManagerSyncSchedulerPauseTest.kt:45` calls `initialize`). The app uses WorkManager's default androidx.startup initializer. `AndroidManifest.xml:81-85` declares `SystemForegroundService` with the `dataSync` type for the clone worker.
- `Settings` has no `remove` (`kmp/src/commonMain/.../platform/Settings.kt:7-18`): only get/put/containsKey.

## 1. WorkManager periodic-work gotchas

### P1. `UPDATE` vs `CANCEL_AND_REENQUEUE` (INFERRED, high impact)
- `UPDATE` (WorkManager 2.8+) keeps the same work id and, per the docs, preserves the existing run schedule while swapping constraints/interval/input; it is the right default for a re-applied setting. `CANCEL_AND_REENQUEUE` resets the schedule (a new period starts now) and is what the repo uses after a clone because "UPDATE can't convert the finished one-time work back into a periodic job" (`WMSS:46-47`; test `UniqueWorkTest:133`).
- Hazard A: the composition-driven `LaunchedEffect` (VERIFIED above) re-fires on every key change and every app open. With `CANCEL_AND_REENQUEUE` the schedule would reset each open (a user who opens the app hourly never gets a background run); with `UPDATE` it is safe. Keep `UPDATE` for settings edits; reserve `CANCEL_AND_REENQUEUE` for the unique-name type-change case only.
- Hazard B: if jitter is implemented as a per-enqueue random initial delay, every `UPDATE` re-roll could shift the schedule. Roll jitter once per *settings change*, and derive it deterministically (see P9), not per app open.
- Hazard C: the unique name must keep a stable *work type* (periodic vs one-time). Reusing the name for chained one-time jitter work (P3) would break `UPDATE` semantics and the clone-pause protocol above. GAP: confirm in a Robolectric spike that `UPDATE` with a changed `flexInterval` or `initialDelay` behaves as documented (the existing tests never change interval across an `UPDATE`; `grep` of the five WorkManagerSyncScheduler tests shows no such case).

### P2. 15-minute floor, flex window (INFERRED)
- `PeriodicWorkRequest` minimum repeat is 15 min (`PeriodicWorkRequest.MIN_PERIODIC_INTERVAL_MILLIS`), minimum flex 5 min; the flex window is the **last** `flex` ms of each period, and a flex >= interval is ignored. The builder silently clamps rather than throwing for sub-minimum values, so a "10 min" setting would run at 15 with no error. Keep the clamp in a pure function and surface it to the UI (`BackgroundSyncSchedulerFactory.minimumIntervalMinutes` already exists, `kmp/src/commonMain/.../git/BackgroundSyncScheduler.kt:20-33`, VERIFIED) rather than clamping silently in the adapter.
- Jitter via the flex window means "run somewhere in the final `flex` of the period", not a random offset; it also shortens the guaranteed-wait the system can use to batch the job. Requirement metric "offsets stay within `[0, jitter]` and never push past platform interval bounds" must be written against whichever mechanism is chosen (P3).

### P3. Jitter on WorkManager: three mechanisms, each with a trap (INFERRED + repo VERIFIED)
1. **Flex window**: native, keeps one periodic request, but only de-correlates *within* the last `flex`; the position inside it is OS-chosen, so it is not testable as "offset within `[0, jitter]`" (the test driver does not model it). Jitter <= period - 5 min.
2. **Random initial delay on the periodic request**: `setInitialDelay` applies only to the first run; later periods follow the period, so jitter would be applied once and then stay fixed (acceptable for de-correlating *devices*, not within one device). On `UPDATE` the initial delay is not re-applied to an already-running chain (INFERRED, P1 GAP).
3. **Chained self re-enqueue one-time work** (each run enqueues the next with `delay = interval + jitter`): true per-run jitter, but loses periodic semantics: needs `ExistingWorkPolicy` choice, a crash/kill between run and re-enqueue silently ends the chain (data loss of the schedule), and it collides with the clone-pause protocol that depends on the shared name being periodic (see baseline and P1-Hazard C). Needs a watchdog: the "behind" staleness state is the only repair signal.
- Recommendation (INFERRED, planning to confirm): periodic + flex for per-run spread, plus a deterministic per-(graph,kind) initial-delay offset derived from a stable hash for cross-device spread. Avoid chained one-time work unless a spike shows flex is too coarse.

### P4. Initial delay on update / app-open re-enqueue (INFERRED, partly VERIFIED)
- A periodic request with no initial delay is eligible immediately: the first `enqueue` after enable runs a sync within seconds (subject to constraints). That is also true for the existing code (`WMSS:55-63`, no delay) so first enable currently triggers an immediate background run; `GraphContentGitSyncSetup.kt:225-227` separately runs an in-process "immediate first tick", so enable may produce two near-simultaneous fetches (one in-process, one WorkManager). Per-graph `NamedLocks`/busy skip should absorb it (`ScheduledSyncPolicy.decide` `i.busy` first, `ScheduledSyncPolicy.kt:60-62`), but add a test.
- Do not give `UPDATE` a new initial delay on every app open expecting it to postpone the next run; see P1.

### P5. Work lost after app-data clear / force-stop (INFERRED)
- Clearing app data wipes WorkManager's database: every unique work name is gone, and the app's own settings go with it, so state is consistent (nothing to restore). **Force-stop** cancels pending alarms/jobs on many OS versions and WorkManager only re-arms when the app process is next started by the user (on API < 31 a boot/package-replaced receiver re-registers jobs, but a force-stopped app receives no broadcasts until user launch). Consequence: a user who force-stops (or whose OEM does, see P8) gets **no runs until the next manual open**; the schedule is re-applied by the composition `LaunchedEffect` (VERIFIED, `GraphContentGitSyncSetup.kt:236-239`) only once the graph screen composes. Mitigation = visibility (behind-state), not recovery. Also: an app update restarts the process and keeps work (WorkManager persists it); a cold boot does the same.
- Hazard: a self-heal on `Application.onCreate` that re-enqueues all enabled schedulers would fix the force-stop case without opening a graph, but must read settings fail-closed and must not run before `WorkManager` init (P6).

### P6. WorkManager initialization in Application and custom Configuration (INFERRED + VERIFIED)
- VERIFIED: default startup initializer; Robolectric never runs it, so tests must `WorkManager.initialize` manually, and the instance is a JVM-static singleton that survives per-test Applications (`WorkManagerSyncSchedulerPauseTest.kt:36-49`). Any new port test must copy that try/catch-on-`IllegalStateException` guard or it fails order-dependently.
- INFERRED: adding a custom `Configuration.Provider` (needed for a `WorkerFactory` that injects the port's task registry into workers) requires removing the default `WorkManagerInitializer` from the manifest (`tools:node="remove"`), else the app crashes at startup with "WorkManager is already initialized". Alternatively keep default init and have workers read from a static registry like `GitSyncServiceRegistry` (`WMSS:119-121`), which is existing precedent but is process-global mutable state (cold-start path then has nothing registered: the slow path exists exactly for this, `WMSS:162-201`).
- `WorkManagerJobRegistry` already guards `WorkManager.getInstance` against "not initialised" (`kmp/src/androidMain/.../jobs/WorkManagerJobRegistry.kt:58-62`, VERIFIED); new adapter code should reuse that `workManagerOrNull()` pattern, not call `getInstance` bare in composition.
- Android `Application.onCreate` must catch `Throwable` (CLAUDE.md, "Android Application.onCreate"; VERIFIED rule, `SteleKitApplication.kt:212-218` is the site). A self-heal re-enqueue added there needs the same guard.

### P7. Doze, standby buckets, expedited quota (INFERRED; probe VERIFIED)
- Periodic work is deferred in Doze to maintenance windows, and standby buckets throttle jobs (Rare ~ once per 24 h on the bucket's job quota; Restricted ~ once per day). A 15-minute setting is a request, not a guarantee. A rarely-opened note app is the exact case the git-integration research already names (`project_plans/git-integration/research/pitfalls.md:11-15`, VERIFIED).
- `AndroidBackgroundRestrictionProbe` reports battery saver, `isBackgroundRestricted`, or bucket >= RESTRICTED (45) and deliberately ignores Doze (`WMSS:280-303`, VERIFIED). It does **not** report the Rare/Frequent buckets, which are the commonly hit throttle; "no hint shown" must not be read as "runs on time". Also `appStandbyBucket` needs API 28; API < 28 has `usage == null` and returns "not restricted".
- Expedited work (`setExpedited`) has a per-bucket quota and requires a foreground-service-type on API < 31 and no Doze/battery-saver exemption. Use only for user-initiated "Sync now" with `OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST` (as git-integration pitfalls item 5 suggests, `pitfalls.md:33`); never for periodic work (periodic work cannot be expedited).
- Constraint: no exact alarms (out of scope in requirements), so there is no way to promise punctuality.

### P8. OEM battery killers (INFERRED: [dontkillmyapp.com](https://dontkillmyapp.com/); repo restates in `git-integration/research/pitfalls.md:17-21`, VERIFIED)
- Xiaomi (auto-start), Samsung (sleeping apps), Huawei, OnePlus, Oppo/Vivo can kill the process and clear WorkManager's scheduled jobs so periodic work simply stops with no exception. A killed-mid-run worker may never get `onStopped` (the repo already built a watchdog for the clone worker for this reason: `WMSS:305-325`, `GitSyncWorker.doWork` `WMSS:138`, VERIFIED). The sync worker has no equivalent; the "behind" state is the only detector.
- GAP: owner-run physical-device verification is a named blocker in requirements; the emulator `Pixel_Fold` has no OEM killer.

### P9. Android 14/15 (INFERRED)
- Android 14: `dataSync` foreground service has an execution-time cap, and starting a foreground service from the background can throw `ForegroundServiceStartNotAllowedException` (repo VERIFIED in `git-sync-resilience/research/pitfalls.md:274-306`). A *scheduled* (background-started) fetch must therefore not promote itself to foreground; only the user-launched clone may. The new port must not offer `setForeground` as a generic scheduled-task capability.
- Android 15 adds a stricter limit on `dataSync` FGS total runtime per 24 h; and "Restricted" bucket pressure grows for rarely-opened apps. Re-check the docs for the actual numbers before citing them in UI copy (not re-fetched).
- Android 14 also enforces `minSdk`/`targetSdk` exact-alarm permission changes: irrelevant here because AlarmManager is out of scope.

## 2. Jitter pitfalls

### P10. Non-determinism in tests; clock injection (INFERRED design, repo VERIFIED precedent)
- Existing code injects the clock as a lambda (`runSlowPathFetch(clock = { System.currentTimeMillis() })`, `WMSS:232`; `checkAndSurfaceStuckGitCloneWorker(nowMs = ...)`, `WMSS:366-370`) and the pure staleness/watchdog helpers are the tested units. The jitter function must be pure `(baseInterval, jitterWindow, seed/random: () -> Double) -> offset` so a commonTest property test can bound it.
- Do not use `kotlin.random.Random.Default` or `Math.random()` in the policy: it makes the property test unrepeatable. Take a `Random` seed parameter; seed from a stable hash of `(graphId, taskKind)` in production so a given (graph,kind) keeps the same offset across process restarts (no re-roll on every app open: see P1-Hazard B), and from a fixed seed in tests. Note: this also keeps the work request equal across idempotent `UPDATE`s, which makes "re-enqueue is a no-op" testable.
- WorkManager's test driver (`WorkManagerTestInitHelper`/`TestDriver.setInitialDelayMet`, `setPeriodDelayMet`) simulates delay completion; it does not simulate flex or Doze (INFERRED, [Testing WorkManager](https://developer.android.com/develop/background-work/background-tasks/testing/persistent/integration-testing)). Assert the enqueued request's `WorkSpec` fields (interval, flex, initial delay, constraints) read back from `getWorkInfosForUniqueWork`, as the requirements demand, not elapsed wall time.
- Existing precedent has no jitter anywhere (`git-sync-resilience/research/pitfalls.md:98-113`, VERIFIED); the backoff in `ScheduledSyncPolicy.backoffMs` is deterministic doubling (`ScheduledSyncPolicy.kt:75-80`, VERIFIED). Decide whether the new jitter also applies to the policy backoff; if so keep it separately seeded to keep existing `ScheduledSyncPolicy` tests green (requirements: "decisions unchanged").
- Jitter clamp: `interval + jitter` must not go below the 15-min floor or above any max the product defines; clamp in the pure function and property-test the boundaries (interval == 15, jitter == 0, jitter >= interval, negative inputs).

## 3. Network policy

### P11. `NetworkType.UNMETERED` is not "Wi-Fi" (INFERRED + repo VERIFIED)
- `UNMETERED` = `NET_CAPABILITY_NOT_METERED`. A metered Wi-Fi hotspot is metered; an unlimited cellular plan can be unmetered (some carriers flag it on API 30+). Copy must say "unmetered", as the requirements already state.
- Constraint vs live check disagree: the WorkManager constraint is evaluated by the OS before the worker starts, but the network can change in between, and the **worker's in-process check uses a different API**. VERIFIED: the repo reads `ConnectivityManager.isActiveNetworkMetered` in two places (`AndroidNetworkMonitor.kt:68-74`, `AndroidGitRepository.kt:90-93`), which reflects the *active* network, not the capability the constraint matched, and `AndroidNetworkMonitor.isMetered` returns `null` on `SecurityException` while `AndroidGitRepository` collapses a failed read to `false` (= unmetered). On a null/unknown read the Wi-Fi-only policy must **fail closed (skip)**, which is the opposite of the LFS path's `?: false` default (`AndroidGitRepository.kt:92`).
- `NetworkType.UNMETERED` also matches an ethernet/VPN-less offline state? No: it requires a connected network. Additionally `NetworkType.CONNECTED` currently implicit-includes validated-internet semantics through WorkManager's `NetworkRequest`; do not assume `isOnline` (`AndroidNetworkMonitor` requires `VALIDATED`, `:63-67`) equals the constraint: captive portals are connected but not validated.
- Add a pure policy rule "unmetered required and `isMetered != false` -> Skip(MeteredNetwork)" so Doze-delayed runs that wake on a different network are caught, and test it with a three-valued input (true/false/null).
- Desktop: JVM has no metered signal (requirements Open Question). Options: disable the unmetered option with a stated reason, or treat as "unknown -> skip" (fails closed: sync never runs, surprising). Prefer disabling the control with a reason (matches the CLAUDE.md "unwritable destinations are shown disabled with a reason" pattern, cited for cross-graph writes).
- Per-API: `NetworkType.METERED`, `TEMPORARILY_UNMETERED` (API 30), and `NOT_ROAMING` exist; do not map the policy "any/unmetered/off" to more than CONNECTED/UNMETERED/none. "Off" must mean *cancel the unique work*, not "enqueue with an impossible constraint".

## 4. Settings and migration

### P12. Silently enabling or disabling sync (VERIFIED mechanisms)
- `ScheduledSyncPreferences` reads `scheduled_sync_enabled` and **fails closed to `false`** on absent or throwing settings (`ScheduledSyncPreferences.kt:29-33`; tests `ScheduledSyncPreferencesTest`). Today's global `true` must become per-(graph, kind) `true` for every graph that has a git config; if migration runs before graph ids are known, or the read throws, the user's sync silently turns off (fail-closed makes an unreadable old key look like a deliberate off).
- The opposite hazard: new-default for a graph that never had the switch. Requirements say default-off per (graph, kind); migrating a global `true` to *all* graphs would enable background network activity on graphs the user never saw a sync prompt for (first-sync confirmation is a separate policy gate, `ScheduledSyncPolicy.kt:70`, VERIFIED, but a fetch-only tick still runs without it per `FetchOnly(AppClosed)`). Apply the old flag only to graphs that currently have a git config and are currently syncing.
- `Settings` has no `remove` (VERIFIED above) so "retain old key read-only for one release" works but the old key can never be deleted by this interface; a migration marker key must be written (`containsKey`) so migration is idempotent and a downgrade-then-upgrade does not re-apply a stale global flag over newer per-graph choices.
- Android `PlatformSettings` (`kmp/src/androidMain/.../platform/PlatformSettings.android.kt:19`) is SharedPreferences-backed (INFERRED from the class name; not opened). The worker slow path constructs a fresh `PlatformSettings()` (`WMSS:182`), so any per-graph key read must work without the app UI having initialized anything; test on the cold path.
- If settings move to a DB table: the mandatory `MigrationRunner.all` entry and committed SQLDelight regen rules apply (CLAUDE.md; VERIFIED text). The slow path opens the DB via `DriverFactory().createDriver(getDatabaseUrl(graphId))` per graph (`WMSS:210-219`), so a settings table that lives in a *per-graph* DB is readable by the worker but one in a *global* DB is a new access path; GAP decide before choosing.
- Rollback hazard: a reverted build still has the old worker name `stelekit_git_sync_<graphId>`. If the new build enqueues under new names and the old ones are cancelled "only after the new request is confirmed" (requirements Risk Control), a crash between the two leaves both or neither; ensure idempotent re-entry, and cancel old names via the existing `WorkManagerSyncScheduler.pauseFor`-style function, not a new one.

## 5. Per-graph unique-work explosion and orphans

### P-Orphan. Orphaned work after graph removal (INFERRED from VERIFIED absence)
- No `cancelUniqueWork` is called from `GraphManager.removeGraph` or its callers in androidMain (grep of `cancelUniqueWork`/`enqueueUniquePeriodicWork` call sites above, VERIFIED). Because scheduling is composition-driven (`GraphContentGitSyncSetup.kt:236-239`), removing a graph whose screen is no longer composed leaves its periodic job enqueued. Each run then starts `GitSyncWorker`, which finds no service and no git config (`runSlowPathFetch` returns `success()` on null config, `WMSS:235`) so it silently succeeds forever: a zombie that still wakes the process and consumes quota. It also shows up in `WorkManagerJobRegistry` only if tagged.
- Names grow as graphs x kinds. `workNameFor(graphId)` has no kind component; the second consumer (`DepthModelDownloader.UNIQUE_WORK_NAME`, `DepthModelDownloader.kt:87`, one-time, `ExistingWorkPolicy.KEEP`, `NetworkType.CONNECTED` + storage-not-low `:76-79`, VERIFIED) is global not per-graph. New names must be `stelekit_<kind>_<graphId>` and the legacy `stelekit_git_sync_<graphId>` must remain the git-sync name (pause/resume/launcher all key on it: `WMSS:97,107`; `AndroidGitCloneWorkerLauncher.kt:183`; `GraphMoveQuiesceStrategy.android.kt:52-89,163`, VERIFIED) until all three are migrated in the same change.
- `graphId` characters in a work name (INFERRED): WorkManager unique names are free-form strings, but graph ids derived from paths may contain spaces/`/`; stable-hash if needed. VERIFIED none of the existing tests use a non-trivial id (`"g1"`, `"unique-work-concurrency"`).
- Mitigation: a reconcile step ("cancel every unique work named `stelekit_*` whose graphId is not in the registry") run at startup, using `WorkManager.getWorkInfosByTag`. Requires tagging each request with a `stelekit.sched` tag + graph id tag. The `JobTags.ANY`/`kind`/`title` tags exist already (`WorkManagerJobRegistry.kt:18-35`; `DepthModelDownloader.kt:79-82`), so reuse them rather than inventing tags. Cap: tens of graphs x handful of kinds is fine for WorkManager; the UI-row count is the real limit (requirements Feasibility).
- Graph-move pause/resume re-enqueues at **15 min, not the configured interval** (`WMSS:107-110`); generalizing it per-kind multiplies this wrong-interval bug. The new `resume` must read the persisted per-(graph,kind) settings (fail-closed) rather than the hard-coded floor.

## 6. Coroutine scope and Throwable rules (CLAUDE.md, VERIFIED text)

- Any long-lived scope that hosts the Desktop in-process timer adapter must own its `CoroutineScope(SupervisorJob() + ...)` plus a `CoroutineExceptionHandler`; never accept a caller scope and never take `rememberCoroutineScope()` (CLAUDE.md "Coroutine scope ownership" and "Uncaught coroutine Throwables"). The existing in-process driver is `PeriodicSyncDriver` / `GitSyncService.startPeriodicSync`; the new Desktop adapter must follow the same ownership.
- A scheduled-tick lambda is a standing launch on that scope: wrap the body in `catch (e: Throwable)` that rethrows `CancellationException` and records a failed run, since `OutOfMemoryError` kills the process on Android though only prints on desktop JVM.
- `GitSyncWorker` catches `Exception`, not `Throwable` (`WMSS:153,196`), unlike `GitCloneWorker` which catches `Throwable` (`GitCloneWorker.kt:77`, VERIFIED). A `CoroutineWorker` that throws an `Error` is reported by WorkManager as failed (INFERRED), but the Android default uncaught handler would not run for the worker's own dispatcher threads; keep the new port's worker wrapper on `Throwable` like the clone worker to avoid a regression.
- Composition: the scheduler registration `LaunchedEffect` (`GraphContentGitSyncSetup.kt:236`) is acceptable (transient, cancellable); do not move long-lived timer state into it.
- Fail closed: a settings read exception must resolve to "no schedule", consistent with `ScheduledSyncPreferences.read` (`ScheduledSyncPreferences.kt:29-33`).

## 7. SAF graphs

- SAF graphs are `FetchOnly(Saf)` by policy (`ScheduledSyncPolicy.kt:69`; VERIFIED) and git operations use a shadow worktree; the cold fetch constructs an uninitialized `PlatformFileSystem()` deliberately because `fetch()` never touches the working tree (`WMSS:176-181`, VERIFIED). **Any generic task that does more than a fetch on a SAF graph in the background would hit the uninitialized filesystem**: the port's task contract must state which tasks are allowed to run in the cold path. Model download and LFS are file-writing: LFS transfer is guard-only on shadow-backed graphs (`AndroidGitRepository.kt:97-99`, VERIFIED), so a scheduled LFS transfer for a SAF graph must be a skip with a reason, not an attempted transfer.
- SAF permission can be revoked silently while work is enqueued; the periodic run must classify that as a skip-with-reason, not repeated `failure()` (INFERRED; repo has no existing test).

## 9. Observability pitfalls

- The cold worker process only has persisted logging if `installPersistentLogging()` ran: it is called in `Application.onCreate` (`SteleKitApplication.kt:217`, VERIFIED), which runs before any worker, so run records via `Logger` will reach `filesDir/logs/current.log`. Using `android.util.Log` would bypass it (CLAUDE.md). The owner cannot use `adb logcat`, so the run log must be written even when the policy skips.
- "Behind" detection must compare against *last successful* time, not last *attempt*, else a worker that wakes and skips every tick looks healthy. `SyncStalenessStore` is the existing store (`WMSS:183,190`); GAP: confirm its key set is per graph only, not per kind.
- The system may run a period late by hours in Doze/Rare bucket; a "behind" threshold too close to the interval (e.g. 1.5x) will false-alarm constantly on restricted devices. Use the configurable multiple from requirements with a default well above 2x (INFERRED; tune from device logs).

## 10. Top risks to take into planning (ranked)

1. **Shared unique-work name + type change** (P1-C, P3, baseline): any jitter or per-kind redesign that changes the work type under `stelekit_git_sync_<graphId>` breaks the clone-pause protocol and the move quiesce/resume hooks. Keep git-sync name and type stable.
2. **Silent settings migration** (P12): fail-closed read of the old flag + no `Settings.remove` can disable users' sync or enable new graphs; needs a one-time idempotent marker migration and tests for the three cases (unset, true with git config, read throws).
3. **Orphaned work and wrong-interval resume** (P-Orphan): a startup reconcile and settings-aware `resume` are required, not optional.
4. **Metered live check disagrees with the constraint** (P11): fail closed on `null`/unknown; the existing LFS `?: false` default is the wrong precedent for a Wi-Fi-only guarantee.
5. **Unprovable punctuality** (P5, P7, P8): success is a visible behind-state; schedule exactness cannot be tested in CI; physical OEM verification is an owner blocker.
