## 2. Android WorkManager (external)

- **Latest stable**: 2.12.0, 2026-09-23, minSdk raised 23 -> 24, requires compileSdk 33+ — https://developer.android.com/jetpack/androidx/release/work (page text reported by fetch tool; VERIFIED via fetch, not independently cross-checked). Repo is on 2.9.1 (two minors behind; minSdk 26 is compatible). `setNextScheduleTimeOverride` exists since 2.9.0 (same page) so it is available on the repo's current pin. Upgrade is optional for this project; a bump must keep runtime and `work-testing` identical (comment at `kmp/build.gradle.kts:377-378`).
- **Periodic minimum**: repeat interval >= 15 min (`MIN_PERIODIC_INTERVAL_MILLIS`); interval is a minimum between runs, actual time depends on constraints and system optimization — https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work (VERIFIED).
- **Flex window**: pass `flexInterval`; run window is `[repeat - flex, repeat]` of each period; flex must be >= `MIN_PERIODIC_FLEX_MILLIS` (same page, VERIFIED). The constant's value (5 min) is INFERRED from memory; confirm against API reference before coding a clamp. Flex is a late window at the end of each period, so it only ever makes runs later than the base period start; it is a bounded form of jitter but not random per device/run.
- **No native random jitter** (VERIFIED by absence in the guide; matches requirements.md rabbit hole). Options (design is for planning):
  1. Flex window only: deterministic-ish spread (system picks point in window). Smallest change; keeps unique periodic work and existing `UniqueWorkTest` invariants.
  2. Random `setInitialDelay` on enqueue: "only the first run of your periodic work would be delayed" (same page, VERIFIED) — so it phase-shifts the whole series once; spreads devices, not successive runs.
  3. `setNextScheduleTimeOverride` (2.9.0+) from inside the worker with a freshly randomised time, using `UPDATE` policy so the running worker is not cancelled (release notes, VERIFIED at the releases page above; exact method signature/semantics NOT read — check API reference, and Robolectric/test-driver support is INFERRED-unknown).
  4. Chained `OneTimeWorkRequest` re-enqueue with per-run random delay: full control and exact jitter property, but forfeits periodic-work semantics and needs its own self-healing if a chain breaks (INFERRED).
- **Network types**: `NetworkType.UNMETERED` is the documented "Wi-Fi" constraint but means "not metered", not Wi-Fi (guide table says "e.g., Wi-Fi (UNMETERED)", VERIFIED; the semantic gap vs. hotspots/unmetered cellular is INFERRED from platform docs). `CONNECTED` = any network. The Android adapter should map: Any -> CONNECTED, Unmetered -> UNMETERED, Off -> do not schedule/cancel. Also `setRequiresCharging`, `setRequiresBatteryNotLow`, `setRequiresDeviceIdle`, `setRequiresStorageNotLow` (all VERIFIED, same guide). All constraints are ANDed.
- **Constraints vs periodic**: an unmet constraint can delay or even skip a run for that period (VERIFIED, guide). A constraint turning unmet mid-run stops the worker and it retries later (VERIFIED). So charging-only on an unplugged phone yields silent gaps, which feeds the "behind" staleness UI.
- **Backoff**: `Result.retry()` + `setBackoffCriteria(policy, delay)`; min backoff 10 s, default EXPONENTIAL 30 s; delays inexact (VERIFIED, guide). Current git worker returns `failure()` by ADR-002, so the port needs a result type that distinguishes retry-worthy from terminal and the git adapter keeps "no WorkManager retry". For periodic work, a `failure()` does not cancel the periodic series (INFERRED from WorkManager behaviour; existing `RetryOwnerTest` should confirm).
- **Unique work**: `enqueueUniquePeriodicWork` with `UPDATE` replaces the definition without cancelling a running worker; `CANCEL_AND_REENQUEUE` is the older hard reset; `KEEP` leaves the existing one (UPDATE vs KEEP semantics INFERRED from API docs; repo's own usage at `WorkManagerSyncScheduler.kt:38-39` confirms UPDATE cannot convert finished one-time work to periodic). Names must stay bounded: `(graphId, taskKind)` -> e.g. `stelekit_<kind>_<graphId>`; git kind must keep the legacy name or migrate with cancel of the old one, because the clone launcher shares it (`:79-80`).
- **Tags/observation**: add `JobTags.ANY` + kind tag for registry visibility (`WorkManagerJobRegistry.kt:18-34`).
- **Testing**: `WorkManagerTestInitHelper.initializeTestWorkManager(context, config)` with `SynchronousExecutor` and `TestDriver` (`setPeriodDelayMet`, `setAllConstraintsMet`, `setInitialDelayMet`) — API per https://developer.android.com/develop/background-work/background-tasks/testing/persistent/integration-tests (INFERRED; page not fetched). Repo already uses the helper (`AndroidGitCloneWorkerLauncherTest.kt:68`). Reading the enqueued request back (success metric) is possible via `WorkManager.getWorkInfosForUniqueWork(...)` -> `WorkInfo.constraints`, `periodicityInfo` (2.9+ exposes `WorkInfo.periodicityInfo`/`nextScheduleTimeMillis`; INFERRED, verify). Robolectric's SQLite lacks fts5, so worker bodies that open the real DB cannot run in tests (`WorkManagerSyncScheduler.kt` doc above `runSlowPathFetch`, VERIFIED); keep worker decision logic in pure functions as the repo already does.
- **Doze / standby / OEM**: restricted-state probe already exists (`AndroidBackgroundRestrictionProbe`, `WorkManagerSyncScheduler.kt` near line 270); reuse for the hint. Product answer is visibility, not a fix (requirements.md).

## 3. Desktop / JVM

- In-process timer only while the app is open; `PeriodicSyncDriver` is commonMain and `delay`-based (see section 1). A port adapter can wrap it per (graph, kind) and replace `intervalMs()` with `base + jitter`. Needs the shared Throwable guard and `CoroutineExceptionHandler` per CLAUDE.md (driver takes caller's `scope`).
- **Metered signals on JVM**: none in the JDK (INFERRED; `java.net.NetworkInterface` has no metered flag). Repo already encodes this: `isMetered = null` on JVM (VERIFIED above). OS-specific options exist but are out of scope and unverified: Windows `NetworkCostType` WinRT API, macOS `NWPath.isExpensive`/Low Data Mode, Linux NetworkManager D-Bus `Metered` property (all INFERRED, none researched). Recommended: Unmetered policy on desktop is `Unknown` -> degrade per existing `cloudNetworkOf` convention ("proceeds") or disable with a reason in the UI; decision belongs to planning. The port's live check should take `Boolean?` and have a policy decision for null.
- No battery/charging signal in JVM either (INFERRED); charging-only should be reported unsupported on Desktop via adapter capabilities.

## 4. iOS (stub only)

- A stub adapter returning `NotSupported`/no-op satisfies the port; `IosGitRepository` is already a stub (VERIFIED). A real adapter would use `BGAppRefreshTask`/`BGProcessingTaskRequest` via `BGTaskScheduler` (earliestBeginDate only, no interval guarantee, identifiers must be declared in Info.plist `BGTaskSchedulerPermittedIdentifiers`) — INFERRED from Apple docs, not fetched; explicitly out of scope. Port capabilities should be queryable (e.g. supportsPeriodic, supportsUnmeteredConstraint, supportsCharging) so UI can disable options with a reason; this matches the repo's "disabled with a reason" pattern (TargetWriterCapabilities, CLAUDE.md).

## 5. Implications for planning

- Port in a neutral commonMain package; adapters: WorkManager (androidMain), `PeriodicSyncDriver`-backed (jvmMain or commonMain), no-op (iOS/web).
- Jitter choice is the main open design point; options 1 and 3 keep periodic semantics, option 2 is nearly free, option 4 gives the strongest property test. Clamp offsets so `interval + jitter` never undershoots 15 min or violates flex minimum.
- Metered live check inside the worker must use `NetworkMonitor.isMetered` (same source as the constraint, `isActiveNetworkMetered`); `null` must be handled explicitly (fail closed for Unmetered policy on Android; define per-platform on desktop).
- Existing tests constrain the migration: unique name sharing with the clone launcher, `failure()` not `retry()` for git, pause/resume.
- Unverified items to check before coding: `MIN_PERIODIC_FLEX_MILLIS` value, `setNextScheduleTimeOverride` signature and test-driver support, `WorkInfo.periodicityInfo`, whether a 2.9.1 -> 2.12.0 bump is needed.
