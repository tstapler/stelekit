# Validation Plan: web-credential-persistence

**Date**: 2026-09-21

## Happy Path Scenario

Given a returning web user whose browser `localStorage` holds a key generated by a prior session
(`CredentialStore.preload()` already ran once), when they save a new LLM provider API key via
`LlmProviderSettings` and reload the page, then `LlmCredentialStore(CredentialStore()).getApiKey(providerId)`
returns the original plaintext value after the reload — proving `store()` → AES-GCM encrypt →
`localStorage` persist → `preload()` → `retrieve()` round-trips correctly through the real
WebCrypto/`localStorage` boundary, not just an in-memory fake.

## Testability Gaps Found During Validation (must resolve before/while implementing Phase 2)

Two of plan.md's own Phase 1 tasks write logic as `private` or inline-lambda code with **no test
seam**, which would leave their acceptance criteria unverifiable by any automated test:

1. **Task 1.4.2a — `migrateLegacyGitCredential(graphId: String)`** is specified as `private suspend
   fun` in `Main.kt`. Kotlin `private` top-level declarations are file-scoped, so no test file
   (even in the same package) can call it directly. **Recommendation**: change its visibility to
   `internal` (no behavior change, matches this codebase's existing precedent of `internal fun
   shouldWarnOnUnload` in the same file, `Main.kt:83`) so `MainCredentialMigrationTest.kt` (row
   below) can call it directly instead of only being exercisable through the untestable `main()`
   entry point.
2. **Task 1.4.1a — the repointed token-resolution expression** (`config.httpsTokenKey?.let {
   CredentialStore().retrieve(it) } ?: PlatformFileSystem.githubToken ?: ""`) is written inline
   inside the `configResolver` lambda literal, duplicated across `main()` and
   `runEphemeralSession()`. Inline lambda bodies inside `main()` cannot be invoked from a test at
   all. **Recommendation**: extract it to `internal fun resolveGitHttpsToken(httpsTokenKey:
   String?): String` in `Main.kt`, called from both `configResolver` definitions — a one-line
   change beyond what Task 1.4.1a already specifies, mirroring `GitSetupScreen.kt`'s existing
   `resolveHttpsTokenKey`/`resolveOauthTokenKey` extraction pattern (tested directly today in
   `GitSetupScreenCredentialPersistenceTest.kt`).

Both rows below assume these two extractions exist. If Phase 5 implementation declines the
extractions, Story 1.4.1 and Task 1.4.2a's acceptance criteria become verified only by manual
reload testing, not by an automated `wasmJsTest` — that would be a real coverage gap, not a
simplification, and should be called out again at Phase 6 review if so.

## Test Stack
- **Unit**: `kotlin.test` (`@Test`, `assertEquals`/`assertTrue`) — for `wasmJsTest` files, in-memory-only assertions that don't require awaiting a background persist or touching real `localStorage`/`crypto.subtle`; for the Epic 1.5 copy check, `androidx.compose.ui.test` (`createComposeRule`, `onNodeWithText`) under `kmp/src/jvmTest`, matching `DemoBannerTest.kt`'s existing pattern.
- **Integration**: `kotlin.test` + `kotlinx-coroutines-test` (`runTest`) running under the real `wasmJs { browser() }` karma-headless-browser target (`./gradlew :kmp:wasmJsBrowserTest`) — exercises real `crypto.subtle`/`crypto.getRandomValues`/`localStorage`, not a fake. This is the only way to prove AES-GCM encryption actually happened and that a value survives a simulated reload.
- **Migration**: same harness as Integration (`wasmJsTest`, real `localStorage`) — called out as its own `Type` in the table above per this validation's Step 5 requirement, not a separate test framework.
- **E2E / UX**: N/A — no new interactive surface (Epic 1.5 is a copy-accuracy fix, covered as a unit-level Compose content assertion, not a Playwright/browser-driven flow).

## Shared Test Infrastructure Required (Task 2.1.1a)
- `CredentialStore.Companion.resetForTest()` — clears `decryptedCache`, `cryptoKey`, **and** the
  real `localStorage` entries it wrote (`stelekit_credential_key`, every `credential_enc.*` key).
  Required because the companion object is a process-wide singleton shared across
  `CredentialStoreTest.kt`, `GitCredentialConnectionStoreWasmJsTest.kt`,
  `LlmCredentialStoreWasmJsTest.kt`, and the two new `Main*Test.kt` files proposed above — all run
  in the same browser session/`localStorage` origin. Call in `@BeforeTest`/`@AfterTest` of every
  file in this table that touches `CredentialStore`.
- `CredentialStore.Companion.flushForTest()` — suspend function that joins all in-flight
  `persistCredential` background jobs, analogous to `PlatformFileSystem.flushPendingWrites()`.
  Required by every Integration-typed row above that asserts on `localStorage` state after a
  `store()` call.
