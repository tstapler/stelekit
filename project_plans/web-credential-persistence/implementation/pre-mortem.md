# Pre-mortem: web-credential-persistence
**Date**: 2026-09-21

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Task 1.2.2a says to "add `CredentialStore.preload()`" at a line in `main()`/`runEphemeralSession()` but never states it must be a directly-awaited suspend call on the boot coroutine — if implemented as `scope.launch { CredentialStore.preload() }` (or any other detached launch), every one of the ~10 ad hoc `CredentialStore()` call sites (`GraphManager.kt:190,564,720`; `App.kt:466,662,916,961,1003,1008`) plus `LlmProviderRegistryFactory`'s pre-paint build can run against a still-empty `decryptedCache`, silently returning `null` for real, previously-saved credentials. This is the adversarial review's own flagged remaining concern, and re-reading the current task text confirms it is still not spelled out as an explicit constraint. | Users intermittently see "unconfigured provider" flashes or a saved git connection failing to resolve a token, non-deterministically (worse under browser-extension-induced `localStorage` read latency) — not on every load, so it looks like a flaky bug rather than a structural race, and is hard to repro locally. | Add an explicit sentence to Task 1.2.2a: "`preload()` must be called as a direct, awaited `suspend` call inside `main()`'s own coroutine (e.g. `fun main() = MainScope().launch { CredentialStore.preload(); ...rest of boot... }`), never wrapped in a separate `scope.launch{}` detached from the boot sequence." Add a Phase 2 test that injects an artificially slow `preload()` (e.g. via a test hook) and asserts `configResolver`/registry builds do not observe an empty cache before it completes. | P1 |
| 2 | `store()`'s write-behind path (Task 1.3.1a) updates the in-memory cache synchronously but fire-and-forgets the WebCrypto encrypt + `localStorage` write via `scope.launch { persistCredential(...) }`. If the user closes the tab, navigates away, or the browser is killed between the UI's "saved" feedback and that coroutine completing, the write is silently lost with no user-visible error — a very plausible sequence for "paste PAT, hit save, close tab" or "paste LLM key, close settings tab." Nothing in the plan registers a `pagehide`/`beforeunload` best-effort flush; the only flush mechanism (`flushForTest()`, Task 2.1.1a) is test-only. | User re-opens the app later and finds the git connection or LLM key they "saved" is gone again, with no error ever having been shown — indistinguishable from the credential never having been entered. | Add a `window` `pagehide` (preferred over `beforeunload` for bfcache compatibility) listener in `CredentialStore`'s companion `init`/bootstrap that best-effort awaits/flushes in-flight persist jobs synchronously where possible, or at minimum document this as an explicit, named data-loss window in the Risk Control section (not silently absent) with a mitigation such as showing a "saving…" indicator that only clears after the background job completes. | P2 |
| 3 | `preload()`'s key bootstrap (Task 1.2.1b step 1) reads-or-generates `localStorage["stelekit_credential_key"]` with no concurrency guard. If two tabs/windows of the app are opened at the same time on a fresh browser profile (a common pattern for a Logseq-style multi-page note app), both can race through "key absent → generate via `randomBytes(32)` → write back" simultaneously; whichever tab's write lands second silently overwrites the first tab's key in `localStorage`. Any credential the first tab encrypts (or already had cached) under its now-orphaned key becomes permanently undecryptable on the next `preload()` in any tab. The codebase already has `WebLock.kt` for exactly this class of race (cited as the interop-layer idiom to mirror) but Epic 1.1/1.2 does not use it for key generation. | A previously-working git connection or LLM key suddenly fails to decrypt after the user had two tabs of the app open at once — `preload()`'s per-entry catch (Task 1.2.1b step 4) logs a decrypt failure and returns `null`, so it looks like silent, total credential loss for that entry with no error surfaced to the user. | Add explicit use of the Web Locks API (same primitive `WebLock.kt` already wraps) around the "read-or-generate-and-write" key bootstrap step in Task 1.2.1b, so concurrent `preload()` calls in different tabs serialize instead of racing. Add a test/manual-verification note for concurrent first-boot in two tabs. | P2 |
| 4 | Task 1.4.2a's `migrateLegacyGitCredential(graphId)` migrates the single **global** legacy `localStorage["githubToken"]` into a **per-graph** key (`git_https_token_$graphId`) keyed on whichever graph happens to boot first, using only "is the target key already non-null" as the check-before-write guard — it ignores that the legacy `githubOwner`/`githubRepo` keys already identify which repo/graph the token was actually for. A user with 2+ graphs who has a legacy plaintext token will have it silently attached to whichever graph boots first (clearing the legacy source in the process), leaving every other graph's git sync unmigrated with no error and no hint that a token existed for it. | A multi-graph user finds git sync works on one graph (unexpectedly, if that wasn't the graph they configured HTTPS_TOKEN auth for) and is silently unconfigured on another, with the legacy `localStorage["githubToken"]` already cleared so there is nothing left to inspect or retry. | Change Task 1.4.2a to use the legacy `githubOwner`/`githubRepo` values to disambiguate which graph the token belongs to (e.g. only migrate when the booting graph's remote matches those values), or explicitly restrict/document the migration as "best-effort, single-graph-safe only" in the Migration Plan section and warn multi-graph users may need to re-enter the PAT for graphs other than the first one booted. | P2 |
| 5 | ADR-001's key-stored-alongside-ciphertext-in-the-same-`localStorage`-origin threat model (any reader with `localStorage` access — XSS, a malicious browser extension, a backup/devtools dump — can trivially decrypt everything) is documented in the ADR and in requirements.md, but nothing in the actual implementation tasks (1.1.1a, 1.2.1a) requires a threat-model comment co-located with the code itself, and Task 1.5.1a's corrected UI copy ("Token is encrypted at rest") drops even the "device-specific" caveat without adding a compensating threat-model caveat. A future reader of `CredentialStore.kt` in isolation, or a user reading the UI copy, has no signal that this is "casual-snooping protection only," not a hardened secret store. | A future contributor treats `CredentialStore` as adequate for a more sensitive secret and stores it there without re-evaluating the threat model, or a security report/bug gets closed by pointing at "it's AES-GCM encrypted" without acknowledging the key sits next to the ciphertext. | Add a short KDoc block at the top of `CredentialStore.kt` (Task 1.2.1a) stating the threat model in one paragraph (mirrors ADR-001, doesn't require reading it), and add a `validation.md` check item confirming the UI copy change in Task 1.5.1a doesn't overclaim relative to that threat model. | P3 |
