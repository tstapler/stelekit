# Pre-mortem: wasm-image-drop
**Date**: 2026-09-22

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The new `wasmJsTest` suite (`WasmMediaAttachmentServiceTest`, `ByteBufferInteropTest`) never runs in CI — `.github/workflows/ci.yml` only runs `compileKotlinWasmJs` (compile-only, line 267) and `ciCheck` has no wasmJs dependency (`kmp/build.gradle.kts:817`); `pages.yml` builds a production distribution, not tests. A regression in the OPFS write/dedup path (e.g. a future refactor of `OpfsInterop.kt`) compiles fine and ships, silently breaking drag-and-drop again. | A user reports drag-and-drop silently does nothing (or corrupts/overwrites assets) weeks after a seemingly unrelated PR touching `OpfsInterop.kt` or `PlatformFileSystem.kt` merged clean. | Add a `wasmJsBrowserTest -PenableJs=true` job to `ci.yml` (headless Chromium is already used for other CI steps in this repo's ecosystem norms) gated the same way `compileKotlinWasmJs` already is; at minimum, add one line to plan.md's Story 5.2.1 flagging that this command is developer-run-only, not CI-enforced, so it doesn't silently bit-rot believing it's a safety net. | P1 |
| 2 | Cross-drop-event OPFS filename race (architecture-review concern, unaddressed in plan.md): two near-simultaneous `drop` events for same-named files each launch on the shared, unserialized `dropScope`; both observe "does not exist" in `opfsFileExists` before either write commits, so the second silently clobbers the first. Both calls return `Either.Right` — no error surfaces. | A user drags two batches of images (or the same filename twice, e.g. two screenshots both named `image.png` from separate drag gestures) and later notices one image's markdown reference points to bytes that don't match — the first image is gone, replaced by the second, with no error ever shown. | Wrap `WasmMediaAttachmentService.attachBytes` in a module-level `Mutex.withLock` (or a small serializing actor mirroring `DatabaseWriteActor`) so dedup-then-write is atomic across concurrent drop events, not just within one batch. Add this as an explicit task in Phase 3 rather than leaving it as an unaddressed review concern. | P2 |
| 3 | Base64 bridge (ADR-002) memory/time cost is asserted ("~33% overhead... negligible") but never measured against a realistic image size. A base64 string crossing the Wasm↔JS boundary is stored as UTF-16 JS-side, so a 8-10MB phone photo (HEIC/JPEG) becomes a ~27MB UTF-16 string plus the original `ByteArray` plus the decoded `Uint8Array` — three multi-MB copies alive simultaneously on a single-threaded (or GC-shared) Wasm/JS heap, during a synchronous JS string-building loop (`fromCharCode.apply` chunking) that blocks the main thread. | The browser tab visibly freezes or shows "Page Unresponsive" for several seconds when a user drags in a normal-sized modern phone photo (not the 50-70KB test fixtures Stories 2.1.1/5.1.2 use); on lower-memory devices, the tab may crash outright. | Add a round-trip timing/memory check at a realistic size (5-10MB, not 50-70KB) to Task 5.1.2a's test, per adversarial-review's own recommendation, before this ships — if the number is bad, ADR-002 needs revisiting (chunked transfer or confirming whether a stdlib bulk `Uint8Array`↔`ByteArray` bridge exists on this Kotlin/Wasm pin, which pitfalls.md §3 flagged as unconfirmed). | P1 |
| 4 | `document.body`-level `dragenter`/`dragover` unconditionally calls `preventDefault()` without checking `dataTransfer.types.includes('Files')` (adversarial-review concern) — every non-file drag anywhere on the page (text selection, an internal link drag, a future Compose-native drag interaction) now shows the browser's "can drop here" cursor instead of its correct reject cursor, and swallows the browser's native default handling for that drag globally, app-wide, not just over the editor. | A user (or QA) notices dragging selected text, or a bookmark/link, over any part of the app shows the wrong drop cursor and does nothing — reported as "drag and drop feels broken" unrelated to images, hard to connect back to this feature since it's a global side effect of a change scoped to "image drop." | Add the one-line `event.dataTransfer.types.includes('Files')` guard to `dragenter`/`dragover` before calling `preventDefault()` (Task 4.1.1a), matching JVM's `shouldStartDragAndDrop` gate — cheap, already identified by research/features.md §2 point 7 and restated by adversarial-review as unresolved. | P2 |
| 5 | Per-file `readFileBytes(file)` call inside `DropZoneInterop`'s drop callback (Task 4.1.2a) has no `try`/`catch` around the `File.arrayBuffer()` await (architecture-review concern). An unreadable file (permissions error, file deleted between OS drag-start and drop, or a corrupted removable-media file) throws inside the `dropScope.launch` coroutine with `SupervisorJob` — that one drop's remaining files in the same batch are never processed, and nothing is logged or shown to the user, indistinguishable from AC4's intended graceful no-op but for an unintended reason. | A user drags 3 images together, only 1-2 land as markdown references, no error anywhere (console shows an unhandled promise-adjacent exception only visible to a developer with devtools open) — reported as "sometimes drag-and-drop loses files" with no reliable repro. | Wrap the per-file loop body in `try`/`catch`, routing failures through the same `graphContentLogger.warn`/`notificationManager.show` path Task 1.1.2b already establishes for the service-layer failure case — small addition to Task 4.1.2a, already flagged by architecture-review. | P2 |

## P1 Items (address before implementation)

- [ ] #1 — Add a `wasmJsBrowserTest -PenableJs=true` CI job (or, at minimum, add an explicit note to plan.md Story 5.2.1 / validation.md stating the new tests are developer-run-only and not CI-enforced, so "tests exist" isn't mistaken for "tests protect this feature going forward").
- [ ] #3 — Extend Task 5.1.2a's round-trip test (or add a dedicated manual timing check to Task 5.2.1a) to a realistic 5-10MB image size, and record the actual main-thread block time / peak memory, before treating ADR-002's "negligible" overhead claim as settled.
