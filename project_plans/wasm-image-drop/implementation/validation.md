# Validation Plan: wasm-image-drop

**Date**: 2026-09-22

## Happy Path Scenario

Given an OPFS-backed graph open in the WASM/web build with a page in view (baseline: `useDemoFallback == false`, per requirements.md's Root-cause investigation §1-2), when the user drags an image file from the OS onto the browser window and releases it, then a `![name](../assets/name)` markdown reference for that file appears in the focused block and the file's bytes are written into `<graphRoot>/assets/` in OPFS — matching JVM's existing drag-and-drop behavior for the same interaction (requirements.md AC1/AC2/AC6).

## Test Stack

- **Unit**: `kotlin.test` (`Test`/`assertEquals`/`assertTrue`/`assertFalse`) across `commonTest`, `jvmTest` (JUnit4 runner via Gradle), and `wasmJsTest` (`kotlin("test-wasm-js")`), matching each source set's existing convention (backtick descriptive names in `commonTest`/`jvmTest`, e.g. `` `import writes image bytes to assets-images directory` `` in `ImageImportServiceIntegrationTest.kt`; plain camelCase in `wasmJsTest`, matching `WasmBenchmarkTest.kt`'s existing style, which plan.md's own Task 5.1.1a/5.1.2a explicitly directs new wasm tests to follow).
- **Integration**: same `kotlin.test` framework; wasm integration tests run against **real OPFS and real DOM APIs in headless Chromium** via `./gradlew wasmJsBrowserTest -PenableJs=true` (confirmed real, not simulated — `WasmBenchmarkTest.kt`'s doc comment and plan.md both state this explicitly, and puppeteer-backed headless Chromium is the existing mechanism). Compose UI integration tests on JVM use `androidx.compose.ui.test.junit4.createComposeRule` (`kmp/src/jvmTest/.../JournalsViewUITest.kt` is the existing model), run via `./gradlew jvmTest`.
- **E2E / UX**: Playwright, using the **existing** `e2e/` harness (`e2e/playwright.config.ts`, `e2e/tests/demo.spec.ts`) — a real production wasmJs build served locally and driven by headless Chromium, run via `npm test` (`e2e/package.json`) from `e2e/`. This project's new spec (`e2e/tests/image-drop.spec.ts`) is additive; plan.md did not design any e2e coverage for this feature despite this harness already existing in-repo, so this closes a gap plan.md left open rather than duplicating anything it already committed to. Remaining UX criteria that require judging canvas-rendered visual output (markdown insertion, toast text/contrast, screen-reader behavior) stay manual, per Task 5.2.1a.

### Known gaps (flagged, not closed by test design alone)

1. **`App.kt`'s `onFileDrop` type-dispatch (Task 1.1.2a) has no automated test.** The `when (file) { is DroppedFileBytes -> ... else -> ... }` branch is inline in a Compose closure with no extraction point, and neither JVM (AWT `DropTarget`) nor wasm (no `compose.ui-test` dependency in `wasmJsTest` — confirmed by inspecting `kmp/build.gradle.kts`'s `wasmJsTest` block, which only adds `kotlin("test-wasm-js")`) can drive a real synthetic drag/drop through the full Compose tree in this repo today. Automated coverage here would require either (a) extracting the branch to a small pure function `App.kt` can unit-test directly, or (b) adding a Compose UI test dependency for wasmJs — both are implementation/architecture decisions, not test-design choices, so this is left as a gap rather than papered over with a test that doesn't exercise the real code path. The toast call site (Task 1.1.2b) has the same limitation.
2. **Concurrent-drop filename race (architecture-review.md, no blockers filed but explicitly flagged).** `WasmMediaAttachmentServiceConcurrencyTest.attachBytes_mayCollideOnFilename_whenCalledConcurrentlyForSameName` (added above) exercises this directly and is expected to be flaky or fail against the plan's current check-then-write (`uniqueOpfsFileName` then `opfsWriteFileBytes`) design, since nothing in Story 2.2.1/2.2.2 makes the pair atomic — only same-batch *sequential* drops (`App.kt`'s unchanged `forEach`) are protected. Fixing this (e.g. a per-directory write mutex, or relying on OPFS's own create-exclusive semantics if available) is an implementation-phase decision; this test's purpose is to surface the gap in CI rather than let it pass silently.
3. **`PageDropTargetListenerLifecycleTest` requires a visibility change** (`private` → `internal` on `activeDropHandler`, `listenerInstalled`, `ensureListenerInstalled` in `PageDropTarget.kt`) to be testable from `wasmJsTest` without a full Compose composition. This is a minimal testability accommodation, not a structural change — flagging so it isn't missed during Task 4.1.2a's implementation.
4. **Migration Plan**: plan.md's Migration Plan section is "Not applicable — no schema or persisted-data-format changes" (confirmed by reading `implementation/plan.md`). No `migration_should_be_reversible` test is designed (Step 5 of this task's instructions is skipped, as anticipated).
