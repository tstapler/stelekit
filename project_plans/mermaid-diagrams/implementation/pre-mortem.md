# Pre-mortem: mermaid-diagrams
**Date**: 2026-09-15

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The wasmJs DOM-overlay + `BlendMode.Clear` technique (Task 2.1.2a) — sourced from a single external repo, never proven in this codebase, and explicitly *not* spike-gated the way the JVM engine is — desyncs from the Compose layout under scroll, resize, or window-DPI change, leaving diagrams visually offset from their code block or punching a hole where no diagram is drawn. | A user scrolls a journal page containing a mermaid block on Web and sees the diagram lag behind, freeze at a stale position, or a blank rectangular gap where content used to render. | Treat Task 2.1.2a as a timeboxed go/no-go spike, exactly like Task 3.1.1a for GraalJS — verify overlay-to-layout sync survives scroll/resize/theme-toggle before Epic 6 wiring starts, and record the verdict as an ADR-001 addendum. If it fails, the fallback (plain `Failed`/raw block, or accepting non-precise positioning) must be decided *before* Phase 6, not discovered after. |
| 2 | Mermaid ships with three unpinned, unequal versions (wasmJs npm latest ~12.x, JVM's `mermaid-java`-style wrapper likely 11.4.1, Android's "free choice" bundled asset) with no shared fixture corpus across them, so a diagram using newer syntax renders correctly on Web but silently falls back to raw text (or renders differently) on Desktop/Android. | A user pastes/imports a Logseq/Obsidian graph with a mermaid diagram; it displays correctly in the browser build but shows as a raw code block (or a visibly different layout/coloring) in the desktop app — the exact "parity" problem requirements.md opens with, now reproduced *between SteleKit's own targets*. | Pin exact versions for all three platforms in ADR-001's Open Items before Phase 2–4 implementation (not deferred to "record final versions" after the fact), and add a shared fixture corpus (same diagram source strings) run through all three platform smoke tests (Story 7.1.2 extended to wasmJs/Android, not JVM-only) asserting `Rendered` on all three, not just visual similarity. |
| 3 | A diagram fence embeds a `%%{init: {"securityLevel": "loose"}}%%`-style directive that overrides the app-level `MERMAID_SECURITY_LEVEL = "strict"` init call, re-enabling `click` bindings / arbitrary HTML label injection — the exact CVE class cited in ADR-001 (gogs GHSA-26gq-grmh-6xm6, docmost GHSA-r4hj-mc62-jmwj) — and no test in the plan ever exercises this path. | A page imported from an untrusted source (shared graph, downloaded template, synced from someone else) renders a mermaid block that executes injected script/HTML or triggers unexpected navigation instead of showing an inert diagram. | Add a malicious-directive fixture (`%%{init: {"securityLevel": "loose", ...}}%%` prepended to a benign diagram) to Story 7.1.2/7.1.3's smoke suite on every JS-execution platform, asserting the directive has no effect (verify via DOM/rendered-output inspection, not just "no crash") before Epic 1.2's constants are considered done. |
| 4 | The GraalJS+`mermaid-java`-style spike (Task 3.1.1a) is time-boxed to "one work session" under implementation-agent time pressure, so its go/no-go verdict is recorded based on a single happy-path fixture (`graph TD; A-->B-->C`) rather than genuinely stress-testing the Batik `getBBox()` shim against text-heavy/nested diagrams, module-system flags under this repo's actual CI JDK, or GraalJS Community Edition licensing — producing a false "go" that Epic 3.2 (five further tasks) is then built on. | Desktop renders simple flowcharts fine in dev testing, but CI fails on a module-access exception, or a real-world diagram with long node labels throws inside the Batik shim / renders with garbled text measurement, discovered only after Epic 3.2 is fully built out. | Make the spike's three required outputs (fidelity/stability verdict, Batik shim confirmation, actor-serialization cost) non-negotiable exit criteria checked by a human/reviewer before Task 3.2.1a starts — not just "recorded in ADR-001" but reviewed for rigor (e.g. require at least one text-heavy fixture and a `./gradlew` CI-JDK smoke run, not just a local IDE run) per adversarial-review's already-flagged CI/JDK-flags concern. |
| 5 | Android hosts one real `android.webkit.WebView` per visible mermaid block inside a `LazyColumn` — the exact "WebView-per-item" memory/lifecycle pitfall the ADR claims to sidestep "on the platform GraalJS covers" (i.e., not Android) — so a journal page with several diagrams causes visible jank, WebView process memory growth, or scroll stutter on lower-end devices. | A user opens a page with 4+ mermaid blocks on a mid/low-end Android device; scrolling becomes janky, or the app's memory footprint climbs noticeably compared to a page of equivalent length with only text/table blocks, within the first month of real usage. | Add an acceptance criterion (and test, even if just a manual perf check documented in validation.md) for "N mermaid blocks visible/recycled in one LazyColumn" scroll performance and WebView instance count, and consider pooling/reusing a small fixed number of WebView instances across scroll-recycled items rather than one per block — currently unaddressed by Story 4.1.3, which only covers the cache-hit-skips-JS-render case, not the WebView-instance-count case. |

## P1 Items (address before implementation)
- [ ] Failure #1 — Add a go/no-go spike checkpoint for `MermaidSvgOverlay` (Task 2.1.2a) in plan.md, mirroring Task 3.1.1a's structure, with a recorded verdict in ADR-001 before Phase 6 UI integration begins.
- [ ] Failure #3 — Add a malicious `securityLevel` override fixture to Story 7.1.2/7.1.3's test plan (validation.md) covering all three JS-execution platforms, and make it a blocking item before Epic 1.2 is marked complete.

## Non-P1 items still worth flagging in validation.md
- Failure #2 (version-skew parity) and #4 (rushed spike) are P2 — recoverable, but should have explicit exit criteria in validation.md rather than relying on task descriptions alone.
- Failure #5 (Android WebView-per-item cost) is P2 — recoverable via a follow-up pooling fix, but should be measured (not assumed away) during Phase 4 implementation.
