# Research: Stack options for Mermaid diagram rendering

Agent 1 (Stack) — mermaid-diagrams project, SDD phase 2.

## Repo baseline (verified from source, not assumed)

- Kotlin `2.3.21`, Compose Multiplatform `1.10.3`, Android Gradle Plugin `8.13.2`, `jvmToolchain(21)` — `settings.gradle.kts:9-21`.
- Targets actually declared in `kmp/build.gradle.kts:30-44`: `jvm()`, `androidTarget()`, `iosX64()/iosArm64()/iosSimulatorArm64()`, and — **only when `-PenableJs=true`** (set in `gradle.properties:20`) — `wasmJs { browser(); binaries.executable() }`.
- **Correction to requirements.md**: there is no classic Kotlin/JS (`js(IR)`) target anywhere in the build. The "jsMain" / "Web (JS)" language in requirements.md and ADR-001 refers to what is actually a **Kotlin/Wasm (`wasmJsMain`) target**, not Kotlin/JS. This matters: Kotlin/Wasm's JS interop uses `external fun` + `JsAny`/`JsString`/`JsNumber` marshaling, not Kotlin/JS's `dynamic` types or `@JsModule`/`@JsName` — a hand-wrapped Kotlin/JS mermaid binding does not port directly.
- `gradle.properties:16` sets `org.jetbrains.compose.experimental.jscanvas.enabled=true`. This means Compose Multiplatform's web target here renders the whole UI onto a single `<canvas>` via Skia/Wasm (the "jscanvas" / ComposeViewport renderer), **not** the DOM-tree-based Compose HTML renderer. Consequence: you cannot just emit a composable that becomes a real `<div>`/`<svg>` node in the page — Mermaid's SVG output has to be layered on top of (or punched through) the canvas via a DOM-overlay technique (see Web section below).

## JVM / Desktop

Two structurally different approaches, not one:

**A. WebView-in-Compose (bundles/launches a browser engine)**
- No first-party Compose Multiplatform WebView exists. JetBrains' own tracker confirms this is still an open feature request as of Sept 2026, unresolved: [CMP-8105 "Official WebView Component for Compose Multiplatform"](https://youtrack.jetbrains.com/projects/CMP/issues/CMP-8105) and the older [CMP-4463](https://youtrack.jetbrains.com/issue/CMP-4463/WebView-support-for-Compose-Multiplatform).
- The community-standard library is [KevinnZou/compose-webview-multiplatform](https://github.com/KevinnZou/compose-webview-multiplatform) (Android/iOS/Desktop). Its desktop backend is JCEF, wrapped via KCEF ([dev.datlag/kcef](https://mvnrepository.com/artifact/dev.datlag/kcef)).
  - **Maintenance risk, verified**: KCEF's own maintainer archived that repository (~Nov 2025) — see [KevinnZou/compose-webview-multiplatform#392 "KCEF is archived, now what?"](https://github.com/KevinnZou/compose-webview-multiplatform/issues/392). compose-webview-multiplatform itself still shows activity into 2026 (open issues from Jan/Feb/Mar 2026), but its desktop story now depends on an unmaintained upstream.
  - JCEF/KCEF bundles a full Chromium runtime — large binary footprint (100+ MB) and >100ms WebView cold-start cost per the same tradeoff ADR-001 already weighed against KaTeX-via-WebView.
- Newer, lighter alternatives avoid bundling Chromium by delegating to the OS's native web engine instead (WebView2 on Windows, WebKitGTK on Linux, WKWebView on macOS) via a Rust bridge: [kdroidFilter/ComposeNativeWebview](https://github.com/kdroidFilter/ComposeNativeWebview) (Wry + UniFFI) and [winterreisender/webviewko](https://winterreisender.github.io/webviewko/) (binding to the `webview` C library). These are smaller/younger projects — plausible but unproven at this repo's scale; no evidence of wide production adoption found.

**B. Headless JS-engine, no WebView at all — pre-render to SVG**
- [esamson/mermaid-java](https://github.com/esamson/mermaid-java): pure-Java library that runs the **actual, unmodified mermaid.js** inside GraalJS and uses Apache Batik for SVG text-measurement (mermaid.js normally needs `document.createElement`/`SVGTextElement.getBBox()`, which GraalJS alone can't provide — Batik supplies that missing browser API). Outputs SVG or `BufferedImage`, no browser, no Node, no native deps. Currently bundles Mermaid **11.4.1** (compiled ESM→IIFE via esbuild) — this pins an older Mermaid release than current npm (see Mermaid version section), a version-skew risk to track.
- This is a materially important finding against requirements.md's stated premise ("no pure-JVM Mermaid-compatible rendering library — this forecloses Option B for JVM"). A pure-JVM path via GraalJS-hosted mermaid.js **does exist** and is directly analogous to ADR-001's own Option C ("pre-render SVG"), just using the real mermaid.js instead of a from-scratch parser. Worth explicit reconsideration in the ADR for this project rather than assuming WebView/JS-bridge is mandatory on JVM.
- GraalVM/GraalJS itself is Oracle-maintained and ECMAScript-2026-compliant ([oracle/graaljs](https://github.com/oracle/graaljs)); it runs on stock JDK 21 (this repo's `jvmToolchain(21)`) via the `org.graalvm.js:js` Maven artifact — no separate GraalVM distribution required.

## Android

- **GraalJS does not reliably run on Android** — confirmed via an open upstream compatibility issue citing `sun.misc.Unsafe` mismatches between the JVM spec GraalJS expects and Android's runtime ([oracle/graaljs#514](https://github.com/oracle/graaljs/issues/514)). This forecloses reusing the JVM GraalJS/mermaid-java path (Option B above) on Android as-is.
- **WebView route**: `android.webkit.WebView` embedded via `AndroidView` (Compose interop) is the current idiomatic pattern — Accompanist's WebView wrapper is legacy/superseded; direct `AndroidView { WebView(context) }` or the Android backend of `compose-webview-multiplatform` (which itself just wraps `android.webkit.WebView`) are both standard. No maintenance concerns here — Android's own WebView is platform-shipped, unlike JVM's JCEF/KCEF situation.
- **Native-Kotlin alternative (no WebView, no JS engine)**: [hggz/Mermaid-Android](https://github.com/hggz/Mermaid-Android) — a pure-Kotlin, zero-dependency library that parses Mermaid syntax itself and renders directly via `android.graphics.Canvas` (claims support for 7 diagram types: flowchart, sequence, class, state, ER, pie, gantt). No WebView, no JS runtime, works off the main thread. This is structurally an Option-B "platform-native renderer," same shape as ADR-001's `jlatexmath` choice — but it is a small, unverified-maturity community project (could not confirm stars/release history/production usage via search); treat as a candidate requiring its own due-diligence pass (license, syntax coverage vs. real mermaid.js, maintenance activity), not a given.
- A broader pattern showed up repeatedly in search: several very recent (2026) community projects reimplement a **Mermaid-compatible parser + Compose Canvas renderer in pure Kotlin Multiplatform** (not Android-only) — [botiverse/mermaid-native](https://github.com/botiverse/mermaid-native) and [swithun-liu/cmp-mermaid](https://github.com/swithun-liu/cmp-mermaid). If mature enough, this is a fourth architectural option worth surfacing to the ADR: **one Kotlin renderer shared across all four targets (JVM, Android, iOS, wasmJs) via `commonMain`, no WebView and no JS engine anywhere.** This would sidestep every WebView-maintenance and JS-interop problem below at the cost of depending on a young, unofficial reimplementation of Mermaid's rendering semantics (coverage/fidelity/license risk vs. the real mermaid.js). Flagging for the planning phase to weigh explicitly rather than defaulting to WebView/JS-engine per target.

## iOS

- WKWebView embeds into Compose Multiplatform iOS via `UIKitView` (the general native-interop primitive, [Kotlin docs](https://kotlinlang.org/docs/multiplatform/compose-uikit-integration.html)). Note the import path moved from `androidx.compose.ui.interop` to `androidx.compose.ui.viewinterop` in CMP 1.7 (this repo is on 1.10.3, well past that migration, so use the new package).
- Technically this is no longer "experimental" plumbing — `compose-webview-multiplatform` ships an iOS backend using exactly this mechanism, and a May-2026 walkthrough ([Roy Watson, Medium](https://medium.com/@rwatson_86305/adding-a-webview-to-compose-multiplatform-android-ios-and-desktop-8f17e91649f4)) demonstrates a working WKWebView-in-Compose-iOS setup end to end. Historical friction existed (e.g. [#222, `IrLinkageError: UIKitView` symbol not found](https://github.com/KevinnZou/compose-webview-multiplatform/issues/222)) but that traces to Kotlin/Compose version-skew in a specific consumer project, not an unsolved platform-level gap.
- Net assessment: WKWebView-in-Compose is mature enough to attempt for v1, but it is still one more platform-specific integration to validate (JS bridge/message-passing for injecting Mermaid source and getting back an SVG/error), and this repo has zero prior WebView code on any platform to build from. Given ADR-001's explicit iOS deferral for the structurally identical problem, and requirements.md's own AC5 explicitly allowing iOS to stay on the raw-fallback path, deferring iOS in v1 is a defensible planning choice — not something the stack forces, but consistent with precedent and this project's stated non-goals.

## Web / Wasm (`wasmJsMain`, `enableJs=true`)

Two separable problems, both need solving:

1. **Calling mermaid.js from Kotlin/Wasm.** Kotlin/Wasm JS interop ([kotlinlang.org/docs/wasm-js-interop.html](https://kotlinlang.org/docs/wasm-js-interop.html)) declares JS functions with `external fun`, and every value crossing the boundary must be a `JsAny` subtype (`JsString`, `JsNumber`, `JsArray`, etc.) — converted via `.toJsString()` / `.toString()` and friends. This is stricter than classic Kotlin/JS's `dynamic`-typed interop. **No published Kotlin/Wasm or Kotlin/JS wrapper for mermaid.js exists** — JetBrains' official [kotlin-wrappers](https://github.com/JetBrains/kotlin-wrappers) catalogue (60+ modules, Maven Central) has no mermaid entry, and the only prior art found is developers hand-rolling `@JsModule`/`@JsName` wrappers for classic Kotlin/JS (Kotlin Slack threads), which do not directly transfer to `wasmJs`'s `JsAny`-based model. A hand-written `external`/`JsAny` interop shim, calling `mermaid.render(id, source)` and marshaling the returned SVG string back, would need to be authored from scratch for this project.
2. **Getting Mermaid's SVG output into the UI.** Because this build renders Compose for Web via canvas/Skia (`jscanvas` flag, confirmed above), the rendered SVG can't just become a child composable node — it needs the DOM-overlay pattern used elsewhere in the CMP ecosystem for embedding native HTML content behind/around the canvas: absolutely-positioned HTML element synced to the composable's layout bounds, with a transparent `BlendMode.Clear` region punched in the canvas layer where it should show through. Prior art: [Hamamas/Kotlin-Wasm-Html-Interop](https://github.com/Hamamas/Kotlin-Wasm-Html-Interop) and CMP's own `WebElementView`/`HtmlView`-style composables mentioned in recent release notes cover this exact technique. This is a real, if fiddly, solved pattern — not a dead end — but it's additional plumbing beyond "just call mermaid.js," and needs its own positioning/resize-sync logic per diagram block.

## Mermaid.js version and distribution

- Latest stable per npm as of this research: **12.0.0** (mermaid npm package). It requires an **ES2024** baseline (Safari 17.4+, Node.js ≥22.12) and now bundles the ELK layout engine by default (previously a separate `@mermaid-js/layout-elk` package).
- 11.15.0 is still the version fronted on cdnjs; jsDelivr (`cdn.jsdelivr.net/npm/mermaid@latest/dist/`) tracks latest automatically. Package ships both ESM and UMD builds under `dist/`.
- Version-skew risk: the only viable pure-JVM path found (`mermaid-java`, above) bundles **11.4.1** — multiple majors behind current. Any JVM headless-render approach inherits whatever Mermaid version its wrapper last vendored, not the latest.

## Summary of options surfaced (for the planning/ADR phase, not a decision here)

| Target | WebView path | Non-WebView path |
|---|---|---|
| JVM/Desktop | compose-webview-multiplatform + JCEF/KCEF (KCEF now unmaintained — risk) or newer native-engine wrappers (ComposeNativeWebview, webviewko — young) | GraalJS + real mermaid.js → SVG (`mermaid-java` pattern), runs on stock JDK 21, no WebView |
| Android | `AndroidView` + `android.webkit.WebView` (platform-shipped, low risk) | GraalJS **does not work** on Android (confirmed incompatibility); pure-Kotlin Canvas renderer (`Mermaid-Android`) exists but is an unverified-maturity community project |
| iOS | `UIKitView` + WKWebView — technically mature in CMP 1.10.3, but net-new integration for this repo | Deferred raw-fallback, consistent with ADR-001 precedent and this project's AC5 |
| Web (wasmJs) | N/A (already in-browser) | Direct mermaid.js call via hand-written `external`/`JsAny` interop + DOM-overlay-on-canvas rendering (no ready-made wrapper exists for either piece) |
| All targets (wildcard) | — | Emerging pure-Kotlin-Multiplatform Mermaid-compatible parser+renderer projects (`mermaid-native`, `cmp-mermaid`) could unify all four targets with zero WebView/JS-engine dependency — flagged as a fourth architectural option for the ADR to weigh, contingent on their actual syntax-coverage/maturity, which requires separate due diligence before betting on them.

No decision is made here — this is input for the architecture/ADR phase, which must weigh these against the LaTeX ADR-001 precedent, the "no existing WebView/JS-bridge infrastructure" constraint, and the acceptance criteria (JVM+Web required for v1; iOS/Android leeway; graceful fallback on failure).
