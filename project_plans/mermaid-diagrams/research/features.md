# Research: Features — Mermaid Diagram Rendering

Agent 2 (Features). Scope: how comparable tools render Mermaid, and which edge
cases / unstated needs the design must handle.

## 1. Industry survey

| Tool | Render trigger | Error display | Diagram types | Sizing/zoom | Theming |
|---|---|---|---|---|---|
| **GitHub** | On view (server round-trip renders the fence to SVG at page-render time, not live-as-you-type in the editor) | Historically a silent ~45s hang followed by "Unable to render rich display"; 2025 updates added inline syntax-error messages instead of a blank/hung state ([community discussion #172498](https://github.com/orgs/community/discussions/172498)) | Broad — GitHub tracks upstream mermaid.js fairly closely | Fixed to content width, no interactive pan/zoom in-page | Auto-detects `prefers-color-scheme` and re-renders the SVG per light/dark; known bug history of dark-mode detection failing when the mermaid renderer doesn't see the media query change ([discussion #12116](https://github.com/orgs/community/discussions/12116), [discussion #35733](https://github.com/orgs/community/discussions/35733)) |
| **GitLab** | On view/preview | Renders a warning banner ("Displaying this diagram might cause performance issues on this page") when limits are hit, rather than failing outright | Mermaid v11 | Not addressed in docs beyond standard block sizing | Not surfaced in survey; GLFM markdown docs don't call out theme sync explicitly |
| **Obsidian** | Both **Live Preview** (as-you-type, native CodeMirror widget) and **Reading view** render mermaid natively, no plugin required — but there's a documented split where a diagram can render correctly in Live Preview and then throw on switching to Reading view/export ([forum #40136](https://forum.obsidian.md/t/mermaid-renders-in-live-preview-errors-in-reading-exporting/40136)) | Inline error text where the diagram would be; forum reports of "Maximum text size exceeded" with no user-facing way to raise `maxTextSize` ([forum #103484](https://forum.obsidian.md/t/mermaid-diagrams-fail-with-maximum-text-size-exceeded-error-no-way-to-configure-maxtextsize-limit/103484)) | Whatever the bundled mermaid.js version supports | No native pan/zoom; some community plugins add it | Follows Obsidian's active theme (light/dark) |
| **Logseq (via `logseq-mermaid-plugin`)** | Explicit action — `/Draw mermaid diagram` inserts a `{{renderer :mermaid_<uuid>, <scale>}}` macro block; the diagram is rendered **to a static PNG** on demand, not live text-to-diagram on every keystroke ([README](https://github.com/benjypng/logseq-mermaid-plugin/blob/main/README.md)) | Not a live syntax-checked editor — errors surface as a failed image render | mermaid.js subset supported by the plugin's bundled version | Configurable scale factor (default 3x) for crisp export; image is a flat raster, so no post-render zoom | Plugin auto-detects Logseq's Light/Dark theme and reruns mermaid with matching `theme` config |

Key structural difference for SteleKit: GitHub/GitLab render server-side (no client JS-engine problem); Obsidian and Logseq-plugin render client-side, and Logseq's plugin explicitly avoids "render on every keystroke" by keying re-render off block save + producing a cached static image, closer to what the `latex-math-rendering` ADR-001 already does for KaTeX/jlatexmath in this codebase.

## 2. Edge cases and failure modes

- **Malformed syntax**: mermaid.js exposes `mermaid.parseError` (override-able) and `mermaid.parse(txt)` (returns bool, lets you validate before render) — [mermaid Interface docs](http://mermaid.js.org/config/setup/mermaid/interfaces/Mermaid.html), [issue #1775](https://github.com/mermaid-js/mermaid/issues/1775). SteleKit's renderer should call `parse()` (or wrap `render()` in try/catch, since `parseError` handling varies across bundled versions) and fall back to `CodeFenceBlock`'s existing raw display on any thrown/reported error — this satisfies acceptance criterion 2 directly.
- **Empty diagram body**: `extractCodeBody()` in `CodeFenceBlock.kt:22-28` already handles empty fenced content (returns `""` if start >= end). A mermaid renderer needs the same guard before invoking mermaid — calling `render()` on an empty string should short-circuit to the raw/empty-fallback path rather than invoking the JS engine at all.
- **Large/complex diagrams**: mermaid.js has a configurable `maxTextSize` (default limit exists specifically to bound pathological render cost) — [issue #1341](https://github.com/mermaid-js/mermaid/issues/1341). GitLab enforces a hard 2K-character-or-50-block cap per page and shows a performance warning rather than rendering ([GitLab issue #510642](https://gitlab.com/gitlab-org/gitlab/-/work_items/510642)); this is also explicitly a **security** consideration — GitLab tracked "Uncontrolled Resource Consumption in any Markdown field using Mermaid" as a vulnerability ([issue #30905](https://gitlab.com/gitlab-org/gitlab/-/issues/30905)). SteleKit should adopt a size/complexity ceiling (e.g. character count or node count) below which it attempts render, falling back to raw code above it, both for UX and to avoid a hostile/malformed import graph hanging a JS engine or WebView.
- **Unsupported diagram types / older mermaid versions**: since the requirements doc already forecloses a pure-JVM mermaid port, whichever mermaid.js version gets bundled per platform (WebView-hosted JS, GraalJS, or browser-native on `jsMain`) determines which diagram types are supported. Version skew across platforms (e.g. a newer mermaid on Web than on a WebView-hosted JVM/Android bundle) is a real risk — a diagram type valid on Web but unsupported by an older bundled version on Desktop needs the *same* try/catch-and-fallback path as a syntax error, since to the renderer it's indistinguishable from "failed to render."
- **Rapid editing / re-render races**: none of the surveyed tools render on every keystroke while a diagram is being actively typed — Obsidian's Live Preview renders the whole widget as one unit rather than a debounced individual mermaid call, and Logseq's plugin only renders on an explicit macro/save action. SteleKit's own `BlockStateManager` already debounces local edits 500ms before writing to disk (per this repo's `CLAUDE.md` data-flow description); the mermaid renderer should trigger off the **committed/saved block content** (i.e. only re-render when `block.content` actually changes after the existing save debounce), not on every recomposition or keystroke, to avoid firing a JS-engine render per character. A render-in-flight guard (cancel-and-restart, or ignore-stale-result-by-token) is needed if a second edit lands before the first render call returns — this mirrors the requirement already implied by ADR-001's `LruCache` keyed on formula text: key any render/cache lookup on the exact source string so a stale in-flight render for an old string can be discarded when a new one supersedes it.
- **Tap-to-edit interaction change**: `CodeFenceBlock.kt:44-48` wires `.clickable { onStartEditing() }` on the whole `Box`. A mermaid-rendering variant needs the equivalent affordance preserved (acceptance criterion 4) — but note the raw code view currently also wraps the code text in `SelectionContainer` for copy (`CodeFenceBlock.kt:65-74`); a rendered diagram (image/canvas/WebView surface) has no native text-selection equivalent, so tap-to-edit becomes the *only* way to reach the source text and must not regress. Should also consider: does a single tap open raw-edit mode, or does the diagram need a distinct "view source" affordance separate from edit? None of the surveyed tools resolve this identically — GitHub/GitLab have no inline edit path at all (edit means switching to a separate raw-file view); Obsidian's Live Preview keeps the diagram and the fenced text co-resident depending on cursor position, which SteleKit's current block-level (not fence-level) edit-mode toggle doesn't support without further design.

## 3. Unstated needs

- **Dark/light theme parity with Material3**: every surveyed tool re-themes the diagram to match host app theme (GitHub via `prefers-color-scheme`, Obsidian via active theme, Logseq plugin via explicit theme detection + re-render). Mermaid's `theme`/`themeVariables` init config would need to be derived from `MaterialTheme.colorScheme` at render time, and — critically — a **theme change must invalidate any cached render** (extend the LruCache-style key from ADR-001 to include a theme/color fingerprint, not just source text, or diagrams will show stale colors after a light/dark toggle).
- **Text selection / copy of raw source**: `CodeFenceBlock`'s current raw view is wrapped in `SelectionContainer` (`CodeFenceBlock.kt:65`), giving users copyable source text today. A rendered diagram loses that unless the design explicitly keeps the raw source copyable (e.g. via the tap-to-edit path, or an explicit "copy source" action) — this is a regression risk if not called out, since raster/WebView diagram surfaces are not naturally text-selectable.
- **Print/export (PDF/image) implications** — confirmed via code and the export project's own docs:
  - `project_plans/stelekit-export/requirements.md:33` lists **PDF export as explicitly out of scope** for that whole project, so there is no PDF pipeline to integrate with today.
  - The implemented export pipeline (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/export/`) supports Markdown, HTML, plain text, and JSON only (`ExportService.kt`, `HtmlExporter.kt`, `MarkdownExporter.kt`, `PlainTextExporter.kt`, `JsonExporter.kt`).
  - `HtmlExporter.kt:58` and `:130` render **every** fenced code block (mermaid included, since the exporter doesn't special-case language) as `<pre><code>` with HTML-escaped raw text — i.e. exported HTML would show mermaid *source*, not the rendered diagram. This is consistent behavior (no regression), but it does mean the in-app "renders as a diagram" experience and the exported HTML diverge — worth a one-line callout in the design note so it's a documented, deliberate v1 gap rather than a surprise. If diagram-in-export is ever wanted, `HtmlExporter` would need a mermaid special case (e.g. render to inline `<img>`/data-URI SVG at export time, echoing Logseq's plugin approach of baking a static raster), but that's out of scope per the non-goals in `requirements.md:15-19` (no visual editing, v1 renders from existing source) and is not requested by acceptance criteria.
  - No headless-render-to-image step exists anywhere in `kmp/src` today (confirmed no WebView/JS-bridge infra per `requirements.md:27`), so "render mermaid to a static image for export" would be new infrastructure, not a hookup to something existing.
- **Accessibility**: none of the four surveyed tools provide a strong answer here — GitHub/GitLab/Obsidian all render an `<img>`/SVG with no reliably-populated alt text derived from diagram content; screen-reader users get little more than "image" today industry-wide. For SteleKit, since the raw mermaid source is always retained as `block.content` (this is a fenced-code-block renderer over existing text, not a new note type per the non-goals), the minimum viable a11y story is: expose the raw source as the `contentDescription`/accessibility label on the rendered diagram composable, so a screen reader falls back to reading the mermaid source text rather than announcing an unlabeled image. This is a small addition (analogous to `ImageBlock`'s existing `altText` parameter visible in `BlockItem.kt:401-406` for regular images) and should be called out explicitly since none of the competitors do it well — it's a place SteleKit could exceed rather than merely match parity.

## 4. Summary of implications for design/ADR

1. **Render trigger**: debounce off saved `block.content` (already debounced 500ms upstream), not per-keystroke; guard against empty body before invoking the renderer.
2. **Failure handling**: wrap parse/render in try/catch (mermaid's own `parseError`/`parse()` API is inconsistent across bundled versions — don't rely on it alone), fall back to the existing `CodeFenceBlock` raw path on any failure, unsupported diagram type, or platform without a v1 renderer — single fallback code path satisfies ACs 2 and 5.
3. **Size ceiling**: adopt a character/complexity limit (GitLab's 2K-char/50-block precedent) below which render is attempted, above which raw fallback is shown, both for UX and to bound worst-case render cost on a hostile/malformed imported graph.
4. **Cache key**: extend ADR-001's `LruCache(source, displayMode, textSizePx)` pattern to `(source, theme-fingerprint, width)` for mermaid, since diagram theming must track Material3 light/dark and stale-theme cache hits are a real regression risk.
5. **Interaction parity**: preserve tap-to-edit (AC 4); explicitly decide whether raw-source copy is reachable only via edit mode or needs a dedicated affordance, since `SelectionContainer` won't apply to a rendered surface.
6. **Export**: no change needed to `HtmlExporter`/other exporters for v1 (they already emit raw fenced-code text, including for mermaid) — document this consciously as a known "rendered in-app, source-only on export" gap rather than silently diverging.
7. **Accessibility**: set the raw mermaid source as the accessibility label on the rendered diagram composable — no competitor does this well; it's a cheap, high-leverage addition given the source text is always available as `block.content`.
