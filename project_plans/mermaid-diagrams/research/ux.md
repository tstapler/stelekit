# UX Research: Mermaid Diagram Rendering

Agent 5 (UX), SteleKit `mermaid-diagrams` project. Scope: comparable-product patterns, mental models, accessibility, error/edge-case UX, and jobs-to-be-done for rendering ```mermaid fences as diagrams with tap-to-edit parity with `CodeFenceBlock` (`kmp/src/commonMain/kotlin/dev/stapler/stelekit/ui/components/CodeFenceBlock.kt`).

## 1. Comparable UX patterns

| Product | Read/edit toggle | Error display |
|---|---|---|
| **GitHub** | No dedicated edit button on the rendered diagram. GitHub's HTML pipeline replaces the raw `<pre>`/mermaid-tagged block with a progressively-enhanced template; a client with JS renders the SVG, a client without JS (or an API request) sees the original Markdown source. Editing happens by switching the whole file/comment from "Preview" to the source editor (a page-level toggle, not a per-diagram click) [github.blog](https://github.blog/developer-skills/github/include-diagrams-markdown-files-mermaid/). | On invalid syntax, GitHub falls back to showing the raw Mermaid source as plain code rather than rendering a broken diagram or a large error box [github/docs#15727 discussion](https://github.com/orgs/community/discussions/203196), [construct#68](https://github.com/lfnovo/construct/issues/68). GitHub also caps diagram size (~50KB) and silently falls back past that limit. |
| **GitLab** | Same shape as GitHub: native Mermaid in fenced blocks across issues/MRs/wikis/snippets, edited via the page's own Markdown source/preview split, not per-diagram [docs.gitlab.com/user/markdown](https://docs.gitlab.com/user/markdown/). | GitLab recommends authors add a plain-text summary near the diagram for both accessibility and graceful degradation, but does not itself provide an inline "why did this fail" UI beyond falling back to source. |
| **Obsidian (core, since 0.15)** | Rendering is tied to the *editor mode*, not the individual block: Source Mode shows raw text, Live Preview shows the rendered diagram inline while the block is still visually present as a block, Reading View shows only the diagram. Clicking into the diagram's screen position in Live Preview places the cursor back in the underlying source, which is the closest first-party analog to "tap to edit" — no separate button. Full drag/rearrange visual editing (Mermaid GUI Editor, Mermaid Flow, Draw a Mermaid, MermaidMaker) is exclusively via third-party community plugins layering an explicit "Edit" button/pencil icon on hover, none of it built in. |
| **Logseq (community mermaid plugins — no first-party support)** | Logseq has no native mermaid rendering; it's 100% plugin-driven (`logseq-mermaid-plugin`, "Fenced Code Plus"). The dominant plugin pattern renders to a static PNG via a `{{renderer :mermaid_<uuid>, <scale>}}` macro block wrapping the source, i.e. mermaid becomes a **separate rendered block type**, not a code-fence that toggles — editing means opening the block's raw text (Logseq's universal click-to-edit-any-block behavior) which reveals the renderer macro and mermaid source together. |

**Implication for SteleKit**: none of the four precedents implement true "click the rendered diagram, drop straight into editing that block's raw text" as a *dedicated, first-party, per-diagram* interaction — Obsidian's core behavior is the closest, and it works because clicking anywhere in a block just moves the cursor there (same principle as `CodeFenceBlock.onStartEditing`). SteleKit's planned approach (tap → `onStartEditing` on the same block, matching existing `CodeFenceBlock`) is actually **ahead of** GitHub/GitLab's page-level-only toggle and matches Obsidian's per-block model. This is a genuine differentiator worth keeping, not a corner being cut.

## 2. User mental models

Logseq/outliner users already have one strong prior: **every block is editable by clicking on it**, full stop — text, code fences, block references, templates. The existing `CodeFenceBlock.onStartEditing()` reinforces this: a code block *looks* like a rendered/styled artifact (rounded surface, monospace, language label) but is still "just text I can click into." A rendered mermaid diagram fits this same category if — and only if — clicking it behaves identically. Any deviation (e.g., mermaid blocks requiring a dedicated edit button while every other block type supports direct-click) would violate the established mental model and register as an inconsistency, not a feature.

Two mental-model risks specific to mermaid:

- **"Is this now a different kind of note?"** Users who know Trilium's dedicated Mermaid note type, or Obsidian Canvas, may expect mermaid blocks to become a first-class object (draggable, exportable separately). The requirements doc already scopes this as a non-goal ("stays a fenced-code-block renderer") — worth reinforcing in the UI by keeping the *same* visual chrome (rounded surface, tap affordance) as `CodeFenceBlock`, just with SVG/canvas content instead of monospace text, so it reads as "still a code block, now with a preview" rather than "a new object type."
- **Affordance while editing**: should the raw-source edit view hint "this will render as a diagram"? Recommendation: yes, minimally — keep the existing language label (`mermaid`) visible in the editor exactly as `CodeFenceBlock` already shows `language` for any fence (`CodeFenceBlock.kt:53-59`), so the signal is "this fence's language tag is special" rather than inventing a new UI element. No product researched (GitHub/GitLab/Obsidian) adds a live inline preview *while typing inside the fence* by default — Obsidian's Live Preview is the exception, and only because it renders outside the cursor's line entirely. A "type here, see live diagram update" split view is a v2 nice-to-have, not baseline; matches the requirements doc's non-goal on visual/live editing.

## 3. Accessibility (WCAG/ARIA/keyboard nav)

The core problem, confirmed across sources: **there is no ARIA specification for diagrams** — a rendered flowchart's node/edge relationships have no standard way to reach assistive technology, and mermaid.js's own maintainers acknowledge this gap directly (["Screen reader / accessibility technology support for diagrams," mermaid-js/mermaid#5632](https://github.com/mermaid-js/mermaid/issues/5632)). What mermaid.js *does* provide, and what SteleKit should adopt directly rather than reinvent:

- **`accTitle` / `accDescr` directives**: authors can add a one-line accessible title (`accTitle: ...`) and a multi-line accessible description (`accDescr: ...` or `accDescr { ... }`) inside the mermaid source itself. Mermaid then sets `aria-roledescription` (to the diagram type, e.g. `"flowchart"`) and populates the SVG's `<title>`/`<desc>` elements from these directives automatically [mermaid.js.org/config/accessibility](http://mermaid.js.org/config/accessibility.html). This is the only mechanism that gives a screen reader anything better than "an unlabeled image" or a meaningless flat list of node text — and it's already spec'd by upstream mermaid, so no custom UI or storage is needed on SteleKit's side beyond rendering the SVG mermaid produces (which already carries these attributes when the author supplies them).
- **Pattern 11 for the SVG itself** (from accessibility research, Deque/CSS-Tricks/DAISY): `<svg role="img" aria-labelledby="[id]">` + `<title id="...">` + `<desc id="...">`, cross-referenced via `aria-labelledby`, tested as the most reliable combination across browser/screen-reader pairs [css-tricks.com/accessible-svgs](https://css-tricks.com/accessible-svgs/), [kb.daisy.org/publishing/docs/html/svg.html](https://kb.daisy.org/publishing/docs/html/svg.html). Since mermaid.js already emits `<title>`/`<desc>` from `accTitle`/`accDescr`, SteleKit's renderer wrapper (WebView or JS-engine host) should not strip these attributes when embedding the SVG into the Compose tree — a concrete implementation constraint to flag for the architecture/tech research agent.
- **Raw source must remain reachable without a mouse.** Because no diagram, however well-labeled, substitutes for the actual semantic content, the raw mermaid text is the real accessible fallback — same principle GitLab's own guidance gives authors ("include a text summary near the diagram") applied structurally instead of by convention: SteleKit's tap-to-edit already exposes the raw source, but it must be **keyboard-reachable**, not just tap/click-reachable — e.g., the diagram surface should be a focusable element (`Modifier.focusable()` / tab-stop) that responds to Enter/Space to trigger `onStartEditing()`, mirroring how the existing `.clickable {}` modifier on `CodeFenceBlock` already gets this for free from Compose's semantics (`clickable` sets up focus + key-triggered activation automatically) — the diagram wrapper must not swallow that by, e.g., putting an opaque WebView surface with its own focus trap on top.
- **Screen-reader users need *some* text even without authored `accTitle`/`accDescr`.** Recommendation: when absent, fall back to an accessible label along the lines of "Mermaid diagram (tap to view source)" rather than nothing — cheap, avoids a silent/unlabeled image node, and is a static string SteleKit controls (unlike mermaid's own node-list fallback, which the mermaid team already flagged as "meaningless" [mermaid-js/mermaid#5632](https://github.com/mermaid-js/mermaid/issues/5632)).

## 4. Error / edge-case UX

- **Empty mermaid block** (` ```mermaid\n``` `): should render as the plain raw fallback (an empty code block), not attempt to invoke the renderer at all — cheapest and matches "unsupported/failed → raw fallback" path already required by the spec (Acceptance Criterion 2). No product researched treats an empty diagram source as a distinct state; it's just a degenerate case of "nothing to render."
- **Syntax error**: mermaid.js's own default behavior (versions > 8.6.0) is to render a visible red "Syntax error in text" box with a mermaid-version footer directly in place of the diagram [mkdocs-mermaid2 troubleshooting](https://mkdocs-mermaid2.readthedocs.io/en/latest/troubleshooting/), [VS Code markdown-pdf#337](https://github.com/yzane/vscode-markdown-pdf/issues/337). **This is the wrong default for SteleKit** — the requirements doc (Acceptance Criterion 2) explicitly calls for falling back to the existing raw-code-block rendering, which both GitHub and GitLab also do in practice rather than surfacing mermaid's own error chrome. Recommendation: catch the render failure at the SteleKit integration layer and suppress mermaid's built-in error box entirely, substituting `CodeFenceBlock`'s normal raw-text rendering — a big red error box inline in a note is disproportionate for what is, from the writer's point of view, an unfinished thought or a typo, and interrupts flow far more than silently falling back does. Do not add a *SteleKit-authored* error banner either, for the same reason — the raw code block *is* the graceful degradation; a user who wants to know why should see it fail to look like a diagram and can then read/fix their own source, exactly the same discovery loop as any other typo in a code fence.
- **Loading state**: WebView/JS-engine cold start is real (the requirements doc itself flags this as an open architectural question — no WebView infra exists in the repo yet). A brief render that takes noticeably longer than typical Compose recomposition needs *some* placeholder, or the block will appear to flicker between raw text and diagram, or appear blank. Recommendation: show the existing raw-code-block appearance as the default/initial state and swap to the rendered diagram only once render succeeds — this reuses `CodeFenceBlock`'s current rendering as a free "loading state" rather than inventing a spinner, and has the added benefit that a page full of mermaid blocks never flashes N spinners at once during initial page load. A spinner overlay is only worth adding if user testing shows the raw-text-then-diagram swap reads as janky rather than as a normal progressive-render.
- **Errors must never block continued writing on the same page.** This falls out of the fallback-to-raw-block behavior directly: because a failed render is indistinguishable in *editability* from a successful one (both are still just a fenced-code block a user can click into), there is no separate "error recovery" flow to design — the user keeps typing in adjacent blocks exactly as before. The one thing to explicitly verify in implementation/testing: a render failure inside the mermaid renderer must not throw/propagate up into the block tree's own recomposition or the page will actually break, not just degrade — this is a correctness/architecture concern more than a UX one, but the UX requirement ("must not block the page") is only true if that isolation holds.

## 5. Jobs-to-be-done

- **Functional**: "When I'm capturing a process or system relationship while writing notes, I want to see it as a diagram without leaving my outliner or exporting to a separate tool, so I can verify the diagram matches my mental model of the process before moving on." This is satisfied by render-in-place; it is *not* satisfied by a workflow that requires switching to a special "diagram mode" or a different pane, which is why GitHub/GitLab/Obsidian all keep it inline.
- **Emotional**: confidence and a short feedback loop — the user's underlying anxiety is "did I get the arrows/order right," and the value is in reducing the gap between typing mermaid syntax (which is not obviously correct by inspection, unlike prose) and seeing whether it's right. This is why render latency matters more here than for, say, LaTeX math (ADR-001's precedent) — a wrong diagram is often not obviously wrong until seen, so a slow or flaky render loop actively undermines the job. This also argues for *not* over-indexing on hiding failures: fallback-to-raw-text should still make it obvious to the user, by the diagram's simple absence, that something didn't render, without needing an alarming error state.
- **Social**: a page that will be shared, exported, or viewed by someone else (e.g., a Logseq-imported graph opened by a teammate, or a page exported to Markdown/HTML) reads as more polished with a live diagram than a fence full of `graph TD` syntax — the same "renders the same everywhere" parity argument the requirements doc opens with. This job is entirely served by the render itself; it doesn't add new UX surface beyond what's already scoped.

## Summary of concrete UX recommendations for the plan/ADR phase

1. Tap/click-to-edit must be a **focusable, keyboard-activatable** element (Enter/Space), not a mouse-only `clickable` — carry over whatever Compose gives `CodeFenceBlock` for free and verify the diagram wrapper (WebView/canvas) doesn't swallow focus.
2. Suppress mermaid.js's own built-in error-box rendering; on any render failure, fall through to the exact same `CodeFenceBlock`-style raw rendering used today — no new error UI, no red box, no toast.
3. Use the raw-code-block appearance as the *default/loading* state and swap to the diagram only on successful render, rather than adding a spinner — avoids flicker and reuses existing component.
4. Do not strip mermaid's `accTitle`/`accDescr`-derived `<title>`/`<desc>` SVG attributes when embedding the rendered SVG; when absent, inject a generic accessible label ("Mermaid diagram — tap to view source") rather than leaving the diagram unlabeled.
5. Keep the same visual chrome (rounded surface, background, language label) between `CodeFenceBlock` and its mermaid-rendering variant, so the feature reads as "a code block that also previews," consistent with the requirements doc's non-goal against inventing a new note type.
